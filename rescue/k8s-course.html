一台機器一個服務

第 1 課 / 共 13 課約 7 分鐘

為什麼當年一台機器只敢跑一個服務——一切的起點。

讀完這課你會

  • 用「會打架」解釋為什麼一台機器只跑一個服務
  • 說出當年上線一個服務為什麼要等兩個月

第一代・實體機

買一台機器，只跑一個服務

以前要上線一個新服務，流程是：填採購單 → 等機器送到 → 搬進機房 → 裝作業系統 → 裝環境 → 部署。前後兩個月跑不掉。

那為什麼不兩個服務擠一台？因為它們會打架——一個要舊版 Java、一個要新版，裝上去互相蓋掉；而且一個寫爆記憶體，另一個跟著陪葬。

重點整理

  • 兩個服務要的環境會互相蓋掉、資源會互搶，所以一台只跑一個。
  • 機器效能大部分閒著，要多一個服務就再買一台、再等兩個月。

虛擬機

第 2 課 / 共 13 課約 7 分鐘

Hypervisor 把一台切成好幾台，解決了浪費，留下了「肥」。

讀完這課你會

  • 說出 Hypervisor 在做什麼
  • 講出虛擬機解決了什麼、代價是什麼

第二代・虛擬機

一台機器，假裝成好幾台

中間多墊一層軟體（叫 Hypervisor，虛擬機管理程式），它把一台實體機的 CPU、記憶體、硬碟切成好幾份，每一份看起來就像一台完整的電腦，可以各自裝自己的作業系統。

解決了什麼
  • 一台機器的效能終於用得完。
  • 開一台新的是幾分鐘，不是兩個月。
  • 隔開了，一台炸掉不拖累別台。
還沒解決的
  • 每台都背一整套作業系統，又肥又慢，開機要一分鐘。
  • 裡面的環境還是靠人一個一個裝，換一台就可能裝得不一樣。
  • 所以「在我電腦上跑得起來」還是天天發生。

重點整理

  • Hypervisor 把一台實體機切成好幾台「看起來完整」的電腦。
  • 解決了浪費和等待：開一台變幾分鐘、效能用得完、彼此隔開。
  • 代價：每台都背一整套作業系統（Guest OS），肥、慢、環境還是靠人裝。

容器

第 3 課 / 共 13 課約 9 分鐘

共用作業系統這一步，換來輕、快、到處一樣。

讀完這課你會

  • 一句話說出容器和虛擬機唯一的差別
  • 解釋為什麼金融業有些場景仍用虛擬機

第三代・容器

不要整套作業系統，共用就好

回頭想一下：三台虛擬機的作業系統其實都是同一套 Linux，只是各裝一份。那能不能大家共用底下那一套，上面只放各自的程式和環境？

可以。Linux 本來就內建兩個機制：一個讓每個容器只看得到屬於自己的東西（看不到別人的檔案和程序），一個限制它最多能吃多少 CPU 和記憶體。容器就是把這兩個開關打開而已。

實體機虛擬機容器
開一個要多久數週～數月數分鐘1 秒內
佔多大一整台機器2–10 GB30–300 MB
一台機器塞得下1 個服務5–20 台數十～上百個
作業系統自己一套每台各一套大家共用一套
隔離程度最徹底很徹底夠用，但底下那套作業系統是共用的

這三代不是互相取代。現在最常見的組合是：實體機上跑虛擬機，虛擬機裡面跑容器。

「隔離程度」那一列在講什麼

這一列最容易被跳過，但它是金融業還在用虛擬機的唯一理由。差別在於：兩邊之間隔的那道牆，是真牆還是紙牆。

重點整理

  • 唯一的差別：作業系統是各背一套，還是共用一套。
  • 少背一套系統：體積幾 GB → 幾十 MB、啟動一分鐘 → 一秒內。
  • 隔離是「牆的厚度」問題：虛擬機隔兩道（切得徹底），容器共用一道；法遵要求硬隔離時只能用虛擬機。
  • 三代不互相取代：實體機上跑虛擬機、虛擬機裡跑容器是常態。

Docker

第 4 課 / 共 13 課約 9 分鐘

食譜、成品、跑起來的那一份——三個詞講完 Docker。

讀完這課你會

  • 分清 Dockerfile／映像檔／容器三個東西
  • 解釋容器為什麼治好「在我電腦上跑得起來」

DOCKER

只有三個東西

Dockerfile一張食譜。先放哪個系統、再裝什麼、程式擺哪、開機跑哪一行。一個純文字檔。
映像檔（Image）照食譜做出來的成品，一包不能再改的檔案。做好就不會再變，誰拿到都一樣。
容器（Container）把映像檔拿去跑，跑起來那一份就叫容器。同一包可以同時跑很多份。

DOCKER 解決的痛

「在我電腦上跑得起來」治好了

因為搬過去的不只是程式碼，而是連環境一起打包。測試機裝的是哪版 Java 已經不重要了，容器裡面自己有。

解決了什麼
  • 不用再背一整套作業系統，輕、快、密度高。
  • 環境跟程式一起打包，到處跑起來都一樣。
  • 環境變成一個文字檔，可以進版控、可以審查。
還沒解決的 → 這就是 K8s 要接手的
  • 跑一個容器很爽。三百個呢？誰決定哪個放哪一台？
  • 容器掛了誰去重開？機器整台掛了呢？
  • 容器換位子後位址就變了，別人怎麼找到它？
  • 要換新版本，怎麼換到一半不會斷線？

重點整理

  • Dockerfile 是食譜、映像檔（image）是不會再變的成品、容器是跑起來的那一份。
  • 映像檔倉庫（registry）是共用的架子：推上去、別台拉下來，每台拿到同一包。
  • 連環境一起打包，所以「在我電腦上跑得起來」治好了。
  • 跑一個容器很爽；三百個誰管？——這就是下一課的主角。

為什麼需要 Kubernetes

第 5 課 / 共 13 課約 6 分鐘

容器多到管不動之後：一個一直在比對的管家。

讀完這課你會

  • 說出 K8s 的一句話本質：比對單子與現況的管家
  • 分清「宣告式」和「一步一步下指令」的差別

一句話本質

一個一直在比對的管家

上一課結尾那四個「還沒解決的」問題——放哪台、誰重開、怎麼找、怎麼換版本——共同點是：都需要有人一直盯著、一直做決定。Kubernetes（常簡寫 K8s，因為 K 和 s 中間有 8 個字母）就是那個盯著的人。

它的運作方式只有一句話：你交一張「我要什麼」的單子，它每分每秒比對現況跟單子一不一樣，不一樣就自己補到一樣。

這種「只講結果，不講步驟」的做法，正式名稱叫宣告式（declarative）。相對的是傳統做法：寫一堆「如果掛了就重開」「先停 A 再起 B」的腳本，一步一步下指令。

你負責「說要什麼」，K8s 負責「讓現況一直是那樣」

「單子交給誰」「誰在比對」「補的動作誰做」——這些角色接下來三課會一個一個拆開。這一課只要記住這個迴圈。

重點整理

  • K8s 的核心是一個沒有停過的迴圈：比對「單子」和「現況」，不一樣就補到一樣。
  • 你只寫「我要 3 份」，不寫「掛了要重開」的腳本——這叫宣告式（declarative）。
  • 掛掉一份，它自己補一份回來，你不用半夜起床。

Pod 與 Node

第 6 課 / 共 13 課約 10 分鐘

派工的最小單位，和它住的那台機器。

讀完這課你會

  • 說出 Pod 和容器的關係、Node 的組成公式
  • 知道一台 Node 通常跑幾個 Pod、kubelet 為什麼存在

第 1 層・最小的

容器

就是第二部分講的那個，你已經懂了。K8s 沒有改變容器是什麼——它只是決定「什麼時候、在哪一台、起幾個」。

第 2 層・往外一層

Pod：一組綁在一起的容器

Pod 是一組永遠綁在一起的容器：同一個網路位址、同一批磁碟、一定在同一台機器上、一起生一起死。

九成情況下，一個 Pod 裡面就是一個容器。那為什麼還要多包這一層？因為那一成的情況：主程式旁邊要擺一個貼身小幫手（正式叫 sidecar，邊車容器——收日誌的、處理加密連線的），這兩個要能用 localhost 互打，所以不能分開放。Pod 就是那個「綁在一起」的盒子。

你說「我要 3 份」，指的是 3 個 Pod，不是 3 個容器

第 3 層・再往外

Node：Pod 住的那台機器

「我可以用 Hypervisor 開一台虛擬機，在那個作業系統裡裝 Docker，然後跑好幾個容器嗎？」

可以，而且這就是最常見的做法。你講的那台虛擬機，只要再多裝一個小東西，它就變成一個 Node。

那個小東西叫 kubelet——一個一直開著、不會關掉的小程式，當這台機器的聯絡窗口：聽大腦（Control Plane，控制平面）的指令、在自己這台把容器叫起來或關掉、然後回報「我這邊還活著、還剩多少資源」。

一台機器 ＋ 容器執行環境（containerd）＋ kubelet ＝ 一個 Node

「可是 Docker 本來就能啟動很多容器啊，為什麼還要裝 kubelet？一定要變成 Node 嗎？」

不一定。一台裝了 Docker、沒有 kubelet 的機器，可以跑得好好的。它只是不在 K8s 叢集裡而已。你甚至可以混著用：三台加入叢集，另外一台獨立跑 Docker。

kubelet 存在的理由，不是「啟動容器」——那件事容器執行環境（container runtime）本來就會做。它存在的理由是回答「誰來決定要起什麼容器」：

要不要裝 kubelet ＝ 這台機器要不要交給大腦管

「一台虛擬機開起來，通常只會跑一個容器嗎？」

不是，通常是幾十個。這點要特別更正——如果一台機器只跑一個容器，那容器就白用了，跟第一代「一台機器一個服務」沒兩樣。

容器的整個價值就在密度：它輕，所以一台塞得下很多個。K8s 預設一台 Node 最多 110 個 Pod（可以調），實際上跑二三十個很常見。

順帶一提：kubelet 自己也不會起容器，它是叫底下的容器執行環境去起。而 K8s 現在預設用的執行環境已經不是完整的 Docker Engine，是 containerd（Docker 本來就拿它當底層）。你在文件上看到「K8s 移除 dockershim」（v1.24，2022 年）講的就是這件事——不影響你，因為 Docker build 出來的映像檔照樣能跑。

重點整理

  • Pod 是派工單位：通常裡面就一個容器，偶爾多一個貼身小幫手（sidecar）。
  • 一台機器＋容器執行環境（containerd）＋kubelet ＝ 一個 Node；kubelet 是聽大腦指令的聯絡窗口。
  • 一台 Node 跑幾十個 Pod 是常態（預設上限 110 個）；一台只跑一個就白用容器了。
  • Pod 落在哪台不用你管，重開一次就可能換位子。

叢集與大腦

第 7 課 / 共 13 課約 10 分鐘

worker 跑你的程式，master 跑大腦——四個角色各自是一個 Pod。

讀完這課你會

  • 分清 master／worker 的分工
  • 講出大腦四個角色各管什麼、etcd 為什麼是命根

第 4 層・再往外

叢集：一堆 Node 湊起來，分兩種角色

  • worker node——跑你的 Pod 的機器。平常口語講「Node」，八成指這種。
  • master node——跑大腦（Control Plane）的機器。它不跑你的程式。

名詞注意：Kubernetes 官方後來把 master 改稱 control plane node，但業界口語還是常講 master node，兩個是同一件事。

第 5 層・最外面

大腦（Control Plane）：四個角色，各自是一個 Pod

「一個 master node 裡面有幾個 pod？」

大約四個。因為那四個角色各自就是一個容器、包在一個 Pod 裡，跑在 master node 上。「大腦」——正式名稱控制平面（Control Plane），舊稱 master——不是一支程式，是這四個 Pod 湊起來的。

四個角色各做什麼

櫃檯（kube-apiserver）所有指令的唯一入口。你打 kubectl 就是打它，其他三個角色也只能透過它講話。它自己不做決定。
檔案室（etcd）把所有單子和所有現況存起來。K8s 的一切狀態都在這裡。
排班的（kube-scheduler）有新 Pod 要跑，看哪台 worker 還有空的 CPU 和記憶體，決定放哪台。決定完就沒它的事，實際起容器是 kubelet。
巡邏的（kube-controller-manager）一直在跑「單子說 3 份，現在幾份？不夠就補」的迴圈。K8s 會自我修復，靠的就是它。

共通的部分

每一台機器都有的三樣東西

「你說 master 上只有那四個角色，那 master 上也有 kubelet 嗎？」

有。每一台機器都有 kubelet，不分 master 還是 worker。這正是為什麼 master 上那四個角色能用 Pod 的形式跑——是那台自己的 kubelet 在顧它們。

更精確地說，每台機器都有三樣共通的東西，master 只是在這三樣之上，額外多跑那四個角色：

用託管的 K8s（GKE、EKS）時，左邊那整個框你看不到也連不進去，雲端商幫你顧。你只看得到右邊。

大腦裡面那個資料庫

etcd 是什麼

它就是一個資料庫，專門存「設定」這種小東西，不存業務資料。名字來自 Linux 放設定檔的那個資料夾 /etc，後面加一個 d 代表分散式——「分散在好幾台上的設定檔資料夾」，這就是它的全部。

它跟一般資料庫的差別只有一個：它可以有好幾份，而且保證每一份內容一樣。做法是每一筆寫入都要超過半數的份數點頭才算數。

K8s 用它存兩種東西：

  • 所有的單子——你要 3 份、用哪個映像檔、Service 叫什麼名字。
  • 所有的現況——現在哪些 Pod 在跑、跑在哪一台、健不健康。

K8s 的一切狀態都在 etcd 裡 ⟹ 備份 etcd ＝ 備份整個叢集

反過來說，etcd 沒了，叢集就沒了。機器都還在、容器可能還在跑，但大腦完全失憶，不知道誰是誰、也不知道該有幾份。

上一份講分散式鎖的資料裡提過 etcd，就是這個東西。它被選中的理由是「換主機時不會弄丟已經答應的事」，這點 Redis 做不到。

重點整理

  • worker node 跑你的 Pod；master node 跑大腦（Control Plane），不跑你的程式。
  • 四個角色：櫃檯（kube-apiserver）、檔案室（etcd）、排班的（kube-scheduler）、巡邏的（kube-controller-manager）——各自是一個 Pod。
  • 每台機器（不分 master/worker）都有三樣：containerd、kubelet、kube-proxy。
  • etcd 存所有單子和現況：備份 etcd ＝ 備份整個叢集。

Deployment：下單

第 8 課 / 共 13 課約 10 分鐘

用一張 YAML 單子講「我要幾份」，換版本不停機。

讀完這課你會

  • 分清 Dockerfile 和 Deployment 兩張單子
  • 說出 requests／limits 的差別與滾動更新的原理

操作一・下單

Deployment：你怎麼跟大腦（Control Plane）講話

你交一張單子（正式叫資源定義檔，就是一個 YAML 檔）：「訂單服務我要 3 份，用 order-svc:1.4 這個映像檔，每份最多吃 1 GB 記憶體。」之後巡邏的（kube-controller-manager）就每分每秒在比對，不一樣就自己補到一樣。

「最多吃 1 GB」其實有兩種寫法

單子上的資源可以寫兩個數字，意思完全不同：

保留量（requests）上限（limits）
意思「至少幫我留這麼多」「絕對不准超過」
誰在看它排班的（kube-scheduler）——照這個數字算哪台機器塞得下那台機器本身——超過就處理你
可以超過嗎可以。機器有空就借你用不行
超過會怎樣不會怎樣，這本來就允許記憶體超過 → 容器直接被殺掉重開
CPU 超過 → 不殺，但被拖慢

所以有人把保留量（requests）叫「軟的那個」、上限（limits）叫「硬的那個」——差別就是「超過會不會被處理」。

兩個都不寫也能跑，但那台機器上的容器會互相搶資源，一個寫爆記憶體全部跟著倒——就是第 1 課講的「一台機器塞兩個服務會打架」那件事又回來了。

實務細節：巡邏的其實隔著一層叫 ReplicaSet 的中間人在數份數——Deployment 管「換版本」、ReplicaSet 管「維持份數」。下指令看狀態時會看到它，知道它是誰就好。

Dockerfile 和 Deployment 差在哪

DockerfileDeployment
給誰看Docker（打包工具）Kubernetes 的大腦（Control Plane）
什麼時候用打包的時候上線的時候
在講什麼這一包裡面要有什麼：打底用的作業系統、Java、你的程式、開機跑哪一行這一包要跑幾份、每份能吃多少資源、怎麼換版本
產出一個映像檔一群跑著的 Pod
多久改一次程式改了才要重建想調份數、換版本就改
知道對方存在嗎不知道，也不需要知道只寫得出映像檔的名字

重點：Dockerfile 完全不知道 K8s 存在。同一個映像檔可以 docker run、可以丟給 Cloud Run、也可以給 K8s。所以你現在學 Docker，一點都不會浪費。

換版本不用停機

重點整理

  • Dockerfile 管打包（這包裡有什麼）；Deployment 管上線（跑幾份、怎麼換版本）。兩者互不相識。
  • requests（保留量）＝至少留這麼多、可以超；limits（上限）＝絕不准超，記憶體超了容器被殺掉重開。
  • 滾動更新（rolling update）：一次只換一份，全程都有人服務；舊映像檔還在倉庫，隨時退回（rollback）。

Service：找路

第 9 課 / 共 13 課約 9 分鐘

Pod 一直換位子，靠一個永遠不變的名字找到它。

讀完這課你會

  • 解釋 Service 為什麼存在、本質是什麼
  • 說出「有幾組 Pod 就有幾個 Service」

操作二・找路

Service：Pod 一直換位子，怎麼找得到

Pod 隨時會重開、換位子，一換位址就變了。所以呼叫方不去找 Pod，只認一個名字 http://backend，Service 負責把這個名字翻成「現在還活著的後端 Pod 有哪幾個」。

先把層次擺正：它不是堆疊裡的一層樓

那它本質是什麼？一條發到每台機器的規則

Service 不是機器、也不是跑著的東西，它是一筆存在檔案室（etcd）裡的規則。大腦把這筆規則發到每一台 worker node，由那台的 kube-proxy 寫進機器的網路轉發表。所以請求根本沒經過任何「Service 伺服器」。

有幾組 Pod，就有幾個 Service

前端那組有自己的 frontend，後端那組有自己的 backend。它們是兩筆各自獨立的規則，不是同一個中繼站被用兩次——所以請求不會繞回去，是一路往前走的。

重點整理

  • Pod 的位址一直變，所以呼叫方只認名字；Service 就是那個永遠不變的名字。
  • 它不是機器也不是 Pod，是一筆存在 etcd 的規則，由每台機器的 kube-proxy 寫進轉發表——請求不經過任何中間伺服器。
  • 「東西住在哪」和「請求怎麼走」是兩個垂直的軸；Service 只在第二個軸上。
  • 有幾組 Pod 就有幾個 Service，前端後端各自一個。

對外入口

第 10 課 / 共 13 課約 9 分鐘

Ingress、負載平衡器、nginx——誰是單子、誰在跑。

讀完這課你會

  • 分清 Ingress（單子）和 Ingress Controller（執行者）
  • 解釋託管環境為什麼常常沒有 nginx

操作三・讓外面進得來

對外入口：router？nginx？Ingress？

Service 的名字預設只在叢集裡面有效，外面的人叫不到。所以前面要擺一個對外入口。而這裡有三個常被混在一起講的東西，拆開就清楚了：

負載平衡器雲端給你的一個對外 IP，把流量丟進叢集。這是基礎設施，GCP／AWS 提供。
Ingress一張規則表，跟 Service 一樣只是存在檔案室的一筆設定。它本身不轉發任何東西。
Ingress Controller真正在跑、真正在轉發的那個程式，跑在一個 Pod 裡。它通常就是一個 nginx。

回答你的三個問題

  • 「是 nginx 嗎？」——常常是，但不一定。最多人用的那一套裡面就是 nginx，但也可以換成 Envoy、Traefik，或雲端自己的負載平衡器。
  • 「是 router 嗎？」——概念上是，但 router 在網路領域專指看 IP 的那種路由器。這裡的東西看得懂網址路徑（/api 跟 /login 可以送去不同地方），業界比較常說反向代理——意思是它代替後面那些服務出面接客，外面的人只看得到它。
  • 「為什麼不直接讓 Service 對外？」——可以，Service 有一種型別會跟雲端要一個對外 IP。但一個 Service 一個 IP，十個服務就十個 IP，又貴又難管。對外入口的價值就是：一個 IP，依網址分給很多 Service。

順帶一提：Ingress 的下一代規格叫 Gateway API，概念一樣（一張單子＋一個執行者），只是表格式更細。新專案的文件上會越來越常看到。

換成雲端託管的服務，nginx 就不見了

「常常看到架構圖上只有一個負載平衡器，沒有 nginx，那是怎麼回事？」

因為那種架構沒有用 K8s。上面那個 nginx 存在的理由，是「K8s 的 Ingress 只是一張規則表，K8s 自己不提供執行者」——所以你得自己養一個。

雲端託管的負載平衡器本身就是執行者。它的設定裡有一份路徑對照表，雲端商託管的轉發層負責照它執行。單子和執行者被包在同一個產品裡了。

自己架 K8s託管的負載平衡器 + 託管容器服務
規則表（單子）Ingress負載平衡器的路徑對照表
執行者你自己養的 nginx Pod雲端商託管，你看不到
找到後端Service負載平衡器的後端設定
送網頁、圖片這類固定檔案nginx，或一個 Pod負載平衡器直接從雲端硬碟讀檔送出
要顧幾個容器你的服務 + 1 個 nginx只有你的服務

順便補正上面那張圖的一個不精準之處：我把負載平衡器畫成「只給一個對外 IP」、把「看得懂網址路徑」全歸給 nginx。那只對「只認 IP 的那種」負載平衡器成立。

負載平衡器分兩種：只認得機器位址、看不懂網址的（業界說第四層），和看得懂網址的（第七層，也叫應用層）。雲端的第七層負載平衡器自己就會依路徑分流——這種情況下根本不需要再擺一個 nginx。

這也是為什麼 GKE 上有兩種選擇：用 nginx 那一套（起一個 nginx Pod），或用 GKE 自己的（不起 Pod，直接叫雲端開一個第七層負載平衡器）。在 GCP 上通常選後者。

把 nginx 拿掉的實際好處

nginx 在這種架構裡傳統上做兩件事：依路徑分流，和送靜態檔案——「靜態檔案」就是做好之後不會再變的那些檔：網頁、樣式、圖片。這兩件事分別交給負載平衡器的路徑規則、和「負載平衡器直接讀雲端硬碟」之後，nginx 就沒事可做了。

好處很實際：少一個容器要顧、少一份映像檔要建、少一個東西會掛、少一份資安掃描要跑。

什麼情況需要把 nginx 留著

  • 要做負載平衡器做不到的事——改寫請求內容、複雜的網址改寫規則、或是在最前面那一關就先把常看的內容存起來、下次直接回。
  • 不想被綁在單一雲——設定寫在自己的 nginx 裡，換雲時搬得動。
  • 前端不只是那些固定檔案——需要在伺服器端先算好畫面再送出，那就得有一個真的在跑的前端程式。

三個都不成立的話，就不需要。

串起來

一個請求實際走哪條路

路徑分兩種，看你的前端是哪一款。判斷方式：「打 API 的那一行程式，是在誰的機器上執行的」。

重點整理

  • Service 的名字只在叢集內有效；對外要靠入口依網址分流。
  • Ingress 是規則表（不會跑）；Ingress Controller 是真的在轉發的 Pod，通常就是 nginx。
  • 負載平衡器分兩種：只認位址的（L4）和看得懂網址的（L7）；雲端 L7 負載平衡器自己就是執行者，所以託管環境常常不需要 nginx。
  • 判斷請求路徑：看「打 API 的那行程式在誰的機器上執行」。

單子與執行者

第 11 課 / 共 13 課約 5 分鐘

一個貫穿全部的模式：看懂這個，前面全部串起來。

讀完這課你會

  • 用「單子＋執行者」一句話統整 K8s 的設計

核心設計

每樣東西都是「一張單子（YAML）」加「一個執行者」

你已經看過三次同樣的形狀，只是我沒有點破：

你寫的每一份設定都只是「你要什麼」
K8s 負責讓某個真的在跑的東西去符合它

這就是「你只講結果，不講步驟」的完整意思。也是為什麼「Service 本質是 Node 還是 Pod」這個問題會問不出答案——它是左欄的東西，Node 和 Pod 是右欄的東西，本來就不同類。

重點整理

  • Deployment／Service／Ingress 都只是存在 etcd 的單子；Pod／轉發表／nginx 才是執行者。
  • 你永遠只寫單子，K8s 負責讓執行者符合單子。
  • 「Service 是 Node 還是 Pod」問不出答案，因為它是單子欄的東西——跟執行者不同類。

壞掉的時候

第 12 課 / 共 13 課約 9 分鐘

補位和選舉是兩回事——誰掛了誰救、誰救不了。

讀完這課你會

  • 分清補位和選舉兩種機制
  • 說出 master 死一台之後會發生什麼、誰負責補

兩種完全不同的機制

補位 vs 選舉

補位
  • 數量不夠了，生一個新的出來。
  • 前提：要有一個「更上層的東西」來生。
  • Pod 掛了、worker node 掛了，都是這種。
選舉
  • 數量本來就固定，不會變多。
  • 只是決定「剩下這群裡面誰做主」。
  • master node 掛了是這種。
誰掛了怎麼發現怎麼處理是哪一種
一個 Pod 巡邏的（kube-controller-manager）發現「單子說 3 份，現在 2 份」 直接開一個新的（會換位子、換位址） 補位
一台 worker node 它的 kubelet 不回報了（約 40 秒沒消息就標記不健康） 再等幾分鐘確認真的死了，把上面的 Pod 排到其他還活著的機器 補位
master 上的一個 Pod 那台自己的 kubelet 發現 它自己就重開了，機器還在，很快回來；期間工作由別台 master 接手 補位
一台 master node 其他 master 發現它沒回應 檔案室（etcd）重選一個主；排班和巡邏由待命的接手。但台數不會變回來 選舉

你問的那題

「死了一個補上一個，所以只剩兩個？」

「原本三個，死了一個，補上一個，所以現在只剩兩個？那下次掛掉呢？」

master node 不會自動補位。3 台死 1 台，就是剩 2 台，不會有第 4 台自己長出來。

原因很簡單：worker 上的 Pod 掛了，是大腦（Control Plane）去補的。那 master 掛了誰去補？沒有更上層的東西了——大腦自己就是壞掉的那個。

master 掛掉時，那兩場選舉在選什麼

檔案室（etcd）選主
  • 3 台裡面要超過半數（2 台）活著才寫得進去。
  • 主的那台掛了，剩下兩台投票選一個新的主。
  • 這就是為什麼要奇數台。
排班的、巡邏的搶標記（leader election）
  • 這兩個角色同一時間只能有一個在做事——不然兩個同時補 Pod，會補出雙份。
  • 3 台上面都有跑，但要先搶到一個標記，搶到的才幹活。
  • 搶到的那台掛了，剩下的重新搶。

「同一時間只能有一個在做事」＝ 這就是分散式鎖

而 K8s 這把鎖是用檔案室（etcd）做的，不是 Redis。理由是 etcd 換主機不會弄丟已經答應的東西，Redis 會。

那 master 全掛了會怎樣？

已經在跑的 Pod 會繼續跑。因為每台 worker 上的 kubelet 是自主的，它照著最後一次收到的指令繼續維持，使用者不會馬上感覺到。

但整個叢集會凍結：不能改任何東西、掛掉的 Pod 不會被補、換版本做不了、自動增減份數停擺。不是立刻全停，是「還在動但沒人管」——這反而更危險，因為不會有人立刻發現。

雲端託管的 K8s（GKE、EKS）是雲端商幫你顧 master，你看不到也不用管。這是託管版最大的價值。

重點整理

  • Pod 掛、worker 掛 → 補位（大腦生一個新的）；master 掛 → 選舉（台數不會自己變回來）。
  • master 要奇數台：3 台可死 1 台，2 台死 1 台就過不了半數。
  • 補回 master 是人的工作——這就是「顧 K8s 是一份全職工作」的原因。
  • master 全掛：已在跑的 Pod 照跑，但叢集凍結——還在動但沒人管，反而更危險。

要不要用 K8s

第 13 課 / 共 13 課約 7 分鐘

分水嶺怎麼判斷，以及大多數團隊實際落腳的中間選項。

讀完這課你會

  • 用一個問題判斷該不該上 K8s
  • 知道託管服務幫你做掉哪些事

分水嶺

什麼時候該從 Docker 轉 K8s

最根本的那條線只有一句話：你需不需要「跨機器決定東西放哪台」。

Docker 管的是這一台機器上的容器，Docker Compose 也一樣。一旦有第二台機器要一起服務，就沒有東西幫你決定新容器放哪一台——那個缺口就是 K8s 補的。

該轉的訊號
  • 機器超過一台。最根本的一條。
  • 整台機器掛了要有人接。Docker 能重開容器，機器整台死掉它救不了。
  • 換版本不能斷線。
  • 流量大要自動多開幾份，小了要縮回去。
  • 服務多到互相找不到對方，位址又一直變。
先別轉的訊號
  • 就一台機器，流量穩定 → Docker Compose 就夠了。
  • 服務只有一到三支，而且不常改。
  • 半夜停 10 分鐘換版本，沒人會抗議。
  • 沒有人要顧它。
  • 「因為大家都在用」——這不是理由。

中間那一格

「託管的服務」到底幫你做掉什麼

判斷流程裡「有人真的會顧它嗎 → 否」那一格，指的是 Cloud Run、ECS Fargate、App Runner 這類服務。它們的共同點是：你只交出一個映像檔，其他全部有人幫你做。

這件事自己架 K8s用託管的
決定放哪台機器排班的 kube-scheduler（你要顧它）雲端商，你看不到
掛了補上巡邏的 kube-controller-manager（你要顧它）同上
master 掛了補台你的工作沒有 master 這回事給你看
滾動更新寫在 Deployment 裡內建，換版本就是換一行
流量小的時候機器照樣開著照樣算錢可以縮到零，沒人用就不算錢
你要寫的東西Dockerfile ＋ 一疊 K8s 設定只有 Dockerfile

代價是彈性變小：託管服務只給你幾個能調的選項（要幾份、每份多少記憶體、等多久算失敗），K8s 那些細緻的擺放規則你調不到。多數團隊願意換。

同一個映像檔，三種地方都能跑
docker run／託管服務／K8s

這是最值得帶走的一句：第 1〜4 課（容器和 Docker）不管最後選哪一條路都要會；第 5〜12 課是背景知識——知道託管服務底下在做什麼、看文件時詞彙對得起來就夠了。

重點整理

  • 分水嶺一句話：需不需要「跨機器決定東西放哪台」。不需要就別上。
  • 一台機器、流量穩定 → Docker Compose 就夠；需要但沒人顧 → 用託管服務（Cloud Run、ECS Fargate）。
  • 同一個映像檔在 docker run／託管服務／K8s 都能跑——Docker 學了不會白學。
