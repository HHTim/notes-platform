讀完這課你會

  • 依任務範圍選對互動方式：自動完成、行內聊天還是側邊欄聊天
  • 用目標、上下文、限制與驗收方式寫出一段能交差的提示
  • 把生成結果當成待驗證的草稿，用差異與測試把關

先把角色擺對

它是副駕駛，你才是機長

原筆記的心法很直接：把它當成打字快、看過很多範例，但不一定真的懂你需求的夥伴。它能補程式碼、解釋邏輯、提修改、產測試，但最後做決定、扛品質責任的還是你。

它產出的不是答案，是「待驗證的候選方案」。它可能用出根本不存在的介面、忽略邊界條件，或寫出跑得動卻不安全的程式碼。這種看起來合理但其實不可靠的輸出，業界叫幻覺（hallucination，模型憑感覺編出來的內容）。

把它當成剛進團隊、技術底子不錯、但還不熟產品規則的工程師。

接受結果前至少問三件事：它符合需求嗎？測過了嗎？會不會洩漏資料或開出安全漏洞？

三種日常互動

範圍越小，用越輕的介面

方式適合什麼使用重點
自動完成（在編輯器裡直接浮出建議）續寫函式、重複樣板、短的轉換先把命名、型別、函式骨架跟註解寫好
行內聊天（在程式碼行間叫出對話框）解釋或修改目前選取的一小段限制修改範圍，套用前先看差異
聊天檢視（側邊欄的對話視窗）討論架構、追跨檔問題、規劃較大的任務明確附上相關檔案與專案限制
快速聊天（浮動的小視窗）不離開目前畫面的短問答適合查語法，不適合複雜的跨檔工作

判斷原則很簡單：牽涉的檔案、規則跟決策越多，就越該換到承載得了較多上下文的介面。

快捷鍵方面，行內聊天是 Ctrl + I（macOS 是 Cmd + I）、聊天檢視是 Ctrl + Alt + I（macOS 是 Ctrl + Cmd + I）；快速聊天現行的預設鍵是 Ctrl + Shift + Alt + L（macOS 是 Shift + Option + Cmd + L）出處。

快捷鍵會因為作業系統、編輯器版本、鍵盤配置與個人設定而不同，實際請以命令選擇區與鍵盤快速鍵設定為準。

讓建議更貼近需求

命名、註解與上下文，就是你的方向盤

自動完成是看游標附近的程式碼在猜下一步。與其只寫「處理資料」，不如先交代輸入、輸出跟限制。精準的函式名稱、型別與註解，本身就是提示。

// 輸入未排序的訂單，排除已取消的項目，
// 依建立時間由新到舊回傳，不修改原本的陣列。
function listActiveOrders(orders) {
  // 讓它提出候選實作，再由你檢查
}

這種先描述意圖、再讓它生成實作的做法，原筆記稱為註解導向開發。要注意註解本身也可能寫錯，所以還是要拿需求、測試與實際資料交叉確認。

提示怎麼寫

一次一件、講具體、講簡短、附上下文

原筆記把有效提示的四個要點整理成一組口訣（四個要點的英文都是 S 開頭，它稱為 4S 原則）：

一次一件不要同時要求重構、換框架、補文件又部署。
講具體說明技術、範圍、輸入輸出、錯誤處理，以及不准動的地方。
講簡短刪掉客套跟重複，只留真正影響答案的限制。
附上下文把相關程式碼、錯誤訊息、規格與既有測試一起給它。

有效提示 ＝ 目標 ＋ 必要上下文 ＋ 限制 ＋ 驗收方式

例如不要只說「幫我寫測試」，改成：

替 UserAuth 的 login 方法補單元測試，測試框架用 Jest。
涵蓋成功、密碼錯誤、帳號不存在、帳號被鎖定四種情境。
沿用現有測試的假物件寫法，不要動正式程式碼。
完成後列出還沒涵蓋到的風險。

把驗收方式寫進提示，等於先替交付品準備好檢查表，通常比堆一串形容詞有效得多。

指定動作與材料

斜線決定要做什麼，井字號決定看哪些資料

斜線命令是工作捷徑，現行常用的有 /explain（解釋）、/fix（修錯）、/tests（產測試）、/doc（寫註解文件）、/new（開新骨架）、/plan（先出實作計畫）。現行的官方功能清單已經沒有 /optimize，改列了 /plan出處；效能的事直接寫進提示描述即可。

用了指令也不代表需求就完整。即使下了產測試的命令，還是要指定測試框架、測試範圍與邊界條件。

井字號用來指定它該看哪些材料。現行的寫法有一部分改了：整個專案搜尋是 #search/codebase，問題面板是 #read/problems，終端機內容是 #read/terminalSelection 與 #read/terminalLastCommand出處；#selection、#file、#changes 則維持原樣。

想給的資料現行引用方式典型用途
選取的程式碼#selection解釋、局部重構、補測試
指定檔案或資料夾#file、#folder，或直接把檔案拖進對話框對照介面、規格或既有實作
終端機輸出#read/terminalSelection、#read/terminalLastCommand分析編譯與執行錯誤
問題清單#read/problems處理型別、語法與檢查工具的問題
整個專案#search/codebase追跨檔流程與既有慣例
版本控制的變更#changes審查這次改了什麼、寫提交訊息

上下文不是越多越好。把整個專案一股腦塞進去，就像把整座倉庫搬進會議室：重要線索反而更難找。只給完成任務真正需要的資料，並說明每份資料的用途。

實際工作流

生成、檢查、測試，再決定要不要用

  • 先縮小問題：指出檔案、函式、錯誤現象與預期結果。
  • 要它先說判斷依據或先提方案，不要急著讓它改一大片。
  • 看差異，特別留意被刪掉的驗證、權限與錯誤處理。
  • 跑格式檢查、靜態分析、單元測試與必要的整合測試。
  • 用邊界輸入驗證行為：空值、極端數字、重複資料、沒授權的請求。
  • 確認沒有把密碼、權杖、個資或公司機密貼進不該貼的地方。

要它產生提交訊息時，先整理並檢查已暫存的差異，免得它把無關的變更包成一段看起來很完整的描述。

安全底線

跑得動，不代表能上線

生成資料庫查詢語法、正規表示式或系統指令時特別要看：輸入有沒有驗證、查詢有沒有用參數化寫法、檔案操作的範圍有多大、有沒有不可逆的破壞性動作。不要因為語法看起來很專業就跳過審查。

遇到不熟的介面時，要它先講出自己的假設，再用專案鎖定的版本、型別檢查、測試或官方文件去驗證；不要讓另一段 AI 的回答變成唯一證據。

重點整理

  • 它產生的是候選方案，需求、品質與安全責任仍在你身上。
  • 小範圍的事用自動完成或行內聊天；跨檔與架構問題換到承載得了上下文的聊天介面。
  • 用「目標＋上下文＋限制＋驗收方式」寫提示，比堆形容詞有效。
  • 斜線命令指定要做什麼，井字號指定看哪些材料，兩者用途不同。
  • 接受修改前看差異，接受之後跑測試與安全檢查。
