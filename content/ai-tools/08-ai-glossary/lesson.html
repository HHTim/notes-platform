模型收到的兩種指示

使用者提示與系統提示

原筆記的例子很好懂：你跟 AI 說「我肚子疼」，它通常回一些沒營養的話；你想要它有個人設，最直接的辦法是把「你是我的女朋友」塞進你的提示裡。這招有效，但那句話其實不是你這次真正想說的內容，所以人們把人設抽出來，放進另一個地方。

使用者提示（User Prompt）你這一次真正要問的問題或要交辦的任務。
系統提示（System Prompt）工作守則：角色、個性、背景知識、語氣、行為限制與輸出要求。每次你送出訊息時，它會被一起送給模型。
系統提示：你是課程助教，用繁體中文回答，先說結論。
使用者提示：請比較代理人跟聊天機器人的差別。

不過提示寫得再完美，模型說到底還是在產生內容。你問問題，它最多給你答案、告訴你怎麼做，真正動手的還是你。要讀檔、查服務或改東西，就得靠代理人跟工具把文字上的意圖變成實際動作。

從回答到行動

代理人與它的工具

AI 代理人（AI Agent）是負責在使用者、模型跟工具之間協調的那支程式。原筆記形容得很傳神：它就是「負責在模型、工具跟使用者之間傳話的程式」。

它的工具（Agent Tool）則是一個個具體的能力，例如：

  • list_files：列出目錄內容。
  • read_file：讀取指定檔案。
  • web_browse：取得網頁資訊。

工作迴圈：理解任務 → 選工具 → 執行 → 看結果 → 決定下一步

這個迴圈會重複很多次，直到任務完成、碰到停止條件，或需要你補資訊、給授權為止。

AutoGPT 由 Toran Bruce Richards 在 2023 年 3 月 30 日發布，出處的說法是「最早讓一般人用得到、能展示 GPT-4 自主能力的應用之一」，而不是斷言它是第一個出處。

把工具呼叫變結構化

函式呼叫解決了什麼

早期的做法是在系統提示裡用自然語言描述工具，並要求模型照某個文字格式回答。問題在於模型本質上是機率模型，還是可能少個括號、拼錯工具名稱，讓代理人解析不了。原筆記說，很多代理人只好在發現格式不對時自動重試——既耗費用，又讓人覺得不可靠。

函式呼叫（Function Calling）就是為了這件事出現的：把工具的名稱、用途與參數整理成機器比較好驗證的結構，模型要用工具時，也產生結構化的呼叫要求。

{
  "name": "read_file",
  "description": "讀取指定的文字檔",
  "parameters": { "path": "string" }
}

它改善的是介面與格式，不代表模型挑的工具一定對，也不會自動給出工具權限。代理人仍然要驗參數、處理錯誤、控制可執行的範圍。

原筆記寫「各家大廠的介面定義都不一樣，而且很多開源模型還不支援，所以要寫跨模型通用的代理人挺麻煩的」。這是它當時的觀察；這幾年主流模型的支援度已經提高不少，MCP 出現後生態也在收斂，但各家的細節仍有差異，實作前還是要看你要用的那家怎麼定義。

兩個常被混在一起的名詞

一個管模型怎麼挑工具，一個管代理人怎麼接服務

概念溝通的是哪兩邊解決什麼問題
系統提示應用程式 ↔ 模型用自然語言設定角色、規則與行為
函式呼叫模型 ↔ 代理人結構化描述工具，以及模型提出呼叫的格式
MCP主機／用戶端 ↔ 外部伺服器找得到並用得到外部的工具、資源與提示模板

代理人可以先透過 MCP 跟伺服器拿到工具說明，再轉成模型支援的函式呼叫格式；模型提出呼叫之後，代理人再透過 MCP 請伺服器去執行。兩者可以合作，但不是同一件事。

MCP 伺服器提供工具資訊
        ↓
代理人轉成模型看得懂的工具定義
        ↓
模型產生一個函式呼叫
        ↓
代理人透過 MCP 請伺服器執行
        ↓
工具結果回到模型

MCP 在做什麼

把工具變成共用的服務

原筆記點出了 MCP 出現的動機：有些工具其實是通用的，例如「瀏覽網頁」，很多代理人都要。總不能在每個代理人裡都複製一份相同的程式碼。於是大家把工具變成一種服務、統一託管，讓所有代理人都來呼叫。

MCP 規定了伺服器跟用戶端怎麼溝通、伺服器要提供哪些共通介面（例如查詢有哪些工具、每個工具的說明、需要什麼參數與格式）。除了可執行的工具，伺服器也能直接提供資料（Resource）或提示模板（Prompt）。

伺服器可以跟代理人跑在同一台機器上、用標準輸入輸出溝通，也可以部署到網路上、透過 HTTP 溝通。這個方向跟現行規格一致——目前定義的兩種標準傳輸就是標準輸入輸出與 Streamable HTTP。

原筆記只講到伺服器提供給用戶端的三種能力。現行規格另有反方向的：取樣（伺服器請主機用模型生成內容）、Roots（伺服器問清楚可以在哪些路徑或網址範圍內作業）、Elicitation（伺服器中途向使用者要一項補充資訊）。其中取樣與 Roots 已在 2026-07-28 版標為淘汰，新的實作不該再採用，最快會在 2027-07-28 之後的版本移除。詳見 MCP 規格與淘汰功能清單。

還有一件原筆記特別強調、也很容易誤解的事：MCP 雖然是為了模型而訂的標準，本身卻跟模型沒有關係。它不管代理人用哪一顆模型，只負責幫代理人管理工具、資源跟提示模板。

需要時再翻資料

檢索增強生成怎麼運作

檢索增強生成（Retrieval-Augmented Generation，簡稱 RAG）像開卷考試：先把文件切成片段，轉成可以比較語意的向量，使用者提問時再找出相關片段交給模型回答。

文件 → 切割 → 轉成向量 → 存進向量資料庫
問題 → 語意檢索 → 相關片段 → 模型 → 回答

它的優點是能很快用上大量既有文件，也比較容易附上是從哪裡查到的；常見問題則是切得不好、找錯片段、該找到的沒找到，以及片段缺少前後文。

另一條路

先把資料整理成知識地圖

原筆記的另一篇提出一種對照做法：不要等提問時才去撈片段，而是先請模型把散落的資料整理成有章節、有連結、有索引的百科頁面，之後人可以直接讀，問答系統也可以拿來用。它用 Obsidian（一套以 Markdown 檔案與雙向連結為主的筆記軟體）承載頁面，模型則協助分類、摘要與產草稿；內容仍要人工核對與維護。

比較項目檢索增強生成先整理成百科
核心做法提問時才檢索相關片段預先整理成主題頁面與概念連結
使用方式適合直接問答與文件搜尋適合瀏覽、教學與建立知識全貌
上下文可能只撈回局部片段，缺前後文同一主題已整合，比較留得住脈絡
知識關聯片段之間通常沒有明確關係可用連結、標籤或圖譜呈現概念關係
維護文件更新後重新切割並重建索引同步更新頁面、摘要、連結與版本
主要風險檢索錯誤、該找到的沒找到摘要失真、內容過時、來源遺失

兩者不互斥。整理好的頁面提供適合閱讀的結構，再用檢索從頁面與原始文件裡撈出相關內容。不論用哪一種，都要留下來源連結、更新日期與人工審核紀錄。

放回同一張地圖

一個完整任務怎麼串起來

系統提示：規定代理人的角色與界線
使用者提示：提出這次的任務
代理人：安排步驟，協調模型與工具
函式呼叫：讓模型用結構化的方式挑工具
MCP：連接外部的工具、資源或提示模板
檢索或整理好的知識：提供任務需要的內容
工具結果：回到模型，形成下一步或最終答案

判斷技巧：先問「這個名詞在解決哪兩個元件之間的問題？」比背定義好用得多，也比較不會把代理人、函式呼叫跟 MCP 混在一起。

重點整理

  • 系統提示管長期的角色與規則，使用者提示表達這一次的任務。
  • 代理人負責協調，工具負責執行；模型不等於代理人。
  • 函式呼叫處理的是模型與工具呼叫的格式，MCP 處理的是主機與外部服務的連接。
  • 檢索增強生成偏向即時撈片段，先整理成百科偏向預先建結構，兩者可以搭配。
  • 模型產生的摘要、詞條與連結都要留來源，並定期回頭核對。
