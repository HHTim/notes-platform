工具從哪裡來

三種來源：內建、本機指令、外接伺服器

要讓助理替你動手，得先有可以呼叫的工具。工具的來源分成三類：

來源白話比喻適合做什麼主要風險
內建工具工具箱原本就附的那幾支讀寫檔案、搜尋內容、待辦清單、抓網頁、執行指令權限範圍太大、誤改檔案
本機指令請它操作你這台電腦跑測試、套件工具、版本控制、自動化腳本指令被塞進惡意內容、破壞性操作、環境差異
MCP 伺服器照共同插座規格接上的外部設備接資料庫、服務、瀏覽器或其他專用能力憑證外洩、第三方信任、來源供應鏈風險

助理不一定把所有工具都丟給模型挑：可以依任務、權限或上下文容量先篩過，減少模型選錯工具的機會。這個道理不限於某一套產品，工具越多、選擇越容易出錯。

共同的插座規格

MCP 是什麼？

MCP（Model Context Protocol，模型上下文協定，一套讓程式接上外部能力的通訊規格）規範的是「怎麼溝通」。承載 AI 體驗的應用程式叫 Host（主機），跟某台伺服器建立連線的那一塊叫 Client（用戶端），對外提供能力的服務叫 Server（伺服器端）。

Tool（工具）可以執行的動作，有輸入有輸出，例如搜尋、建工單、操作瀏覽器。
Resource（資源）可以讀取的資料或內容，例如文件、日誌、設定。
Prompt（提示模板）可重複使用的互動樣板，例如「幫我審這段程式碼」的標準流程。

MCP 本身不負責推理，也不限定背後要用哪一顆模型。「伺服器」在這裡指的是提供能力的那一端，不一定是一直開著的機器出處——用標準輸入輸出連線時，它是主機在需要時才啟動的子程序，用完就結束。

另外要注意：協定統一的是溝通方式，不是每套應用程式的設定檔放哪裡。要把伺服器加進來，還是得照該產品當下的設定規格操作。

部署與傳輸

本機程序、容器與遠端服務

把伺服器分成「本機標準輸入輸出」「本機容器」「遠端 HTTP」三種，是混了兩件事的講法——現行規格只定義兩種標準傳輸：標準輸入輸出（stdio）與 Streamable HTTP；容器是打包與部署的方式，不是另一種傳輸出處，容器裡的伺服器實際上還是走前面那兩種之一。

形式怎麼運作要注意什麼
標準輸入輸出（stdio）主機啟動一個本機子程序，用輸入輸出串流一行一行交換訊息部署直接，但要自己管本機執行環境與套件
Streamable HTTP每則訊息是一個 HTTP 請求，回覆可能是一包資料，也可能是一條持續回傳的串流方便集中管理，但要處理身分驗證、加密、延遲與費用
容器（打包方式，不是傳輸）伺服器跑在容器裡，對外仍用上面兩種之一連線環境比較一致，但映像來源、掛載路徑與權限仍要自己審

遠端的伺服器不一定要付費：收費與否看的是該服務本身的商業模式，跟用哪種傳輸方式無關。

一次呼叫怎麼跑完

裝箱、寄出、拆箱

當助理判斷需要外接工具時，用戶端會照協定組出一個請求。可以比喻成寄包裹：先按格式填單，再把內容轉成可傳送的位元組；伺服器收到後反向還原、執行工具，結果再沿原路回來。

你的要求
  ↓
主機挑出要用的工具
  ↓
用戶端組出結構化的請求
  ↓
序列化（轉成文字）＋ 加上分隔換行
  ↓
編碼成位元組送出去
  ↓
伺服器解碼、還原、執行工具
  ↓
結果沿相反方向回到助理
  ↓
模型根據結果回答，或再發一次呼叫

訊息格式用的是 JSON-RPC（用 JSON 表達遠端呼叫的格式，裡面有方法名稱、參數、識別碼、結果與錯誤），傳輸層則負責把訊息真的送到。兩者角色不同：訊息格式像表單的欄位規定，傳輸像寄送的管道。標準輸入輸出這種傳輸會用換行當分隔，等於一行一則 JSON-RPC。

SDK 幫你擋掉的細節

底層瑣事大多不用自己寫

自己實作用戶端或伺服器時，通常不必逐一處理編碼、解析與錯誤。SDK（軟體開發套件，官方給的現成程式庫）會提供型別、訊息處理與傳輸介面。介面分成高階與低階兩種：高階像用現成櫃台，常見功能做得快；低階像進後場自己組，控制力高但要自己扛協定細節與測試。

官方 SDK 目前有十套（TypeScript、Python、C#、Go、Rust、Java、Ruby、Swift、PHP、Kotlin），而且每一套都同時支援寫用戶端與寫伺服器出處，不再是用戶端只能用某一種語言。

把規範變成自動檢查

Hooks：在固定時機自動跑一段檢查

Hook（掛鉤，指在特定事件發生時自動執行的一段命令）像產線上的檢查站：送出提示時、工具執行前、檔案改完後、需要通知時，都能插進一段固定流程。最常用的四個事件：

事件可以做什麼設計重點
UserPromptSubmit（你送出提示時）補上團隊提醒、檢查任務前置條件別塞太長或互相打架的規則
PreToolUse（工具執行前）檢查權限、參數與安全性高風險操作直接擋掉或要求人工核准
PostToolUse（工具執行後）跑格式化、靜態檢查或測試控制耗時，失敗時把原因講清楚
Notification（需要通知時）回報任務完成、等待輸入或出錯別把程式碼、憑證與個資寫進通知

設定放在 .claude/settings.json，用 matcher 篩選要攔哪些工具，寫法是「事件、篩選條件、要執行的命令」三層：

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/safety-check.sh" }
        ]
      }
    ]
  }
}

上面那張表只是常用的幾個，現行版本的事件遠不止這些（開場、結束、壓縮前後、子代理啟動與結束等都有），而且 PreToolUse 的掛鉤可以直接擋下一次工具呼叫。完整清單與回傳格式請查 官方 Hooks 文件，設定鍵與欄位會隨版本調整。

安全邊界

外掛能力越強，界線越要先畫清楚

  • 最小權限：只給完成任務需要的檔案、帳號與網路範圍。
  • 憑證分離：不要把權杖或密碼寫進提示、版本庫或掛鉤的輸出。
  • 信任來源固定：外接伺服器、套件、容器映像與它們的更新方式都要先審過。
  • 留下稽核紀錄：記工具名稱、時間、結果與錯誤，敏感欄位遮起來。
  • 想好失敗要怎麼辦：測試失敗要能擋住交付；通知失敗就不一定要中止全部工作。
  • 防止無限循環：避免掛鉤觸發修改、修改又觸發同一個掛鉤。

專案規則檔描述的是「應該怎麼做」，掛鉤則能把部分規範變成「每次都會跑的檢查」。兩者搭配，才同時有語意上的指引跟機械式的防線。

重點整理

  • 工具有三種來源：內建工具、本機指令、外接的 MCP 伺服器；三種的風險不一樣。
  • MCP 規範的是主機、用戶端與伺服器怎麼交換工具、資源與提示模板，它不是模型。
  • 現行規格只有標準輸入輸出與 Streamable HTTP 兩種傳輸；容器是打包方式，不是第三種傳輸。
  • JSON-RPC 管訊息長什麼樣，傳輸層管訊息怎麼送到，兩件事不要混在一起。
  • Hooks 適合把權限檢查、測試與通知變成固定流程，但要控制耗時、副作用與敏感資料。
