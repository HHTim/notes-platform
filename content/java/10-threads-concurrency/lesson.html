從藍圖、工廠到員工

程式、行程與執行緒

原筆記的比喻很好記：程式（program）是工廠藍圖，還沒執行的程式碼；行程（process）是照藍圖開起來、已經拿到資源的工廠；執行緒（thread）是工廠裡真正在做事的員工。

對照一下用詞：原筆記寫的是「程序」「進程」「線程」，這課一律用台灣講法的「行程」「執行緒」，指的是同一件事。

程式（Program）
└── 啟動後成為行程（Process）
    ├── 主執行緒（Main Thread）
    ├── 工作執行緒 A
    └── 工作執行緒 B
概念角色跟資源的關係
程式還沒執行的程式碼同一份程式可以啟動成多個行程
行程執行中的程式實例有自己的記憶體空間，彼此看不到對方；至少含一個執行緒
執行緒行程內的執行單位共用行程的物件與記憶體，但各自有呼叫堆疊

「共用記憶體、各有自己的堆疊」這句是關鍵：執行緒之間透過參考碰得到同一個物件，但各自方法裡的區域變數是獨立的。

「一個 CPU 一次只能執行一個行程」要改成一個處理核心。八核心的 CPU 在同一瞬間就能真的跑八件事，這正是下面「並行」跟「平行」的差別所在出處。

並行 concurrency多件事在一段時間內交錯推進。單核心靠快速切換也做得到。
平行 parallelism多件事在同一瞬間真的同時執行。要有多個核心才可能。

多行程隔離性好，但行程之間要交換資料得靠行程間通訊，而且每個行程都要一份資源，比較吃記憶體（Chrome 就是這種設計）。多執行緒交換資料直接，代價就是共享狀態容易打架——接下來整課都在講這件事。

start() 才會真的開新執行緒

在 Java 建立與管理工作

兩種做法：繼承 Thread，或把工作寫成 Runnable。因為 Java 類別只能單一繼承，繼承 Thread 會把繼承的名額用掉，所以實務上多半把「工作」跟「執行機制」分開，用 Runnable。

Runnable task = () -> {
    System.out.println(Thread.currentThread().getName());
};

Thread worker = new Thread(task);
worker.start();

一定要呼叫 start()。直接呼叫 run() 只是在目前這條執行緒裡執行一個普通方法，根本不會有新執行緒——原筆記的步驟清單最後一步寫成「呼叫 run() 方法」，跟它自己前面寫的 start() 互相矛盾出處。

join() 讓目前這條執行緒等另一條結束再繼續，控制的是等待關係，不是整個系統的執行順序。

worker.start();
worker.join();   // 等 worker 跑完再往下

join(毫秒) 的意思是「最多等這麼久」——對方提早結束就提早往下走，時間到了對方還沒完就不等了。它不會去強制中斷或介入對方執行緒出處。

執行緒優先權（1 到 10，預設 5）與 yield() 都只是給排程器的提示，不同作業系統的對待方式還不一樣。絕對不要拿它們來保證程式的正確性出處。原筆記自己也總結得很對：多執行緒難以預測、順序無法完全保證、切換可能發生在任何時刻。

大量工作不要一個配一條新執行緒。執行緒池（thread pool）會重複利用固定數量的執行緒，並集中管理工作佇列與生命週期——例如 Spring Boot 內建的 Tomcat 預設最多 200 條，每個進來的請求分一條。

看似一行，底層是三步

競爭條件與原子性

多條執行緒同時讀寫同一份狀態，結果又取決於誰先誰後，就是競爭條件（race condition）。

stock--;   // 看起來一個動作，其實是三個：
           // 1. 讀取 stock 的值
           // 2. 算出 stock - 1
           // 3. 把結果寫回 stock

原筆記的購物範例很清楚：庫存 100，兩個人同時買——

時間        T1        T2        T3
執行緒 1    讀到 100   （處理中） 寫回 99
執行緒 2              讀到 100   寫回 99

預期：98　　實際：99

兩個人都買到了，庫存只少 1。這叫遺失更新（lost update）。

原子性（atomicity）指的是：這個操作對其他執行緒而言不可分割——要嘛完整做完，要嘛還沒發生，不會被看到做到一半。

原子性跟可見性是兩件不同的事。原子性講的是「不會被拆開觀察」，可見性講的是「我寫的值別人什麼時候看得到」——一個操作可以不可分割卻還沒被別人看到。AtomicInteger 這類原子類別確實兩者都給，但那是它額外提供的保證，不是原子性的定義出處。

一次只准一個人進去

synchronized 與顯式鎖

臨界區（critical section，原筆記叫「危險區域」）是會碰到共享可變資料、需要協調的那段程式。synchronized 會先取得指定物件的監視器鎖（monitor lock），同一時間只有拿到同一把鎖的執行緒進得去，其他人就在門外等。

private int stock = 100;

public synchronized boolean buy() {
    if (stock <= 0) {
        return false;
    }
    stock--;
    return true;
}

鎖住的範圍必須涵蓋完整的判斷條件——「先檢查庫存，再扣庫存」是一組，只保護扣的那一行照樣會超賣

ReentrantLock 提供 synchronized 沒有的彈性：可中斷的等待、限時嘗試（tryLock()）、多個條件佇列。代價是你得自己記得解鎖，而且一定要寫在 finally 裡：

lock.lock();
try {
    // 存取受保護的共享狀態
} finally {
    lock.unlock();   // 例外了也要放開，不然這把鎖永遠鎖著
}

看得到，不等於不會踩到

可見性、volatile 與指令重排序

可見性（visibility）講的是：一條執行緒寫進去的值，其他執行緒什麼時候看得到。編譯器、處理器跟快取都會做最佳化，所以不能用單執行緒的直覺去推測結果。

volatile 提供可見性與順序保證，最適合「一個人寫狀態、其他人讀狀態」的旗標：

private volatile boolean shutdownRequested;

public void requestShutdown() {
    shutdownRequested = true;
}

public void runLoop() {
    while (!shutdownRequested) {
        // 執行工作
    }
}

volatile int count 的 count++ 仍然是讀取、計算、寫回三步，照樣會遺失更新。原筆記的程式碼註解把它寫成「立即刷新到主記憶體」，讓人以為問題解決了，但同一份筆記的小結又正確地說 volatile 不能解決原子性——以小結那段為準出處。要原子遞增請用同步區段或 AtomicInteger。

原筆記用「立即寫入主記憶體、其他 CPU 快取失效」來解釋 volatile。當直覺可以，但嚴格講，Java 記憶體模型是用先行發生關係（happens-before）來定義的，並沒有規定實作一定要去刷快取；同步、volatile 與各種並行工具的作用，是建立這種關係，讓跨執行緒的可見性與順序有明確保證。

指令重排序（instruction reordering）是編譯器與處理器在不破壞單執行緒語意的前提下調整執行順序。原筆記的例子：a 跟 b 沒有依賴關係，順序換一下結果一樣，但可能跑得比較快。問題是這種「單執行緒看起來沒差」的最佳化，在多執行緒下就看得出來了。

先比較，再交換

AtomicInteger 與 CAS

原子類別用在單一變數的原子更新，底層靠的是比較並交換（compare-and-swap，CAS）：帶著「我以為現在是多少」去改，只有真的還是那個值才寫進去，否則回報失敗、由演算法決定要不要重試。

AtomicInteger count = new AtomicInteger(0);
int result = count.incrementAndGet();
目前值 = 5
執行緒 A：compareAndSet(5, 6) → 成功
執行緒 B：compareAndSet(5, 6) → 失敗（已經是 6 了）
執行緒 B：重新讀到 6，再試 compareAndSet(6, 7) → 成功

跟鎖比起來，CAS 不阻塞——失敗的人立刻重試，不會被掛起來等。這是它在高併發下常常比較快的原因。但它有兩個代價：

  • ABA 問題：值從 A 變成 B 又變回 A，單看值看不出中間發生過事，CAS 會誤以為沒人動過。
  • CPU 開銷：競爭很激烈時，大量的失敗重試也是在燒 CPU。

AtomicInteger 只保護得了一個變數。跨多個欄位的業務規則它管不到——那種情況要用鎖、不可變資料，或更高階的並行設計。

原筆記的庫存範例是「先扣，發現扣成負的再加回來」。這樣在補回來之前，其他執行緒會讀到負數的庫存，或被誤判成賣完了。要一次完成「檢查＋扣減」，用 updateAndGet 這種帶重試的寫法比較穩出處：

int after = stock.updateAndGet(current -> current > 0 ? current - 1 : current);
// after 等於原值表示沒扣成，也就是賣完了

大家都拿著一把，又都在等另一把

死結與怎麼避免

死結（deadlock）要四個條件同時成立才會發生：

  • 互斥：這份資源同一時間只能給一個人用。
  • 持有並等待：手上抓著一個，又在等另一個。
  • 不可搶占：占著很久也不能把他趕走。
  • 循環等待：A 等 B、B 等 C、C 又等 A，繞成一圈。
// 兩個方法拿鎖的順序相反，就湊齊了循環等待
public void transferAtoB() {
    synchronized (lock1) { synchronized (lock2) { /* ... */ } }
}

public void transferBtoA() {
    synchronized (lock2) { synchronized (lock1) { /* ... */ } }
}

最常用的預防法是破壞循環等待：讓所有程式一律照同一個順序拿鎖。其他做法還有縮小鎖定範圍、減少巢狀鎖，或用 tryLock() 加逾時，拿不到就放棄重來。

同步的重點不是「加一把鎖」，而是講清楚哪些狀態必須一起保持一致，以及由哪一把鎖負責保護它們。

Java 21 之後多了一個選項

補充：虛擬執行緒

原筆記那句「不要啟動 1000 條執行緒，那會把 JVM 弄死」在當時完全正確——每一條執行緒都對應一條作業系統執行緒，很貴。Java 21 起定案的虛擬執行緒（virtual thread）改變了這個前提：它由 JVM 自己排程，非常輕，開幾十萬條都不成問題出處。

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> handleRequest());
    }
}

它最適合的是「大部分時間在等」的工作——等資料庫、等外部 API。但要講清楚：虛擬執行緒完全沒有解決這一課講的任何一個問題。競爭條件、可見性、死結，一條都沒少，該加的鎖還是要加。

工具怎麼挑

一張表收尾

工具適合要注意
synchronized保護一段複合邏輯或多個相關狀態鎖太大就是大家一起排隊
ReentrantLock需要限時取得、可中斷等待一定要在 finally 裡解鎖
AtomicInteger單一計數器或簡單的原子更新跨欄位的規則它管不到
volatile狀態旗標、發布最新的參考不保證複合操作的原子性
ExecutorService提交大量工作、管理執行緒池記得關閉，也要處理工作失敗

重點整理

  • 程式是靜態的碼，行程是執行中的實例，執行緒是行程裡的執行單位。
  • 同一行程的執行緒共用物件與記憶體，各有自己的呼叫堆疊——所以共享狀態要協調。
  • start() 才會開新執行緒，直接呼叫 run() 只是普通方法呼叫。
  • 優先權與 yield() 都只是提示，不能拿來保證正確性。
  • synchronized 與鎖保護的是完整的臨界區；AtomicInteger 只管單一變數。
  • volatile 給可見性與順序，但 count++ 照樣不是原子的。
  • 死結靠一致的鎖定順序、縮小鎖定範圍或限時取鎖來避免。
  • 虛擬執行緒讓「開很多條」變便宜了，但競爭條件、可見性、死結一個都沒消失。
