JVM 這個行程裡面分成幾塊

執行期資料區：誰共用、誰獨有

〈作業系統怎麼跑程式：行程、執行緒、記憶體與 I/O〉講過，一個 JVM 就是一個行程，它有自己的虛擬位址空間。JVM 把這塊空間再分成幾個用途不同的區域，Java 虛擬機規格（JVMS）叫執行期資料區（run-time data areas）：「有些在 JVM 啟動時建立、JVM 結束時才銷毀；其他是每條執行緒一份，隨執行緒建立與銷毀」（Some of these data areas are created on Java Virtual Machine start-up and are destroyed only when the Java Virtual Machine terminates. Other data areas are per thread.）。出處

JVMS 第 2.5 節的定義：出處

區域規格怎麼說誰擁有出事時
pc 暫存器「每條 JVM 執行緒有自己的 pc（程式計數器）暫存器」，記著目前執行到哪一條指令每條執行緒—
JVM 堆疊「與執行緒同時建立」，存放「框」（frame）：區域變數與運算中的部分結果，「參與方法的呼叫與回傳」每條執行緒需要的深度超過允許值丟 StackOverflowError；配不出記憶體丟 OutOfMemoryError
堆「所有 JVM 執行緒共用」，是「配置所有類別實體與陣列的執行期資料區」；物件「從不明確釋放」，由垃圾回收器回收共用OutOfMemoryError
方法區「所有 JVM 執行緒共用」，存放每個類別的結構：執行期常數池、欄位與方法的資料、方法與建構子的程式碼共用OutOfMemoryError
本機方法堆疊執行 C 這類原生方法時用的堆疊每條執行緒StackOverflowError 或 OutOfMemoryError

每次呼叫方法就推一個框進那條執行緒的 JVM 堆疊，方法結束就彈出。所以區域變數只有自己那條執行緒看得到，天生不必同步；堆上的物件大家都拿得到參考，才需要〈執行緒與並行〉講的那些鎖。方法區在 HotSpot 裡的實作叫 Metaspace：Java 8 的 JEP 122「從 HotSpot JVM 移除永久代，因此也不再需要調整永久代的大小」（Remove the permanent generation from the Hotspot JVM and thus the need to tune the size of the permanent generation.）出處，類別中繼資料改放在原生記憶體（native memory，作業系統直接給行程、不在 Java 堆裡的記憶體）。出處

堆與方法區共用；JVM 堆疊、pc、本機方法堆疊每條執行緒一份

方法裡宣告的區域變數 int count = 0; 放在哪一塊？

  • 堆，跟物件放在一起
  • 那條執行緒的 JVM 堆疊
  • 方法區，跟類別資料放一起
  • pc 暫存器

JVMS：JVM 堆疊存放框，框裡是區域變數與運算中的部分結果。每條執行緒的堆疊各自獨立，所以區域變數不會被別的執行緒看到。

new Account("A001") 建立出來的物件實體放在哪一塊？

  • 呼叫者的 JVM 堆疊
  • 方法區
  • 堆
  • 本機方法堆疊

JVMS：堆是「配置所有類別實體與陣列」的區域。指向它的參考變數若是區域變數，那個參考放在堆疊上，但物件本身在堆裡。

下面哪一塊是所有執行緒共用的？

  • pc 暫存器
  • JVM 堆疊
  • 本機方法堆疊
  • 方法區

JVMS：堆與方法區由所有 JVM 執行緒共用；pc 暫存器、JVM 堆疊、本機方法堆疊每條執行緒各一份。

類別的結構、執行期常數池、方法的程式碼，放在哪一塊？

  • 方法區（Metaspace）
  • 堆的老年代，跟長壽物件一起
  • 每條執行緒各自的 JVM 堆疊
  • pc 暫存器

JVMS 2.5.4：方法區存放每個類別的結構，例如執行期常數池、欄位與方法資料、方法與建構子的程式碼。Java 8 起 HotSpot 把它放在原生記憶體的 Metaspace。

Java 8 的 JEP 122 移除了什麼？

  • 整個垃圾回收器
  • 年輕代裡的 Survivor 空間
  • 永久代（PermGen）
  • 每條執行緒的 JVM 堆疊

JEP 122：從 HotSpot 移除永久代，也就不必再調永久代的大小；類別中繼資料改放原生記憶體（Metaspace）。

為什麼方法裡的區域變數不需要用 synchronized 保護？

  • 因為它在自己那條執行緒的堆疊上，別人碰不到
  • 因為區域變數一律被當成 final 處理
  • 因為 JVM 會自動替每個區域變數加鎖
  • 因為區域變數其實存在 pc 暫存器裡

每條執行緒的 JVM 堆疊是私有的。但要注意：區域變數若是一個參考，它指向的物件在堆上，那個物件被多條執行緒共用時照樣要同步。

多數物件很快就死

堆的分代：Eden、Survivor、老年代與晉升

最笨的回收法是每次把所有活物件都走一遍，調校指南說這樣花的時間跟活物件數成正比，「對保有大量活資料的大型應用程式來說代價太高」。HotSpot 改用分代回收（generational collection），依據的是弱分代假說（weak generational hypothesis）：「大多數物件只存活很短的時間」（most objects survive for only a short period of time）。出處

調校指南的描述：「絕大多數物件配置在專門給年輕物件的池（年輕代），而且大部分死在那裡」；年輕代滿了就做一次年輕代回收（minor collection），「只回收年輕代」，成本大致跟活物件數成正比，所以「滿是死物件的年輕代回收得非常快」；老年代最後也會滿，那時做主要回收（major collection），「整個堆都要回收」，通常比年輕代回收久得多。年輕代由 Eden 與兩塊 Survivor 組成：「大多數物件一開始配置在 Eden」，任何時候都有一塊 Survivor 是空的，回收時當作 Eden 與另一塊 Survivor 裡活物件的目的地；物件就這樣在兩塊 Survivor 之間來回複製，「直到被複製過一定次數、或那邊空間不夠，就複製進老年代」，這叫老化（aging）。出處

實跑一個「交易字串大量產生、千分之一留下來」的程式，用 -Xlog:gc 看回收：

public class Churn {
    public static void main(String[] args) {
        List<String> survivors = new ArrayList<>();
        long sum = 0;
        for (int i = 0; i < 3_000_000; i++) {
            String tx = "TX-" + i;                 // 大部分物件用完就沒人參考了
            sum += tx.length();
            if (i % 1000 == 0) {
                survivors.add(tx);                 // 千分之一活下來
            }
        }
        System.out.println(sum + " " + survivors.size());
    }
}

// [0.028s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 24M->1M(64M) 0.630ms
// [0.034s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 38M->1M(64M) 0.486ms
// [0.039s][info][gc] GC(2) Pause Young (Normal) (G1 Evacuation Pause) 38M->1M(64M) 0.490ms

38M->1M(64M) 是「回收前用了 38 MB、回收後剩 1 MB、堆目前 64 MB」。括號裡的堆大小跟機器記憶體有關：初始堆是實體記憶體的 1/64，在 2 GB 的容器裡跑同一個程式，日誌就變成 19M->1M(34M) 這樣。不管哪一種，每次年輕代回收，幾乎全部都是死物件，零點幾毫秒就清掉了，這就是弱分代假說的效果。

堆多大：調校指南列的預設值是「初始堆大小為實體記憶體的 1/64」「最大堆大小為實體記憶體的 1/4」，最小與最大堆分別用 -Xms、-Xmx 設。出處 它還說 HotSpot 啟動時「在位址空間裡保留整個 Java 堆，但除非需要，不會替它配置實體記憶體」出處，這正是〈作業系統怎麼跑程式：行程、執行緒、記憶體與 I/O〉的需求分頁：-Xmx4g 不代表一啟動就吃掉 4 GB 實體記憶體。在只給 2 GB 記憶體的容器裡實跑 java -XX:+PrintCommandLineFlags -version，看到 -XX:InitialHeapSize=33554432（32 MB，2 GB 的 1/64）與 -XX:MaxHeapSize=536870912（512 MB，2 GB 的 1/4）：JVM 認的「實體記憶體」是容器給的上限。

小容器有例外：java 指令手冊說，堆很小（約 125 MB 以下）時改用 -XX:MinRAMPercentage，預設是 50%（A small heap is a heap of approximately 125 MB. The default value is 50 percent.）。Java 21 實跑：容器給 128 MB 時最大堆是 64 MiB、256 MB 時是 126 MiB，都比 1/4 大；512 MB 起才是 1/4。出處

新物件進 Eden；年輕代回收快，因為大多數都死了；活得夠久才晉升老年代

HotSpot 把堆分代，依據的是什麼觀察？

  • 大物件比小物件更常被存取
  • 老物件比新物件更容易變成垃圾
  • 大多數物件只活很短的時間
  • 每個物件的壽命其實都差不多長

這是弱分代假說。調校指南：最直接的演算法每次走過所有活物件，太慢；分代回收利用「大多數物件很快就死」，把力氣集中在年輕代。

一個剛 new 出來的一般物件，大多配置在哪裡？

  • 老年代
  • 空的那塊 Survivor
  • Eden
  • Metaspace

調校指南：大多數物件一開始配置在 Eden。Survivor 是年輕代回收時活物件的目的地；Metaspace 放的是類別中繼資料，不是物件。

為什麼年輕代回收通常很快？

  • 年輕代裡大多是死物件，只要處理活的
  • 因為年輕代回收完全不暫停應用程式
  • 因為年輕代用了比較快的記憶體
  • 因為年輕代回收只檢查一半的物件

調校指南：回收成本大致跟被回收那一代的活物件數成正比，「滿是死物件的年輕代回收得非常快」。實跑的日誌裡，每次 38 MB 回收後只剩 1 MB，停頓不到一毫秒。

物件在什麼情況下會晉升到老年代？

  • 物件第一次被其他執行緒讀取時
  • 物件所屬的類別被宣告成 static 時
  • 在 Survivor 間被複製夠多次
  • 物件所屬的類別第一次被載入時

調校指南：物件在兩塊 Survivor 之間來回複製，直到複製過一定次數或那邊空間不夠，就複製進老年代，這個過程叫老化。

GC 日誌 Pause Young (Normal) (G1 Evacuation Pause) 38M->1M(64M) 0.486ms 裡的 38M->1M 是什麼意思？

  • 這次回收把堆從 38 MB 縮成 1 MB 的上限
  • 回收前用了 38 MB，回收後剩 1 MB
  • 有 38 MB 物件晉升到老年代
  • 應用程式被暫停了 38 毫秒

箭頭兩邊是回收前後的用量，括號裡的 64M 是目前的堆大小，最後是這次停頓的時間。回收後只剩 1 MB，表示幾乎全是死物件。

沒設 -Xmx 時，Java 21 的最大堆大小預設是多少？

  • 實體記憶體的 1/4
  • 固定 256 MB
  • 實體記憶體的 1/64
  • 實體記憶體的全部

調校指南的預設值：初始堆是實體記憶體的 1/64、最大堆是 1/4。容器給 2 GB 時實跑得到最大堆 512 MB、初始 32 MB，剛好是 1/4 與 1/64。

設了 -Xmx4g，JVM 一啟動就會占掉 4 GB 實體記憶體嗎？

  • 會，堆一開始就全部配置好
  • 不會，需要時才配實體記憶體
  • 會，但只有用 G1 時才會這樣
  • 不會，因為 -Xmx 只限制老年代

調校指南：HotSpot 啟動時在位址空間保留整個 Java 堆，但除非需要不配置實體記憶體。這跟作業系統的需求分頁是同一件事。

誰還活著，從根開始算

GC Root 與可達性

垃圾回收器怎麼知道一個物件是垃圾？調校指南的定義：物件「再也無法從執行中程式的任何活物件的任何參考到達」時，就被視為垃圾，記憶體可以重用（An object is considered garbage and its memory can be reused by the VM when it can no longer be reached from any reference of any other live object in the running program.）。出處 「到達」要有起點，這些起點叫 GC Root。HotSpot 詞彙表的定義：「從堆外指進 Java 物件堆的指標，例如來自類別的靜態欄位、執行中方法框裡的區域參考等」（A pointer into the Java object heap from outside the heap. These come up, e.g., from static fields of classes, local references in activation frames, etc.）。出處 「執行中方法框裡的區域參考」就是各條執行緒 JVM 堆疊上的區域變數與參數。回收器從根出發，沿著參考把走得到的都標成活的，其餘就是垃圾，這叫可達性分析。

class Branch {
    static final List<Account> ACTIVE = new ArrayList<>();   // 靜態欄位：一條 GC Root

    void open() {
        Account a = new Account("A001");   // a 在堆疊上：Account 物件可達
        ACTIVE.add(a);                     // 靜態清單也指向它
        Account tmp = new Account("TMP");  // 只有 tmp 指著
    }   // 方法結束：a、tmp 這兩個區域變數消失
        // "TMP" 那個物件再也走不到，變成垃圾；"A001" 還被 ACTIVE 抓著，仍然活著
}

可達性也讓循環參考不成問題：兩個物件互相指著對方，但從任何根都走不到它們，它們就一起是垃圾。〈Java 進階快答：JVM 記憶體、垃圾回收與類別載入〉整理了強、軟、弱、虛四種參考強度，是在「走得到」裡再分強弱。

上面 Branch 的片段是說明用的：Account 假設是一個有 String 參數建構子的類別。

依 HotSpot 調校指南，一個物件什麼時候算垃圾？

  • 超過一分鐘都沒有被讀取時
  • 它的參考計數變成 0 時
  • 建立它的那個方法執行完時
  • 再也無法從活物件走到它時

調校指南的定義是「再也到達不了」。物件建立的方法執行完不代表它死了，它可能已經被別的活物件（例如靜態集合）抓住。

上面 Branch.open() 執行完之後，下面哪一個物件可以被回收？

  • "TMP" 那個 Account
  • "A001" 那個 Account
  • ACTIVE 那份清單
  • 兩個 Account 都可以

tmp 是區域變數，方法結束後就沒有任何參考指向 "TMP"；"A001" 還被靜態清單 ACTIVE 指著，從 GC Root 走得到。

兩個物件互相持有對方的參考，但程式裡已經沒有任何變數指向它們。HotSpot 會回收它們嗎？

  • 不會，因為它們的參考數都不是 0
  • 會，因為從 GC Root 走不到它們
  • 只有呼叫 System.gc() 才會
  • 只有其中一個會被回收

HotSpot 看可達性，不是看參考計數。從根出發走不到，兩個就一起是垃圾。循環參考只會難倒單純用參考計數的做法。

下面哪一個不是常見的 GC Root？

  • 執行中方法的區域變數
  • 類別的靜態欄位
  • 沒人參考的物件裡的欄位
  • 執行中方法的參數

GC Root 是「從堆外指進來」的起點：堆疊上的區域變數與參數、靜態欄位等。一個沒人參考的物件本身就是垃圾，它的欄位不能讓別人活下來。

一個物件被放進 static final Map 之後忘了拿出來，會怎樣？

  • 它一直從 GC Root 可達，不會被回收
  • 過一陣子 JVM 會自動把它移除
  • 老年代滿了的時候就會被回收
  • 呼叫一次 System.gc() 就會被回收

靜態欄位是 GC Root，Map 裡的物件一直走得到。這正是後面「記憶體洩漏」那一段的第一個來源。

四個回收器，兩條取捨軸

Serial、Parallel、G1、ZGC 與 Stop-The-World

Stop-The-World（STW）是回收器暫停所有應用程式執行緒的那段時間。回收器要搬物件、改參考，應用程式如果同時在改同一批物件，兩邊會互相踩到，所以至少有一部分工作要在暫停中做。調校指南說衡量回收的兩個主要指標是吞吐量（throughput，花在應用程式而不是回收上的時間比例）與延遲（latency，停頓多長）。出處 Java 21 的四個回收器：出處

回收器調校指南怎麼說適合開啟
Serial「用單一執行緒做所有回收工作」，沒有執行緒之間溝通的成本單處理器，或資料量小（約 100 MB 以內）-XX:+UseSerialGC
Parallel「也叫吞吐量回收器」，跟 Serial 一樣分代，差在「用多條執行緒加速回收」多處理器上中大型資料量，吞吐量第一、能接受一秒以上的停頓-XX:+UseParallelGC
G1「大致並行」（mostly concurrent）的回收器，「能以高機率達成停頓時間目標，同時保有高吞吐量」回應時間比吞吐量重要，停頓要短-XX:+UseG1GC
ZGC「最大停頓在一毫秒以內，但犧牲一些吞吐量」，停頓時間與堆大小無關，適合「幾百 MB 到 16 TB」的堆延遲最優先Java 21：-XX:+UseZGC -XX:+ZGenerational

G1 怎麼縮短停頓：

  • 區域：調校指南：G1 把堆切成「一組大小相等的區域」，每塊是「配置與回收的單位」；比較花時間的全堆標記「與應用程式並行」；並「追蹤過去應用程式行為與回收停頓的資訊，建立成本模型」，用來決定每次停頓做多少工作。出處
  • 停頓目標：用 -XX:MaxGCPauseMillis 設，java 手冊寫「G1 預設的最大停頓目標是 200 毫秒」，而且它只是「軟性目標」。出處
  • 不是即時回收器：指南也明說「G1 不是即時回收器」，只是以高機率達成目標。出處

Java 21 預設哪一個：調校指南：「伺服器級機器上用 G1，否則用 Serial」，而 VM 認定伺服器級的條件是「偵測到兩顆以上處理器，且實體記憶體大於等於 1792 MB」。出處 G1 自 Java 9 起成為預設，JEP 248 的理由是「一般來說，限制 GC 停頓時間比最大化吞吐量更重要」（Limiting GC pause times is, in general, more important than maximizing throughput.）。出處 用 Docker 限制 CPU 與記憶體實跑 java -XX:+PrintCommandLineFlags -version：

--cpus=2 --memory=1g-XX:+UseSerialGC（記憶體不到 1792 MB）

所以 K8s 上 limits 設成 1 顆 CPU，或記憶體 limits 低於 1792 MB（例如 1 GB）的 Java 服務，沒指定的話跑的是 Serial；實跑 --memory=1792m 是 G1、--memory=1791m 就變 Serial。

只設 requests 不算：K8s 文件說 CPU 的 request「通常定義的是一個權重」（The CPU request typically defines a weighting）出處，落到節點上是 CPU 份額（shares），而 Java 19 起 JVM 不再用份額算處理器數（JDK-8281181，Do not use CPU Shares to compute active processor count）出處；實跑 --cpu-shares=512 --memory=2g 照樣是 G1。

訊息文字告訴你哪一塊爆了

OutOfMemoryError 的種類，以及 StackOverflowError

OutOfMemoryError 不是一種錯，而是一組；後面的訊息文字決定是哪一塊記憶體不夠。下面幾種都在 Java 21 的 Linux 容器裡實際重現過。

Java heap space。疑難排解指南：這個訊息表示「物件無法在 Java 堆配置」，而且「不一定代表記憶體洩漏」，可能只是堆設太小；但對長時間執行的應用，它可能表示程式「無意間持有物件的參考，讓它們無法被回收——這就是 Java 語言版的記憶體洩漏」（This is the Java language equivalent of a memory leak.）。出處

public class HeapOom {
    public static void main(String[] args) {
        List<byte[]> keep = new ArrayList<>();
        try {
            while (true) {
                keep.add(new byte[1024 * 1024]);   // 每次 1 MB，全部抓著不放
            }
        } catch (OutOfMemoryError e) {
            int n = keep.size();
            keep = null;                           // 放手，讓後面的 println 有記憶體可用
            System.out.println("撐了 " + n + " MB：" + e);
        }
    }
}
// java -Xmx64m HeapOom（預設 G1）：            撐了 31 MB：java.lang.OutOfMemoryError: Java heap space
// java -Xmx64m -XX:+UseSerialGC HeapOom：     撐了 60 MB：java.lang.OutOfMemoryError: Java heap space

同樣 64 MB 的堆，G1 只放得進 31 個 1 MB 陣列，Serial 放得進 60 個。原因在 G1 的區域：這個堆的區域大小是 1 MB（-Xlog:gc+init 印出 Heap Region Size: 1M），調校指南說「大於等於半個區域的物件」是巨型物件（humongous object），每一個「配置成老年代裡一串連續的區域」，最後一塊區域剩下的空間「在整個物件被回收前都不能再拿來配置」。出處 1 MB 的陣列加上物件標頭比 1 MB 多一點，就占掉兩塊區域。所以用 G1 時，大小剛好超過半個區域（或剛好超過區域整數倍）的大陣列最浪費空間。

Metaspace。指南：「Java 類別中繼資料配置在原生記憶體（這裡稱為 Metaspace）」，用完就丟訊息是 Metaspace 的 OutOfMemoryError；上限是 MaxMetaspaceSize。出處 讓每個新的類別載入器各定義一次同一份位元碼，每次都是一個新類別：

public class Meta {
    // 每個載入器各自定義一次同一份位元碼，就是一個新的類別，類別中繼資料放進 Metaspace
    static class OneShotLoader extends ClassLoader {
        Class<?> define(byte[] bytes) {
            return defineClass("Payload", bytes, 0, bytes.length);
        }
    }

    public static void main(String[] args) throws Exception {
        byte[] bytes = Files.readAllBytes(Path.of(args[0]));
        List<Class<?>> keep = new ArrayList<>();
        try {
            while (true) {
                keep.add(new OneShotLoader().define(bytes));   // 抓著類別，載入器也就跟著活
            }
        } catch (OutOfMemoryError e) {
            int n = keep.size();
            keep = null;
            System.out.println("定義了 " + n + " 個類別：" + e);
        }
    }
}
// java -XX:MaxMetaspaceSize=32m Meta Payload.class
// 定義了 5375 個類別：java.lang.OutOfMemoryError: Metaspace

直接緩衝區。ByteBuffer.allocateDirect 配的記憶體在堆外，上限用 -XX:MaxDirectMemorySize 設：

List<ByteBuffer> keep = new ArrayList<>();
try {
    while (true) {
        keep.add(ByteBuffer.allocateDirect(1024 * 1024));   // 堆外 1 MB
    }
} catch (OutOfMemoryError e) {
    System.out.println("配了 " + keep.size() + " MB 直接緩衝區：" + e);
}
// java -XX:MaxDirectMemorySize=16m Direct
// 配了 16 MB 直接緩衝區：java.lang.OutOfMemoryError: Cannot reserve 1048576 bytes of direct buffer memory (allocated: 16777216, limit: 16777216)

StackOverflowError 不是 OutOfMemoryError。JVMS：執行緒的計算「需要比允許的更大的 JVM 堆疊」時丟 StackOverflowError。出處 每條執行緒的堆疊大小用 -Xss 設，java 手冊列的預設值依平台不同，例如 Linux/x64 是 1024 KB、Linux/Aarch64 是 2048 KB。出處

public class Deep {
    static int depth = 0;

    static void down() {
        depth++;
        down();                                    // 沒有終止條件的遞迴
    }

    public static void main(String[] args) {
        try {
            down();
        } catch (StackOverflowError e) {
            System.out.println("遞迴 " + depth + " 層後：" + e);
        }
    }
}
// Linux/Aarch64 容器，預設 -Xss（2048 KB），實跑六次：遞迴 45102〜94549 層後丟 java.lang.StackOverflowError
// java -Xss256k Deep，實跑六次：                遞迴 1629〜2793 層後丟 java.lang.StackOverflowError

層數每次都不一樣，因為即時編譯（後面 JIT 一段）把 down() 編成機器碼的時機不同，每一框占的堆疊大小也跟著變；要看的是量級：預設是幾萬層，256 KB 只剩兩千層上下。

還有兩種沒在這裡重現：GC overhead limit exceeded，指南說是回收器「幾乎一直在跑」，一次回收後「花超過大約 98% 的時間在回收」卻收回很少出處；以及開太多執行緒時的 unable to create native thread，對應 JVMS 那句「沒有足夠記憶體替新執行緒建立初始的 JVM 堆疊時，丟 OutOfMemoryError」。出處 每一種的完整排查方向整理在〈Java 進階快答：JVM 記憶體、垃圾回收與類別載入〉。

服務丟出 java.lang.OutOfMemoryError: Java heap space，依疑難排解指南，這一定是記憶體洩漏嗎？

  • 不一定，可能只是堆太小
  • 一定是，堆爆了就是洩漏
  • 一定不是，洩漏會丟出別的訊息
  • 一定是 Metaspace 設定的問題

指南原文：這個錯「不一定代表記憶體洩漏」，可能是堆大小設定的問題；但長時間執行的應用出現它，可能是無意間持有物件參考，也就是 Java 版的記憶體洩漏。

程式一直動態產生類別（例如每次請求都用新的類別載入器載一次），最後丟的最可能是哪一種？

  • Java heap space
  • StackOverflowError
  • OutOfMemoryError: Metaspace
  • Cannot reserve direct buffer memory

類別中繼資料放在 Metaspace。實跑時每個新載入器定義一個類別，32 MB 的 Metaspace 定義了五千多個類別後就丟 OutOfMemoryError: Metaspace。

程式丟出 Cannot reserve 1048576 bytes of direct buffer memory，把 -Xmx 調大有用嗎？

  • 有用，直接緩衝區也算在堆裡
  • 沒用，直接緩衝區在堆外
  • 有用，但要同時把 -Xss 調大
  • 沒用，因為這其實是 StackOverflowError

allocateDirect 配的是堆外記憶體，不受 -Xmx 管。實跑時 -XX:MaxDirectMemorySize=16m，配到 16 MB 就丟這個錯。

遞迴沒有終止條件，最後會丟什麼？

  • StackOverflowError
  • OutOfMemoryError: Java heap space
  • OutOfMemoryError: Metaspace
  • 什麼都不丟，會一直跑下去

每次呼叫推一個框進 JVM 堆疊，超過允許的深度，JVMS 規定丟 StackOverflowError，它不是 OutOfMemoryError。

把 -Xss 從預設改成 256k，上面 Deep 能遞迴的層數會怎樣？

  • 變多，因為堆疊比較小跑得比較快
  • 不變，-Xss 只影響堆
  • 變少，因為每條執行緒的堆疊變小了
  • 直接丟 OutOfMemoryError

-Xss 設的是每條執行緒的堆疊大小。實跑六次，預設（2048 KB）是四萬五千到九萬多層，256 KB 只剩一千六百到兩千八百層左右；層數每次不同，但量級差很多。

  • 因為 G1 回收得比 Serial 頻繁
  • 因為 G1 會把每個陣列複製兩份
  • 因為 G1 的堆實際上只有 32 MB
  • 1 MB 陣列是巨型物件，各占兩塊區域

調校指南：大於等於半個區域的物件是巨型物件，配置成一串連續區域，最後一塊剩下的空間在物件被回收前不能用。1 MB 陣列加標頭略大於 1 MB，就占兩塊。

一個沒有上限的執行緒池在尖峰時開了好幾萬條平台執行緒，最可能出現哪一個錯？

不是忘了釋放，是忘了放手

記憶體洩漏的常見來源

Java 有垃圾回收，所以不會因為「忘了 free」而洩漏；洩漏是「一個活很久的東西抓著一個本該死掉的東西」，照可達性的定義，被抓著的就永遠不是垃圾。常見的來源：

  • 只放不拿的 static 集合或快取：靜態欄位是 GC Root，Map 裡的東西一直可達。
  • 沒關的資源：連線、檔案、串流沒關，背後的作業系統資源與緩衝區就一直占著，用 try-with-resources（見〈例外機制〉）。
  • ThreadLocal 用完沒 remove：ThreadLocal 的文件說，每條執行緒「只要還活著、而且 ThreadLocal 實體可存取」，就持有它那份副本的隱含參考；執行緒消失後副本才可以被回收。出處 執行緒池裡的執行緒不會消失，所以要在用完時呼叫 remove()，〈執行緒池與並行工具〉會實跑。
  • 註冊了沒取消的監聽器：長壽的事件來源抓著監聽器，監聽器又抓著一大串物件。
  • 類別載入器洩漏：只要載入器載出的類別還有實體活著，整個載入器和它所有類別的中繼資料都留在 Metaspace；上一段的 Meta 就是刻意做出來的版本。

找洩漏最便宜的第一步是看類別直方圖：哪個類別的實體最多、占最多位元組。下面的程式模擬一個只放不拿的 session 快取：

public class Leak {
    record Session(String user, byte[] payload) {}

    static final Map<String, Session> CACHE = new HashMap<>();   // 只放不拿：典型洩漏

    public static void main(String[] args) throws Exception {
        for (int i = 0; ; i++) {
            CACHE.put("session-" + i, new Session("u" + i, new byte[1024]));
            if (i % 1_000 == 0) Thread.sleep(50);
        }
    }
}
// 執行中另開一個終端機：jcmd 30 GC.class_histogram（節錄）
//  num     #instances         #bytes  class name (module)
// -------------------------------------------------------
//    1:        248079       88034000  [B (java.base@21.0.12.1)
//    2:        167997        4031928  java.lang.String (java.base@21.0.12.1)
//    3:         81018        2592576  java.util.HashMap$Node (java.base@21.0.12.1)
//    4:         80001        1920024  Leak$Session

[B 是 byte[]：Class.getName 的文件規定陣列類別名稱用 [ 加元素型別的編碼，byte 編成 B。出處 八萬多個 Leak$Session、同樣多的 HashMap$Node，而且每跑一次數字都變大，就是一直有人往 Map 裡放、沒人拿出來。要看「是誰抓著它們」，就要抓 heap dump（jcmd <pid> GC.heap_dump），用分析工具看從 GC Root 到這些物件的參考鏈。

下面哪一種寫法最可能造成記憶體洩漏？

  • 方法裡 new 了大陣列，方法結束後沒再用
  • 往 static Map 放了從不移除
  • 兩個物件互相參考，之後都沒人用
  • 在迴圈裡大量建立用完就丟的字串

static Map 從 GC Root 可達，放進去的東西永遠不會變成垃圾。「方法結束後沒再用的大陣列」「互相參考、之後都沒人用的兩個物件」「用完就丟的字串」在沒人參考後都會被回收，用完就丟的短命字串正是年輕代最擅長處理的情況。

執行緒池裡的執行緒用 ThreadLocal 存了一個大物件，用完沒呼叫 remove()，會怎樣？

  • 執行緒回到池子時 JVM 會自動清掉
  • 副本一直被執行緒抓著，還可能被下個任務讀到
  • 下一次 GC 一定會把它回收
  • 呼叫者會立刻收到 IllegalStateException

ThreadLocal 文件：執行緒活著且 ThreadLocal 可存取，就持有副本的隱含參考；池裡的執行緒不會消失，所以要自己 remove()。

類別直方圖裡 [B 排第一、占八千多萬位元組，[B 是什麼？

  • 一個叫 B 的自訂類別
  • byte 陣列
  • boolean 欄位
  • 類別載入器

類別什麼時候進來、由誰載入

類別載入、連結、初始化與雙親委派

JVMS 第 5 章：JVM「動態地載入、連結、初始化類別與介面」。載入是「找到某個名稱的類別的二進位表示，並據此建立類別」；連結是「把類別結合進 JVM 的執行期狀態，讓它可以執行」；初始化是「執行類別的初始化方法 <clinit>」，也就是靜態欄位的初始值與 static 區塊。出處

初始化是懶的。JLS 12.4.1：類別「在下列任一事件第一次發生之前立刻初始化」：建立它的實體、呼叫它的靜態方法、對它的靜態欄位賦值、使用它的靜態欄位「而且那個欄位不是常數變數」。出處 常數變數（static final 而且值是編譯期常數）在編譯時就被抄進使用它的地方，讀它不會觸發初始化：

class Rates {
    static final int SCALE = 2;                    // 編譯期常數
    static double usd = load();                    // 要執行程式才知道的值
    static {
        System.out.println("Rates 初始化了");
    }
    static double load() { return 32.5; }
}

public class Init {
    public static void main(String[] args) throws Exception {
        System.out.println("1. 讀常數 SCALE = " + Rates.SCALE);
        System.out.println("2. 準備讀 usd");
        System.out.println("3. usd = " + Rates.usd);
        System.out.println("4. 再讀一次 usd = " + Rates.usd);
    }
}

// 2. 準備讀 usd
// Rates 初始化了
// 3. usd = 32.5
// 4. 再讀一次 usd = 32.5

三個內建載入器與雙親委派。ClassLoader 的文件：Java 執行期內建三個載入器：啟動類別載入器（bootstrap）「是虛擬機內建的載入器，通常以 null 表示，沒有父載入器」；平台類別載入器（platform）負責載入平台類別，也就是 Java SE 平台 API 與它們的實作；系統類別載入器（system）「也叫應用程式類別載入器」，通常用來載入應用程式類別路徑與模組路徑上的類別。而且「每個 ClassLoader 實體都有一個關聯的父載入器；被要求找類別或資源時，通常會先把搜尋委派給父載入器，再嘗試自己找」（a ClassLoader instance will usually delegate the search for the class or resource to its parent class loader before attempting to find the class or resource itself）。出處 這就是常說的雙親委派（parent delegation，先問父親，父親找不到才自己找）。好處是 java.lang.String 這類核心類別一定由上層載入器定義，自己在類別路徑放一個同名類別也搶不到。

為什麼剛啟動比較慢

JIT 與分層編譯

Java 程式不是一開始就跑機器碼。JVM 指南：HotSpot「一開始用標準的直譯器啟動應用程式」，程式跑起來後分析出效能瓶頸，也就是熱點（hot spots），再把「效能關鍵的那部分程式碼」編譯成機器碼，很少用到的程式碼（應用程式的大部分）就不編。出處 這就是 JIT（Just-In-Time，執行中才編譯）。分層編譯（tiered compilation）在 Java SE 7 引入：先用用戶端編譯器（C1）產生「會自己收集側寫資訊的編譯版本」，它比直譯器快得多，所以側寫（profiling，記錄哪個分支常走、哪個型別常出現）的階段也跑得快；最後再由伺服器編譯器（C2）產生最佳化最深的版本。它預設開啟，可以用 -XX:-TieredCompilation 關掉。出處

不必背每一欄的意思，只要看出一件事：同一個 Churn::main 在幾十毫秒內出現了好幾行，也就是被編譯了不只一個版本，越後面的越晚才出現。這就是分層編譯在「先快速編一版、側寫夠了再編更好的一版」。所以壓測要先跑一段「暖機」再計時，剛部署的服務前幾分鐘延遲偏高也是正常的。

  • 先用直譯器執行，熱點才編譯
  • 交給作業系統直接執行 .class 檔
  • 用 C2 編譯器一次編好所有方法

JVM 指南：用標準直譯器啟動，分析出熱點後才編譯效能關鍵的部分，很少用到的程式碼不編。

為什麼壓力測試要先跑一段時間「暖機」再開始計時？

  • 因為 JVM 要先下載更新
  • 因為垃圾回收器要先把堆填滿
  • 熱點要跑一陣子才被分層編譯完
  • 因為剛啟動時 CPU 頻率比較低

剛啟動在直譯器裡跑，熱點浮現後先由 C1 編譯並收集側寫，再由 C2 深度最佳化。實跑時同一個 main 被編了好幾個版本，量測要等最佳化完成。

重點整理

  • 五塊執行期資料區：堆與方法區（HotSpot 叫 Metaspace，在原生記憶體）所有執行緒共用；JVM 堆疊、pc 暫存器、本機方法堆疊每條執行緒一份，所以區域變數天生不必同步。
  • 依弱分代假說，新物件進 Eden，年輕代回收只看活物件所以很快；在兩塊 Survivor 之間被複製夠多次才晉升老年代。最大堆預設是實體記憶體的 1/4，啟動時只保留位址空間。
  • 物件死活看可達性：從 GC Root（堆疊上的變數、靜態欄位等）走不到就是垃圾，循環參考不是問題。
  • Serial 單執行緒、Parallel 拚吞吐、G1 有停頓目標（預設 200 毫秒，軟性）、ZGC 停頓一毫秒內。Java 21 在兩顆以上 CPU、1792 MB 以上預設 G1，否則 Serial；分代 ZGC 在 21 要加 -XX:+ZGenerational，24 起只剩分代。
  • OOM 看訊息：Java heap space 是堆、Metaspace 是類別、direct buffer memory 是堆外、unable to create native thread 是執行緒；StackOverflowError 是堆疊太深，不是 OOM。G1 裡大於等於半個區域的是巨型物件，很吃空間。
  • 洩漏是長壽的東西抓著該死的東西：static 集合、沒關的資源、沒 remove 的 ThreadLocal、沒取消的監聽器、類別載入器。先看類別直方圖，再抓 heap dump 看參考鏈。
  • 類別載入分載入、連結、初始化；初始化是懶的，讀常數變數不觸發。載入器有啟動、平台、應用程式三層，先委派給父親。JIT 先直譯、再分層編譯熱點，所以要暖機。卡住先 jcmd Thread.print，長期問題開 JFR。
