讀完這課你會

  • 把一條 Stream 拆成來源、中間操作、終端操作三段，說明「沒有終端操作就不執行」與「一條流只能用一次」
  • 用 filter、map、flatMap、sorted、limit 這些中間操作，配上 collect、reduce、anyMatch、toList() 這些終端操作，讀懂一段 Stream 會輸出什麼
  • 用 Collectors 依分行分組加總、計數、分成兩組、串成字串，知道 toMap 鍵重複會丟例外
  • 知道基本型別流省掉裝箱、平行流的代價，並判斷什麼時候一般迴圈比較好

先看整條管線長什麼樣子

一條流的三段：來源、中間操作、終端操作

上一課〈Lambda 與函式介面〉把「一段行為」變成可以傳的參數；Stream API（Java 8 起）就是一整套收這種參數的方法，讓「篩選、轉換、加總」這類迴圈改寫成一條由方法串起來的管線（pipeline）。套件說明：一條管線「由一個來源（例如集合、陣列、產生器函式或 I/O 通道），接著零個或多個中間操作，例如 Stream.filter 或 Stream.map，再加上一個終端操作，例如 Stream.forEach 或 Stream.reduce」組成（A stream pipeline consists of a source (such as a Collection, an array, a generator function, or an I/O channel); followed by zero or more intermediate operations such as Stream.filter or Stream.map; and a terminal operation such as Stream.forEach or Stream.reduce.）。出處

這兩課的例子都用同一份交易清單（record 是精簡資料類別，見〈現代 Java 語法：var、record、switch、文字區塊與 sealed〉）：

record Tx(String id, String branch, long amount) {}

List<Tx> txs = List.of(
        new Tx("T1", "信義", 12_000),
        new Tx("T2", "大安", 3_500),
        new Tx("T3", "信義", 80_000),
        new Tx("T4", "松山", 45_000),
        new Tx("T5", "大安", 150_000),
        new Tx("T6", "信義", 7_200));

「一萬元以上的交易加總」寫成迴圈與寫成 Stream：

long loopTotal = 0;
for (Tx tx : txs) {
    if (tx.amount() >= 10_000) {
        loopTotal += tx.amount();
    }
}
System.out.println(loopTotal);   // 287000

long total = txs.stream()                         // 來源
        .filter(tx -> tx.amount() >= 10_000)      // 中間操作：留下一萬以上
        .mapToLong(Tx::amount)                    // 中間操作：取出金額
        .sum();                                   // 終端操作：加總
System.out.println(total);       // 287000

流跟集合長得像，但不一樣。套件說明列的第一點就是「不儲存資料：流不是存放元素的資料結構，它把元素從來源經過一連串運算送出去」（No storage. A stream is not a data structure that stores elements; instead, it conveys elements from a source ...）；第二點是「流的操作會產生結果，但不修改來源」（An operation on a stream produces a result, but does not modify its source.）。出處 所以對清單做 sorted() 得到的是新結果，原本的清單順序不變。

來源 → 零個或多個中間操作 → 一個終端操作；流不存資料，也不改來源

在 txs.stream().filter(tx -> tx.amount() >= 10_000).mapToLong(Tx::amount).sum() 裡，哪一個是終端操作？

  • stream()
  • filter(...)
  • mapToLong(...)
  • sum()

stream() 取得來源；filter、mapToLong 回傳新的流，是中間操作；sum() 產生一個值、結束整條管線，是終端操作。

這段程式印出什麼？

List<Long> amounts = new ArrayList<>(List.of(3L, 1L, 2L));
List<Long> sorted = amounts.stream().sorted().toList();
System.out.println(amounts + " " + sorted);
  • [1, 2, 3] [1, 2, 3]
  • [3, 1, 2] [1, 2, 3]
  • [3, 1, 2] [3, 1, 2]
  • [1, 2, 3] [3, 1, 2]

流的操作產生新結果、不修改來源，所以 amounts 還是 [3, 1, 2]；排好的是 toList() 收集出來的那份新清單。

用上面的 txs，這段程式印出什麼？

long sum = txs.stream()
        .filter(tx -> tx.branch().equals("信義"))
        .mapToLong(Tx::amount)
        .sum();
System.out.println(sum);
  • 92000
  • 287000
  • 99200
  • 3

信義的三筆是 T1 12,000、T3 80,000、T6 7,200，加起來 99,200。3 是筆數，要用 count() 才會得到。

下面哪一句話描述了流（Stream）和集合的差別？

  • 流不儲存元素，只負責送過運算
  • 流一定比集合快，因為它會自動平行處理
  • 流可以用索引直接取第 n 個元素
  • 流處理完，會把結果寫回原本的集合裡取代舊資料

套件說明列的第一點就是「不儲存資料」。流預設是循序的，要明確要求才會平行；它沒有用索引取值的方法；它也不修改來源。

long n = txs.stream().count(); 中間一個中間操作都沒有，會怎樣？

  • 可以，n 是 6
  • 編譯錯誤，至少要有一個中間操作
  • 執行時丟出 IllegalStateException
  • 可以，但 n 是 0，因為沒有東西流過

管線是「來源、零個或多個中間操作、一個終端操作」，中間操作可以一個都沒有。count() 回傳元素個數，txs 有 6 筆。

什麼時候真的開始跑

惰性求值與「一條流只能用一次」

惰性求值（lazy evaluation，要用到結果時才真的計算）是 Stream 最容易出錯的地方。套件說明：「中間操作一律是惰性的；執行像 filter() 這樣的中間操作，並不會真的篩選……在管線的終端操作執行之前，不會開始走訪來源」（Intermediate operations return a new stream. They are always lazy ... Traversal of the pipeline source does not begin until the terminal operation of the pipeline is executed.）。出處 下面在 lambda 裡印字，看清楚每一步什麼時候發生：

Stream<String> s = Stream.of("a", "bb", "ccc")
        .filter(x -> {
            System.out.println("filter " + x);
            return x.length() > 1;
        })
        .map(x -> {
            System.out.println("map " + x);
            return x.toUpperCase();
        });
System.out.println("還沒有終端操作");
List<String> result = s.toList();
System.out.println(result);
// 還沒有終端操作
// filter a
// filter bb
// map bb
// filter ccc
// map ccc
// [BB, CCC]

兩件事要看出來：第一，「還沒有終端操作」最先印，前面串好的 filter、map 一行都沒跑；第二，不是「全部 filter 完再全部 map」，而是一筆一筆走完整條管線。套件說明說，惰性讓篩選、轉換、加總可以「合併成走一次資料」（can be fused into a single pass on the data）。出處

惰性也讓短路（short-circuiting，答案確定就提早停下）成為可能。findFirst、anyMatch、limit 都是短路操作；找第一筆五萬以上的交易，看到 T3 就停了：

Optional<Tx> firstLarge = txs.stream()
        .peek(tx -> System.out.println("看過 " + tx.id()))
        .filter(tx -> tx.amount() >= 50_000)
        .findFirst();
System.out.println(firstLarge.map(Tx::id).orElse("沒有"));
// 看過 T1
// 看過 T2
// 看過 T3
// T3

只能用一次：套件說明把流列為「可消耗的」：「流的元素在它的生命期間只會被走訪一次。跟 Iterator 一樣，要再走一次同樣的元素，就得產生新的流」（The elements of a stream are only visited once during the life of a stream. Like an Iterator, a new stream must be generated to revisit the same elements of the source.）。出處 Stream 的文件說，實作在偵測到重複使用時「可能丟出 IllegalStateException」（A stream implementation may throw IllegalStateException if it detects that the stream is being reused.）。出處

Stream<Tx> once = txs.stream();
System.out.println(once.count());   // 6
once.count();
// 丟出 IllegalStateException: stream has already been operated upon or closed

要重複用，就把「怎麼產生流」存起來，例如每次都呼叫 txs.stream()，或存成 Supplier<Stream<Tx>>，而不是把同一個流物件傳來傳去。

終端操作不一定會跑完整條管線：count() 的文件說，如果能直接從來源算出筆數，實作「可以選擇不執行管線」，這時「不會走訪任何來源元素，也不會執行任何中間操作」（In such cases no source elements will be traversed and no intermediate operations will be evaluated.）。它舉的例子正是 List 加上 peek(System.out::println) 再 count()，結果不會印出任何元素。出處 在 Java 21 實跑 List.of("A", "B", "C").stream().peek(System.out::println).count()，確實只得到 3、什麼都沒印。所以不要把要做的事寫在 peek 裡。

這段程式印出什麼？

Stream.of("A", "B").peek(System.out::println);
System.out.println("完");
  • A 換行 B 換行 完
  • 完
  • 完 換行 A 換行 B
  • 編譯錯誤，peek 的結果沒有被使用

peek 是中間操作，後面沒有終端操作，整條管線不會執行，A、B 都不會印出。Java 不會因為沒用到回傳值而編譯錯誤。

這段程式依序印出什麼？

Stream.of("a", "bb")
        .filter(x -> { System.out.println("filter " + x); return x.length() > 1; })
        .map(x -> { System.out.println("map " + x); return x; })
        .toList();
  • filter a、filter bb、map a、map bb
  • filter a、map a、filter bb、map bb
  • filter a、filter bb、map bb
  • map a、map bb、filter a、filter bb

元素一筆一筆走完整條管線：a 在 filter 被擋下，不會進 map；bb 通過 filter 後馬上進 map。不是全部篩完才全部轉換。

這段程式印出什麼？

Optional<Integer> first = Stream.of(1, 2, 3, 4, 5)
        .peek(x -> System.out.print(x + " "))
        .filter(x -> x > 2)
        .findFirst();
System.out.println("→ " + first.get());
  • 1 2 3 4 5 → 3
  • 3 → 3
  • 1 2 3 4 5 → 5
  • 1 2 3 → 3

findFirst 是短路的終端操作，找到第一個大於 2 的元素（3）就停，4、5 不會流進 peek。

Stream<Tx> once = txs.stream(); once.count(); once.count(); 第二次 count() 會怎樣？

  • 丟出 IllegalStateException
  • 照樣回傳 6，流可以重複使用
  • 回傳 0，因為元素在第一次就被讀完了
  • 編譯錯誤

終端操作執行後，管線就被消耗掉了；再用同一個流，JDK 的實作丟出 IllegalStateException: stream has already been operated upon or closed。編譯器看不出這件事，所以能編譯。

這段程式第三行會怎樣？

Stream<Tx> s = txs.stream();
Stream<Tx> large = s.filter(tx -> tx.amount() >= 50_000);
Stream<Tx> small = s.filter(tx -> tx.amount() < 50_000);
  • 丟出 IllegalStateException
  • 沒事，large 與 small 各自拿到一半的交易
  • 沒事，但 small 是空的，因為元素被 large 拿走了
  • 編譯錯誤，filter 不能呼叫兩次

文件說一個流只應該被操作（呼叫中間或終端操作）一次，並明確排除「同一個來源分岔給兩條管線」。對 s 呼叫第二次 filter 時，JDK 的實作就丟出 IllegalStateException。要分兩組就各自呼叫 txs.stream()，或用後面的 partitioningBy。

long n = list.stream().peek(System.out::println).count();，list 有三個元素。下面哪個說法正確？

  • 一定會印出三個元素
  • 一定只印出第一個元素
  • 編譯錯誤，peek 後面不能直接接 count 這種終端操作
  • 不一定會印出任何元素

count() 的文件以這個例子說明：來源是 List、peek 不增減元素，筆數就是清單大小，不必執行管線，也就不會印。Java 21 實跑確實什麼都沒印。

這段程式印出什麼？（改寫自 java.util.stream 套件說明的例子）

List<String> l = new ArrayList<>(List.of("one", "two"));
Stream<String> sl = l.stream();
l.add("three");
System.out.println(sl.collect(Collectors.joining(" ")));
  • one two
  • one two three
  • 丟出 ConcurrentModificationException
  • three

建立流的時候還沒開始走訪；清單是在終端操作 collect 開始之前被修改的，所以修改會反映進結果。套件說明說，JDK 集合產生的流都是這樣。執行途中才改來源，才會出問題。

這段程式印出什麼？

boolean found = Stream.of(5, 20, 7)
        .peek(x -> System.out.print(x + " "))
        .anyMatch(x -> x > 10);
System.out.println(found);
  • 5 20 true
  • 5 20 7 true
  • 20 true
  • 5 20 7 false

anyMatch 是短路操作，「可能不會對所有元素評估條件」。看到 20 就確定答案是 true，7 不會流過來。

每一段回傳新的流

常用的中間操作

操作做什麼要記得的事
filter(條件)留下符合條件的元素條件是 Predicate
map(函式)每個元素換成另一個值，型別可以變一進一出
flatMap(函式)每個元素換成一個流，再把這些流攤平接成一條一進多出（也可以是零）
distinct()去掉重複（依 equals）有順序的流保留第一次出現的那個
sorted()／sorted(比較器)排序有順序的流是穩定排序；要看完全部元素才能輸出
limit(n)最多留前 n 個短路操作
skip(n)丟掉前 n 個不足 n 個就得到空的流
peek(動作)元素經過時做一個動作，元素原樣往下傳主要給除錯用

表中「要記得的事」一欄都來自 Stream 的方法說明：flatMap「把每個元素換成套用函式後產生的流的內容」，效果是「一對多的轉換，再把產生的元素攤平成一條新的流」（The flatMap() operation has the effect of applying a one-to-many transformation to the elements of the stream, and then flattening the resulting elements into a new stream.）；distinct「對有順序的流，挑選是穩定的（重複的元素保留順序中最先出現的那一個）」；sorted「對有順序的流，排序是穩定的」（For ordered streams, the sort is stable.）；skip 在元素少於 n 個時「回傳空的流」；peek「這個方法主要是為了支援除錯」（This method exists mainly to support debugging）。出處 穩定排序（stable sort）是指比較結果相等的元素，排完仍維持原本的先後。distinct、sorted 是有狀態的操作，套件說明舉例「看完流的所有元素之前，排序產生不了任何結果」（one cannot produce any results from sorting a stream until one has seen all elements of the stream）。出處

record Account(String id, List<Long> deposits) {}

List<Account> accounts = List.of(
        new Account("A001", List.of(1_000L, 2_500L)),
        new Account("A002", List.of(800L)),
        new Account("A003", List.of()));
List<Long> allDeposits = accounts.stream()
        .flatMap(acct -> acct.deposits().stream())   // 每個帳戶換成它的存款流，再接成一條
        .toList();
System.out.println(allDeposits);   // [1000, 2500, 800]

List<String> branches = txs.stream()
        .map(Tx::branch)
        .distinct()
        .toList();
System.out.println(branches);      // [信義, 大安, 松山]

List<String> page2 = txs.stream()
        .sorted(Comparator.comparingLong(Tx::amount))   // 金額小到大
        .skip(2)                                        // 每頁兩筆，跳過第一頁
        .limit(2)
        .map(Tx::id)
        .toList();
System.out.println(page2);         // [T1, T4]

上面 accounts 的例子，如果把 flatMap(acct -> acct.deposits().stream()) 改成 map(acct -> acct.deposits())，toList() 得到什麼？

  • [1000, 2500, 800]
  • [[1000, 2500], [800], []]
  • [[1000, 2500], [800]]
  • 編譯錯誤，map 的函式不能回傳一整個清單

map 一進一出：三個帳戶換成三個清單（第三個是空清單），不會攤平，也不會丟掉空的。要把清單裡的元素接成一條流，才用 flatMap。

這段程式印出什麼？

long n = Stream.of("A001 A002", "B001")
        .flatMap(s -> Arrays.stream(s.split(" ")))
        .count();
System.out.println(n);
  • 2
  • 1
  • 3
  • 4

第一個字串切成 A001、A002 兩個，第二個是 B001 一個，攤平後共 3 個元素。用 map 的話得到的是 2 個陣列。

這段程式印出什麼？

System.out.println(Stream.of(3, 1, 3, 2, 1).distinct().toList());
  • [1, 2, 3]
  • [3, 1, 2]
  • [2]
  • [3, 1, 3, 2, 1]

distinct 只去重複、不排序；有順序的流保留第一次出現的元素，順序照原本的 3、1、2。只出現一次的元素是 2，但 distinct 不是挑這個。

這段程式印出什麼？

System.out.println(Stream.of(3, 1, 2).sorted(Comparator.reverseOrder()).toList());
  • [1, 2, 3]
  • [3, 1, 2]
  • [2, 1, 3]
  • [3, 2, 1]

Comparator.reverseOrder() 是自然順序的相反，整數就是由大到小。

這段程式印出什麼？

System.out.println(Stream.of(10, 20, 30, 40, 50).skip(1).limit(3).toList());
  • [20, 30, 40]
  • [10, 20, 30]
  • [20, 30]
  • [40, 50]

先丟掉第一個（10），剩下 20、30、40、50，再留前三個。

把上一題換成 .limit(3).skip(1)，印出什麼？

  • [20, 30, 40]
  • [20, 30]
  • [10, 20]
  • [30, 40, 50]

順序換了結果就不同：先留前三個（10、20、30），再丟掉第一個，剩 20、30。管線照寫的順序一段一段處理。

這段程式印出什麼？

System.out.println(Stream.of("bb", "a", "cc", "d")
        .sorted(Comparator.comparingInt(String::length))
        .toList());
  • [a, d, cc, bb]
  • [d, a, bb, cc]
  • [a, d, bb, cc]
  • [a, bb, cc, d]

只比長度：a、d 一個字在前，bb、cc 兩個字在後。長度相同的元素，穩定排序維持原本的先後：a 原本在 d 前、bb 原本在 cc 前。

依 Stream 的 API 說明，peek 主要是用來做什麼的？

  • 除錯時看元素流過的樣子
  • 把元素寫進資料庫
  • 修改元素的內容再往下傳
  • 保證每個元素一定都被處理到一次

文件：「這個方法主要是為了支援除錯」。短路操作或 count() 可能讓 peek 根本不被呼叫，所以不要把該做的事寫在裡面。

這段程式印出什麼？

System.out.println(Stream.of("A001", "B02", "C3").map(String::length).toList());
  • [A001, B02, C3]
  • [4, 3, 2]
  • [9]
  • [3]

map 把每個字串換成它的長度，元素型別從 String 變成 Integer，個數不變。

txs.stream().filter(a).filter(b) 和 txs.stream().filter(tx -> a.test(tx) && b.test(tx))（a、b 都是 Predicate<Tx>，而且沒有副作用）留下的元素一樣嗎？

  • 不一樣，前者等於 a 或 b
  • 不一樣，前者會把元素處理兩次所以重複
  • 一樣，都是同時符合 a 與 b 的元素
  • 不一樣，前者只套用最後一個 filter

每個元素先經過 a，通過了才到 b，兩關都過才留下，等同於 &&。挑哪種寫法看可讀性。

一條管線的結尾

終端操作：collect、reduce、match、find、toList

操作回傳要記得的事
forEach(動作)沒有平行流時不保證照順序；要照順序用 forEachOrdered
collect(收集器)收集器決定（清單、Map、字串……）下一段的 Collectors
reduce(初始值, 合併函式)一個值不給初始值的版本回傳 Optional
count()long可能不執行管線
anyMatch／allMatch／noneMatchboolean短路；空的流：any 是 false，all 與 none 是 true
findFirst()Optional空的流得到空的 Optional
min／max(比較器)Optional空的流得到空的 Optional
toList()（Java 16 起）不可修改的 List改它會丟 UnsupportedOperationException

表中的根據，都在 Stream 的方法說明裡：forEach「的行為明確是不確定的」（The behavior of this operation is explicitly nondeterministic.），平行時不保證照順序；anyMatch「如果流是空的，回傳 false，而且不評估條件」（If the stream is empty then false is returned and the predicate is not evaluated.），allMatch、noneMatch 在空的流則回傳 true；findFirst、min、max 在空的流回傳空的 Optional；toList()「回傳的 List 是不可修改的，呼叫任何修改方法都一定會丟出 UnsupportedOperationException」（The returned List is unmodifiable; calls to any mutator method will always cause UnsupportedOperationException to be thrown.），它標示 Since 16。出處 舊寫法 collect(Collectors.toList()) 則「對回傳 List 的型別、可變性……沒有任何保證」（There are no guarantees on the type, mutability, serializability, or thread-safety of the List returned），需要能修改的清單就用 Collectors.toCollection(ArrayList::new) 指定。出處

long sum = txs.stream().map(Tx::amount).reduce(0L, Long::sum);
System.out.println(sum);                                                   // 297700
System.out.println(txs.stream().anyMatch(tx -> tx.amount() > 100_000));    // true
System.out.println(txs.stream().allMatch(tx -> tx.amount() > 0));          // true
System.out.println(txs.stream().noneMatch(tx -> tx.branch().equals("中山"))); // true
Optional<Tx> max = txs.stream().max(Comparator.comparingLong(Tx::amount));
System.out.println(max.map(Tx::id).orElse("沒有"));                         // T5

List<String> ids = txs.stream().map(Tx::id).toList();
ids.add("T7");   // 丟出 UnsupportedOperationException
List<String> mutable = txs.stream().map(Tx::id).collect(Collectors.toCollection(ArrayList::new));
mutable.add("T7");
System.out.println(mutable);   // [T1, T2, T3, T4, T5, T6, T7]

  • 24

從初始值 0 開始，逐一用 Integer::sum 合併：0+1+2+3+4 = 10。給了初始值的 reduce 直接回傳值，不是 Optional。24 是相乘的結果。

用上面的 txs，txs.stream().max(Comparator.comparingLong(Tx::amount)) 的結果是什麼？

分組、計數、串字串

Collectors：toList、toMap、groupingBy、partitioningBy、joining

collect 要一個收集器（Collector），告訴它「元素怎麼收」。Collectors 類別備好了常用的，它的類別說明就列了收成清單、依部門分組、依部門加總薪水、分成及格與不及格這些例子。出處 換成銀行的情境：

// 依分行分組加總金額（傳 TreeMap::new 讓鍵排好序，印出來比較好比對）
Map<String, Long> sumByBranch = txs.stream()
        .collect(Collectors.groupingBy(Tx::branch, TreeMap::new,
                Collectors.summingLong(Tx::amount)));
System.out.println(sumByBranch);    // {信義=99200, 大安=153500, 松山=45000}

// 依分行計數
Map<String, Long> countByBranch = txs.stream()
        .collect(Collectors.groupingBy(Tx::branch, TreeMap::new, Collectors.counting()));
System.out.println(countByBranch);  // {信義=3, 大安=2, 松山=1}

// 依分行列出交易編號
Map<String, List<String>> idsByBranch = txs.stream()
        .collect(Collectors.groupingBy(Tx::branch, TreeMap::new,
                Collectors.mapping(Tx::id, Collectors.toList())));
System.out.println(idsByBranch);    // {信義=[T1, T3, T6], 大安=[T2, T5], 松山=[T4]}

// 分成大額（五萬以上）與非大額兩組
Map<Boolean, List<String>> largeOrNot = txs.stream()
        .collect(Collectors.partitioningBy(tx -> tx.amount() >= 50_000,
                Collectors.mapping(Tx::id, Collectors.toList())));
System.out.println(largeOrNot);     // {false=[T1, T2, T4, T6], true=[T3, T5]}

// 串成一個字串
String joined = txs.stream().map(Tx::id).collect(Collectors.joining(", ", "[", "]"));
System.out.println(joined);         // [T1, T2, T3, T4, T5, T6]

// 金額最大的前三筆
List<Tx> top3 = txs.stream()
        .sorted(Comparator.comparingLong(Tx::amount).reversed())
        .limit(3)
        .toList();
top3.forEach(tx -> System.out.println(tx.id() + " " + tx.amount()));
// T5 150000
// T3 80000
// T4 45000

幾個要記得的規則，都來自 Collectors 的方法說明：出處

  • groupingBy(分類函式) 產生 Map<K, List<T>>，第二個參數可以接「下游收集器」（downstream collector，對每一組再做一次收集），例如 counting()、summingLong、mapping。回傳的 Map「對型別、可變性……沒有任何保證」，所以要固定順序就像上面傳 TreeMap::new。
  • counting() 的結果型別是 Long（簽名是 Collector<T,?,Long>），所以計數的 Map 是 Map<String, Long>，不是 Integer。summingLong 在沒有元素時結果是 0。
  • partitioningBy(條件) 把元素分成 true、false 兩組，而且「回傳的 Map 一定同時有 false 與 true 兩個鍵」（The returned Map always contains mappings for both false and true keys.），某一組沒有元素時值是空清單。
  • toMap(取鍵, 取值)：「如果取出的鍵有重複（依 Object.equals），收集時會丟出 IllegalStateException」（If the mapped keys contain duplicates (according to Object.equals(Object)), an IllegalStateException is thrown when the collection operation is performed.）；鍵可能重複就用三個參數的版本，第三個是合併函式（merge function，遇到同一個鍵時決定兩個值怎麼合成一個）。
  • joining(分隔字串, 前綴, 後綴) 依流的順序把元素串起來，前後加上前綴與後綴。
txs.stream().collect(Collectors.toMap(Tx::branch, Tx::amount));
// 丟出 IllegalStateException: Duplicate key 信義 (attempted merging values 12000 and 80000)

Map<String, Long> merged = txs.stream()
        .collect(Collectors.toMap(Tx::branch, Tx::amount, Long::sum, TreeMap::new));
System.out.println(merged);   // {信義=99200, 大安=153500, 松山=45000}

分組加總用 groupingBy＋summingLong 或 toMap＋Long::sum 都得到同樣的結果；前者讀起來就是「依分行分組、組內加總」，後者在鍵重複時才合併。

用上面的 txs，groupingBy(Tx::branch, Collectors.summingLong(Tx::amount)) 得到的 Map 裡，「大安」對到多少？

  • 2
  • 150000
  • 3500
  • 153500

大安有 T2（3,500）與 T5（150,000）兩筆，下游收集器 summingLong 把同一組的金額加起來：153,500。2 是筆數，要用 counting()。

Map<String, ???> m = txs.stream().collect(Collectors.groupingBy(Tx::branch, Collectors.counting()));，??? 要填什麼型別才能編譯？

  • Integer
  • Long
  • int
  • List<Tx>

counting() 的簽名是 Collector<T,?,Long>，結果是 Long。泛型裡不能放基本型別 int；填 Integer 會型別不符。

txs.stream().collect(Collectors.toMap(Tx::branch, Tx::amount)) 會怎樣？

  • 得到每家分行第一筆的金額
  • 得到每家分行的金額總和
  • 丟出例外

信義有三筆，鍵重複。兩個參數的 toMap 遇到重複鍵就丟 IllegalStateException（訊息是 Duplicate key 信義 ...），不會自己挑一筆或加總。

Collectors.toMap(Tx::branch, Tx::amount, Long::sum) 得到的 Map 裡，「信義」對到多少？

  • 99200
  • 7200
  • 12000
  • 3

第三個參數是合併函式，同一個鍵的值用 Long::sum 合併：12,000＋80,000＋7,200 = 99,200。跟 groupingBy＋summingLong 結果相同。

這段程式印出什麼？

Map<Boolean, Long> m = txs.stream()
        .collect(Collectors.partitioningBy(tx -> tx.amount() > 1_000_000,
                Collectors.counting()));
System.out.println(m);
  • {false=6}
  • {false=6, true=0}
  • {true=0}
  • {}

沒有任何一筆超過一百萬，但 partitioningBy 回傳的 Map 一定同時有 false 與 true 兩個鍵；true 那組沒有元素，計數是 0。

這段程式印出什麼？

System.out.println(Stream.of("A", "B", "C")
        .collect(Collectors.joining("-", "(", ")")));
  • A-B-C
  • (A)-(B)-(C)
  • (A-B-C)
  • (-A-B-C-)

joining(分隔, 前綴, 後綴)：元素之間放分隔字串，整串的最前與最後各放一次前綴與後綴，不是每個元素都包一次。

groupingBy(Tx::branch, Collectors.mapping(Tx::id, Collectors.toList())) 得到的 Map 裡，「信義」對到什麼？

  • T1、T3、T6 三筆交易物件組成的清單
  • 三個交易編號字串
  • 3
  • [12000, 80000, 7200]

mapping(Tx::id, toList()) 先把每筆交易換成編號，再收成清單，所以值是 List<String>。不加 mapping 的 groupingBy(Tx::branch) 才是交易物件的清單。

用上面的 txs，要「金額最大的前三筆」，下面哪一段結果是 T5、T3、T4？

  • sorted(comparingLong(Tx::amount).reversed()).limit(3)
  • sorted(comparingLong(Tx::amount)).limit(3)
  • limit(3).sorted(comparingLong(Tx::amount).reversed())
  • sorted(comparingLong(Tx::amount)).skip(3)

先由大到小排、再取前三。沒有 reversed 的版本取到最小的三筆；先 limit 再 sorted 只排了 T1、T2、T3 這三筆；skip(3) 留下的是最大三筆但順序由小到大（T4、T3、T5）。

groupingBy(Tx::branch) 回傳的 Map，鍵的走訪順序有保證嗎？

  • 有，照分行第一次出現的順序
  • 有，照鍵的字母或筆畫順序
  • 沒有保證
  • 有，照每組元素的數量由多到少排列

文件寫明對回傳 Map 的型別「沒有任何保證」。三個參數的 groupingBy(分類, Map 工廠, 下游) 可以指定 TreeMap::new（依鍵排序）或 LinkedHashMap::new（依放入順序）。

要把交易分成「大額」與「非大額」兩組，哪個收集器最直接？

  • Collectors.joining
  • Collectors.toMap
  • Collectors.counting
  • Collectors.partitioningBy

依一個是非條件分兩組正是 partitioningBy，結果是 Map<Boolean, List<Tx>>，而且兩組都一定在。groupingBy 也做得到，但某組沒有元素時那個鍵就不會出現。

int、long、double 專用的流

基本型別流：IntStream、mapToInt、sum、average、range

Stream<Long> 裡每個元素都是包裝物件。套件說明列出四種流：「Stream、IntStream、LongStream、DoubleStream，分別是物件與基本型別 int、long、double 的流」（are streams over objects and the primitive int, long, and double types）。出處 基本型別流直接放數值、不必裝箱，還多了 sum()、average()、summaryStatistics() 這些數字專用的終端操作。物件流用 mapToInt、mapToLong 轉過去，反方向用 boxed()（「把每個元素裝箱成 Integer」，each boxed to an Integer）。出處 裝箱為什麼有成本，見〈Lambda 與函式介面〉的基本型別版一段。

IntStream.range(a, b) 產生 a 到 b-1（不含 b），rangeClosed(a, b) 含 b；文件說它們等同於 for (int i = a; i < b; i++) 與 i <= b 的迴圈。average() 回傳 OptionalDouble，空的流得到空的。出處

System.out.println(IntStream.range(0, 5).sum());                     // 10（0+1+2+3+4）
System.out.println(IntStream.rangeClosed(1, 5).sum());               // 15（1+2+3+4+5）
System.out.println(txs.stream().mapToLong(Tx::amount).average());    // OptionalDouble[49616.666666666664]
System.out.println(IntStream.empty().average());                     // OptionalDouble.empty
System.out.println(IntStream.range(0, 3).boxed().toList());          // [0, 1, 2]

LongSummaryStatistics stats = txs.stream().mapToLong(Tx::amount).summaryStatistics();
System.out.println(stats.getCount() + " " + stats.getMin() + " " + stats.getMax() + " " + stats.getSum());
// 6 3500 150000 297700

上一段的 map(Tx::amount).reduce(0L, Long::sum) 跟 mapToLong(Tx::amount).sum() 結果一樣，但前者一路處理的是 Long 物件；要做數字運算時，先 mapToLong 比較直接。

IntStream.range(1, 5).sum() 回傳什麼？

  • 15
  • 10
  • 5
  • 14

range 不含結尾：1、2、3、4，加起來 10。含 5 的是 rangeClosed(1, 5)，結果 15。

IntStream.rangeClosed(1, 5).count() 回傳什麼？

  • 5
  • 4
  • 15
  • 6

rangeClosed 包含結尾：1 到 5 共 5 個數。

IntStream.empty().average() 回傳什麼？

  • 0.0
  • NaN
  • 丟出 ArithmeticException
  • OptionalDouble.empty

文件：average() 回傳描述平均值的 OptionalDouble，流是空的就是空的 Optional，不會假裝平均是 0，也不會除以零。

要加總交易金額，mapToLong(Tx::amount).sum() 比 map(Tx::amount).reduce(0L, Long::sum) 好在哪？

  • 不必把每筆金額裝箱成 Long
  • 結果比較精確，後者加總大量數字時會有誤差
  • 前者是平行執行，後者是循序執行
  • 後者編譯不過

LongStream 放的是基本型別 long，不必建立 Long 物件；兩者都是整數加總，結果完全一樣，也都預設循序執行。

有一條 IntStream，想收成 List<Integer>，要先做哪一步？

  • mapToInt
  • boxed()
  • sum()
  • 什麼都不用，IntStream 直接有 collect(Collectors.toList())

List 只能放物件，要先 boxed() 把每個 int 裝箱成 Integer，變回 Stream<Integer> 再 toList()。IntStream 的 collect 不收 Collector。

多核心不是免費的

平行流：parallelStream 的代價與注意事項

把 stream() 換成 parallelStream()，或在管線中呼叫 parallel()，就會平行執行。套件說明：JDK 的流實作「除非明確要求平行，否則都建立循序的流」（The stream implementations in the JDK create serial streams unless parallelism is explicitly requested.）。出處 但 Collection.parallelStream() 回傳的是「可能平行的」流，文件也允許它回傳循序的流（It is allowable for this method to return a sequential stream.）。出處

誰在跑：dev.java 說平行流建立在 Fork/Join 框架上，工作由一個叫「共用 Fork/Join 池」（Common Fork/Join Pool）的執行緒池分頭處理。出處 實跑印出處理元素的執行緒名稱（把結尾編號換成 N），呼叫端自己的 main 執行緒也會一起做：

Set<String> threadNames = IntStream.range(0, 1_000)
        .parallel()
        .mapToObj(i -> Thread.currentThread().getName().replaceAll("\\d+$", "N"))
        .collect(Collectors.toSet());
System.out.println(threadNames);   // [ForkJoinPool.commonPool-worker-N, main]

這個池是整個 JVM 共用的；它預設有多少條執行緒、為什麼不能拿來跑會阻塞的 I/O，見〈Java 並行快答：執行緒池、鎖與並行集合〉的 CompletableFuture 一段，那裡講的是同一個池。

不一定比較快：Oracle 的教學說「平行不會自動比循序快，雖然在資料夠多、核心夠多時可能會」（parallelism is not automatically faster than performing operations serially, although it can be if you have enough data and processor cores）。出處 dev.java 列的代價：資料要先切開（ArrayList 好切，LinkedList 要一路走到中間才切得開）、切完的部分結果要再合併（合併數字加總很便宜，合併 HashMap 比較貴），以及平行會多用 CPU 與執行緒；它的建議是「不要猜，量測你的程式碼的效能」（Rule #4 Do not guess; measure the performance of your code.）。出處

副作用不要寫在 lambda 裡：套件說明：「傳給流操作的行為參數裡有副作用，一般是不鼓勵的」（Side-effects in behavioral parameters to stream operations are, in general, discouraged），並示範把 forEach(s -> results.add(s)) 改成直接 toList()，理由是平行執行時 ArrayList 不是執行緒安全的，「會造成錯誤的結果」（the non-thread-safety of ArrayList would cause incorrect results）。出處 實跑一百萬個數字：

List<Integer> unsafe = new ArrayList<>();
IntStream.range(0, 1_000_000).parallel().forEach(unsafe::add);   // 錯誤示範：多條執行緒同時改 ArrayList
System.out.println("unsafe.size() = " + unsafe.size());
// 在 Java 21 跑四次，分別印出 224646、184699、247407、271277；
// dev.java 提醒也可能丟出 ArrayIndexOutOfBoundsException

List<Integer> safe = IntStream.range(0, 1_000_000).parallel().boxed().toList();
System.out.println("safe.size() = " + safe.size());   // safe.size() = 1000000

只要讓結果由終端操作產生（toList()、collect、sum），平行也能拿到正確結果，而且照來源的順序：套件說明的例子 IntStream.range(0,5).parallel().map(x -> x*2).toArray()「一定產生 [0, 2, 4, 6, 8]」，只是 map 對各元素的執行順序與執行緒都不保證。出處 跟共用狀態有關的競爭條件（多條執行緒同時改同一份資料，結果看誰先誰後），在〈執行緒與並行〉有完整說明。

平行流先量再用；結果交給終端操作產生，lambda 裡不改外面的東西

依 dev.java 的說明，平行流的工作預設由誰執行？

  • 每次呼叫都新建一個專屬的執行緒池
  • 共用的 Fork/Join 執行緒池
  • 每個元素各開一條新的平台執行緒，處理完就結束
  • 虛擬執行緒

dev.java：平行流建立在 Fork/Join 框架上，工作分給共用 Fork/Join 池的執行緒。實跑印出的執行緒名稱是 ForkJoinPool.commonPool-worker-N 加上 main。

IntStream.range(0, 1_000_000).parallel().forEach(unsafe::add)（unsafe 是一般的 ArrayList），結果會怎樣？

  • 一定是 1000000 筆，只是順序打亂
  • 一定是 1000000 筆，順序也正確
  • 不可預期：筆數常常少掉，也可能丟出例外
  • 編譯錯誤，平行流不能用 forEach

多條執行緒同時呼叫非執行緒安全的 ArrayList.add，是競爭條件。實跑四次得到四個不同、都遠少於一百萬的數字；dev.java 提醒也可能丟 ArrayIndexOutOfBoundsException。改用 boxed().toList() 就正確。

把 stream() 改成 parallelStream()，一定會變快嗎？

  • 一定會，核心越多越快
  • 一定會變慢
  • 只要資料少於一千筆就一定會變快
  • 不一定，要量測過才知道

Oracle 教學：平行不會自動比循序快。dev.java 的守則是「不要猜，量測你的程式碼的效能」；資料量、資料結構好不好切、合併成本都會影響。

IntStream.range(0, 5).parallel().map(x -> x * 2).toArray() 的結果是什麼？

  • [0, 2, 4, 6, 8]，一定照順序
  • [0, 2, 4, 6, 8] 的某種排列，每次可能不同
  • [0, 1, 2, 3, 4]
  • 空陣列

來源有順序，結果就照來源的順序排；套件說明用的正是這個例子，說它「一定產生 [0, 2, 4, 6, 8]」。不保證的是 map 對各元素的執行順序與在哪條執行緒上跑。

在 Web 伺服器裡，某個處理請求的方法用了 parallelStream()，而 lambda 裡會呼叫遠端服務、等它回應。依 dev.java 與本課的說明，主要的隱憂是什麼？

  • 收集到的結果順序一定會亂掉，需要重新排序
  • 占住整個 JVM 共用的執行緒池，拖慢其他用到它的程式
  • parallelStream 不能呼叫遠端服務
  • 伺服器會自動改成循序執行，沒有影響

dev.java 提醒平行會消耗執行緒（以 Web 伺服器處理 HTTP 請求的執行緒為例）。共用池是整個 JVM 共用的，拿來等 I/O 會占住它；〈Java 並行快答：執行緒池、鎖與並行集合〉說明了同一個池為什麼不該跑阻塞工作。

不是每個迴圈都該改。下面幾種情況，一般迴圈通常比較直接（這是寫法上的建議，不是規定）：

  • 每一步都要丟受檢例外，例如逐筆讀檔、寫資料庫。Function、Predicate 這些介面的方法沒宣告 throws，lambda 裡丟不出受檢例外（JLS 的規定見〈Lambda 與函式介面〉）出處，硬塞進去就得在每個 lambda 裡包 try／catch。
  • 迴圈要一邊走一邊改好幾個區域變數，例如同時累計金額、筆數、上一筆的時間。lambda 只能讀 effectively final 的區域變數。出處
  • 需要依前一筆決定下一步、或中途視情況 break、continue 好幾種方向。Stream 的行為參數最好是無狀態的，套件說明說結果不該依賴「管線執行期間可能改變的任何狀態」。出處
  • 要用到索引去讀相鄰元素，例如比較第 i 筆和第 i+1 筆。

Java 24 起的差異：Stream 多了 gather 這個中間操作，可以自訂中間操作，例如每 N 筆一批。JEP 485 說 gather 之於中間操作，就像 collect 之於終端操作（Stream::gather(Gatherer) is to intermediate operations what Stream::collect(Collector) is to terminal operations.），在 JDK 24 正式定案。出處 Java 25 的 Gatherers.windowFixed 文件說「最後一批的元素可能少於指定的大小」（The last window may contain fewer elements than the supplied window size.）。出處 Java 21 沒有這個方法（編譯報 cannot find symbol）；以 Java 25 執行：

// Java 24 起（以 Java 25 執行）
List<Long> amounts = List.of(1_000L, 2_000L, 3_000L, 4_000L, 5_000L);
List<List<Long>> batches = amounts.stream()
        .gather(Gatherers.windowFixed(2))      // 每兩筆一批
        .toList();
System.out.println(batches);   // [[1000, 2000], [3000, 4000], [5000]]

下面這個迴圈，改寫成哪一段 Stream 結果相同？

long total = 0;
for (Tx tx : txs) {
    if (tx.branch().equals("大安")) total += tx.amount();
}
  • txs.stream().mapToLong(Tx::amount).filter(a -> a > 0).sum()
  • txs.stream().filter(tx -> tx.branch().equals("大安")).mapToLong(Tx::amount).sum()
  • txs.stream().filter(tx -> tx.branch().equals("大安")).count()
  • txs.stream().map(Tx::branch).filter("大安"::equals).count()

if 對應 filter、total += 對應 mapToLong(...).sum()。兩個 count() 的版本算的是筆數；第一個沒篩分行，加的是全部金額。

下面哪一種情況，一般迴圈通常比 Stream 直接？

  • 把交易清單篩出大額交易
  • 依分行分組加總金額
  • 逐筆寫資料庫，可能丟 SQLException、要決定繼續或中止
  • 把交易編號串成一個用逗號分隔的長字串，放進報表

SQLException 是受檢例外，lambda 丟不出去；再加上「依情況繼續或中止」的流程控制，用迴圈配 try／catch、break 比較直接。其餘三個正好是 filter、groupingBy、joining 的強項。

迴圈「找到第一筆凍結帳戶就 break」，對應哪個 Stream 寫法？

  • filter(Account::frozen).toList().get(0)
  • filter(Account::frozen).count()
  • map(Account::frozen).findFirst()
  • filter(Account::frozen).findFirst()

findFirst 是短路操作，找到就停，跟 break 一樣不會看後面的元素，而且找不到時回傳空的 Optional。先 toList() 會把全部走完，沒找到時 get(0) 還會丟例外；map(Account::frozen) 拿到的是第一個帳戶的 true／false。

Java 24 起，Stream.of(1, 2, 3, 4, 5).gather(Gatherers.windowFixed(2)).toList() 得到什麼？

  • [[1, 2], [3, 4]]
  • [[1, 2], [2, 3], [3, 4], [4, 5]]
  • [[1, 2], [3, 4], [5]]
  • [3, 7, 5]

windowFixed(2) 每兩個一批、不重疊，最後一批可以不足兩個，所以 5 單獨一批。每次滑動一格、會重疊的是 windowSliding。

重點整理

  • 一條流＝來源＋零個或多個中間操作＋一個終端操作；流不存資料、不修改來源。
  • 中間操作是惰性的：沒有終端操作就一行都不跑；元素一筆一筆走完整條管線；findFirst、anyMatch、limit 會短路。一條流只能用一次，重用會丟 IllegalStateException。
  • peek 只用來除錯，count() 等操作可能讓它根本不執行；要做的事不要寫在 peek 或其他行為參數的副作用裡。
  • toList()（Java 16 起）回傳不可修改的清單；要能修改就 collect(Collectors.toCollection(ArrayList::new))。空的流：anyMatch 是 false、allMatch 是 true，findFirst、max、average 回傳空的 Optional。
  • groupingBy＋counting（結果是 Long）／summingLong／mapping 做分組統計；partitioningBy 一定有 true、false 兩個鍵；toMap 鍵重複丟 IllegalStateException，要給合併函式。
  • 數字運算先 mapToInt／mapToLong 轉成基本型別流，省掉裝箱；range 不含結尾、rangeClosed 含結尾。
  • 平行流用的是整個 JVM 共用的 Fork/Join 池，不保證變快，先量再用；結果交給終端操作產生，不要在 lambda 裡改外面的集合。
