起點

沒有它的時候，你在做什麼

開一個 Java 專案，總要用到別人寫好的東西——連資料庫的 mysql-connector-j、處理 JSON 的 Gson。沒有工具幫忙時，這件事是這樣做的：上官網找到 jar 檔、下載、丟進專案的 lib 資料夾，再到 IDE 裡手動把它加進類別路徑（classpath——Java 執行時去哪些地方找 class 檔的清單）。

三個地方會出事：

  • 依賴自己還有依賴：你抓的那包 jar 內部又要用別的 jar（傳遞依賴，transitive dependency）。你得一路追下去，漏抓一個，編譯時看不出來，執行到那一行才爆。
  • 換台機器就不一樣：組員的 lib 裡少一包、或版本差一號，就變成「在我電腦上明明可以跑」。
  • 每個 IDE 一套長相：Eclipse 建的專案結構跟 IntelliJ IDEA 不一樣，專案丟給別人，對方打不開。

Maven 就是來收掉這三件事的。它是一個專案管理與建置工具，核心概念叫專案物件模型（POM，Project Object Model）——你在 pom.xml 裡描述「這個專案是誰、要用到什麼、怎麼建」，Maven 照著這份描述去做，不用你一步步下指令。

Maven 最常用在 Java，但不限於 Java出處——換上對應的外掛，C#、Ruby、Scala 的專案一樣建得起來。日常遇到它幾乎都在 Java 圈，知道它不是綁死在 Java 上就好。

標準目錄結構規定原始碼、測試、資源檔各放哪個資料夾，所有 IDE 開出來都同一個長相。
標準建置流程編譯、測試、打包、安裝、發佈串成固定順序，每個專案的建置指令都一樣。
依賴管理你只寫「我要 Gson 2.10.1」，去哪抓、抓它自己的依賴、放哪裡，Maven 全包。

版本界線：這課講的是 Maven 3 的行為，也是 2026 年實務上的主流。Maven 4 目前還在候選版（release candidate）階段、尚未正式發佈；它主要動的是多模組專案的處理與 pom 格式，這課講的目錄結構、座標、生命週期、依賴範圍都照舊。

規矩一

東西放哪裡，不用再吵

Maven 規定了每種檔案該放哪。這件事聽起來瑣碎，但它讓你拿到任何一個沒看過的 Maven 專案，都知道程式碼在 src/main/java：

放對位置還有一層意義：Maven 不用你交代「原始碼在哪、測試在哪」，它照約定去找。這叫慣例優於設定（convention over configuration——先給一套預設規矩，只有你要打破時才寫設定）。這也是為什麼一個最小的 pom.xml 可以短到只有座標那幾行。

目錄結構統一了，專案才能在不同 IDE、不同機器之間直接對開

target/ 是唯一一個「不要碰、也不要進 git」的資料夾——它每次建置都整個重新產生，塞進版本控制只會天天製造衝突。所以 Java 專案的 .gitignore 第一行通常就是它。

規矩二

座標：每一包程式的門牌

Maven 要去倉庫（repository——存放 jar 的地方）幫你把依賴抓下來，就得有辦法唯一指到「就是那一包、那一版」。這組門牌叫座標（coordinates），三個欄位：

groupId誰做的。慣例是把網域名反過來寫（com.google.code.gson、org.springframework），為的是全世界不撞名。
artifactId這一包叫什麼。它同時決定產出的檔名——gson 建出來就是 gson-2.10.1.jar。
version哪一版。結尾掛 -SNAPSHOT 代表「開發中、內容隨時會變」，正式版不會有這個尾巴。

兩個地方會用到座標。一個是宣告「我自己是誰」，寫在 pom.xml 最上面；另一個是宣告「我要用誰」，寫在 <dependencies> 裡：

<!-- 我自己是誰 -->
<groupId>com.hhtim</groupId>
<artifactId>my-app</artifactId>
<version>1.0-SNAPSHOT</version>

<!-- 我要用誰 -->
<dependencies>
    <dependency>
        <groupId>com.google.code.gson</groupId>
        <artifactId>gson</artifactId>
        <version>2.10.1</version>
    </dependency>
</dependencies>

寫完這幾行，Maven 會自己去倉庫抓 Gson、連同 Gson 需要的東西一起抓、擺進本機倉庫、加到類別路徑上。你要做的只是把座標抄對。

座標其實還能再細：packaging（產出型別，預設是 jar，網頁專案常設成 war）和 classifier（同一版的不同變體，例如 sources、javadoc）。日常寫依賴，三個欄位就夠。

規矩三

生命週期與階段：先把詞分清楚

為什麼 mvn clean package 要寫兩個詞，mvn package 卻不用另外叫編譯？

要回答這題，得先把兩個常被混用的詞分開。指令其實只有一個，就是 mvn；compile、test、package、install 這些是階段（phase）的名字，你打 mvn package 是在跟 Maven 說「一路跑到 package 這個階段為止」出處。

這些階段被串成三套生命週期（lifecycle），各管各的一條路：

同一套生命週期裡，叫後面的階段，前面的階段全部自動先跑一遍

所以 mvn package 會自動先做 validate、compile、test 才打包——不用你另外叫編譯。這也解釋了一件日常會遇到的事：測試沒過，打包就停在那裡，因為 test 排在 package 前面，前面卡住後面不會跑。

而這條規則只在同一套裡成立。clean 和 default 是兩套，彼此不會自動接，所以「先清乾淨再打包」得兩個都講出來：

mvn clean package     # clean 那套跑到 clean，default 那套跑到 package
mvn package           # 只有 default 這套，上次的 target/ 還留著

install 是裝到哪裡

install 不是把程式裝進作業系統，而是把打包好的成品放進本機倉庫——你家目錄底下的 ~/.m2/repository出處。放進去之後，這台電腦上的其他專案就能用座標把它當依賴引用。再往外一步的 deploy 才是上傳到遠端倉庫（公司內部的 Nexus，或公開的 Maven Central），給別人用。

原筆記的常用清單停在 install，後面其實還有一個 deploy——那是 default 生命週期的最後一個階段。實務上 deploy 通常不是你在自己電腦上打，而是交給 CI／CD 流水線去做。

規矩四

依賴範圍：這包 jar 該在什麼場合出現

不是每個依賴都該一路跟到底。測試用的 JUnit，沒道理跟著打包進上線的成品；Servlet API 由容器（Tomcat 那類）自己提供，你再塞一份進去只會撞版本。

控制這件事的欄位是 <scope>（依賴範圍）。它決定這包 jar 出現在哪幾條類別路徑上——Maven 分成編譯用、測試用、執行用三條：

scope編譯測試執行典型用途
compile✓✓✓預設值。一般的函式庫，例如 Gson。
provided✓✓✗編譯時要、但執行環境會自己提供，例如 Servlet API、Lombok。
runtime✗✓✓寫程式時碰不到、跑起來才需要，例如 JDBC 驅動。
test✗✓✗只有測試要，例如 JUnit、Mockito。
system✓✓✗直接指定本機檔案路徑——已不建議使用。
import———只出現在 <dependencyManagement>，把別人整份版本清單拉進來用。

不寫 <scope> 就是 compile——編譯、測試、執行三條路徑全都在

表裡的 system 要避開：它靠絕對路徑指到本機某個 jar，換台電腦就找不到，Maven 3.9 以後用了會跳警告。要引用一包不在公開倉庫的 jar，正解是先 mvn install:install-file 把它裝進本機倉庫，再用一般的座標引用。出處

import 是另一類東西：其他五個在講「這包 jar 跟不跟」，它在講「版本號聽誰的」。Spring Boot 專案最常見的用法就是把官方的版本清單（BOM，Bill of Materials——一份「這些套件彼此相容的版本組合」）整份匯進來，之後寫依賴連 <version> 都不用填。

重點整理

  • Maven 扛三件事：統一目錄結構、統一建置流程、依賴管理——對應的就是「換台機器跑不起來」這類老問題。
  • 座標＝groupId（誰做的，網域反著寫）＋artifactId（叫什麼，也是檔名）＋version（哪一版）。
  • 指令只有 mvn，後面接的是階段；階段被串成 clean／default／site 三套生命週期。
  • 同一套裡叫後面的會自動跑前面的，跨套不會——所以是 mvn clean package 兩個詞。
  • scope 預設 compile；測試用 test、容器提供用 provided、只在執行期要用 runtime，system 已經不該再用。
