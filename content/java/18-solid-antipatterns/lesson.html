原則，不是規定

SOLID 是什麼：五個讓程式好改的設計原則

SOLID 是五個物件導向設計原則的英文首字母：

字母原則一句話
S單一職責原則（Single Responsibility Principle）一個類別只該因為一種理由被修改
O開放封閉原則（Open Closed Principle）加新功能時擴充，不要回頭改舊程式
L里氏替換原則（Liskov Substitution Principle）子型別放進父型別的位置，程式要照常運作
I介面隔離原則（Interface Segregation Principle）不要逼使用端依賴它用不到的方法
D依賴反轉原則（Dependency Inversion Principle）高層規則依賴抽象，不依賴具體細節

這五條大多由 Robert C. Martin 整理推廣。他在 2000 年的文章「Design Principles and Design Patterns」開頭先講軟體為什麼會爛掉：需求一直變，模組之間的相依關係越纏越緊，改一處壞一片；要擋住這種退化，就得管理模組之間的相依，而物件導向設計裡「有很多原則與技巧，用來建立這種防火牆、管理模組相依」（Object Oriented Design is replete with principles and techniques for building such firewalls, and for managing module dependencies.）。出處 所以 SOLID 的目的只有一個：讓程式在需求改變時好改。

它們是原則，不是編譯器會檢查的規定。違反了程式照樣能跑，只是之後改起來比較痛；硬套也有代價（多出來的介面與類別）。〈介面與抽象類別〉講過的「耦合要低、凝聚要高」是這五條背後共同的方向。

SOLID 這五個字母不是同一份文件同時提出的：2000 年那篇文章講的是開放封閉、里氏替換、依賴反轉、介面隔離四條（外加幾條套件層級的原則），單一職責原則出自 Martin 另一篇文章與他後來的書。

SOLID 五個原則最主要想解決的問題是什麼？

  • 需求改變時程式還是好改
  • 讓程式在任何機器上都跑得比較快
  • 讓專案裡的類別數量越多越好
  • 讓程式不需要寫測試

Martin 2000 年的文章從「相依關係越纏越緊、軟體爛掉」講起，原則是用來管理模組相依的。它們跟執行速度無關，也不是類別越多越好。

一段程式違反了單一職責原則，會發生什麼事？

  • 編譯器報錯，整個專案無法編譯
  • 執行時一定丟出例外並中止
  • JVM 會在執行時自動把類別拆開
  • 照樣能跑，之後難改

SOLID 是設計原則，不是語言規則。違反它不會有任何錯誤訊息，代價出現在之後改需求的時候。

Martin 2000 年的「Design Principles and Design Patterns」沒有講到下面哪一條？

  • 開放封閉原則
  • 依賴反轉原則
  • 單一職責原則
  • 里氏替換原則

那篇文章講類別層級的開放封閉、里氏替換、依賴反轉、介面隔離四條；單一職責原則出自他另一篇文章與後來的書。

誰會要求你改這段程式

單一職責原則：一個類別只為一群人負責

Martin 在「SRP: The Single Responsibility Principle」那篇文章裡的寫法是「一個類別不該有超過一個被修改的理由」（THERE SHOULD NEVER BE MORE THAN ONE REASON FOR A CLASS TO CHANGE.），並解釋「每一種職責都是一條會變動的軸」（each responsibility is an axis of change）。出處 常見的英文轉述是「A class should have only one reason to change」，沒有出處；Martin 2014 年自己的寫法見下一段。

「理由」很容易被誤解成「功能」或「做一件事」。Martin 2014 年在部落格上補充：單一職責原則說的是「每個軟體模組應該有一個、而且只有一個被修改的理由」（each software module should have one and only one reason to change），而「這個原則講的是人」（This principle is about people.）：修改的要求應該只來自「一群緊密相關、代表單一業務功能的人」（a single tightly coupled group of people representing a single narrowly defined business function）。出處 他的例子是一個員工類別同時有算薪水、存資料庫、出工時報表三個方法，分別由財務長、技術長、營運長的部門提出修改。

換成銀行：一個 Account 同時負責算利息（財務部決定）、印對帳單（營運部決定）、存檔（資訊部決定），三個方法共用一個「四捨五入到元」的小工具：

class Account {
    private final String id;
    private final BigDecimal balance;
    private static final BigDecimal YEARLY_RATE = new BigDecimal("0.0125");

    Account(String id, String balance) {
        this.id = id;
        this.balance = new BigDecimal(balance);
    }

    BigDecimal monthlyInterest() {                     // 財務部決定：利息怎麼算
        return toDollar(balance.multiply(YEARLY_RATE).divide(BigDecimal.valueOf(12), 10, RoundingMode.HALF_UP));
    }

    String statement() {                               // 營運部決定：對帳單長什麼樣
        return id + " 餘額 " + toDollar(balance) + " 元";
    }

    void save() {                                      // 資訊部決定：資料怎麼存
        System.out.println("寫入資料庫：" + id + " = " + balance);
    }

    private BigDecimal toDollar(BigDecimal v) {        // 三個方法共用的小工具：四捨五入到元
        return v.setScale(0, RoundingMode.HALF_UP);
    }
}

某天財務部要求「利息一律無條件捨去」。工程師看到利息用的是 toDollar，就把那一行改成 RoundingMode.DOWN（範例檔裡的 AccountAfterFinanceChange 就是把捨入那一行改成 DOWN）。實跑：

改之前：利息 11 元；A-001 餘額 10501 元
財務部改完：利息 10 元；A-001 餘額 10500 元

利息照財務部的意思從 11 變 10，但對帳單上的餘額也從 10501 變成 10500，營運部根本沒要求改。這就是 Martin 說的：改了財務部要的東西，卻弄壞營運部負責的東西。重構的方向是照「誰會要求改」拆開：

import java.math.BigDecimal;
import java.math.RoundingMode;

public class SrpAfter {
    public static void main(String[] args) {
        Account a = new Account("A-001", new BigDecimal("10500.50"));
        System.out.println("利息 " + new InterestPolicy().monthlyInterest(a) + " 元；" + new StatementPrinter().print(a));
        new AccountRepository().save(a);
    }
}

class Account {                                        // 帳戶自己的規則：餘額不能是負的
    private final String id;
    private BigDecimal balance;

    Account(String id, BigDecimal balance) {
        if (balance.signum() < 0) throw new IllegalArgumentException("餘額不可為負");
        this.id = id;
        this.balance = balance;
    }

    String id() { return id; }
    BigDecimal balance() { return balance; }
}

class InterestPolicy {                                 // 只有財務部會要求改這裡
    private static final BigDecimal YEARLY_RATE = new BigDecimal("0.0125");

    BigDecimal monthlyInterest(Account a) {
        return a.balance().multiply(YEARLY_RATE)
                .divide(BigDecimal.valueOf(12), 0, RoundingMode.DOWN);   // 無條件捨去
    }
}

class StatementPrinter {                               // 只有營運部會要求改這裡
    String print(Account a) {
        return a.id() + " 餘額 " + a.balance().setScale(0, RoundingMode.HALF_UP) + " 元";
    }
}

class AccountRepository {                              // 只有資訊部會要求改這裡
    void save(Account a) {
        System.out.println("寫入資料庫：" + a.id() + " = " + a.balance());
    }
}

寫入資料庫：A-001 = 10500.50

界線：拆到每個類別只剩一個方法不是目標。Martin 自己的說法是同樣理由會變的東西放在一起、不同理由會變的分開（Gather together the things that change for the same reasons. Separate those things that change for different reasons.）。出處 例如「餘額不能是負的」是帳戶本身的規則，就留在 Account 裡，沒有跟著拆出去。

上面的 Account 同時有 monthlyInterest()、statement()、save()。照 Martin 部落格的說法，判斷它是否違反單一職責原則，最該問哪一個問題？

  • 會有幾群不同的人要求改它
  • 這個類別有沒有超過一百行程式碼
  • 這個類別總共宣告了幾個方法
  • 這些方法是不是每個都很短

Martin 說這個原則講的是人：修改要求應該只來自單一業務功能的那群人。行數與方法數只是旁證。

實跑結果裡，財務部只要求改利息的捨入方式，結果哪裡也跟著變了？

  • 寫進資料庫的帳戶金額
  • 帳戶編號的顯示格式
  • 什麼都沒有改變
  • 對帳單顯示的餘額

利息與對帳單共用 toDollar，改成無條件捨去之後，對帳單餘額從 10501 變成 10500。兩個職責綁在同一個小工具上，就會互相波及。

重構後，如果營運部要求「對帳單餘額改成顯示到角（小數一位）」，要改哪個類別？

  • StatementPrinter
  • InterestPolicy
  • AccountRepository
  • Account

對帳單格式只歸營運部管，所以只動 StatementPrinter；利息與存檔的程式不會被碰到。

下面哪一句最符合 Martin 對單一職責原則的補充說明？

  • 同理由一起，不同理由分開
  • 每個類別最多只能有一個方法
  • 每個方法只能做一件事情
  • 每個類別都要搭配自己的介面

原文：Gather together the things that change for the same reasons. Separate those things that change for different reasons.「只能有一個方法」是常見的誤讀。

重構後的 Account 為什麼還留著「餘額不可為負」的檢查，沒有拆到別的類別？

  • 因為建構子不能被拆出去
  • Java 規定驗證要寫在建構子
  • 其實應該拆，這裡漏掉了
  • 那是帳戶本身的規則

單一職責不是把類別拆空。帳戶本身的不變條件跟帳戶一起變，留在 Account 裡剛好；這也接到後面「貧血模型」的討論。

新增帳戶類型，不要回頭改舊程式

開放封閉原則：對擴充開放，對修改封閉

Martin 的原文：「一個模組應該對擴充開放、對修改封閉」（A module should be open for extension but closed for modification.），並說這條源自 Bertrand Meyer；意思是「改變模組做的事，卻不必改它的原始碼」（we want to be able to change what the modules do, without changing the source code of the modules）。做法只有一個方向：「抽象是開放封閉原則的關鍵」（abstraction is the key to the OCP）。出處

跨行轉帳手續費依帳戶類型不同。違反的版本用一個 switch 判斷類型：

public class OcpBefore {
    public static void main(String[] args) {
        FeeCalculator calc = new FeeCalculator();
        for (String type : new String[]{"一般戶", "薪轉戶", "數位帳戶", "VIP 戶"}) {
            try {
                System.out.println(type + " 跨行轉帳 5000 元，手續費 " + calc.fee(type, 5000) + " 元");
            } catch (IllegalArgumentException e) {
                System.out.println(type + "：" + e.getMessage());
            }
        }
    }
}

class FeeCalculator {
    int fee(String accountType, int amount) {
        return switch (accountType) {                  // 每多一種帳戶，就要回來改這裡
            case "一般戶" -> 15;
            case "薪轉戶" -> 0;
            case "數位帳戶" -> amount >= 1000 ? 10 : 0;
            default -> throw new IllegalArgumentException("不認得的帳戶類型");
        };
    }
}

薪轉戶 跨行轉帳 5000 元，手續費 0 元
數位帳戶 跨行轉帳 5000 元，手續費 10 元
VIP 戶：不認得的帳戶類型

業務新推出 VIP 戶，FeeCalculator 不認得。要支援它，就得回頭打開這個已經上線、測過的方法加一個 case；而且所有判斷帳戶類型的 switch（算手續費、算利息、算額度……）都要一起找出來改。Martin 在文章裡描述過同樣的症狀：這樣設計的程式「到處是類似的 if/else 或 switch」。重構的做法是把「會變的那一塊」（手續費怎麼算）抽成介面：

import java.util.List;

public class OcpAfter {
    public static void main(String[] args) {
        List<FeePolicy> policies = List.of(new RegularFee(), new PayrollFee(), new DigitalFee(), new VipFee());
        TransferService service = new TransferService();
        for (FeePolicy p : policies) {
            System.out.println(p.name() + " 跨行轉帳 5000 元，手續費 " + service.fee(p, 5000) + " 元");
        }
    }
}

interface FeePolicy {
    String name();
    int feeFor(int amount);
}

class TransferService {                                // 新增帳戶類型時，這個類別一個字都不用改
    int fee(FeePolicy policy, int amount) {
        return policy.feeFor(amount);
    }
}

class RegularFee implements FeePolicy {
    public String name() { return "一般戶"; }
    public int feeFor(int amount) { return 15; }
}

class PayrollFee implements FeePolicy {
    public String name() { return "薪轉戶"; }
    public int feeFor(int amount) { return 0; }
}

class DigitalFee implements FeePolicy {
    public String name() { return "數位帳戶"; }
    public int feeFor(int amount) { return amount >= 1000 ? 10 : 0; }
}

class VipFee implements FeePolicy {                    // 後來新增：只加這個類別
    public String name() { return "VIP 戶"; }
    public int feeFor(int amount) { return 0; }
}

薪轉戶 跨行轉帳 5000 元，手續費 0 元
數位帳戶 跨行轉帳 5000 元，手續費 10 元
VIP 戶 跨行轉帳 5000 元，手續費 0 元

新增 VIP 戶只加了 VipFee 這個類別，TransferService 與其他三種手續費都沒有改。這個結構就是〈設計模式〉的策略模式（Strategy）。

界線：沒有程式能對所有變化都封閉。這裡封閉的是「新增帳戶類型」；如果變化反過來是「每種帳戶都要多一種費用」，就得改介面、改所有實作。所以先問「哪裡最常變」，只在那裡留擴充點。帳戶種類固定、很少新增時，〈現代 Java 語法：var、record、switch、文字區塊與 sealed〉講的 sealed 介面搭配 switch 模式比對也是合理的選擇：少處理一種，編譯器會提醒你。

照開放封閉原則，新增一種「VIP 戶」最理想的改法是？

  • 在 switch 加一個 case
  • 複製一份 TransferService 改名
  • 在 TransferService 加 if 判斷
  • 新增實作 FeePolicy 的類別

擴充靠新增類別，既有的 TransferService 與其他手續費類別都不用打開。加 case、加 if 都是在改舊程式。

Martin 說達成開放封閉原則的關鍵是什麼？

  • 把所有欄位設成 final
  • 把所有方法設成 static
  • 抽象
  • 盡量少寫類別

原文 abstraction is the key to the OCP。呼叫端依賴 FeePolicy 這個抽象，具體算法才能自由增加。

重構前的版本跑到 VIP 戶時，實跑輸出是什麼？

  • VIP 戶：不認得的帳戶類型
  • VIP 戶跨行轉帳，手續費 0 元
  • VIP 戶跨行轉帳，手續費 15 元
  • 編譯失敗，switch 少了 case

switch 走到 default 丟出 IllegalArgumentException。要支援 VIP 戶只能回頭改 FeeCalculator。

重構後的手續費設計，對下面哪一種變化不封閉，仍然要改到很多既有類別？

  • 新增一種「學生戶」帳戶
  • 每種帳戶都多算匯率加價
  • VIP 戶改成每筆收 5 元
  • 數位帳戶門檻從 1000 改成 2000

新增類型或調整單一類型都只動一個類別；但「每種帳戶都多一種費用」要改 FeePolicy 介面與所有實作。開放封閉只對你選定的那種變化成立。

重構後「把會變的演算法包成可替換的物件」這個結構，在〈設計模式〉裡叫什麼？

  • Singleton
  • Adapter
  • Facade
  • Strategy

每種手續費算法各包成一個 FeePolicy 物件、執行時選一個用，就是策略模式。

子型別要守父型別的約定

里氏替換原則：放進父型別的位置，要照常運作

Barbara Liskov 1987 年在 OOPSLA 的講稿「Data Abstraction and Hierarchy」寫下原始定義：「如果對每個型別 S 的物件 o1，都有一個型別 T 的物件 o2，使得所有以 T 定義的程式 P 在把 o2 換成 o1 時行為不變，那麼 S 就是 T 的子型別」（If for each object o1 of type S there is an object o2 of type T such that for all programs P defined in terms of T, the behavior of P is unchanged when o1 is substituted for o2 then S is a subtype of T.）。她還特別區分：子型別、父型別講的是「語意上的區別」，子類別、父類別「只是程式語言的語法概念」。出處 也就是說，extends 寫得出來，不代表語意上真的是子型別。

Martin 把它濃縮成「子類別應該能替換它們的父類別」（Subclasses should be substitutable for their base classes.），並用約定來講：子類別的方法「前置條件不比父類別強、後置條件不比父類別弱」，換句話說「要求不能更多，提供不能更少」（derived methods should expect no more and provide no less）。出處 前置條件是呼叫前必須成立的條件，後置條件是方法保證做完之後成立的結果。

定存「是一種」帳戶，直覺上就讓它繼承 Account。但 Account.withdraw 的約定是「金額不超過餘額就一定扣得成」，定存卻多加了「沒到期一律不能提」，前置條件變強了：

import java.util.List;

public class LspBefore {
    public static void main(String[] args) {
        List<Account> accounts = List.of(new Account("活存-01", 3000), new FixedDeposit("定存-02", 100000), new Account("活存-03", 500));
        for (Account a : accounts) {                   // 月底批次：每個帳戶扣 10 元帳戶管理費
            try {
                a.withdraw(10);
                System.out.println(a.id() + " 扣款成功，餘額 " + a.balance());
            } catch (RuntimeException e) {
                System.out.println(a.id() + " 扣款失敗：" + e.getMessage());
            }
        }
    }
}

class Account {
    private final String id;
    protected int balance;

    Account(String id, int balance) { this.id = id; this.balance = balance; }

    // 約定：amount 不超過餘額就一定扣得成
    void withdraw(int amount) {
        if (amount > balance) throw new IllegalArgumentException("餘額不足");
        balance -= amount;
    }

    String id() { return id; }
    int balance() { return balance; }
}

class FixedDeposit extends Account {                   // 定存「是一種」帳戶？
    FixedDeposit(String id, int balance) { super(id, balance); }

    @Override
    void withdraw(int amount) {                        // 多加了條件：沒到期一律不能提
        throw new IllegalStateException("定存未到期，不能提款");
    }
}

定存-02 扣款失敗：定存未到期，不能提款
活存-03 扣款成功，餘額 490

月底批次只認得 Account，照父型別的約定扣款，碰到定存就失敗。呼叫端只好開始寫 if (a instanceof FixedDeposit) 跳過它，這正是 Martin 說的後果：違反里氏替換原則之後，常見的補救是在呼叫端加 if/else，「所以違反里氏替換原則，就是潛在地違反開放封閉原則」（Thus, violations of LSP are latent violations of OCP.）。〈封裝、繼承、多型〉也提醒過：程式到處判斷具體子型別，通常表示共同介面沒設計好。重構：把「能隨時提款」變成一個獨立的能力，定存不具備它：

import java.util.List;

public class LspAfter {
    public static void main(String[] args) {
        List<Withdrawable> chargeable = List.of(new SavingsAccount("活存-01", 3000), new SavingsAccount("活存-03", 500));
        for (Withdrawable a : chargeable) {            // 批次只拿「能提款」的帳戶
            a.withdraw(10);
            System.out.println(a.id() + " 扣款成功，餘額 " + a.balance());
        }
        FixedDeposit fd = new FixedDeposit("定存-02", 100000, 12);
        System.out.println(fd.id() + " 到期可領 " + fd.maturityAmount() + " 元（不在扣款名單）");
    }
}

abstract class Account {
    private final String id;
    protected int balance;

    Account(String id, int balance) { this.id = id; this.balance = balance; }

    String id() { return id; }
    int balance() { return balance; }
}

interface Withdrawable {
    String id();
    int balance();
    void withdraw(int amount);                         // 約定：amount 不超過餘額就一定扣得成
}

class SavingsAccount extends Account implements Withdrawable {
    SavingsAccount(String id, int balance) { super(id, balance); }

    public void withdraw(int amount) {
        if (amount > balance) throw new IllegalArgumentException("餘額不足");
        balance -= amount;
    }

    public String id() { return super.id(); }
    public int balance() { return super.balance(); }
}

class FixedDeposit extends Account {                   // 不實作 Withdrawable：型別上就看得出它不能隨時提款
    private final int months;

    FixedDeposit(String id, int balance, int months) { super(id, balance); this.months = months; }

    int maturityAmount() { return balance + balance * months / 100 / 12; }   // 年利率 1%，簡化成整數
}

爭議：JDK 自己的「可選操作」

Java 的集合框架有一個常被拿來討論的設計。Collection 的 API 文件寫明：某些會修改內容的方法「可以被規定成丟出 UnsupportedOperationException，如果這個集合實作不支援那個操作」（They can be specified to throw UnsupportedOperationException if this collection implementation does not support the operation.）。出處 所以 List.of(1, 2).add(3) 會丟例外。一派認為這就是違反里氏替換原則：拿到一個 List，你不知道能不能 add。另一派認為它沒有違反：父型別的約定本來就寫了「可能丟 UnsupportedOperationException」，子型別沒有比約定要求更多；代價是呼叫端得自己知道拿到的是哪一種。兩邊的共同點是：里氏替換原則看的是約定寫了什麼，不是方法名稱長得一不一樣。

Liskov 的原始定義裡，判斷 S 是不是 T 的子型別，看的是什麼？

  • S 有沒有寫 extends T
  • 替換後程式行為不變
  • S 的方法名稱跟 T 一樣
  • S 的欄位比 T 多

定義是「所有以 T 定義的程式，替換之後行為不變」。Liskov 也強調子類別只是語法概念，子型別才是語意上的關係。

定存覆寫 withdraw、沒到期一律丟例外。照 Martin 的約定說法，它違反了哪一點？

  • 後置條件變強了
  • 前置條件變強了
  • 方法名稱改了
  • 存取權限變小了

父類別只要求金額不超過餘額，定存多要求「已到期」，呼叫前必須成立的條件變多了，就是前置條件變強。Martin：要求不能更多，提供不能更少。

月底批次扣款跑到定存失敗，呼叫端最常見的「補救」是什麼？Martin 怎麼評價它？

  • 加 instanceof 跳過；也違反開放封閉
  • 改用 static 方法就沒問題
  • 多 catch 一次，問題就解決
  • 把定存的餘額直接改成 0 元避開扣款

每多一種「不能扣款」的帳戶，批次就得再加一個判斷，呼叫端被迫跟著改。Martin 原文：violations of LSP are latent violations of OCP。

重構後，批次扣款的名單型別是 List<Withdrawable>。想把定存放進去，會發生什麼事？

  • 執行時丟出 IllegalStateException
  • 可以放進去，扣款金額變成 0
  • 編譯失敗，型別不符
  • 可以放進去，批次自動跳過

FixedDeposit 沒有實作 Withdrawable，型別不符，編譯時就擋下來，不必等到批次執行。

下面哪一個子類別寫法符合里氏替換原則？（父類別約定：金額大於 0 且不超過餘額就扣款成功）

  • 金額超過一萬元就丟出例外
  • 扣款成功但不更新帳戶餘額
  • 只在營業時間內允許扣款
  • 扣款後另外記一筆稽核紀錄

多記一筆紀錄是「提供更多」，父類別承諾的結果一樣成立。另外三個不是多加要求（前置條件變強），就是少做了承諾的事（後置條件變弱）。

List.of(1, 2).add(3) 丟出 UnsupportedOperationException。關於它算不算違反里氏替換原則，這課的說法是？

  • 一定違反，JDK 這裡寫錯了
  • 一定沒違反，因為它是 JDK 自己
  • 兩派都有，要看約定寫了什麼
  • 跟里氏替換原則完全無關

Collection 文件寫明修改方法可以被規定成丟 UnsupportedOperationException。一派說呼叫端仍無法放心替換，一派說約定本來就允許。判斷都回到約定寫了什麼。

介面隔離原則：介面照使用端切

Martin 的原文：「很多個針對使用端的介面，勝過一個通用的大介面」（Many client specific interfaces are better than one general purpose interface）；做法是：一個類別有好幾種使用端時，「不要把所有使用端需要的方法都塞進這個類別，而是替每一種使用端建立專屬的介面」（rather than loading the class with all the methods that the clients need, create specific interfaces for each client）。出處

public class IspBefore {
    public static void main(String[] args) {
        BankOperations auditor = new AuditPortal();
        System.out.println(auditor.auditReport("2026-09"));
        try {
            auditor.withdraw("A-001", 1000);
        } catch (UnsupportedOperationException e) {
            System.out.println("稽核入口呼叫 withdraw：" + e.getMessage());
        }
    }
}

interface BankOperations {                             // 一個大介面，什麼都放

    void withdraw(String accountId, int amount);
    void approveLoan(String applicationId);
    String auditReport(String month);

    public void withdraw(String accountId, int amount) { throw new UnsupportedOperationException("稽核不能提款"); }

重構前，AuditPortal 被迫實作 withdraw 並丟出 UnsupportedOperationException。這是因為違反了什麼？

  • 單一職責：AuditPortal 的方法太少
  • 介面隔離：被迫實作用不到的方法
  • 開放封閉：AuditPortal 不能被繼承
  • 沒有違反任何一條原則

BankOperations 把所有使用端的方法塞在一起，稽核入口只好實作一堆用不到的方法。它同時也讓 AuditPortal 無法安全替換 BankOperations。

  • 照資料表的結構來切
  • 照方法名稱的字母順序
  • 照使用端需要的方法
  • 每個方法各一個介面

  • AuditPortal 與 AtmTerminal 都要改
  • 只有 AtmTerminal 要改
  • 只有實作 LoanApprovals 的類別要改
  • 所有類別都要重新編譯並修改

AuditPortal 與 AtmTerminal 沒有實作 LoanApprovals，不受影響。重構前所有類別都實作同一個大介面，加一個方法就全部要改。

重構前，呼叫端拿到一個 BankOperations 型別的變數（實際是 AuditPortal）並呼叫 withdraw，問題在什麼時候才會被發現？

  • 編譯時
  • 執行時丟出例外才發現
  • 永遠不會發現

從型別上看 withdraw 是合法的方法，編譯器不會擋；要等執行時丟 UnsupportedOperationException。重構後 AuditReports 根本沒有 withdraw 可以呼叫。

ATM 終端機需要存款與提款，該實作哪一個介面？

  • AuditReports
  • LoanApprovals
  • CashOperations
  • 三個介面都要實作

CashOperations 只有 deposit 與 withdraw，剛好是 ATM 要的；不必為了核貸與報表寫空方法。

高層規則不該綁死在資料庫與簡訊商身上

依賴反轉原則：依賴抽象，不依賴具體

Martin 的原文：「依賴抽象，不要依賴具體」（Depend upon Abstractions. Do not depend upon concretions.）。他把它跟開放封閉原則放在一起看：「如果開放封閉原則說的是物件導向架構的目標，依賴反轉原則說的就是主要的機制」（If the OCP states the goal of OO architecture, the DIP states the primary mechanism.）。為什麼叫「反轉」：傳統程序式設計是高層模組依賴低層模組，但高層模組處理的是應用程式的高層政策，「這些政策通常不在乎實作它們的細節」。出處 依賴反轉之後，高層規則與低層細節都依賴中間的抽象。

public class DipBefore {
    public static void main(String[] args) {
        new TransferService().transfer("A-001", "B-002", 500);
    }
}

class TransferService {                                // 高層的轉帳規則，直接 new 出低層細節
    private final MySqlAccountStore store = new MySqlAccountStore();
    private final SmsSender sms = new SmsSender();

    void transfer(String from, String to, int amount) {
        store.debit(from, amount);
        store.credit(to, amount);
        sms.send(from, "您已轉出 " + amount + " 元");

}

    void credit(String id, int amount) { System.out.println("UPDATE：" + id + " 加 " + amount); }
}

class SmsSender {
    void send(String accountId, String text) { System.out.println("真的傳簡訊給 " + accountId + " 的手機：" + text); }

轉帳規則（扣款、入帳、通知）是高層政策，卻在自己裡面 new 出正式資料庫與簡訊商。想單獨測試轉帳規則，一跑就連正式資料庫、傳真的簡訊。重構：

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class DipAfter {
    public static void main(String[] args) {
        // 測試時：換成記憶體裡的假實作，不連資料庫、不傳簡訊
        InMemoryAccountStore store = new InMemoryAccountStore(Map.of("A-001", 1000, "B-002", 0));

        new TransferService(store, notifier).transfer("A-001", "B-002", 500);
        System.out.println("A-001 = " + store.balance("A-001") + "，B-002 = " + store.balance("B-002"));
        System.out.println("應該送出的通知：" + notifier.sent);
    }

interface AccountStore {                               // 抽象由高層需要什麼來決定
    void debit(String id, int amount);
    void credit(String id, int amount);
}

interface Notifier {
    void notify(String accountId, String text);
}

class TransferService {                                // 只依賴抽象；具體實作從建構子傳進來
    private final AccountStore store;
    private final Notifier notifier;

    TransferService(AccountStore store, Notifier notifier) {
        this.store = store;
        this.notifier = notifier;
    }

    void transfer(String from, String to, int amount) {
        store.debit(from, amount);
        store.credit(to, amount);
        notifier.notify(from, "您已轉出 " + amount + " 元");
    }
}

class InMemoryAccountStore implements AccountStore {
    private final Map<String, Integer> balances;
    InMemoryAccountStore(Map<String, Integer> initial) { balances = new HashMap<>(initial); }
    public void debit(String id, int amount) { balances.merge(id, -amount, Integer::sum); }
    public void credit(String id, int amount) { balances.merge(id, amount, Integer::sum); }
    int balance(String id) { return balances.get(id); }
}

class RecordingNotifier implements Notifier {
    final List<String> sent = new ArrayList<>();
    public void notify(String accountId, String text) { sent.add(accountId + "：" + text); }
}

界線：不是每個具體類別都要先包一層介面。Martin 自己也寫了緩和條件：依賴反轉假設「任何具體的東西都會變動」，但有例外，像 C 的 string.h 非常具體卻一點也不會變，依賴它無害；「經過考驗、具體但不會變動的模組，依賴它們不算太糟」（if you have tried and true modules that are concrete, but not volatile, depending upon them is not so bad）。出處 換成 Java，直接依賴 String、BigDecimal 完全沒問題；該抽象的是資料庫、外部 API、簡訊、時間這類會換、或測試時需要換掉的東西。

重構前的 TransferService 最大的問題是什麼？

  • 完全沒有使用 static 方法
  • 自己 new 出正式資料庫與簡訊商
  • TransferService 沒有實作介面

高層的轉帳規則直接依賴具體細節，一建立就連正式資料庫，一轉帳就真的傳簡訊。實跑輸出的第一行與最後一行就是證據。

  • 兩者是同一條原則的兩個名字
  • 開放封閉是目標，依賴反轉是機制

原文：If the OCP states the goal of OO architecture, the DIP states the primary mechanism。依賴抽象，才有辦法不改舊程式就換掉實作。

  • 依賴反轉是原則，注入是技巧
  • 兩個詞指的是同一件事

  • 外部銀行的匯率 API
  • 簡訊服務商的 SDK
  • java.math.BigDecimal

  • 測試前先啟動一台正式資料庫
  • 傳入記憶體版與記錄版的假實作
  • 用反射把 private 欄位換掉
  • 把 TransferService 改成 static

原則是目標，模式是常見的做法

跟設計模式的關係

〈設計模式〉說過模式是「經驗的名字」。Martin 2000 年那篇文章的結構正好說明兩者怎麼接：先講原則，「再講技巧，也就是幫助維持應用程式相依架構的設計模式」（First we will examine the principles, and then the techniques, or design patterns, that help maintain the dependency architecture of an application.）；照著原則做，「會發現自己一再重複同樣的結構」，這些重複出現的結構就叫設計模式。出處 他舉的一個例子：程式最常依賴具體類別的地方是建立物件（抽象類別不能 new），解法是 Abstract Factory。

原則常一起出現的模式（不是一對一）本課的例子
開放封閉Strategy、Template Method、Decorator手續費 FeePolicy
依賴反轉Abstract Factory、Factory Method，以及依賴注入TransferService 依賴 AccountStore
介面隔離Adapter（把大介面轉成使用端要的小介面）稽核只拿 AuditReports
單一職責Facade（拆開之後，對外仍給一個簡單入口）利息、對帳單、存檔拆成三個類別
里氏替換所有靠多型的模式的前提子型別要守父型別的約定

這張表是常見的搭配，不是規定：同一個模式可以同時服務好幾條原則，用了模式也不保證符合原則。判斷順序跟〈設計模式〉講的一樣：先找出會變的是哪一塊，再選做法。

照 Martin 2000 年文章的說法，原則與設計模式的關係是？

  • 兩者之間沒有任何關係
  • 照原則做，同樣結構重複出現就是模式
  • 學了模式就不必再管原則
  • 原則只適用於 C++，模式才適用於 Java

文章先講原則、再講維持相依架構的技巧，也就是設計模式；模式是遵循原則時一再重複出現的結構。

Martin 指出「程式最常依賴具體類別的地方」是哪裡？他給的解法是哪個模式？

  • 寫日誌的地方；Observer
  • 建立物件的地方；Abstract Factory
  • 迴圈裡；Iterator
  • 例外處理；Chain of Responsibility

要建立物件就得 new 一個具體類別，抽象類別不能 new。Abstract Factory 讓建立的動作也隔著抽象。

下面哪一句對「原則與模式」的描述最不恰當？

  • 同一個模式可以同時服務好幾條原則
  • 先找出會變的地方，再選模式
  • 只要用了設計模式，就一定符合 SOLID
  • 里氏替換原則是所有靠多型的模式的前提

模式用錯地方一樣會讓程式難改，例如為只有一種實作的東西套上 Strategy 加 Factory，就是下一段的過早抽象。

看起來能跑，其實在累積債務

常見反模式

反模式（anti-pattern）是很常見、看起來也合理，但長期會帶來麻煩的做法。下面五個都跟上面的原則有關。

上帝類別：什麼都管的類別

一個類別什麼都做：開戶、存提款、算利息、印報表、寄通知、寫資料庫，幾千行、幾十個欄位，大家都依賴它，誰都不敢改，這種類別常被叫做上帝類別（god class）。它是單一職責原則的反面：每個部門的需求都落在它身上，任何修改都可能波及別人。修法是照「誰會要求改」一塊一塊搬出去，Fowler 的重構目錄把這個動作叫 Extract Class（把一部分欄位與方法搬到新類別）。出處 一次拆完風險很高，通常是每次碰到相關需求時順手搬一塊。

貧血模型對充血模型：兩派

貧血模型（anemic domain model）是實體只有欄位與 getter、setter，業務規則全部放在服務類別；充血模型（rich domain model，也叫豐富領域模型）是規則跟資料放在同一個物件裡。先看程式：

public class Anemic {
    public static void main(String[] args) {
        Account a = new Account();
        a.setBalance(1000);
        new AccountService().withdraw(a, 300);
        System.out.println("透過服務提款後：" + a.getBalance());
        a.setBalance(-5000);                           // 規則寫在服務裡，誰都能繞過
        System.out.println("直接呼叫 setter 之後：" + a.getBalance());
    }
}

class Account {                                        // 只有資料：getter 與 setter
    private int balance;
    int getBalance() { return balance; }
    void setBalance(int balance) { this.balance = balance; }
}

class AccountService {                                 // 規則全部放在服務
    void withdraw(Account a, int amount) {
        if (amount <= 0 || amount > a.getBalance()) throw new IllegalArgumentException("金額不合法");
        a.setBalance(a.getBalance() - amount);
    }
}
透過服務提款後：700
直接呼叫 setter 之後：-5000
public class Rich {
    public static void main(String[] args) {
        Account a = new Account(1000);
        a.withdraw(300);
        System.out.println("提款後：" + a.balance());
        try {
            a.withdraw(5000);
        } catch (IllegalArgumentException e) {
            System.out.println("再提 5000：" + e.getMessage());
        }
    }
}

class Account {                                        // 資料與規則放在一起，沒有 setter 可以繞過
    private int balance;

    Account(int opening) {
        if (opening < 0) throw new IllegalArgumentException("開戶金額不可為負");
        this.balance = opening;
    }

    void withdraw(int amount) {
        if (amount <= 0 || amount > balance) throw new IllegalArgumentException("金額不合法");
        balance -= amount;
    }

    int balance() { return balance; }
}
提款後：700
再提 5000：金額不合法

反對貧血的一派以 Fowler 為代表。他在 2003 年把貧血模型稱為反模式：這些物件「只不過是一袋 getter 和 setter」（little more than bags of getters and setters），而它根本的問題是「完全違背物件導向設計的基本想法，也就是把資料和處理放在一起」（so contrary to the basic idea of object-oriented design; which is to combine data and process together）；更實際的批評是它「付出了領域模型的所有成本，卻得不到任何好處」（they incur all of the costs of a domain model, without yielding any of the benefits）。出處 上面實跑的 setBalance(-5000) 就是它的代價：規則放在服務裡，任何人都能繞過去。

另一派認為把資料與邏輯分開本身是正當的設計。Oracle 的 Java 語言架構師 Brian Goetz 2022 年介紹資料導向程式設計（data-oriented programming）時寫：它「鼓勵我們把資料當成（不可變的）資料來建模，並把描述『怎麼處理這些資料』的業務邏輯分開放」（Data-oriented programming encourages us to model data as (immutable) data, and keep the code that embodies the business logic of how we act on that data separately.），而且「物件導向與資料導向不互相衝突，是不同情境用的不同工具」（The techniques of OOP and data-oriented programming are not at odds; they are different tools for different granularities and situations.）。出處 用 Java 21 的 record 與 sealed 介面寫起來是這樣：

public class Dop {
    public static void main(String[] args) {
        Account a = new Account("A-001", 1000);
        for (int amount : new int[]{300, 5000}) {
            String msg = switch (Withdrawals.withdraw(a, amount)) {
                case Withdrawals.Ok ok -> { a = ok.updated(); yield "提 " + amount + " 成功，餘額 " + a.balance(); }
                case Withdrawals.Rejected r -> "提 " + amount + " 被拒：" + r.reason();
            };
            System.out.println(msg);
        }
    }
}

record Account(String id, int balance) {               // 不可變的資料：只檢查「資料本身合不合法」
    Account {
        if (balance < 0) throw new IllegalArgumentException("餘額不可為負");
    }
}

final class Withdrawals {                              // 業務規則放在資料之外的函式
    sealed interface Result permits Ok, Rejected {}
    record Ok(Account updated) implements Result {}
    record Rejected(String reason) implements Result {}

    static Result withdraw(Account a, int amount) {
        if (amount <= 0 || amount > a.balance()) return new Rejected("金額不合法");
        return new Ok(new Account(a.id(), a.balance() - amount));
    }

    private Withdrawals() {}
}
提 300 成功，餘額 700
提 5000 被拒：金額不合法

注意它跟上面的貧血版不一樣：record 不可變，沒有 setter 可以把餘額改成 -5000；結果用 sealed 介面表達，呼叫端的 switch 少處理一種會編譯失敗。

兩派其實有交集：Fowler 在同一篇文章也說「領域模型不一定總是最好的工具」（Domain Models aren't always the best tool）出處。

他在《企業應用架構模式》裡把「每個請求寫成一個程序」的做法叫 Transaction Script，跟 Domain Model 並列為兩種組織業務邏輯的方式。Transaction ScriptDomain Model

實務上的判斷：

  • 偏向充血模型：規則多、彼此牽連、不變條件很重要（帳戶、額度、利率）。
  • record 加服務：資料只是在服務之間流動、規則簡單（查詢結果、API 回應），把資料寫成 record、邏輯放在服務或函式裡也很合理。

真正要避免的是「看起來是物件、其實誰都能用 setter 亂改」的那一種。

過早抽象：為還沒出現的需求蓋架構

public class Premature {
    public static void main(String[] args) {
        // 為了「以後可能有別種利息」先蓋好的三層：介面、工廠、唯一的實作
        InterestStrategy s = InterestStrategyFactory.create("DEFAULT");
        System.out.println("過早抽象版：" + s.monthly(12000));
        // 目前真正的需求只有一種算法
        System.out.println("直接寫版：" + monthlyInterest(12000));
    }

    static int monthlyInterest(int balance) { return balance / 100 / 12; }   // 年利率 1%
}

interface InterestStrategy { int monthly(int balance); }

class DefaultInterestStrategy implements InterestStrategy {
    public int monthly(int balance) { return balance / 100 / 12; }
}

final class InterestStrategyFactory {
    static InterestStrategy create(String type) {
        return switch (type) {
            case "DEFAULT" -> new DefaultInterestStrategy();
            default -> throw new IllegalArgumentException(type);
        };
    }
    private InterestStrategyFactory() {}
}
過早抽象版：10
直接寫版：10

兩種寫法結果一樣，但第一種多了介面、工廠、字串參數三層，而目前只有一種算法。這叫過早抽象：為了「以後可能」先蓋好擴充點。Fowler 的 Yagni（You Aren't Gonna Need It，你不會需要它）一文說：某些我們預期軟體未來需要的能力「現在不應該先做」（some capability we presume our software needs in the future should not be built now）；但他也強調 Yagni 不反對讓程式好改，「Yagni 只有在程式容易修改時才是可行的策略」（Yagni is only a viable strategy if the code is easy to change）。出處 Sandi Metz 的說法更直接：「重複比錯誤的抽象便宜得多」（duplication is far cheaper than the wrong abstraction），抽象錯了，「最快的前進方式是往回走」（the fastest way forward is back），先把抽象拆回各個呼叫端。出處

這跟開放封閉原則看起來衝突，其實是同一件事的兩面：開放封閉要你在「會變的地方」留擴充點，過早抽象是在「還不知道會不會變」的地方先留。實務上常見的做法是：第一次直接寫；同樣的變化真的出現第二、三次，再抽出抽象。

import java.math.BigDecimal;
import java.math.RoundingMode;

public class StaticUtil {

        // 改成物件：匯率來源從外面傳進來，測試可以給固定值
        RateSource fixed = () -> new BigDecimal("32.0");
        System.out.println("注入固定匯率：" + new Exchanger(fixed).toTwd(new BigDecimal("100")));
    }
}

final class Money {                                    // 沒有狀態、同樣輸入永遠同樣輸出：static 很合適
    static BigDecimal toDollar(BigDecimal v) { return v.setScale(0, RoundingMode.HALF_UP); }
    private Money() {}
}

final class RateUtil {                                 // 藏著外部相依的 static 工具
    static BigDecimal toTwd(BigDecimal usd) {
        return usd.multiply(fetchRateFromBankApi());
    }
    private static BigDecimal fetchRateFromBankApi() {
        System.out.println("（呼叫外部匯率 API）");
        return new BigDecimal("31.85");
    }
    private RateUtil() {}
}

interface RateSource { BigDecimal usdToTwd(); }

class Exchanger {
    private final RateSource rates;
    Exchanger(RateSource rates) { this.rates = rates; }
    BigDecimal toTwd(BigDecimal usd) { return usd.multiply(rates.usdToTwd()); }
}

static 方法不是壞東西。Money.toDollar 沒有狀態、同樣輸入永遠同樣輸出，Math.abs 也是這樣，寫成 static 很合適；上面資料導向那段的 Withdrawals.withdraw 也是。問題出在 RateUtil 這種裡面藏著外部相依的 static：呼叫端從簽章看不出它會打外部 API，測試時也沒辦法指定匯率。Google 的 Miško Hevery 2008 年的文章「Static Methods are Death to Testability」解釋：單元測試靠的是能替換相依的「接縫」，接縫靠多型運作，「static 方法沒有東西可以覆寫」（With static methods there is nothing to override.）；但他也承認呼叫樹最底層、不再呼叫別人的 static 方法（leaf method）測起來沒有問題。出處 判斷方式：純計算的放心寫成 static；碰到資料庫、網路、時間、亂數、全域狀態的，改成物件、從外面注入（就是上面的依賴反轉）。〈設計模式〉講單例「把相依藏起來」，是同一個問題。

吞掉例外

public class Swallow {
    public static void main(String[] args) {
        AccountStore store = new AccountStore();
        System.out.println("吞掉版本：" + new SilentTransfer(store).transfer("A-001", 500));
        try {
            new HonestTransfer(store).transfer("A-001", 500);
        } catch (TransferFailedException e) {
            System.out.println("不吞版本：" + e.getMessage() + "；原因：" + e.getCause().getMessage());
        }
    }
}

class AccountStore {
    void debit(String id, int amount) {
        throw new IllegalStateException("資料庫連線逾時");   // 模擬底層失敗
    }
}

class SilentTransfer {
    private final AccountStore store;
    SilentTransfer(AccountStore store) { this.store = store; }

    String transfer(String from, int amount) {
        try {
            store.debit(from, amount);
        } catch (Exception e) {
            // 什麼都不做
        }
        return "轉帳成功";                             // 錢根本沒扣，卻回報成功
    }
}

class TransferFailedException extends Exception {
    TransferFailedException(String message, Throwable cause) { super(message, cause); }
}

class HonestTransfer {
    private final AccountStore store;
    HonestTransfer(AccountStore store) { this.store = store; }

    String transfer(String from, int amount) throws TransferFailedException {
        try {
            store.debit(from, amount);
        } catch (IllegalStateException e) {
            throw new TransferFailedException("轉帳失敗：" + from + " 扣款 " + amount + " 元", e);   // 補上情境、保留原因
        }
        return "轉帳成功";
    }
}
吞掉版本：轉帳成功
不吞版本：轉帳失敗：A-001 扣款 500 元；原因：資料庫連線逾時

吞掉版本的 catch 什麼都不做，錢根本沒扣，卻回報「轉帳成功」。這比直接當掉更糟：錯誤被藏起來，之後的帳對不起來，也找不到原因。〈例外機制〉講過不要為了讓程式看起來沒壞就寫空的 catch；不吞版本照那課的做法：補上情境（哪個帳戶、多少錢）、把原本的例外當 cause 傳下去。Throwable 的 API 文件說明了為什麼要包一層而不是直接往外丟：上層的操作因為下層失敗而失敗時，「讓下層丟出的例外直接往外傳是不好的設計，因為它通常跟上層提供的抽象無關」（It would be bad design to let the throwable thrown by the lower layer propagate outward, as it is generally unrelated to the abstraction provided by the upper layer.）。出處 在 Spring 裡吞掉例外還有另一個後果：例外到不了交易攔截器，交易照常提交（〈Spring 面試快答：IoC、Bean、AOP 與交易〉）。

一個 BankService 類別有 4000 行，開戶、存提款、利息、報表、通知、資料庫存取全在裡面。它最直接違反哪一條原則？

  • 單一職責原則
  • 里氏替換原則
  • 介面隔離原則
  • 沒有違反，只是比較長

每個部門的需求都落在同一個類別，這是上帝類別，也就是單一職責原則的反面。修法是一塊一塊 Extract Class。

貧血版的實跑輸出中，a.setBalance(-5000) 之後餘額變成多少？這說明了什麼？

  • 還是 700，setter 會檢查
  • 丟出例外，程式中止
  • 0，Java 自動把負數改 0
  • -5000，setter 繞過了規則

Account 只有 setter，不檢查任何規則；只有走 AccountService 才會檢查。這是 Fowler 批評貧血模型的實際代價。

關於貧血模型，這課的立場是？

  • 兩派：反模式，或正當的分開設計
  • 一定是錯的，所有規則都要放進實體
  • 一定是對的，實體只該放資料
  • 兩派都同意貧血模型最好

Fowler 批評它違背「資料與處理放在一起」；Goetz 的資料導向主張不可變資料加分開的邏輯，並說兩種做法是不同情境的工具。兩派都反對「誰都能用 setter 亂改」。

資料導向版本跟貧血版本都把規則放在資料之外，最大的差別是什麼？

  • 資料導向版本的執行速度比較快
  • 資料導向版本不需要寫規則
  • 兩者其實完全一樣
  • record 不可變，不能繞過規則

record 的欄位不能改，要改餘額只能透過 Withdrawals.withdraw 拿到新的 Account；結果用 sealed 介面表達，少處理一種情況編譯器會提醒。

只有一種利息算法，卻先寫了 InterestStrategy 介面、InterestStrategyFactory 與唯一的實作。這屬於哪一種反模式？

  • 上帝類別
  • 過早抽象
  • 吞掉例外
  • 貧血模型

為了還沒出現的需求先蓋三層結構，結果跟直接寫一樣。Yagni：現在不需要的能力，現在不要做。

Sandi Metz 對錯誤的抽象給的建議是？

  • 拆回各呼叫端，先接受重複
  • 再多加一層抽象把它整個包起來
  • 加更多參數讓它支援新需求
  • 改寫成 static 工具類別

原文：duplication is far cheaper than the wrong abstraction，以及 the fastest way forward is back。硬改錯的抽象，只會變成充滿條件判斷的程序。

下面哪一個寫成 static 方法最合適？

  • 查詢目前匯率並換算成台幣金額
  • 把 BigDecimal 四捨五入到元
  • 寫一筆交易紀錄進資料庫
  • 取得現在時間判斷是否營業中

四捨五入沒有狀態、同樣輸入同樣輸出，測起來沒問題。另外三個碰到外部 API、資料庫、時間，寫成 static 測試時就換不掉。

常見的追問與回答方向：

  • 「SOLID 一定要遵守嗎？」它們是原則不是規定，目的是讓程式好改；硬套會多出不需要的抽象（過早抽象），所以要看哪裡真的會變。
  • 「依賴反轉和依賴注入差在哪？」前者是原則（相依指向抽象），後者是技巧（相依從外面交進來）；Spring 是做注入的工具。
  • 「舉一個違反里氏替換原則的例子。」Martin 文章裡的例子是圓形繼承橢圓（橢圓的使用端可以預期「設定兩個焦點之後，讀回來就是剛設的那兩個點」，圓形為了保持兩個焦點重合守不住這個約定），本課的例子是定存繼承可提款帳戶；重點是講出「哪一個約定被打破」。
  • 「貧血模型好不好？」講兩派：Fowler 認為是反模式，資料導向認為資料與邏輯分開是正當的；再講自己的判斷依據（規則多寡、不變條件重不重要）。

面試官問「SOLID 一定要遵守嗎？」，下面哪個回答最好？

  • 一定要遵守，違反的就是錯誤的程式
  • 不用，那是已經過時的觀念
  • 只有大型專案才需要遵守
  • 原則，不是規定；硬套會過早抽象

原則不是規定。回答時講出目的（好改）與代價（多餘的抽象），比非黑即白的答案更有說服力。

回答「舉一個違反里氏替換原則的例子」時，最關鍵要講出什麼？

  • 那個子類別總共用了幾次 extends
  • 子類別打破了父型別的哪一個約定
  • 子類別有幾個方法
  • 那個類別是哪一年寫的

里氏替換看的是約定：前置條件變強或後置條件變弱。講出「父類別承諾什麼、子類別哪裡沒做到」，例子才算講對。

用「一句話、一個例子、一個界線」講開放封閉原則，下面哪個界線講得最對？

  • 所有類別都要設成 final
  • 代表程式永遠不需要修改
  • 只對選定的那種變化封閉
  • 只能用繼承來擴充

手續費例子對「新增帳戶類型」封閉，但「每種帳戶多一種費用」還是要改介面與所有實作。擴充也不一定要靠繼承，實作介面同樣可以。

重點整理

  • SOLID 是五個讓程式在需求改變時好改的設計原則，不是編譯器會檢查的規定；每一條都有界線，硬套會變成過早抽象。原則是目標，設計模式是遵循原則時一再出現的做法：Strategy 對應開放封閉、Abstract Factory 與依賴注入對應依賴反轉。
  • 單一職責：一個類別只該因為一群人的需求而改（Martin：this principle is about people）；拆的依據是「誰會要求改」，不是方法數量。
  • 開放封閉：新增功能靠擴充、不改舊程式，關鍵是抽象；只對你選定的那種變化封閉。
  • 里氏替換：子型別放進父型別的位置要照常運作；前置條件不能變強、後置條件不能變弱。extends 寫得出來不代表語意上是子型別；違反它，呼叫端就會冒出 instanceof 判斷。
  • 介面隔離：照使用端切介面，不逼別人實作用不到的方法；也不是一個方法一個介面。
  • 依賴反轉：高層規則與低層細節都依賴抽象；依賴注入是實現它的技巧。穩定的具體類別（String、BigDecimal）可以直接依賴。
  • 反模式：上帝類別（違反單一職責）、貧血模型（兩派，共同反對 setter 亂改）、過早抽象（Yagni、重複比錯的抽象便宜）、藏著外部相依的 static 工具、吞掉例外（補上情境、保留 cause）。
