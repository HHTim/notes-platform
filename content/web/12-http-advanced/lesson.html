先看第一位數

狀態碼的五大類與常見的 17 個

〈HTTP 與 HTTPS〉介紹過五大類。RFC 9110 的規則：「狀態碼的第一位數定義回應的類別，後兩位數沒有分類的作用」（The first digit of the status code defines the class of response. The last two digits do not have any categorization role.）。RFC 9110 第 15 節 而且用戶端不必認得每一個碼，但「必須（MUST）認得任何狀態碼的類別，把看不懂的碼當成該類的 x00」（a client MUST understand the class of any status code, as indicated by the first digit, and treat an unrecognized status code as being equivalent to the x00 status code of that class.）——收到沒見過的 471，就當 400 處理。RFC 9110 第 15 節

面試清單上最常被問的 17 個，用「什麼情境回它」來記：

301 與 302 有一個歷史包袱：RFC 寫「因為歷史原因，使用者代理（user agent，瀏覽器這類替使用者發請求的程式）可以（MAY）把下一個請求的方法從 POST 改成 GET；不想要這種行為，可以改用 308（永久）或 307（暫時）」（For historical reasons, a user agent MAY change the request method from POST to GET for the subsequent request. If this behavior is undesired, the 308 (Permanent Redirect) status code can be used instead.）。RFC 9110 第 15.4.2 節 307 的定義直接寫明使用者代理自動轉址時「不得（MUST NOT）改變請求方法」（the user agent MUST NOT change the request method if it performs an automatic redirection to that URI.）。RFC 9110 第 15.4.8 節

2026-10-02 用 curl -sI 打本站的 http 網址，回的就是 301，把人送到 https：

$ curl -sI http://hhtim.github.io/notes-platform/
HTTP/1.1 301 Moved Permanently
Location: https://hhtim.github.io/notes-platform/

401 是「你是誰？」，403 是「知道你是誰，不行」；502 是上游回了壞東西，504 是上游沒在時限內回

使用者沒登入，直接打 GET /api/accounts/me，請求裡沒有任何 token。該回哪個？

  • 403 Forbidden
  • 401 Unauthorized
  • 400 Bad Request
  • 500 Internal Server Error

缺少有效的身分驗證憑據就是 401，而且要附 WWW-Authenticate 告訴用戶端怎麼驗證。403 是「知道你是誰，但不准」。

一般行員登入了，token 有效，卻去打只有主管能用的 POST /api/approvals。該回哪個？

  • 403 Forbidden
  • 401 Unauthorized
  • 409 Conflict
  • 405 Method Not Allowed

身分已經確認，只是權限不夠：伺服器看懂了請求但拒絕。這時回 401 會讓用戶端以為換個 token 就好。405 是這個資源不支援這個方法，不是權限問題。

轉帳 API 收到的 JSON 格式完全正確，但轉帳金額是 -500。比較精確的回應是？

  • 400 Bad Request
  • 422 Unprocessable Content
  • 500 Internal Server Error
  • 409 Conflict

422：內容型別看得懂、語法正確，但裡面的指令處理不了。400 偏向請求本身壞掉（例如 JSON 少一個括號）。很多團隊兩者都回 400，這題問的是哪個比較精確。

送來的 body 是 {"amount": 500，少了右大括號。該回哪個？

  • 422 Unprocessable Content
  • 400 Bad Request
  • 415 Unsupported Media Type
  • 500 Internal Server Error

語法本身就錯了，是 400 的範圍（malformed request syntax）。422 的前提是語法正確；415 是用戶端送了伺服器不支援的內容型別。

兩個人同時編輯同一份文件，後存的那個人送出的版本號已經過時。該回哪個，讓使用者知道要先合併？

  • 400 Bad Request
  • 403 Forbidden
  • 404 Not Found
  • 409 Conflict

409 是請求跟資源目前的狀態衝突，而且使用者可能解決衝突後重送。請求本身沒壞，人也有權限。

某個用戶端一秒打了 300 次查詢 API，超過每秒 50 次的上限。該回哪個？

  • 503 Service Unavailable，伺服器整個暫停服務
  • 403 Forbidden
  • 429 Too Many Requests
  • 400 Bad Request

429 就是限流（rate limiting），RFC 6585 說可以附 Retry-After 告訴對方等多久。503 是伺服器本身暫時撐不住，跟某個用戶端送太多是不同情境。

Nginx 當反向代理，後面的 Spring Boot 程式當掉了，Nginx 連過去被直接拒絕連線。使用者最可能看到？

  • 500 Internal Server Error
  • 504 Gateway Timeout
  • 404 Not Found
  • 502 Bad Gateway

Nginx 當代理、從上游拿不到有效回應，就是 502。504 是上游太慢、沒在時限內回；500 是 Nginx 自己出錯。

接上題，換成 Spring Boot 還活著，但一個查詢跑了 90 秒，Nginx 的上游逾時設 60 秒。使用者會看到？

  • 504 Gateway Timeout
  • 502 Bad Gateway
  • 500 Internal Server Error
  • 408 Request Timeout

上游沒在時限內回應，代理回 504。408 是伺服器等「用戶端」送完請求等到逾時，方向不同。

系統排定今晚 23:00 到 01:00 維護，期間所有 API 該回什麼？

  • 503 Service Unavailable
  • 500 Internal Server Error
  • 404 Not Found
  • 403 Forbidden，維護期間禁止存取

RFC 9110：503 是暫時過載或排定維護，可以附 Retry-After 建議等多久再試。用 500 或 404 會讓監控與用戶端誤判。

新增客戶的 POST /api/customers 成功了。最精確的回應是？

  • 201 Created 加 Location
  • 200 OK，body 放新客戶資料
  • 204 No Content，什麼都不回
  • 302 Found，轉到新客戶的頁面

201 表示建立了新資源，新資源的位置由 Location 標頭指出。200 也不算錯，但 201 把「建了新的」說清楚。

登入表單用 POST 送到 /login，網站搬家要轉到新網址，而且轉過去後要還是 POST。該用哪個？

  • 301 Moved Permanently
  • 302 Found
  • 308 Permanent Redirect
  • 304 Not Modified

301 與 302 因為歷史原因，用戶端可以把 POST 改成 GET。308（永久）與 307（暫時）不准改方法。

用戶端收到一個它從沒見過的狀態碼 432。照 RFC 9110 應該怎麼處理？

  • 當成 200，因為沒看過就假設成功
  • 當成 400 處理
  • 當成網路錯誤
  • 直接忽略，等下一個回應

用戶端 MUST 認得類別，看不懂的碼當成同類的 x00。4 開頭就照 400 處理。

能不能放心再按一次

方法的安全與冪等

〈HTTP 與 HTTPS〉的方法表已經列出結論，這裡把兩個詞講清楚，再講它們為什麼重要。

  • 安全（safe）：方法的語意「本質上是唯讀的」，用戶端不要求、也不預期伺服器狀態因此改變（Request methods are considered "safe" if their defined semantics are essentially read-only）。RFC 9110 定義的方法裡，「GET、HEAD、OPTIONS、TRACE 定義為安全」（the GET, HEAD, OPTIONS, and TRACE methods are defined to be safe.）。RFC 9110 第 9.2.1 節
  • 冪等（idempotent）：同樣的請求送很多次，「對伺服器的預期效果跟送一次一樣」（the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request.）；「PUT、DELETE 與安全方法是冪等的」（PUT, DELETE, and safe request methods are idempotent.）。RFC 9110 第 9.2.2 節 PATCH 的規格 RFC 5789 寫它「既不安全也不冪等」（PATCH is neither safe nor idempotent），RFC 5789 第 2 節 POST 也不是。
方法安全冪等白話
GET、HEAD是是只讀，看幾次都一樣
PUT否是「整個換成這一份」，換十次結果還是這一份
DELETE否是刪一次跟刪十次，結果都是「不在了」
POST否否「照你的規則處理這份資料」，送兩次可能建兩筆、扣兩次
PATCH否不保證看怎麼寫：「餘額設成 100」冪等，「餘額加 100」不冪等

為什麼要分：RFC 說冪等方法特別的地方是「回應還沒收到、連線就斷了時，可以自動重送請求」（the request can be repeated automatically if a communication failure occurs before the client is able to read the server's response.）。RFC 9110 第 9.2.2 節 瀏覽器、代理、HTTP 用戶端程式庫敢自動重試 GET、PUT，不敢自動重試 POST，就是靠這個。冪等看的是「伺服器的狀態」，不是回應碼：第二次 DELETE 回 404，資源一樣不在了，仍然算冪等。RFC 也補充，冪等只管使用者要求的效果，伺服器「可以每個請求各記一筆日誌」（a server is free to log each request separately），不影響冪等。

安全＝不改東西；冪等＝改了也只算一次。安全的一定冪等，冪等的不一定安全（PUT、DELETE）

要讓 POST 也能安心重試，常見做法是冪等鍵（用戶端替每次操作產生一個唯一編號，伺服器看過就不重做），見面試集〈系統設計：秒殺與限流〉。

行動 App 送出轉帳的 POST /transfers，網路斷了沒收到回應。程式庫該不該自動重送？

  • 該，HTTP 用戶端都會自動重送
  • 不該，POST 不是冪等方法
  • 該，有 TLS 保護
  • 不該，因為 POST 是安全方法，送一次就夠

自動重送只適合冪等方法。POST 不冪等，伺服器可能已經做完、只是回應丟了，再送一次就是第二筆轉帳。POST 也不是安全方法。

同一個 DELETE /cards/77 送了兩次，第一次回 204，第二次回 404。DELETE 還算冪等嗎？

  • 不算，回應碼不同
  • 算，冪等看的是伺服器狀態
  • 不算，第二次應該也回 204 才對
  • 要看伺服器有沒有替每次請求記日誌

冪等的定義是對伺服器的預期效果一樣，不是回應一樣。記日誌也不影響，RFC 明說伺服器可以每個請求各記一筆。

下面哪一個請求是冪等的？

  • PATCH，內容是「把點數加 10」
  • POST /orders，建立一張新訂單
  • POST /counters/visits，訪客數加一
  • PUT，「信箱改成 a@example.com」

PUT 是整個換成請求裡那一份，送幾次信箱都是 a@example.com。「加 10」「加一」「新建一筆」送兩次效果就不一樣。

某團隊用 GET /accounts/9/close 來關閉帳戶。這樣設計最大的問題是？

  • GET 不能帶路徑參數，要改用查詢字串
  • 周邊工具會放心地自動發 GET
  • GET 太慢
  • GET 不能用 HTTPS

安全方法的語意是唯讀，周邊工具會放心地預先抓取或重送。拿它做會改狀態的事，等於讓那些工具都有機會觸發。

PATCH 的請求內容是 {"status": "closed"}（直接設成某個值）。這個請求送兩次會怎樣？

  • 一定會出錯，PATCH 不能重複送
  • 狀態會變成 closed 兩次，變成不同的值
  • 伺服器回 409
  • 效果跟只送一次一樣

RFC 5789 說 PATCH 不保證冪等，但「設成某個值」這種寫法送幾次都一樣；「加多少」這種寫法就不冪等。冪等是看實際語意。

一條連線用到底

Keep-Alive 與隊頭阻塞

〈TCP、UDP 與 TLS 握手〉算過：每開一條新連線，要先付一趟 TCP 交握、再一趟 TLS 握手，壅塞視窗還要從慢啟動重新長。所以 HTTP/1.1 的預設是不關：「HTTP/1.1 預設使用『持久連線』，讓多個請求與回應走同一條連線」（HTTP/1.1 defaults to the use of "persistent connections", allowing multiple requests and responses to be carried over a single connection.）。RFC 9112 第 9.3 節 判斷規則是：收到的協定是 HTTP/1.1 以上，「這次回應之後連線繼續保持」（the connection will persist after the current response）；HTTP/1.0 才要看有沒有 keep-alive 連線選項。RFC 9112 第 9.3 節

換句話說，Connection: keep-alive 是 HTTP/1.0 留下來的寫法，HTTP/1.1 不寫也會保持連線，要關才寫 Connection: close。2026-10-02 用 curl -v --http1.1 對本站連抓兩頁（節錄）：

* Connected to hhtim.github.io (185.199.108.153) port 443
> GET /notes-platform/ HTTP/1.1
< HTTP/1.1 200 OK
< Connection: keep-alive
* Connection #0 to host hhtim.github.io left intact
* Re-using existing connection with host hhtim.github.io
> GET /notes-platform/web/ HTTP/1.1
< HTTP/1.1 200 OK

第二個請求前面沒有新的 Connected to，而是 Re-using existing connection：同一條連線（#0）接著用，省下交握與握手。GitHub Pages 的回應還是附了 Connection: keep-alive，對 HTTP/1.1 來說這行寫不寫都一樣。這跟 TCP 自己的 keep-alive（定時送探測區段，確認閒置連線還活著）是兩件事，名字撞在一起而已。

隊頭阻塞從哪來：同一條 HTTP/1.1 連線上，下一個請求要等上一個回應回來。HTTP/1.1 雖然允許管線化（pipelining，不等回應就連續送請求），但規定伺服器「必須（MUST）照收到請求的順序送出對應的回應」（it MUST send the corresponding responses in the same order that the requests were received.），RFC 9112 第 9.3.2 節 第一個回應慢，後面的就算算好了也得排隊。MDN 寫現代瀏覽器預設不開管線化（HTTP pipelining is not activated by default in modern browsers），MDN「Connection management in HTTP/1.x」 實務上就是「多開幾條連線」：RFC 9112 說多條連線「通常是用來避開隊頭阻塞問題」（Multiple connections are typically used to avoid the "head-of-line blocking" problem），但每條都吃伺服器資源，所以不訂上限、只鼓勵用戶端保守；RFC 9112 第 9.4 節 MDN 寫的常見數字是 6 條平行連線（a more common use of 6 parallel connections）。MDN「Connection management in HTTP/1.x」

用戶端送出的請求是 HTTP/1.1，沒有任何 Connection 標頭。伺服器回完之後，連線照規格會怎樣？

  • 立刻關閉，要保持得寫 Connection: keep-alive
  • 5 秒後關閉
  • 保持開著，給下一個請求用
  • 看伺服器是 Nginx 還是 Apache

RFC 9112：收到的是 HTTP/1.1 以上，這次回應後連線繼續保持。要關才寫 Connection: close。閒置多久後關，則是各伺服器自己設的。

curl -v 的輸出裡，第二個請求前面出現 Re-using existing connection，沒有新的 Connected to。這代表？

  • 同一條連線接著用，沒有重新交握
  • 第二個請求失敗了，curl 改用快取的內容
  • 伺服器拒絕新連線
  • 第二個請求改走 UDP

持久連線的效果就是省掉第二次的 TCP 交握與 TLS 握手。curl 用連線編號 #0 標出它是同一條。

一條 HTTP/1.1 連線上開了管線化，依序送出 A（要算 3 秒）、B（0.1 秒）、C（0.1 秒）。B 的回應什麼時候到用戶端？

  • 0.1 秒後，B 算完就回
  • 0.2 秒後，B、C 依序算完就回
  • B 會被丟掉
  • 等 A 的回應送完之後

RFC 9112：伺服器 MUST 照收到請求的順序送出回應。A 慢，B、C 就算先算好也得排在後面，這就是 HTTP 層的隊頭阻塞。

HTTP/1.1 時代的瀏覽器為什麼會對同一台主機開好幾條連線？

  • 因為 TCP 規定一條連線只能傳一個檔案
  • 一條連線同時只能等一個回應
  • 為了讓伺服器記得是同一個使用者
  • 為了繞過 TLS 憑證檢查

RFC 9113 第 1 節也這樣寫：HTTP/1.0 與 1.1 的用戶端靠對同一台伺服器開多條連線來同時發請求。代價是每條都要交握、都吃伺服器資源。

一條連線，很多條車道

HTTP/2：多路複用與標頭壓縮

RFC 9113 開頭講了 HTTP/2 要解的兩個問題：HTTP/1.1 的管線化「只部分解決請求的併發，仍然受應用層隊頭阻塞所苦」（only partially addressed request concurrency and still suffers from application-layer head-of-line blocking）；而且 HTTP 標頭「常常重複又冗長，造成不必要的網路流量」（HTTP fields are often repetitive and verbose, causing unnecessary network traffic）。對策是「允許在同一條連線上交錯傳送訊息，並對 HTTP 欄位使用有效率的編碼」（it allows interleaving of messages on the same connection and uses an efficient coding for HTTP fields.）。RFC 9113 第 1 節

  • 多路複用（multiplexing，也常叫多工：一條連線同時跑很多組請求回應）：每組請求回應是一個串流（stream），訊息切成一塊塊二進位的訊框（frame）。RFC 的定義：串流是「一條 HTTP/2 連線裡，用戶端與伺服器之間交換的一串獨立、雙向的訊框」，而且「一條連線可以同時有多個開著的串流，任一端都可以交錯送出不同串流的訊框」（A single HTTP/2 connection can contain multiple concurrently open streams, with either endpoint interleaving frames from multiple streams.）。RFC 9113 第 5 節 用戶端開的串流「必須（MUST）用奇數編號」（Streams initiated by a client MUST use odd-numbered stream identifiers）。RFC 9113 第 5.1.1 節
  • 標頭壓縮 HPACK：RFC 7541 說它「消除重複的標頭欄位」（eliminates redundant header fields）。RFC 7541 第 1 節 做法是兩張對照表：靜態表預先定義常見的標頭，動態表由編碼的一方把這條連線上重複出現的標頭加進去（The static table ... is predefined and contains common header fields ... The dynamic table ... can be used by the encoder to index header fields repeated in the encoded header lists.）。RFC 7541 第 2.3 節 第二個請求的 user-agent、cookie 跟第一個一樣，就只送一個小小的編號。

2026-10-02 用 curl -v --http2 連抓本站兩頁（節錄）：

* ALPN: curl offers h2,http/1.1
* ALPN: server accepted h2
* [HTTP/2] [1] OPENED stream for https://hhtim.github.io/notes-platform/
* [HTTP/2] [1] [:method: GET]
* [HTTP/2] [1] [:scheme: https]
* [HTTP/2] [1] [:authority: hhtim.github.io]
* [HTTP/2] [1] [:path: /notes-platform/]
* Re-using existing connection with host hhtim.github.io
* [HTTP/2] [3] OPENED stream for https://hhtim.github.io/notes-platform/web/

三件事對得上規格：用 TLS 握手裡的 ALPN（應用層協定協商）談好走 h2；兩個請求是同一條連線上的串流 1 和 3（奇數）；請求行變成 :method、:scheme、:authority、:path 四個偽標頭（〈從輸入網址到看到網頁〉提過）。另外，HTTP/2 不准帶 Connection、Keep-Alive 這類只跟單一連線有關的標頭：「端點不得（MUST NOT）產生含有連線專用標頭欄位的 HTTP/2 訊息」（An endpoint MUST NOT generate an HTTP/2 message containing connection-specific header fields.）。RFC 9113 第 8.2.2 節

沒解決的那一層：RFC 9113 自己寫「TCP 的隊頭阻塞本協定沒有處理」（TCP head-of-line blocking is not addressed by this protocol.）。RFC 9113 第 1 節 多個串流在 HTTP 層是分開的，到了 TCP 只是一條位元組串流，丟一包，後面所有串流的資料都卡在接收端等重傳。

瀏覽器用 HTTP/2 同時抓 30 張圖片。通常會開幾條 TCP 連線到同一台主機？

  • 30 條，一張一條
  • 6 條，跟 HTTP/1.1 一樣
  • 1 條，30 個串流在上面交錯傳
  • 0 條，HTTP/2 不用 TCP

RFC 9113 第 9.1 節：Clients SHOULD NOT open more than one HTTP/2 connection to a given host and port pair，同一個主機與連接埠，用戶端不應該開超過一條 HTTP/2 連線，30 張圖就是同一條連線上的 30 個串流。HTTP/2 仍跑在 TCP 上，不用 TCP 的是 HTTP/3。RFC 9113 第 9.1 節

HTTP/2 連線上，用戶端開了串流 1、3，接著要開第三個。它的編號會是？

  • 2
  • 4
  • 5
  • 0

用戶端開的串流 MUST 用奇數，而且照順序遞增：1、3、5。偶數留給伺服器開的串流，0 號是整條連線本身用的。

HTTP/2 連線上同時有 5 個串流在傳，中間一個 TCP 封包遺失。會發生什麼事？

  • 整條連線斷掉，要重新交握
  • 5 個串流都要等那個封包重傳
  • 遺失的資料直接跳過不補

這就是 HTTP/2 還留著的 TCP 層隊頭阻塞。RFC 9114 寫：一個遺失或亂序的封包會讓所有進行中的交易停擺。只卡單一串流是 HTTP/3 的 QUIC 做到的。

第二個 HTTP/2 請求帶的 user-agent、cookie 跟第一個完全一樣。HPACK 會怎麼送？

  • 直接省略
  • 用對照表裡的編號代替
  • 改放進 body 裡一起壓縮

HPACK 的動態表記住這條連線上出現過的標頭，重複的就用索引代替，這就是「消除重複的標頭欄位」。

  • 沒問題，跟 HTTP/1.1 一樣
  • 必須帶
  • 可以帶，但會被當成註解略過
  • 不合 HTTP/2 的規定

RFC 9113 第 8.2.2 節：MUST NOT generate an HTTP/2 message containing connection-specific header fields，Connection、Keep-Alive 都在裡面。HTTP/2 的連線管理靠訊框，不靠標頭。

  • TLS 握手的時候
  • DNS 查詢的時候
  • TCP 三向交握的時候

ALPN 是 TLS 的擴充，用戶端在 ClientHello 列出 h2、http/1.1，伺服器挑一個。所以第一個 HTTP 請求送出時，雙方已經知道要講哪一版。

把車道搬到傳輸層

HTTP/3 與 QUIC

RFC 9114 先點出 HTTP/2 的問題：「因為 HTTP/2 多路複用的平行性對 TCP 的遺失復原機制不可見，一個遺失或亂序的封包會讓所有進行中的交易停擺，不管那筆交易有沒有直接受到影響」（because the parallel nature of HTTP/2's multiplexing is not visible to TCP's loss recovery mechanisms, a lost or reordered packet causes all active transactions to experience a stall regardless of whether that transaction was directly impacted by the lost packet.）。RFC 9114 第 1.1 節 解法是把多路複用交給傳輸層。QUIC「內建串流多工與每個串流各自的流量控制」，「在串流層級提供可靠性、在整條連線上做壅塞控制」（By providing reliability at the stream level and congestion control across the entire connection），也「在傳輸層整合了 TLS 1.3」（QUIC also incorporates TLS 1.3 ([TLS]) at the transport layer）。RFC 9114 第 1.2 節

  • 只卡遺失的那個串流：RFC 9000：「QUIC 的好處之一是避免跨串流的隊頭阻塞。封包遺失時，只有資料在那個封包裡的串流要等重傳，其他串流可以繼續前進」（One of the benefits of QUIC is avoidance of head-of-line blocking across multiple streams. When a packet loss occurs, only streams with data in that packet are blocked waiting for a retransmission to be received, while other streams can continue making progress.）。RFC 9000 第 13 節
  • 握手合併：「QUIC 的握手同時協商加密與傳輸參數」（The QUIC handshake combines negotiation of cryptographic and transport parameters.），RFC 9000 第 1 節 不用先 TCP 交握一趟、再 TLS 握手一趟。
  • 換網路不斷線：QUIC 用連線 ID 認連線，不靠 IP 加連接埠，「讓連線在端點位址改變後還能存活，例如端點換到新的網路」（The use of a connection ID allows connections to survive changes to endpoint addresses (IP address and port), such as those caused by an endpoint migrating to a new network.）。RFC 9000 第 9 節 手機從 Wi-Fi 切到行動網路，TCP 連線會斷，QUIC 連線可以接著用。
  • 標頭壓縮改成 QPACK：「HPACK 壓縮的變形，目的是減少隊頭阻塞」（a variation of HPACK compression that seeks to reduce head-of-line blocking.）。RFC 9204 HPACK 假設標頭照順序到，QUIC 的串流之間不保證順序，所以要改。

瀏覽器怎麼知道可以用 HTTP/3：常見的做法是伺服器在 HTTP/1.1 或 HTTP/2 的回應裡帶 Alt-Svc 標頭，用 h3 宣告有對應的 HTTP/3 端點。RFC 9114 第 3.1.1 節 2026-10-02 實測，本站（GitHub Pages）的回應裡沒有 Alt-Svc；同一天打 www.cloudflare.com 有：

$ curl -sI https://www.cloudflare.com/ | grep -i alt-svc
alt-svc: h3=":443"; ma=86400

意思是「同一個主機的 UDP 443 也有 HTTP/3，這個資訊可以記 86400 秒」。UDP 被擋、QUIC 連不上時，用戶端應該退回 TCP 版的 HTTP（〈TCP、UDP 與 TLS 握手〉講過）。

  • 只有串流 9 要等重傳
  • 連線重建
  • 遺失的資料不補，串流 9 直接結束

使用者在捷運上開著網銀，手機從車站 Wi-Fi 切到 4G，IP 位址變了。哪一種連線比較有機會不斷線、接著用？

  • HTTP/1.1 over TCP
  • HTTP/3 over QUIC
  • HTTP/2 over TCP

TCP 連線是用 IP 加連接埠認的，位址一換就不是同一條。QUIC 用連線 ID 認，RFC 9000 第 9 節說連線可以在位址改變後存活。

某網站回應帶 alt-svc: h3=":443"; ma=86400。瀏覽器接下來可能怎麼做？

  • 把網址改成 h3:// 開頭
  • 把這個回應本身快取 86400 秒再重新驗證
  • 關掉 TLS
  • 之後改試 UDP 443 的 HTTP/3

Alt-Svc 用 h3 宣告同一主機的 443 埠有 HTTP/3；ma 是這個宣告能記多久，不是回應本身的快取時間。網址的 scheme 還是 https。

為什麼 HTTP/3 不能直接沿用 HTTP/2 的 HPACK，要改成 QPACK？

  • HPACK 的專利過期了
  • HPACK 要求照順序更新動態表
  • HTTP/3 不需要壓縮標頭
  • QPACK 壓得比較小

RFC 9204 說 QPACK 是 HPACK 的變形，目的是減少隊頭阻塞。HPACK 的動態表要照順序更新，在 TCP 上沒問題，在各串流獨立的 QUIC 上會卡住。

同樣在一個來回 100 毫秒的網路上、第一次連一台伺服器，HTTPS 走 HTTP/2（TCP＋TLS 1.3）與走 HTTP/3，建立好連線大約各要多久？

  • HTTP/2 約 200、HTTP/3 約 100 毫秒
  • 兩個都是 100 毫秒
  • HTTP/2 100 毫秒，HTTP/3 200 毫秒
  • 兩個都是 300 毫秒

TCP 三向交握一趟、TLS 1.3 握手一趟；QUIC 把傳輸與加密參數合在同一個握手。0-RTT 能再省，但要有上次連線留下的金鑰，不算第一次連。

存一份，下次少跑一趟

Cache-Control、ETag 與 304

快取要回答兩個問題：「存著的這份能不能不問伺服器就用」叫新鮮度，「過期了能不能只問一句『變了沒』就繼續用」叫驗證。RFC 9111 的定義：「新鮮」的回應是年齡還沒超過新鮮期限的回應，超過就是「過期」（A "fresh" response is one whose age has not yet exceeded its freshness lifetime. Conversely, a "stale" response is one where it has.）。RFC 9111 第 4.2 節 快取分兩種：私有快取「專屬單一使用者」，通常就是瀏覽器；共用快取「存回應給多個使用者重用」，通常是 CDN 或代理（A "shared cache" is a cache that stores responses for reuse by more than one user ... A "private cache", in contrast, is dedicated to a single user）。RFC 9111 第 1 節

2026-10-02 用 curl -sI 看本站首頁的回應標頭（節錄）：

HTTP/2 200
last-modified: Fri, 02 Oct 2026 11:14:10 GMT
etag: "6abf9202-1edf"
expires: Fri, 02 Oct 2026 11:25:02 GMT
cache-control: max-age=600
date: Fri, 02 Oct 2026 11:15:18 GMT
via: 1.1 varnish
age: 16
x-cache: HIT
vary: Accept-Encoding

一行一行讀：

  • cache-control: max-age=600：「回應的年齡超過 600 秒就視為過期」（the response is to be considered stale after its age is greater than the specified number of seconds.）。RFC 9111 第 5.2.2.1 節 也就是 10 分鐘內，瀏覽器可以完全不連線、直接用存著的那份。
  • expires：舊式的過期時間。同時有 max-age 時，「接收者必須（MUST）忽略 Expires」（If a response includes a Cache-Control header field with the max-age directive (Section 5.2.2.1), a recipient MUST ignore the Expires header field.）。RFC 9111 第 5.3 節
  • age: 16：發送者估計這份回應「從原始伺服器產生或驗證以來過了多久」，單位秒（the sender's estimate of the time since the response was generated or successfully validated at the origin server.）。RFC 9111 第 5.1 節 這份在中間的 CDN（via: 1.1 varnish、x-cache: HIT）已經放了 16 秒，所以瀏覽器拿到時只剩 584 秒新鮮。
  • etag 與 last-modified：兩種驗證器（用來問「變了沒」的版本標記）。ETag 是不透明的版本字串；RFC 說它在修改時間不好保存、或「HTTP 日期只到一秒的精度不夠」時比修改日期可靠（where the one-second resolution of HTTP-date values is not sufficient）。RFC 9110 第 8.8.3 節

過期之後，瀏覽器把 ETag 放進 If-None-Match 送條件式請求。兩個條件都帶時，If-None-Match 優先：「請求有 If-None-Match 時，接收者必須（MUST）忽略 If-Modified-Since」（A recipient MUST ignore If-Modified-Since if the request contains an If-None-Match header field）。RFC 9110 第 13.1.3 節 同一天實測：

$ curl -sI -H 'If-None-Match: "6abf9202-1edf"' https://hhtim.github.io/notes-platform/
HTTP/2 304
cache-control: max-age=600
etag: "6abf9202-1edf"
age: 16
vary: Accept-Encoding

304 沒有內容，只帶回 cache-control、etag 這些更新快取用的標頭——RFC 規定 304 要帶回 200 時會有的 Date、ETag、Vary、Cache-Control、Expires 等欄位。RFC 9110 第 15.4.5 節 快取收到 304，就拿新資訊「更新」存著的回應繼續用。RFC 9111 第 4.3.4 節

網銀的「帳戶明細」頁不希望留在任何快取裡，包括使用者的瀏覽器。回應該帶？

  • Cache-Control: max-age=0

  • 存起來，但每次用之前先問

  • 450 秒
  • 已經過期，要重新驗證
  • 大約 150 秒

新鮮與否看「年齡有沒有超過新鮮期限」。CDN 已經放了 450 秒，600 − 450 ＝ 150 秒後就過期。

回應同時有 Cache-Control: max-age=60 與 Expires（寫的是一小時後）。快取該照哪個？

  • Expires，因為比較長
  • 取比較長的
  • 兩個都不管，由快取自己估
  • max-age，照 60 秒

RFC 9111 第 5.3 節：回應有 max-age 時，接收者 MUST ignore the Expires header field。所以是 60 秒。

條件式請求同時帶了 If-None-Match 與 If-Modified-Since，而 ETag 對不上、修改時間卻沒變。伺服器該怎麼判斷？

  • 看 If-Modified-Since，回 304
  • 回 304
  • 回 200 和新的內容
  • 回 412 Precondition Failed

RFC 9110：請求有 If-None-Match 時 MUST ignore If-Modified-Since，因為 ETag 比日期精確（日期只到秒）。ETag 不同代表內容變了。

CDN 想把圖片存 1 天，但希望使用者的瀏覽器只存 5 分鐘。哪個寫法符合？

  • max-age=86400
  • max-age=86400, private
  • no-cache, max-age=300, s-maxage=300
  • max-age=300, s-maxage=86400

s-maxage 只對共用快取有效，而且蓋過 max-age；瀏覽器（私有快取）照 max-age=300。加 private 會讓 CDN 根本不能存。

同一個網址，不只一種答案

Vary：告訴快取「還要看這幾個請求標頭」

同一個網址可能依請求不同回不同內容，例如有的用戶端支援 gzip 壓縮、有的不支援。快取如果只用網址當鑰匙，可能把壓縮版交給不會解壓縮的用戶端。RFC 9110：Vary 描述「除了方法與目標網址之外，請求的哪些部分可能影響了伺服器怎麼挑這份回應的內容」（describes what parts of a request message, aside from the method and target URI, might have influenced the origin server's process for selecting the content of this response.），一句話就是「Vary 擴大了比對快取所需的鍵」（In other words, Vary expands the cache key required to match a new request to the stored cache entry.）。RFC 9110 第 12.5.5 節 快取端的規則：存著的回應有 Vary 時，除非新請求在 Vary 列出的每個標頭都跟原本那個請求相符，否則「不得（MUST NOT）未經驗證就使用」。RFC 9111 第 4.1 節

本站首頁回 vary: Accept-Encoding。2026-10-02 實測，帶 Accept-Encoding: gzip 與不帶，拿到的是兩份不同的回應：

$ curl -s -o /dev/null -D - -H 'Accept-Encoding: gzip' https://hhtim.github.io/notes-platform/
HTTP/2 200
content-encoding: gzip
vary: Accept-Encoding
content-length: 3358

$ curl -s -o /dev/null -D - https://hhtim.github.io/notes-platform/
HTTP/2 200
vary: Accept-Encoding
content-length: 7903

反過來，Vary: * 表示還有請求以外的因素（例如用戶端的網路位址）影響了結果，快取無法自己判斷，等於每次都要轉送給伺服器。RFC 9110 第 12.5.5 節

一個 API 依 Accept-Language 回中文或英文的錯誤訊息，回應可以被 CDN 快取。回應該加什麼？

  • Vary: Accept-Language
  • Vary: Accept-Encoding
  • Cache-Control: public
  • Content-Language: *

內容依 Accept-Language 而不同，就要讓快取把它算進鍵裡。沒有這行，CDN 可能把中文版交給要英文的人。

CDN 存了一份回應，標頭有 Vary: Accept-Encoding，當初請求帶的是 Accept-Encoding: gzip。新請求帶 Accept-Encoding: br。CDN 能直接把存著的那份交出去嗎？

  • 不能直接交出去
  • 能，網址一樣就可以
  • 能，都是壓縮
  • 不能，而且要回 406 Not Acceptable

RFC 9111 第 4.1 節：Vary 列出的請求標頭都要跟原請求相符，否則不得未經驗證就用。值不同就是另一把鑰匙。

某工程師在所有回應都加上 Vary: User-Agent。最可能的副作用是？

  • 瀏覽器會拒絕這個回應
  • 回應會變大很多
  • 快取命中率大幅下降
  • TLS 握手會失敗

Vary 擴大快取鍵。User-Agent 每個瀏覽器版本都不同，鍵分得太碎，快取命中率會掉很多。

回應帶 Vary: *。共用快取下一次收到同網址的請求時？

  • 直接用存著的那份
  • 改用 Accept-Encoding 當鍵
  • 要轉送給伺服器
  • 回 304

* 表示請求以外的因素也可能影響結果，快取無從比對，只能把請求轉給伺服器。

先說你要什麼

內容協商

Vary 的另一面是內容協商（content negotiation）：用戶端在請求裡說偏好，伺服器挑一份最合適的回。RFC 9110 把這種由伺服器挑的方式叫「主動協商」，也叫「伺服器端協商」（it is called "proactive negotiation" (a.k.a., "server-driven negotiation").）。RFC 9110 第 12.1 節 常見的請求標頭：

請求標頭問的是伺服器回應時對應的標頭
Accept要什麼格式，例如 application/json、text/htmlContent-Type
Accept-Encoding接受哪些壓縮，例如 gzip、brContent-Encoding
Accept-Language偏好的語言，例如 zh-TW、enContent-Language

偏好用 q 值（quality value）排先後：權重「正規化成 0 到 1 的實數，0.001 最不想要、1 最想要，0 代表『不接受』」（The weight is normalized to a real number in the range 0 through 1, where 0.001 is the least preferred and 1 is the most preferred; a value of 0 means "not acceptable".），沒寫 q 就是 1。RFC 9110 第 12.4.2 節 例如 Accept-Language: zh-TW, en;q=0.5 是「最想要台灣中文，英文也行」。

挑不出來時：伺服器找不到符合偏好的表述、又不願給預設版本，回 406 Not Acceptable。RFC 9110 第 15.5.7 節 至於壓縮，「請求沒有 Accept-Encoding 時，任何內容編碼都算用戶端可以接受」（If no Accept-Encoding header field is in the request, any content coding is considered acceptable by the user agent.）。RFC 9110 第 12.5.3 節 規格這樣允許，但上面的實測裡，本站對沒帶 Accept-Encoding 的請求還是回了沒壓縮的原文，比較保守。

另一種「回應式協商」是伺服器先回一份候選清單，由使用者代理自己挑（selection of content ... is performed by the user agent after receiving an initial response.），RFC 9110 第 12.2 節 網頁上的「切換語言」連結就是這一類。

請求帶 Accept: application/json，這個 API 只會回 XML，也不願意給預設版本。照 RFC 9110 該回？

  • 200，照樣回 XML
  • 415 Unsupported Media Type
  • 400 Bad Request
  • 406 Not Acceptable

406：找不到符合主動協商標頭的表述、又不願給預設的。415 方向相反，是用戶端「送來」的內容型別伺服器不支援。

請求帶 Accept-Language: ja;q=0.2, en;q=0.8, zh-TW。伺服器三種語言都有，照偏好該回哪一種？

  • ja，因為排第一個
  • en，因為寫了 q 值的裡面最高
  • zh-TW
  • 三種都回

沒寫 q 的預設權重是 1，比 0.8、0.2 都高。排序看 q 值，不看寫在第幾個。

請求帶 Accept-Encoding: gzip;q=0, br。伺服器手上有 gzip 版、br 版與原文。不該回哪一種？

  • br 版
  • 原文（沒壓縮的版本）
  • gzip 版
  • 三種都可以

q=0 代表「不接受」。br 沒寫 q，權重 1，是最好的選擇。原文沒有被 q=0 排除，照規格也可以。

伺服器依 Accept 回 JSON 或 HTML，回應可以被快取。除了 Content-Type，還應該帶什麼？

  • Vary: Accept-Encoding
  • Cache-Control: no-store
  • Vary: Accept
  • Content-Encoding: json

有做內容協商、又能被快取，就要用 Vary 告訴快取把 Accept 算進鍵。不然要 HTML 的瀏覽器可能拿到別人快取的 JSON。

重點整理

  • 狀態碼看第一位數分五類，看不懂的照同類 x00 處理。401 不知道你是誰、403 知道但不准；400 語法壞、422 語法對但內容不合理；502 上游回了壞的、504 上游沒回；429 限流、503 暫時撐不住；要保留方法就用 307、308。
  • 安全＝唯讀（GET、HEAD、OPTIONS、TRACE）；冪等＝送多次效果跟一次一樣（再加 PUT、DELETE）。冪等決定能不能自動重試；POST 不冪等。
  • HTTP/1.1 預設持久連線，Connection: keep-alive 是 HTTP/1.0 的寫法；管線化的回應要照順序，前面慢後面全等（HTTP 層隊頭阻塞），所以瀏覽器多開連線。
  • HTTP/2：一條連線多個串流（用戶端開奇數），HPACK 用靜態表與動態表壓縮重複標頭，禁止連線專用標頭；TCP 層的隊頭阻塞還在。
  • HTTP/3：QUIC 在 UDP 上做串流、可靠性與 TLS 1.3，遺失只卡該串流、握手一趟、換網路不斷線，標頭用 QPACK；靠 Alt-Svc 的 h3 得知可以用。
  • 快取：max-age 內直接用（Age 要扣掉）；過期帶 If-None-Match 問，沒變回 304；no-cache 是每次先問、no-store 才是不准存；private 不准 CDN 存、s-maxage 給 CDN 用。
  • Vary 把列出的請求標頭加進快取鍵；內容協商用 Accept 系列與 q 值（沒寫是 1、0 是不接受），挑不出來回 406。
