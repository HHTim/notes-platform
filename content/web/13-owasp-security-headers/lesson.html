先有一張地圖

OWASP Top 10:2025：十類最常見的風險

OWASP（Open Worldwide Application Security Project）是一個整理網頁安全知識的非營利基金會。它的 Top 10 官方說法是「給開發者與網頁應用程式安全的標準認知文件，代表對網頁應用程式最關鍵安全風險的廣泛共識」（It represents a broad consensus about the most critical security risks to web applications.），撰寫時的現行版是 2025 年版。出處 它是一張「最常出事的地方」的地圖，不是完整的檢查清單。

編號與名稱一個例子一個防法
A01 存取控制失效把網址裡的帳戶編號改成別人的，就看到別人的資料除了公開資源，預設拒絕，而且在伺服器端檢查
A02 安全設定錯誤正式環境還開著預設帳號，錯誤頁印出整段堆疊一套可重複的加固流程，各環境設定一致
A03 軟體供應鏈失效用到一個早就有已知漏洞、沒人更新的套件追蹤直接與間接相依的版本，持續更新
A04 密碼學失效傳輸沒加密、敏感資料明文存放傳輸一律加密，敏感資料不必要就不存
A05 注入使用者輸入被拼進 SQL，改變了查詢參數化查詢，把資料跟指令分開
A06 不安全的設計設計時根本沒想到要限制轉帳次數設計階段就做威脅建模
A07 認證失效允許拿外洩的帳密大量試登入多因子認證、檢查是否為已外洩密碼
A08 軟體或資料完整性失效CI/CD 從不受信任的地方抓套件、不驗簽章只用受信任的套件來源，驗證數位簽章
A09 安全記錄與告警失效只記成功登入，失敗的沒記登入、存取控制失敗都要記錄並告警
A10 例外狀況處理不當轉帳做到一半出錯，扣款沒有一起撤回出錯就整筆撤回（fail closed）

表格的防法都出自各類別頁的「How to prevent」。幾句原文：

  • A01：「除了公開資源以外，預設拒絕」，而且存取控制「只有實作在受信任的伺服器端程式碼裡才有效」。OWASP：Except for public resources, deny by default.出處
  • A05：「最好的方法是讓資料跟指令、查詢分開」。OWASP：keeping data separate from commands and queries出處
  • A10：正好用轉帳當例子：「扣款、入帳、記錄交易」做到一半出錯，系統沒把整筆撤回（fail closed），攻擊者可能把帳戶掏空。出處

跟 2021 年版比，導言說 SSRF「已併入」A01（Server-Side Request Forgery (SSRF) has been rolled into this category），並有兩個新類別：A03 供應鏈與 A10 例外狀況。出處

A07 的密碼怎麼存、A01 裡 JWT 與 Session 的問題，在 Spring 模組〈網站安全三題：CORS、CSRF、密碼學〉與面試集〈認證與安全面試題：JWT、OAuth 2.0、OIDC 與密碼保存〉。

OWASP Top 10:2025 排第一的類別是？

  • 注入
  • 密碼學失效
  • 安全設定錯誤
  • 存取控制失效

2025 年版 A01 是存取控制失效（Broken Access Control），注入是 A05，安全設定錯誤是 A02。

登入後把網址 /statements?account=1001 改成 1002，看到別人的對帳單。這屬於哪一類？

  • A01 存取控制失效
  • A05 注入
  • A07 認證失效
  • A02 安全設定錯誤

已經登入（認證沒問題），但能存取不屬於自己的資料，是授權沒做。A01 的描述裡就有「提供別人的唯一識別碼就能看或改別人的帳戶」。

A01 的防法裡，存取控制應該做在哪裡才有效？

  • 前端的 JavaScript，按鈕不給按就好
  • HTML 隱藏欄位
  • 瀏覽器的 Cookie 設定
  • 受信任的伺服器端程式碼

OWASP：只有實作在攻擊者改不到的伺服器端才有效。前端的限制使用者都能繞過，例如直接送 API 請求。

2025 年版跟 2021 年版比，SSRF 怎麼了？

  • 併入 A01 存取控制失效
  • 從清單上移除，因為雲端環境已經把這類問題都擋掉了
  • 升到第一名
  • 改名為 A10

導言原文：SSRF has been rolled into this category，指 A01。它的防法下面會講，仍然重要。

2025 年版新增的兩個類別是？

  • 注入與跨網站指令碼（XSS）
  • 軟體供應鏈失效與例外狀況處理不當
  • 認證失效與密碼學失效
  • SSRF 與 CSRF

導言寫 two new categories and one consolidation：新的是 A03 供應鏈與 A10 例外狀況，合併的是 SSRF 併進 A01。

轉帳流程是「扣款、入帳、記錄」，入帳時出錯，系統只停在那裡，扣款沒有撤回。照 OWASP 2025 年版，最直接相關的是哪一類？

  • A05 注入
  • A04 密碼學失效
  • A09 安全記錄與告警失效
  • A10 例外狀況處理不當

A10 頁面就用這個轉帳例子，要求出錯時整筆撤回（fail closed）。Spring 的交易還原就是實作這件事的工具。

系統只記錄成功的登入，失敗的登入沒有記。攻擊者用外洩的帳密試了一整晚都沒人發現。主要是哪一類的問題？

  • A01 存取控制失效，因為攻擊者存取了不屬於他的帳戶
  • A06 不安全的設計
  • A03 軟體供應鏈失效
  • A09 安全記錄與告警失效

A09 的描述直接舉了「只記成功登入、沒記失敗」這個例子。允許大量試登入本身則是 A07 的問題，兩者常常一起出現。

「設計時沒想到要限制每天的轉帳次數」跟「程式寫錯讓限制沒生效」，OWASP 怎麼區分？

  • 兩個都是 A05 注入
  • 兩個是同一件事
  • 前者是 A06，後者是實作缺陷
  • 前者是 A02，後者是 A06

A06 原文：An insecure design cannot be fixed by a perfect implementation as needed security controls were never created。

資料被當成指令

注入：SQL 注入與 PreparedStatement

注入（injection）的定義是：「不受信任的使用者輸入被送進直譯器（例如瀏覽器、資料庫、命令列），讓直譯器把部分輸入當成指令執行」。出處 直譯器（interpreter）就是讀一段文字並照著執行的程式。SQL 是最常見的例子：把輸入拼進 SQL 字串，資料庫分不出哪段是你寫的、哪段是使用者打的。

實際跑一次。帳戶表裡有 alice、bob、carol 三筆，兩個 API 都用帳戶名稱查詢，差別只在 SQL 怎麼組：

    // 錯誤示範：把使用者輸入直接拼進 SQL 字串
    @GetMapping("/unsafe/accounts")
    public List<String> unsafe(@RequestParam String owner) throws Exception {
        String sql = "select owner, balance from account where owner = '" + owner + "'";
        try (Connection c = dataSource.getConnection();
             Statement st = c.createStatement();
             ResultSet rs = st.executeQuery(sql)) {
            return rows(rs);
        }
    }

    // 正確做法：SQL 結構先固定，使用者輸入只當成參數值
    @GetMapping("/safe/accounts")
    public List<String> safe(@RequestParam String owner) throws Exception {
        String sql = "select owner, balance from account where owner = ?";
        try (Connection c = dataSource.getConnection();
             PreparedStatement ps = c.prepareStatement(sql)) {
            ps.setString(1, owner);
            try (ResultSet rs = ps.executeQuery()) {
                return rows(rs);
            }
        }
    }

執行結果（Spring Boot 4.1.1、H2）：

$ curl -G 'http://127.0.0.1:18093/unsafe/accounts' --data-urlencode "owner=alice"
["alice=1200"]

$ curl -G 'http://127.0.0.1:18093/unsafe/accounts' --data-urlencode "owner=alice' OR '1'='1"
["alice=1200","bob=98000","carol=560"]

$ curl -G 'http://127.0.0.1:18093/safe/accounts' --data-urlencode "owner=alice"
["alice=1200"]

$ curl -G 'http://127.0.0.1:18093/safe/accounts' --data-urlencode "owner=alice' OR '1'='1"
[]

OWASP 的 SQL 注入防範速查表把預備語句（prepared statement，又叫參數化查詢）列為主要防禦的第一項：它「強迫開發者先寫好全部的 SQL，之後才一個一個傳入參數」，所以「不管使用者輸入什麼，資料庫都分得出程式碼跟資料」，「就算攻擊者塞進 SQL 指令，也改變不了查詢的意圖」。同一份清單把「跳脫所有使用者輸入」標成強烈不建議（STRONGLY DISCOURAGED）。出處 Spring 的 JdbcTemplate 用 ?、JPA 用 :name 綁參數，背後都是同一件事；〈Spring 資料存取〉的命名參數也是。

兩個常見的漏洞位置：表名、欄位名不能用參數，A05 寫「SQL 的結構，例如表名、欄位名，不能被跳脫，所以使用者提供的結構名稱很危險」，排序欄位這類需求要用允許清單對照（只接受事先列好的幾個值）；用了 ORM 也可能出事，在 JPQL 裡自己拼字串一樣會被注入。出處

用拼字串的 /unsafe/accounts，輸入 alice' OR '1'='1，實跑回傳幾個帳戶？

  • 3 個
  • 0 個
  • 1 個
  • 資料庫報錯

單引號提早結束字串，OR '1'='1' 永遠成立，where 條件等於沒寫，三個帳戶全部回傳。

同樣的輸入送給 PreparedStatement 版本的 /safe/accounts，結果是？

  • 空的，沒有帳戶叫這一整串
  • 3 個帳戶，因為單引號在參數裡一樣會結束字串
  • 只有 alice
  • 資料庫報語法錯誤

整段輸入只是 owner 要比對的值，SQL 結構早就固定了。實跑回傳 []。

為什麼 PreparedStatement 擋得住 SQL 注入？

  • 因為它會自動刪掉單引號
  • 結構先固定，輸入只當成值
  • 因為它會加密使用者輸入
  • 因為它只允許英文字母

OWASP：the database will always distinguish between code and data, regardless of what user input is supplied。它沒有刪字元，也沒有加密。

OWASP 的 SQL 注入速查表對「自己把使用者輸入跳脫一遍」的評價是？

  • 強烈不建議
  • 首選，比參數化查詢快
  • 跟參數化查詢一樣好
  • 只要用在 MySQL 就安全

速查表原文標成 STRONGLY DISCOURAGED: Escaping All User Supplied Input。跳脫規則複雜、容易漏，參數化才是正解。

報表 API 讓使用者用網址參數選排序欄位：order by ? 綁參數能解決注入嗎？

  • 能，參數化萬用
  • 能，只要用 JPA
  • 不能，所以只好自己跳脫
  • 不能，要用允許清單

A05：table names, column names, and so on cannot be escaped。參數只能放「值」，結構名稱要比對允許清單後才拼進去。

下面哪個也屬於注入？

  • 使用者猜到別人的帳戶編號
  • 把輸入拼進作業系統指令
  • 密碼用 MD5 存
  • 伺服器時間不準

A05 列的常見注入包含 SQL、NoSQL、作業系統指令（OS command）、LDAP 等，概念都是「輸入被直譯器當指令」。

用 Spring 的 JdbcTemplate 寫 jdbc.queryForList("select * from account where owner = ?", owner)，對注入來說是？

  • 危險，內部也是拼字串
  • 危險，要先把 owner 轉成大寫
  • 只有 owner 是數字時才安全
  • 安全，問號會綁成參數

問號是參數佔位，JdbcTemplate 底下用的就是 PreparedStatement，owner 只當成值傳入。

用了 JPA，就一定不會有 SQL 注入嗎？

  • 是，JPA 會自動處理
  • 是，因為 JPA 不用 SQL
  • 不是，自己拼字串一樣會
  • 只有 Hibernate 6 以後才不會

A05 也列了 ORM 注入。JPA 的參數綁定（:name 或 ?1）才安全，自己用加號拼字串就跟 Statement 一樣危險。

資料被瀏覽器當成程式

XSS：輸出編碼

跨網站指令碼（Cross-Site Scripting，XSS）是注入的另一種：直譯器換成瀏覽器。使用者輸入被原樣放進 HTML，裡面的 <script> 就會在別人的瀏覽器裡執行，能讀走頁面上的資料、冒用登入狀態送請求。範例：

    // 錯誤示範：把輸入原樣放進 HTML
    @GetMapping(value = "/unsafe/greet", produces = MediaType.TEXT_HTML_VALUE)
    public String unsafe(@RequestParam String name) {
        return "<p>您好，" + name + "</p>";
    }

    // 正確做法：放進 HTML 之前先做 HTML 輸出編碼
    @GetMapping(value = "/safe/greet", produces = MediaType.TEXT_HTML_VALUE)
    public String safe(@RequestParam String name) {
        return "<p>您好，" + HtmlUtils.htmlEscape(name) + "</p>";
    }
$ curl -G 'http://127.0.0.1:18093/unsafe/greet' --data-urlencode "name=小明"
<p>您好，小明</p>

$ curl -G 'http://127.0.0.1:18093/unsafe/greet' --data-urlencode "name=<script>alert('XSS')</script>"
<p>您好，<script>alert('XSS')</script></p>

$ curl -G 'http://127.0.0.1:18093/safe/greet' --data-urlencode "name=<script>alert('XSS')</script>"
<p>您好，&lt;script&gt;alert(&#39;XSS&#39;)&lt;/script&gt;</p>

只看文字不夠，用真的瀏覽器（Playwright 開的 Chromium）打開兩個網址，輸入改成 <script>document.title='XSS 執行了'</script>，看指令碼有沒有跑：

預設設定 /unsafe/greet：document.title = 'XSS 執行了'
預設設定 /safe/greet：document.title = ''

沒編碼的版本，攻擊者的程式真的執行了；編碼後，< 變成 &lt;，瀏覽器只當成文字顯示。OWASP 的 XSS 防範速查表：「要把資料照使用者輸入的樣子安全顯示時，建議用輸出編碼」，變數「不應被當成程式碼，而是文字」；而且先用框架內建的自動編碼，現代框架「靠樣板與自動跳脫」讓 XSS 少很多。出處

框架內建的預設：

  • Thymeleaf：教學說 th:text 把標籤跳脫掉「是 th:text 屬性的預設行為」，不要跳脫才改用 th:utext（unescaped text）。Thymeleaf 教學：This is the default behaviour of the th:text attribute.出處
  • Angular：安全指南說它「預設把所有值都當成不受信任」，透過樣板綁定或插值放進頁面時「會淨化並跳脫不受信任的值」。Angular 安全指南：Angular sanitizes and escapes untrusted values出處

但框架都留了跳脫出口，例如 Angular 的 bypassSecurityTrust… 系列、Thymeleaf 的 th:utext、直接設定 innerHTML，用了就等於關掉這層保護；XSS 速查表也提醒，「熱門框架像 React 與 Angular 仍然有安全缺口」（security gaps still exist in popular frameworks like React and Angular）。出處

要注意編碼要對位置：放進 HTML 內文、HTML 屬性、JavaScript、網址，各有不同的編碼規則，速查表也提醒「輸出編碼不是萬能的」，像直接放進 <script> 裡、CSS 裡這些「危險的位置」，編碼也救不了，根本不該放使用者資料。出處

把 <script>alert('XSS')</script> 經過 HtmlUtils.htmlEscape 後放進頁面，瀏覽器會怎樣？

  • 跳出 alert 視窗
  • 把整段當成文字顯示出來，不會執行
  • 什麼都不顯示
  • 頁面報錯打不開

角括號被換成 &lt; &gt;，瀏覽器看到的是文字不是標籤。實跑時 document.title 沒被改。

XSS 跟 SQL 注入的共同點是？

  • 都只發生在資料庫
  • 都靠竊聽網路
  • 輸入被當成指令執行
  • 都可以用 HTTPS 完全擋下，因為加密之後攻擊者送不出惡意內容

兩者都是「資料被當成程式」。HTTPS 只保護傳輸過程，擋不了這兩種。

用 Thymeleaf 顯示使用者的暱稱，哪個寫法預設就做了 HTML 輸出編碼？

  • th:text
  • th:utext
  • 直接用字串相加組 HTML
  • 前端拿到後設定 innerHTML

th:text 會編碼；th:utext 的 u 就是不編碼（unescaped）；innerHTML 會把字串當 HTML 解析。先用框架的自動編碼，是速查表的第一建議。

OWASP 說輸出編碼「不是萬能的」，指的是什麼？

  • 有些位置編碼也擋不住
  • 編碼會讓網頁變慢
  • 編碼只對英文有效
  • 編碼會被 HTTPS 取消

速查表的 Dangerous Contexts 一節列了這些位置。不同位置要用不同的編碼規則，有些位置則完全不該放。

XSS 被打中時，攻擊者的程式碼在哪裡執行？

  • 攻擊者自己的電腦
  • 你的資料庫
  • 受害者的瀏覽器
  • 你的伺服器的作業系統

它跑在受害者打開的頁面裡，所以能讀頁面上的資料、用受害者的身分送請求。這也是為什麼權杖不建議放 localStorage（面試集〈認證與安全面試題：JWT、OAuth 2.0、OIDC 與密碼保存〉）。

要在頁面上安全顯示使用者打的留言（原樣顯示、不允許任何格式），第一選擇是？

  • 過濾掉 script 這個字
  • 用框架的自動輸出編碼
  • 只靠 CSP
  • 把留言轉成大寫

只刪 script 很容易被繞過（例如用 onerror 屬性）。輸出編碼讓所有內容都當文字；CSP 是第二道牆，不是主要防線。

伺服器被借去連它不該連的地方

SSRF：伺服器端請求偽造

SSRF（Server-Side Request Forgery）發生在「伺服器照使用者給的網址去發請求」的功能，例如用網址上傳頭像、設定 webhook 回呼網址。攻擊者把網址換成內網位址，伺服器就替他連到外面連不到的地方。OWASP 的 SSRF 速查表特別提到雲端：SSRF 常被用來「從中繼資料服務竊取憑證與存取權杖」（AWS、Azure、GCP 的中繼資料服務都是）。出處

速查表把情況分成兩種：應用程式「只會連到已識別、受信任的應用程式」，就用允許清單（allowlist），只放行事先登記的網域或位址；真的要能連到任意外部網址時，才退而求其次做更多檢查，例如解析後的 IP 不能是內網或本機位址，並在網路層限制伺服器能連出去的範圍。出處 這課不實作攻擊，速查表本身也說它「只從防守的角度寫，不解釋怎麼發動攻擊」。

下面哪個功能最可能有 SSRF 風險？

  • 顯示目前時間
  • 讓使用者貼一個圖片網址，伺服器去下載當頭像
  • 登出按鈕
  • 把金額格式化成千分位

SSRF 的前提是「伺服器照使用者給的網址發請求」。下載頭像正是這種功能。

雲端上的 SSRF 最常被拿來偷什麼？

  • 使用者的瀏覽器 Cookie
  • 網站的 CSS 檔
  • DNS 紀錄
  • 中繼資料服務裡的憑證

速查表：SSRF is often used to access and steal credentials and access tokens from metadata services。拿到憑證就能用伺服器的身分操作雲端資源。

webhook 只需要回呼三家合作廠商。最好的防 SSRF 做法是？

  • 允許清單：只放行這三家登記過的網域
  • 封鎖清單：列出所有內網位址與雲端中繼資料位址擋掉，其他一律放行
  • 不檢查，因為合作廠商可信任
  • 把網址轉成小寫再用

目標是已知、受信任的少數幾家時，速查表建議用允許清單。封鎖清單容易漏，例如換個寫法的內網位址。

SSRF 跟 CSRF 差在哪？

  • 沒差，是同一種攻擊的兩種寫法
  • SSRF 偷 Cookie，CSRF 偷密碼
  • 發請求的一方不同：伺服器對瀏覽器
  • SSRF 只發生在前端

兩個字只差一個字母，發請求的人不同：SSRF 是伺服器，CSRF 是受害者的瀏覽器。CSRF 見〈網站安全三題：CORS、CSRF、密碼學〉。

告訴瀏覽器，這個頁面能載入什麼

CSP：內容安全政策

CSP（Content Security Policy）是伺服器用回應標頭交給瀏覽器的一組規則。MDN：它「由網站給瀏覽器的一系列指示組成，指示瀏覽器限制網站程式碼能做的事」，主要用途是控制「文件可以載入哪些資源，特別是 JavaScript」，「主要用來防禦 XSS」。出處 一條政策由好幾個指令組成：

Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'
  • default-src 'self'：沒另外規定的資源，只能從自己的網域載入。
  • script-src 'self'：指令碼只能是自己網域的檔案；沒寫 'unsafe-inline'，頁面裡直接寫的 <script> 就不能執行。
  • object-src 'none'：不准用 object、embed 載入外掛。
  • frame-ancestors 'none'：不准別的網站用 iframe 把這頁嵌進去（下一段）。

把上面這條政策加到 Spring Security 的設定，再用同一個瀏覽器打開沒編碼的 /unsafe/greet：

    // strict：在預設之外，再加上 CSP 與 Referrer-Policy
    @Bean
    @Profile("strict")
    SecurityFilterChain strict(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(a -> a.anyRequest().permitAll())
            .headers(h -> h
                .contentSecurityPolicy(csp -> csp.policyDirectives(
                        "default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'none'"))
                .referrerPolicy(r -> r.policy(ReferrerPolicy.STRICT_ORIGIN_WHEN_CROSS_ORIGIN)));
        return http.build();
    }

加上CSP /safe/greet：document.title = ''

注入的指令碼還在頁面裡，但瀏覽器拒絕執行，主控台寫著違反了 script-src 'self'。這就是「第二道牆」。兩個提醒：MDN 說「設定 CSP 不能取代淨化輸入」，兩者要一起做；要允許少數自己的行內指令碼，MDN 建議用 nonce（每次回應產生的隨機值），不要開 'unsafe-inline'。上線前可以先用 Content-Security-Policy-Report-Only，「政策不會被強制執行，但違規會被回報」，確認不會擋到正常功能再正式啟用。出處

CSP 主要是用來防哪種攻擊？

  • SQL 注入
  • XSS
  • 暴力破解密碼
  • DDoS

MDN：mainly used as a defense against cross-site scripting (XSS)。它在瀏覽器端限制能載入、執行什麼，管不到資料庫。

政策是 script-src 'self'，頁面裡有一段被注入的行內 <script>。結果是？

  • 照常執行，因為它出現在自己網域的頁面裡，算是 'self'
  • 執行一半
  • 瀏覽器拒絕執行，並在主控台回報違反 CSP
  • 伺服器回 403

'self' 只允許自己網域的指令碼檔案，行內指令碼要另外用 'unsafe-inline'、nonce 或雜湊才允許。實跑主控台就是 violates the following Content Security Policy directive。

已經設了很嚴格的 CSP，還需要做輸出編碼嗎？

  • 不用，CSP 會擋下所有 XSS
  • 不用，兩個只能選一個
  • 只有舊瀏覽器才需要
  • 需要，CSP 只是第二道牆

OWASP XSS 速查表：Use a CSP as an additional layer of defense；MDN 也說設定 CSP 不能取代淨化輸入。政策很容易寫錯或被放寬。

網站要加 CSP，又怕擋到既有功能，第一步建議怎麼做？

  • 直接上線，壞了再說
  • 先用 Report-Only 版本，只回報不擋
  • 在政策裡加 'unsafe-inline' 與 *
  • 只在開發環境加

MDN：report-only 模式下政策不強制執行，違規會送到回報端點。調整到沒有誤擋，再換成正式的標頭。

頁面有少數幾段自己寫的行內指令碼要保留，比較安全的允許方式是？

  • script-src 'unsafe-inline'
  • script-src *
  • 把 CSP 拿掉
  • 每次回應產生 nonce

'unsafe-inline' 會連被注入的行內指令碼一起放行，等於白設。nonce 每次都不同，攻擊者猜不到。

CSP 的 frame-ancestors 'none'，效果類似哪個舊標頭？

  • X-Content-Type-Options: nosniff
  • X-Frame-Options: DENY
  • Referrer-Policy: no-referrer
  • Strict-Transport-Security: max-age=0

MDN：Setting this directive to 'none' is similar to X-Frame-Options: deny。兩個都是不准任何網站用 iframe 嵌入這一頁。

Google 首頁的回應實測帶的是 content-security-policy-report-only。這個標頭的效果是？

  • 強制執行政策，違規的資源一律擋下，比一般的 CSP 更嚴格
  • 只對舊瀏覽器有效
  • 不擋任何東西，只把違反政策的情況回報給指定的網址
  • 關閉瀏覽器的 CSP 功能

report-only 只回報、不強制，常用在調整新政策的期間。2026-10-03 實測 www.google.com 帶的就是這個版本。

幾行標頭，各管一件事

安全標頭清單

除了 CSP，還有幾個常用的安全標頭，各自擋一種問題。OWASP 的 HTTP 標頭速查表與 MDN 的說法：

標頭做什麼建議值
Strict-Transport-Security（HSTS）要瀏覽器以後只用 HTTPS 連這個網站，就算使用者打 http 也一樣max-age=63072000; includeSubDomains; preload
X-Content-Type-Options要瀏覽器照 Content-Type 走、不要自己猜檔案類型nosniff
Referrer-Policy控制跳到別的網站時，Referer 標頭要帶多少網址資訊strict-origin-when-cross-origin
CSP 的 frame-ancestors誰可以用 iframe 嵌入這頁，防點擊劫持'none' 或 'self'
X-Frame-Options舊版的嵌入限制，給不支援 frame-ancestors 的瀏覽器DENY
X-XSS-Protection舊瀏覽器的 XSS 過濾器，本身可能造成漏洞0（關掉）

表格根據：

  • HSTS：「指示瀏覽器只用 HTTPS 存取網站，即使使用者試著用 HTTP 連線」，速查表也警告設錯或憑證出問題時「合法使用者可能無法連上網站」出處；MDN 補充 HSTS 生效後，瀏覽器「不允許使用者略過安全連線的錯誤，例如無效的憑證」。出處
  • X-Content-Type-Options：用來阻擋瀏覽器的類型猜測（MIME sniffing），那「可能把不可執行的類型變成可執行的類型」。出處
  • Referrer-Policy：建議 strict-origin-when-cross-origin，MDN 說這個值「同源請求送完整網址，跨來源只送來源，從 HTTPS 到 HTTP 則不送」，也是沒指定時的預設。出處
  • frame-ancestors：「取代了」X-Frame-Options。OWASP 速查表：obsoletes X-Frame-Options for supporting browsers出處
  • X-XSS-Protection：警告是「在某些情況下，這個標頭會在原本安全的網站製造 XSS 漏洞」，建議值是 0。出處

點擊劫持（clickjacking）是把你的頁面透明地疊在惡意網站上，騙使用者點到看不見的按鈕；MDN 說 frame-ancestors 'none'「類似 X-Frame-Options: deny」。出處

OWASP HTTP 標頭速查表建議的 HSTS 值是？

  • max-age=0
  • max-age=60; includeSubDomains
  • max-age=63072000; includeSubDomains; preload
  • includeSubDomains; preload

63072000 秒是兩年；includeSubDomains 連子網域一起適用；preload 表示願意被列進瀏覽器內建的 HSTS 名單。max-age=0 反而是要瀏覽器取消 HSTS。

使用者在網址列打 http://bank.example，網站之前回過 HSTS。瀏覽器會怎麼做？

  • 先用 HTTP 連，等伺服器回 301 轉址到 HTTPS 再連一次
  • 直接改用 HTTPS 連，不送出 HTTP 請求
  • 拒絕連線

HSTS 讓瀏覽器記住這個網站只能用 HTTPS，之後的 HTTP 嘗試會自動升級成 HTTPS，中途被竊聽或竄改的機會就少了。

HSTS 生效後，網站的憑證過期了，使用者還能點「繼續前往」嗎？

  • 不能，瀏覽器不允許略過安全連線錯誤
  • 能，跟平常一樣
  • 能，但只能瀏覽、不能送出表單，因為 HSTS 只保護 POST 請求
  • 能，只要清掉 Cookie

MDN：the browser will not allow the user to bypass secure connection errors。所以速查表提醒設定前要確定憑證管理沒問題，否則合法使用者會連不上。

X-Content-Type-Options: nosniff 擋的是什麼？

  • Cookie 被 JavaScript 讀走，送到攻擊者的伺服器
  • 瀏覽器自己猜檔案類型
  • 網頁被嵌進 iframe
  • Referer 外洩

速查表：它阻擋 MIME 類型猜測，那可能把不可執行的類型變成可執行的。例如使用者上傳的「圖片」其實是 JavaScript。

要防止別的網站把你的轉帳頁用透明 iframe 疊起來騙點擊，現在建議用哪個？

  • X-Content-Type-Options: nosniff
  • Referrer-Policy: no-referrer
  • HSTS 加上 includeSubDomains
  • CSP 的 frame-ancestors

速查表：frame-ancestors 取代了 X-Frame-Options（支援的瀏覽器上）。'none' 等於不准任何人嵌入。

  • XSS 防護是最高等級

  • 只對 IE 開啟

程式之外，主機本身

伺服器加固與機密管理

A02 安全設定錯誤列的情況包括「啟用或安裝了不必要的功能，例如不必要的連接埠、服務、頁面、帳號」與「預設帳號與密碼仍然啟用、沒改過」，防法第一條是「一套可重複的加固流程」，而且開發、測試、正式環境「設定一致，各用不同的憑證」。出處 落到主機上，基本動作是這幾件：

  • SSH 用金鑰登入，關掉密碼登入。OpenSSH 的伺服器設定 PasswordAuthentication「指定是否允許密碼認證，預設是 yes」，要自己改成 no；PermitRootLogin 的預設是 prohibit-password，root 不能用密碼登入，能設成 no 就完全不准 root 直接登入。出處 用金鑰登入，就不會被大量試密碼的方式破解。
  • 防火牆只開必要的埠。A02 把「不必要的連接埠、服務」（unnecessary ports, services）列為安全設定錯誤的情況之一。出處 做法是預設全部擋，只放行服務需要的（例如 443），管理用的 SSH 只開給公司的網段。
  • 最小權限。應用程式用一般帳號跑、不用 root；資料庫帳號只給需要的權限（查詢服務不需要刪表權限）。A01 第一條就是違反最小權限原則。出處
  • 照現成的基準做。CIS Benchmarks 是「針對 25 個以上產品家族的規範性設定建議」，代表「全球資安專家的共識」，作業系統、雲端、資料庫都有，不用自己從零想加固項目。出處

機密管理。API 金鑰、資料庫密碼、SSH 私鑰這類「機密」（secret），OWASP 機密管理速查表說很多組織「把它們以明文寫死在原始碼裡，散落在設定檔與組態管理工具中」。它對機密的要求：只存在必要的時間（經常輪替，最好能自動輪替）、只給需要的人看（最小權限）、可以撤銷、絕不寫進日誌。出處 實務上就是不進程式碼、不進 git、不進映像檔，正式環境從集中式的機密管理服務取得；環境變數與 Vault 這類服務怎麼取捨，在面試集〈認證與安全面試題：JWT、OAuth 2.0、OIDC 與密碼保存〉。

OpenSSH 伺服器沒改設定時，PasswordAuthentication 是什麼？

  • no，新版 OpenSSH 預設只能用金鑰登入
  • yes，要自己改成 no
  • 沒有這個設定
  • 只允許 root 用密碼

sshd_config 手冊：The default is yes。要只用金鑰登入，得自己改成 no。

一台只提供 HTTPS 網站的主機，防火牆對外最少要開哪個埠？

  • 全部開，由應用程式自己擋
  • 22、80、443、3306 都開
  • 443；SSH 只開給管理用的網段
  • 3306，讓資料庫能被連

預設拒絕、只開必要的。資料庫的 3306 不該對外；SSH 也不該對全世界開放。

開發者把資料庫密碼寫在 application.yaml 一起推上 git。這違反了機密管理的哪個原則？

  • 機密不該以明文進程式碼
  • 密碼長度太短
  • YAML 格式不支援密碼
  • 沒有違反，只要 git 儲存庫設成私有，看得到的都是自己人

OWASP 點名的反面教材就是 hardcoded within the source code in plaintext。git 歷史一旦有過，刪掉檔案也還在，只能換掉那組密碼。

OWASP 對機密的生命週期要求，下面哪一項不在其中？

  • 經常輪替，最好能自動輪替
  • 只給需要的人看
  • 可以撤銷
  • 寫進日誌方便事後追查

速查表明列 Never be logged：機密絕不能寫進日誌，要遮蔽或加密。

重點整理

  • OWASP Top 10:2025：A01 存取控制失效、A02 安全設定錯誤、A03 軟體供應鏈失效、A04 密碼學失效、A05 注入、A06 不安全的設計、A07 認證失效、A08 軟體或資料完整性失效、A09 安全記錄與告警失效、A10 例外狀況處理不當；SSRF 併入 A01。
  • 注入是資料被直譯器當成指令：SQL 用 PreparedStatement（或框架的參數綁定），表名、欄位名用允許清單；跳脫輸入是強烈不建議的做法。
  • XSS 是使用者輸入被瀏覽器當成程式：先用框架的自動輸出編碼，注意編碼要對位置；CSP 是第二道牆，不能取代輸出編碼。
  • SSRF 是伺服器被借去連內網或雲端中繼資料：目標已知就用允許清單。
  • 安全標頭：CSP（限制能載入、執行什麼）、HSTS（只用 HTTPS）、X-Content-Type-Options: nosniff、Referrer-Policy: strict-origin-when-cross-origin、frame-ancestors（取代 X-Frame-Options）、X-XSS-Protection: 0。Spring Security 預設送後面幾個，HSTS 只在 HTTPS，CSP 要自己加。
  • 伺服器：SSH 用金鑰、關密碼登入，防火牆只開必要的埠，最小權限，照 CIS Benchmarks 加固；機密不進程式碼、git、映像檔，輪替、限權、可撤銷、不寫日誌。
