檔案在哪裡，決定指令做什麼

三個區域：工作目錄、暫存區、儲存庫

Git 是版本控制系統（追蹤程式碼每一次修改的工具；它跟 GitHub 的差別見〈Java 基礎快答〉）。Pro Git 說，要把 Git 學順，最重要的一件事是：檔案有三種狀態，已修改（modified）、已暫存（staged）、已提交（committed），對應到一個 Git 專案的三個區域：「工作目錄、暫存區、Git 目錄」（the working tree, the staging area, and the Git directory）。基本流程是：在工作目錄改檔案；只把想放進下一個 commit 的修改加到暫存區；commit 時「把暫存區裡的檔案原樣拿出來，存成一張永久的快照」（takes the files as they are in the staging area and stores that snapshot permanently to your Git directory）。出處

用寄包裹比喻：工作目錄是你的桌子，東西隨便擺；暫存區是打包中的紙箱，git add 是把東西放進箱子；git commit 是封箱、貼上單號寄出，寄出去的箱子就固定不變了。下面的 Git 目錄這課叫儲存庫（repository，就是專案裡那個 .git 資料夾）。

git add 放進暫存區，git commit 存暫存區；git diff 看還沒 add 的，git diff --staged 看要 commit 的

新建一個檔案 a.txt，還沒做任何 Git 指令。git status 會把它列在哪一段？

  • Changes to be committed
  • Changes not staged for commit
  • Untracked files
  • 不會出現，Git 看不到新檔案

Git 還沒追蹤過的新檔案列在 Untracked files，要 git add 之後才會進暫存區、出現在 Changes to be committed。

git status --short 顯示  M fee.txt（M 在右邊那欄）。意思是？

  • fee.txt 改了，但還沒 git add
  • fee.txt 已經放進暫存區，等著 commit
  • fee.txt 是 Git 還沒追蹤的新檔案
  • fee.txt 合併時發生了衝突

右欄比的是工作目錄對暫存區。M 在右表示工作目錄改了、暫存區還是舊的；add 之後 M 會換到左欄。

剛對 fee.txt 做完 git add，接著執行不加參數的 git diff，會看到什麼？

  • 這次修改的完整差異
  • 什麼都沒有
  • 整個檔案從頭到尾的內容
  • 錯誤訊息，要先 commit 才能看

不加參數的 git diff 比工作目錄與暫存區；add 之後兩邊相同，所以是空的。要看暫存區對最新 commit 的差異，用 git diff --staged。

想在 commit 之前，確認「這次到底要存進去哪些修改」，該用哪個指令？

  • git diff
  • git log --oneline
  • git branch -vv
  • git diff --staged

commit 存的是暫存區，所以要看暫存區跟最新 commit 差在哪：git diff --staged。git log 只列出已經存好的 commit。

a.txt 改成 v2 後 git add，接著又改成 v3，沒有再 add 就 git commit。這個 commit 裡的 a.txt 是？

  • v3，commit 會存工作目錄的最新內容
  • v2，add 當下的內容
  • v1，兩次修改互相抵消
  • commit 失敗，要求先處理 v3

commit 拿的是暫存區的內容。v3 還留在工作目錄，git status 會顯示檔案已修改；要放進去就再 add 一次。

改了三個檔案，但這次只想 commit 其中一個。正確做法是？

  • 先把另外兩個刪掉再 commit
  • 直接 git commit，Git 會問你要哪個
  • 只 git add 那一個檔案，再 git commit
  • 開三個分支各 commit 一個

暫存區就是用來挑「這次要存哪些」的：只 add 想要的，其他的留在工作目錄，下次再處理。

每個 commit 都記得自己從哪裡來

commit 是什麼：快照、雜湊值、父節點

很多版本控制系統存的是「每次改了哪幾行」，Git 不是。Pro Git 說 Git 存的是「一連串快照」（a series of snapshots）：每次 commit，Git 存一個 commit 物件，裡面有「指向這次暫存內容快照的指標」、作者名字與 email、訊息，以及指向前一個（或前幾個）commit 的指標，也就是父節點（parent）：「第一個 commit 沒有父節點，一般的 commit 有一個，合併產生的 commit 有兩個以上」（zero parents for the initial commit, one parent for a normal commit, and multiple parents for a commit that results from a merge）。出處

每個 commit 的名字是一個雜湊值（hash，由內容算出來的一串編號）。Pro Git 寫 Git 用的是 SHA-1，「一個 40 個十六進位字元組成的字串，依檔案或目錄結構的內容算出來」（a 40-character string composed of hexadecimal characters (0–9 and a–f) and calculated based on the contents），所以「不可能改了任何檔案或目錄的內容而 Git 不知道」。出處 git log --oneline 印的 ae9db02 就是雜湊值的前幾碼。直接把 commit 物件打開來看：

$ git rev-parse HEAD
ae9db020e322d1e9efc80c0dfa0c90f6086763ea

$ git cat-file -t HEAD
commit

$ git cat-file -p HEAD
tree 3ac7ada85045e14fa21480938566b118bba9f777
parent 08f39321626199f784ea9b311f603e619dc8ecfc
author Tim <tim@example.com> 1759370520 +0800
committer Tim <tim@example.com> 1759370520 +0800

新增跨行手續費

$ git cat-file -p HEAD~1
tree 8b1a686c8fbb8ae2a7b989520ccbf622c1a2efeb
author Tim <tim@example.com> 1759370460 +0800
committer Tim <tim@example.com> 1759370460 +0800

新增手續費設定

tree 指向這次的快照，parent 指向上一個 commit；第一個 commit（HEAD~1，HEAD 往前一代）沒有 parent 那一行。父節點的雜湊值也是內容的一部分，所以改了任何一個舊 commit，它之後每個 commit 的雜湊值都會跟著變——這是後面講 rebase 時最重要的一點。

commit＝快照＋作者與訊息＋父節點；名字是內容算出來的雜湊值，內容一變，雜湊值就變

Pro Git 說 Git 存資料的方式是？

  • 每次 commit 存一張快照，加上父節點
  • 每次只存這次改動的那幾行差異
  • 每天自動備份一次整個專案資料夾
  • 只存最新版本，舊版本會自動刪除

Git 存的是一連串快照，每個 commit 物件指向它的快照與父節點，不是存差異。

一個「把兩個分支合併起來」產生的 commit，有幾個父節點？

  • 0 個
  • 1 個
  • 2 個（或更多）
  • 看合併了幾個檔案

第一個 commit 沒有父節點、一般 commit 一個、合併 commit 兩個以上。上面三方合併的實跑輸出裡，git cat-file 會看到兩行 parent。

把某個 commit 的訊息改一個字（內容不變），它的雜湊值會怎樣？

  • 不變，雜湊值只看檔案內容
  • 只有最後一碼會變，前面不變
  • 整串變成另一個雜湊值
  • Git 不允許改 commit 的訊息

commit 物件包含 tree、parent、作者、時間與訊息，任何一項改了，算出來的雜湊值就不同。實測改訊息後雜湊值整串都變了。

git cat-file -p HEAD~1 印出的內容裡沒有 parent 那一行。代表什麼？

  • 那個 commit 壞掉了
  • 那個 commit 是合併 commit
  • 那是儲存庫的第一個 commit
  • parent 被刪除了

第一個 commit 前面沒有東西，所以沒有父節點。上面實跑的 HEAD~1 就是「新增手續費設定」那個第一個 commit。

HEAD~1 指的是？

  • 目前 commit 的父節點
  • 下一個 commit（往後一代）
  • 儲存庫的第一個 commit
  • 遠端分支上最新的 commit

~1 是往前一代，~2 是往前兩代，沿著父節點往回走。

分支不是複製一份，是多貼一張標籤

分支其實是指向 commit 的標籤，HEAD 指向目前的分支

Pro Git：「Git 的分支只是一個輕量、可以移動的指標，指向某一個 commit」（A branch in Git is simply a lightweight movable pointer to one of these commits），每次 commit，目前分支的指標「自動往前移」。出處 分支實際上就是一個檔案，裡面寫著它指向的那個 commit 的 40 碼雜湊值，所以「建立新分支就像寫 41 個位元組到一個檔案（40 個字元加一個換行）那麼快」（Creating a new branch is as quick and simple as writing 41 bytes to a file (40 characters and a newline).）。出處

那 Git 怎麼知道你現在在哪個分支？靠一個特別的指標 HEAD：「指向你目前所在的本機分支」（this is a pointer to the local branch you’re currently on），而且「git branch 只建立新分支，不會切換過去」。出處 切換分支用 git switch，文件寫它會「切換到指定的分支，工作目錄與暫存區會更新成跟那個分支一致」（Switch to a specified branch. The working tree and the index are updated to match the branch.）；git switch -c 新分支 是建立並切換。出處（Pro Git 的例子用比較舊的 git checkout，切換分支的效果相同。）

$ git branch limit

$ git log --oneline --decorate --all
ae9db02 (HEAD -> main, limit) 新增跨行手續費
08f3932 新增手續費設定

$ cat .git/HEAD
ref: refs/heads/main

$ git switch limit
Switched to branch 'limit'

$ cat .git/HEAD
ref: refs/heads/limit

$ echo "單筆上限 50000 元" > limit.txt

$ git add limit.txt

$ git commit -m "新增單筆上限"
[limit 99eabc9] 新增單筆上限
 1 file changed, 1 insertion(+)
 create mode 100644 limit.txt

$ git log --oneline --decorate --all
99eabc9 (HEAD -> limit) 新增單筆上限
ae9db02 (main) 新增跨行手續費
08f3932 新增手續費設定

$ cat .git/refs/heads/limit
99eabc9937647249d346a14b9c6e12e3dfaf1fdd

對照圖看輸出：(HEAD -> main, limit) 表示 main 和 limit 兩個標籤都在 ae9db02，HEAD 指著 main；.git/HEAD 檔案的內容就是 ref: refs/heads/main。切到 limit 再 commit，只有 limit 往前移到 99eabc9，main 留在原地；.git/refs/heads/limit 裡就只是那串雜湊值。

分支＝指向 commit 的標籤；HEAD 指向目前的分支；commit 時只有 HEAD 指著的那個分支往前移

在 main 上執行 git branch feature，接著馬上 git commit。新的 commit 會讓哪個分支往前移？

  • feature
  • 兩個都移
  • 都不移，要先 push
  • main

git branch 只建立標籤、不切換，HEAD 還指著 main，所以 commit 時是 main 往前，feature 留在原處。要切過去用 git switch feature 或一開始就 git switch -c feature。

執行 git switch -c feature 之後，.git/HEAD 檔案的內容最可能是？

  • feature 分支最新 commit 的雜湊值
  • ref: refs/heads/feature
  • ref: refs/heads/main
  • 空的

HEAD 指向目前所在的分支，檔案裡寫的是分支的名字；分支檔案裡才是雜湊值。實跑 switch limit 之後就是 ref: refs/heads/limit。

建立一個新分支，Git 實際上做了什麼？

  • 寫一個小檔案，記下 commit 的雜湊值
  • 把整個專案複製一份到另一個資料夾
  • 把目前分支上的所有 commit 複製一份
  • 在遠端建立一份完整的副本

分支就是一個 41 位元組的檔案（40 碼雜湊值加換行），所以建立和刪除都很快，不像舊的版本控制工具要複製整個專案。

git log --oneline --decorate --all 印出 99eabc9 (HEAD -> limit) 新增單筆上限 與 ae9db02 (main) 新增跨行手續費。現在 commit 一次，哪個標籤會移動？

  • main 移到新的 commit
  • main 和 limit 都移
  • HEAD 移到 main
  • limit 移到新的 commit

HEAD -> limit 表示目前在 limit，commit 時 limit 往前移到新 commit，main 不動。

在 main 上，下面哪個指令會「建立 report 分支並切過去」？

  • git branch report
  • git switch report（report 還不存在）
  • git switch -c report
  • git commit -b report

git branch 只建不切；不存在的分支不能直接 switch 過去；-c 是建立並切換。git commit 沒有 -b 這個用法。

用 git branch -D tryout 刪掉一個分支之後，那個分支上的 commit 會怎樣？

  • 立刻從硬碟上消失，再也找不到
  • 自動合併進 main 分支保存
  • commit 還在，只是沒有標籤指著
  • 被自動推到遠端保存一份

刪分支只是撕掉標籤。實測刪掉之後 git cat-file 還找得到那個 commit；後面「救回」一段會用 reflog 把它接回來。

從 main 切到 limit 分支時，工作目錄裡的檔案會怎樣？

  • 不變，switch 只改 HEAD
  • 更新成 limit 指向的 commit 的內容
  • 全部清空，要重新 git pull
  • 變成兩個分支內容合併後的樣子

git switch 的文件寫：工作目錄與暫存區會更新成跟那個分支一致。所以切到 limit 才看得到 limit.txt，切回 main（合併前）它就不見了。

merge：快轉合併、三方合併，與衝突怎麼解

快轉合併

如果要合併進來的分支就在目前分支的正前方，中間沒有岔開，Git 只要把標籤往前移，Pro Git 叫它快轉（fast-forward）：「沒有分岔的工作需要合併，Git 只是把指標往前移」（Git simplifies things by moving the pointer forward because there is no divergent work to merge together）。出處

$ git switch main

$ git merge limit

Fast-forward

08f3932 新增手續費設定

$ git branch -d limit
Deleted branch limit (was 99eabc9).

衝突：兩邊改了同一個地方

Pro Git：如果兩個分支「用不同方式改了同一個檔案的同一部分」，Git 沒辦法自動合併，就會發生合併衝突（merge conflict）；這時 Git「還沒有自動建立合併 commit，而是暫停整個流程，等你解決衝突」。出處 例子：rate 分支把轉帳手續費調成 12 元，main 同時調成 8 元：

$ git commit -q -m "轉帳手續費調成 12 元"

  (use "git add <file>..." to mark resolution)
	both modified:   fee.txt

正前方就快轉；岔開了就三方合併、多一個雙父節點的 commit；同一處被改兩次才衝突：改好檔案、刪標記、add、commit

main 在 commit A，feature 從 A 開始又 commit 了 B、C，main 沒有新的 commit。在 main 上 git merge feature，結果是？

  • 產生一個新的合併 commit 接起兩邊
  • main 直接移到 C，不產生新 commit
  • 發生衝突，要手動解決才能合併
  • feature 被移回 A，跟 main 對齊

C 就在 main 的正前方，沒有分岔，只要把 main 標籤往前移。實跑 merge limit 時印的就是 Fast-forward。

接上題，快轉合併之後 git log --oneline --decorate 最上面那行最可能是？

  • C (HEAD -> main, feature) …
  • M (HEAD -> main) Merge branch 'feature'
  • A (HEAD -> main) …

快轉之後 main 和 feature 指向同一個 commit，HEAD 還在 main。實跑輸出是 99eabc9 (HEAD -> main, limit)。

main 和 report 都從 commit X 之後各自 commit 過一次，兩邊改的是不同檔案。在 main 上 git merge report，結果是？

  • 快轉，main 直接移到 report
  • 衝突，因為兩邊都有新 commit
  • 三方合併，產生合併 commit
  • Git 拒絕合併，要先 rebase

歷史岔開了，不能只移標籤；兩邊改不同檔案，Git 能自動合好，產生合併 commit。實跑印的是 Merge made by the 'ort' strategy.

三方合併的「三方」是哪三個快照？

  • 工作目錄、暫存區、儲存庫這三個區域
  • 本機、遠端、備份三份儲存庫
  • 兩個分支的頂端，加上共同祖先
  • 目前分支最近的三個 commit

Pro Git 寫三方合併用兩個分支頂端指向的快照和兩者的共同祖先。三個區域是另一件事。

  • 一定衝突，因為改了同一個檔案
  • 自動合併成功，兩處修改都保留
  • 只保留目前分支的修改
  • Git 要求你先刪掉其中一個分支

衝突的條件是改到同一部分，不是同一個檔案。實測一邊改第一行、一邊改第五行，自動合併後兩行都是新的。

  • 再執行一次 git merge rate
  • git add 這個檔案，再 git commit
  • git switch rate 切過去看

把檔案加到暫存區就是告訴 Git 這個衝突解決了；全部解完再 commit，合併 commit 才會產生。

  • git merge --abort
  • git commit
  • git push --force
  • git branch -D main

git status 的提示就寫著 use "git merge --abort" to abort the merge，會回到合併前的狀態。實測 abort 後檔案是合併前的內容。

衝突的兩邊分別是「手續費 8 元」和「手續費 12 元」。最負責的處理方式是？

  • 先問清楚正確的值再改
  • 永遠保留自己目前分支的那一邊
  • 永遠保留要合併進來的那一邊
  • 兩行都留著，讓程式執行時自己選

Git 只知道兩邊衝突，不知道哪個對。手續費這種業務規則要跟需求方或改另一邊的同事確認；兩行都留下會讓檔案內容錯誤。

把自己的 commit 搬到最新的起點上

rebase 對 merge：改寫歷史，以及黃金守則

合併岔開的歷史還有另一種方法：rebase（重定基底：把一串 commit 改接到另一個起點後面）。它把目前分支上的修改，一個一個在新的起點上重做一遍。Pro Git 說最後的內容跟 merge 一樣，「但 rebase 讓歷史比較乾淨」，看起來像一條直線，好像所有工作都是依序做的。出處

對照輸出：rebase 前，audit 的兩個 commit 是 595e91b、07f2d33；rebase 後變成 416ce71、3191e26。內容一樣，但父節點換了，雜湊值就全部不同（commit 一段講過的那一點）。之後在 main 上合併 audit，因為 audit 已經在 main 正前方，是快轉。

這就是 rebase 的代價：它不是搬動，是丟掉舊的 commit、做出新的。Pro Git 的黃金守則只有一句：「不要 rebase 已經存在於你的儲存庫之外、別人可能已經以它為基礎在工作的 commit」（Do not rebase commits that exist outside your repository and that people may have based work on.），因為「rebase 時你是在丟棄既有的 commit、建立相似但不同的新 commit」。出處 實務上的分界：還沒 push 的、只有自己在用的分支，可以 rebase 整理；已經推到共用分支、同事可能已經拉下來的，用 merge。

feature 分支有兩個 commit，雜湊值是 595e 開頭與 07f2 開頭。執行 git rebase main 之後，這兩個 commit 的雜湊值會？

  • 不變，rebase 只移動標籤
  • 變成新的雜湊值，因為父節點換了
  • 只有第一個會變
  • 變成跟 main 最新的 commit 一樣

rebase 是在新起點上重做 commit，父節點不同，雜湊值就不同。實跑 595e91b、07f2d33 變成 416ce71、3191e26。

audit 分支 rebase 到 main 之後，在 main 上 git merge audit，會是哪一種合併？

  • 三方合併
  • 一定衝突
  • 不能合併，要先 push
  • 快轉

rebase 之後 audit 的 commit 接在 main 最新的 commit 後面，main 只要往前移。實跑印的是 Fast-forward。

Pro Git 的 rebase 黃金守則是？

  • 每次 push 之前都要先 rebase 一次
  • 只能 rebase main，不能 rebase 其他分支
  • 別人可能拿到的 commit 不要 rebase
  • rebase 之後一定要刪掉舊的分支

rebase 丟棄舊 commit、建立新 commit；別人手上還有舊的，兩邊歷史就對不起來了。

下面哪個情況最適合用 rebase？

  • main 已經推到公司遠端，同事都拉過了
  • 同事正在你推上去的 feature 上接著開發
  • 自己本機、還沒推出去的分支
  • 已經合併進 main、上線的 commit

只有自己有、還沒推出去的 commit，改寫歷史不會影響別人。其他三個都已經在別人手上。

merge 和 rebase 合併出來的最終檔案內容（沒有衝突的情況下），差在哪？

  • rebase 合出來的內容比較新
  • merge 會遺失另一邊的一些修改
  • 內容一樣，只差在歷史的長相
  • rebase 會刪掉另一個分支的修改

Pro Git 寫兩種方式的最終快照相同，差別只在歷史怎麼記錄。

rebase 之後，舊的那兩個 commit（595e…、07f2…）會怎樣？

  • 被合併進新的 commit 裡
  • 還在儲存庫裡，只是沒有分支指著它們
  • 被推到遠端備份
  • 變成 main 的父節點

跟刪分支一樣，舊 commit 沒有標籤指著，但物件還在，reflog 也記得 rebase 之前的位置。

本機的 Git 跟伺服器上的 Git 怎麼同步

遠端：fetch、pull、push 與追蹤分支

遠端（remote）是放在別處的同一個儲存庫，例如公司的 GitLab 或 GitHub，慣例取名 origin。本機看得到的 origin/main 叫遠端追蹤分支（remote-tracking branch）。Pro Git：它們是「遠端分支狀態的參考，你不能自己移動，Git 會在每次跟遠端通訊時幫你移動」，可以想成「書籤，提醒你上次連線時遠端的分支在哪裡」（Think of them as bookmarks, to remind you where the branches in your remote repositories were the last time you connected to them.）。出處

  • git fetch：從遠端抓回你沒有的資料，更新 origin/main 這類書籤；Pro Git 說它「完全不會修改你的工作目錄」（it will not modify your working directory at all）。
  • git pull：「大多數情況下就是 git fetch 接著 git merge」（essentially a git fetch immediately followed by a git merge in most cases）。
  • 追蹤分支（tracking branch）：跟某個遠端分支有直接關係的本機分支，被它追蹤的那個叫上游分支（upstream branch）；在追蹤分支上 git pull，Git 就知道要從哪裡抓、合併哪個分支。出處 第一次 git push -u origin main 的 -u 就是設定這個關係。

  • git fetch 加 git merge

Pro Git 寫 pull 大多數情況是 fetch 之後立刻 merge。所以 pull 也可能產生合併 commit 或衝突。

origin/main 這個分支可以自己 commit 上去讓它往前移嗎？

  • 可以，跟一般分支一樣 commit 就好
  • 可以，但 commit 時要加 --force
  • 只有儲存庫的管理者可以

遠端追蹤分支是書籤，記錄上次連線時遠端在哪；要改遠端，是在本機分支 commit 再 push。

你 commit 完執行 git push，得到 ! [rejected] main -> main (fetch first)。最可能的原因是？

  • 網路斷線，連不到遠端
  • 遠端有你沒有的 commit
  • 遠端的 main 分支被刪掉了

提示寫著 the remote contains work that you do not have locally。先 pull 把別人的 commit 整合進來，再 push。

接上題，正確的下一步是？

  • 刪掉本機的 commit，重新寫一次
  • 換一個分支名稱推上去，不管 main

restore：還沒 commit 的修改

git restore 的文件寫它「用還原來源的內容，還原工作目錄裡指定的路徑」，加 --staged 則還原暫存區。出處 注意 git restore 檔案 會直接丟掉那個檔案還沒 commit 的修改，丟了就找不回來。

$ echo "打錯的一行" >> fee.txt

$ git status --short
 M fee.txt

$ git restore fee.txt

$ git status --short

$ echo "也打錯了" >> fee.txt

$ git add fee.txt

$ git status --short
M  fee.txt

$ git restore --staged fee.txt

$ git status --short
 M fee.txt

$ git restore fee.txt

$ git status --short

revert：已經推出去的錯 commit

git revert 的文件：它「記錄一些新的 commit，來抵銷先前某些 commit 的效果（通常只是一個出錯的）」（git revert is used to record some new commits to reverse the effect of some earlier commits (often only a faulty one).）。出處 歷史只往前加，同事手上的 commit 不會對不起來，所以已經推出去的錯誤用它。

$ printf "轉帳手續費 12 元\n跨行手續費 20 元\n臨櫃手續費 30 元\n外幣手續費 100 元\n" > fee.txt

$ git add fee.txt

$ git commit -q -m "跨行手續費調成 20 元"

$ git push -q

# 上線後發現跨行手續費不該調：已經推出去了，用 revert

$ git revert --no-edit HEAD

$ git log --oneline -3

5599170 跨行手續費調成 20 元
bc4046c Merge branch 'main' of ../origin

外幣手續費 100 元

$ git push -q

reset 與 reflog：還沒推出去的 commit

git reset --hard 把目前分支的標籤移回指定的 commit，文件寫它會「用那個 commit 的版本覆蓋所有檔案與目錄」，暫存區也會跟著更新。出處 Pro Git 特別提醒：--hard 是讓 reset 變危險的唯一方式，也是「Git 真的會毀掉資料的少數情況之一」，因為它強制覆蓋工作目錄。出處 實測 reset --hard 之前沒 commit 的修改就直接不見了。

被跳過的 commit 還能救，靠的是 reflog：Pro Git 說 Git 在背景記錄「過去幾個月裡 HEAD 和分支參考去過哪裡」（a log of where your HEAD and branch references have been for the last few months）出處；git reflog 的文件舉例，HEAD@{2} 表示「HEAD 兩次移動之前在哪」。出處 reflog 只存在你本機，記的是你自己做過的移動。

$ echo "草稿一" > draft.txt

$ git add draft.txt

$ git commit -q -m "草稿一"

$ echo "草稿二" >> draft.txt

$ git add draft.txt

$ git commit -q -m "草稿二"

$ git log --oneline -3
f0804cb 草稿二
067f509 草稿一
58c3d74 Revert "跨行手續費調成 20 元"

# 兩個草稿都還沒推，決定整個不要

$ git reset --hard HEAD~2
HEAD is now at 58c3d74 Revert "跨行手續費調成 20 元"

$ git log --oneline -2
58c3d74 Revert "跨行手續費調成 20 元"
5599170 跨行手續費調成 20 元

# 反悔了：reflog 找得到剛剛的位置

$ git reflog -3
58c3d74 HEAD@{0}: reset: moving to HEAD~2
f0804cb HEAD@{1}: commit: 草稿二
067f509 HEAD@{2}: commit: 草稿一

$ git reset --hard HEAD@{1}
HEAD is now at f0804cb 草稿二

$ git log --oneline -3
f0804cb 草稿二
067f509 草稿一
58c3d74 Revert "跨行手續費調成 20 元"

$ git switch -q -c tryout

$ echo "試驗功能" > tryout.txt

$ git add tryout.txt

$ git commit -q -m "試驗功能"

$ git switch -q main

$ git branch -D tryout
Deleted branch tryout (was c104f03).

$ git reflog -2
f0804cb HEAD@{0}: checkout: moving from tryout to main
c104f03 HEAD@{1}: commit: 試驗功能

$ git branch tryout HEAD@{1}

$ git log --oneline -1 tryout
c104f03 試驗功能

最後幾行示範刪錯分支的救法：git branch -D 只撕掉標籤，reflog 裡還看得到那個 commit（HEAD@{1}），用 git branch 名稱 HEAD@{1} 重新貼一張標籤就回來了。

沒 commit 用 restore；推出去了用 revert；沒推出去才用 reset；reset 或刪錯分支，先看 reflog

fee.txt 改壞了，還沒 add，想恢復成最新 commit 的樣子。用哪個指令？

  • git revert HEAD
  • git restore fee.txt
  • git reset --hard HEAD~1
  • git branch -D main

還沒 commit 的修改在工作目錄，git restore 把它還原。revert 是對已經存在的 commit 做反向 commit；reset HEAD~1 會連上一個 commit 都退掉。

不小心 git add 了一個檔案，想拿出暫存區、但保留修改。用哪個？

  • git restore fee.txt
  • git restore --staged fee.txt
  • git revert fee.txt
  • git reset --hard

--staged 只還原暫存區，修改還在工作目錄。實跑之後 git status --short 從 M（左）變回 M（右）。不加 --staged 會丟掉修改；reset --hard 更會連工作目錄一起覆蓋。

一個調錯手續費的 commit 已經推到共用的 main，同事也拉了。要撤銷它，該用？

  • git reset --hard HEAD~1 再 git push --force
  • git revert 那個 commit，再正常 push
  • 刪掉 main 重新建立
  • git restore fee.txt

revert 新增一個反向 commit，歷史只往前加，同事那邊不會對不起來。reset 加 force 會改寫共用歷史。

執行 git revert HEAD 之後，git log --oneline -2 最上面兩行會是？

  • 只剩原本 HEAD 的前一個 commit
  • 上面多一個 Revert commit
  • 原本的 HEAD 被改了訊息
  • 兩個 commit 都從 log 消失

revert 不刪 commit，而是多一個。實跑 58c3d74 Revert "跨行手續費調成 20 元" 在上、5599170 跨行手續費調成 20 元 在下。

兩個還沒推出去的草稿 commit，決定整個不要了。下面哪個指令最直接？

  • git revert HEAD 兩次
  • git restore --staged .
  • git fetch
  • git reset --hard HEAD~2

沒推出去、沒人拿到，改寫歷史不影響別人，reset 把標籤移回兩代前。revert 也行但會多留兩個反向 commit；restore 不處理已經 commit 的東西。

工作目錄有一段還沒 commit 的修改，這時執行 git reset --hard HEAD，那段修改會？

  • 自動存成一個新 commit
  • 移到暫存區
  • 直接被覆蓋掉，找不回來
  • 留在工作目錄不受影響

--hard 會用 commit 的版本覆蓋工作目錄。沒 commit 過的修改不在任何 commit 裡，reflog 也救不回來。這是 Pro Git 說 Git 會真的毀掉資料的少數情況。

剛用 git reset --hard HEAD~2 退掉兩個 commit，又後悔了。git reflog -3 顯示第二行是 f0804cb HEAD@{1}: commit: 草稿二。怎麼救？

  • 救不回來了，reset 已經刪掉 commit
  • git revert HEAD
  • git pull origin main
  • git reset --hard HEAD@{1}

HEAD@{1} 是 HEAD 上一次移動之前的位置，就是 reset 之前的草稿二。實跑之後 log 又看得到兩個草稿。

用 git branch -D tryout 刪錯分支了。reflog 裡看得到那個分支最後的 commit 是 c104f03。怎麼接回來？

  • git branch tryout c104f03
  • git revert c104f03
  • git restore tryout
  • 只能從遠端重新複製整個儲存庫

分支只是標籤，commit 還在；在那個 commit 上重新建一個同名分支就回來了。實跑用的是 git branch tryout HEAD@{1}。

關於 reflog，哪一句對？

  • 它只在本機，記錄 HEAD 與分支去過哪
  • 它記錄遠端上所有人的操作
  • push 時會跟著推到遠端
  • 它永久保存每次修改，包括沒 commit 的

reflog 記的是本機參考的移動。沒 commit 過的修改從來沒進過 commit，reflog 也沒有它。

分支策略、PR 流程與 code review

短命的分支：GitHub flow 與 trunk-based

Pro Git 把分支分成兩種用法：長期存在、代表不同穩定程度的長期分支，以及主題分支（topic branch）：「為單一功能或相關工作建立、用完就合併的短命分支」（a short-lived branch that you create and use for a single particular feature or related work）。出處 現在常見的兩種團隊做法都以短命分支為主：

  • GitHub flow：GitHub Docs 說它是「輕量、以分支為基礎的工作流程」（a lightweight, branch-based workflow）。步驟是：建分支（取簡短、看得懂的名字，例如 increase-test-timeout）、在分支上 commit 並 push、開 PR 請同事給意見、依審查意見繼續修、PR 被核准後合併、合併後刪掉分支。出處 文件也建議每個 commit 是「一個獨立、完整的修改」，不相關的修改各開一個分支，審查和日後 revert 都比較容易。
  • trunk-based development（主幹開發）：DORA 的說明是每個開發者把工作切成小批，「每天至少一次」合併進主幹（trunk，也就是 main），分支「通常不超過幾個小時」；DORA 整理的資料顯示，活躍分支在三個以內、每天至少合併一次的團隊，交付表現比較好。出處

PR 與 code review

PR（pull request）在 GitHub Docs 的定義是「把程式碼修改合併進專案的提議」（proposals to merge code changes into a project），讓團隊「在合併前討論與審查修改」；PR 頁面有對話、commit、檢查（自動化測試與建置）、修改的檔案幾個分頁。出處 GitHub flow 那頁說 PR 審查重要到「有些儲存庫要求一定要有核准的審查，PR 才能合併」，開 PR 時要寫清楚改了什麼、解決什麼問題。出處 公司內部用 GitLab 時叫 merge request，概念相同。

銀行職場：不能直接推 main

在銀行這類需要留下審核紀錄的職場，常見的設定是 main 分支不准直接推、一定要經過 PR 審核。GitHub 用保護分支（protected branch）做這件事：規則可以決定「協作者能不能刪除或強制推送這個分支」，並對推送設條件，例如通過狀態檢查；可開的設定包括「合併前要求 PR 審查」「合併前要求狀態檢查通過」「限制誰能推送」等，啟用審查要求後，PR 要拿到指定數量的核准才能合併進受保護的分支。出處 所以實際的一天大概是：

  1. git switch main、git pull，從最新的 main 出發。
  2. git switch -c fix-fee-rounding，在自己的分支上改、commit。
  3. git push -u origin fix-fee-rounding，在網頁上開 PR，寫清楚改了什麼、為什麼、怎麼測的。
  4. 自動化檢查跑完、同事審查並核准；有意見就在同一個分支繼續 commit、push，PR 會自動更新。
  5. 合併進 main，刪掉分支。上線出問題時，用 revert 撤銷那個合併，而不是改寫 main 的歷史。

面試講專題時，這段流程本身就是好素材：分支怎麼切、PR 怎麼審、衝突怎麼協調。怎麼把它講成一個有結構的故事，見〈行為面試與專題表達〉；〈軟體開發生命週期〉的實作階段說的「使用版本控制、程式碼審查與持續整合」，指的就是這一整套。

短命分支 → push → 開 PR → 自動檢查與審查 → 核准才合併 → 刪分支；main 受保護，出錯用 revert

照 GitHub flow，下面步驟的正確順序是？

  • 開 PR → 建分支 → commit → 合併 → 刪分支
  • 建分支 → push → 開 PR → 審查 → 合併 → 刪分支
  • 在 main 上 commit → push → 開 PR → 合併
  • 合併 → 開 PR → 審查 → 建分支 → push

GitHub Docs 的步驟就是建分支、改並推送、開 PR、處理審查意見、合併、刪分支。PR 是對分支提出的，所以一定要先有分支。

公司的 main 開了「合併前要求 PR 審查」與「限制誰能推送」，你在本機 main 上 commit 後直接 git push，最可能的結果是？

  • 成功，保護規則只是提醒，不會擋
  • 被拒絕，要推到自己的分支再開 PR
  • 自動幫你開好 PR 並直接合併
  • 本機的 commit 被遠端刪除

保護分支的用意就是讓修改一定經過 PR 與審查。正確做法是在分支上 commit、push 分支、開 PR。

DORA 對 trunk-based development 的描述，哪一句對？

  • 每個功能一個分支，做完（可能幾週）才合併
  • 小批、每天至少合併一次，分支只活幾小時
  • 完全不用分支，也不需要審查
  • 每個版本保留一條長期存在的分支

DORA 說主幹開發的分支通常不超過幾個小時、每天至少合併一次；好幾週才合併的是它拿來對比的長期功能分支。

開 PR 時，描述裡最該寫的是？

  • 只寫「修正 bug」三個字就好
  • 把所有修改的程式碼貼進描述
  • 改了什麼、解決什麼、怎麼測
  • 什麼都不寫，審查的人自己看 diff

GitHub flow 建議 PR 描述要寫改了什麼、解決什麼問題；diff 在「修改的檔案」分頁就看得到，不用重貼。寫上怎麼測的，審查者才能判斷風險。

PR 被審查者留了修改意見。接下來怎麼做？

  • 關掉這個 PR，重開一個新的
  • 在同一個分支繼續 commit、push
  • 直接推到 main，跳過審查
  • rebase 已經合併進 main 的 commit

GitHub flow 寫可以繼續在分支上 commit、push 回應審查，PR 會自動更新。

一個 PR 同時「重新命名變數」又「新增測試」，日後只想撤銷重新命名、保留測試。怎麼做事前準備最省事？

  • 全部放在同一個 commit，之後再手動改回
  • 兩件事分成兩個 commit
  • 乾脆不要寫測試，就不用拆
  • 每改一行程式就 commit 一次

GitHub Docs 舉的正是這個例子：每個 commit 是一個獨立、完整的修改，日後 revert 才能只撤銷其中一個。

合併進 main、已經上線的 PR 造成問題，要盡快撤銷。在受保護的 main 上，合理的做法是？

  • reset --hard 再 push --force 到 main
  • 刪掉 main 分支，從頭重建
  • 用 revert 產生反向 commit 走 PR
  • 在 main 上直接改程式碼，不留紀錄

main 受保護，通常不允許強制推送；revert 不改寫歷史、留下紀錄，也能走一樣的審查流程。

重點整理

  • 三個區域：工作目錄改檔案、git add 放進暫存區、git commit 存成快照；git diff 看沒 add 的、git diff --staged 看要 commit 的；commit 存的是 add 當下的內容。
  • commit＝快照＋作者與訊息＋父節點，名字是內容算出的雜湊值；第一個 commit 沒有父節點、合併 commit 有兩個以上。
  • 分支是指向 commit 的標籤（41 位元組的檔案），HEAD 指向目前的分支；commit 時只有 HEAD 指著的分支往前移；git branch 不切換，git switch -c 建立並切換。
  • merge：正前方就快轉；岔開就三方合併、產生雙父節點的合併 commit；改到同一處才衝突——改好檔案、刪標記、add、commit，或 git merge --abort。
  • rebase 在新起點上重做 commit，雜湊值全換、歷史變一條直線；不要 rebase 已經在別人手上的 commit。
  • fetch 只更新 origin/main 書籤、不動工作目錄；pull＝fetch＋merge；push 被拒絕就先 pull 再 push，不要 --force。
  • 救回：沒 commit 用 restore（--staged 拿出暫存區）、推出去了用 revert、沒推出去才用 reset --hard；reset 或刪錯分支看 reflog。沒 commit 過的修改被 --hard 蓋掉就救不回來。
  • 團隊：短命分支、push、開 PR、自動檢查與審查、核准才合併；main 用保護分支禁止直接推送，出錯用 revert。
