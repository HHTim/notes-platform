先看四種做法長什麼樣

伺服器有新消息，怎麼讓瀏覽器知道

HTTP 是用戶端問、伺服器答。匯率變了、轉帳入帳了，伺服器沒辦法主動開口，只能等瀏覽器來問。RFC 6455 開頭就講這個痛點：過去需要雙向通訊的網頁應用程式，「得濫用 HTTP 去輪詢伺服器有沒有更新，往上送的通知再另外發 HTTP 呼叫」（has required an abuse of HTTP to poll the server for updates while sending upstream notifications as distinct HTTP calls）。RFC 6455 第 1.1 節 常見的四種做法，下圖橫軸是時間：

  • 短輪詢（short polling）：RFC 6202 的定義是用戶端定期送請求、試著「拉」回事件，沒有就回空的，等一陣子再問（a client sends regular requests to the server and each request attempts to "pull" any available events or data）。缺點是要越即時就得問越頻繁，「輪詢頻率可能對伺服器、網路或兩者造成無法接受的負擔」（the polling frequency can cause an unacceptable burden on the server, the network, or both.）。RFC 6202 第 2.1 節
  • 長輪詢（long polling）：伺服器「只有在特定事件、狀態或逾時發生時才回應請求」（by responding to a request only when a particular event, status, or timeout has occurred.），用戶端收到回應通常馬上再發下一個。RFC 6202 第 2.1 節 逾時不能設太長，否則可能先收到伺服器的 408 或代理的 504。RFC 6202 第 5.5 節
  • SSE（Server-Sent Events，伺服器送出事件）：用戶端發一個 GET，伺服器把回應一直開著，有事件就寫一段進去。瀏覽器端的 API 叫 EventSource。
  • WebSocket：先用一個 HTTP 請求「升級」，之後同一條 TCP 連線改講 WebSocket，兩個方向都能隨時送訊息。

Spring 文件給的選法很務實：很多情況「AJAX 加 HTTP 串流或長輪詢就是簡單有效的解法」（in many cases, a combination of AJAX and HTTP streaming or long polling can provide a simple and effective solution.），「低延遲、高頻率、大量，三者同時成立，才是 WebSocket 最適合的情況」（It is the combination of low latency, high frequency, and high volume that make the best case for the use of WebSocket.）。Spring Framework 7.0 WebSocket 章

網銀首頁要顯示「目前有幾則未讀公告」，幾分鐘更新一次就夠。最省事的做法是？

  • WebSocket，加上 STOMP 訂閱
  • 短輪詢
  • 每個分頁各開一條 SSE
  • 長輪詢，逾時設 10 分鐘

更新慢、晚幾分鐘也沒關係，短輪詢就是普通 HTTP，最容易穿過代理、最好維護。Spring 文件也說新聞、信件這類每幾分鐘更新一次的需求，不一定要 WebSocket。長輪詢逾時設 10 分鐘還可能撞到代理的逾時。

短輪詢每 2 秒問一次。伺服器在剛好被問完之後 0.1 秒有了新資料，使用者最晚大約多久後才看得到？

  • 0.1 秒，有資料就馬上看得到
  • 大約 1 秒
  • 永遠看不到
  • 將近 2 秒

短輪詢的延遲上限就是輪詢間隔。想降到 0.5 秒就得每 0.5 秒問一次，請求數變四倍，這就是 RFC 6202 說的負擔。

長輪詢的請求送到伺服器時，伺服器手上沒有新資料。照 RFC 6202 的做法，伺服器會？

  • 馬上回一個空的回應
  • 回 404，表示目前沒有新資料
  • 等有新資料或逾時才回
  • 改用 WebSocket 推給用戶端

長輪詢的伺服器只在事件、狀態或逾時發生時才回應。馬上回空的是短輪詢。

長輪詢的用戶端收到一個回應之後，通常下一步是？

  • 等 5 分鐘再問
  • 關閉連線，改用 SSE
  • 送一個 Close 訊框
  • 立刻再發下一個長輪詢請求

RFC 6202：Once the server sends a long poll response, typically the client immediately sends a new long poll request。這樣伺服器手上隨時都有一個掛著的請求可以回。Close 訊框是 WebSocket 的東西。

長輪詢的逾時設成 10 分鐘。最可能遇到什麼問題？

  • 伺服器回 201 Created
  • 瀏覽器自動改用 HTTP/3 重送
  • 代理先逾時，回 504 或切斷
  • TLS 憑證過期

RFC 6202 第 5.5 節：逾時太長可能收到伺服器的 408 或代理的 504。很多代理的逾時比 10 分鐘短得多，例如 Nginx 讀取上游回應的逾時預設 60 秒。

客服聊天室：客戶與行員都要隨時打字給對方，延遲越低越好。哪一種最合適？

  • 短輪詢，每 0.5 秒問一次
  • SSE，客戶打字時另外發 POST
  • 長輪詢
  • WebSocket

兩個方向都頻繁送訊息，正是 WebSocket 的場景。SSE 只有伺服器到用戶端一個方向，客戶打字還得另外發 HTTP 請求。

匯率看板：伺服器每秒推最新匯率，使用者只看不送。哪一種最合適？

  • WebSocket，因為最即時
  • 每 100 毫秒短輪詢一次
  • 長輪詢，每筆匯率一個請求
  • SSE

單向推播、頻繁，SSE 剛好：一個請求收很多筆，瀏覽器還會自動重連。WebSocket 也做得到，但要多處理握手、重連與代理設定，這裡用不到雙向。

WebSocket 握手：Upgrade、101、Sec-WebSocket-Accept

RFC 6455 的摘要：WebSocket「讓在受控環境裡執行不受信任程式碼的用戶端，跟同意與它通訊的遠端主機雙向溝通」，協定由「開場握手，加上基本的訊息框架，疊在 TCP 上」組成（The protocol consists of an opening handshake followed by basic message framing, layered over TCP.）。RFC 6455 摘要 開場握手刻意長得像 HTTP，「讓同一個連接埠可以同時服務 HTTP 用戶端與 WebSocket 用戶端」（so that a single port can be used by both HTTP clients talking to that server and WebSocket clients talking to that server.），所以預設跟 HTTP 共用 80，走 TLS 時（wss://）共用 443。RFC 6455 第 1.3 節

換協定用的是 HTTP/1.1 的 Upgrade 標頭：用戶端「邀請」伺服器換到列出的協定（to invite the server to switch to one or more of the named protocols），伺服器可以不理。RFC 9110 第 7.8 節 伺服器同意就回 101 Switching Protocols，表示它「理解並願意照 Upgrade 的要求換掉這條連線上的應用協定」（the server understands and is willing to comply with the client's request, via the Upgrade header field (Section 7.8), for a change in the application protocol being used on this connection.）。RFC 9110 第 15.2.2 節 2026-10-02 用 curl 對示範專案的 /ws/echo 手動送一次握手（金鑰用 RFC 6455 的範例值）：

$ curl -sv -N -H 'Connection: Upgrade' -H 'Upgrade: websocket' \
    -H 'Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==' -H 'Sec-WebSocket-Version: 13' \
    http://127.0.0.1:9149/ws/echo
> GET /ws/echo HTTP/1.1
> Host: 127.0.0.1:9149
> Connection: Upgrade
> Upgrade: websocket
> Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
> Sec-WebSocket-Version: 13
>
< HTTP/1.1 101
< Upgrade: websocket
< Connection: upgrade
< Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

（Spring Boot 內建的 Tomcat 回應狀態行只寫碼、不寫 Switching Protocols 這幾個字，HTTP/1.1 的狀態行裡原因說明本來就可以省略。RFC 9112 第 4 節）同一個網址不帶 Upgrade 直接 GET，回的是 400，內文 Can "Upgrade" only to "WebSocket".——後面 Nginx 那一段會用到這個現象。

Sec-WebSocket-Accept 怎麼算：伺服器拿用戶端送來的 Sec-WebSocket-Key，接上一個固定的 GUID「258EAFA5-E914-47DA-95CA-C5AB0DC85B11」，做 SHA-1，再轉 Base64（concatenate this with the Globally Unique Identifier ... A SHA-1 hash (160 bits) [FIPS.180-3], base64-encoded (see Section 4 of [RFC4648]), of this concatenation is then returned in the server's handshake.）。RFC 6455 第 1.3 節 用 Python 照算一次，跟上面伺服器回的一模一樣：

>>> import base64, hashlib
>>> key = "dGhlIHNhbXBsZSBub25jZQ=="
>>> guid = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"
>>> base64.b64encode(hashlib.sha1((key + guid).encode()).digest()).decode()
's3pPLMBiTxaQ9kYGzzhZRbK+xOo='

這個值的用途是讓用戶端確認「伺服器願意接受這條連線」（indicates whether the server is willing to accept the connection），值不對就「不得被解讀成伺服器接受了連線」。RFC 6455 第 1.3 節 它不加密任何東西，也不驗證誰的身分；要加密就用 wss://（WebSocket 跑在 TLS 上），要驗證身分就用 Cookie 或權杖，跟一般 HTTP 一樣。

握手之後：同一條 TCP 連線改送 WebSocket 的訊框（frame，每則訊息切成的一段，前面帶著「這是文字、二進位、Ping 還是 Close」的標記）。幾條規則：

  • 用戶端「必須（MUST）遮罩送給伺服器的所有訊框」（a client MUST mask all frames that it sends to the server），伺服器送的「不得（MUST NOT）遮罩」。RFC 6455 第 5.1 節 遮罩（masking）是用一組隨機的 4 位元組把內容打亂。它不是為了保密，RFC 第 10.3 節說明是為了防止有人透過升級過的連線送出「看起來像 GET 請求」的資料，污染中間的快取代理。RFC 6455 第 10.3 節
  • 收到 Ping「必須（MUST）回一個 Pong」（Upon receipt of a Ping frame, an endpoint MUST send a Pong frame in response, unless it already received a Close frame.）。RFC 6455 第 5.5.2 節 常拿來確認對方還在，也讓中間的代理看到連線有動靜、不要當成閒置切掉。
  • 關閉時雙方各送一個 Close 訊框，再關 TCP。RFC 說這個關閉握手是用來補 TCP 揮手的不足，因為有攔截式代理時 TCP 的關閉「不一定端到端可靠」（the TCP closing handshake is not always reliable end-to-end, especially in the presence of intercepting proxies and other intermediaries.）。RFC 6455 第 1.4 節

WebSocket 的 Upgrade 是 HTTP/1.1 的機制。HTTP/2 寫明「101 的語意不適用於多工的協定」（The semantics of 101 (Switching Protocols) aren't applicable to a multiplexed protocol.），RFC 9113 第 8.6 節 要在 HTTP/2 上跑 WebSocket 得用 RFC 8441 定義的另一套做法（在 HTTP/2 的單一串流上跑 WebSocket）。RFC 8441

瀏覽器要開 WebSocket，送出的第一個東西是什麼？

  • 一個 WebSocket 文字訊框
  • 一個 UDP 封包，先探路
  • 帶 Upgrade 的 HTTP GET
  • 一個 Ping 訊框，確認伺服器在不在

WebSocket 的開場握手就是一個 HTTP Upgrade 請求，伺服器回 101 之後才開始送訊框。WebSocket 跑在 TCP 上，不是 UDP。

伺服器同意升級成 WebSocket，回的狀態碼是？

  • 200 OK
  • 101 Switching Protocols
  • 201 Created，代表連線建立了
  • 302 Found，轉到 ws:// 網址

101 表示伺服器理解並願意依 Upgrade 換掉這條連線上的應用協定。用戶端收到不是 101，就照一般 HTTP 回應處理，WebSocket 連線沒有建立。

用戶端送的 Sec-WebSocket-Key 是 dGhlIHNhbXBsZSBub25jZQ==，伺服器回 Sec-WebSocket-Accept: dGhlIHNhbXBsZSBub25jZQ==（原樣送回）。用戶端該怎麼做？

  • 接受，因為值跟送出去的一樣
  • 接受，Accept 的值不重要
  • 重送同一個 Key 再試
  • 不能當成連線成功，值不對

正確的值要是 Key 接上 GUID 後做 SHA-1 再 Base64，也就是 s3pPLMBiTxaQ9kYGzzhZRbK+xOo=。原樣送回正是「不懂 WebSocket 的伺服器」會有的樣子，RFC 說其他值都不得解讀成接受連線。

Sec-WebSocket-Accept 的主要作用是？

  • 證明伺服器懂 WebSocket
  • 把之後的訊息加密
  • 驗證使用者的帳號密碼是否正確、有沒有權限
  • 壓縮訊框

它只是一個用 Key 與固定 GUID 算出來的雜湊，誰都算得出來，所以不能拿來加密或驗證身分。加密靠 wss://（TLS），身分靠 Cookie 或權杖。

算 Sec-WebSocket-Accept 的步驟，順序正確的是？

  • Key 先 Base64 解碼 → SHA-256 → 十六進位
  • GUID 接上伺服器私鑰 → SHA-1 → Base64
  • Key 直接 Base64 再編碼一次
  • Key＋固定 GUID → SHA-1 → Base64

RFC 6455 第 1.3 節：把 Key（照原本的字串，不解碼）接上 258EAFA5-E914-47DA-95CA-C5AB0DC85B11，做 SHA-1，結果用 Base64 編碼。不涉及任何私鑰。

網址是 wss://chat.example.com/ws。這條 WebSocket 預設連哪個連接埠、有沒有 TLS？

  • 80，沒有 TLS
  • 8080，有 TLS
  • 443，有 TLS
  • 443，沒有 TLS

RFC 6455：一般 WebSocket 預設用 80，跑在 TLS 上的用 443。wss 的 s 就是加了 TLS，跟 https 對 http 一樣。

下面哪一個訊框送出去違反 RFC 6455？

  • 伺服器送給用戶端、沒有遮罩的文字訊框
  • 用戶端送給伺服器、有遮罩的文字訊框
  • 用戶端送給伺服器、沒有遮罩的文字訊框
  • 伺服器收到 Ping 後回的 Pong

用戶端送的訊框 MUST 遮罩，伺服器送的 MUST NOT 遮罩。伺服器收到沒遮罩的用戶端訊框，要關閉連線。

WebSocket 用戶端訊框要遮罩，主要是為了防什麼？

  • 防止別人偷看訊息內容
  • 防止污染中間的快取代理
  • 讓訊框比較小，傳得比較快
  • 讓伺服器知道訊息是誰送的

RFC 6455 第 10.3 節講的是攻擊基礎設施：讓快取代理把偽造的資料當成某個網址的回應存起來。遮罩金鑰就放在訊框裡，所以它擋不住偷看，要保密得用 wss://。

WebSocket 連線上，伺服器送來一個 Ping 訊框。用戶端照規格該做什麼？

  • 盡快回一個 Pong
  • 不理它，Ping 只是通知
  • 關閉連線
  • 回一個 HTTP 200

RFC 6455 第 5.5.2 節：收到 Ping MUST 回 Pong（除非已經收到 Close），而且 SHOULD 盡快。握手之後就不講 HTTP 了，不會回 200。

為什麼 WebSocket 除了 TCP 的揮手，還要自己定義一個 Close 訊框的關閉握手？

  • 有代理時 TCP 的關閉不一定可靠
  • 因為 WebSocket 不跑在 TCP 上
  • 因為 TCP 沒有關閉的機制
  • 為了加密關閉的原因

RFC 6455 第 1.4 節：the TCP closing handshake is not always reliable end-to-end, especially in the presence of intercepting proxies。Close 訊框走在 WebSocket 這一層，兩端確定都知道連線要關了。

某系統的入口全面走 HTTP/2。工程師說「WebSocket 照樣用 Upgrade 加 101 就好」。這句話？

  • 不對，HTTP/2 不適用 101
  • 對，HTTP/2 也用 101
  • 對，HTTP/2 會自動降級成 HTTP/1.1 再升級
  • 不對，WebSocket 根本不能跟 HTTP/2 並存

RFC 9113 第 8.6 節：101 的語意不適用於多工的協定。RFC 8441 定義了在 HTTP/2 的單一串流上跑 WebSocket 的方法；實務上也常見 WebSocket 那條連線另外走 HTTP/1.1。

id設定「最後事件編號」（set the last event ID buffer to the field value），重連時會送回去
retry值全是數字時，設成重連等待時間，單位毫秒（set the event stream's reconnection time to that integer）
以 : 開頭的行註解，忽略（Ignore the line.）

Spring 寫的是 data:{…}，冒號後面沒有空格；規格寫「值若以空格開頭，就去掉那個空格」（If value starts with a U+0020 SPACE character, remove it from value.），WHATWG HTML 第 9.2.5 節 所以 data: x 與 data:x 是同一件事。

自動重連與 Last-Event-ID：規格說連線關掉時「用戶端會重連」，伺服器要它別再連可以回 204（Clients will reconnect if the connection is closed; a client can be told to stop reconnecting using the HTTP 204 No Content response code.）。WHATWG HTML 第 9.2 節 重連時，瀏覽器用 Last-Event-ID 請求標頭「把最後事件編號回報給伺服器」（reports an EventSource object's last event ID string to the server when the user agent is to reestablish the connection.）。WHATWG HTML 第 9.2.4 節 伺服器看這個標頭，就能從下一筆接著送。示範專案這樣做：沒帶標頭從第 1 筆送，帶了就從下一筆送。用 Node 內建的 EventSource 實測（伺服器送完三筆就結束回應）：

readyState 0 是 CONNECTING：EventSource 斷線後不是放棄，而是回到「連線中」準備重連。WebSocket 沒有這個機制，斷了要自己寫重連，自己決定從哪裡補。

兩個實務限制：

  • 連線數：MDN 警告，沒有用 HTTP/2 時，SSE 受最大連線數限制，而且這個限制是每個瀏覽器、每個網域只有 6 條，開多個分頁時特別痛（When not used over HTTP/2, SSE suffers from a limitation to the maximum number of open connections, which can be especially painful when opening multiple tabs, as the limit is per browser and is set to a very low number (6).）。MDN〈Using server-sent events〉 走 HTTP/2 時，多條 SSE 只是同一條連線上的多個串流。
  • 代理逾時：規格建議每 15 秒左右送一行註解，防止舊的代理在短暫逾時後切斷連線（authors can include a comment line (one starting with a ':' character) every 15 seconds or so.）。WHATWG HTML 第 9.2.7 節

SseEmitter、WebSocketHandler 與 STOMP

以下程式碼節錄自示範專案（Spring Boot 4.1.1，帶進的是 Spring Framework 7.0.9，Java 21 編譯執行），相依只有 spring-boot-starter-webmvc 與 spring-boot-starter-websocket。

SSE：回傳 SseEmitter。Spring 文件說 SseEmitter（ResponseBodyEmitter 的子類別）支援 SSE，「從控制器產生 SSE 串流，回傳 SseEmitter 即可」（To produce an SSE stream from a controller, return SseEmitter）。Spring Framework 7.0 非同步請求

@GetMapping(path = "/rates/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@RequestHeader(name = "Last-Event-ID", required = false) String lastId) {
    SseEmitter emitter = new SseEmitter(30_000L);          // 30 秒逾時
    int start = (lastId == null) ? 1 : Integer.parseInt(lastId) + 1;
    for (int i = 0; i < 3; i++) {
        int id = start + i;
        boolean last = (i == 2);
        timer.schedule(() -> {                            // 在別的執行緒裡送
            try {
                emitter.send(SseEmitter.event()
                        .id(String.valueOf(id))
                        .name("rate")
                        .reconnectTime(3000)
                        .data("{\"pair\":\"USD/TWD\",\"rate\":" + rateOf(id) + "}"));
                if (last) emitter.complete();
            } catch (IOException e) {
                emitter.completeWithError(e);
            }
        }, i + 1, TimeUnit.SECONDS);
    }
    return emitter;
}

三個重點：方法很快就 return，真正的事件是之後在別的執行緒用 send 寫進去；id、name、reconnectTime 分別變成 id:、event:、retry: 三行；complete() 結束回應，瀏覽器那端會照 retry 重連。建構子的逾時沒給的話，用的是 MVC 設定或底層伺服器的預設值。

原生 WebSocket：繼承 TextWebSocketHandler。文件寫建 WebSocket 伺服器「就是實作 WebSocketHandler，更常見的是繼承 TextWebSocketHandler 或 BinaryWebSocketHandler」（Creating a WebSocket server is as simple as implementing WebSocketHandler or, more likely, extending either TextWebSocketHandler or BinaryWebSocketHandler.）。Spring Framework 7.0 WebSocket API

STOMP 一眼：原生 WebSocket 只管把訊息送到，不管訊息是什麼意思。Spring 文件說 WebSocket「不規定訊息內容的語意」，除非雙方約好，否則「沒辦法路由或處理訊息」（there is no way to route or process a message unless the client and the server agree on message semantics.），雙方可以在握手時用 Sec-WebSocket-Protocol 談好用 STOMP 這類上層協定。Spring Framework 7.0 WebSocket 章 STOMP（Simple Text Oriented Messaging Protocol）是「以 HTTP 為模型的訊框式協定」，用戶端用 SEND 或 SUBSCRIBE 送出或訂閱訊息，加上 destination 標頭說明訊息是關於什麼、誰該收（Clients can use the SEND or SUBSCRIBE commands to send or subscribe for messages, along with a destination header that describes what the message is about and who should receive it.）。Spring Framework 7.0 STOMP 概觀

@Configuration
@EnableWebSocketMessageBroker
public class StompConfig implements WebSocketMessageBrokerConfigurer {
    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/stomp");
    }
    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.setApplicationDestinationPrefixes("/app");
        registry.enableSimpleBroker("/topic");
    }
}

@Controller
public class NotifyController {
    @MessageMapping("/transfer")
    @SendTo("/topic/notifications")
    public String transfer(String body) {
        return "交易通知：" + body + " 已入帳";
    }
}

文件的路由規則：destination 以 /app 開頭的訊息「可能被送到 @MessageMapping 方法」，/topic 與 /queue 的「可能直接送到訊息代理」（STOMP messages whose destination headers start with /app may be routed to @MessageMapping methods in annotated controllers, while /topic and /queue messages may be routed directly to the message broker.）。Spring Framework 7.0 STOMP 訊息流程

中間還有一個人

Nginx 代理 WebSocket 與 SSE

〈Web Hosting 與 Nginx〉的 proxy_pass 設定，直接拿來代理 WebSocket 會失敗。nginx.org 的說明：「因為 Upgrade 是逐跳標頭，它不會從用戶端傳給被代理的伺服器」（since the "Upgrade" is a hop-by-hop header, it is not passed from a client to proxied server.）。逐跳標頭（hop-by-hop header）只管「這一段連線」，代理收下就算數，不往下一段傳；RFC 9110 用 Connection 標頭區分這類欄位與要傳到終點的欄位。RFC 9110 第 7.6.1 節 所以「這些標頭必須明確傳過去」（these headers have to be passed explicitly）：nginx.org〈WebSocket proxying〉

location /ws/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;                    # Nginx 1.29.7 以前的預設是 1.0，要寫
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 300s;                   # 預設 60 秒沒資料就關
}

三個設定各有出處：

  • proxy_http_version：nginx.org 寫「從 1.29.7 起預設用 1.1，1.29.7 以前預設用 1.0」（Since 1.29.7, version 1.1 is used by default. Before 1.29.7, version 1.0 was used by default.）。ngx_http_proxy_module Upgrade 是 HTTP/1.1 的機制，舊版 Nginx 一定要寫這行。
  • proxy_read_timeout：「被代理的伺服器在這段時間內沒有送任何東西，連線就關掉」（If the proxied server does not transmit anything within this time, the connection is closed.），預設 60 秒。ngx_http_proxy_module nginx.org 也提另一個做法：讓後端定期送 Ping 訊框重設逾時（the proxied server can be configured to periodically send WebSocket ping frames to reset the timeout）。nginx.org〈WebSocket proxying〉
  • SSE 的緩衝：SSE 不用 Upgrade，但 Nginx 預設會先把上游的回應收進緩衝區（proxy_buffering 預設 on），事件可能卡住不即時。可以對這個位置設 proxy_buffering off，或讓後端在回應加 X-Accel-Buffering: no（Buffering can also be enabled or disabled by passing "yes" or "no" in the "X-Accel-Buffering" response header field.）。ngx_http_proxy_module 逾時同樣適用 proxy_read_timeout，定期送註解行可以撐住。

Nginx 之外，公司網路與網際網路上的代理也可能擋 WebSocket。Spring 文件提醒，網際網路上你管不到的嚴格代理可能「沒設定轉送 Upgrade 標頭，或把看起來閒置的長連線關掉」（either because they are not configured to pass on the Upgrade header or because they close long-lived connections that appear idle.），所以防火牆內的內部系統用 WebSocket 比較單純。Spring Framework 7.0 WebSocket 章 Spring 為此提供 SockJS 備援：「先試 WebSocket，不行就退回用 HTTP 技術模擬」（attempting to use WebSocket first and then falling back on HTTP-based techniques that emulate a WebSocket interaction）。Spring Framework 7.0 SockJS 備援

前端連 wss://bank.example/ws/，經過 Nginx 到後端 Spring Boot。Nginx 只有 proxy_pass，沒補任何標頭。最可能的結果是？

  • 握手失敗
  • 正常，Nginx 會自動處理升級
  • 回 101，但之後收不到訊息
  • Nginx 自動改用 SSE

Upgrade 與 Connection 是逐跳標頭，不會自動傳給後端。後端看到的是普通 GET，示範專案對這種請求回 400。

要讓 Nginx 正確代理 WebSocket，location 裡最關鍵的兩行是？

  • 補上 Upgrade 與 Connection 標頭
  • Host 與 X-Forwarded-For
  • proxy_buffering off 與 gzip on
  • add_header Cache-Control no-store

nginx.org：這些標頭必須明確傳過去。Host、X-Forwarded-For 是〈Web Hosting 與 Nginx〉講的轉送資訊，跟升級無關。

WebSocket 經過 Nginx 能連上，但使用者一分鐘沒動作就斷線。最可能的原因是？

  • proxy_read_timeout 預設 60 秒
  • TLS 憑證過期
  • 瀏覽器規定 WebSocket 連線最多只能開一分鐘就要重建
  • Sec-WebSocket-Accept 算錯

proxy_read_timeout 預設 60s。解法是加長逾時，或讓後端定期送 Ping 訊框，nginx.org 兩種都有提。Accept 算錯根本連不上，不會撐一分鐘。

SSE 經過 Nginx 後，事件不是每秒一筆，而是好幾筆一起「一坨」到。最該先檢查什麼？

  • 是不是漏了 Upgrade 與 Connection 標頭
  • Nginx 的代理緩衝
  • 瀏覽器的 retry 設定
  • Last-Event-ID 有沒有帶

Nginx 預設會先把上游回應收進緩衝區再送，SSE 一筆一筆的效果就沒了。SSE 是普通 HTTP，不需要 Upgrade；retry 與 Last-Event-ID 管的是重連。

公司用的是 Nginx 1.24。WebSocket 的 location 沒寫 proxy_http_version 1.1。會怎樣？

  • 沒差，Nginx 一直都預設 1.1
  • Nginx 會自動改用 HTTP/2 對上游說話
  • 可能失敗，舊版預設 1.0
  • 只影響 SSE，不影響 WebSocket

nginx.org：Before 1.29.7, version 1.0 was used by default。舊版要明寫 proxy_http_version 1.1，新版不寫也是 1.1。

網銀的對外 App 要做即時通知，但有些客戶在管得很嚴的公司網路裡，WebSocket 常連不上。Spring 生態裡的對策是？

  • 用 SockJS 備援
  • 改用 UDP 繞過代理
  • 要客戶換網路
  • 把 Sec-WebSocket-Version 改成 8

Spring 文件：嚴格的代理可能不轉送 Upgrade 或關掉閒置的長連線，解法是 WebSocket 模擬，Servlet 堆疊提供 SockJS。另一個選擇是改用 SSE 這類普通 HTTP 的做法。

放回銀行的情境

匯率推播、交易通知怎麼選

下面是依前面各段的取捨整理的建議，不是唯一答案；實際還要看前端、代理與既有架構。

情境建議理由
匯率、股價看板SSE伺服器單向推、頻繁；瀏覽器自動重連；斷線補送可以只補最新一筆（舊匯率沒意義）
入帳、扣款通知SSE 或 STOMP，事件給遞增編號不能漏：重連時依 Last-Event-ID（或自己記的編號）補送；也要有「打開 App 時查一次未讀」當保險
線上客服、行員協作WebSocket（常搭 STOMP）雙向、頻繁；STOMP 讓訊息依 destination 分流，並能用 Spring Security 管權限
大型報表產生完成短輪詢或長輪詢一天幾次、晚幾秒沒差；就是普通 HTTP，最好維護

先問「誰要說話」：只有伺服器說，用 SSE；兩邊都要說，用 WebSocket；偶爾才有事，輪詢就夠

即時推播只是「盡量快」，不是「保證送到」。交易通知這類一筆都不能漏的訊息，常見的做法是推播之外，另外有一個查詢介面讓用戶端補齊；推播端則可以接訊息佇列。

匯率看板斷線 30 秒後重連。伺服器最合理的補送策略是？

  • 把 30 秒內的每一筆都照順序補送一遍
  • 什麼都不送，等下一次變動
  • 回 204，要使用者重新整理
  • 只送最新一筆，舊的匯率已經沒意義

看板只在乎現在的值。逐筆補送適合交易通知這種每筆都重要的事件。等下一次變動，畫面會停在舊值；回 204 會讓 EventSource 停止重連。

入帳通知用 SSE 推，使用者的手機在地下室斷線 5 分鐘。哪個設計最能確保不漏？

  • 把 retry 設成 100 毫秒
  • 依編號補送，再加「查未讀」
  • 改用短輪詢
  • 開兩條 SSE 備援

斷線期間怎麼重連都連不上，retry 再小也沒用。能補的是伺服器記得事件、依編號補送；App 重新打開時再查一次未讀，連重連失敗的情況也顧到。

行內系統要做「多位行員同時編輯同一份授信文件，即時看到彼此的修改」。最合適的是？

  • SSE
  • WebSocket（可搭 STOMP）
  • 每 30 秒短輪詢一次，看有沒有人改過
  • 電子郵件通知

每個人都在送修改、也都要收別人的修改，雙向又頻繁。行內網路在防火牆內，也是 Spring 文件說 WebSocket 比較好決定的情境。

工程師說「我們改用 WebSocket 推交易通知，所以通知一定送得到」。這句話的問題是？

  • 沒問題，WebSocket 跑在 TCP 上，保證送到
  • WebSocket 不能傳中文
  • WebSocket 只能用在聊天室
  • 斷線時送不出去，也不會自動補

TCP 只保證連線還在時照順序送到，連線斷了這段期間的通知就送不出去。WebSocket 沒有像 SSE 那樣內建重連與 Last-Event-ID，補送機制得自己做。

重點整理

  • 短輪詢定期問、延遲上限是間隔；長輪詢讓請求掛著，有事或逾時才回；SSE 是一個一直不結束的 HTTP 回應，只有伺服器往用戶端；WebSocket 升級後雙向。低延遲、高頻率、大量同時成立，才最適合 WebSocket。
  • WebSocket 握手：GET 帶 Upgrade: websocket、Connection: Upgrade、Sec-WebSocket-Key；伺服器回 101 與 Sec-WebSocket-Accept＝Base64(SHA-1(Key＋固定 GUID))。它證明伺服器懂 WebSocket，不是加密；加密用 wss://。
  • 握手後送訊框：用戶端必須遮罩、伺服器不遮罩；收到 Ping 必須回 Pong；關閉時雙方各送 Close。101 不適用於 HTTP/2，要用 RFC 8441。
  • SSE：text/event-stream，欄位 data、event、id、retry，空行結束一個事件，冒號開頭是註解。斷線後瀏覽器等 retry 毫秒自動重連，帶 Last-Event-ID，伺服器要自己依它補送；回 204 叫它別再連。HTTP/1.1 下每個網域只有 6 條。
  • Spring：回傳 SseEmitter，在別的執行緒 send、最後 complete；原生 WebSocket 繼承 TextWebSocketHandler 並用 @EnableWebSocket 註冊；STOMP 用 @EnableWebSocketMessageBroker，/app 進 @MessageMapping、/topic 交給訊息代理廣播。
  • Nginx：Upgrade、Connection 是逐跳標頭，要用 proxy_set_header 補；舊版要寫 proxy_http_version 1.1；proxy_read_timeout 預設 60 秒；SSE 要關代理緩衝。嚴格的代理擋 WebSocket 時，Spring 有 SockJS 備援。
