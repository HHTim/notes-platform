先把舞台搭好，代理、執行緒、連線

宣告式交易到底怎麼運作

〈Spring AOP 與交易控制〉講過：在服務方法上加 @Transactional，Spring 就替你開交易、提交、還原。這課要回答的是接下來的問題：一個有交易的方法呼叫另一個有交易的方法時會怎樣？例外被誰接住才會還原？哪些寫法看起來有交易、其實沒有？要答這些，得先知道它背後怎麼運作。

Spring 文件的說法是：交易的設定加上 AOP，會產生一個「使用 TransactionInterceptor 搭配適當的 TransactionManager 實作、在方法呼叫前後驅動交易的 AOP 代理」（an AOP proxy that uses a TransactionInterceptor in conjunction with an appropriate TransactionManager implementation to drive transactions around method invocations）。出處 代理（proxy）就是包在你的物件外面的一層替身：別的 Bean 拿到的其實是代理，呼叫先進代理，代理裡的交易攔截器（interceptor）開好交易，再轉給你寫的方法；方法結束後，攔截器決定提交還是還原。

交易開好之後放在哪？綁在目前這條執行緒上。JDBC 的交易管理器 DataSourceTransactionManager 的文件寫它「把指定 DataSource 的一條 JDBC 連線綁到目前的執行緒」（Binds a JDBC Connection from the specified DataSource to the current thread）出處；負責記帳的 TransactionSynchronizationManager 是「以每條執行緒為單位管理資源與交易同步的中央委派」（Central delegate that manages resources and transaction synchronizations per thread）。出處 同一條執行緒裡後面再用 JdbcTemplate 或 Repository，拿到的都是同一條連線，所以它們自然在同一筆交易裡。

還要分清兩個詞，Spring 文件特別提醒要注意「實體交易與邏輯交易的差別」（the difference between physical and logical transactions）。出處 實體交易是資料庫真的開的那一筆（一條連線上的 begin 到 commit）；邏輯交易範圍是每個標了 @Transactional 的方法各自圈出的一段。好幾個邏輯範圍可以共用同一筆實體交易，這正是傳播行為在決定的事。

這課的範例都實際跑過：Spring Boot 4.1.1（內含 Spring Framework 7.0.9）、Java 21，資料庫用 Docker 起的 MySQL 8.4，交易管理器是 JdbcTemplate 搭配的 DataSourceTransactionManager；JPA 那一段另外用 Hibernate 7.4.5 與 H2。本課講的傳播、還原規則在 Spring Framework 6.2（Spring Boot 3.4）以後都一樣；Boot 4 的變動之一是 starter（一包預先配好的相依組合）改名，例如 Web 改叫 spring-boot-starter-webmvc。兩張表 transfer_record（轉帳紀錄）與 audit_log（稽核紀錄），每個情境先清空、執行，再數各剩幾筆。

docker run -d --name tx-mysql -e MYSQL_ROOT_PASSWORD=demo -e MYSQL_DATABASE=bank \
  -p 127.0.0.1:33961:3306 mysql:8.4

範例裡的 Db 類別只包了幾個 JdbcTemplate 呼叫：db.transfer(…) 寫一筆轉帳、db.audit(…) 寫一筆稽核，另外兩個方法數各剩幾筆。

別的 Bean 注入 TransferService 之後呼叫它的 @Transactional 方法，這次呼叫第一個碰到的是什麼？

  • TransferService 方法的第一行
  • Spring 產生的代理
  • 資料庫的觸發程序
  • JdbcTemplate

注入進去的是代理。呼叫先進代理、由 TransactionInterceptor 開交易，才轉給你寫的方法。

交易開好之後，Spring 把那條連線放在哪裡，讓後面的 JdbcTemplate 也用同一條？

  • 放在 static 全域變數，整個程式共用
  • 放在 HTTP Session 裡
  • 綁在目前這條執行緒上
  • 每次查詢都重新拿一條新連線

DataSourceTransactionManager 把連線綁到目前的執行緒；同一條執行緒後面的資料存取拿到的都是它。這也是另開執行緒會脫離交易的原因。

「實體交易」跟「邏輯交易範圍」差在哪？

  • 實體交易是寫在程式碼裡的，邏輯交易是資料庫裡的
  • 兩個是同一件事的不同叫法，Spring 文件只是換個說法強調交易很重要，實作上完全一樣
  • 實體交易只用在 JPA，邏輯交易只用在 JDBC
  • 實體是資料庫真的開的那筆，好幾段邏輯範圍可以共用它

傳播行為決定的就是：這一段邏輯範圍要加入既有的實體交易、另開一筆，還是不用交易。

為什麼交易邊界通常放在服務層，而不是每個 DAO 方法各開一個？

  • 因為 DAO 不能加 @Transactional
  • 一件商業操作的幾步要一起成功或失敗
  • 因為服務層比較快
  • 因為 DAO 上的 @Transactional 會被忽略

轉帳要扣款又入帳，兩步必須在同一筆交易裡。各自在 DAO 開交易，扣款提交了、入帳失敗就只做一半。〈Spring AOP 與交易控制〉講過這點。

裡面那層，要加入、另開，還是不要交易

七種傳播行為

傳播行為（propagation）決定：一個 @Transactional 方法被呼叫時，如果外面已經有交易，它要怎麼辦；外面沒有交易時，又要怎麼辦。Propagation 列舉定義了七種，預設是 REQUIRED：

傳播行為官方說明（原文）外層有交易時外層沒有交易時
REQUIRED（預設）Support a current transaction, create a new one if none exists.加入外層自己開一筆
REQUIRES_NEWCreate a new transaction, and suspend the current transaction if one exists.暫停外層，另開一筆自己開一筆
NESTEDExecute within a nested transaction if a current transaction exists, behave like REQUIRED otherwise.在外層裡設儲存點跟 REQUIRED 一樣
SUPPORTSSupport a current transaction, execute non-transactionally if none exists.加入外層不用交易
MANDATORYSupport a current transaction, throw an exception if none exists.加入外層丟例外
NOT_SUPPORTEDExecute non-transactionally, suspend the current transaction if one exists.暫停外層，不用交易不用交易
NEVERExecute non-transactionally, throw an exception if a transaction exists.丟例外不用交易

原文出自 Propagation 的 API 文件。出處 表格右兩欄不用背，自己跑一次就看得到：每個方法回報「現在有沒有實體交易、這筆交易是誰開的」，再分別從沒有交易的地方、從一個有交易的外層方法裡呼叫它。

@Service
public class ProbeService {
    // 回報「現在有沒有實體交易、交易叫什麼名字」
    static String now() {
        return TransactionSynchronizationManager.isActualTransactionActive()
                ? "在交易中（" + TransactionSynchronizationManager.getCurrentTransactionName()
                        .replace("com.example.txjdbc.", "") + "）"
                : "沒有交易";
    }

    @Transactional(propagation = Propagation.REQUIRED)      public String required()     { return now(); }
    @Transactional(propagation = Propagation.REQUIRES_NEW)  public String requiresNew()  { return now(); }
    @Transactional(propagation = Propagation.NESTED)        public String nested()       { return now(); }
    @Transactional(propagation = Propagation.SUPPORTS)      public String supports()     { return now(); }
    @Transactional(propagation = Propagation.MANDATORY)     public String mandatory()    { return now(); }
    @Transactional(propagation = Propagation.NOT_SUPPORTED) public String notSupported() { return now(); }
    @Transactional(propagation = Propagation.NEVER)         public String never()        { return now(); }
}

執行結果（括號裡是開這筆交易的方法）：

REQUIRED       外層沒有：在交易中（ProbeService.required）｜外層有：在交易中（OuterService.inTransaction）
REQUIRES_NEW   外層沒有：在交易中（ProbeService.requiresNew）｜外層有：在交易中（ProbeService.requiresNew）
NESTED         外層沒有：在交易中（ProbeService.nested）｜外層有：在交易中（OuterService.inTransaction）
SUPPORTS       外層沒有：沒有交易｜外層有：在交易中（OuterService.inTransaction）
MANDATORY      外層沒有：丟出 IllegalTransactionStateException｜外層有：在交易中（OuterService.inTransaction）
NOT_SUPPORTED  外層沒有：沒有交易｜外層有：沒有交易
NEVER          外層沒有：沒有交易｜外層有：丟出 IllegalTransactionStateException

幾個要看懂的地方：REQUIRED 在外層有交易時，交易名稱是外層的 OuterService.inTransaction，代表它加入了外層；REQUIRES_NEW 不管外面有沒有，交易都是自己開的；NOT_SUPPORTED 在外層有交易時也回報「沒有交易」，因為外層被暫停了。MANDATORY 與 NEVER 丟的是 IllegalTransactionStateException。

沒寫 propagation 的 @Transactional，傳播行為是哪一個？

  • REQUIRES_NEW
  • SUPPORTS
  • REQUIRED
  • NESTED

參考文件列的預設值第一條就是 PROPAGATION_REQUIRED：有交易就加入，沒有就開一筆。

一個標 MANDATORY 的方法，被一個沒有交易的地方呼叫，會怎樣？

  • 丟出 IllegalTransactionStateException
  • 自己開一筆交易
  • 不用交易照常執行
  • 先不執行，排進佇列，等呼叫端之後開了交易才補做

MANDATORY：throw an exception if none exists。適合「一定要被包在別人交易裡才能呼叫」的方法，用它在一開始就擋掉誤用。

一個標 NEVER 的方法，被一個有交易的方法呼叫，會怎樣？

  • 加入外層交易
  • 暫停外層，不用交易執行，跑完再讓外層恢復
  • 另開一筆交易
  • 丟出 IllegalTransactionStateException

NEVER：throw an exception if a transaction exists。暫停外層、不用交易的是 NOT_SUPPORTED。

哪兩種傳播行為在「外層有交易」時，都會暫停外層？

  • REQUIRED 與 SUPPORTS
  • REQUIRES_NEW 與 NOT_SUPPORTED
  • NESTED 與 MANDATORY
  • NEVER 與 REQUIRED

REQUIRES_NEW 暫停外層、另開一筆；NOT_SUPPORTED 暫停外層、不用交易。NESTED 不暫停，是在外層裡設儲存點。

執行結果裡，REQUIRES_NEW 在「外層有」那欄，交易名稱為什麼是 ProbeService.requiresNew，不是外層的 OuterService.inTransaction？

  • 因為外層交易已經提交了
  • 因為 REQUIRES_NEW 會改掉外層交易的名字
  • 因為它另開了一筆自己的實體交易，現在看到的是這一筆
  • 因為 Spring 印錯了

REQUIRES_NEW 暫停外層、開一筆新的，方法裡看到的是新開的那一筆；外層在它結束後才恢復。

最常考的三個，加上那個嚇人的例外

REQUIRED、REQUIRES_NEW、NESTED 實際跑一次

三種的差別用一張圖看：

  • REQUIRED：文件說，每個方法各有一個邏輯範圍，但「這些範圍全部對應到同一筆實體交易」（all these scopes are mapped to the same physical transaction），所以內層設的還原標記「會影響外層真正提交的機會」。出處
  • REQUIRES_NEW：「對每個受影響的交易範圍都用獨立的實體交易，絕不參與外層既有的交易」，所以「可以各自獨立提交或還原」，內層的鎖「在它完成後馬上釋放」。出處
  • NESTED：「用單一實體交易，帶著好幾個可以退回去的儲存點」（uses a single physical transaction with multiple savepoints that it can roll back to），內層可以只還原自己那一段，外層繼續；它「通常對應到 JDBC 儲存點，所以只對 JDBC 資源交易有效」。出處 儲存點（savepoint）是交易中途做的記號，可以只退回到記號那裡，不用整筆還原。

實驗用一個稽核服務，三個方法只差傳播行為；fail 為 true 時寫完稽核再丟例外：

    @Transactional                                     // 預設 REQUIRED：加入外層交易
    public void logRequired(String message, boolean fail) {
        db.audit(message);
        if (fail) throw new IllegalStateException("稽核失敗");
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)   // 暫停外層，自己另開一筆
    public void logRequiresNew(String message, boolean fail) {
        db.audit(message);
        if (fail) throw new IllegalStateException("稽核失敗");
    }

    @Transactional(propagation = Propagation.NESTED)         // 在外層交易裡設一個儲存點
    public void logNested(String message, boolean fail) {
        db.audit(message);
        if (fail) throw new IllegalStateException("稽核失敗");
    }

外層是轉帳服務，六個情境寫在同一個類別，這裡節錄 A、B、C 三個（D、E、F 只差在 REQUIRES_NEW／NESTED 與丟例外的位置）：

    // 情境 A：內層 REQUIRED 丟例外，外層不接，例外一路往外丟
    @Transactional
    public void requiredInnerFails() {
        db.transfer("轉帳 1000");
        audit.logRequired("轉帳 1000", true);
    }

    // 情境 B：內層 REQUIRED 丟例外，外層 catch 住、假裝沒事
    @Transactional
    public void requiredInnerFailsCaught() {
        db.transfer("轉帳 1000");
        try {
            audit.logRequired("轉帳 1000", true);
        } catch (IllegalStateException e) {
            // 吞掉例外，想讓轉帳照常提交
        }
    }
…
    // 情境 C：稽核用 REQUIRES_NEW 先寫好，之後轉帳失敗
    @Transactional
    public void requiresNewThenOuterFails() {
        db.transfer("轉帳 1000");
        audit.logRequiresNew("嘗試轉帳 1000", false);
        throw new IllegalStateException("餘額不足");
    }

執行結果：

A REQUIRED 內層丟例外、外層不接
    例外：IllegalStateException；transfer_record 0 筆 []、audit_log 0 筆
B REQUIRED 內層丟例外、外層 catch 住
    例外：UnexpectedRollbackException；transfer_record 0 筆 []、audit_log 0 筆
C 稽核 REQUIRES_NEW，之後外層失敗
    例外：IllegalStateException；transfer_record 0 筆 []、audit_log 1 筆
D REQUIRES_NEW 內層丟例外、外層 catch 住
    例外：沒有例外；transfer_record 1 筆 [轉帳 1000]、audit_log 0 筆
E NESTED 內層丟例外、外層 catch 住
    例外：沒有例外；transfer_record 1 筆 [轉帳 1000]、audit_log 0 筆
F NESTED 內層成功，之後外層失敗
    例外：IllegalStateException；transfer_record 0 筆 []、audit_log 0 筆

逐一看：A 是同一筆交易，例外丟出去整筆還原；B 是外層吞掉例外，卻拿到 UnexpectedRollbackException（下一段解釋）；C 的稽核用 REQUIRES_NEW 先提交，外層失敗只還原轉帳；D 是 REQUIRES_NEW 內層自己還原、外層照常提交；E 的 NESTED 失敗只退回儲存點，結果跟 D 一樣，但只用一條連線；F 的 NESTED 是外層交易的一部分，外層失敗連它一起還原，這是它跟 REQUIRES_NEW（情境 C）最大的不同。

UnexpectedRollbackException 從哪來？情境 B 裡，內層是 REQUIRED，跟外層共用同一筆實體交易。內層丟例外時，它的攔截器把整筆交易標成「只能還原」（rollback-only）。外層 catch 住例外繼續跑，結束時要求提交，交易管理器看到標記，只能還原。文件說這時丟出 UnexpectedRollbackException 是刻意的：「讓呼叫端永遠不會被誤導，以為已經提交了，其實沒有」（so that the caller of a transaction can never be misled to assume that a commit was performed when it really was not）。出處

要讓內層失敗不拖累外層，做法有三：內層改 REQUIRES_NEW（多一條連線）、內層改 NESTED（JDBC 才行），或內層根本不要丟例外到攔截器，改回傳結果讓外層判斷。

REQUIRES_NEW 的代價：多吃一條連線。文件警告，外層的連線還綁著，內層「取得自己的資源，例如一條新的資料庫連線」，這「可能耗盡連線池，甚至造成死結」；「除非連線池大小至少比同時執行的執行緒數多 1，否則不要用 PROPAGATION_REQUIRES_NEW」（Do not use PROPAGATION_REQUIRES_NEW unless your connection pool is appropriately sized, exceeding the number of concurrent threads by at least 1.）。出處 連線池（connection pool）是事先開好、大家輪流借用的一批資料庫連線；全部借光時，後來的執行緒就得排隊等。

銀行情境：轉帳與稽核紀錄要不要同一筆交易？要看稽核紀錄想證明什麼：

稽核要記的是選擇結果
「發生了一筆成功的轉帳」REQUIRED，跟轉帳同一筆交易轉帳還原，稽核也跟著消失，不會留下沒發生的事
「有人嘗試轉帳」（不論成敗都要留）REQUIRES_NEW，另開一筆先提交情境 C：轉帳失敗，嘗試紀錄還在；稽核寫入失敗也不拖垮轉帳（情境 D）

用 REQUIRES_NEW 時，稽核內容要寫成「嘗試」而不是「完成」，因為它提交的時候還不知道轉帳會不會成功；要記最後結果，可以再搭配下面的交易事件，在提交或還原之後補一筆。

REQUIRED 一筆交易、REQUIRES_NEW 兩筆交易兩條連線、NESTED 一筆交易加儲存點；內層 REQUIRED 失敗被外層吞掉，換來 UnexpectedRollbackException

哪些例外會還原，哪些不會

還原規則：rollbackFor 與受檢例外

預設規則，參考文件寫得很直接：「任何 RuntimeException 或 Error 會觸發還原，任何受檢的 Exception 則不會」（Any RuntimeException or Error triggers rollback, and any checked Exception does not.）。出處 受檢例外（checked exception）就是方法要寫 throws 才能丟出去的那種，例如 IOException。而且判斷的時機是：交易基礎建設「在例外往上冒出呼叫堆疊時，接住任何沒被處理的例外」（catches any unhandled Exception as it bubbles up the call stack），再決定要不要標成還原。出處

    // 受檢例外：預設不還原
    @Transactional
    public void checkedDefault() throws IOException {
        db.transfer("轉帳 1000");
        throw new IOException("對帳檔寫不出去");
    }

    // 指定 rollbackFor 之後，受檢例外也還原
    @Transactional(rollbackFor = Exception.class)
    public void checkedWithRollbackFor() throws IOException {
        db.transfer("轉帳 1000");
        throw new IOException("對帳檔寫不出去");
    }
受檢例外、預設設定
    例外：IOException；transfer_record 1 筆 [轉帳 1000]、audit_log 0 筆
受檢例外、rollbackFor = Exception.class
    例外：IOException；transfer_record 0 筆 []、audit_log 0 筆

同樣丟 IOException，預設版本把轉帳提交了；加了 rollbackFor = Exception.class 才還原。可以設的規則：

  • rollbackFor／noRollbackFor：用例外型別指定，丟出的例外「等於這個型別或是它的子類別」就算符合。出處
  • rollbackForClassName：用類別名稱的字串比對，文件提醒它用「名稱包含」比對，"Exception"「幾乎什麼都符合」，可能誤中名字相似的例外，所以優先用型別。出處
  • 整個應用程式改預設：「從 6.2 起，可以全域改變預設的還原行為，例如 @EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS)，讓交易內丟出的所有例外都還原，包含受檢例外」。出處
  • 不丟例外也要還原：用 TransactionAspectSupport 拿到目前交易的狀態（currentTransactionStatus()），再呼叫 setRollbackOnly()。文件說這做法「侵入性很高」，能用宣告式就用宣告式。出處

同時有人在讀寫，要隔到什麼程度

隔離層級與唯讀交易

髒讀、不可重複讀、幻讀這三種「讀到怪東西」，以及各隔離層級怎麼擋、資料庫怎麼用鎖與多版本實作，在資料庫模組〈交易隔離層級與鎖〉。這裡只講 Spring 這邊怎麼設：

    @Transactional
    public String byDefault() throws SQLException { return describe(); }

    @Transactional(isolation = Isolation.SERIALIZABLE)
    public String serializable() throws SQLException { return describe(); }

    @Transactional(readOnly = true)
    public String readOnly() throws SQLException { return describe(); }

    @Transactional(readOnly = true)
    public void writeInReadOnly() { db.transfer("唯讀交易裡寫入"); }

從交易綁的那條連線讀出實際設定，同一支程式分別接 MySQL 與 H2：

預設：隔離層級 REPEATABLE_READ，唯讀 false
SERIALIZABLE：隔離層級 SERIALIZABLE，唯讀 false
readOnly = true：隔離層級 REPEATABLE_READ，唯讀 true
唯讀交易裡寫入
    資料庫回應：Connection is read-only. Queries leading to data modification are not allowed
    例外：TransientDataAccessResourceException；transfer_record 0 筆 []、audit_log 0 筆
  • 預設的 Isolation.DEFAULT 是「用底層資料庫的預設」（Use the default isolation level of the underlying data store）。出處 所以同一支程式，MySQL 跑出來是 REPEATABLE_READ，換 H2 實跑是 READ_COMMITTED。換資料庫時這個差別要留意。
  • 隔離層級只在開新交易時生效。參考文件的設定表寫 isolation「只適用於 REQUIRED 或 REQUIRES_NEW 傳播」；而且加入既有交易時，「預設會沿用外層範圍的特性，默默忽略自己的隔離層級、逾時與唯讀設定」（silently ignoring the local isolation level, timeout value, or read-only flag (if any)）。出處 想讓這種不一致直接報錯，可以把交易管理器的 validateExistingTransaction 設成 true。
  • 唯讀只是提示。readOnly 的 API 文件：「這只是給實際交易子系統的提示，不一定會讓寫入失敗」（it will not necessarily cause failure of write access attempts），看不懂提示的交易管理器「會默默忽略」。出處 實跑結果正好示範：連線確實被設成唯讀（唯讀 true），MySQL 的驅動拒絕寫入；同一段程式換成 H2，寫入照樣成功、留下 1 筆。唯讀交易的價值是讓資料庫與 ORM 做最佳化，不是拿來當權限控管。

@Transactional 沒寫 isolation，接 MySQL 8.4（InnoDB）時，實際的隔離層級是？

  • READ_COMMITTED，Spring 的預設
  • REPEATABLE_READ，用資料庫自己的預設
  • SERIALIZABLE
  • READ_UNCOMMITTED

Isolation.DEFAULT 是「用底層資料庫的預設」，Spring 自己不挑。實跑印出 REPEATABLE_READ；同一支程式接 H2 是 READ_COMMITTED。

外層是 @Transactional(isolation = READ_COMMITTED)，裡面呼叫一個 @Transactional(isolation = SERIALIZABLE)（傳播是預設的 REQUIRED）的方法。內層方法裡實際的隔離層級是？

  • SERIALIZABLE，比較嚴格的優先
  • READ_COMMITTED，沿用外層
  • 丟出 IllegalTransactionStateException
  • 資料庫預設的 REPEATABLE_READ

實跑印出「隔離層級 READ_COMMITTED」。REQUIRED 加入既有交易時，預設默默忽略內層的隔離層級；要讓它報錯得開 validateExistingTransaction。

外層是一般的讀寫交易，裡面呼叫一個 @Transactional(readOnly = true)（傳播 REQUIRED）的方法，那個方法寫入一筆。在 MySQL 上結果是？

  • 丟出例外，因為內層是唯讀
  • 內層另開一筆唯讀交易，寫入失敗
  • 寫入了，但外層提交時會發現內層是唯讀，整筆改成還原並丟出例外
  • 寫入成功，轉帳 1 筆；加入外層時沿用外層的讀寫特性

實跑結果：沒有例外、1 筆。REQUIRED 加入外層時忽略自己的唯讀設定。

同樣的情況，但內層改成 @Transactional(readOnly = true, propagation = REQUIRES_NEW)，在 MySQL 上寫入會怎樣？

  • 寫入成功，唯讀只是提示
  • 內層另開一筆唯讀交易，MySQL 驅動拒絕寫入、丟出例外
  • 沿用外層的讀寫特性，寫入成功
  • 內層改成不用交易，寫入走自動提交，所以會成功並且留下一筆

REQUIRES_NEW 開的是自己的新交易，唯讀設定生效；實跑丟出 TransientDataAccessResourceException，例外往外丟，外層也一起還原。

關於 readOnly = true，下面哪一句正確？

  • 它保證任何寫入都會失敗，可以拿來做權限控管
  • 它會讓交易的隔離層級變成 SERIALIZABLE
  • 它只是提示，擋不擋看資料庫與驅動
  • 它只對 JPA 有效，用 JdbcTemplate 時這個設定會被完全忽略，連線也不會被設成唯讀

API 文件：This just serves as a hint……it will not necessarily cause failure of write access attempts。

寫了註解，交易卻沒開或沒還原

常見的失效情境

失效分兩類：代理攔不到（根本沒開交易），或攔到了但還原條件不成立（開了卻不還原）。

  • 自我呼叫：參考文件：「在代理模式（預設）下，只有從外面經過代理進來的方法呼叫會被攔截。這表示自我呼叫……即使被呼叫的方法標了 @Transactional，執行期也不會產生實際的交易」（does not lead to an actual transaction at runtime even if the invoked method is marked with @Transactional）。同一頁也提醒：代理要完全初始化才會有預期的行為，不要在 @PostConstruct 這類初始化程式裡依賴它。出處
  • 方法可見度：「從 6.0 起，類別式代理預設也可以讓 protected 或套件可見的方法有交易」；介面式代理的交易方法「永遠必須是 public，而且定義在被代理的介面裡」。出處 private 方法別的 Bean 呼叫不到，只能從自己內部呼叫，那就是自我呼叫。6.0 之前只有 public 方法有效（上面那句 As of 6.0 指的就是這個改變）。
  • 例外被吞掉：還原的判斷是在例外「往上冒出呼叫堆疊時」做的；方法自己 catch 住、只寫日誌，攔截器看不到例外，就提交。
  • 另開執行緒：交易綁在執行緒上，新執行緒拿不到這筆交易的連線，它的寫入自己自動提交。
  • 不是 Spring 管理的物件：自己 new 出來的物件沒有代理包著，上面的註解沒人處理。
    // 自我呼叫：從同一個物件裡的方法呼叫有 @Transactional 的方法
    public void selfInvocation() {
        this.saveAndFail();
    }

    @Transactional
    public void saveAndFail() {
        db.transfer("轉帳 1000");
        throw new IllegalStateException("餘額不足");
    }

    // 例外被吞掉：方法自己 catch，交易攔截器看不到例外
    @Transactional
    public void swallow() {
        db.transfer("轉帳 1000");
        try {
            throw new IllegalStateException("餘額不足");
        } catch (IllegalStateException e) {
            System.out.println("    （只印了日誌：" + e.getMessage() + "）");
        }
    }

    // 另開執行緒：新執行緒拿不到這筆交易
    @Transactional
    public void otherThread() throws InterruptedException {
        db.transfer("主執行緒寫的");
        Thread t = new Thread(() -> db.transfer("另一條執行緒寫的"));
        t.start();
        t.join();
        throw new IllegalStateException("餘額不足");
    }
// 沒有 @Service：不是 Spring 管理的 Bean，要自己 new
public class PlainService {
    private final Db db;

    public PlainService(Db db) { this.db = db; }

    @Transactional
    public void saveAndFail() {
        db.transfer("轉帳 1000");
        throw new IllegalStateException("餘額不足");
    }
}

    db.transfer("t");
    try { throw new IllegalStateException(); }
    catch (IllegalStateException e) { System.out.println("失敗"); }
}
  • 0 筆，收到 IllegalStateException
  • 0 筆，收到 UnexpectedRollbackException
  • 1 筆，沒有例外
  • 1 筆，收到 IllegalStateException

例外在方法裡就被處理掉了，攔截器看到的是正常結束，所以提交。想還原就重新丟出去，或呼叫 setRollbackOnly。

交易方法裡開了一條新執行緒寫入一筆，主執行緒也寫一筆，最後丟例外。哪一筆會留下？

  • 兩筆都留下
  • 兩筆都還原
  • 主執行緒那筆留下
  • 新執行緒那筆留下

主執行緒的寫入在交易裡，例外丟出去就還原；新執行緒拿不到綁在主執行緒上的交易，它的寫入自動提交了。實跑結果留下的就是「另一條執行緒寫的」。

自己 new 出來的物件外面沒有代理，註解只是一段沒人讀的資訊。要交易就讓它成為 Bean，用注入拿。

下面四種狀況，哪一種是「交易有開，只是沒還原」，而不是「根本沒開交易」？

  • 自我呼叫
  • 自己 new 出來的物件
  • private 方法
  • 方法裡把例外 catch 住吞掉

吞掉例外時代理有攔到、交易有開，只是攔截器沒看到例外就提交了。其他三種都是代理攔不到，交易根本沒開。

提交之後才做的事

@TransactionalEventListener：等交易有結果再通知

轉帳成功之後要發簡訊。如果在交易方法裡直接發，萬一後面的步驟失敗還原了，客戶已經收到「轉帳成功」的簡訊。比較好的做法是發布一個事件，讓監聽器等交易有結果再處理。參考文件：用 @TransactionalEventListener 時，「監聽器預設綁在交易的提交階段」；可選的階段有 BEFORE_COMMIT、AFTER_COMMIT（預設）、AFTER_ROLLBACK、AFTER_COMPLETION（提交或還原都算）；而且「如果沒有交易在跑，監聽器根本不會被呼叫」，除非把 fallbackExecution 設成 true。出處

    @Transactional
    public void transfer(boolean fail) {
        db.transfer("轉帳 1000");
        events.publishEvent(new TransferDone("轉帳 1000"));   // 在交易中發布事件
        System.out.println("    發布事件之後、方法結束之前");
        if (fail) throw new IllegalStateException("餘額不足");
    }
@Component
public class Notifier {
    @EventListener                                   // 一般監聽器：發布當下就執行
    public void onEvent(TransferDone e) {
        System.out.println("    @EventListener 收到：" + e.note());
    }

    @TransactionalEventListener                      // 預設 AFTER_COMMIT：提交成功後才執行
    public void afterCommit(TransferDone e) {
        System.out.println("    AFTER_COMMIT 收到：發簡訊通知「" + e.note() + "」");
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
    public void afterRollback(TransferDone e) {
        System.out.println("    AFTER_ROLLBACK 收到：" + e.note() + " 沒有成功");
    }
}

執行結果：

提交成功
    @EventListener 收到：轉帳 1000
    發布事件之後、方法結束之前
    AFTER_COMMIT 收到：發簡訊通知「轉帳 1000」
    例外：沒有例外；transfer_record 1 筆 [轉帳 1000]、audit_log 0 筆
還原
    @EventListener 收到：轉帳 1000
    發布事件之後、方法結束之前
    AFTER_ROLLBACK 收到：轉帳 1000 沒有成功
    例外：IllegalStateException；transfer_record 0 筆 []、audit_log 0 筆

還原那次，@EventListener 還是收到了事件（它在發布當下就執行），AFTER_COMMIT 則沒有執行。所以「提交後才能做」的事（發通知、送訊息到外部系統）要用 AFTER_COMMIT。在 AFTER_COMMIT 裡要再寫資料庫時要小心：TransactionSynchronization.afterCommit 的 API 文件說，這時交易已經提交，但交易資源可能還開著，「這個時間點觸發的任何資料存取程式碼仍然會『參與』原本的交易……（之後不會再有提交！）」（any data access code triggered at this point will still "participate" in the original transaction……(with no commit following anymore!)），所以「從這裡呼叫的任何交易操作都要用 PROPAGATION_REQUIRES_NEW」。出處 沒另開交易的寫入，等於加入一筆已經提交、不會再提交的交易。

交易方法裡發布事件，之後方法丟例外還原。哪個監聽器不會執行？

  • @EventListener
  • @TransactionalEventListener(phase = AFTER_ROLLBACK)
  • @TransactionalEventListener(phase = AFTER_COMPLETION)
  • @TransactionalEventListener（預設 AFTER_COMMIT）

AFTER_COMMIT 只在提交成功後跑。@EventListener 在發布當下已經跑過；AFTER_ROLLBACK 與 AFTER_COMPLETION 都會在還原後執行。

轉帳成功後要發簡訊給客戶。監聽器該用哪個？

  • @EventListener，發布當下就送
  • @TransactionalEventListener，預設的 AFTER_COMMIT
  • @TransactionalEventListener(phase = BEFORE_COMMIT)
  • 直接在交易方法最後一行發簡訊

提交成功才發，才不會發生「簡訊說成功、資料卻還原」。BEFORE_COMMIT 與交易方法裡直接發，都還不確定會不會提交。

在沒有交易的方法裡發布事件，@TransactionalEventListener（沒設 fallbackExecution）會怎樣？

  • 立刻執行
  • 等下一筆交易提交時執行
  • 不會被呼叫
  • 丟出 IllegalTransactionStateException

參考文件：If no transaction is running, the listener is not invoked at all。實跑時只有 @EventListener 收到。要它照樣執行得設 fallbackExecution = true。

JPA 的寫入，錯誤可能到提交才出現

交易與 JPA：兩件跟交易有關的事

用 JPA 時，save 不一定馬上送出 SQL：持久化環境（persistence context，JPA 在記憶體裡替你記住這筆交易讀過、改過的物件）先把變更記著，等 flush（把記住的變更寫回資料庫）時才送出；預設的 AUTO 模式會在「提交交易之前」flush。出處 flush 的其他時機、主鍵產生方式的影響、N+1 這類效能問題，在〈JPA 效能：N+1、延遲載入與批次〉。這裡只講兩件跟交易邊界有關的事：

    @Transactional
    public void duplicate() {
        accounts.save(new Account("001-1"));                    // 這個帳號已經存在
        System.out.println("  save 正常回來了，方法也準備結束");
    }

    @Transactional
    public void duplicateWithFlush() {
        accounts.saveAndFlush(new Account("001-1"));
        System.out.println("  （這行不會印出來）");
    }

    @Transactional(propagation = Propagation.NESTED)
    public void nested() {
        accounts.save(new Account("002-2"));
    }

執行結果（H2、JPA 交易管理器 JpaTransactionManager，帳號欄位設成不能重複）：

== 帳號重複，用 save
  save 正常回來了，方法也準備結束
  結果：DataIntegrityViolationException
== 帳號重複，用 saveAndFlush
  結果：DataIntegrityViolationException
== JPA 交易管理器下的 NESTED
  結果：NestedTransactionNotSupportedException：Transaction manager does not allow nested transactions by default - specify 'nestedTransactionAllowed' property with value 'true'
  • 違反唯一限制的錯誤，用 save 時到提交才出現：方法裡的「save 正常回來了」有印出來，例外是在方法結束、攔截器提交時才丟，方法裡的 try／catch 接不到。想在方法裡就知道，用 saveAndFlush，它「儲存實體，並且立刻 flush 變更」（Saves an entity and flushes changes instantly.）。出處
  • JPA 交易管理器預設不支援 NESTED：JpaTransactionManager 的文件說它雖然能用 JDBC 儲存點做巢狀交易，但「nestedTransactionAllowed 預設是 false，因為巢狀交易只作用在 JDBC 連線，不作用在 JPA 的 EntityManager 與它快取的實體物件」。出處 實跑丟出的就是 NestedTransactionNotSupportedException。JPA 專案要「失敗也留下紀錄」，用 REQUIRES_NEW。

帳號欄位有唯一限制，交易方法裡用 save 存一個重複的帳號，並用 try／catch 包住 save。例外會在哪裡出現？

  • save 那一行，catch 接得到
  • 不會出現，重複的資料會被忽略
  • 下一次查詢時
  • 提交時，方法裡的 catch 接不到

實跑時「save 正常回來了」有印出來，DataIntegrityViolationException 在方法結束、攔截器提交時才丟。要在方法裡處理，用 saveAndFlush。

JPA 專案（JpaTransactionManager 預設設定）裡，內層用 Propagation.NESTED 會怎樣？

  • 跟 JDBC 一樣設儲存點
  • 自動改成 REQUIRES_NEW
  • 丟出 NestedTransactionNotSupportedException
  • 自動改成 REQUIRED

JpaTransactionManager 的 nestedTransactionAllowed 預設 false，因為儲存點只管得到 JDBC 連線，管不到 EntityManager 快取的物件。實跑就是這個例外。

重點整理

  • @Transactional 靠代理加交易攔截器運作，交易（連線）綁在目前的執行緒上；好幾個邏輯範圍可以共用一筆實體交易。
  • 七種傳播：REQUIRED（預設，有就加入、沒有就開）、REQUIRES_NEW（暫停外層另開）、NESTED（外層裡設儲存點）、SUPPORTS、MANDATORY（沒有就丟例外）、NOT_SUPPORTED（暫停外層不用交易）、NEVER（有就丟例外）。
  • REQUIRED 內層丟例外、外層吞掉 → UnexpectedRollbackException 整筆還原；REQUIRES_NEW 多一條連線、各自提交，外層失敗留得住；NESTED 只對 JDBC 有效，外層失敗一起還原。
  • 預設只有 RuntimeException 與 Error 還原，受檢例外提交；用 rollbackFor／noRollbackFor 調整，6.2 起可全域 rollbackOn。
  • isolation 預設用資料庫的（MySQL 是 REPEATABLE_READ）；isolation 與 readOnly 只在開新交易時生效；readOnly 只是提示，擋不擋寫入看資料庫與驅動。
  • 失效：自我呼叫、private（6.0 起 protected 與套件可見可以）、自己 new、例外被吞、另開執行緒。
  • 提交後才做的事用 @TransactionalEventListener（預設 AFTER_COMMIT，沒有交易時不執行）；JPA 的 save 要到 flush 才送 SQL，違反限制的錯誤可能到提交才出現，用 saveAndFlush 提早。
