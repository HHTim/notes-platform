一個下游變慢，整串一起倒

為什麼要韌性模式，以及實驗環境

〈Maven、微服務與全域例外〉講過：拆成微服務不等於故障自動隔離，要另外做逾時、重試上限、斷路器與降級。Google 的 SRE 書把不做的後果叫連鎖故障（cascading failure）：「因為正回饋而隨時間擴大的故障」，系統的一部分出事，「讓其他部分出事的機率跟著升高」（A cascading failure is a failure that grows over time as a result of positive feedback. It can occur when a portion of an overall system fails, increasing the probability that other portions of the system fail.）。出處

以下用 Resilience4j 把這幾種保護一個一個開起來看。

實驗環境

專案用 Spring Boot 4.1.1（Spring Framework 7.0.9）、Java 21 與 resilience4j-spring-boot4 2.4.0。Resilience4j 從 2.4.0 起才有 Spring Boot 4 的模組，發佈說明寫「新增對 Spring Boot 4／Spring Cloud 5 的支援」（Add support for Spring Boot 4 / Spring Cloud 5）出處；這個模組的說明檔把詳細用法指向 Spring Boot 2&3 那份使用指南（For detailed documentation look at our Usage Guide）出處，所以下面引的設定文件都出自那一頁。那一頁寫模組「預期執行時已經有 actuator 與 aop 兩個 starter」（The module expects that org.springframework.boot:spring-boot-starter-actuator and org.springframework.boot:spring-boot-starter-aop are already provided at runtime.）出處；Spring Boot 4 把 AOP 的 starter 改名為 spring-boot-starter-aspectj，Web MVC 與 RestClient 也各有自己的 starter（遷移指南的對照表：AspectJ spring-boot-starter-aspectj、Spring Web MVC spring-boot-starter-webmvc、Spring’s Imperative RestClient and RestTemplate spring-boot-starter-restclient）出處。實驗的 pom.xml：

下游是同一個程式裡一支故意會壞的「核心帳務」API，用一個開關決定它正常、回 500、回 400 或變慢；呼叫端用 RestClient 真的走 HTTP 去打它（4xx 會丟 HttpClientErrorException，5xx 丟 HttpServerErrorException）：

@RestController
public class Downstream {
    static volatile String mode = "OK";
    static volatile long delayMs = 0;

    @GetMapping("/core/balance")
    ResponseEntity<String> balance() throws InterruptedException {
        // （實驗程式在這裡印「下游收到第 n 次請求」）
        if (delayMs > 0) Thread.sleep(delayMs);
        return switch (mode) {
            case "FAIL" -> ResponseEntity.status(500).body("core down");
            case "BAD" -> ResponseEntity.status(400).body("bad account");
            default -> ResponseEntity.ok("1000");
        };
    }
}

輸出每行開頭是從實驗開始算起的毫秒數，每次跑會差幾毫秒，順序與次數不變。

連鎖故障＝一處出事讓別處更容易出事；韌性模式的工作，是讓下游的壞停在下游

核心帳務每筆變成要 10 秒，餘額服務呼叫它時沒有設任何逾時與斷路器。最先撐不住的通常是什麼？

  • 餘額服務的執行緒，全卡在等回覆
  • 核心帳務的資料庫，因為寫入變多
  • 網銀前台的瀏覽器，因為畫面太大
  • 沒有東西會撐不住，只是每筆慢一點

每個等待中的請求都占著一條執行緒。下游慢了，呼叫端的執行緒越積越多，自己也回不了新請求，接著再往上傳，就是連鎖故障。慢不會「只是慢一點」，它會占住資源。

在 Spring Boot 4 用 Resilience4j 的註解，下面哪一個相依套件不加也可以？

  • spring-boot-starter-aspectj
  • spring-boot-starter-actuator
  • resilience4j-spring-boot4
  • micrometer-registry-prometheus

使用指南寫這個模組預期執行時已經有 actuator 與 aop 兩個 starter，aop 那個在 Spring Boot 4 叫 spring-boot-starter-aspectj。Prometheus 那個只有要從 /actuator/prometheus 拿指標時才需要。

實驗裡的下游回 HTTP 400。RestClient 的 retrieve() 會丟出哪一類例外？

  • HttpServerErrorException
  • HttpClientErrorException
  • CallNotPermittedException
  • 不丟例外，回傳 null

4xx 是用戶端錯誤，丟 HttpClientErrorException；5xx 才是 HttpServerErrorException。CallNotPermittedException 是斷路器擋下呼叫時丟的，跟 HTTP 無關。後面重試要靠這個差別決定「哪些錯值得再試」。

斷路器：從實驗紀錄看三態怎麼切換

Resilience4j 文件：斷路器是「有限狀態機，有三個正常狀態 CLOSED、OPEN、HALF_OPEN」，並「用滑動視窗儲存並彙總呼叫結果」（The CircuitBreaker is implemented via a finite state machine with three normal states: CLOSED, OPEN and HALF_OPEN … The CircuitBreaker uses a sliding window to store and aggregate the outcome of calls.）。出處 實驗把參數調得很小，才看得到每一步：

resilience4j.circuitbreaker:
  instances:
    core:
      registerHealthIndicator: true
      slidingWindowType: COUNT_BASED          # 看最近 N 次
      slidingWindowSize: 5                    # N = 5
      minimumNumberOfCalls: 5                 # 記滿 5 次才開始算失敗率
      failureRateThreshold: 50                # 失敗率 ≥ 50% 就跳開
      waitDurationInOpenState: 2s             # 跳開後等 2 秒才試探
      permittedNumberOfCallsInHalfOpenState: 2  # 試探時放 2 次

被保護的方法加 @CircuitBreaker，名字對到上面的 core；兩個降級回呼（fallback）下一段細講：

@Service
public class BalanceService {
    private final CoreClient core;
    BalanceService(CoreClient core) { this.core = core; }

    @CircuitBreaker(name = "core", fallbackMethod = "balanceFallback")
    public String balance(String account) {
        return core.balance();
    }
    // 斷路器擋下來（OPEN、或半開名額用完）時：回快取
    private String balanceFallback(String account, CallNotPermittedException e) {
        return "快取餘額";
    }
    // 其他例外（例如下游回 500）：回「暫時查不到」
    private String balanceFallback(String account, Exception e) {
        return "暫時查不到（" + e.getClass().getSimpleName() + "）";
    }
}

逐段對照文件：

  • 第 1〜4 次，失敗率是 -1。失敗率「要記錄到最少呼叫數之後才能計算」，文件的例子是最少 10 次時「只評估了 9 次，就算 9 次全失敗也不會跳開」（If only 9 calls have been evaluated the CircuitBreaker will not trip open even if all 9 calls have failed.）。出處 實驗的第 4 次已經 2 敗 2 成、剛好 50%，但才記 4 次，不算。
  • 第 5 次跳開。「失敗率大於或等於門檻時，從 CLOSED 變成 OPEN」（The state of the CircuitBreaker changes from CLOSED to OPEN when the failure rate is equal or greater than a configurable threshold.）。5 次裡 3 次失敗是 60%，大於 50%。注意第 5 次本身是正常打到下游、失敗之後才跳開的，所以它拿到的是 500 那條回呼。
  • 第 6、7 次被擋。「OPEN 時用 CallNotPermittedException 拒絕呼叫」（The CircuitBreaker rejects calls with a CallNotPermittedException when it is OPEN.）。下游的請求計數停在 5，這兩次根本沒送出去，這就是斷路器替下游減壓的方式。出處
  • OPEN → HALF_OPEN 發生在第 8 次呼叫的那一刻（2210 毫秒），不是剛好滿 2 秒時。automaticTransitionFromOpenToHalfOpenEnabled 預設 false，文件：這時「就算過了 waitDurationInOpenState，也要有呼叫進來才會轉成 HALF_OPEN」（if set to false the transition to HALF_OPEN only happens if a call is made, even after waitDurationInOpenState is passed.）；設成 true 會多一條執行緒定時去轉。出處
  • 半開放行 2 次，都成功就回 CLOSED，而且「記了 0 次」：回到 CLOSED 時滑動視窗重新開始記。半開時「其餘的呼叫照樣用 CallNotPermittedException 拒絕，直到放行的呼叫都完成」；放行的跑完後，「失敗率或慢呼叫比例仍大於等於門檻就退回 OPEN；都低於門檻就回 CLOSED」（If the failure rate or slow call rate is then equal or greater than the configured threshold, the state changes back to OPEN. 計數型視窗看「最近 N 次」，時間型（TIME_BASED）看「最近 N 秒」，文件說兩種都把結果先彙總好，所以讀取快照是 O(1)。視窗大小也不是同時呼叫的上限：「20 條執行緒同時要求執行時，只要狀態是 CLOSED，全部都會放行，就算滑動視窗大小是 15」，要限制同時在跑的數量得用隔艙。出處

CLOSED 記帳（記滿最少次數才算）→ 失敗率 ≥ 門檻跳 OPEN（直接擋）→ 等滿時間、下一次呼叫時轉 HALF_OPEN → 放行那幾次的比例決定回 CLOSED 或退回 OPEN

實驗的設定是 minimumNumberOfCalls: 5、門檻 50%。第 4 次呼叫後已經 2 次失敗、2 次成功，為什麼還是 CLOSED？

  • 因為 50% 要「大於」門檻才會跳開
  • 因為最近一次是失敗，要等成功才算
  • 只記了 4 次，還沒到最少呼叫數
  • 因為失敗是 500，不算在失敗率裡

失敗率要記到 minimumNumberOfCalls 才計算，之前一律是 -1。門檻的規則是「大於或等於」，所以如果最少次數是 4，50% 就會跳開。預設所有例外都算失敗，500 也算。

同樣的設定（視窗 5、最少 5 次、門檻 50%），依序是 成功、失敗、成功、失敗、成功。第 5 次呼叫後斷路器是什麼狀態？

  • OPEN，因為已經有 2 次失敗
  • HALF_OPEN，因為成功與失敗交錯出現
  • 還不能判斷，失敗率是 -1
  • CLOSED，失敗率 40% 低於門檻

記滿 5 次，2 次失敗是 40%，小於 50%，維持 CLOSED。HALF_OPEN 只會從 OPEN 等滿時間後進入，不會從 CLOSED 直接進去。

斷路器跳開後的第 6、7 次呼叫，下游收到幾次請求？

  • 2 次，斷路器只是把結果換成回呼
  • 1 次，第 6 次送出去試探
  • 0 次，在斷路器這層就被擋下
  • 4 次，被擋的呼叫會自動重送兩次

實驗裡下游的計數停在 5，跳開之後要到第 8 次（半開）才收到第 6 次請求。OPEN 時呼叫在斷路器這一層就被 CallNotPermittedException 擋下，根本不會送出去。

第 5 次呼叫打到下游、拿到 500，斷路器也在這次跳開。這一次呼叫拿到的回呼結果是哪一個？

  • 快取餘額（CallNotPermittedException 那條）
  • 暫時查不到（InternalServerError）
  • 拿不到回呼，跳開那次的例外直接丟給呼叫端
  • 1000，跳開的那一次會改回上一次的成功值

第 5 次是真的送到下游、拿到 500 之後才記帳、才跳開，所以傳給回呼的例外是 InternalServerError，對到參數型別是 Exception 的那一個。要等第 6 次才會拿到 CallNotPermittedException、走「快取餘額」。

waitDurationInOpenState 是 2 秒，沒有開 automaticTransitionFromOpenToHalfOpenEnabled。跳開後 10 秒內都沒有任何呼叫，第 10 秒時斷路器是什麼狀態？

  • 還是 OPEN，要有呼叫進來才轉
  • HALF_OPEN，2 秒一到就自己轉過去
  • CLOSED，閒置太久會自動重置
  • DISABLED，沒有呼叫就停用

這個開關預設 false，文件寫此時「就算過了 waitDurationInOpenState，也要有呼叫進來才會轉成 HALF_OPEN」。實驗裡的轉換時間點 2210 毫秒，正是第 8 次呼叫進來的那一刻。

半開放行 2 次（permittedNumberOfCallsInHalfOpenState: 2），第 1 次失敗、第 2 次成功。之後斷路器會怎樣？

  • 回 CLOSED，因為最後一次成功了
  • 維持 HALF_OPEN，再放行 2 次
  • 第 1 次失敗時就立刻退回 OPEN
  • 退回 OPEN，失敗率 50% 達到門檻

放行的兩次跑完才計算：1 敗 1 成是 50%，「大於或等於」門檻 50%，退回 OPEN（實跑這個順序，第 2 次成功拿到 1000 之後狀態就變 OPEN）。第 1 次失敗時失敗率還是 -1，不會立刻退回；「任一失敗就退回」是 Azure 的通用描述，不是 Resilience4j 的算法。

半開放行 2 次，這兩次都還在等下游回覆時，第 3 個呼叫進來了。它會怎樣？

  • 也放行，半開時放行數量只是建議值
  • 排隊等前兩次跑完，再補送出去
  • 直接把斷路器退回 OPEN，重新計時
  • 被擋下，跟 OPEN 時一樣

文件：半開時放行設定的數量，其餘的呼叫照樣用 CallNotPermittedException 拒絕，直到放行的呼叫都完成。所以這個呼叫會走「快取餘額」那條回呼。

半開的兩次都成功，回到 CLOSED。這時 getMetrics().getNumberOfBufferedCalls() 是多少？

  • 7，從頭累計
  • 5，保留跳開前的視窗
  • 2，保留半開的那兩次
  • 0，視窗重記

實驗最後一行印「記了 0 次」：回到 CLOSED 時滑動視窗從頭開始記，跳開前的 3 次失敗不會再拖累新的判斷。

斷路器設 slidingWindowSize: 15，正處於 CLOSED。這時 20 條執行緒同時呼叫，會放行幾條？

  • 15 條，視窗大小就是同時呼叫的上限
  • 10 條，另一半等前面完成
  • 20 條全部放行，視窗不管並行
  • 0 條，超過視窗大小就跳開

文件的例子：CLOSED 時 20 條執行緒同時要求執行，就算視窗大小是 15 也全部放行。視窗只管「記最近幾次的結果」，要限制同時在跑的數量得用隔艙。

把 slidingWindowType 改成 TIME_BASED、slidingWindowSize: 10。失敗率改成怎麼算？

  • 看最近 10 秒內的所有呼叫
  • 每 10 次呼叫結算一次，結算完清空
  • 看最近 10 次呼叫，跟計數型一樣
  • 看最近 10 分鐘，單位固定是分鐘

文件：計數型彙總最近 N 次呼叫，時間型彙總最近 N 秒的呼叫。兩種都是連續滑動的，不是滿一批就清空。

沒失敗，但太慢

慢呼叫：成功了也會被算進去

下游沒有報錯、只是變慢，對呼叫端一樣傷。文件：斷路器在「慢呼叫的比例大於或等於門檻時」也會跳開，用意是「在外部系統真的沒有回應之前，先減輕它的負擔」（This helps to reduce the load on an external system before it is actually unresponsive.）。出處 兩個參數：slowCallDurationThreshold 定義多久算慢（預設 60 秒），slowCallRateThreshold 是慢呼叫比例的門檻（預設 100%，也就是全部都慢才跳）。

resilience4j.circuitbreaker:
  instances:
    coreSlow:
      slidingWindowSize: 4
      minimumNumberOfCalls: 4
      slowCallDurationThreshold: 300ms        # 超過 300 毫秒算慢
      slowCallRateThreshold: 50               # 慢的占一半以上就跳開

記不記成失敗、降級回呼與自我呼叫

哪些例外算失敗

文件：「預設所有例外都算失敗」；可以列 recordExceptions 指定哪些算失敗，「那麼其他例外都算成功，除非被忽略」；ignoreExceptions 列的「既不算失敗也不算成功」（By default all exceptions count as a failure. … Exceptions can also be ignored so that they neither count as a failure nor success.）。出處 實務上要想清楚：帳號打錯（400）、餘額不足這類「下游正確地拒絕了」的情況，記成失敗會讓斷路器把好端端的下游擋掉，通常該列進 ignoreExceptions（例子見〈微服務與架構面試題：服務發現、韌性、可觀測性與十二要素〉）。

降級回呼（fallback）

文件把回呼比成 try／catch：「設了回呼方法，每個例外都會轉給回呼方法的執行器，它找出最符合、能處理這個例外的回呼方法，類似 catch 區塊」，而且「回呼的執行跟斷路器目前的狀態無關」（The fallback is executed independently of the current state of the circuit breaker.）。簽名的規則：「回呼方法要放在同一個類別，方法簽名要一樣，只多一個目標例外參數」；有好幾個時，「呼叫最接近的那一個」（the method that has the most closest match will be invoked）。文件另外允許一種「全域回呼」：好幾個方法回傳型別相同時，可以共用一個只收例外參數的回呼（You can define one global fallback method with an exception parameter only if multiple methods has the same return type）；實跑 String onlyEx(Exception e) 確實接得到。出處

對照實驗輸出：CLOSED 時下游回 500，進的是參數為 Exception 的那個（暫時查不到）；OPEN 時被擋，例外是 CallNotPermittedException，兩個回呼都接得住，選比較接近的那個（快取餘額）。降級要回什麼是業務決定：Azure 的建議是應用程式可以「暫時降低功能、改用替代的操作」（an application might temporarily degrade its functionality, invoke an alternative operation）。出處 餘額這種會影響決策的資料，回快取時畫面上要標「資料時間」。

隔艙與限流：名額與速率

隔艙（bulkhead）的名字來自船體的分艙：Azure 寫「船身破了，只有受損的那一艙進水，船不會沉」（If the hull of a ship is compromised, only the damaged section fills with water, which prevents the ship from sinking.）。出處 Resilience4j 的 SemaphoreBulkhead 限制「同時在跑的數量」：maxConcurrentCalls（預設 25）與 maxWaitDuration（預設 0，滿了時最多等多久）；另有 FixedThreadPoolBulkhead「用有界佇列與固定大小的執行緒池」。出處

resilience4j.bulkhead:
  instances:
    coreBulk:
      maxConcurrentCalls: 2
      maxWaitDuration: 0

下游每筆 500 毫秒，4 條執行緒每隔 20 毫秒各叫一次：

   68 ms  下游收到第 1 次請求（OK）
   68 ms  下游收到第 2 次請求（OK）

  569 ms  下游第 1 次處理完
  573 ms  下游第 2 次處理完
  583 ms  呼叫 2 → 1000
  583 ms  呼叫 1 → 1000

前兩個拿到名額，第 3、4 個在名額用完時進來，maxWaitDuration 是 0，當場丟 BulkheadFullException，連下游都沒碰到。每個下游各配一個隔艙，核心帳務卡住，最多只占兩條執行緒，其他功能照常。

限流器（RateLimiter）管的是速率：文件說它把時間切成一個個週期，「每個週期開始時，把可用的許可數設回 limitForPeriod」（At the start of each cycle, the RateLimiter sets the number of active permissions to RateLimiterConfig.limitForPeriod.）；timeoutDuration 是拿不到許可時最多等多久（預設 5 秒）。出處

    coreRl:
      limitForPeriod: 3                       # 每個週期 3 個許可

   96 ms  第 2 次 → 1000
   99 ms  第 3 次 → 1000

呼叫一個接一個、每次都很快完成，所以隔艙不會擋；但限流器只看「這個週期用了幾個」，第 4、5 次照樣被擋。保護下游的配額（例如對方規定每秒最多 3 筆）用限流器；保護自己的執行緒用隔艙。Gateway 層的限流演算法與 429 回應見〈系統設計：秒殺與限流〉。

隔艙＝同時在跑的上限（BulkheadFullException）；限流＝每個週期的許可數（RequestNotPermitted）；一個擋並行、一個擋速率

隔艙 maxConcurrentCalls: 2、maxWaitDuration: 0，下游每筆 500 毫秒。4 個呼叫幾乎同時進來，結果是？

  • 2 個成功，2 個丟 BulkheadFullException
  • 4 個都成功，只是後兩個晚 500 毫秒
  • 2 個成功，2 個丟 RequestNotPermitted
  • 1 個成功，其他 3 個被擋

名額 2 個、等待時間 0，第 3、4 個進來時名額用完，當場丟 BulkheadFullException。要排隊等就把 maxWaitDuration 設大於 0。RequestNotPermitted 是限流器丟的。

同樣的隔艙，如果 4 個呼叫是一個做完才叫下一個（每個 500 毫秒）。會有幾個被擋？

  • 2 個，名額只有 2
  • 1 個，最後一個
  • 0 個，同時只有一個在跑
  • 3 個，只有第一個拿得到名額

隔艙限制的是「同時在跑」的數量。一次只有一個在跑，從來沒超過 2，全部放行。總共幾次、多快不是它管的。

限流器 limitForPeriod: 3、limitRefreshPeriod: 1s、timeoutDuration: 0。同一秒內連續叫 5 次（每次都很快完成），結果是？

  • 5 次都成功，因為每次都很快做完
  • 前 3 次成功，後 2 次等下一秒自動送出
  • 前 3 次成功，後 2 次被擋
  • 全部失敗，超過上限就整批拒絕

限流器只看這個週期用掉幾個許可，跟每次多快做完無關。timeoutDuration 是 0，拿不到就立刻失敗；設大於 0 才會等下一個週期。實驗的第 4、5 次就是這樣被擋。

合作的徵信公司規定「每秒最多呼叫 10 次，超過就停權」。該用哪一個保護？

  • 隔艙，maxConcurrentCalls: 10，同時最多 10 個
  • 斷路器，failureRateThreshold: 10
  • 重試，maxAttempts: 10
  • 限流器，每秒 10 個許可，超過就擋

規定的是速率（每秒幾次），用限流器。隔艙限的是同時在跑的數量，呼叫很快時一秒可以遠超過 10 次；斷路器和重試都不管次數上限。

斷路器、隔艙、限流器擋下呼叫時，分別丟出哪個例外？

  • 都是 CallNotPermittedException
  • BulkheadFullException、CallNotPermittedException、RequestNotPermitted
  • CallNotPermittedException、BulkheadFullException、RequestNotPermitted
  • CallNotPermittedException、RequestNotPermitted、BulkheadFullException

實驗輸出：斷路器 OPEN 時是 CallNotPermittedException，隔艙滿了是 BulkheadFullException，限流器沒許可是 RequestNotPermitted。回呼方法可以各寫一個，對到不同的降級。

逾時：TimeLimiter 與真正停下來的地方

TimeLimiter 包的是 CompletionStage 或 Future，設逾時時間與「要不要對執行中的 future 呼叫 cancel」。出處 原始碼的預設是 1 秒、取消（timeoutDuration = Duration.ofSeconds(1)、cancelRunningFuture = true）。出處

resilience4j.timelimiter:
  instances:
    coreTl:
      timeoutDuration: 500ms
      cancelRunningFuture: true
@TimeLimiter(name = "coreTl")
public CompletableFuture<String> balanceAsync(String account) {
    return CompletableFuture.supplyAsync(core::balance, pool);   // pool 是自己建的執行緒池
}

下游這次每筆要 1.5 秒：

   47 ms  下游收到第 1 次請求（OK）
  510 ms  呼叫端拿到 TimeoutException
 1549 ms  下游第 1 次處理完

呼叫端在 500 毫秒準時拿到 TimeoutException，但下游照樣做到 1.5 秒才完成，送出去的 HTTP 請求沒有被停下來。原因在 JDK 文件：CompletableFuture「對完成它的那段運算沒有直接的控制權，取消只是另一種例外完成」，cancel 的參數「沒有作用，因為這個實作不用中斷來控制處理」（this value has no effect in this implementation because interrupts are not used to control processing.）。出處 所以 TimeLimiter 保護的是「呼叫端別再等」；要讓連線真的斷掉、釋放 pool 裡那條執行緒，HTTP 用戶端自己要設連線逾時與讀取逾時。

逾時設多長，SRE 書的說法是兩邊都有代價：「不設或設得極長，早就過去的短暫問題會一直占著伺服器資源」，太短則「比較花時間的請求會一直失敗」（Short deadlines can cause some more expensive requests to fail consistently.）。出處 一般做法是看下游正常時的延遲分布（例如 99% 的請求多久內回來），再留一點餘裕。

TimeLimiter 讓呼叫端準時放棄；底層的 HTTP 呼叫要靠用戶端自己的逾時才會真的停

TimeLimiter 設 500 毫秒、cancelRunningFuture: true，下游要 1.5 秒。下游那邊會怎樣？

  • 500 毫秒時收到取消，停止處理
  • 照樣做完，1.5 秒時處理完
  • 500 毫秒時連線被切斷，下游丟例外
  • 根本不會收到請求

實驗裡呼叫端 510 毫秒拿到 TimeoutException，下游 1549 毫秒照樣處理完。CompletableFuture 的 cancel 不中斷執行中的運算，送出去的 HTTP 請求不受影響。

@TimeLimiter 可以直接加在回傳 String 的同步方法上嗎？

  • 不行，同步方法一呼叫就丟例外
  • 可以，它會自動改成在另一條執行緒執行
  • 可以，但逾時時間會被忽略，照樣等完
  • 可以，同步方法的逾時一律 1 秒

文件：TimeLimiter 裝飾 CompletionStage 或 Future 來限制執行時間。實跑在回傳 String 的方法上加 @TimeLimiter，一呼叫就丟 IllegalReturnTypeException，訊息寫 CompletionStage expected。同步呼叫要有終點，靠的是 HTTP 用戶端自己的連線逾時與讀取逾時。

為什麼逾時不能「設長一點比較保險」？

  • 逾時太長，斷路器的失敗率會算錯
  • 卡住的呼叫一直占著執行緒與連線
  • 逾時太長，下游會拒絕新的連線
  • 逾時太長，重試次數會自動變少

SRE 書：不設或設得極長，早就過去的問題會一直消耗資源。每個等待中的呼叫都占著資源，逾時越長，下游一慢，呼叫端被拖垮得越快。

用 resilience4j-spring-boot4 2.4.0、開了 health.circuitbreakers.enabled，沒設 allowHealthIndicatorToFail。斷路器 OPEN 時，/actuator/health 最上層的 status 是？

  • DOWN，因為有斷路器跳開
  • CIRCUIT_OPEN，直接沿用斷路器的狀態
  • OUT_OF_SERVICE，整個實例暫停收流量
  • UP，斷路器那項顯示 CIRCUIT_OPEN

實跑結果：core 是 CIRCUIT_OPEN、circuitBreakers 這一組是 UNKNOWN，最上層還是 UP，HTTP 200。原始碼只有 allowHealthIndicatorToFail 為 true 時才給 DOWN。文件那句「OPEN 時狀態是 DOWN」跟這版的行為不同。

打開 allowHealthIndicatorToFail 之後，斷路器 OPEN 時有人把 /actuator/health 接進 Kubernetes 的存活探針。下游核心帳務一掛，會發生什麼事？

  • 沒影響，存活探針只看 HTTP 200
  • 只有一個 Pod 會被重啟
  • 斷路器會被 Kubernetes 自動重置
  • health 回 503，所有實例可能被一起重啟

每個實例都在呼叫同一個壞掉的下游，斷路器都跳開，health 都回 503，存活探針就把它們全部重啟，重啟也修不好下游。存活探針不應依賴外部系統。

斷路器記了 5 次失敗、擋下 2 次。resilience4j.circuitbreaker.calls 加上 tag=name:core 的 COUNT 是多少？

  • 7，所有呼叫都算
  • 5，只算真的執行過的
  • 2，只算被擋的
  • 0，OPEN 時不記指標

這個指標只算真的執行過的呼叫（kind 有 successful、failed、ignored）。被擋的另外記在 resilience4j_circuitbreaker_not_permitted_calls_total，實跑是 2。

要寫一條 Prometheus 告警：「core 的斷路器跳開超過 5 分鐘就通知」。該看哪個指標？

  • resilience4j_circuitbreaker_state 的 state="open" 等於 1
  • resilience4j_circuitbreaker_failure_rate 大於 50
  • resilience4j_circuitbreaker_calls_seconds_count 停止增加
  • resilience4j_circuitbreaker_not_permitted_calls_total 大於 0

state 指標每種狀態一條，當下那種是 1，最直接對應「跳開了」。失敗率超過門檻不代表還開著（可能已經回到 CLOSED 重新計算）；被擋次數大於 0 只說明曾經擋過。

重點整理

  • 連鎖故障：一處出事讓別處更容易出事；逾時、斷路器、隔艙、重試上限、降級，是讓下游的壞停在下游的幾道閘門。
  • 斷路器：CLOSED 記帳，記滿 minimumNumberOfCalls 才算失敗率，≥ 門檻跳 OPEN；OPEN 直接丟 CallNotPermittedException、下游收不到；等滿 waitDurationInOpenState 後下一次呼叫轉 HALF_OPEN；放行那幾次跑完，用比例決定回 CLOSED 或退回 OPEN。慢呼叫比例達門檻一樣跳開。
  • 預設所有例外都算失敗；列了 recordExceptions，沒列的都算成功；ignoreExceptions 不算成也不算敗。回呼像 catch：同類別、同簽名多一個例外參數、選最接近的，跟斷路器狀態無關。自我呼叫不經過代理，全部失效。
  • 重試：maxAttempts 含第一次；指數退避每次乘倍數（預設 1.5）；抖動在基準值上下隨機；永久性錯誤列 ignoreExceptions；多層重試會相乘；寫入要冪等。
  • 預設順序 Retry 包住 CircuitBreaker：每次嘗試都記一筆；Retry 要忽略 CallNotPermittedException，不然會對著 OPEN 的斷路器空轉。
  • 隔艙擋「同時幾個」（BulkheadFullException），限流擋「一段時間幾個」（RequestNotPermitted）；TimeLimiter 讓呼叫端準時放棄，底層呼叫要靠 HTTP 用戶端自己的逾時才會停。
  • 指標自動發佈到 metrics、prometheus；health 要另外開，2.4.0 預設 OPEN 只顯示 CIRCUIT_OPEN、整體 UP，開 allowHealthIndicatorToFail 才會 DOWN，別接進存活探針。
