表要改，但不能靠運氣

為什麼不能靠 ddl-auto

Spring Data JPA（見〈Spring 資料存取〉）可以用 spring.jpa.hibernate.ddl-auto 讓 Hibernate 依實體類別自己建表。Spring Boot 文件列出可用的值是 none、validate、update、create、create-drop，而且預設值看資料庫而定：用內嵌資料庫（H2 這類）又沒偵測到 Flyway 或 Liquibase 時預設 create-drop，「其他情況預設 none」（In all other cases, it defaults to none.）。出處

Hibernate 自己的文件也說：自動產生結構「對測試與做雛形很有用，但在正式環境，用遞增的遷移腳本管理結構彈性大得多」（Although the automatic schema generation is very useful for testing and prototyping purposes, in a production environment, it's much more flexible to manage the schema using incremental migration scripts.）。出處 銀行的正式資料庫裡，每一次改表都要能審查、能重現、能說得出是哪一版改的，這正是遷移工具（migration tool：把每一次改資料庫結構寫成一支有版本號的腳本、依序執行並記錄的工具）在做的事。Spring Boot 內建支援兩種：Flyway 與 Liquibase（Spring Boot supports two higher-level migration tools: Flyway and Liquibase.）。出處

示範專案的結構全部交給 Flyway，Hibernate 只設 ddl-auto=validate：對不上就不讓應用程式起來。

正式環境：表由遷移腳本建、由遷移工具記錄；Hibernate 只用 validate 核對

Spring Boot 連的是 Docker 裡的 MySQL（不是內嵌資料庫），沒有另外設 ddl-auto。預設值是什麼？

  • create-drop，每次啟動都重建
  • update，自動補上缺的欄位
  • none
  • validate，啟動時核對結構

文件：只有內嵌資料庫而且沒偵測到 Flyway／Liquibase 時才預設 create-drop，其他情況預設 none。

結構交給 Flyway 管之後，spring.jpa.hibernate.ddl-auto 最適合設成哪一個？

  • update，讓 Hibernate 補 Flyway 漏掉的
  • create，確保表一定存在
  • create-drop，測試和正式都一樣
  • validate，只核對不修改

兩個工具同時改結構就分不清是誰改的；validate 只核對，對不上就讓啟動失敗。

實體多了一個欄位 nickname，但沒有寫遷移腳本，ddl-auto=validate。實跑結果是？

  • 啟動失敗，缺 nickname 欄位
  • Hibernate 自動在表上補一個 nickname 欄位
  • 啟動成功，等到存資料時才報錯
  • Flyway 偵測到差異，自動產生補欄位的腳本

實跑訊息：Schema validation: missing column [nickname] in table [account]。validate 只核對、不修改，問題在啟動時就被擋下。

一個資料夾、一張表

Flyway 的兩樣東西：腳本與歷史表

Spring Boot 4 加 spring-boot-starter-flyway；連 MySQL 還要加 flyway-mysql：文件寫內嵌與檔案型資料庫用 starter 就好，「其他情況還需要資料庫專用的模組」，例子就是 MySQL 用 org.flywaydb:flyway-mysql（Other cases require also a database-specific module. … org.flywaydb:flyway-mysql with MySQL.）。腳本預設放在 classpath:db/migration，檔名是「V<版本>__<名稱>.sql」，版本用底線分隔，例如 1 或 2_1（Typically, migrations are scripts in the form V<VERSION>__<NAME>.sql (with <VERSION> an underscore-separated version, such as '1' or '2_1').）。出處

Flyway 文件：版本化腳本「依順序、只套用一次」（Versioned migrations are applied to a target database in order exactly once.），而 flyway_schema_history 表「記錄哪些版本化腳本已經套用過，並存下校驗和，確保它們沒被改過」（tracks which versioned migrations have already been applied and stores the checksum to make sure they haven't changed.）；版本「照數字排序」（Versions are sorted numerically）。出處 校驗和（checksum：把腳本內容算成一個數字，內容改一個字數字就變）是 CRC32（Validate works by storing a checksum (CRC32 for SQL migrations)）。出處

下面哪一個檔名，Flyway 會當成版本 2.1 的版本化腳本？

已經加了 spring-boot-starter-flyway，資料庫是 MySQL。照 Spring Boot 文件，還必須加哪個 Flyway 模組？

  • 不用，starter 已經支援所有資料庫
  • flyway-core，starter 沒有帶
  • flyway-database-postgresql
  • flyway-mysql

文件：starter 只涵蓋內嵌與檔案型資料庫，其他情況要加資料庫專用模組，MySQL 是 org.flywaydb:flyway-mysql。

示範專案把腳本放在專案外的 mig/ 資料夾，啟動時加 --spring.flyway.locations=filesystem:mig。這個屬性的作用是？

  • 指定 flyway_schema_history 要建在哪個 schema
  • 指定去哪裡找遷移腳本
  • 指定 MySQL 存放資料檔的磁碟路徑
  • 只在測試環境有效的除錯開關

文件：預設 classpath:db/migration，可以用 spring.flyway.locations 改成一個或多個 classpath: 或 filesystem: 位置。

第一次對空資料庫啟動，日誌顯示 Schema history table ... does not exist yet。接下來 Flyway 做了什麼？

  • 停止啟動，要求先手動建立歷史表
  • 建歷史表，再依序跑 V1、V2
  • 先跑 V2，再回頭跑 V1
  • 先把兩支腳本跑完，最後才建歷史表

實跑：Creating Schema History table …，接著 Migrating … to version "1 - create account"、"2 - seed accounts"。

flyway_schema_history 的 checksum 欄位是用來做什麼的？

  • 把腳本內容加密，避免外洩
  • 記錄每支腳本執行花了多少毫秒
  • 偵測腳本事後有沒有被改
  • 決定同一版號的腳本誰先執行

Flyway 存下 CRC32 校驗和，每次啟動重算本機檔案的值來比；順序由版本決定。

檔案 V10__add_fee.sql 與 V9__add_rate.sql 都還沒跑過。Flyway 先跑哪一支？

  • V10，因為字串排序 "1" 在 "9" 前面
  • 兩支同時跑
  • 看檔案建立的時間
  • V9，版本照數字排序

文件：Versions are sorted numerically as you would normally expect。9 小於 10。

實跑日誌裡，Hibernate 的 entityManagerFactory 依賴 flywayInitializer。這代表什麼？

  • Flyway 先跑完，Hibernate 才核對
  • Hibernate 會先建表，Flyway 再補上缺的
  • 兩者同時啟動、平行執行
  • Flyway 失敗時改由 Hibernate 接手建表

Spring Boot 讓需要資料庫的元件依賴負責初始化的元件，所以 validate 看到的是遷移後的結構。

已經跑到 V2，什麼都沒改又重啟一次。日誌會出現什麼？

  • V1、V2 會重新執行一次
  • No migration necessary
  • 校驗和錯誤，啟動失敗
  • 刪掉歷史表後重新建立一次

歷史表已經記了 V1、V2，沒有新腳本，就什麼都不做。這也是 migrate 可以每次啟動都跑的原因。

同一次啟動有一支新的 V3 和一支新的 R 腳本，執行順序是？

  • R 先跑，因為字母 R 在 V 前面
  • 兩支同時跑
  • 看檔案大小
  • V3 先，R 最後

文件：repeatable migrations are always applied last, after all pending versioned migrations。實跑日誌也是先 version "3 - add branch"，再 repeatable migration。

把 R__account_summary_view.sql 的 SELECT 多加一個欄位再啟動，會發生什麼？

  • 啟動失敗，因為校驗和不符
  • V1 到 V3 也會跟著重跑一次
  • 什麼都不做，R 只會跑一次
  • R 重跑，歷史表多一筆

可重複腳本的校驗和一變就重跑，不算錯誤。實跑：with repeatable migration "account summary view"，歷史表第 5 筆的 checksum 變成 25797383。

可重複腳本裡建 view，用 CREATE VIEW 而不是 CREATE OR REPLACE VIEW。第二次重跑時最可能怎樣？

  • Flyway 會自動先 DROP
  • 沒差，結果一樣
  • 失敗，因為 view 已經存在
  • 跳過不跑

文件說確保可重複執行是你的責任，通常用 CREATE OR REPLACE。單純 CREATE 在物件已存在時會報錯。

已經跑過的腳本，不能再改

校驗和被改了會怎樣

假設有人覺得 V1 的 owner VARCHAR(50) 太短，直接把已經套用過的 V1 改成 80，然後重啟：

Migration checksum mismatch for migration version 1
-> Applied to database : 490333979
-> Resolved locally    : 64298645
Either revert the changes to the migration, or run repair to update the schema history.

應用程式直接起不來。Spring Boot 的 spring.flyway.validate-on-migrate 預設是 true（Whether to automatically call validate when performing a migration. true）出處，validate 不過就不 migrate。錯誤訊息給了兩條路：

  • 把檔案改回去（revert the changes）：這幾乎永遠是對的。改 V1 不會讓已經存在的表變成 80，正式環境的表還是 50，只是腳本跟實際對不上了。要改長度，新增一支 V 去 ALTER。Flyway 文件的建議就是：已經套用到下游環境的版本化腳本不要改，「最好建立一支新的版本化腳本，往前修」（It's best to create a new versioned migration script and roll forward any necessary changes.）。出處
  • 執行 repair：repair 會「把已套用腳本的校驗和、描述與類型，對齊成目前檔案的版本」（Realign the checksums, descriptions and types of the applied migrations with the ones of the available migrations）。出處 它只改歷史表、不改你的表。只有在「改的內容不影響結果」（例如只改註解、排版）時才適合用。

已套用的版本化腳本不改；要改結構就加一支新的 V；repair 只改歷史表

已經套用到正式環境的 V1 被改了一個字，重啟時 Flyway 怎麼處理？

  • validate 失敗，啟動失敗
  • 自動重跑 V1，把表改成新的樣子
  • 忽略差異，繼續跑新的腳本
  • 自動執行 repair 之後繼續啟動

實跑：Migration checksum mismatch for migration version 1，Applied to database 490333979、Resolved locally 64298645，Spring Boot 啟動失敗。

把已套用的 V1 裡 VARCHAR(50) 改成 VARCHAR(80)，再執行 repair 讓啟動成功。正式環境的 owner 欄位現在是多長？

  • 80，repair 會重跑 V1
  • 還是 50；repair 只改歷史表
  • 80，Flyway 會自動 ALTER
  • 欄位被刪掉重建

repair 只對齊歷史表、不執行腳本：腳本說 80、資料庫是 50，新建的環境會跟正式環境不一樣。

owner 欄位需要從 50 加長到 80，照 Flyway 文件建議該怎麼做？

  • 改 V1，再 repair
  • 直接在正式資料庫下 ALTER，不寫腳本
  • 新增一支版本化腳本去 ALTER
  • 把 V1 刪掉重新編號

文件：It's best to create a new versioned migration script and roll forward any necessary changes。每個環境都照同樣的腳本走到同樣的結果。

什麼情況下用 repair 處理校驗和不符是合理的？

  • 任何情況都可以，repair 很安全
  • 改了欄位型別，例如加長字串
  • 刪掉了一張已經沒用的表
  • 只改了註解或排版

repair 只對齊歷史表的紀錄。內容的效果沒變時對齊沒問題；效果變了的話，腳本與實際結構會從此不一致。

為什麼校驗和不符時，Spring Boot 連 V5、V6 這些新腳本都不跑，直接啟動失敗？

  • validate-on-migrate 預設 true
  • 新腳本的校驗和也跟著一起壞了
  • Flyway 只在第一次啟動時跑腳本
  • MySQL 偵測到校驗和不符而拒絕連線

屬性附錄：spring.flyway.validate-on-migrate 預設 true。先驗、驗過才補新腳本，避免在不一致的基礎上繼續改。

版本號比較小，卻比較晚到

晚到的版本：out-of-order

團隊同時開發時常見：A 寫了 V3 先上了，B 的 V2_1 比較晚合進來。這時資料庫已經在 V3，又出現一支版本更小、還沒跑過的 V2_1：

Detected resolved migration not applied to database: 2.1.

預設是拒絕。要讓它跑，設 spring.flyway.out-of-order=true（預設 false）：Flyway 文件的說明是「已經套用 1.0 與 3.0、又找到 2.0 時，也會把它套用，而不是忽略」（If you already have versions 1.0 and 3.0 applied, and now a version 2.0 is found, it will be applied too instead of being ignored.）。出處

WARN DbMigrate : outOfOrder mode is active. Migration of schema `bank` may not be reproducible.
INFO DbMigrate : Migrating schema `bank` to version "2.1 - add index owner" [out of order]
INFO DbMigrate : Successfully applied 1 migration to schema `bank`, now at version v2.1 (execution time 00:00.015s)

它跑了，但警告「可能無法重現」（may not be reproducible）：正式環境是 V3 → V2_1，新建的環境卻是 V2_1 → V3。另一種做法是 Flyway 文件建議的：用時間當版本號，例如 V4_20220308163340__mychange4.sql，降低兩人撞號或插隊的機會。出處

版本比目前小又沒跑過：預設擋下；out-of-order=true 會跑，但順序可能不能重現

資料庫已經在 V3，新出現一支沒跑過的 V2_1，out-of-order 是預設值。啟動結果是？

  • 自動在 V3 之後補跑 V2_1，啟動成功
  • 忽略 V2_1，照常啟動
  • validate 失敗，啟動失敗
  • 刪掉 V3，再依版本順序全部重跑

預設 out-of-order 是 false，validate 發現有本機腳本沒套用、版本又比目前小，就擋下。

設了 spring.flyway.out-of-order=true 讓 V2_1 跑完。Flyway 警告「may not be reproducible」，指的是什麼？

  • V2_1 下次啟動時會再跑一次
  • 新環境跑的順序跟正式環境不同
  • 歷史表會在下次啟動時被清空
  • V2_1 的校驗和無法計算，之後不會驗證

新環境從頭跑時照版本排序，跟正式環境實際的順序不同；兩支有關聯時結果就可能不同。

兩個人常在同一天各自新增遷移腳本、撞到同一個版本號。Flyway 文件建議的減少衝突方式是？

  • 兩個人共用同一支腳本，輪流往下寫
  • 全部改用可重複腳本，就不需要版本號
  • 每次部署都打開 out-of-order
  • 版本號加上時間

文件：To avoid version conflicts in team environments, use timestamps in the migration versions。

歷史表多了一筆 success = 0，而第一句加的 status 欄位已經在表裡了。原因在 MySQL：手冊寫 DDL 會「隱含地結束目前的交易，就像先做了 COMMIT」，而且「大多數也會在執行後隱含提交」（implicitly end any transaction active in the current session, as if you had done a COMMIT before executing the statement. Most of these statements also cause an implicit commit after executing.）出處；8.0 起的原子 DDL 也只保證單一句子不留半套，手冊特別註明「原子 DDL 不是交易式 DDL」（Atomic DDL is not transactional DDL.）。出處 Flyway 文件也說，資料庫不能乾淨地在交易裡跑 DDL 時，失敗了它「無法乾淨地退回，只會把這支腳本標成失敗，表示可能需要手動清理」，也可能要跑 repair（Flyway won't be able to perform a clean rollback in case of failure and will instead mark the migration as failed, indicating that some manual cleanup may be required.）。出處

把腳本改好直接重啟，還是起不來：

Detected failed migration to version 4 (add status).
Please remove any half-completed changes then run repair to fix the schema history.

照訊息做：手動 ALTER TABLE account DROP COLUMN status; 清掉半套，再執行 repair。repair 的第一件事就是「移除失敗的紀錄（留下的物件仍要手動清理）」（Remove any failed migrations (User objects left behind must still be cleaned up manually)），而且文件提醒 repair「必須給跟 migrate 一樣的 locations」（repair must be given the same locations as migrate!）。出處

DbRepair : Successfully repaired schema history table `bank`.`flyway_schema_history` (execution time 00:00.052s).
DbRepair : Manual cleanup of the remaining effects of the failed migration may still be required.
repair：[Removed failed migrations]
INFO DbMigrate : Migrating schema `bank` to version "4 - add status"
INFO DbMigrate : Successfully applied 1 migration to schema `bank`, now at version v4 (execution time 00:00.038s)

實跑時故意讓 repair 去預設位置找（腳本其實在 mig/），它回報 Marked missing migrations as deleted，在歷史表插入 type 為 DELETE 的紀錄，把「找不到檔案」的腳本標成已刪除。這就是文件那句提醒的原因。

MySQL 的 DDL 一句一提交：一支腳本只放一件 DDL；失敗了先清半套、repair（同樣的 locations）、再重跑

V4 有兩句 DDL，第一句成功、第二句語法錯誤，資料庫是 MySQL 8.4。失敗後第一句加的欄位怎樣了？

  • 被 Flyway 自動退回
  • 還在表裡，已經提交
  • 被 MySQL 標成暫時不可用
  • 要等重啟才會出現

MySQL 的 DDL 會隱含提交，實跑 SHOW COLUMNS 看得到 status。Flyway 也只能把這支腳本標成失敗。

接上題，失敗後 flyway_schema_history 裡 V4 那筆的 success 是多少？

  • 1
  • 沒有這一筆
  • 0
  • null

實跑：7 | 4 | add status | 0。資料庫不支援交易式 DDL 時，Flyway 留下一筆失敗紀錄，提醒你需要手動處理。

把 V4 的錯字改好，沒做別的就重啟。結果是？

  • V4 重跑成功，status 欄位不受影響
  • 還是失敗：Detected failed migration
  • 只跑第二句，第一句自動略過
  • Flyway 自動 repair 後繼續

歷史表還留著失敗紀錄，Flyway 要你先清掉半套、再 repair。實跑訊息：Please remove any half-completed changes then run repair。

清理順序哪一個正確？

  • 刪掉 flyway_schema_history 整張表再重啟
  • 先 repair，再重啟，status 欄位會被自動處理掉
  • 直接把 V4 改名成 V5，讓它當成新腳本
  • 刪 status 欄位、repair、再重啟

repair 只移除失敗紀錄；不先刪 status，V4 第一句重跑時會因為欄位已存在而失敗。

執行 repair 時沒給跟 migrate 一樣的 locations，Flyway 在預設位置找不到任何腳本。實跑結果是？

  • 報錯並停止，什麼都不改
  • 只移除失敗的那一筆，其他不動
  • 把找不到檔案的紀錄標成已刪除
  • 自動在整台機器上搜尋正確的資料夾

repair 會 Mark all missing migrations as deleted；找不到檔案就全部當成「缺少」。所以文件寫 repair must be given the same locations as migrate。

在 MySQL 上，為什麼建議一支遷移腳本只放一件 DDL？

  • 失敗時只會留下一句的半套
  • Flyway 規定每支腳本只能有一句
  • 一句一支跑起來比較快
  • MySQL 一個連線一次只能執行一句 SQL

MySQL 不支援交易式 DDL，一支腳本裡前面成功的 DDL 退不回去。拆小之後，失敗的範圍就只有那一句。

回不去，只能往前

回退策略：社群版沒有 undo

Flyway 有 undo 腳本（檔名 U 開頭，對應同版本的 V），但 undo 指令的文件頁一開頭就標著 Flyway Teams，是付費版的功能。出處 Spring Boot 內建的 Flyway 是社群版，所以上線後發現改錯，做法是往前修：再寫一支新的 V 把結構改回需要的樣子。這也符合前面那句「roll forward any necessary changes」。

  • 先備份再上線。刪欄位、刪表這種資料會消失的改動，undo 腳本也救不回資料；能救的是上線前的備份。
  • 不要在正式環境開 clean。Flyway 的 clean 會清空整個 schema。Spring Boot 的 spring.flyway.clean-disabled 預設是 true（Whether to disable cleaning of the database. true）出處，不要把它關掉。
  • 既有資料庫第一次導入 Flyway：已經有表的 schema 不是空的，要先 baseline，標記「現在這個狀態是起點」。Spring Boot 有 spring.flyway.baseline-on-migrate（預設 false，Whether to automatically call baseline when migrating a non-empty schema.）。出處

社群版沒有 undo：改錯就加一支新的 V 往前修；刪資料的改動靠備份；clean 永遠關著

用 Spring Boot 內建的 Flyway（社群版），上週上線的 V7 把一個欄位型別改錯了。該怎麼處理？

  • 寫一支 U7 undo 腳本執行
  • 改 V7 的內容再 repair
  • 新增 V8 把型別改成正確的
  • clean 之後從 V1 重跑

undo 是 Flyway Teams 的功能；改 V7 會讓腳本與實際不一致；clean 會清空資料。

Spring Boot 的 spring.flyway.clean-disabled 預設是什麼？為什麼？

  • false，方便開發時隨時清空重來
  • true，避免誤清空整個 schema
  • 沒有這個屬性，clean 一律禁止
  • true，因為社群版根本不支援 clean

屬性附錄寫預設 true。clean 會刪掉 schema 裡的所有物件，正式環境絕不能誤觸。

一個已經上線多年、表都建好了的資料庫，第一次要改用 Flyway 管。第一步該做什麼？

  • 打開 out-of-order，讓 V1 可以晚一點跑
  • 把現有的表全部刪掉，再用 V1 重建一次
  • 直接放 V1 進去，讓 Flyway 照常執行
  • 先 baseline，把現狀標成起點

非空的 schema 要先 baseline（或設 baseline-on-migrate），Flyway 才知道現在的狀態是起點，不會拿 V1 去建已經存在的表。

同一件事，另一套工具

Liquibase 一眼

Liquibase 用 changelog（變更紀錄檔）描述結構，裡面每一個 changeset 是一個變更單位。文件：changeset「由 author 與 id 兩個屬性，加上 changelog 的檔案路徑，唯一標記」（A changeset is uniquely tagged by both the author and id attributes (author:id), as well as the changelog file path.）出處；changelog 可以寫成 SQL、XML、YAML、JSON。出處 Spring Boot 加 spring-boot-starter-liquibase 就會在啟動時執行。示範的第二個 changeset（YAML）：

Liquibase 怎麼辨識「這個 changeset 跑過了沒」？

  • 只看 id，id 必須是遞增的整數
  • 看檔名裡的版本號，跟 Flyway 一樣
  • author、id 與 changelog 路徑
  • 看每個 changeset 最後一次被修改的時間

文件：uniquely tagged by both the author and id attributes (author:id), as well as the changelog file path；而且 id 不決定執行順序、也不必是整數。

實跑時 DATABASECHANGELOG 裡兩個 changeset 的 EXECTYPE 是什麼？

  • SUCCESS
  • EXECUTED
  • APPLIED
  • 1（代表成功）

實跑印出 1-create-account | tim | … | 1 | EXECUTED。文件列的可能值還有 FAILED、SKIPPED、RERAN、MARK_RAN。

Liquibase 的 changeset 依什麼順序執行？

  • changelog 裡的順序
  • id 的數字由小到大
  • author 名字的字母順序
  • 檔案在磁碟上的修改時間

文件：The id tag is just an identifier—it doesn't direct the order that changes are run。順序是 changelog 寫的順序。

團隊需要「每個變更都附上怎麼退回」，而且只能用免費版。Flyway 社群版與 Liquibase 哪個比較直接？

  • Flyway 社群版，用 U 開頭的 undo 腳本就好
  • 兩個都沒有任何回退機制
  • Liquibase，changeset 可寫 rollback
  • 兩個都要買付費版才能回退

Flyway 的 undo 標示為 Flyway Teams；Liquibase 文件說模型化的 changelog 可以自訂 rollback，rollback-count 等指令標為 All editions。

改名不停機：先加、再搬、最後刪

擴張收縮：不停機改欄位

把 owner 改名成 owner_name，最直覺的寫法是一支 V 做 RENAME COLUMN。問題是上線那一刻：新版程式還沒全部部署完，舊版程式（還在讀寫 owner）已經找不到欄位；滾動更新期間新舊版本一定會同時在跑。Martin Fowler 把解法叫平行變更（parallel change），「也叫擴張收縮」，把不相容的改動拆成三個階段：「擴張、遷移、收縮」（Parallel change, also known as expand and contract, … by breaking the change into three distinct phases: expand, migrate, and contract.），並說「大多數資料庫重構都照這個模式」（Most database refactorings follow the parallel change pattern）。出處

擴張（這一版程式還在讀寫 owner）：

-- 擴張：先加新欄位（可為 NULL、即時完成），再把舊資料複製過去
ALTER TABLE account ADD COLUMN owner_name VARCHAR(80) NULL, ALGORITHM=INSTANT;
UPDATE account SET owner_name = owner WHERE owner_name IS NULL;
id	owner	owner_name
1	alice	alice
2	bob	bob

新欄位要可以是 NULL，舊程式插入資料時才不會失敗；加欄位用 ALGORITHM=INSTANT 不會鎖住大表（Online DDL 的細節見〈交易隔離層級與鎖〉）。過渡期那一版程式要兩個欄位都寫，UPDATE 補的是上線前的舊資料。遷移：所有程式改讀寫 owner_name（示範把實體改成 @Column(name = "owner_name")），舊版全部下線。收縮：

-- 收縮：確定沒有任何版本的程式還在讀寫 owner 之後才做
ALTER TABLE account MODIFY COLUMN owner_name VARCHAR(80) NOT NULL;
ALTER TABLE account DROP COLUMN owner;

實跑時踩到一個坑：V6 成功了，但前面那支可重複腳本的 view 還寫著 owner：

ERROR 1356 (HY000) at line 1: View 'bank.account_summary' references invalid table(s) or column(s) or function(s) or definer/invoker of view lack rights to use them

MySQL 允許刪掉 view 用到的欄位，view 就這樣壞了，Flyway 與啟動都沒有報錯。把 R__account_summary_view.sql 改成用 owner_name，同一次啟動就會在 V6 之後重跑它：

INFO DbMigrate : Migrating schema `bank` with repeatable migration "account summary view"
INFO DbMigrate : Successfully applied 1 migration to schema `bank` (execution time 00:00.013s)

不相容的改動拆三步：擴張（加可為 NULL 的新欄位、補資料）、遷移（程式換用新欄位）、收縮（刪舊欄位，連同 view 一起改）

為什麼不直接用一支 V 做 RENAME COLUMN owner TO owner_name？

  • RENAME COLUMN 會把欄位裡的資料清掉
  • MySQL 不支援修改欄位名稱
  • Flyway 不允許腳本裡出現 RENAME
  • 舊版程式還在跑，會找不到 owner

部署不是瞬間完成的，新舊版本會同時存在一段時間。擴張收縮讓每個時間點的每一版程式都找得到它要的欄位。

擴張那一步加 owner_name 時，為什麼要先設成可以是 NULL？

  • NULL 欄位比 NOT NULL 省空間
  • 舊程式不會寫它，NOT NULL 會讓插入失敗
  • MySQL 規定新加的欄位只能是 NULL
  • NOT NULL 欄位之後不能再建索引

擴張期間舊程式還在跑，它不知道新欄位。等所有程式都寫 owner_name、資料補齊後，收縮那支 V6 才改成 NOT NULL。

擴張收縮的三個階段，正確順序是？

  • 收縮、遷移、擴張
  • 擴張、遷移、收縮
  • 遷移、擴張、收縮
  • 擴張、收縮、遷移

Fowler：expand, migrate, and contract。先加新的、再讓所有程式改用新的、最後刪舊的。

什麼時候才能跑收縮那支 V6（刪掉 owner）？

  • 擴張的 V5 一跑完就可以立刻接著跑
  • 任何時候都可以，順序不重要
  • 舊程式全部下線之後
  • 等 MySQL 自動更新完 view 之後

收縮是不可逆的（刪欄位就刪了資料），只能在舊程式全部下線後做，而且要先備份。

V6 刪掉 owner 成功，但 view account_summary 還寫著 SELECT owner …。實跑時發生什麼？

  • view 會自動改成讀 owner_name
  • V6 失敗，MySQL 不准刪 view 用到的欄位
  • Flyway 偵測到 view 並自動改寫
  • V6 成功，查 view 時 ERROR 1356

MySQL 允許刪掉 view 依賴的欄位，壞掉的 view 要等被查詢才報錯；收縮時要連 view 一起改。

重點整理

  • 正式環境的結構交給 Flyway／Liquibase；Hibernate 設 ddl-auto=validate 只核對。非內嵌資料庫的 ddl-auto 預設是 none。
  • Flyway 檔名 V版本__描述.sql，版本照數字排序、只跑一次；R__描述.sql 沒有版本、內容變了就重跑、永遠排最後。歷史表記版本、CRC32 校驗和與成敗。Boot 4 要 spring-boot-starter-flyway，MySQL 再加 flyway-mysql。
  • 改了已套用的腳本：校驗和不符、啟動失敗。改回去，要改結構就加新的 V；repair 只改歷史表。
  • 版本比目前小又沒跑過：預設擋下；out-of-order=true 會跑，但順序可能無法重現；版本號可以加時間減少衝突。
  • MySQL 的 DDL 會隱含提交，失敗會留半套與一筆 success = 0：先手動清理、再 repair（同樣的 locations）、再重跑；一支腳本只放一件 DDL。
  • 社群版 Flyway 沒有 undo（Teams 才有），改錯就往前修；clean-disabled 預設 true；既有資料庫先 baseline。Liquibase 用 changelog 與 changeset，可自帶 rollback。
  • 不相容的改動用擴張收縮：先加可為 NULL 的新欄位並補資料、程式全部換用新欄位、最後才刪舊欄位，依賴舊欄位的 view 要一起改。
