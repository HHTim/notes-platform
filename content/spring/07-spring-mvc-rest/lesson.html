一次 Web 溝通的基本單位

HTTP 請求與回應

用戶端先送出 HTTP 請求，伺服器處理後傳回 HTTP 回應。請求包含方法、網址、標頭與可能存在的本體；回應包含狀態碼、標頭與可能存在的本體。

POST /api/students HTTP/1.1
Content-Type: application/json

{"name":"小安","age":20}
HTTP/1.1 201 Created
Location: /api/students/42
Content-Type: application/json

{"id":42,"name":"小安","age":20}

回應裡那個 Location 不是裝飾。HTTP 規格說 201 建立出來的主要資源，「由回應中的 Location 標頭指出；如果沒有收到 Location 標頭，就以目標網址為準」——而這次的目標網址是 /api/students 這個集合，不是剛建好的那一筆。所以用 POST 對集合新增時，要自己把新資源的網址放進 Location，用戶端才知道去哪裡拿它出處。

POST 的請求本體一樣是明文傳送。MDN 說 HTTP 訊息「設計上就是人看得懂的」，而且它「送在 TCP 上，或送在一條受 TLS 加密的 TCP 連線上」——加密來自 TLS 而不是方法。POST 跟 GET 的差別只在資料不會出現在網址、瀏覽紀錄與伺服器存取紀錄裡出處。機密資料要不要安全，取決於 HTTPS、權限控管與資料處理方式；GET 也不該帶密碼或權杖。

把請求送到正確的方法

Controller 與路徑對應

@RestController 讓類別成為 Web 控制器，而且方法的回傳值預設會直接寫進回應本體。可以把它看成 @Controller 加 @ResponseBody 的便利組合。

@RestController
@RequestMapping("/api/students")
public class StudentController {
    @GetMapping("/{id}")
    public StudentResponse find(@PathVariable long id) {
        return studentService.find(id);
    }
}

@RequestMapping 可以同時設定路徑與方法；@GetMapping、@PostMapping、@PutMapping、@DeleteMapping 則是語意更清楚的快捷寫法。

資料可能藏在四個地方

路徑、查詢字串、標頭與本體

請求裡的位置Spring 註解適合放什麼
路徑 /students/42@PathVariable特定資源的識別碼
查詢字串 ?page=2@RequestParam篩選、排序、分頁等條件
請求標頭@RequestHeader媒體格式、驗證資訊、追蹤資訊
請求本體@RequestBody新增或更新所需的結構化資料

請求本體不是 POST 專屬。HTTP 規格定義 PUT 的語意就是「用請求訊息裡附上的內容去建立或取代目標資源的狀態」，本體是它的必要組成，PATCH 同理，@RequestBody 在這些方法上都用得上出處。原筆記在另一篇也寫了 PUT 要同時用 @PathVariable 與 @RequestBody，前後其實是矛盾的。

缺少必填的 @RequestParam 通常會直接變成用戶端錯誤（400），要讓它非必填就加 required=false 或 defaultValue。JSON 少了欄位時能不能接受，則應該由型別與驗證規則明確決定，不要依賴 Java 欄位自動變成 null——原筆記觀察到的「若前端送出的請求，省略了必須設置的屬性，則後端不會報錯 => 顯示null」，就是沒有加驗證時的預設行為。

網址描述資源，方法表達動作

RESTful API 的基本設計

REST 是一種架構風格。常見做法是用名詞式網址表示資源，再用 HTTP 方法表達操作，避免把動作名稱重複塞進網址。

需求方法與路徑常見的成功狀態
取得學生清單GET /api/students200 OK
取得單一學生GET /api/students/{id}200 OK
新增學生POST /api/students201 Created
完整更新學生PUT /api/students/{id}200 OK 或 204 No Content
刪除學生DELETE /api/students/{id}204 No Content

資源有階層關係時可以設計成 /students/{studentId}/courses。層級不宜無限加深；子資源本身如果可以獨立識別，也可以提供比較扁平的網址。

JSON 的值不只四種

輸入與輸出的資料結構

JSON 的值可以是物件、陣列、數字、字串，以及 true、false、null 這三個字面值。原筆記漏掉了物件、陣列與 null，而且 JSON 的數字並不分整數與浮點數兩型出處。

{
  "id": 42,
  "name": "小安",
  "active": true,
  "tags": ["java", "spring"],
  "address": {
    "city": "臺北市"
  }
}

Spring MVC 會透過訊息轉換器在 JSON 與 Java 物件之間轉換。API 的輸入輸出建議用專用的 DTO（Data Transfer Object，資料傳輸物件），不要直接把資料庫實體的所有欄位暴露出去，驗證與版本調整也會比較清楚。

不合法的資料在入口就擋下

Bean Validation 與 @Valid

public record CreateStudentRequest(
    @NotBlank String name,
    @Min(0) int age
) {}

@PostMapping
public ResponseEntity<StudentResponse> create(
        @Valid @RequestBody CreateStudentRequest request) {
    StudentResponse created = studentService.create(request);
    return ResponseEntity
            .created(URI.create("/api/students/" + created.id()))
            .body(created);
}

ResponseEntity.created(...) 會一次把狀態碼設成 201 並填好 Location，比自己寫 status(HttpStatus.CREATED) 再補標頭不容易漏。

@NotNull不可以是 null，但空字串會過。
@NotEmpty字串、集合或陣列不可以是空的。
@NotBlank字串去掉前後空白後還要有內容，最適合姓名這類欄位。
@Min數值的下限。

驗證註解的套件名也跟著 Jakarta 改過：Spring Boot 2 以前是 javax.validation，Spring Boot 3 起是 jakarta.validation。原筆記沒有標版本，抄程式碼時要對一下自己專案的版本。

成功與失敗都要說清楚

ResponseEntity 與統一的例外處理

ResponseEntity 可以明確指定狀態碼、標頭與本體。找不到資源要回適當的 4xx，不要把所有情況都包成 200 OK。

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(StudentNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(
            StudentNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorResponse("STUDENT_NOT_FOUND", ex.getMessage()));
    }
}

@ControllerAdvice 搭配 @ExceptionHandler 可以集中處理多個 Controller 的例外；純 API 的專案常直接用 @RestControllerAdvice。處理器可以針對具體的例外給精準回應，再留一個比較一般的例外處理當最後防線。

原筆記提到的「例外處理有繼承關係」是對的：找不到處理 IllegalArgumentException 的方法時，會往上找 RuntimeException，一路到 Exception。所以最後防線寫到 Exception 就夠了。

每一層只做好自己的事

Controller、Service、Repository 與攔截器

元件主要責任
Controller接收 HTTP 請求、轉換輸入、建立 HTTP 回應。
Service執行商業規則、協調資料操作與交易。
DAO／Repository把資料存取細節包起來。
Interceptor（攔截器）在 Controller 前後執行 Web 層的共同處理。

Spring MVC 的攔截器實作 HandlerInterceptor，再透過 WebMvcConfigurer.addInterceptors 註冊。preHandle() 回傳 true 代表繼續往下走，回傳 false 就停在這裡、不送到 Controller。

攔截器適合請求追蹤、地區判斷這類 MVC 流程的需求。完整的身分驗證與授權應該用專門的安全框架，不要在一般攔截器裡自己拼一套安全規則——第 9 課會談這件事。

重點整理

  • 路徑識別資源，HTTP 方法表達操作；POST 本身不代表資料已加密。
  • @PathVariable、@RequestParam、@RequestHeader、@RequestBody 分別取請求裡不同位置的資料。
  • 請求本體不是 POST 專屬，PUT 與 PATCH 也常帶。
  • JSON 的值有物件、陣列、數字、字串、true、false、null 七種。
  • 用 DTO 搭配 @Valid 與驗證註解，在進入商業邏輯前就檢查輸入。
  • Controller 處理 HTTP，Service 處理商業規則，Repository 處理資料存取。
