中間多一站，兩邊就不用互等

為什麼要佇列：解耦、緩衝尖峰、非同步

你把信丟進郵筒就可以走了，不用站在收件人門口等他開門。訊息佇列（message queue）就是程式之間的郵筒：送訊息的程式叫生產者（producer），收訊息的叫消費者（consumer），中間保管訊息的那台伺服器叫 broker（訊息代理）。

放一個 broker 在中間，換到三件事：

  • 解耦：轉帳服務只管把「A 轉出 1000」送出去，不需要知道誰要收、對方現在活著沒。
  • 緩衝尖峰：發薪日早上一口氣湧進十萬筆通知，佇列先收下來，消費者照自己的速度慢慢處理，不會被一次壓垮。
  • 非同步：使用者按下轉帳，畫面先回「處理中」，寄通知、更新報表這些不急的事，在背後由別的服務接手。

代價跟面試集那課講的一樣，三份帳單：結果從「馬上」變成「稍後」、每個消費者都要能承受同一則訊息來兩次（後面的冪等）、多一套系統要監控。要馬上拿到結果（例如查餘額）就直接呼叫。

下面哪個情境最不適合放訊息佇列？

  • 轉帳成功後寄 email 通知
  • 使用者打開 App 要立刻看到自己的餘額
  • 每天湧進大量交易紀錄，要慢慢寫進報表系統
  • 一筆轉帳完成後，風控、通知、報表三個服務都要知道

查餘額要馬上拿到結果，經過佇列只會變慢、變複雜，直接查就好。寄通知、慢慢寫報表、讓多個服務各自知道，都是不需要馬上回應的事，適合佇列。

「發薪日早上通知量是平常的十倍，通知服務的處理速度不變」，佇列在這裡幫的是哪一件事？

  • 緩衝尖峰：多的先收著，再慢慢消化
  • 解耦：讓轉帳服務不用知道通知服務的位址
  • 讓每則通知只會送一次
  • 讓通知處理得比較快

量突然變大、處理速度跟不上時，佇列先把多出來的存著，尖峰過了再追上。它不會讓處理變快，也不保證只送一次。

引進訊息佇列之後，下面哪一件事不是它帶來的代價？

  • 結果從「馬上」變成「稍後」
  • 消費者要能承受同一則訊息來兩次
  • 多一套系統要監控
  • 生產者得等消費者處理完

生產者送出就走，不用等消費者，這正是佇列的好處。前三個才是要付的代價。

轉帳服務改成「扣款後丟訊息給通知服務」，下面哪個說法對？

  • 通知服務掛掉時，轉帳服務也一定會跟著失敗、要整筆重來
  • 通知服務暫時掛掉，訊息會留在 broker 等它
  • 轉帳服務要改成知道通知服務的 IP
  • 通知一定在扣款的同一毫秒送到

這就是解耦：轉帳服務只跟 broker 打交道。代價是通知會「稍後」才到，不是同一瞬間。

一本只往後寫的帳本，切成好幾本

Kafka 的模型：主題、分區、位移、消費者群組

把 Kafka 想成銀行櫃檯的流水帳本：每發生一件事就往最後一行寫，寫上去就不改，誰想看都可以從某一行開始往下讀。Kafka 裡這本帳叫日誌（log），四個名詞都從這裡長出來：

  • 主題（topic）：一類事件放一個主題，例如 transfers。「跟傳統的訊息系統不同，事件被消費之後不會刪除」（unlike traditional messaging systems, events are not deleted after consumption），保留多久由主題的設定決定。出處
  • 分區（partition）：一個主題切成好幾本帳，放在不同的 broker 上，才能很多人同時讀寫。同一個 key 的事件寫進同一個分區，讀一個分區的順序跟寫入時相同（Events with the same event key… are written to the same partition, and Kafka guarantees that any consumer of a given topic-partition will always read that partition’s events in exactly the same order as they were written.）。出處
  • 位移（offset）：每本帳的行號，從 0 開始。消費者讀到哪裡，就只是記一個數字：它在每個分區的位置只是一個整數，也就是下一則要讀的訊息的位移。出處
  • 消費者群組（consumer group）：用同一個群組名稱、一起分工的消費者。規則只有一條：每個分區在任一時刻，只歸群組裡的一個消費者（each of which is consumed by exactly one consumer within each subscribing consumer group at any given time）。出處

從這條規則可以推出兩件事。第一，同一個群組裡的消費者比分區多，多出來的分不到分區，只能閒著；想加人加速，分區數要先估夠。第二，不同群組各讀各的，每個群組都有自己的位移，帳務群組讀完了，稽核群組照樣從頭讀到尾。訊息不會讀完就刪，所以消費者也能倒回舊的位移重讀（A consumer can deliberately rewind back to an old offset and re-consume data.），例如修好 bug 後重跑。出處

用 Spring 實際跑一次。主題 transfers 切 3 個分區，送 6 筆轉帳事件，key 是帳號；群組 ledger 開兩個消費者，audit 只開一個。Spring Boot 啟動時會建立 NewTopic Bean 描述的主題（To create a topic on startup, add a bean of type NewTopic.）。出處

    return TopicBuilder.name("transfers").partitions(3).replicas(1).build();
}

for (String[] e : events) {                             // e[0] 是帳號（key），e[1] 是內容

    System.out.printf("送出 key=%s「%s」→ 分區 %d、位移 %d%n",
            e[0], e[1], r.getRecordMetadata().partition(), r.getRecordMetadata().offset());

主題切成分區，同一個 key 進同一個分區、分區內有序；每個分區在一個群組裡只歸一個消費者，不同群組各讀各的

主題 transfers 有 3 個分區，群組 ledger 開了 5 個消費者。會怎樣？

  • 3 個消費者各分到一個分區，2 個閒著
  • 5 個消費者平均分，每個分到 0.6 個分區
  • Kafka 自動把主題改成 5 個分區
  • 5 個消費者都讀全部 3 個分區，每則訊息處理 5 次

每個分區在一個群組裡只歸一個消費者，所以最多 3 個人有事做。分區數不會自己變；要多人分工，得先把分區開夠。

上面的實跑，audit 群組為什麼也讀到全部 6 筆，而不是跟 ledger 分著讀？

  • 因為 audit 先啟動
  • 因為不同的群組各自有自己的位移，各讀各的
  • 因為 Kafka 會把訊息複製一份給第二個群組，複製完原本那份才刪掉
  • 因為 audit 只有一個消費者

分工只發生在同一個群組裡。群組之間互不影響，訊息也不會讀完就刪，所以每個群組都能從頭讀到尾。

轉帳事件用帳號當 key 送出。要保證「同一個帳號的事件照發生順序處理」，靠的是什麼？

  • Kafka 保證整個主題的所有事件全域有序
  • 每個消費者處理前先把事件排序
  • 把消費者數量設成跟帳號數一樣多
  • 同 key 進同一分區，分區內照寫入順序讀

Kafka 只保證分區內有序，不保證跨分區。同一個帳號都進同一個分區，那個帳號的事件就有序；不同帳號之間的先後就沒有保證。

上面的實跑裡，「D 轉出 500」的位移是 1。這個 1 是什麼意思？

  • 它是整個主題的第二則，三個分區一起編號
  • 它被處理了 1 次
  • 它的優先順序是 1
  • 它是分區 0 的第二則（從 0 起算）

位移是每個分區各自的行號。分區 0 的第一則「D 轉出 200」是 0，第二則是 1；分區 1、2 也各自從 0 開始。

帳務程式有 bug，昨天處理的事件算錯了。修好之後，用 Kafka 可以怎麼補救？

  • 沒辦法，事件被消費之後就刪了
  • 請生產者把昨天的事件全部重送一次
  • 把消費者的位移倒回昨天的位置，重新讀一遍
  • 把主題刪掉重建，Kafka 會自動從備份把昨天的事件還原回來

Kafka 的事件不會讀完就刪（保留期限內都在），消費者可以刻意倒回舊的位移重新消費。這也是它跟「讀完即刪」的佇列最大的差別。

3 個分區、群組裡只有 1 個消費者，後來又啟動第 2 個消費者（同一個群組）。會發生什麼？

  • 第 2 個消費者閒著，因為分區已經被第 1 個拿走了
  • 群組重新分配分區，兩個消費者分掉 3 個分區
  • 兩個消費者都讀全部分區，訊息會處理兩次
  • 第 2 個消費者啟動失敗

有人加入或離開群組，Kafka 會重新分配分區，讓每個分區仍然只歸一個人。這也是加消費者能分攤負載的原因（前提是分區夠多）。

郵局依地址分信，讀完就拿走

RabbitMQ 的模型：交換器、佇列、綁定

RabbitMQ 像郵局。生產者不直接把信塞進信箱，而是交給郵局，郵局照規則分到各個信箱（messages are published to exchanges, which are often compared to post offices or mailboxes. Exchanges then distribute message copies to queues using rules called bindings.）。出處

  • 交換器（exchange）：收訊息、決定送去哪些佇列，本身不存訊息。
  • 佇列（queue）：真正存訊息的地方，消費者從這裡拿。
  • 綁定（binding）：「佇列 Q 要收交換器 E 的哪些訊息」的規則。訊息帶一個路由鍵（routing key，像信封上的地址），綁定上寫的條件拿來跟它比。

交換器有幾種，差在怎麼比路由鍵：

交換器怎麼分
direct路由鍵跟綁定鍵完全相同才送（the exchange routes it to the queue if K = R）
fanout綁定的佇列全部都送，不看路由鍵（the routing key is ignored）
topic路由鍵用點分成好幾個字，跟綁定的樣式比對（matching between a message routing key and the pattern）

三種的定義出自同一頁。出處

topic 交換器的樣式有兩個萬用字元：「* 剛好代表一個字，# 代表零個或多個字」（* (star) can substitute for exactly one word. # (hash) can substitute for zero or more words.）。出處

另外有一個沒有名字的預設交換器，每條佇列都自動用佇列名稱當路由鍵綁上去（a routing key which is the same as the queue name），所以看起來像直接送進佇列，其實還是經過交換器。出處

實跑一個 topic 交換器 bank.events，三條佇列各綁一個樣式。Spring 裡把交換器、佇列、綁定宣告成 Bean，Spring Boot 自動建立的 RabbitAdmin 會在連上 broker 時建好它們（any Queue that is defined as a bean is automatically used to declare a corresponding queue on the RabbitMQ instance）。出處

@Bean
Declarables topology() {
    TopicExchange events = new TopicExchange("bank.events");
    Queue audit = new Queue("audit.all");
    Queue notify = new Queue("notify.large");
    Queue tw = new Queue("risk.tw");
    return new Declarables(events, audit, notify, tw,
            BindingBuilder.bind(audit).to(events).with("#"),                  // 全部都要
            BindingBuilder.bind(notify).to(events).with("transfer.*.large"),  // 大額轉帳
            BindingBuilder.bind(tw).to(events).with("*.tw.*"));               // 台灣的事件
}

// 送到交換器，不是送到佇列
rabbit.convertAndSend("bank.events", "transfer.tw.large", "事件 transfer.tw.large");

@RabbitListener(queues = {"audit.all", "notify.large", "risk.tw"})
void onEvent(@Payload String body, @Header(AmqpHeaders.CONSUMER_QUEUE) String queue) { … }

讀完就刪。這是跟 Kafka 最大的不同：RabbitMQ 收到消費者的確認（ack）之後，「才會把訊息從佇列裡完全移除」（a broker will only completely remove a message from a queue when it receives a notification for that message）。出處

所以同一條佇列有好幾個消費者時，一則只給一個人，通常是輪流分；出處 要讓好幾個服務都收到，就像上面那樣給每個服務一條自己的佇列。

還有一種情況要小心：沒有任何綁定符合的訊息，在生產者的 mandatory 屬性是預設的 false 時會被丟掉（或轉給另外設定的備用交換器）（the publisher set the mandatory message property to false (this is the default), the message is discarded or republished to an alternate exchange, if any）。出處

在 RabbitMQ，生產者的訊息第一站送到哪裡？

  • 交換器
  • 直接送進消費者
  • 直接送進佇列，交換器只在佇列滿的時候才會出來分流
  • 綁定

訊息一律先到交換器，交換器再照綁定分到佇列。就算是「直接送到佇列」的寫法，其實也是經過預設交換器。

topic 交換器上，佇列用 order.* 綁定。下面哪一個路由鍵會送到這條佇列？

  • order
  • order.tw.created
  • order.created
  • payment.created

* 剛好代表一個字。order.created 是 order 加一個字，符合。order 少了一個字、order.tw.created 多了一個字，都不符合；要比對任意多個字得用 order.#。

同一個 topic 交換器上，佇列用 order.# 綁定。下面哪一個路由鍵不會送到這條佇列？

  • order
  • order.created
  • order.tw.created
  • payment.order

# 代表零個或多個字，所以 order、order.created、order.tw.created 都符合。payment.order 的第一個字不是 order，不符合。

轉帳完成後，通知、風控、報表三個服務都要收到同一個事件，而且路由鍵不重要。最簡單用哪種交換器？

  • fanout，三個服務各綁一條佇列
  • direct，三個服務共用一條佇列
  • 不用交換器，生產者自己送三次，每次直接寫進一個服務的佇列
  • topic，三個服務共用一條佇列

fanout 把訊息複製給所有綁定的佇列，不看路由鍵。三個服務共用一條佇列的話，一則訊息只會被其中一個拿走，另外兩個收不到。

一條佇列開了 3 個消費者（同一個服務的 3 台）。佇列裡來了 1 則訊息，會怎樣？

  • 3 個消費者都收到一份
  • 只有其中一個收到
  • 3 個人要同時確認才算處理完
  • 沒人收到，要先設定由誰負責

  • audit.all 和 risk.tw
  • 三條都進
  • 只有 audit.all
  • 哪一條都不進，訊息被丟掉

送到交換器的訊息，如果沒有任何一條綁定符合，預設會怎樣？

  • broker 先存著，等之後有符合的佇列再補送過去
  • broker 自動建一條新的佇列來收
  • 被丟掉，除非生產者設了要退回的屬性
  • 送到死信佇列

無法路由的訊息會被丟掉或退回給生產者，看送出時設的屬性。所以綁定寫錯，訊息會默默消失，這是 RabbitMQ 常見的除錯題。

先記進度還是先做事，決定了會丟還是會重複

送達保證：至多一次、至少一次、剛好一次

Kafka 的傳遞保證有三種：出處

  • 至多一次：可能丟，不重送。
  • 至少一次：不丟，可能重送。
  • 剛好一次：只處理一次。

消費者這端決定是哪一種的，就是「記進度」和「做事」誰先：

  • 先記位移、再處理：存好位置之後、處理完之前當機，接手的程序從新位置開始，那幾則就沒處理到，對應到至多一次。
  • 先處理、再記位移：處理完之後、存好位置之前當機，接手的程序會再收到已經處理過的那幾則，對應到至少一次。

兩種情況出自 Kafka 設計文件的同一段。出處

銀行的帳寧可重複、不能丟（重複可以靠程式擋掉，丟了就是錢對不上），所以通常選至少一次，再讓消費者擋掉重複。生產者沒收到 broker 回應時也只能重送；enable.idempotence 開著時，「生產者會確保每則訊息在串流裡只寫入一份」（the producer will ensure that exactly one copy of each message is written in the stream），而且預設開啟（Idempotence is enabled by default if no conflicting configurations are set.）。出處 它擋不住「消費者處理兩次」。

剛好一次要什麼前提？這個保證有但書，只在「從 Kafka 讀、寫回 Kafka」時成立：出處

  • 交易式生產者把輸出的訊息和消費者的位移寫進同一筆 Kafka 交易。
  • 下游消費者設 isolation.level=read_committed（只讀已提交的交易）。
  • 寫到資料庫這種外部系統，Kafka 自己做不到，要讓消費者把位移存在跟輸出同一個地方，或讓處理冪等。

實務上寫資料庫的「剛好一次」，就是「至少一次＋消費者冪等」，也就是本課後半的去重表。RabbitMQ 用確認機制做到的是至少一次，要剛好一次，一樣得靠消費者冪等。

先記位移再處理＝至多一次（會丟）；先處理再記位移＝至少一次（會重複）；剛好一次只在 Kafka 讀寫 Kafka 的交易內成立，寫資料庫靠至少一次加冪等

消費者的寫法是「讀到訊息 → 先提交位移 → 再扣款」。在提交位移之後、扣款之前當機，結果是？

  • 這則訊息會被扣款兩次
  • 沒扣到款，重啟後也不會再收到
  • Kafka 會偵測到漏做的扣款，自動補做一次
  • 沒影響

位移已經往前了，重啟從下一則開始，這則就跳過了，這是至多一次的「丟」。要避免，就要先處理再提交位移。

消費者改成「讀到 → 先扣款 → 再提交位移」，在扣款之後、提交之前當機，結果是？

  • 重啟後再收到同一則，沒擋的話會扣兩次
  • 這則訊息丟了
  • Kafka 會發現位移沒提交，把剛才的扣款復原
  • 扣款會被寫成負數

位移沒提交，重啟從舊的位移開始，同一則再來一次。這是至少一次的「重複」，所以消費者要冪等。

生產者開了 enable.idempotence（Kafka 預設），下面哪個說法對？

  • 消費者一定只會處理每則訊息一次
  • 從此不需要去重表
  • 生產者送出後就不會重試
  • 生產者重試不會讓日誌多一份

冪等生產者擋的是「生產者重試造成日誌裡重複」。消費者處理完、提交位移前當機，一樣會再收到同一則，消費端還是要自己去重。

服務從 Kafka 讀轉帳事件，扣款寫進資料庫。想做到「每筆只扣一次」，最實際的做法是？

  • 至少一次＋消費者用去重表或唯一鍵擋掉重複
  • 把 Kafka 設成剛好一次模式，資料庫那邊就自動只寫一次
  • 改成先提交位移再扣款
  • 關掉生產者的重試

Kafka 的交易只管 Kafka 自己的讀寫，管不到外部資料庫。寫資料庫要嘛把位移跟扣款放同一筆資料庫交易，要嘛至少一次加冪等；先提交再扣款會變成會丟。

下游消費者要只讀「已提交的 Kafka 交易」寫出來的訊息，要設什麼？

  • isolation.level=read_uncommitted
  • enable.auto.commit=true
  • isolation.level=read_committed
  • acks=all

isolation.level 預設是 read_uncommitted，會讀到被中止的交易裡的訊息；設成 read_committed 才只讀已提交的。acks 是生產者要等幾個複本（同一個分區放在別台 broker 上的備份）確認。

處理完才說「收到了」

Spring 接 Kafka：@KafkaListener 與手動 ack

@KafkaListener 把一個 Bean 的方法指定為監聽器容器的監聽器。出處 監聽器容器是 Spring 替你開的背景執行緒，負責拉訊息、交給你的方法、提交位移。什麼時候提交，由 AckMode（ack 模式；ack 是 acknowledge，確認處理完了）決定：

  • Kafka 用戶端預設會在背景定期提交（enable.auto.commit），跟你處理到哪裡無關。出處 所以 Spring 把它關掉：從 2.3 版起，除非設定裡明確指定，框架會把 enable.auto.commit 設成 false，改由容器提交。
  • 預設的 AckMode 是 BATCH：一次 poll()（消費者向 Kafka 拉一批訊息的方法）拿回來的紀錄全部處理完才提交。也就是說預設就已經是「先處理、再提交」。
  • MANUAL／MANUAL_IMMEDIATE：你的方法多收一個 Acknowledgment 參數，自己呼叫 acknowledge() 才算數；MANUAL_IMMEDIATE 是呼叫 acknowledge() 時立刻提交。出處

要自己決定哪個時間點算成功，就用手動，Spring Boot 一行設定：

spring.kafka.listener.ack-mode=manual_immediate

下面把「處理完、ack 前當機」真的做一次：扣完款之後用 Runtime.getRuntime().halt(1) 讓程序直接死掉，位移就沒提交。資料庫用 H2（用 Java 寫的小型資料庫）的檔案模式，重啟後資料還在。這一版先不做去重：

@KafkaListener(topics = "debits", groupId = "ledger-service")
void onDebit(ConsumerRecord<String, String> rec, Acknowledgment ack) {
    String[] f = rec.value().split(":");                 // 序號:帳號:金額
    System.out.printf("收到 %s（分區 %d、位移 %d）%n", f[0], rec.partition(), rec.offset());
    long balance = ledger.debit(f[0], f[1], Long.parseLong(f[2]));   // 扣款
    System.out.println("  扣款完成，餘額 " + balance);
    if (crash) {
        System.out.println("  處理完、還沒 ack 就當機");
        Runtime.getRuntime().halt(1);                     // 模擬程序直接死掉，位移沒提交
    }
    ack.acknowledge();                                     // 處理完才提交位移
    System.out.println("  ack：位移提交");
}

收到 t-1001（分區 0、位移 0）

  處理完、還沒 ack 就當機

如果在監聽器方法上加 @Transactional，那筆交易管的只是資料庫，管不到位移提交；「資料庫提交了、位移還沒提交」的空窗一樣在，結果跟上面相同。@Transactional 的運作見〈Spring AOP 與交易控制〉與〈@Transactional 的傳播、隔離與失效情境〉。

  • BATCH
  • RECORD
  • 沒有預設，一定要設

預設 AckMode 是 BATCH，一次 poll() 拿回來的紀錄全部處理完才提交。

在 Spring 裡用 Kafka，為什麼框架預設把 enable.auto.commit 關掉？

  • 因為自動提交會讓訊息重複寫進 Kafka
  • 因為 Kafka 4 已經移除這個設定
  • 因為背景定期提交跟處理進度無關，可能先提交了還沒處理完的
  • 因為自動提交太慢，關掉之後 Kafka 的吞吐量會變好很多

Kafka 用戶端的自動提交是在背景定期做，不知道你的方法處理到哪裡。Spring 改由容器在處理完之後提交，才做得到「先處理、再提交」。

監聽器方法要收 Acknowledgment ack 參數、自己呼叫 ack.acknowledge()，AckMode 要設成哪一種？

  • BATCH
  • RECORD，每筆處理完由你呼叫 acknowledge()
  • TIME
  • MANUAL 或 MANUAL_IMMEDIATE

  • 因為第一次扣款的資料沒寫進 H2，程式自己補送
  • 因為群組名稱換了

把上面的 ack.acknowledge() 移到扣款之前（AckMode 是 MANUAL_IMMEDIATE），在扣款前當機，結果是？

  • 還是會扣兩次
  • Spring 會偵測到，自動把位移倒回去
  • 位移已提交，不會再收到，款沒扣到
  • 程式編譯不過

@Transactional 預設只管資料庫那筆交易；位移是 Kafka 那邊的事。兩者之間的空窗還在，消費端一樣要冪等。

冪等消費：去重表

冪等（idempotent）是「做一次和做很多次，結果一樣」。按電梯的樓層鍵就是冪等，按十次也只去那一層；扣款不是。面試集〈系統設計：訊息佇列與最終一致性〉列了三招：去重表、業務唯一鍵、版本號；消費者「必須冪等，例如追蹤已經處理過的訊息編號」（a message consumer must be idempotent, perhaps by tracking the IDs of the messages that it has already processed）。出處 這裡把去重表實作出來。

關鍵只有一句：去重表那一列和扣款，寫在同一筆資料庫交易裡。重複的訊息一插入就撞主鍵，整筆交易回復，扣款也跟著沒發生。

CREATE TABLE processed_message (
  message_id   VARCHAR(64) NOT NULL,     -- 生產者給的唯一編號（這裡用轉帳序號）
  consumer     VARCHAR(64) NOT NULL,     -- 哪個服務處理的：不同服務各記各的
  processed_at TIMESTAMP   DEFAULT CURRENT_TIMESTAMP NOT NULL,
  PRIMARY KEY (message_id, consumer)
);
@Component
static class Ledger {
    // 去重表與扣款放在同一筆交易：重複的訊息撞主鍵，整筆回復
    @Transactional
    public long debit(String messageId, String account, long amount) {
        jdbc.update("INSERT INTO processed_message (message_id, consumer) VALUES (?, 'ledger-service')", messageId);
        jdbc.update("UPDATE account SET balance = balance - ? WHERE id = ?", amount, account);
        return jdbc.queryForObject("SELECT balance FROM account WHERE id = ?", Long.class, account);
    }
}

// 監聽器裡：撞到主鍵就是做過了
try {
    long balance = ledger.debit(f[0], f[1], Long.parseLong(f[2]));
    System.out.println("  扣款完成，餘額 " + balance);
} catch (DuplicateKeyException e) {
    System.out.println("  去重表已有 " + f[0] + "：做過了，跳過");
}
ack.acknowledge();                                         // 做過了也要 ack，不然會一直收到

訊息一樣來了兩次，但餘額只少一次 1000（跳過的那則也要 ack，不然位移不前進、會一直重來）。三個細節：

  • @Transactional 放在 Ledger 這個 Bean 上，例外在交易外面接。例外從交易方法丟出來，Spring 才會回復整筆；同一個類別裡自己呼叫自己，@Transactional 不會生效（見〈Spring AOP 與交易控制〉與〈@Transactional 的傳播、隔離與失效情境〉），所以拆成兩個 Bean。
  • 編號要由生產者給、全域唯一。用 Kafka 的位移當編號不行：冪等生產者（預設開啟）自己重試不會多寫一份，但應用程式重新送一次（例如轉送器重啟後重送），同一件事會拿到新的位移。
  • 主鍵包含 consumer 欄位。帳務服務與通知服務各自處理同一則訊息，各記各的，不會互相擋掉。

冪等消費：生產者給唯一編號；去重那一列和業務更新同一筆交易；撞主鍵就跳過，做過了也要 ack

下面哪個操作本來就是冪等的？

  • 把餘額減 1000，扣完存回資料庫
  • 寄一封轉帳成功的通知信給客戶
  • 把訂單狀態設成「已出貨」
  • 在交易紀錄表插入一筆新紀錄（主鍵自動遞增）

把狀態「設成」某個值，做幾次結果都一樣。減金額、寄信、插入自動編號的紀錄，每做一次就多一次效果，要另外擋重複。

去重表的 INSERT 和扣款的 UPDATE，為什麼一定要放在同一筆交易？

  • 因為分開寫比較慢
  • 不然可能一個成功一個沒做到，下次重送時判斷錯
  • 因為 Kafka 規定要這樣寫，不然位移會提交失敗
  • 因為主鍵只在交易裡有效

如果先寫去重表、扣款前當機，重送時以為做過了，款就沒扣；先扣款、寫去重表前當機，重送時又扣一次。放同一筆交易，兩件事要嘛都成功、要嘛都沒發生。

去重表的主鍵為什麼是 (message_id, consumer)，而不是只有 message_id？

  • 因為 message_id 可能是空的
  • 因為這樣查詢比較快
  • 因為 Kafka 要求主鍵要有兩個欄位
  • 不同服務處理同一則，各記各的

如果只用 message_id，帳務服務先記下 t-1001，通知服務處理同一則時就撞主鍵、以為做過了，通知就不會寄。

去重時，訊息的唯一編號用什麼最恰當？

  • 生產者給的業務編號，例如轉帳序號
  • Kafka 的位移，同一則訊息永遠是同一個數字
  • 消費者收到的時間
  • 訊息內容的長度

位移是 Kafka 寫進日誌時才給的。同一筆轉帳被重新送一次（例如轉送器重啟後重送），會拿到另一個位移，去重表就擋不住。要用代表「同一件事」的編號。

上面的監聽器撞到 DuplicateKeyException 之後，如果不呼叫 ack.acknowledge()，會怎樣？

  • 沒差，反正已經做過了
  • Spring 會自動幫你 ack
  • 還會再收到同一則
  • broker 會把這則訊息直接刪掉

MANUAL_IMMEDIATE 模式下，只有呼叫 acknowledge() 才提交位移。跳過也是處理完了，一樣要確認。

重試與死信

消費者處理失敗有兩種：暫時性的（下游逾時、資料庫剛好忙），等一下再試可能就好；永久性的（金額格式錯、欄位缺了），試一萬次也一樣錯。後者叫毒訊息（poison message）：卡在那裡、永遠處理不了的訊息。重試的設計就是：暫時性的試幾次，用完還不行，或一看就是永久性的，就把它移到旁邊的死信（dead letter）區，讓後面的訊息繼續走，之後再有人工查原因、修好重放。

丟了例外呢？通常訊息會被拒絕，並由 broker 重新排入佇列。出處 沒開重試的話，這則訊息會無限次重送。出處 毒訊息就會在佇列頭上轉個不停。

要讓它停，有三條路：

  • 丟棄或送死信：容器的 defaultRequeueRejected 設成 false，訊息就被丟棄（或送到死信交換器）。
  • 丟特定例外：針對這一則丟 AmqpRejectAndDontRequeueException。出處
  • 開監聽器重試：開 Spring Boot 的監聽器重試（spring.rabbitmq.listener.simple.retry.enabled=true，預設關閉），重試用完一樣是拒絕：丟掉，或在 broker 有設定時送到死信交換器。出處

被拒絕、不重新排入的訊息會不會留下來，看佇列有沒有設死信交換器（dead letter exchange，DLX）。會變成死信的情況有四種：出處

  • 消費者負面確認且不重新排入（basic.reject 或 basic.nack 帶 requeue=false）
  • 訊息的 TTL（存活時間）過期
  • 佇列超過長度上限
  • 仲裁佇列的訊息被退回超過 delivery-limit（退回次數上限）次

仲裁佇列（quorum queue）是需要把佇列複製到多台、維持高可用時的預設選擇，因為經典佇列的鏡像從 RabbitMQ 4.0 起移除。出處

交易式 Outbox 的實作骨架

最後一個問題：扣款寫資料庫、發事件寫 broker，是對兩個系統各寫一次（這叫雙重寫入）。先寫資料庫、再送訊息，中間當機，下游就永遠不知道這筆扣款；先送訊息、交易卻回復了，下游收到一件沒發生的事。用兩階段提交（2PC，先問兩邊能不能做、都說能才一起提交）也不實際（The database and/or the message broker might not support 2PC.）。出處 用 @TransactionalEventListener（預設在 AFTER_COMMIT，交易提交後才執行）去送訊息，擋得住「交易還原了、訊息卻送出」，擋不住「提交之後、送出之前當機」，那則訊息就丟了；這正是 Outbox 要解決的。這個監聽器的用法見〈@Transactional 的傳播、隔離與失效情境〉。

解法是交易式 Outbox（transactional outbox）：「先把訊息當作更新業務資料那筆交易的一部分存進資料庫，再由另一個程序把訊息送到 broker」（first store the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages to the message broker.）。出處 存訊息的表叫寄件匣（outbox），另一個程序叫訊息轉送器（message relay）。骨架三塊：

CREATE TABLE outbox (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,   -- 轉送器照它的順序送
  aggregate_id VARCHAR(64) NOT NULL,                -- 帳號：送 Kafka 時當 key，同帳號進同一分區
  event_type   VARCHAR(64) NOT NULL,                -- 'TransferDebited'
  payload      VARCHAR(1000) NOT NULL,
  created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
  published_at TIMESTAMP                            -- 送成功才填；NULL 表示還沒送
);
// ① ② 扣款與寫寄件匣在同一筆交易：要嘛都成功，要嘛都沒發生
@Transactional
public void debit(String txId, String account, long amount) {
    int rows = jdbc.update("UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?",
            amount, account, amount);
    jdbc.update("INSERT INTO outbox (aggregate_id, event_type, payload) VALUES (?, 'TransferDebited', ?)",
            account, txId + ":" + account + ":" + amount);
    if (rows == 0) throw new IllegalStateException("餘額不足");   // 丟例外：上面兩句一起回復
}

// ③ 訊息轉送器：每 0.5 秒撈還沒送的，依序號送出，送成功才標記
@Scheduled(fixedDelay = 500)
public void relay() throws Exception {
    List<Map<String, Object>> rows = jdbc.queryForList(
            "SELECT id, aggregate_id, payload FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 100");
    for (Map<String, Object> r : rows) {
        kafka.send("transfer-events", (String) r.get("AGGREGATE_ID"), (String) r.get("PAYLOAD"))
             .get(5, TimeUnit.SECONDS);                     // 等 broker 確認
        jdbc.update("UPDATE outbox SET published_at = CURRENT_TIMESTAMP WHERE id = ?", r.get("ID"));
    }
}

轉送器：outbox 第 1 筆送出並標記

t-2002 的 INSERT 其實執行了，但跟扣款一起回復，所以寄件匣只有 1 筆，下游也只收到 t-2001，不會收到一件沒發生的扣款。這套骨架還有三個要注意的地方：

  • 轉送是至少一次。轉送器可能在送出之後、記下已送之前當機，重啟後再送一次（It might, for example, crash after publishing a message but before recording the fact that it has done so.），所以消費者必須冪等。出處 上一段的去重表在這裡派上用場。
  • 等 broker 確認才標記。.get(5, TimeUnit.SECONDS) 等到 Kafka 回應才往下；沒等就標記，送失敗的那筆就再也不會重送。
  • 同時跑好幾台轉送器，會撈到同一批。要嘛只讓一台跑，要嘛撈的時候把那幾列鎖住。

Outbox：業務更新和寄件匣同一筆交易；轉送器撈未送的、等 broker 確認才標記；轉送是至少一次，下游要冪等

程式寫成「先 kafka.send(...)，再在 @Transactional 方法裡扣款」，扣款因為餘額不足回復了。下游會怎樣？

  • 不會收到，因為交易回復時 Kafka 的訊息也會收回
  • 還是會收到這筆「已扣款」的事件，但款其實沒扣
  • 收到兩次
  • Kafka 會等交易提交才送

資料庫交易管不到已經送出的 Kafka 訊息，下游收到的是一件沒發生的事。這就是雙重寫入的問題，Outbox 把「發訊息」變成資料庫裡的一筆 INSERT，跟扣款一起提交或一起回復。

轉送器送出訊息、Kafka 也收到了，但在 UPDATE outbox SET published_at 之前當機。重啟後會怎樣？

  • 同一筆再送一次，下游會收到兩次
  • 這筆永遠不會送
  • Kafka 會自動拒絕重複的
  • 轉送器會先問 Kafka 有沒有送過

轉送器為什麼要等 kafka.send(...) 回應（.get(...)）之後，才把那筆標記成已送？

  • 因為 KafkaTemplate 不呼叫 get 就不會送
  • 為了讓程式跑比較快，一次只送一筆
  • 沒確認就標記，送失敗的那筆就不會重送了
  • 因為 Kafka 規定要同步送

先標記、後確認，送失敗時寄件匣已經寫著「已送」，這筆就丟了。等確認才標記，最壞只是重送，下游冪等擋得住。

寄件匣的 aggregate_id 存帳號，轉送時拿來當 Kafka 的 key。目的是什麼？

  • 讓訊息比較小
  • 讓 Kafka 能去重
  • 讓轉送器知道這筆該送到哪一個主題
  • 同帳號進同一分區，保持順序

同一個 key 一定寫進同一個分區，分區內有序，所以同一個帳號的扣款事件會照順序被讀到。key 跟去重、主題名稱無關。

重點整理

  • 佇列換到解耦、緩衝尖峰、非同步；代價是結果變「稍後」、消費者要冪等、多一套要監控。要馬上拿結果的別用。
  • Kafka：主題切成分區，同一個 key 進同一個分區、分區內有序；位移是每個分區各自的行號；每個分區在一個群組裡只歸一個消費者，消費者比分區多就閒著；不同群組各讀各的；讀完不刪，可以倒回重讀。
  • RabbitMQ：訊息先到交換器，照綁定分到佇列；direct 比完全相同、fanout 全送、topic 用 * 與 # 比樣式；同一條佇列的消費者輪流拿；確認後刪除；沒有綁定符合的訊息預設丟掉。
  • 先記位移再處理是至多一次（會丟），先處理再記位移是至少一次（會重複）。剛好一次只在 Kafka 讀寫 Kafka 的交易內成立；寫資料庫靠至少一次加冪等。冪等生產者只擋日誌裡的重複；消費者用去重表：生產者給唯一編號，主鍵（訊息編號、消費者），跟業務更新同一筆交易，撞主鍵就跳過，跳過也要 ack。
  • Spring Kafka 預設 AckMode 是 BATCH，框架關掉 enable.auto.commit；MANUAL／MANUAL_IMMEDIATE 自己呼叫 acknowledge()。ack 前當機，重啟會再收到同一則；@Transactional 管不到位移。
  • 重試與死信：Spring Kafka 預設試 10 次後寫日誌跳過，接 DeadLetterPublishingRecoverer 才送到「原主題-dlt」，重試期間同分區要等；Spring AMQP 預設拒絕並無限次重新排入，用 defaultRequeueRejected=false、AmqpRejectAndDontRequeueException 或開重試讓它停，佇列設死信交換器才留得住。
  • Outbox：業務更新與寄件匣同一筆交易，轉送器撈未送的、等 broker 確認才標記；轉送是至少一次，下游要冪等。
