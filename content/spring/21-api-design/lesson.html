先講好範圍

上線之後才會痛的四件事

API 上線之後最常痛的四件事：改版、分頁、重送、錯誤格式，最後補上文件與選型。

控制器與統一例外處理的基本寫法見〈Spring MVC 與 RESTful API〉〈Maven、微服務與全域例外〉。以下用一個小銀行 API：Spring Boot 4.1.1（內含 Spring Framework 7.0.9）、Java 21、H2 記憶體資料庫，文件用 springdoc-openapi 3.1.1。相依是 spring-boot-starter-webmvc（Boot 4 的 Spring MVC starter）、spring-boot-starter-validation、spring-boot-starter-jdbc、h2 與 springdoc-openapi-starter-webmvc-ui（3.1.1）。

改版

什麼時候要開新版

API 一旦有人在用，回應的形狀就是一份「約定」。範例帳戶 API 第 1 版回 "balance":10000；後來要支援外幣，想改成 "balance":{"amount":10000,"currency":"TWD"}。舊的 App 還在讀數字，收到物件就壞了，這叫破壞相容的變更（breaking change）。相對地，多加一個欄位通常不會讓舊用戶端壞掉（前提是用戶端會忽略看不懂的欄位）。實務上的判斷是：能用「加欄位、加端點」解決的就不開新版；非改不可的才開新版，讓舊版跟新版並存一段時間。

版本號要放在請求的哪裡，沒有標準答案，所以啟用 API 版本功能時，要自己指定怎麼解析版本。出處 Spring 內建四種解析方式：出處

  • 標頭
  • 查詢參數
  • 媒體類型參數
  • 網址路徑

查詢參數（?version=2）用法跟標頭很像，這課看另外三種。

常見的取捨：

放法長相好處代價
路徑/v2/accounts/A-001一眼看得出版本；瀏覽器、記錄檔、快取都直接分得開同一個資源有兩個網址；版本號混進資源的識別
自訂標頭API-Version: 2網址不變；沒帶時可以給預設版本網址上看不到版本，除錯要看標頭；中間的快取要知道回應會隨這個標頭改變
媒體類型參數Accept: application/json;v=2用的是 HTTP 本來就有的內容協商最不直覺；用戶端與工具要會設定 Accept

第三種靠的是內容協商（content negotiation，用戶端用 Accept 標頭說「我想要哪種格式」，伺服器挑一種回）；application/json 這種格式名字叫媒體類型（media type），分號後面可以接參數。

帳戶 API 想把 balance 從數字改成 {"amount":…,"currency":…}。這個改動對還在讀數字的舊 App 是什麼？

  • 破壞相容，舊 App 會壞，要開新版
  • 相容的變更，直接上線就好
  • 只是文件要更新，程式不用動
  • 只要把 HTTP 狀態碼改成 201 就相容

欄位的型別變了，舊用戶端照數字去讀會失敗，這是破壞相容的變更。這種改動才需要開新版，讓新舊版並存一段時間。

回應裡多加一個新欄位 nickname，通常要不要開新版？

  • 一定要，回應的任何改動都要開新版
  • 要，因為 JSON 的欄位順序跟著變了
  • 通常不用，用戶端會略過不認識的欄位
  • 要看資料庫那張表有沒有加欄位

加欄位一般不會讓舊用戶端壞掉，條件是用戶端遇到不認識的欄位會略過。能用加欄位解決的，就不必開新版。

想讓網址上一眼就看得到版本，記錄檔與快取也能直接依網址分開，該選哪一種？

  • 自訂標頭 API-Version
  • Accept 的媒體類型參數
  • 放在 Cookie
  • 放在路徑，例如 /v2/…

只有路徑會讓版本出現在網址裡。代價是同一個資源有兩個網址。

Spring Framework 7 內建的 API 版本

Spring Framework 7 以前，要做版本得自己在 @GetMapping 寫 headers = "API-Version=2" 或 produces = "application/vnd.bank.v2+json" 這類條件。7.0 起 @RequestMapping 多了 version 屬性，同一個路徑可以對到不同版本的方法。控制器只寫一次：

@RestController
@RequestMapping("/accounts/{id}")
public class AccountController {
    record AccountV1(String id, String owner, BigDecimal balance) {}
    record Money(BigDecimal amount, String currency) {}
    record AccountV2(String id, String owner, Money balance) {}
    // 建構子注入 TransferService bank，省略

    @GetMapping(version = "1")              // 第 1 版：餘額是一個數字
    AccountV1 v1(@PathVariable String id) {
        return new AccountV1(id, bank.owner(id), bank.balance(id));
    }

    @GetMapping(version = "2")              // 第 2 版：餘額改成「金額＋幣別」，舊用戶端會讀不懂，所以開新版
    AccountV2 v2(@PathVariable String id) {
        return new AccountV2(id, bank.owner(id), new Money(bank.balance(id), "TWD"));
    }
}

版本從哪裡讀，集中在 WebMvcConfigurer 的 configureApiVersioning。範例用一個自訂設定值 bank.versioning 切換三種放法，方便同一份程式碼實跑三次（正式專案選一種就好）：

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Value("${bank.versioning:path}")
    private String mode;                     // 示範用：同一份程式碼切換三種放版本的位置

    @Override
    public void configureApiVersioning(ApiVersionConfigurer api) {
        switch (mode) {
            case "path"   -> api.usePathSegment(0);                                 // /v1/accounts/A-001
            case "header" -> api.useRequestHeader("API-Version");                   // API-Version: 2
            case "media"  -> api.useMediaTypeParameter(MediaType.APPLICATION_JSON, "v"); // Accept: application/json;v=2
            default -> throw new IllegalArgumentException(mode);
        }
        if (!mode.equals("path")) api.setVersionRequired(false).setDefaultVersion("1");   // 沒帶版本就當第 1 版

        StandardApiVersionDeprecationHandler deprecation = new StandardApiVersionDeprecationHandler();
        deprecation.configureVersion("1")
                .setDeprecationDate(ZonedDateTime.parse("2026-10-01T00:00:00Z"))
                .setSunsetDate(ZonedDateTime.parse("2027-04-01T00:00:00Z"))
                .setSunsetLink(URI.create("https://bank.example/docs/migrate-v2"));
        api.setDeprecationHandler(deprecation);
    }

    @Override
    public void configurePathMatch(PathMatchConfigurer path) {   // 版本放路徑：每個控制器的網址前面加 /{version}
        if (mode.equals("path")) path.addPathPrefix("/{version}", HandlerTypePredicate.forBasePackage("demo.bank"));
    }
}

放路徑時，路徑片段必須宣告成 URI 變數（例如 /{version}、/api/{version}，變數名稱不重要），並建議用路徑比對的設定統一加前綴，範例的 addPathPrefix 就是這個。出處 Spring Boot 也可以只用設定檔，例如 spring.mvc.apiversion.use.header=X-Version 加 spring.mvc.apiversion.default=1.0.0。出處

版本放路徑時實跑（--bank.versioning=path，只留關鍵行：省略 Date 等標頭與空行）：

$ curl -i http://127.0.0.1:9579/v1/accounts/A-001
HTTP/1.1 200
Deprecation: @1790812800
Sunset: Thu, 1 Apr 2027 00:00:00 GMT
Link: <https://bank.example/docs/migrate-v2>; rel="sunset"; type="text/html"
Content-Type: application/json

{"id":"A-001","owner":"王小明","balance":10000}

$ curl -i http://127.0.0.1:9579/v2/accounts/A-001
HTTP/1.1 200
{"id":"A-001","owner":"王小明","balance":{"amount":10000,"currency":"TWD"}}

$ curl -i http://127.0.0.1:9579/v3/accounts/A-001
HTTP/1.1 400
{"detail":"Invalid API version: '3.0.0'.","instance":"/v3/accounts/A-001","status":400,"title":"Bad Request"}

三件事值得看。第一，v3 被解析成 3.0.0：內建解析器跳過開頭的非數字字元，再拆成主、次、修訂三段，沒寫的次版與修訂補 0。第二，不受支援的版本丟 InvalidApiVersionException，回 400。出處；受支援的版本預設從控制器宣告的 version 收集，這裡只有 1 和 2。第三，第 1 版的回應多了三個標頭，下一段講。

換成標頭與媒體類型實跑，回應的內容跟上面第 1、2 版一樣，只差版本從哪裡讀：

$ curl -i http://127.0.0.1:9579/accounts/A-001                      # bank.versioning=header，沒帶版本
HTTP/1.1 200
Deprecation: @1790812800
…
{"id":"A-001","owner":"王小明","balance":10000}

$ curl -i -H 'Accept: application/json;v=2' http://127.0.0.1:9579/accounts/A-001   # bank.versioning=media
HTTP/1.1 200
Content-Type: application/json;v=2
{"id":"A-001","owner":"王小明","balance":{"amount":10000,"currency":"TWD"}}

沒帶版本時拿到第 1 版，是因為範例設了 setVersionRequired(false) 與預設版本 1。不設的話，啟用 API 版本時預設必須帶版本，沒帶就丟 MissingApiVersionException，回 400。出處 對已經上線、從沒帶過版本的舊 App，給預設版本是比較溫和的做法。

Spring Framework 7 起，同一個路徑要對到第 1 版和第 2 版兩個方法，控制器上怎麼寫？

  • 兩個方法取不同名稱，Spring 會自動分版本
  • 一定要寫 headers = "API-Version=2"
  • 只能拆成兩個控制器類別，各自對應一版
  • 在 @GetMapping 加 version 屬性

7.0 起 @RequestMapping 有 version 屬性。版本從哪裡讀（路徑、標頭、媒體類型）另外在 configureApiVersioning 設定，控制器不用管。

範例從「版本放標頭」改成「版本放路徑」，控制器程式碼要改哪裡？

  • 不用改，只換版本解析的設定與路徑前綴
  • 每個方法加 @RequestHeader
  • 每個 @GetMapping 都要加 /v1
  • 把 version 屬性拿掉

範例三種放法共用同一個控制器，只換 configureApiVersioning 的解析方式；路徑那種再用 addPathPrefix 統一加 /{version} 前綴。

實跑 GET /v3/accounts/A-001，控制器只宣告了第 1、2 版。結果是什麼？

  • 404，找不到這個路徑
  • 400，版本不受支援
  • 200，退回最新的第 2 版
  • 500，伺服器例外

實跑回 400，detail 是 Invalid API version: '3.0.0'。版本不受支援時丟 InvalidApiVersionException，回 400。

版本放標頭、沒有設定 setVersionRequired(false)，請求完全沒帶版本會怎樣？

  • 自動用最新版
  • 回 400
  • 自動用第 1 版
  • 回 404

預設必須帶版本，沒帶丟 MissingApiVersionException、回 400。範例設成可以不帶，再給預設版本 1，所以實跑沒帶版本拿到第 1 版。

要淘汰舊版時，先用標頭通知

新版上線後，舊版不能說關就關，要先通知、給期限。Spring 內建的 StandardApiVersionDeprecationHandler 能送 RFC 9745 與 RFC 8594 定義的三種標頭：出處

  • Deprecation（棄用）：表示這個資源將要或已經被棄用，值必須是結構化標頭的日期格式，寫成 @ 加上 1970 年起算的秒數。出處 實跑的 @1790812800 換算回來就是設定的 2026-10-01 00:00 UTC。
  • Sunset（停用日）：伺服器用它告訴用戶端，這個資源預計在某個時間點之後不再回應，值是一般的 HTTP 日期。出處
  • Link：rel="sunset" 指向遷移說明頁。

棄用不等於停用：棄用日之後舊版照常回應，只是在提醒；停用日才是真的要關。第 2 版的回應沒有這三個標頭，因為只有第 1 版被設成棄用。

實跑打第 1 版，回應多了 Deprecation: @1790812800。這個值是什麼意思？

  • 還剩 1790812800 秒停用
  • 這支 API 的流水號
  • 棄用日期，1970 年起算的秒數
  • 伺服器處理這個請求花的微秒數

Deprecation 的值是結構化標頭的 Date，寫成 @ 加秒數。換算回來是 2026-10-01 00:00 UTC，正是 setDeprecationDate 設的日期。

Deprecation 與 Sunset 兩個標頭的差別，哪個說法對？

  • 兩個是同一件事的新舊名稱
  • 前者是提醒棄用，後者是預計停止回應的時間
  • Deprecation 一出現，伺服器就不再回應
  • Sunset 是用戶端送給伺服器的

棄用是提醒，舊版照常回應；RFC 8594 的 Sunset 才是預計 become unresponsive 的時間點。兩者都是伺服器放在回應裡的。

分頁

偏移分頁：第幾頁、每頁幾筆

交易明細可能有幾十萬筆，一定要分頁。最直覺的是偏移分頁（offset pagination）：用戶端說「第 page 頁、每頁 size 筆」，SQL 用 LIMIT size OFFSET page×size，跳過前面那些列。

SELECT id, amount FROM tx WHERE account_no = ? ORDER BY id DESC LIMIT ? OFFSET ?   -- 參數：帳號、size、page × size
SELECT COUNT(*) FROM tx WHERE account_no = ?                                     -- 算總筆數

它的好處是能直接跳到第 37 頁、能算出總頁數，適合後台表格。問題有兩個。

第一，翻頁途中有新資料會重複或漏掉。範例先讀第 0 頁，接著有一筆新交易進來，再讀第 1 頁：

$ curl 'http://127.0.0.1:9579/v1/accounts/0000001234/txs?page=0&size=5'
{"items":[{"id":50,…},{"id":49,…},{"id":48,…},{"id":47,…},{"id":46,"amount":7020.00}],"page":0,"size":5,"total":50}

$ curl -X POST 'http://127.0.0.1:9579/v1/accounts/0000001234/txs?amount=1200'    # 這時有一筆新交易
{"id":51,"amount":1200}

$ curl 'http://127.0.0.1:9579/v1/accounts/0000001234/txs?page=1&size=5'
{"items":[{"id":46,"amount":7020.00},{"id":45,…},{"id":44,…},{"id":43,…},{"id":42,…}],"page":1,"size":5,"total":51}

id 46 出現了兩次。新的一筆排在最前面，把所有列往後推了一格，「跳過 5 筆」就少跳了一筆。反過來，前面有資料被刪掉時則會漏掉一筆。

第二，越後面越慢。OFFSET 不是「直接跳到第 90 萬筆」，資料庫得把前面的列一筆一筆讀過再丟掉。〈索引是怎麼運作的〉教過 EXPLAIN ANALYZE；這裡在 MySQL 8.4 建一張 100 萬筆的交易表（索引 (account_no, id)），每頁 20 筆，比較第一頁與最後幾頁（取第二次執行的數字；輸出是節錄，省略 Filter 那一層與 cost）：

-- 偏移 0
-> Limit: 20 row(s)  (actual time=0.129..0.133 rows=20 loops=1)
    -> Index lookup on tx using idx_acct_id (account_no='0000001234') (reverse)  (actual time=0.127..0.13 rows=20 loops=1)

-- 偏移 900000
-> Limit/Offset: 20/900000 row(s)  (actual time=497..497 rows=20 loops=1)
    -> Index lookup on tx using idx_acct_id (account_no='0000001234') (reverse)  (actual time=0.136..409 rows=900020 loops=1)

同樣只回 20 列，偏移 90 萬那條實際讀了 900,020 列、花了約 497 毫秒；第一頁 0.13 毫秒。毫秒數依機器與快取狀態而異，重點是讀了幾列。偏移式捲動要求多數資料庫先把整個結果建出來，伺服器才能回傳。出處

讀完第 0 頁後進來一筆新交易，再讀第 1 頁，實跑看到 id 46 出現兩次。原因是？

  • H2 資料庫在分頁時的已知錯誤
  • JdbcClient 把第 0 頁的結果快取了
  • 新資料插在最前面，後面整批往後移一格
  • SQL 的 ORDER BY 忘了寫 DESC

依 id 由新到舊排，新的 id 51 插在最前面，原本第 5 筆的 46 被推到第 6 位，「跳過 5 筆」後又讀到它。

偏移分頁讀第 0 頁後，最前面有一筆資料被刪掉，再讀第 1 頁會怎樣？

  • 不受影響
  • 重複出現一筆
  • 直接回 404
  • 漏掉一筆

刪掉一筆，後面每列往前移一格，原本第 1 頁的第一筆跑到第 0 頁的最後一格，已經翻過去了，就被漏掉。

哪個場景偏移分頁仍然是合理選擇？

  • 手機 App 無限往下滑的動態
  • 每秒有新資料進來的即時明細
  • 要跳頁、顯示總頁數的後台表格
  • 幾千萬筆、使用者常翻到很後面的匯出

偏移分頁能直接跳到第幾頁、算總頁數，資料量不大的後台表格很合適。另外三個都會踩到「越後面越慢」或「途中有新資料」。

鍵集分頁與游標

鍵集分頁（keyset pagination）換個問法：不問「跳過幾筆」，而是問「排在上一頁最後一筆之後的是誰」。上一頁最後是 id 46，下一頁就是 WHERE id < 46 ORDER BY id DESC LIMIT 5。排序欄位有索引時，資料庫沿著 B-tree 直接找到 46 的位置往下讀，前面讀過的列不用再碰。同一張 100 萬筆的表，跟偏移 90 萬拿到同一頁：

-- WHERE account_no = '0000001234' AND id < 100001 ORDER BY id DESC LIMIT 20（節錄，省略 Filter 那一層）
-> Limit: 20 row(s)  (actual time=0.043..0.0472 rows=20 loops=1)
    -> Index range scan on tx using PRIMARY over (id < 100001) (reverse)  (actual time=0.0407..0.042 rows=20 loops=1)

只讀 20 列、0.047 毫秒，跟翻到第幾頁無關（最佳化器這次選了主鍵做範圍掃描，因為這張表所有列都是同一個帳號）。代價是不能直接跳到第 37 頁、也不好算總頁數，排序欄位還要唯一（不唯一時要再接一個唯一欄位，例如 (tx_date, id)）。

對外的 API 通常不讓用戶端自己組 id < 46，而是給一個游標（cursor，一段代表「讀到哪裡了」的字串）。範例把 id:46 用 Base64（把位元組轉成英數字的編碼方式）包起來，用戶端只要原封不動帶回來；這種用戶端不必看懂內容的字串叫「不透明」（opaque）的游標，伺服器日後要改成 (tx_date, id) 也不影響用戶端。

@GetMapping("/accounts/{no}/txs/scroll")
CursorPage byCursor(@PathVariable String no, @RequestParam(required = false) String cursor,
                    @RequestParam(defaultValue = "5") int size) {
    long after = cursor == null ? Long.MAX_VALUE : decode(cursor);
    List<Tx> rows = jdbc.sql("SELECT id, amount FROM tx WHERE account_no = ? AND id < ? ORDER BY id DESC LIMIT ?")
            .params(no, after, size + 1).query(Tx.class).list();      // 多讀一筆，用來判斷還有沒有下一頁
    List<Tx> items = rows.subList(0, Math.min(size, rows.size()));
    String next = rows.size() > size ? encode(items.get(items.size() - 1).id()) : null;
    return new CursorPage(items, next);
}
// encode(46) 把 "id:46" 用不補等號的 URL 安全 Base64 編碼

多讀一筆（size + 1）是為了知道後面還有沒有：讀到 6 筆就表示還有下一頁，只回前 5 筆；不到 6 筆，nextCursor 就是 null。剛好最後一頁是滿的 5 筆時，也不會多給一個「點下去是空的」游標。實跑，同樣在第一頁之後插入一筆新交易：

$ curl 'http://127.0.0.1:9579/v1/accounts/0000001234/txs/scroll?size=5'
{"items":[{"id":50,…},{"id":49,…},{"id":48,…},{"id":47,…},{"id":46,…}],"nextCursor":"aWQ6NDY"}

（這時插入 id 51）

{"items":[{"id":45,…},{"id":44,…},{"id":43,…},{"id":42,…},{"id":41,"amount":5170.00}],"nextCursor":"aWQ6NDE"}

aWQ6NDY 解開就是 id:46。第二頁從 45 開始，新插入的 51 不影響。Spring Data 也內建這種做法：Repository 方法收 KeysetScrollPosition、回 Window，用 ScrollPosition.keyset() 從頭開始；注意鍵集在可為 null 的屬性上會有意料外的結果。出處

偏移分頁鍵集分頁（游標）
用戶端帶什麼page、size上一頁給的 nextCursor
翻到很後面越來越慢（實測 90 萬偏移約 497 毫秒）一樣快（約 0.05 毫秒）
途中有新增、刪除會重複或漏掉不受影響
跳頁、總頁數可以不行，只能下一頁
適合資料量不大的後台表格無限捲動、大表、會一直新增的明細

排序欄位用 tx_date，但同一天有很多筆。鍵集分頁要怎麼處理？

  • 不用處理，日期的精確度已經足夠
  • 改回 OFFSET，用筆數補足重複的部分
  • 把每頁筆數調大，讓同一天落在同頁
  • 排序與游標都再接上唯一的 id

排序值有重複時，「排在這筆之後」不明確，同一天的資料可能被跳過或重複。排序改成 (tx_date, id)，讓每一列的位置唯一。

為什麼游標要做成用戶端不必看懂的字串，而不是直接開放 ?afterId=46？

  • Base64 編碼比直接寫數字還短
  • 這樣比較安全，別人無法解開內容
  • 日後換排序鍵或格式，用戶端都不用改
  • HTTP 規定查詢參數不能直接放數字

用戶端只負責把字串帶回來，伺服器日後把內容改成 (tx_date, id) 也不影響用戶端。Base64 不是加密，不能拿來當安全手段。

範例查詢 LIMIT size + 1，多讀的那一筆用來做什麼？

  • 判斷後面還有沒有下一頁
  • 補償偏移分頁漏掉的那筆
  • 計算總筆數
  • 當作下一頁的第一筆回給用戶端

讀到 size+1 筆就表示還有下一頁，只回前 size 筆、給 nextCursor；不到就給 null。最後一頁剛好滿的時候，也不會多給一個空的下一頁。

讀完第一頁（nextCursor 是 aWQ6NDY）後插入 id 51，再帶這個游標讀下一頁，實跑第一筆是哪個 id？

  • 51
  • 46
  • 45
  • 50

游標代表「id 46 之後」，條件 id < 46，所以從 45 開始，新插入的 51 不影響。偏移分頁同樣情況會讀到 46 兩次。

重送

為什麼轉帳需要冪等鍵

App 送出轉帳，伺服器扣款成功，回應卻在路上斷了。App 只看到逾時，不知道錢扣了沒，自動重送一次，結果扣了兩次。POST 本身不保證冪等（冪等：同一個操作做一次和做很多次，對伺服器的效果一樣；定義見〈網路與 HTTP 面試題：三向交握、TLS、REST 對 gRPC〉），要靠應用層補上：用戶端替每一筆操作產生一個唯一編號，放在 Idempotency-Key 標頭，重送時帶同一個；伺服器看過這個編號，就不再做一次，直接回上次的結果。這個編號叫冪等鍵。

它目前沒有正式標準。IETF（制定網路標準的組織）的草案 draft-ietf-httpapi-idempotency-key-header 最新是第 07 版，2026 年 4 月 18 日起已是過期狀態，下面的規則都出自這份草案，不是 RFC；業界的實作（例如 Stripe 的做法）見面試集〈系統設計：秒殺與限流〉。冪等鍵是用戶端產生的唯一值，資源用它辨識同一個請求的後續重試。出處 幾條重點：

  • 值必須是結構化標頭的字串，所以要加雙引號：Idempotency-Key: "8e0f6c1a-…"；建議用 UUID（隨機產生、幾乎不會重複的 128 位元編號）或類似的隨機編號。
  • 重試時回第一次的結果，不管成功或失敗。
  • API 文件規定要帶卻沒帶：回 400。
  • 同一個鍵配了不同內容：回 422。
  • 第一次還在處理、重試就到了：回 409。
  • 鍵可以有保存期限，要寫在 API 文件裡。出處

注意草案裡的 SHOULD（應該）不是 MUST（必須），狀態碼是建議。422 在 RFC 9110 的名字是 Unprocessable Content（伺服器無法處理請求裡的指示）出處；Spring Framework 7 把 HttpStatus.UNPROCESSABLE_ENTITY 標成棄用，改用 UNPROCESSABLE_CONTENT。出處

轉帳成功但回應在路上斷了，App 自動重送。沒有任何防護時，最可能的後果是？

  • 伺服器自動判斷是重送
  • HTTP 協定會擋下第二次 POST
  • 伺服器再扣一次，總共扣兩次
  • 第二次一定回 409

POST 本身不保證冪等，伺服器分不出這是重送還是新的一筆。要靠應用層的冪等鍵才能認出來。

冪等鍵是誰產生的？

  • 用戶端，送出前自己產生
  • 伺服器在第一次回應時發給用戶端
  • 資料庫的自動遞增主鍵
  • 負載平衡器

草案：a unique value generated by the client。用戶端在送出前就產生，重送時才能帶同一個；建議用 UUID。

同一個冪等鍵第二次進來，但轉帳金額從 3000 變成 5000。草案建議回什麼？

  • 201，照新的金額再轉一次
  • 409 Conflict，請用戶端稍後再試
  • 422，這個鍵配了不同內容
  • 200，回第一次的那個結果

草案：reuse an idempotency key with a different request payload 時 SHOULD 回 422。409 是第一次還在處理、重試就到的情況。

第一次請求還在處理，同一個冪等鍵的重試就到了。草案建議回什麼？

  • 400 Bad Request
  • 422 Unprocessable Content
  • 201，再處理一次
  • 409 Conflict

草案：retried while the original request is still being processed 時 SHOULD 回 409，用戶端不用改請求，稍後再試。

第一次轉帳因為餘額不足失敗（422）。用同一個冪等鍵重送，依草案應該回什麼？

  • 這次重新檢查餘額，夠了就轉
  • 回第一次的錯誤，同一個 422
  • 一律回 409，請稍後再試
  • 回 200 和空白的內容

草案：respond with the result of the previously completed operation, success or an error。失敗也算結果，範例實跑補足餘額後原樣重送，拿到的還是同一個 422。草案也說用戶端 MUST correct the requests before performing a retry；同一個鍵配上改過的內容又會變成 422，所以要重新嘗試就換一個新的鍵。

在 Spring 裡實作

@PostMapping("/transfers")
ResponseEntity<TransferResult> transfer(@RequestHeader(name = "Idempotency-Key", required = false) String key,
                                        @Valid @RequestBody TransferRequest req) {
    if (key == null) throw problem(HttpStatus.BAD_REQUEST, "缺少 Idempotency-Key 標頭");
    synchronized (this) {                       // 示範用：同一台機器上排隊；多台伺服器要靠資料庫唯一鍵
        Saved saved = done.get(key);
        if (saved == null) {                    // 第一次看到這個冪等鍵：真的轉帳，結果不論成敗都存起來
            try {
                BigDecimal after = bank.transfer(req.from(), req.to(), req.amount());
                saved = new Saved(req, new TransferResult("T-" + seq.incrementAndGet(), req.from(), after), null);
            } catch (ErrorResponseException e) {
                if (!e.getStatusCode().is4xxClientError()) throw e;   // 5xx 不存，讓用戶端可以重試
                saved = new Saved(req, null, e);  // 4xx（例如餘額不足）也是「完成了的結果」
            }
            done.put(key, saved);
        } else if (!Objects.equals(saved.request(), req)) {   // 同一個冪等鍵、不同內容：拒絕
            throw problem(HttpStatus.UNPROCESSABLE_CONTENT, "這個 Idempotency-Key 已用於另一筆不同的請求");
        }
        if (saved.error() != null) throw saved.error();       // 重送：回第一次的錯誤
        return ResponseEntity.status(HttpStatus.CREATED).body(saved.result());   // 重送：回第一次的結果，不再扣款
    }
}

private static ErrorResponseException problem(HttpStatus status, String detail) {
    return new ErrorResponseException(status, ProblemDetail.forStatusAndDetail(status, detail), null);
}

done 是一個 ConcurrentHashMap<String, Saved>，存「冪等鍵 → 當時的請求內容與結果」；Saved 是 record Saved(TransferRequest request, TransferResult result, ErrorResponseException error)，成功時存結果，4xx 時存那個錯誤，這樣重送才能照草案回第一次的結果「不管成功或失敗」。5xx 不存，伺服器自己出錯時讓用戶端可以再試。比對請求內容用的是 record 自動產生的 equals；草案也允許改存內容的「指紋」（fingerprint，例如整個內容算出的雜湊值）。實跑（A-001 原有 10,000 元）：

範例為了好讀，有三個地方跟正式環境不同，要知道：

  • 存在記憶體裡：重開機就忘了，多台伺服器之間也不共用。正式做法是存資料庫，冪等鍵欄位加唯一索引，讓資料庫擋第二筆；用 Redis 的 SET … NX 做法見〈系統設計：秒殺與限流〉。
  • 用 synchronized 讓同一個鍵排隊：所以範例的同時重試是「等第一個做完、拿同一個結果」，而不是草案建議的 409。資料庫做法通常是先寫一列「處理中」，第二個請求看到「處理中」就回 409。
  • 沒有保存期限：正式環境要設期限並寫進文件，見上面草案那條。存了錯誤結果之後，期限也決定了「同一個鍵多久之後才能重新用」。

五個請求同時帶同一個冪等鍵進來，範例實跑的結果是？

  • 五個都扣款，餘額少 500
  • 只扣一次，都拿到 T-3
  • 一個成功，四個回 409
  • 五個都失敗，回 500

synchronized 讓它們排隊，第一個做完存起來，後面四個直接拿同一個結果；A-002 從 5000 變 4900。草案建議的是「還在處理就回 409」，範例選了排隊的簡化做法。

錯誤格式

RFC 9457 的 ProblemDetail

每支 API 自己發明一種錯誤格式，用戶端就得每支各寫一套解析。RFC 9457 定了一種通用的格式，叫 problem detail：在 HTTP 回應裡放機器讀得懂的錯誤細節，HTTP API 就不用各自定義新的錯誤格式。它取代舊的 RFC 7807。出處 媒體類型是 application/problem+json，五個標準欄位：

欄位意思範例實跑的值
type錯誤「種類」的識別網址；沒寫等於 about:blankhttps://bank.example/problems/insufficient-funds
title這個種類的簡短說明，同一種錯誤每次都一樣餘額不足
statusHTTP 狀態碼，方便讀，必須跟真正的狀態碼一致422
detail「這一次」發生了什麼，給人看帳戶 A-001 餘額 7000，不足以轉出 9000
instance這一次錯誤的識別/v2/transfers

表裡三條規則：

  • 沒有 type 時，當作 about:blank
  • status 必須跟真正的 HTTP 狀態碼一致
  • 用戶端不該解析 detail 取資訊；要取資訊用擴充欄位，比較不容易出錯 出處

最後這條是重點：程式要判斷的東西放進自訂欄位，別讓用戶端去切 detail 字串。

RFC 9457 的錯誤回應，Content-Type 應該是什麼？

  • application/json
  • application/problem+json
  • text/plain
  • application/json+problem

JSON 格式的 problem details 用 application/problem+json 這個媒體類型。實跑的 404、400、422 都是這個。

ProblemDetail 沒有 type 欄位時，依 RFC 9457 代表什麼？

  • 格式錯誤，用戶端要整個丟棄
  • 代表伺服器內部發生錯誤
  • about:blank
  • 代表這次其實沒有錯誤

原句：When this member is not present, its value is assumed to be "about:blank"；about:blank 表示除了 HTTP 狀態碼沒有額外意義。

用戶端想知道「餘額還剩多少」，以便顯示給使用者。依 RFC 9457 的建議，該從哪裡讀？

  • 用正規表示式切 detail 字串
  • 從 title 裡找數字
  • 從 instance 解析
  • 伺服器另外放一個擴充欄位

用戶端不該解析 detail 取資訊，擴充欄位比較不容易出錯。範例放了 "balance":7000 這個擴充欄位。

ProblemDetail 裡的 status 寫 422，HTTP 回應的狀態碼卻是 200。這樣可以嗎？

  • 可以，status 只是參考
  • 不行，兩邊必須是同一個狀態碼
  • 可以，用戶端會以 body 為準
  • 只要 type 有寫就可以

產生錯誤回應的一方必須在實際的 HTTP 回應用同一個狀態碼，不懂這個格式的通用 HTTP 軟體才能照狀態碼正確運作。

Spring 怎麼產生 ProblemDetail

Spring 這邊有四個元件：出處

  • ProblemDetail：資料容器
  • ErrorResponse：讓例外說出自己對到什麼狀態碼與內容的介面，Spring MVC 的例外全都實作它
  • ErrorResponseException：它的基本實作
  • ResponseEntityExceptionHandler：處理這些例外的 @ControllerAdvice 基底類別

Spring Boot 這邊，設定 spring.mvc.problemdetails.enabled=true 就會自動註冊一個處理器，內建例外都回 ProblemDetail。出處 範例要再加欄位錯誤，所以自己繼承 ResponseEntityExceptionHandler；Boot 那個自動註冊的處理器帶有「容器裡沒有同型別才建立」的條件（〈Spring Boot 自動組態與 Actuator〉講的 @ConditionalOnMissingBean），看到範例自己的就退開。出處

業務錯誤則讓例外直接繼承 ErrorResponseException，自己填好 type、title 與擴充欄位：

public class InsufficientFundsException extends ErrorResponseException {
    public InsufficientFundsException(String account, BigDecimal balance, BigDecimal amount) {
        super(HttpStatus.UNPROCESSABLE_CONTENT, problem(account, balance, amount), null);
    }

    private static ProblemDetail problem(String account, BigDecimal balance, BigDecimal amount) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_CONTENT,
                "帳戶 " + account + " 餘額 " + balance + "，不足以轉出 " + amount);
        pd.setType(URI.create("https://bank.example/problems/insufficient-funds"));
        pd.setTitle("餘額不足");
        pd.setProperty("balance", balance);           // 擴充成員：用戶端可以直接讀
        return pd;
    }
}

setProperty 放進去的值，會被攤平成最外層的 JSON 欄位：Spring 註冊的 Jackson 設定會把這個 properties Map 攤開，在回應裡成為最外層的 JSON 屬性。出處 驗證失敗則覆寫 handleMethodArgumentNotValid，在 Spring 已經做好的 ProblemDetail 上補一個 errors 欄位：

@RestControllerAdvice
public class ApiErrors extends ResponseEntityExceptionHandler {
    record FieldProblem(String field, String message) {}

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
            HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ex.getBody();                       // Spring 已經填好 title、status、detail
        List<FieldProblem> errors = ex.getFieldErrors().stream()
                .map(e -> new FieldProblem(e.getField(), e.getDefaultMessage()))
                .sorted((a, b) -> a.field().compareTo(b.field()))
                .toList();
        pd.setProperty("errors", errors);                      // 擴充成員：哪個欄位、錯在哪
        return handleExceptionInternal(ex, pd, headers, status, request);
    }
}

實跑兩種錯誤（餘額不足的 422 見上一節的輸出）：

（找不到帳戶：TransferService 丟 ResponseStatusException(NOT_FOUND, …)）
HTTP/1.1 404
Content-Type: application/problem+json
{"detail":"帳戶 X-999 不存在","instance":"/v2/accounts/X-999","status":404,"title":"Not Found"}

（驗證失敗：to 空白、amount 0）
HTTP/1.1 400
{"detail":"Invalid request content.","instance":"/v2/transfers","status":400,"title":"Bad Request",
 "errors":[{"field":"amount","message":"至少 1 元"},{"field":"to","message":"不可空白"}]}

用戶端必須忽略看不懂的擴充欄位，所以加 balance、errors 不會弄壞只認得標準欄位的用戶端；RFC 9457 自己的驗證錯誤範例用的也是 errors 這個名字。出處 沒有加 errors 之前，同一個請求只會拿到 "detail":"Invalid request content."，用戶端根本不知道是哪個欄位錯。

注意實跑的 404、400 沒有 type 欄位。這是 Spring Framework 7 的改變：7.0 的 ProblemDetail 預設不設定 type（依規格，沒有時當作 about:blank），出處 6.2 版的欄位預設值則是 about:blank（private URI type = BLANK_TYPE;）出處，所以 Framework 6.2（Boot 3.5）同一個 404 會回 "type":"about:blank"，欄位順序也可能不同。兩種寫法依 RFC 意思相同，用戶端不該依賴 type 一定存在，也不該依賴欄位順序。另外，422 的 title 是 Unprocessable Content，用的是 RFC 9110 的新名字。

最後一個提醒：problem detail 不是底層實作的除錯工具。出處 例外的堆疊、SQL 錯誤訊息不要放進 detail，那是給攻擊者的線索；記在伺服器的記錄檔就好。

範例自己繼承了 ResponseEntityExceptionHandler，又設了 spring.mvc.problemdetails.enabled=true。Boot 會再註冊一個自己的處理器嗎？

  • 會，兩個都生效、各處理一半
  • 會，然後啟動失敗
  • 會，而且 Boot 的優先
  • 不會，看到同型別就退開

Boot 那個處理器的條件是 @ConditionalOnMissingBean(ResponseEntityExceptionHandler.class)：容器裡已經有一個，就不建立（Boot 4.1.1 原始碼 WebMvcAutoConfiguration 的 ProblemDetailsErrorHandlingConfiguration）。

pd.setProperty("balance", balance) 在實跑的 JSON 裡長什麼樣？

  • 最外層多一個 "balance":7000
  • 包在 "properties":{"balance":7000} 裡
  • 寫進 detail 字串
  • 放在回應標頭

Spring 的 Jackson 設定把 properties 這個 Map 攤平成最外層欄位，實跑是 …,"type":"…","balance":7000}。

沒有覆寫 handleMethodArgumentNotValid 時，驗證失敗的 ProblemDetail 缺了什麼？

  • status 欄位
  • Content-Type 標頭
  • title 欄位
  • 哪個欄位錯、錯在哪

預設只有 "detail":"Invalid request content."。範例把 getFieldErrors() 整理成 errors 擴充欄位，實跑看得到 amount「至少 1 元」、to「不可空白」。

Spring Boot 4.1 實跑的 404 ProblemDetail 沒有 type 欄位，Boot 3.5 卻有 "type":"about:blank"。用戶端該怎麼看？

  • Boot 4.1 漏了欄位，是錯誤
  • 意思相同，type 可能不存在
  • 要升級用戶端才讀得懂
  • 沒有 type 表示不是錯誤

Framework 7 的 ProblemDetail 預設不設 type；RFC 9457 規定沒有 type 時當作 about:blank。兩者意思一樣，用戶端讀不到 type 就當 about:blank。

  • 好，detail 就是給工程師看的
  • 不好，會把內部實作洩漏出去
  • 好，只要狀態碼是 500

problem detail 不是底層實作的除錯工具。堆疊、SQL 訊息記在伺服器記錄檔，detail 只寫幫用戶端修正的話。

文件

OpenAPI 與 springdoc

OpenAPI 是描述 HTTP API 的標準格式（路徑、參數、請求與回應的長相，用 JSON 或 YAML 寫），讓人和電腦不用看原始碼就能理解服務的能力。出處 有了它，可以產生互動式文件頁（Swagger UI）、各語言的用戶端程式碼，也能在 CI 比對新舊版找出破壞相容的變更。

springdoc-openapi 在執行期檢查應用程式，從 Spring 設定、類別結構與各種註解推斷 API 的語意：

  • 它是社群專案，不是 Spring 官方維護的
  • 版本要對：springdoc-openapi 3.x 相容 Spring Boot 4，Boot 3.x 用 2.x 出處

加上 starter 不用任何設定，/v3/api-docs 就是 JSON 文件，/swagger-ui.html 會轉到互動頁（實跑回 302 到 /swagger-ui/index.html）。

實跑 springdoc 3.1.1 產生的文件是 "openapi":"3.1.0"。轉帳的請求格式直接從 record 與驗證註解推出來：

"TransferRequest": {
  "type": "object",
  "properties": {
    "from":   { "type": "string", "minLength": 1 },
    "to":     { "type": "string", "minLength": 1 },
    "amount": { "type": "number", "minimum": 1 }
  },
  "required": [ "amount", "from", "to" ]
}

@NotBlank 變成 minLength: 1 加上必填，@DecimalMin("1") 變成 minimum: 1，@NotNull 讓 amount 進了 required。如果只寫 @DecimalMin，文件裡 amount 不會列為必填，因為 @DecimalMin 本來就不擋 null出處，不帶 amount 的請求會通過驗證；所以要再加 @NotNull。產生出來的文件也能幫你看出驗證的漏洞。版本放標頭時，文件還會自動列出 API-Version 這個標頭參數，可選值是 "2"、"1"、"1.0.0"。

自動推斷也有推錯的地方。轉帳方法回的是 ResponseEntity，springdoc 看不出實際狀態碼，沒加註解前文件寫成 "200"，實際卻回 201；錯誤回應也完全沒列。要用 swagger 的註解補上：

@Operation(summary = "轉帳", description = "同一個 Idempotency-Key 重送只會扣一次款")
@ApiResponse(responseCode = "201", description = "轉帳成功（重送時回第一次的結果）")
@ApiResponse(responseCode = "422", description = "餘額不足，或同一個冪等鍵配了不同內容",
        content = @Content(mediaType = "application/problem+json", schema = @Schema(implementation = ProblemDetail.class)))
@PostMapping("/transfers")

422 那行不寫 content 的話，springdoc 會把 422 的內容也標成 TransferResult（沿用方法的回傳型別），等於說「錯誤時回轉帳結果」；要補上 application/problem+json 與 ProblemDetail 才對。版本放路徑時，springdoc 3.1.1 把路徑列成 /1/accounts/{id}、/2/accounts/{id} 與 /{version}/transfers（實跑），跟真正的 /v1/… 對不起來，要另外調整。結論：自動產生的文件是起點，上線前要對照實際行為看一遍。

只寫 @DecimalMin("1") 時，springdoc 產生的文件裡 amount 不在 required。這反映了什麼？

  • 不帶 amount 也會通過驗證
  • springdoc 讀不懂驗證註解
  • OpenAPI 不支援必填
  • BigDecimal 不能設成必填

@DecimalMin 把 null 當成通過，所以產生的文件標它不是必填，正確反映了驗證的漏洞；範例補 @NotNull 後，amount 才進了 required。

轉帳方法實際回 201，springdoc 沒加註解前的文件卻寫 200。怎麼修？

  • 用 @ApiResponse 寫明 201
  • 把方法的回應改回 200
  • 升級 springdoc 就會自動修好
  • 直接手改 /v3/api-docs 的輸出

回傳 ResponseEntity 時，springdoc 看不出實際狀態碼；用 swagger 的 @ApiResponse 註解寫清楚 201 與各種錯誤。

422 的 @ApiResponse 沒寫 content，實跑文件把它的內容標成什麼？

  • ProblemDetail
  • TransferResult
  • 空的，什麼都沒有
  • text/plain 純文字

沒指定時 springdoc 沿用方法的回傳型別 TransferResult，變成「錯誤時回轉帳結果」。要用 @Content 指定 application/problem+json 與 ProblemDetail。

選型

REST、gRPC、GraphQL

三者的基本比較（契約、序列化、HTTP/2）面試集〈網路與 HTTP 面試題：三向交握、TLS、REST 對 gRPC〉已經整理過，這裡用改版、錯誤、分頁、文件四個主題再對一次：

REST（HTTP＋JSON）gRPCGraphQL

錯誤HTTP 狀態碼＋ProblemDetailgRPC 自己定義的一組狀態碼出處有資料就回 2xx，錯誤放在回應的 errors（HTTP 還沒有代表「部分成功」的狀態碼）出處
分頁查詢參數帶頁碼或游標請求訊息帶游標，或改用串流（含雙向串流：兩邊各用一條讀寫串流送一連串訊息）出處常見用游標的連線模式

表裡「gRPC 換服務或套件名稱」「GraphQL 常見用游標的連線模式」兩格，以及「適合」那一列，是常見的做法，不是各自規格的硬性規定。銀行對外的開放 API 常見選 REST：工具最普遍、狀態碼與快取都是 HTTP 原生的；內部的高流量服務之間再考慮 gRPC。

GraphQL 對 API 版本的立場是？

  • 傾向不開版本，讓 schema 演進
  • 規定版本一律放在路徑的第一段
  • 規定用 Accept 標頭的參數帶版本
  • 每次改 schema 都要開一個新版

graphql.org：GraphQL takes a strong opinion on avoiding versioning，靠新增欄位與標記棄用讓 schema 持續演進。

內部兩個服務之間要低延遲、還要雙向一直傳訊息，三者中最適合哪一個？

  • REST 加偏移分頁
  • GraphQL 查詢
  • gRPC 的雙向串流
  • REST 加 ProblemDetail

gRPC 用二進位的 Protocol Buffers，內建雙向串流（兩邊都能送一連串訊息），適合內部服務之間。

重點整理

  • 只有破壞相容的變更才開新版，加欄位通常不用。版本放路徑最直觀、放標頭網址不變、放媒體類型用的是內容協商；沒有標準，選一種。
  • Spring Framework 7 用 @GetMapping(version = "2") 讓同一個路徑對到不同版本，解析方式在 configureApiVersioning 設定；不支援的版本、該帶沒帶都回 400。淘汰舊版先送 Deprecation、Sunset 與 Link 標頭。
  • 偏移分頁能跳頁，但途中新增會重複、刪除會漏掉，而且越後面越慢（偏移 90 萬讀了 900,020 列）。鍵集分頁接在上一頁最後一筆之後，只讀 20 列；排序鍵要唯一，對外給不透明的游標，多讀一筆判斷有沒有下一頁。
  • 冪等鍵由用戶端產生（建議 UUID），重送帶同一個，伺服器回第一次的結果，成功或 4xx 錯誤都要存。依過期的 IETF 草案：沒帶 400、同鍵不同內容 422、還在處理 409、保存期限寫進文件。正式環境存資料庫、冪等鍵加唯一索引。
  • RFC 9457 的 ProblemDetail：application/problem+json，沒有 type 等於 about:blank，status 要跟真正的狀態碼一致，程式要用的資訊放擴充欄位，不放堆疊。Spring 用 ErrorResponseException 與 ResponseEntityExceptionHandler；Framework 7 預設不輸出 type。
  • springdoc 3.x 對應 Boot 4，從程式碼與驗證註解產生 OpenAPI；狀態碼與錯誤回應要用 @ApiResponse 補。對外公開常見選 REST，內部低延遲與串流考慮 gRPC，前端欄位組合多變考慮 GraphQL。
