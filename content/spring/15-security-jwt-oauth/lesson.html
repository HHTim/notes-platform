三個角色、三種設定

以下用 Spring Security 7.1 把 OAuth 2.0 的三個伺服器端角色各架一次；JWT、OAuth 2.0、PKCE 的定義見〈認證與安全面試題：JWT、OAuth 2.0、OIDC 與密碼保存〉。Filter 鏈與路徑規則見〈Spring Security 認證與授權〉。

Spring Boot 4 的 starter 名字多了 security-，舊名字的描述寫著已棄用（deprecated in favor of spring-boot-starter-security-oauth2-resource-server）。出處

行動銀行 App 讓使用者登入，再拿權杖呼叫帳戶 API。「放登入頁、發權杖」的那台服務是哪個角色？

  • 資源伺服器，因為它保護使用者的資料
  • 授權伺服器，負責認證與簽發權杖
  • 用戶端，因為登入頁是它畫出來的
  • 資源擁有者，也就是銀行本身

帳戶 API 是資源伺服器、App 是用戶端、使用者本人是資源擁有者。

一個只提供 REST API、收 Authorization: Bearer 權杖的 Spring Boot 4 服務，該加哪個 starter？

  • spring-boot-starter-security-oauth2-client
  • spring-boot-starter-security-oauth2-authorization-server
  • spring-boot-starter-security-oauth2-resource-server
  • 只要 spring-boot-starter-webmvc，驗權杖的 Filter 自己寫

收權杖、驗權杖的是資源伺服器；client 去拿權杖，authorization-server 發權杖。

網銀前台要「用銀行的統一帳號登入」：按登入後被導去統一登入頁，回來後就是登入狀態。前台用哪個設定？

  • oauth2Login()
  • oauth2ResourceServer()
  • oauth2AuthorizationServer()
  • httpBasic()

把使用者導去別人的登入頁、帶結果回來，是用戶端的工作。

簽章、時間、誰發的、發給誰

JWT 的結構與驗簽：拆一張來看

第一個示範專案是帳戶 API，用 openssl 自己產了一對 2048 位元 RSA 金鑰：私鑰簽 JWT（模擬授權伺服器），公鑰驗。登入 POST /token 拿到一張權杖，三段各自 base64url 解碼：

=== JWT 的三段
段數：3
標頭：{"alg":"RS256"}
聲明：{"iss":"https://login.bank.example","sub":"alice","aud":"core-banking","exp":1790939460,"iat":1790939160,"scope":"accounts:read"}
簽章長度：256 位元組

RFC 7519：JWT 是「以句點分隔的一串網址安全片段，每段都是 base64url 編碼」（a sequence of URL-safe parts separated by period ('.') characters. Each part contains a base64url-encoded value.）。出處 標頭的 RS256 是「RSA 簽章搭配 SHA-256」；第三段 256 位元組，正好是 2048 位元 RSA 金鑰的長度。前兩段只是編碼，誰都解得開，機密不放進 JWT。

資源伺服器怎麼驗

JwtDecoder jwtDecoder() {
    NimbusJwtDecoder decoder = NimbusJwtDecoder.withPublicKey(publicKey).build();   // 只接受 RS256
    OAuth2TokenValidator<Jwt> audienceOk =
            new JwtClaimValidator<java.util.List<String>>("aud", aud -> aud != null && aud.contains(audience));
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
            JwtValidators.createDefaultWithIssuer(issuer), audienceOk));          // exp、nbf、iss，再加 aud
    return decoder;
}
  • NimbusJwtDecoder.withPublicKey 是文件的「信任單一公鑰」寫法（Trusting a Single Asymmetric Key）。出處 驗證端手上只有一把 RSA 公鑰，權杖標頭宣告什麼演算法都沒用。
  • createDefaultWithIssuer 檢查 exp、nbf 與 iss。文件列的預設行為是驗簽章、「驗證 exp 與 nbf 時間戳記以及 iss 聲明」、「把每個 scope 對應成前綴 SCOPE_ 的權限」（Validate the JWT's exp and nbf timestamps and the JWT's iss claim, and Map each scope to an authority with the prefix SCOPE_）。出處
  • aud 預設不驗，所以另外加 JwtClaimValidator：aud 裡沒有 core-banking 就拒絕。發給貸款服務的權杖，不該拿來呼叫帳戶 API。

測試自己造出各種有問題的權杖（輸出省略 error_uri、resource_metadata 兩個欄位，「…」代表 An error occurred while attempting to decode the Jwt: ）：

=== 驗簽與聲明檢查
過期 30 秒        → 200  {"balance":5000,"owner":"alice"}
過期 2 分鐘       → 401  WWW-Authenticate: Bearer error="invalid_token", error_description="…Jwt expired at 2026-10-02T11:04:00Z"
aud 是別的服務    → 401  WWW-Authenticate: Bearer error="invalid_token", error_description="…The aud claim is not valid"
iss 不對          → 401  WWW-Authenticate: Bearer error="invalid_token", error_description="…The iss claim is not valid"
竄改聲明          → 401  WWW-Authenticate: Bearer error="invalid_token", error_description="…Signed JWT rejected: Invalid signature"
alg 改成 none     → 401  WWW-Authenticate: Bearer error="invalid_token", error_description="Unsupported algorithm of none"
別把金鑰簽的      → 401  WWW-Authenticate: Bearer error="invalid_token", error_description="…Signed JWT rejected: Invalid signature"

另一個測試把標頭改成 HS256，拿公開的 RSA 公鑰當 HMAC 金鑰簽名（演算法混淆）：

alg 換成 HS256 → 401  Bearer error="invalid_token", error_description="…Signed JWT rejected: Another algorithm expected, or no matching key(s) found"
  • 過期 30 秒還能過：文件寫「資源伺服器預設容許 60 秒的時鐘誤差」（By default, Resource Server configures a clock skew of 60 seconds.）出處。
  • 竄改聲明：把 alice 的 scope 偷加 transfers:write，簽章不動，驗簽失敗。簽章涵蓋標頭加聲明，改一個字就對不上。
  • alg 改成 none 或 HS256：都被擋，這就是面試集那課 RFC 8725 講的「演算法由驗證端寫死」。
  • 這些全是 401 加 error="invalid_token"。RFC 7519：驗證步驟「任何一步失敗，JWT 就必須被拒絕」（If any of the listed steps fail, then the JWT MUST be rejected）。出處

演算法由驗證端決定；exp、nbf、iss 預設檢查（容許 60 秒誤差）；aud 要自己加；任一關失敗都是 401 invalid_token

把這課 API 簽出的 JWT 第二段做 base64url 解碼，會看到什麼？

  • 亂碼，要有私鑰才解得開
  • 看得懂的 JSON 聲明，誰都能解
  • 聲明的 SHA-256 雜湊值
  • alice 的密碼經過 bcrypt 的結果

第二段只是 base64url 編碼的聲明 JSON，誰都能解。簽章保證沒被改，不保證沒被看。

這課的權杖第三段解碼後是 256 位元組，為什麼？

  • RSA 簽章跟金鑰一樣長：2048 位元
  • 因為聲明的內容剛好 256 個字元長
  • JWT 規格規定簽章一律 256 位元組
  • SHA-256 的輸出本來就是 256 位元組

RSA 簽章長度等於金鑰長度。SHA-256 的輸出是 256 位元（32 位元組）。

權杖在 30 秒前過期，這課的 API 還是回 200。原因是？

  • 資源伺服器預設根本不檢查 exp
  • MockMvc 測試的時鐘跟真實時間不同
  • 過期的權杖會被資源伺服器自動續期
  • 預設容許 60 秒的時鐘誤差，還在寬限內

文件寫預設時鐘誤差 60 秒；實跑時過期 2 分鐘的就被擋。

同一個授權伺服器簽的、簽章正確、但 aud 是 loan-service 的權杖，拿來呼叫這課的帳戶 API。結果是？

  • 200，同一個授權伺服器簽的就能用
  • 401，因為 aud 檢查不通過
  • 403，因為 alice 沒有貸款權限
  • 500，驗證器拋出未處理的例外

這課自己加了 JwtClaimValidator 檢查 aud，訊息 The aud claim is not valid；權杖本身不能用在這裡，所以是 401 不是 403。

如果 JwtDecoder 沒有另外加 aud 檢查，上一題那張權杖會怎樣？

  • 還是 401，因為預設會驗 iss 和 aud
  • 啟動時就會報錯，要求一定要設 aud
  • 驗證通過，接著照 scope 判斷權限
  • 還是 401，因為 loan-service 不在白名單

文件列的預設檢查是 exp、nbf 與 iss，aud 要自己加（或用 Boot 的 audiences 屬性）。

攻擊者把 alice 權杖的 scope 改成多了 transfers:write，簽章原封不動。結果是？

  • 401，改過的內容跟簽章對不上
  • 200，因為簽章確實是授權伺服器簽的
  • 403，因為 alice 本來就沒有轉帳權限
  • 400，格式錯誤

簽章算的是原本的內容；改過就驗不過，走不到授權規則，所以是 401。

攻擊者把標頭改成 {"alg":"HS256"}，拿 API 公開的 RSA 公鑰當 HMAC 金鑰重簽。這課的 API 怎麼回？

  • 200，因為用的是正確的那把公鑰
  • 403，HS256 簽的權杖權限比較少
  • 500，伺服器不支援 HS256 所以出錯
  • 401，驗證端只接受 RS256

NimbusJwtDecoder.withPublicKey 只用 RSA 驗，實跑訊息 Another algorithm expected, or no matching key(s) found。

權杖的簽章、期限都對，但 iss 是 https://evil.example。為什麼被擋？

  • iss 規定必須是 localhost 才行
  • iss 不是設定的那個發行者，所以拒絕
  • 因為 evil 是關鍵字，會被過濾
  • 沒有被擋，iss 只是參考用的欄位

createDefaultWithIssuer 規定 iss 必須等於信任的那個授權伺服器。實跑：The iss claim is not valid。

下面哪一種情況，資源伺服器回 403 而不是 401？

  • 權杖過期超過一分鐘，而且簽章正確
  • 權杖的聲明被改過、簽章對不上
  • 請求完全沒有帶 Authorization 標頭
  • 權杖有效，但 scope 不夠

401 是「沒帶或權杖不可信」，403 是「知道你是誰，但你不能做這件事」，標頭寫 error="insufficient_scope"。

一支 API，兩條 Filter 鏈

資源伺服器的設定

@Bean
@Order(1)
SecurityFilterChain tokenEndpoint(HttpSecurity http) throws Exception {
    http
        .securityMatcher("/token")                           // 這條鏈只管 /token
        .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())                // 帳號密碼換 JWT
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(csrf -> csrf.disable());                       // 示範用；真的登入頁要防 CSRF
    return http.build();
}

@Bean
@Order(2)
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.GET, "/accounts/**").hasAuthority("SCOPE_accounts:read")
            .requestMatchers("/transfers/**").hasAuthority("SCOPE_transfers:write")
            .anyRequest().authenticated())
        .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults()))
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
    return http.build();
}
  • STATELESS：不建 Session，每個請求都靠權杖重新認證。
  • 兩條鏈分工：/token 那條只做帳號密碼登入（HTTP Basic），其他路徑只認 Bearer 權杖。一開始兩種寫在同一條鏈時，沒帶權杖的請求收到 WWW-Authenticate: Basic；拆開後才是下面的 Bearer。securityMatcher 決定一條鏈管哪些請求，@Order 決定先比對哪一條。
  • CSRF：API 那條沒關 CSRF，帶 Bearer 權杖的 POST 照樣能過。原始碼裡 OAuth2ResourceServerConfigurer 會呼叫 csrf.ignoringRequestMatchers(this.requestMatcher)，把帶 Bearer 權杖的請求排除在 CSRF 檢查外。出處 權杖要程式主動放進標頭、瀏覽器不會自動帶，這是〈網站安全三題：CORS、CSRF、密碼學〉講的前提。
=== 帶權杖呼叫 API
沒帶權杖  GET /accounts/alice → 401  WWW-Authenticate: Bearer
alice     GET /accounts/alice → 200  {"balance":5000,"owner":"alice"}
alice     GET /accounts/bob   → 403  WWW-Authenticate: Bearer error="insufficient_scope", error_description="The request requires higher privileges than provided by the access token."
alice     POST /transfers     → 403  WWW-Authenticate: Bearer error="insufficient_scope", error_description="The request requires higher privileges than provided by the access token."
carol     POST /transfers     → 200  轉帳受理，操作人 carol

alice 只有 accounts:read：查自己 200、轉帳 403；carol 有 transfers:write，轉帳 200。alice 查 bob 為什麼 403，下一段講。

正式環境：給 issuer-uri 就好

這課為了離線跑才自己放公鑰。正式環境的授權伺服器會公開它的公鑰，Spring Boot 只要：

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.bank.example
          audiences: core-banking

issuer-uri 驗 iss，audiences 驗 aud（Boot also has the audiences property for validating the aud claim）；授權伺服器換新金鑰時，「Spring Security 會自動輪替」驗證用的金鑰（Spring Security will automatically rotate the keys used to validate JWTs.）。出處

權杖裡的權限怎麼變成 Spring 的權限

預設把 scope 每一項加上 SCOPE_。角色放在別的聲明（例如 roles）時，換一個 JwtGrantedAuthoritiesConverter，文件的範例就是 setAuthoritiesClaimName。出處 這課對一張帶 "roles":["TELLER","AUDITOR"] 的 JWT 實跑：預設轉換得到 SCOPE_accounts:read；改用 setAuthoritiesClaimName("roles") 加 setAuthorityPrefix("ROLE_") 後得到 ROLE_TELLER、ROLE_AUDITOR，兩次都另外多一個 FACTOR_BEARER。FACTOR_BEARER 是 Spring Security 7 為多因素認證加的：用密碼登入時，會自動加上密碼那一種 FactorGrantedAuthority（when a user authenticates using a password a FactorGrantedAuthority … is automatically added）。出處 實跑時權杖認證是 FACTOR_BEARER（原始碼裡的常數 BEARER_AUTHORITY = "FACTOR_BEARER"出處）、密碼登入是 FACTOR_PASSWORD；這課的 /token 寫 scope 時特意濾掉 FACTOR_ 開頭的。

兩條鏈：/token 用 Basic、API 用 Bearer；帶 Bearer 的請求不做 CSRF 檢查；權限預設是 SCOPE_ 加 scope

同一條 Filter 鏈同時開了 httpBasic() 和 oauth2ResourceServer()，沒帶憑證的請求打 API。實跑時的 WWW-Authenticate 是？

  • Bearer，因為資源伺服器的優先
  • Basic realm="Realm"
  • Basic 與 Bearer 兩個標頭都有
  • 沒有這個標頭，只回 401

實跑是 Basic realm="Realm"。拆成兩條鏈、API 那條只留 oauth2ResourceServer 之後，才回 Bearer。

資源伺服器那條鏈沒寫 csrf(...)，carol 帶 Bearer 權杖 POST /transfers、沒帶 CSRF 權杖。結果是？

  • 403，因為沒帶 CSRF 權杖
  • 401，CSRF 失敗被當成認證失敗
  • 200，不檢查 CSRF
  • 要看 carol 之前有沒有用瀏覽器登入

OAuth2ResourceServerConfigurer 把帶 Bearer 權杖的請求排除在 CSRF 外；瀏覽器不會自動附帶 Bearer 權杖。

權杖的 scope 是 "accounts:read transfers:write"，預設轉換會產生哪些權限（不算 FACTOR_ 開頭的）？

  • ROLE_accounts:read 與 ROLE_transfers:write
  • SCOPE_accounts:read、SCOPE_transfers:write
  • 一個權限，內容是整段 accounts:read transfers:write
  • 沒有任何權限，scope 要另外設定才會讀

scope 以空白分隔，每一項各成一個權限，前綴 SCOPE_。

授權伺服器把角色放在 roles 聲明，值是 ["TELLER"]。要讓 hasRole('TELLER') 生效，該怎麼做？

  • 不用做，預設會讀 roles
  • 把規則改成 hasAuthority('SCOPE_TELLER')
  • 請授權伺服器把 roles 搬到 JWT 標頭裡
  • 換轉換器：讀 roles、前綴 ROLE_

hasRole('TELLER') 比對的是 ROLE_TELLER；預設只讀 scope。實跑改讀 roles 後得到 ROLE_TELLER、ROLE_AUDITOR。

資源伺服器設了 issuer-uri。授權伺服器某天換了一把新的簽章金鑰，API 要怎麼處理？

  • 重新部署 API，把新公鑰放進設定檔
  • 所有使用者要重新登入，舊權杖全部失效
  • 把 issuer-uri 改成新金鑰的網址
  • 不用處理，Spring 會自動輪替金鑰

給了 issuer-uri，授權伺服器換新金鑰時 Spring 會自動輪替；像這課自己寫死公鑰的，才要自己換。

兩條 Filter 鏈：@Order(1) 那條寫了 securityMatcher("/token")，@Order(2) 那條沒寫。請求 GET /accounts/alice 會由哪一條處理？

  • 第 1 條，因為它的順序比較前面
  • 第 2 條，因為它管其餘所有請求
  • 兩條都會依序處理一次
  • 都不處理，要每條都寫 securityMatcher

依 @Order 順序比對，第 1 條只管 /token，不符合；第 2 條沒寫 securityMatcher，代表其他請求都歸它。

這課的 API 設了 SessionCreationPolicy.STATELESS。alice 帶權杖查過一次帳戶後，下一個請求不帶權杖，結果是？

  • 200，伺服器記得她
  • 401，沒帶權杖
  • 200，Cookie 自動帶上
  • 403，Session 過期

STATELESS 不建 Session，伺服器不記得任何人；每個請求都要自己帶權杖重新認證。

路徑規則之外的第二道門

方法層級授權：只能查自己的帳戶

路徑規則只看得出「有沒有 accounts:read」，看不出「查的是不是自己的帳戶」。把 /accounts/alice 改成 /accounts/bob 就看到別人的資料，是 OWASP Top 10:2025 排第一的「存取控制失效」（Broken Access Control）最典型的樣子出處（面試集〈認證與安全面試題：JWT、OAuth 2.0、OIDC 與密碼保存〉有十項的整理）。這種檢查放在方法上：

@Service
public class AccountService {
    @PreAuthorize("#owner == authentication.name")   // 只能查自己的帳戶
    public long balance(String owner) {
        return owner.length() * 1000L;                 // 示範用的假餘額
    }
}

設定類別要加 @EnableMethodSecurity，之後「就能在任何 Spring 管理的類別或方法上加 @PreAuthorize」（you are immediately able to annotate any Spring-managed class or method with @PreAuthorize）。#owner 是參數名稱，文件說用 -parameters 編譯就讀得到（If you compile your code with the -parameters argument, the standard JDK reflection API is used to discover the parameter names.），Spring Boot 的 Maven 設定預設就有。出處 authentication.name 在資源伺服器裡就是 JWT 的 sub（Authentication#getName maps to the JWT's sub property）。出處

前面 alice 查 bob 得到 403，標頭卻寫 insufficient_scope：原始碼的 BearerTokenAccessDeniedHandler 只要看到請求是用權杖認證的（request.getUserPrincipal() instanceof AbstractOAuth2TokenAuthenticationToken），被拒時一律寫 INSUFFICIENT_SCOPE。出處 所以帶有效 Bearer 權杖的請求被方法規則擋下，也是這個字，不代表真的是 scope 不夠。

測試不必真的簽 JWT：jwt()

spring-security-test 的 jwt() 直接放一個已驗證的 JWT 身分進請求，文件寫預設的 JWT 是 "sub": "user", "scope": "read"。這課用 jwt().jwt(j -> j.subject("alice")).authorities(…SCOPE_accounts:read) 分別查自己與 bob，再試一次不給 authorities：出處

jwt() 查自己 → 200
jwt() 查別人 → 403
jwt() 沒給 authorities → 403

路徑規則管「有沒有這類權限」，@PreAuthorize 管「是不是你的資料」；兩道都要有

alice 的權杖有 accounts:read，她呼叫 GET /accounts/bob。結果是？

  • 200，因為她有 accounts:read 這個 scope
  • 403，@PreAuthorize 不讓她查別人
  • 401，因為權杖的 sub 跟網址不同
  • 404，因為 bob 的帳戶對 alice 隱藏

路徑規則通過；方法上的 #owner == authentication.name 不成立（bob ≠ alice），所以 403。

@PreAuthorize 寫在 AccountService 上，但設定類別忘了 @EnableMethodSecurity。alice 查 bob 會怎樣？

  • 200，方法上的註解沒有生效
  • 403，註解不需要另外啟用
  • 應用程式啟動時直接失敗
  • 401，因為方法安全沒有設定好

沒啟用時註解不會被攔截，只剩路徑規則。

在資源伺服器裡，authentication.name 取的是 JWT 的哪個聲明？

  • iss
  • aud
  • sub
  • jti

文件：Authentication#getName 對應 JWT 的 sub，所以 sub 的值要對得上帳戶擁有者。

測試寫 .with(jwt())、沒指定權限，去打需要 SCOPE_accounts:read 的路徑。結果是？

  • 200，jwt() 產生的身分擁有所有權限
  • 401，因為 jwt() 的權杖沒有真的簽章
  • 500，缺少 JwtDecoder
  • 403，預設只有 SCOPE_read

文件：預設 JWT 的 scope 是 read，轉成 SCOPE_read，不符合路徑規則。實跑也是 403。

alice 查 bob 被 @PreAuthorize 擋下，回應標頭寫 error="insufficient_scope"。該怎麼解讀？

  • alice 的權杖少了某個 scope，補上就能查 bob
  • 只是統一寫法，是 @PreAuthorize 擋的
  • 代表 alice 的權杖已經過期，要換新的
  • 代表 CSRF 檢查失敗，要補防偽權杖

被拒是因為不是自己的帳戶，再多 scope 也查不了 bob。

授權碼流程與 PKCE，一步一步跑

第二個示範專案是一台授權伺服器（Spring Security 7 內建，照文件的 getting started 寫法出處），登記兩個用戶端：

RegisteredClient mobile = RegisteredClient.withId("1")
    .clientId("mobile-app")                                       // 公開用戶端：沒有密碼
    .clientAuthenticationMethod(ClientAuthenticationMethod.NONE)
    .authorizationGrantType(AuthorizationGrantType.AUTHORIZATION_CODE)
    .authorizationGrantType(AuthorizationGrantType.REFRESH_TOKEN)      // 登記了也拿不到，見課文
    .redirectUri("https://app.bank.example/callback")
    .scope(OidcScopes.OPENID).scope("accounts:read")
    .clientSettings(ClientSettings.builder().requireProofKey(true).build())
    .build();

mobile-app 是公開用戶端：裝在使用者手機上、藏不住密碼，所以用 NONE。另一個 web-portal 是機密用戶端：跑在銀行自己的伺服器、用 client secret 認證，權杖設定是存取權杖 5 分鐘、更新權杖 8 小時、reuseRefreshTokens(false)。

測試照圖上的步驟發請求（第 ③ 步真的用表單登入）：

=== 第 1 步：還沒登入就去授權端點
302 /login
=== 第 1 步：沒帶 code_challenge
302 https://app.bank.example/callback?error=invalid_request&error_description=OAuth%202.0%20Parameter%3A%20code_challenge&error_uri=https%3A%2F%2Fdatatracker.ietf.org%2Fdoc%2Fhtml%2Frfc7636%23section-4.4.1&state=s-123
=== 第 1 步：redirect_uri 不在登記清單裡
400 null 錯誤：[invalid_request] OAuth 2.0 Parameter: redirect_uri
=== 第 2 步：登入後授權，帶著授權碼導回
302 https://app.bank.example/callback?code=（授權碼）&state=s-123
=== 第 3 步：拿授權碼換權杖，送錯 code_verifier
400 {"error":"invalid_grant"}
=== 第 3 步：同一個授權碼，送對的 code_verifier
200 欄位：access_token, scope, id_token, token_type, expires_in
access_token 的聲明：{"sub":"alice","aud":"mobile-app","nbf":1790939164,"scope":["openid","accounts:read"],"iss":"https://login.bank.example","exp":1790939464,"iat":1790939164,"jti":"35a17793-b5d1-4b1e-9557-d989a86d4746"}

=== 第 3 步：同一個授權碼再換一次

（最後一行之後是 400 {"error":"invalid_grant"}。）逐步看：

  • 沒帶 code_challenge：導回並帶 error=invalid_request。7.0 的新功能列表寫「授權伺服器預設啟用 PKCE」（Enabled PKCE by default in OAuth 2.0 Authorization Server）。出處
  • redirect_uri 沒登記過：直接 400、不導過去，因為網址不可信。RFC 9700 要求比對時「必須用完全相同的字串比對」（authorization servers MUST utilize exact string matching），只有原生 App 的 localhost 連接埠例外。出處
  • state 原封不動回來：用戶端拿它比對，確認這次導回是自己發起的；RFC 6749 說它「應該用來防範跨站請求偽造」（The parameter SHOULD be used for preventing cross-site request forgery）。出處
  • 授權碼只能用一次：RFC 6749 寫授權碼「建議最長 10 分鐘」，「被使用超過一次時，授權伺服器必須拒絕，並應該盡可能撤銷之前用它簽發的所有權杖」（If an authorization code is used more than once, the authorization server MUST deny the request and SHOULD revoke (when possible) all tokens previously issued based on that authorization code.）。出處

Spring 有沒有撤銷？用機密用戶端換完權杖後重送同一個授權碼，再用 introspect 端點（讓用戶端問授權伺服器「這張權杖現在還有效嗎」的端點）查：

=== 授權碼被重複使用
換權杖前 introspect access_token：active=true
同一個授權碼再換：400 {"error":"invalid_grant"}
之後 introspect access_token：active=false
之後 introspect refresh_token：active=false

授權伺服器把兩張權杖都標成失效。但資源伺服器離線驗 JWT（只看簽章與期限），那張存取權杖到期前照樣能用，所以存取權杖要短效（這台的 expires_in 是 299 秒）。

PKCE 的兩個值

RFC 7636：code_verifier 長度「至少 43、最多 128 個字元」（with a minimum length of 43 characters and a maximum length of 128 characters）；S256 是 BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))，而且「做得到 S256 就必須用 S256」（If the client is capable of using "S256", it MUST use "S256"）。出處

測試裡的 challenge() 就是照這個公式寫的（MessageDigest 算 SHA-256，再用不補等號的 base64url 編碼）。拿 RFC 7636 附錄 B 的 verifier dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk 驗算，得到的 E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM 跟 RFC 列的一字不差。出處 這台授權伺服器的探索文件（授權伺服器公開自己端點與能力的那份清單，網址是 /.well-known/openid-configuration）也只列一種：code_challenge_methods_supported=["S256"]。

導回網址完全比對；state 防 CSRF；授權碼短效、只能用一次；換權杖時要拿出原本的 verifier

使用者還沒登入授權伺服器，瀏覽器就被導到 /oauth2/authorize。實跑結果是？

  • 302 導去授權伺服器的 /login
  • 直接發授權碼，之後再補登入
  • 回 401，整個流程就此結束
  • 導回用戶端，並帶上 error=login_required

認證發生在授權伺服器；瀏覽器請求未登入時被導去它的登入頁，用戶端看不到帳密。

授權請求的 redirect_uri 是沒登記過的 https://evil.example/cb。授權伺服器怎麼處理？

  • 導到 evil.example，並帶上錯誤訊息
  • 導到 evil.example，並帶上授權碼
  • 直接回 400，不導去任何地方
  • 改導到登記清單裡的第一個網址

網址不可信就不能往那裡導。實跑：400，[invalid_request] OAuth 2.0 Parameter: redirect_uri。

mobile-app 的授權請求沒帶 code_challenge，redirect_uri 是登記過的。實跑結果是？

  • 照常發授權碼，公開用戶端可以不用 PKCE
  • 直接回 400，不導回任何地方
  • 302 導去 /login 要求重新登入
  • 導回 callback，帶上錯誤

導回網址可信，就把錯誤導回用戶端。跟上一題對照：網址不可信才直接 400。

攻擊者在同一支手機上攔到 mobile-app 的授權碼，拿去換權杖，code_verifier 是自己亂產的。結果是？

  • 200，因為授權碼是真的
  • 400 invalid_grant
  • 401，要先用 client secret 認證
  • 302，導回 callback 重新授權

授權伺服器拿 verifier 算 S256，跟授權請求時的 challenge 比，對不上就拒絕。

32 個隨機位元組做 base64url（不補等號）得到 43 個字元，拿來當 code_verifier，符合 RFC 7636 嗎？

  • 符合，長度在範圍內
  • 不符合，最少 64 字
  • 不符合，要十六進位
  • 不符合，要剛好 128 字

RFC 7636：最少 43、最多 128 個字元，字元限英數與 - . _ ~，base64url 的輸出剛好落在範圍內。

授權請求只送 code_challenge，換權杖時才送 code_verifier。為什麼不在授權請求就送 verifier？

  • 授權請求經過瀏覽器，只送雜湊推不回原值
  • verifier 太長，網址裝不下
  • 只是規格的習慣，先送哪個都可以
  • challenge 才是祕密，verifier 本來就可以公開

授權請求經過瀏覽器與網址列；換權杖是用戶端直接打 token 端點，verifier 只出現在後者，S256 又是單向的。

同一個授權碼成功換過權杖後，又被拿來換第二次。照 RFC 6749 與這課實跑，會怎樣？

  • 第二次也成功，拿到另一組新權杖
  • 第二次失敗，第一次的權杖不受影響
  • 授權伺服器鎖住這個用戶端一小時
  • 第二次失敗，第一次的權杖也被撤銷

RFC 6749：必須拒絕，並應撤銷之前用它簽發的權杖。實跑：introspect 從 active=true 變 active=false。

接上題，授權伺服器已把那張 JWT 存取權杖標成失效。到期前拿它打這課只離線驗 JWT 的帳戶 API，結果是？

  • 401，資源伺服器會收到撤銷通知
  • 還是能過，因為驗的只是簽章與期限
  • 403，因為權杖被標記了
  • 要看 aud 是不是 core-banking

離線驗 JWT 不回頭問授權伺服器。要即時撤銷，得改成向授權伺服器查詢（introspection）或維護拒絕清單。

授權請求帶了 state=s-123，導回時 state 是 s-999。用戶端該怎麼辦？

  • 照常拿授權碼去換權杖
  • 改用 s-999 重送一次授權請求
  • 拒絕這次導回，不拿授權碼去換
  • 忽略 state，只檢查授權碼的格式

state 要原封不動回來；對不上代表這次導回不是自己發起的（可能是 CSRF）。Spring 的 oauth2Login 會自動產生並比對。

  • 10 分鐘
  • 8 小時
  • 沒有建議

RFC 6749 第 4.1.2 節：A maximum authorization code lifetime of 10 minutes is RECOMMENDED。授權碼要走瀏覽器、可能外洩，所以短效又只能用一次。

短效的存取權杖、輪替的更新權杖

Refresh Token：誰拿得到、被偷了會怎樣

更新權杖「由授權伺服器發給用戶端，用來在存取權杖失效或過期時取得新的」（Refresh tokens are issued to the client by the authorization server and are used to obtain a new access token when the current access token becomes invalid or expires），只送授權伺服器、不送資源伺服器。出處 看三件實作上的事。

公開用戶端拿不到。前面 mobile-app 換到的欄位沒有 refresh_token，而它登記時明明有 REFRESH_TOKEN。原始碼的 OAuth2RefreshTokenGenerator 遇到「授權碼流程、用戶端認證方式是 NONE」直接回傳 null，註解寫「不要發更新權杖給公開用戶端」（Do not issue refresh token to public client）。出處 RFC 9700 對公開用戶端的要求是：更新權杖「必須綁定發送者，或使用更新權杖輪替」（Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation）。出處

輪替：舊的一用就失效。web-portal 設了 reuseRefreshTokens(false)：

=== 更新權杖輪替
第一次換到：access_token, refresh_token, scope, id_token, token_type, expires_in，expires_in=299
用 rt1 換：200，拿到新的 refresh_token，跟 rt1 一樣嗎？false
再用舊的 rt1 換：400 {"error":"invalid_grant"}

最後再用 rt2 換：200，照樣拿到新權杖（權杖內容很長，省略）。

RFC 9700 的描述：攻擊者和合法用戶端都用了同一把時，其中一方一定會拿出已作廢的那把，「授權伺服器分不出是誰送的，但會撤銷現行的那把」（The authorization server cannot determine which party submitted the invalid refresh token, but it will revoke the active refresh token.）。出處 實跑的 rt2 仍然 200：這課的設定只做到「舊的那把失效」，沒有連帶撤銷 rt2；要照 RFC 9700 的完整做法，得自己在授權伺服器補上。

用戶端會自動換新。oauth2-client 用更新權杖換新的預設實作是 RestClientRefreshTokenTokenResponseClient（obtain an access token at the Authorization Server's Token Endpoint）。出處

公開用戶端不發更新權杖；輪替讓舊的一用就失效；偵測到重複使用時要不要撤銷整串，看授權伺服器的實作

mobile-app（公開用戶端）登記時加了 REFRESH_TOKEN，換權杖的回應裡有沒有 refresh_token？

  • 有，登記了就發
  • 有，但只能用一次
  • 沒有，公開用戶端不發
  • 要看同意畫面

實跑的欄位沒有 refresh_token；OAuth2RefreshTokenGenerator 遇到授權碼流程的公開用戶端直接回傳 null。

web-portal 設了 reuseRefreshTokens(false)。用 rt1 換過一次後，再拿 rt1 去換，結果是？

  • 400 invalid_grant
  • 200，rt1 還在效期內就能用
  • 200，但這次不會再給新的更新權杖
  • 401，要先用帳號密碼重新登入

每次換發都給新的、舊的作廢。實跑：再用舊的 rt1 換 → 400 {"error":"invalid_grant"}。

有人拿已作廢的 rt1 換過之後，合法用戶端再用 rt2 換。RFC 9700 的做法和這課實跑分別是？

  • 兩者都讓 rt2 照樣能用
  • 兩者都把 rt2 撤銷
  • RFC 撤銷 rt2；實跑 rt2 仍可用
  • RFC 9700 沒有規定這種情況

RFC 9700 第 4.14.2 節：分不出誰是攻擊者，就撤銷現行的那把，逼合法用戶端重新授權。這課的設定沒做這一步。

網銀前台用 oauth2-client，存取權杖五分鐘過期。需要自己寫「拿更新權杖去換新」的程式嗎？

  • 要，Spring 不會換
  • 通常不用，會自動換
  • 要，送去資源伺服器換
  • 不用，權杖不會過期

oauth2-client 的更新權杖授權預設由 RestClientRefreshTokenTokenResponseClient 處理。更新權杖絕不送去資源伺服器。

OIDC 登入：oauth2Login()

第三個示範專案是網銀前台，用銀行的授權伺服器登入：

spring:

    oauth2:
      client:
        registration:
          bank:
            client-id: web-portal

provider 那段另外寫授權伺服器的三個端點網址；Filter 鏈裡只要 .oauth2Login(Customizer.withDefaults())。{baseUrl}/login/oauth2/code/{registrationId} 是文件寫的預設樣板（The default redirect URI template is {baseUrl}/login/oauth2/code/{registrationId}.）。出處 實跑看 Spring 組了什麼：

  • 忽略，nonce 只是除錯用的參考值

新舊格式共存，登入時順便升級

DelegatingPasswordEncoder

面試集那課講了 {id} 前綴格式與設計理由，這裡看實際行為（對 createDelegatingPasswordEncoder() 呼叫 encode、matches、upgradeEncoding）：

編碼一次：{bcrypt}$2a$10$XBOYmWbC0RjDL6…（共 68 字元）
同一組密碼編兩次一樣嗎？false
matches 正確密碼：true
matches {noop} 舊格式：true
{noop} 需要升級嗎？true；{bcrypt} 需要嗎？false
沒有前綴：Given that there is no default password encoder configured, each password must have a password encoding prefix. Please either prefix this password with '{noop}' or set a default password encoder in `DelegatingPasswordEncoder`.
  • 同一組密碼編兩次結果不同：bcrypt 每次產生新的鹽，比對一定要用 matches。
  • 沒有前綴會丟 IllegalArgumentException：7.1.1 實跑的訊息如上；參考文件「Password Storage」列的是舊版訊息 There is no PasswordEncoder mapped for the id "null"。出處 意思一樣：沒有前綴的舊密碼要先補上正確的前綴（原本是 bcrypt 就補 {bcrypt}）。

下次登入時自動升級

這課的 bob 故意存成 {noop}bob-pw（明文，模擬舊系統的資料），他用正確密碼登入一次：

=== 舊格式密碼自動升級
登入前：{noop}bob-pw
登入後：{bcrypt}$2a$10$…

做這件事的是 DaoAuthenticationProvider：登入成功後，如果 upgradeEncoding(舊值) 為 true、又有 UserDetailsPasswordService，就用剛輸入的密碼重新編碼，呼叫 updatePassword 存回去。出處 InMemoryUserDetailsManager 本身就實作了這個介面；正式系統要自己實作，把新值寫回資料庫。只有使用者輸入正確密碼的那一刻才拿得到明文，所以要換成直接對密碼算的 bcrypt，只能等他登入時做。

這是「等使用者登入」的升級法。不想讓舊雜湊在資料庫留那麼久，OWASP 列了另一種：直接拿舊的雜湊值當輸入，整批包成更安全的演算法，例如把 md5($password) 升級成 bcrypt(md5($password))（Use the existing password hashes as inputs for a more secure algorithm.），這樣不必知道原密碼；但這種疊起來的雜湊「應該在使用者下次登入時換成直接對密碼算的雜湊」（These hashes should be replaced with direct hashes of the users' passwords next time the user logs in.）。出處

編碼用現行演算法、比對看前綴；沒前綴丟例外；登入成功時用 UserDetailsPasswordService 換成新格式；要整批升級可以先包一層

用 createDelegatingPasswordEncoder() 把同一組密碼編碼兩次，兩個結果會怎樣？

  • 完全一樣，所以可以直接用 equals 比對
  • 不同，因為每次都產生新的鹽
  • 第二次會丟出例外，同一組密碼只能編一次
  • 內容一樣，只有前綴會不同

實跑：同一組密碼編兩次一樣嗎？false。每次產生新鹽，只能用 matches 驗。

資料庫的舊密碼存成 $2a$10$...（是 bcrypt，但沒有 {bcrypt} 前綴），交給 DelegatingPasswordEncoder 比對。結果是？

  • 丟出 IllegalArgumentException
  • 自動看出是 bcrypt，正常比對
  • 回傳 false，使用者登入失敗
  • 自動當成明文比對

沒有前綴，它不知道該交給哪個編碼器；要先補上正確的前綴。

bob 的密碼存成 {noop}bob-pw。他用正確密碼登入成功後，存起來的密碼變成什麼？

  • 不變，還是 {noop}bob-pw
  • 被清空，下次要求他重設密碼
  • {bcrypt} 開頭的新值
  • {sha256} 開頭的新值

upgradeEncoding 對 {noop} 回 true，DaoAuthenticationProvider 用剛輸入的密碼以 bcrypt 重新編碼後存回去。

銀行有 50 萬筆舊的 sha1(密碼)。為什麼不能今晚把每一筆直接換成 bcrypt(密碼)？

  • bcrypt 太慢，一晚算不完
  • Spring 7 讀不了 SHA-1
  • 手上只有雜湊值，推不回原密碼
  • 要先關掉密碼編碼器

bcrypt(密碼) 要對原密碼算，SHA-1 推不回原密碼。整批能做的是包一層 bcrypt(sha1(密碼))（OWASP 的第二種升級法），等使用者登入時再換成直接對密碼算的。

重點整理

  • 三個角色在 Spring Security 7 各一個設定：oauth2Login()、oauth2AuthorizationServer()、oauth2ResourceServer()；Spring Boot 4 的 starter 名字多了 security-。
  • 資源伺服器驗 JWT：演算法由驗證端決定，預設檢查 exp、nbf（容許 60 秒誤差）與 iss，aud 要自己加；權杖不可信是 401，權限不夠才是 403。
  • 帶 Bearer 權杖的請求不做 CSRF 檢查；scope 預設變成 SCOPE_ 權限，角色在別的聲明就換 JwtGrantedAuthoritiesConverter。
  • 路徑規則管「有沒有這類權限」，@PreAuthorize("#owner == authentication.name") 管「是不是你的資料」；要先 @EnableMethodSecurity，測試用 jwt()。
  • 授權碼流程：導回網址完全比對、state 防 CSRF、授權碼只能用一次，重複使用時已發的權杖被撤銷；PKCE 用 S256，攔到授權碼沒有 verifier 也換不到。
  • 公開用戶端拿不到更新權杖；輪替讓舊的一用就失效，但「偵測到重複使用就撤銷整串」要看實作；離線驗的 JWT 撤銷不了，存取權杖要短效。
  • oauth2Login 自動帶 state、nonce、PKCE；ID Token 給用戶端驗、Access Token 給 API 驗。DelegatingPasswordEncoder 沒前綴丟例外，舊格式在登入成功時自動升級。
