先確認身分，再判斷權限

認證與授權是兩道不同的門

Spring Security 是 Spring 生態系的安全框架，處理登入、權限控制、密碼驗證、工作階段與常見的網站攻擊防護。它像大樓的門禁系統：先在櫃檯確認「你是誰」（認證，Authentication），再判斷這張門禁卡能不能開某個房間（授權，Authorization）。

概念要回答的問題失敗時的狀況
認證你是誰？提供的憑證有效嗎？帳號或密碼錯、權杖失效，通常要求重新登入
授權已登入的你可以做什麼？身分有效，但角色或權限不足

原筆記用了一個很好懂的例子：一般會員看免費影片，VIP 會員看付費影片。還沒登入就要看影片是認證問題；已登入的一般會員要看 VIP 影片是授權問題。

公開資源不需要先認證。Spring Security 官方文件說明，標成 permitAll 的路徑不需要授權判斷，而且根本不會去工作階段裡取出身分出處。所以「先認證再授權」是理解一般流程的好方法，但不是所有請求都這樣走。

把登入資料包成框架看得懂的物件

Spring Security 的認證流程

帳號密碼登入時，請求先由負責認證的 Filter 接住，再把憑證交給認證管理元件。它透過使用者資料服務查出帳號，用密碼編碼器比對密碼。成功之後，已認證的身分會放進安全內容保存區。

Authentication代表目前的身分與憑證，也可以帶著角色或權限。
AuthenticationManager接收認證要求，協調整個認證流程。
UserDetailsService依使用者名稱載入帳號資料。
UserDetails描述帳號、密碼雜湊值與權限的介面。
SecurityContextHolder讓目前這次請求取得已認證身分的入口。

帳號可以先放在記憶體裡方便示範或測試（原筆記用的 InMemoryUserDetailsManager 就是這個用途），正式系統通常改從資料庫、LDAP 或其他身分服務載入。密碼不應該存明文，要存適合密碼用途的單向雜湊結果，這點第 10 課會細談。

每個請求都先走檢查站

Filter 鏈怎麼保護 API

Servlet Filter（過濾器）像機場一連串的檢查站，能在請求進 Controller 之前檢查或補資料。Spring Security 會建立自己的安全 Filter 鏈，依序處理安全內容、登入、例外轉換與授權判斷。

  • 讀 Session、Basic 憑證或權杖，試著建立使用者身分。
  • 把認證結果放進安全內容保存區。
  • 判斷目標資源允不允許目前這個身分存取。
  • 把未登入或權限不足的錯誤轉成適當的 HTTP 回應。

自訂 Filter 可以直接實作 Filter，也可以繼承 OncePerRequestFilter。後者的重點是：一次請求的分派流程裡，同一個 Filter 不會重複執行。

把 Filter 加進安全鏈時是指定相對位置，例如放在某個既有 Filter 前面或後面，而不是指定「第五個位置」。原筆記提醒的那個坑也很實際：同一個 Filter 如果既被 @Component 掃描自動註冊進 Servlet 容器，又被手動 addFilterBefore() 加進 Spring Security 鏈，它就會對同一次請求執行兩次。

原筆記講的 FilterSecurityInterceptor 是 Spring Security 5 的元件。官方文件直接寫 AuthorizationFilter 取代了它，並且說明「當使用 authorizeHttpRequests 而非 authorizeRequests 時，會改用 AuthorizationFilter」——而 authorizeHttpRequests 就是現在的標準寫法出處。

把路徑規則寫成看得懂的門禁表

用 HttpSecurity 設定路徑授權

HttpSecurity 可以設定路徑授權、表單登入、HTTP Basic、CSRF、CORS、Session 與 OAuth 相關功能。授權規則由「比對哪些請求」加上「採取什麼限制」兩部分組成。

@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/welcome", "/register").permitAll()
        .requestMatchers("/admin/**").hasRole("ADMIN")
        .requestMatchers("/member/**").hasAnyRole("USER", "ADMIN")
        .anyRequest().authenticated()
    );
    return http.build();
}
規則意義
permitAll()所有人都能存取，包含還沒登入的人
denyAll()所有人都不能存取
authenticated()必須完成認證
hasRole("ADMIN")必須具備指定角色
hasAnyRole("USER", "ADMIN")具備其中一個角色就行

規則照宣告順序比對，所以比較明確的路徑要放前面，最後再用 anyRequest() 收尾。

原筆記用的是新版寫法，但網路上大量教學仍停在 Spring Security 5：WebSecurityConfigurerAdapter 在 6.0 已移除，改成宣告一個 SecurityFilterChain 的 Bean；authorizeRequests() 換成 authorizeHttpRequests()，antMatchers()、mvcMatchers() 換成 requestMatchers()，@EnableGlobalMethodSecurity 換成 @EnableMethodSecurity。抄範例前先看它是哪個版本。

角色像職稱，權限像可以做的動作

RBAC 與方法層級授權

角色存取控制（Role-Based Access Control，RBAC）不是逐一把權限發給每個使用者，而是先把一組權限指派給角色，再讓使用者擁有角色。例如 ADMIN 可以管理會員，USER 只能讀自己的資料。

路徑授權守在 HTTP 入口；方法層級授權則直接守住 Service 或 Controller 的方法。後者適合保護那些可能被多個入口呼叫的核心操作。

@PreAuthorize("hasRole('ADMIN')")
public void deleteMember(long memberId) {
    // 只有符合授權條件的身分才能執行
}

不要只靠前端把按鈕藏起來做權限控制。使用者還是可以自己呼叫 API，真正的授權判斷必須在後端執行。

瀏覽器拿號碼牌，伺服器保管登入狀態

Cookie、Session 與權杖

Cookie 是瀏覽器保存、依規則附在請求上的一小段資料，格式像 名稱=值。Session（工作階段）是伺服器端維護的狀態；瀏覽器通常只保存一個識別碼，例如 JSESSIONID。

登入成功
  → 伺服器建立 Session
  → 回應用 Cookie 交付 JSESSIONID
  → 瀏覽器後續請求都帶著 JSESSIONID
  → 伺服器用它找到 Session 與登入身分
  → 登出或逾時後讓 Session 失效

Session 本身是 Servlet 容器提供的 HttpSession，Spring Security 沒有自己實作一套。官方文件的說法是「HttpSessionSecurityContextRepository 把 SecurityContext 關聯到 HttpSession」——它負責的是安全內容要放在哪裡，而放的地方就是容器的工作階段；換成 Redis 這類外部儲存也是換掉這個儲存庫，不是換掉 Session 本身出處。

Cookie 不只用來登入，也可以保存個人化設定、購物車識別資訊或表單進度。但敏感內容不該直接明文放進去。

另一種架構是登入後發出權杖（token），之後由自訂 Filter 解析權杖並建立安全內容。最常見的權杖格式是 JWT（JSON Web Token）：伺服器把「你是誰、有哪些權限、什麼時候過期」寫成一段字串，再用自己的金鑰簽名；之後收到這段字串時驗一下簽名，就知道內容沒被人動過手腳，不必回頭查資料庫。要不要再把使用者狀態放進 Redis 是架構選擇，不是 JWT 的必要條件。

重點整理

  • 認證確認身分，授權判斷這個身分能不能做某件事；公開資源兩者都不需要。
  • Spring Security 透過 Filter 鏈在請求到達 Controller 前做安全檢查。
  • 授權判斷現在由 AuthorizationFilter 負責，搭配 authorizeHttpRequests 設定。
  • 路徑規則與方法層級規則互補，但後端才是權限判斷的最後防線。
  • RBAC 用角色承接一組權限，省掉逐一管理使用者權限的成本。
  • Session 由 Servlet 容器維護，Spring Security 只是把安全內容存進去。
