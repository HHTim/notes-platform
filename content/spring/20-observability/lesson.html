可觀測性與三種訊號

Spring Boot 文件的定義：「可觀測性是從外部觀察一個執行中系統內部狀態的能力，由三個支柱組成：日誌、指標、追蹤」（Observability is the ability to observe the internal state of a running system from the outside. It consists of the three pillars: logging, metrics and traces.）。出處 OpenTelemetry 對三種訊號各一句：追蹤是「請求穿過應用程式的路徑」（The path of a request through your application.）、指標是「執行期擷取的量測」（A measurement captured at runtime.）、日誌是「一件事情的紀錄」（A recording of an event.）。出處

用醫院比喻：指標像體溫、血壓這些一直量的數字，告訴你「有沒有事」；追蹤像病人從掛號、檢查到批價的動線紀錄，告訴你「卡在哪一站」；日誌像每一站的病歷，寫下「那一站發生了什麼」。下面這張圖的數字來自實跑的兩個服務：

示範環境：transfer 服務（轉帳前檢查）呼叫 account 服務（查餘額），帳號 X999 會模擬核心帳務逾時、回 503。兩個服務都用 Spring Boot 4.1.1、Java 21；Prometheus 收指標、Jaeger 收追蹤，都用 Docker 跑。面試怎麼把三種訊號講成一句答案，見〈微服務與架構面試題：服務發現、韌性、可觀測性與十二要素〉；端到端監控那題見〈後端與雲端面試題庫〉。

指標說「有沒有事」、追蹤說「事在哪一段」、日誌說「那一段發生了什麼」；三者靠同一個 traceId 串起來

網銀 API 的錯誤率在 10:05 突然升到 5%。這個「有沒有事」最先從哪一種訊號看出來？

  • 日誌
  • 指標
  • 追蹤
  • 程式碼

錯誤率是一直在量的數字，屬於指標。指標先告訴你出事了，接著才用追蹤找慢在哪一段、用日誌看那一段發生什麼。

已經知道「轉帳檢查變慢了」，想知道慢在 transfer 自己還是它呼叫的 account。最直接的是看哪一種？

  • 那個請求的追蹤
  • 兩台機器的 CPU 使用率
  • 兩個服務的每秒請求數
  • 把全部服務的日誌從頭讀一遍

追蹤記錄請求穿過每個服務的路徑與每段耗時。實跑那條追蹤顯示 transfer 335 毫秒裡，有 314 毫秒花在 account。

追蹤指出慢在 account，想知道 account 那一段到底發生了什麼錯。下一步看哪裡？

  • Prometheus 上的錯誤率趨勢圖
  • Grafana 上的整體儀表板
  • 把 account 服務重開一次看看
  • account 的日誌，用 traceId 篩

日誌寫下那一段發生的事。實跑時 account 那行日誌寫著「核心帳務逾時 account=X999」，靠的是它跟追蹤帶著同一個 traceId。

OpenTelemetry 對「追蹤」的定義是？

  • 執行期擷取的量測
  • 一件事情的紀錄
  • 請求穿過應用程式的路徑
  • 每秒的請求數

追蹤是請求的路徑；執行期的量測是指標，一件事情的紀錄是日誌。

三種訊號是靠什麼串在一起，讓你能從一個錯誤的請求找到它的追蹤和日誌？

  • 相同的主機名稱與連接埠
  • 相同的時間戳記，精確到秒
  • 相同的程式碼行號
  • 同一個 trace ID

同一個請求在每個服務、每一行日誌、每一段 span 都帶著同一個 trace ID。只靠時間戳記，同一秒有幾百個請求時分不出誰是誰。

先決定量什麼，再決定什麼時候叫人

四個黃金訊號，與「看症狀不看原因」的告警

Google 的 SRE 書第 6 章：「監控的四個黃金訊號是延遲、流量、錯誤與飽和。如果面向使用者的系統只能量四個指標，就專注在這四個」（The four golden signals of monitoring are latency, traffic, errors, and saturation. If you can only measure four metrics of your user-facing system, focus on these four.）。出處

訊號SRE 書的定義（節譯）本課實跑怎麼量
延遲 latency服務一個請求要多久；要分開看成功與失敗的延遲，「慢的錯誤比快的錯誤更糟」histogram_quantile(0.95, …) 算出 p95 約 0.134 秒
流量 traffic系統承受多少需求，網路服務通常是每秒 HTTP 請求數rate(http_server_requests_seconds_count[1m]) 約每秒 10.9 個
錯誤 errors失敗請求的比例：明確失敗（HTTP 500）、隱性失敗（回 200 但內容錯）、違反政策的5xx 次數除以全部次數，約 1.2%
飽和 saturation服務有多「滿」，強調最受限的資源本課沒量；例如網銀的瓶頸若在核心帳務的連線池，就量它的使用率

實跑也印證了「慢的錯誤」：失敗的 X999 請求每個要等 300 毫秒逾時，比成功的請求還慢。如果把錯誤從延遲裡濾掉，平均延遲反而變好看，這就是書裡要你分開看的原因。

告警看症狀，不看原因

同一章說，監控系統要回答兩個問題：「什麼壞了、為什麼壞」，「什麼壞了」是症狀（symptom），「為什麼」是原因（cause）；例如「回應變慢」是症狀，「CPU 被一支爛排序程式吃滿」是原因。出處 Prometheus 官方的告警建議總結成：「告警保持簡單、對症狀告警、有好的主控台讓人找出原因、避免發出沒事可做的呼叫」（keep alerting simple, alert on symptoms, have good consoles to allow pinpointing causes, and avoid having pages where there is nothing to do），並建議「告警盡量少，對跟使用者痛苦相關的症狀告警，而不是想抓住每一種可能造成痛苦的方式」。出處 SRE 書的另一句話是判斷標準：「每一次呼叫都應該要能採取行動」（Every page should be actionable.）。出處

照這個原則寫兩條規則：錯誤率與 p95 延遲，都是使用者感受得到的症狀。for 子句讓 Prometheus「在第一次符合條件之後，等一段時間才把告警算成觸發」（The optional for clause causes Prometheus to wait for a certain duration between first encountering a new expression output vector element and counting an alert as firing），用來忽略一閃而過的波動。出處

groups:
  - name: transfer-symptoms
    rules:
      # 症狀一：使用者看到錯誤。轉帳檢查的 5xx 比例連續 5 分鐘超過 2%
      - alert: TransferHighErrorRatio
        expr: |
          sum(rate(http_server_requests_seconds_count{job="transfer",uri="/transfers/check",status=~"5.."}[5m]))
            / sum(rate(http_server_requests_seconds_count{job="transfer",uri="/transfers/check"}[5m])) > 0.02
        for: 5m
        labels:
          severity: page
        annotations:
          summary: "轉帳檢查錯誤率超過 2%"
      # 症狀二：使用者覺得慢。p95 延遲連續 10 分鐘超過 0.5 秒
      - alert: TransferSlowP95
        expr: |
          histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket{job="transfer",uri="/transfers/check"}[5m]))) > 0.5
        for: 10m
        labels:
          severity: page
        annotations:
          summary: "轉帳檢查 p95 延遲超過 0.5 秒"

用 Prometheus 映像裡的 promtool 檢查語法：

$ promtool check rules rules.yml
Checking rules.yml
  SUCCESS: 2 rules found

CPU 90%、某台機器記憶體高這類「原因」，適合放在儀表板上，出事時幫你找原因；直接拿來半夜叫人，常常是 CPU 高但使用者沒感覺，叫醒了也沒事可做。

量延遲、流量、錯誤、飽和；告警只對使用者感受得到的症狀，原因放在儀表板上查

SRE 書的四個黃金訊號是哪四個？

  • CPU、記憶體、磁碟、網路
  • 延遲、流量、錯誤、飽和
  • 指標、日誌、追蹤、告警
  • 可用性、一致性、分區容錯、延遲

原文：latency, traffic, errors, and saturation。CPU、記憶體是資源，可以拿來量飽和，但不是四個訊號本身。

網銀轉帳 API 的「流量」最適合用什麼量？

  • 每秒的 HTTP 請求數
  • CPU 使用率的百分比
  • JVM 堆積的用量
  • 日誌檔每天長多大

SRE 書說網路服務的流量通常是每秒 HTTP 請求數。實跑用 rate(http_server_requests_seconds_count[1m]) 算出約每秒 10.9 個。

某 API 都回 HTTP 200，但回傳的餘額是錯的。依 SRE 書，這算不算錯誤？

  • 不算，狀態碼是 200 就是成功
  • 算，這是隱性失敗
  • 不算，那是延遲的問題
  • 超過 1% 的請求出錯才算

SRE 書把錯誤分成明確失敗（HTTP 500）、隱性失敗（200 但內容錯）與違反政策的。所以只數 5xx 會漏掉這種，需要端到端的檢查才抓得到。

計算延遲時，為什麼不該直接把失敗的請求濾掉？

  • 失敗的請求一定比較快
  • Prometheus 不允許過濾狀態碼
  • 失敗的可能更慢，濾掉會失真
  • 濾掉會讓流量的數字變少

SRE 書說慢的錯誤比快的錯誤更糟。實跑的 X999 每個等 300 毫秒才失敗，比成功的請求還慢。

下面哪一個比較適合當「半夜叫醒值班人員」的告警？

  • 5xx 比例連續 5 分鐘超過 2%
  • 某台機器 CPU 超過 80%
  • JVM 執行緒數比昨天多一倍
  • 日誌裡出現一行 WARN

錯誤率是使用者感受得到的症狀；CPU、執行緒數是可能的原因，使用者不一定有感覺，叫醒了常常沒事可做。原因放在儀表板上幫忙查。

告警規則裡的 for: 5m 作用是？

  • 每 5 分鐘發一次告警
  • 告警發出後只保留 5 分鐘
  • 條件持續 5 分鐘才算觸發
  • 只看最近 5 分鐘的日誌

Prometheus 文件：for 子句讓它在第一次符合條件後等一段時間，才把告警算成觸發。

「每一次呼叫都應該要能採取行動」這句話，用來篩掉哪一種告警？

  • 錯誤率太高時發出的告警
  • 延遲太高時發出的告警
  • 收到了也沒事可做的告警
  • 寫在 rules.yml 裡的所有告警

SRE 書：Every page should be actionable。收到後只會「再觀察看看」的，不該是半夜叫人的告警。

網銀 API 的「飽和」最該量什麼？

  • 最受限的資源
  • 每秒的請求數
  • 失敗請求的比例
  • 首頁的載入時間

SRE 書說飽和要強調最受限的資源。如果瓶頸是連到核心帳務的連線數，CPU 再低也沒用。

指標從哪裡來

Micrometer 與 Actuator：/actuator/prometheus

Micrometer 是 Spring Boot 收集指標用的程式庫。官方文件說它在各種監控系統的用戶端之上「提供一層簡單的門面」，讓你寫程式時不被特定廠商綁住，「就像 SLF4J，只是用在可觀測性」（Think SLF4J, but for observability.）。出處 意思是：程式裡只用 Micrometer 的計數器、計時器，要送去 Prometheus 還是別的系統，換一個相依套件就好。

Spring Boot 4.1 的相依套件（兩個服務都有；transfer 另外加 spring-boot-starter-restclient 來呼叫 account）：

<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webmvc</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-restclient</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-opentelemetry</artifactId>
  </dependency>
  <dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
  </dependency>
</dependencies>

Spring Boot 文件：「Prometheus 預期去抓取或輪詢各個應用程式實例的指標，Spring Boot 在 /actuator/prometheus 提供一個端點」，但「預設這個端點不可用，必須暴露」（By default, the endpoint is not available and must be exposed.）。出處 端點那頁也說「預設只有 health 端點透過 HTTP 與 JMX 暴露」，而且端點可能含敏感資訊，要想清楚再開。出處 設定檔（account 的，transfer 只差名字與埠號）：

spring.application.name=account
server.port=8081
# 預設只有 health；打開 prometheus 端點
management.endpoints.web.exposure.include=health,prometheus
# 預設取樣 10%；示範時全取樣
management.tracing.sampling.probability=1.0
# 追蹤用 OTLP 送到 Jaeger（4318 是 OTLP over HTTP 的埠）
management.opentelemetry.tracing.export.otlp.endpoint=http://localhost:4318/v1/traces
# OpenTelemetry starter 也會用 OTLP 推指標；這裡指標交給 Prometheus 來拉，所以關掉推送
management.otlp.metrics.export.enabled=false
# 讓 http.server.requests 輸出直方圖桶，PromQL 才能算百分位數
management.metrics.distribution.percentiles-histogram.http.server.requests=true
# 內建結構化日誌（Spring Boot 3.4 起）：主控台輸出 JSON（ECS 格式）
logging.structured.format.console=ecs

只打開 health 與 prometheus，所以 /actuator/metrics 回 404。打開的 /actuator/prometheus 是純文字，每行一個時間序列（指標名稱加上一組標籤）：

$ curl -s -o /dev/null -w "%{http_code}\n" localhost:8080/actuator/metrics
404

$ curl -s localhost:8080/actuator/prometheus | grep -E "^http_server_requests_seconds_(count|sum)\{.*uri=\"/transfers/check\""
http_server_requests_seconds_count{error="ServiceUnavailable",exception="ServiceUnavailable",method="GET",outcome="SERVER_ERROR",status="500",uri="/transfers/check"} 10
http_server_requests_seconds_sum{error="ServiceUnavailable",exception="ServiceUnavailable",method="GET",outcome="SERVER_ERROR",status="500",uri="/transfers/check"} 3.129694042
http_server_requests_seconds_count{error="none",exception="none",method="GET",outcome="SUCCESS",status="200",uri="/transfers/check"} 793
http_server_requests_seconds_sum{error="none",exception="none",method="GET",outcome="SUCCESS",status="200",uri="/transfers/check"} 89.261272875

http_server_requests_seconds 是 Spring 自動量的每個 HTTP 請求耗時。標籤把它切成好幾條：成功（status="200"）793 次、失敗（status="500"）10 次；_count 是次數，_sum 是總秒數。這些數字只會一直往上加，叫計數器（counter）：Prometheus 的定義是「只會增加、或在重新啟動時歸零的累計值」（A counter is a cumulative metric that represents a single monotonically increasing counter whose value can only increase or be reset to zero on restart.）。出處

業務指標自己加。transfer 用 Micrometer 的 Counter 記檢查結果（完整程式在後面的追蹤段）：

Counter.builder("transfer.checks").tag("result", "ok").register(registry).increment();
$ curl -s localhost:8080/actuator/prometheus | grep -E "^(# TYPE )?transfer_checks"
# TYPE transfer_checks_total counter
transfer_checks_total{result="error"} 10.0
transfer_checks_total{result="ok"} 793.0

程式裡取名 transfer.checks，送到 Prometheus 時點換成底線、計數器加上 _total，變成 transfer_checks_total；result 標籤把成功與失敗分開。

Micrometer 是指標的門面；Actuator 預設只開 health，/actuator/prometheus 要自己打開；計數器只增不減，重啟歸零

Micrometer 官方說它「就像 SLF4J，只是用在可觀測性」。這個比喻的意思是？

  • Micrometer 會取代 SLF4J 印日誌
  • 程式不綁廠商，換監控系統只要換相依套件
  • Micrometer 只能搭配 Logback
  • Micrometer 會把指標寫進日誌檔

SLF4J 讓你不綁定 Logback 或 Log4j；Micrometer 讓你不綁定 Prometheus 或其他監控系統，兩者都是門面。

加了 Actuator 和 micrometer-registry-prometheus，但沒設定任何暴露屬性。GET /actuator/prometheus 會？

  • 拿不到，預設只暴露 health
  • 回傳所有指標
  • 回傳 health 的結果
  • 自動跳轉到 Prometheus

Spring Boot 文件：預設只有 health 端點透過 HTTP 暴露，prometheus 端點要用 management.endpoints.web.exposure.include 打開。

設定 management.endpoints.web.exposure.include=health,prometheus 之後，GET /actuator/metrics 會？

  • 回 200 並列出所有指標名稱
  • 回 500，因為設定錯了
  • 回 404，沒在暴露清單裡
  • 自動導向 /actuator/prometheus

只暴露清單裡的端點，其他都不對外。實跑 curl 這個網址得到 404。

http_server_requests_seconds_count{…status="200"…} 793 中的 793 是什麼？

  • 最近一秒內的請求數
  • 平均每個請求耗時 793 毫秒
  • 啟動以來成功請求的累計次數
  • 目前同時在處理的請求數

_count 是計數器，從啟動起一直累加；要「每秒幾個」得交給 PromQL 的 rate 算。

服務重新啟動之後，transfer_checks_total 會變成多少？

  • 維持重啟前的值繼續加
  • 變成負數
  • Prometheus 會自動補回重啟前的值
  • 從 0 重新開始加

計數器只會增加，或在重新啟動時歸零。計數器歸零時，rate 會自動處理（後面講），所以不用自己補。

程式裡建立 Counter.builder("transfer.checks")，在 Prometheus 裡看到的名稱是？

  • transfer.checks（原名不變）
  • transfer-checks-total
  • TransferChecksTotal
  • transfer_checks_total

送到 Prometheus 時點換成底線，計數器加上 _total。實跑的端點輸出就是 transfer_checks_total{result="ok"}。

想分開統計「檢查成功」和「檢查失敗」的次數，Micrometer 的做法是？

  • 建兩個不同名字的指標
  • 同一個名字，加上 result 標籤
  • 寫進日誌，事後再用工具數
  • 每次檢查都建一個新的 MeterRegistry

用標籤切維度，PromQL 才能 sum by (result) 一起看或分開看。實跑的 transfer_checks_total 就有 result="ok" 與 result="error" 兩條。

Actuator 的端點為什麼不建議全部打開（include=*）？

  • 會讓服務的啟動變慢
  • Prometheus 會因此拉不到資料
  • Spring Boot 根本不允許這樣設
  • 可能含敏感資訊

Spring Boot 文件說端點可能含敏感資訊，暴露前要仔細考慮。只開需要的，例如 health 與 prometheus。

Prometheus 自己來拿

拉取模型與 PromQL：rate、histogram_quantile、錯誤率

Prometheus 官方總覽列的特性：「時間序列的收集透過 HTTP 拉取模型進行」（time series collection happens via a pull model over HTTP），推送則「透過中介的 gateway 支援」。出處 意思是服務不用知道 Prometheus 在哪，只要提供 /actuator/prometheus，Prometheus 照設定定時來拉。實跑的設定：

global:
  scrape_interval: 5s          # 每 5 秒去拉一次（示範用；預設是 1 分鐘）
scrape_configs:
  - job_name: transfer
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["host.docker.internal:8080"]
  - job_name: account
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["host.docker.internal:8081"]

下面是打了 70 秒流量之後，用 Prometheus 的 HTTP API 查的實際結果（jq 只是把回應整理成一行一筆）。先看 up：1 表示上一次拉取成功。

$ curl -s --get localhost:9090/api/v1/query --data-urlencode 'query=up' | jq -c '.data.result[] | {job: .metric.job, value: .value[1]}'
{"job":"account","value":"1"}
{"job":"transfer","value":"1"}

流量：rate

計數器一直往上加，原始值看不出快慢。rate「計算區間向量裡時間序列每秒的平均增加量」，而且計數器重啟歸零造成的斷點「會自動調整」（Breaks in monotonicity (such as counter resets due to target restarts) are automatically adjusted for.）。要加總時有一條規則：「一定先 rate，再加總，否則 rate 偵測不到目標重啟造成的計數器歸零」（always take a rate() first, then aggregate.）。出處 [1m] 是取最近一分鐘；uri!~"/actuator.*" 排除 Prometheus 自己來拉的請求。

$ curl -s --get localhost:9090/api/v1/query --data-urlencode 'query=sum by (job) (rate(http_server_requests_seconds_count{uri!~"/actuator.*"}[1m]))' | jq -c '.data.result[] | {job: .metric.job, value: .value[1]}'
{"job":"account","value":"10.745454545454544"}
{"job":"transfer","value":"10.927272727272726"}

延遲：直方圖與 histogram_quantile

設定檔那行 percentiles-histogram 讓耗時輸出成直方圖：不存每一筆耗時，只存「耗時不超過某條線的有幾筆」，每條線是一個桶（bucket），用 le（less than or equal）標籤標出。下面挑出 p95 附近的幾個桶（中間還有很多桶，這裡用 grep 只挑幾個）：

$ curl -s localhost:8080/actuator/prometheus | grep -E "^http_server_requests_seconds_bucket\{.*status=\"200\".*uri=\"/transfers/check\"" | grep -E "le=\"(0.089478485|0.111848106|0.134217727|0.156587348|\+Inf)\""
http_server_requests_seconds_bucket{error="none",exception="none",method="GET",outcome="SUCCESS",status="200",uri="/transfers/check",le="0.089478485"} 0
http_server_requests_seconds_bucket{error="none",exception="none",method="GET",outcome="SUCCESS",status="200",uri="/transfers/check",le="0.111848106"} 432
http_server_requests_seconds_bucket{error="none",exception="none",method="GET",outcome="SUCCESS",status="200",uri="/transfers/check",le="0.134217727"} 774
http_server_requests_seconds_bucket{error="none",exception="none",method="GET",outcome="SUCCESS",status="200",uri="/transfers/check",le="0.156587348"} 792
http_server_requests_seconds_bucket{error="none",exception="none",method="GET",outcome="SUCCESS",status="200",uri="/transfers/check",le="+Inf"} 793

histogram_quantile 從這些桶估出百分位數。文件寫：百分位數沒剛好落在桶邊界時，它「在百分位數所在的桶裡內插」，傳統直方圖「假設觀測值在桶內均勻分布，也叫線性內插」（it assumes a uniform distribution of observations within the bucket (also called linear interpolation)）；要彙總時用 sum 包住 rate，而且 le 一定要留在 by 裡。出處

$ curl -s --get localhost:9090/api/v1/query --data-urlencode 'query=histogram_quantile(0.95, sum by (le, job) (rate(http_server_requests_seconds_bucket{uri!~"/actuator.*"}[1m])))' | jq -c '.data.result[] | {job: .metric.job, value: .value[1]}'
{"job":"account","value":"0.12986914981422415"}
{"job":"transfer","value":"0.1337764512732422"}

p95 約 0.134 秒：100 個請求裡有 95 個在 0.134 秒內完成。它是估出來的，準不準看桶切得細不細；圖上用累計數字算出約 0.133 秒，Prometheus 用最近一分鐘的速率、也算進了失敗請求，所以差一點點。

錯誤率與業務指標

錯誤率是「5xx 的速率除以全部的速率」；increase 是「rate 乘以區間秒數」，主要讓人看得懂。出處

$ curl -s --get localhost:9090/api/v1/query --data-urlencode 'query=sum(rate(http_server_requests_seconds_count{job="transfer",uri!~"/actuator.*",status=~"5.."}[1m])) / sum(rate(http_server_requests_seconds_count{job="transfer",uri!~"/actuator.*"}[1m]))' | jq -c '.data.result[] | {value: .value[1]}'
{"value":"0.011647254575707155"}

$ curl -s --get localhost:9090/api/v1/query --data-urlencode 'query=sum by (result) (increase(transfer_checks_total[1m]))' | jq -c '.data.result[] | {result: .metric.result, value: .value[1]}'
{"result":"error","value":"7.636363636363636"}
{"result":"ok","value":"648"}

錯誤率約 1.2%：打流量時每輪 8 個正常請求、每 10 輪混一個 X999，約 1／81，大致對得上。最近一分鐘約 648 次成功、7.6 次失敗；increase 是從速率推回來的，所以會出現小數。

Prometheus 定時來拉；看快慢用 rate（先 rate 再 sum）；百分位數用 histogram_quantile 從桶裡估，le 要留在 by 裡

Prometheus 怎麼拿到 transfer 服務的指標？

  • transfer 每 5 秒把指標推給 Prometheus
  • Prometheus 每 5 秒來拉
  • transfer 把指標寫進日誌，Prometheus 讀日誌
  • Prometheus 直接連資料庫查

Prometheus 是拉取模型：照 prometheus.yml 的 scrape_configs 定時去拉。這課 scrape_interval 設 5 秒。

PromQL 查 up 得到 transfer 是 1。代表？

  • transfer 目前有 1 個錯誤
  • transfer 每秒收到 1 個請求
  • 上一次拉取 transfer 成功
  • transfer 只部署了 1 個實例

up 是 Prometheus 替每個拉取目標記的：拉成功是 1、失敗是 0。服務掛掉時最先變的就是它。

想知道「每秒幾個請求」，該對 http_server_requests_seconds_count 用哪個函式？

  • rate(…[1m])
  • 直接查原始值
  • histogram_quantile
  • max

原始值是啟動以來的累計，rate 才是每秒的平均增加量。實跑算出 transfer 約每秒 10.9 個。

要算所有實例加總的每秒請求數，下面哪一個寫法對？

  • rate(sum(http_server_requests_seconds_count)[1m])
  • sum(rate(http_server_requests_seconds_count[1m]))
  • sum(http_server_requests_seconds_count) / 60
  • max(http_server_requests_seconds_count)

文件：一定先 rate 再加總，否則 rate 偵測不到某個實例重啟造成的計數器歸零。

某台實例重啟，它的計數器從 800 掉回 0。rate 會算出一個很大的負數嗎？

  • 會，所以要手動排除那一段
  • 會，所以計數器不能用 rate
  • 不會，rate 會自動調整
  • 不會，因為 rate 只看最後一個值

文件寫明計數器重啟造成的斷點會自動調整。前提是先 rate 再 sum。

直方圖的桶 le="0.134217727"} 774 是什麼意思？

  • 有 774 個請求剛好花 0.134 秒
  • 累計 774 個不超過 0.134 秒
  • 第 774 個請求花了 0.134 秒
  • 代表 p95 是 0.134 秒

le 是 less than or equal，每個桶是累計數：不超過 0.1118 秒的 432 個，不超過 0.1342 秒的 774 個。

用 histogram_quantile 彙總多個實例時，by 裡一定要留哪個標籤？

  • job
  • instance
  • le
  • status

histogram_quantile 靠 le 知道每個桶的上界；sum 時把 le 加總掉，就算不出百分位數了。文件的範例是 sum by (job, le)。

histogram_quantile 算出的 p95 是精確值嗎？

  • 是，它記得每一筆耗時
  • 不是，在桶裡內插估出來的
  • 是，只要桶夠多就跟平均一樣
  • 不是，它只是把最大值乘以 0.95

直方圖只存累計數，文件說它假設觀測值在桶內均勻分布、線性內插。實跑 p95 落在 0.1118 到 0.1342 秒的桶裡。

錯誤率的 PromQL 最合理的寫法是？

  • 5xx 的 rate 除以全部的 rate
  • sum(…{status=~"5.."}) 的累計值
  • rate(…_seconds_sum[1m])
  • max(…_seconds_max)

比例要兩個速率相除；只看 5xx 的累計次數看不出比例，也看不出是不是最近才發生。實跑結果約 0.012。

一個請求，跨兩個服務

分散式追蹤：Micrometer Tracing、OpenTelemetry 與 traceparent

一個請求從 transfer 走到 account，要把兩邊的紀錄接起來，就要給它一個貫穿全程的編號。一次追蹤（trace）由好幾段 span 組成，span 是其中一段工作，各有自己的 span ID，並記得自己的父節點。OpenTelemetry 文件說：「A 服務呼叫 B 服務時，A 把 trace ID 與 span ID 放進情境裡。B 用這些值建立一個屬於同一條 trace 的新 span，並把 A 的那段設成父節點」（When Service A calls Service B, Service A includes a trace ID and a span ID as part of the context. Service B uses these values to create a new span that belongs to the same trace, setting the span from Service A as its parent.）；傳播「通常由 instrumentation 函式庫處理」，預設用「W3C TraceContext 規格定義的標頭」。出處

Spring 這邊是 Micrometer Tracing：它「替最常見的追蹤程式庫提供一層簡單的門面」（provides a simple facade for the most popular tracer libraries），原本是 Spring Cloud Sleuth 的那一套。出處 Spring Boot 4.1 內建兩種組合：OpenTelemetry 用 OTLP（OpenTelemetry 自己的傳輸協定）送出，或 Brave 用 Zipkin 送出；前者要加 spring-boot-starter-opentelemetry，用 management.opentelemetry.tracing.export.otlp.* 設定送到哪。出處 這課用前者，送到 Jaeger（它直接收 OTLP）。

transfer 的程式：用 Spring Boot 自動設定的 RestClient.Builder 建立用戶端。文件特別警告：「如果不是用自動設定的 builder 建立 RestTemplate、RestClient 或 WebClient，自動的追蹤傳播就不會生效！」（If you create the RestTemplate, the RestClient or the WebClient without using the auto-configured builders, automatic trace propagation won’t work!）出處

package demo.transfer;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.RestClientResponseException;

@SpringBootApplication
@RestController
public class TransferApp {
    private static final Logger log = LoggerFactory.getLogger(TransferApp.class);
    private final RestClient accountClient;
    private final MeterRegistry registry;

    // 用 Spring Boot 自動設定的 RestClient.Builder 建立，追蹤標頭才會自動帶過去
    TransferApp(RestClient.Builder builder, MeterRegistry registry) {
        this.accountClient = builder.baseUrl("http://localhost:8081").build();
        this.registry = registry;
    }

    public static void main(String[] args) {
        SpringApplication.run(TransferApp.class, args);
    }

    @GetMapping("/transfers/check")
    public String check(@RequestParam String account) {
        MDC.put("account", account);                       // 業務欄位放進 MDC，這次請求的每行日誌都會帶著
        try {
            log.info("轉帳前檢查餘額");
            String body = accountClient.get().uri("/accounts/{id}/balance", account)
                    .retrieve().body(String.class);
            Counter.builder("transfer.checks").tag("result", "ok").register(registry).increment();
            return body;
        } catch (RestClientResponseException e) {
            Counter.builder("transfer.checks").tag("result", "error").register(registry).increment();
            log.warn("查餘額失敗 status={}", e.getStatusCode().value());
            throw e;
        } finally {
            MDC.remove("account");
        }
    }
}

account 收到請求時，順手把上游傳來的 traceparent 標頭印出來：

// 查餘額：模擬 20〜120 毫秒的處理時間；帳號 X999 模擬核心帳務逾時
@GetMapping("/accounts/{id}/balance")
public String balance(@PathVariable String id,
                      @RequestHeader(value = "traceparent", required = false) String traceparent)
        throws InterruptedException {
    log.info("查詢餘額 account={} traceparent={}", id, traceparent);   // 看上游傳來的 W3C 標頭
    if (id.equals("X999")) {
        Thread.sleep(300);
        log.error("核心帳務逾時 account={}", id);
        throw new ResponseStatusException(HttpStatus.SERVICE_UNAVAILABLE, "core timeout");
    }
    Thread.sleep(20 + Math.floorMod(id.hashCode(), 100));
    return "{\"account\":\"" + id + "\",\"balance\":12000}";
}

traceparent 標頭長什麼樣

W3C Trace Context 推薦標準：「traceparent 標頭識別追蹤系統裡傳入的請求，有四個欄位：version、trace-id、parent-id、trace-flags」。trace-id「是整個追蹤森林的 ID」，16 個位元組；parent-id「是呼叫端所知的這個請求的 ID（有些追蹤系統叫 span-id）」，8 個位元組；全部為零都是無效值。trace-flags 的最低位元是 sampled，表示「呼叫端可能已經記錄了追蹤資料」。出處 實跑時 account 收到的是：

traceparent=00-67e70a401431e867dab5b5ae6729fde2-ceae3b4330fd56b3-03
             │  │                                │                └ trace-flags：03＝sampled（01）加 random（02）
             │  │                                └ parent-id：transfer 發出呼叫那一段 span 的 ID
             │  └ trace-id：整條追蹤的 ID，兩個服務都是這一個
             └ version：00

flags 是 03 而不是常見範例的 01：多出來的 02 是 Level 2 草案新增的 random-trace-id 旗標，「trace-flags 的第二個最低位元」，表示 trace-id 至少右邊 7 個位元組是隨機產生的。出處 Level 2 目前是候選推薦草案；本課實跑的 OpenTelemetry 1.62（Spring Boot 4.1.1 管理的版本）有設這個旗標。

到 Jaeger 查這條追蹤

用上面那個 trace ID 去 Jaeger 的查詢 API 拿資料，三段 span 依開始時間排好：

$ curl -s localhost:16686/api/traces/67e70a401431e867dab5b5ae6729fde2 | jq -c '.data[0] as $t | $t.spans | sort_by(.startTime)[] | {service: $t.processes[.processID].serviceName, name: .operationName, id: .spanID, parent: (.references[0].spanID // null), ms: (.duration / 1000 | floor)}'
{"service":"transfer","name":"http get /transfers/check","id":"078dd44cd50adb93","parent":null,"ms":335}
{"service":"transfer","name":"http get","id":"ceae3b4330fd56b3","parent":"078dd44cd50adb93","ms":331}
{"service":"account","name":"http get /accounts/{id}/balance","id":"8b5c899fd52d0c0f","parent":"ceae3b4330fd56b3","ms":314}

對照起來：transfer 收到請求那段（078dd44c…）沒有父節點，是這條追蹤的根；transfer 發出呼叫那段（ceae3b43…）的父節點是根；account 那段（8b5c899f…）的父節點是 ceae3b43…，正是 traceparent 的第三欄。335 毫秒裡有 314 毫秒花在 account，問題在哪一段一眼就看出來。

取樣要注意：Spring Boot 預設「只取樣 10% 的請求，避免把追蹤後端壓垮」（By default, Spring Boot samples only 10% of requests to prevent overwhelming the trace backend.），這課為了示範設成 1.0。出處

trace ID 貫穿全程、span ID 標每一段；跨服務靠 traceparent 傳父節點；用自動設定的 builder 建用戶端，傳播才會生效；預設取樣 10%

transfer 呼叫 account 時，account 要怎麼知道「這個請求屬於哪一條追蹤」？

  • account 自己產生一個新的 trace ID
  • 兩邊去同一個資料庫查
  • 靠兩邊的時間戳記對齊
  • 用 traceparent 標頭傳過去

OpenTelemetry 文件：A 呼叫 B 時把 trace ID 與 span ID 放進情境，B 用它們建立同一條 trace 的新 span、把 A 的那段設成父節點。HTTP 上就是 traceparent 標頭。

在 traceparent: 00-67e70a40…e2-ceae3b4330fd56b3-03 裡，ceae3b4330fd56b3 是？

  • trace-id，整條追蹤的 ID
  • account 自己這一段的 span ID
  • version，規格的版本號
  • parent-id，呼叫端那段的 ID

四個欄位依序是 version、trace-id、parent-id、trace-flags。parent-id 是呼叫端所知的這個請求的 ID，也就是 transfer 發出呼叫那段的 span ID。

W3C 規格裡，trace-id 有多長？

  • 8 個位元組（16 個十六進位字元）
  • 16 個位元組（32 個十六進位字元）
  • 4 個位元組
  • 沒有規定長度

trace-id 是 16 位元組的陣列，寫成 32 個十六進位字元；parent-id 是 8 位元組。實跑的 67e70a401431e867dab5b5ae6729fde2 正好 32 個字元。

實跑的 trace-flags 是 03。拆開來是？

  • sampled 加 random
  • 版本號 3，代表第三版規格
  • 這條追蹤一共有 3 段 span
  • 錯誤碼 3，代表呼叫失敗

最低位元是 sampled；第二個最低位元是 Level 2 草案的 random-trace-id 旗標，表示 trace-id 至少右邊 7 個位元組是隨機的。

同事自己 RestClient.create() 出一個用戶端去呼叫 account，結果 account 的 trace ID 跟 transfer 對不上。最可能的原因是？

  • 沒用自動設定的 RestClient.Builder
  • Jaeger 那邊壞掉了
  • account 沒有開 Prometheus 端點
  • 取樣率設得太高

Spring Boot 文件明白警告：不用自動設定的 builder 建立 RestTemplate、RestClient 或 WebClient，自動的追蹤傳播就不會生效。

Jaeger 查出三段 span，其中 account 那段的 parent 是 ceae3b43…。ceae3b43… 是哪一段？

  • transfer 發出 HTTP 呼叫那段
  • transfer 收到請求那段（根）
  • account 自己
  • Prometheus 拉指標那段

transfer 收到請求是根；它發出呼叫是子段（CLIENT）；account 處理請求那段的父節點就是這個 CLIENT 段，也就是 traceparent 的 parent-id。

Spring Boot 沒設定 management.tracing.sampling.probability 時，大約多少比例的請求會被送去追蹤後端？

  • 100%
  • 50%
  • 10%
  • 0%，要手動開

Spring Boot 預設只取樣 10%，避免壓垮追蹤後端。示範時設成 1.0 是為了每個請求都看得到。

Spring Boot 4.1 要用 OpenTelemetry 送追蹤，加哪個 starter？

  • spring-cloud-starter-sleuth
  • spring-boot-starter-opentelemetry
  • spring-boot-starter-zipkin
  • spring-boot-starter-jaeger-tracing

Spring Boot 4.1 文件：OpenTelemetry 加 OTLP 需要 spring-boot-starter-opentelemetry；spring-boot-starter-zipkin 是 Brave 加 Zipkin 那一組。Sleuth 是 Spring Boot 2 時代的東西。

實跑時加了 OpenTelemetry starter，又設了 management.otlp.metrics.export.enabled=false。為什麼？

  • 不關的話追蹤送不出去
  • Prometheus 規定一定要關
  • 不關的話日誌不會是 JSON
  • starter 也會推指標，這課改用拉

spring-boot-starter-opentelemetry 帶著 micrometer-registry-otlp，指標推送預設是開的；Jaeger 只收追蹤，指標這邊用 /actuator/prometheus 讓 Prometheus 拉。

讓機器讀得懂的日誌

結構化日誌與 MDC

Spring Boot 文件：「結構化日誌是把日誌輸出寫成定義清楚、通常機器可讀的格式」（Structured logging is a technique where the log output is written in a well-defined, often machine-readable format.），內建支援 Elastic Common Schema（ECS）、Graylog（GELF）、Logstash 三種 JSON 格式，設定 logging.structured.format.console 就能開。出處 這個功能是 Spring Boot 3.4 加進來的（Support for structured logging has been introduced），4.1 照樣用。出處 設成 ecs 之後，transfer 的一行日誌長這樣：

$ grep 67e70a401431e867dab5b5ae6729fde2 transfer.log | head -1 | jq .
{
  "@timestamp": "2026-10-02T15:56:10.412703Z",
  "log": {
    "level": "INFO",
    "logger": "demo.transfer.TransferApp"
  },
  "process": {
    "pid": 43777,
    "thread": {
      "name": "http-nio-8080-exec-3"
    }
  },
  "service": {
    "name": "transfer",
    "version": "1.0",
    "node": {}
  },
  "message": "轉帳前檢查餘額",
  "traceId": "67e70a401431e867dab5b5ae6729fde2",
  "spanId": "078dd44cd50adb93",
  "account": "X999",
  "ecs": {
    "version": "8.11"
  }
}

每個欄位都有名字，日誌平台可以直接用 service.name、log.level、traceId 篩選，不用寫正規表示式去切字串。traceId 與 spanId 是 Micrometer Tracing 自動放的：文件說「用了 Micrometer Tracing，Spring Boot 預設就會在日誌裡加上關聯 ID」，由 MDC 裡的 traceId 與 spanId 組成。出處

account 那個欄位是程式自己放的，用的是 MDC（Mapped Diagnostic Context，對應式診斷情境）。Logback 手冊：MDC「讓開發者把資訊放進診斷情境，之後由 logback 的元件取出」，而且「以執行緒為單位管理」（The MDC manages contextual information on a per thread basis.）；典型用法是開始處理一個請求時，把客戶 ID 這類資訊放進去。出處 因為是綁在執行緒上，而 Tomcat 會重複使用執行緒，所以 transfer 的程式在 finally 裡 MDC.remove，不然下一個請求會帶著上一個人的帳號。

同一個 traceId，跨兩個服務

把兩個服務的日誌合在一起，用 trace ID 篩出同一個請求（jq 只挑出幾個欄位，並略過錯誤堆疊那一行）：

$ cat transfer.log account.log | grep 67e70a401431e867dab5b5ae6729fde2 | jq -c 'select(.error == null) | {service: .service.name, level: .log.level, message, traceId, spanId}'
{"service":"transfer","level":"INFO","message":"轉帳前檢查餘額","traceId":"67e70a401431e867dab5b5ae6729fde2","spanId":"078dd44cd50adb93"}
{"service":"transfer","level":"WARN","message":"查餘額失敗 status=503","traceId":"67e70a401431e867dab5b5ae6729fde2","spanId":"078dd44cd50adb93"}
{"service":"account","level":"INFO","message":"查詢餘額 account=X999 traceparent=00-67e70a401431e867dab5b5ae6729fde2-ceae3b4330fd56b3-03","traceId":"67e70a401431e867dab5b5ae6729fde2","spanId":"8b5c899fd52d0c0f"}
{"service":"account","level":"ERROR","message":"核心帳務逾時 account=X999","traceId":"67e70a401431e867dab5b5ae6729fde2","spanId":"8b5c899fd52d0c0f"}

四行來自兩個服務，trace ID 都是同一個；transfer 的兩行 spanId 相同（同一段），account 的兩行是 account 自己那段。從指標看到錯誤率升高，到追蹤看到慢在 account，再到這裡看到「核心帳務逾時」，三種訊號就這樣接起來。日誌不要寫進身分證字號、卡號這類敏感資料；結構化之後欄位更容易被整批搜出來，更要小心。

結構化日誌讓欄位可以篩選；traceId、spanId 由 Micrometer Tracing 自動放進 MDC；業務欄位自己放進 MDC，用完一定要清

開啟 logging.structured.format.console=ecs 之後，主控台的日誌會變成？

  • 彩色的純文字
  • 每行一筆 JSON（ECS）
  • 直接寫進資料庫
  • 只剩 ERROR 等級的日誌

ECS 是 Spring Boot 內建的三種結構化格式之一。實跑的每一行都是 JSON，有 service.name、log.level、message、traceId、spanId 等欄位。

結構化日誌比一般純文字日誌好在哪？

  • 日誌檔案會比較小
  • 寫日誌的速度比較快
  • 欄位有名字，可以直接篩選
  • 不需要時間戳記了

純文字要寫正規表示式切出欄位，格式一改就壞；結構化日誌的欄位機器直接讀得懂。

日誌裡的 traceId 與 spanId 是誰放進去的？

  • 程式設計師在每一行 log 手動加上
  • Micrometer Tracing 自動放進 MDC
  • Prometheus 來拉指標時順便加上去
  • Jaeger 收到 span 之後回寫到日誌

Spring Boot 文件：用了 Micrometer Tracing，預設就會在日誌加上關聯 ID，由 MDC 的 traceId 與 spanId 組成。

MDC 的資料是以什麼為單位管理的？

  • 以整個應用程式為單位
  • 以 HTTP 連線為單位
  • 以 logger 名稱為單位
  • 以執行緒為單位，各自一份

Logback 手冊：MDC 以執行緒為單位管理情境資訊。所以同一條執行緒處理下一個請求時，沒清掉的值還在。

transfer 在請求開始時 MDC.put("account", …)，卻忘了在 finally 裡 MDC.remove。可能出什麼事？

  • 程式會編譯不過
  • traceId 會從日誌裡不見
  • 下個請求可能帶著上個人的帳號
  • Prometheus 會拉不到指標

MDC 綁在執行緒上，執行緒池會把同一條執行緒交給下一個請求；沒清掉，舊值就跟著寫進別人的日誌。

把兩個服務的日誌合起來，怎麼找出「同一個請求」的所有紀錄？

  • 找時間戳記在同一秒的日誌
  • 找執行緒名稱相同的日誌
  • 找 logger 名稱相同的日誌
  • 用同一個 traceId 篩選

不同服務的執行緒、logger 都不一樣，同一秒也有很多請求；只有 traceId 是同一個請求全程共用的。實跑篩出四行，兩個服務各兩行。

重點整理

  • 三種訊號：指標說「有沒有事」、追蹤說「在哪一段」、日誌說「發生了什麼」，靠同一個 trace ID 串起來。
  • 四個黃金訊號：延遲、流量、錯誤、飽和；延遲要把失敗請求算進去，飽和看最受限的資源。告警只對使用者感受得到的症狀，加 for 忽略一閃而過的波動，每次呼叫都要能採取行動。
  • Micrometer 是指標的門面；Actuator 預設只暴露 health，要打開 prometheus；計數器只增不減、重啟歸零，名稱的點換底線並加 _total。
  • Prometheus 定時來拉；rate 算每秒增加量，先 rate 再 sum；histogram_quantile 從直方圖的桶線性內插估百分位數，le 要留在 by 裡；錯誤率是兩個 rate 相除。
  • 追蹤：trace ID 貫穿全程，span 記得父節點；跨服務靠 W3C traceparent（version、trace-id、parent-id、trace-flags）；用自動設定的 builder 建 HTTP 用戶端；預設取樣 10%。Spring Boot 4.1 用 spring-boot-starter-opentelemetry 以 OTLP 送出。
  • 結構化日誌（3.4 起內建，logging.structured.format.console=ecs）讓欄位可篩選；traceId 與 spanId 自動進 MDC；業務欄位自己放進 MDC，用完在 finally 清掉；敏感資料不進日誌。
