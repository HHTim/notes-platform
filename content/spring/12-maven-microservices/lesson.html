專案建置

Maven 解決什麼問題？

Maven 是 Java 專案的建置與管理工具。它像一份標準化的施工圖：用 POM（Project Object Model，專案物件模型）描述專案資訊、相依套件與建置規則，讓不同開發工具與自動化環境都能用同一套方式處理專案。

  • 提供標準目錄，正式程式、測試程式與資源各有固定位置。
  • 提供編譯、測試、打包與安裝等建置流程。
  • 用座標宣告第三方程式庫，並自動解析它們的相依套件。
目錄用途
src/main/java正式的 Java 原始碼
src/main/resources正式環境的資源與組態
src/test/java測試的 Java 原始碼
src/test/resources測試需要的資源

原筆記說「不同的 IDE 之間，目錄結構不一樣，無法互通」，正是這套標準目錄要解決的事——所有 IDE 用 Maven 產生的結構都一樣，專案就能互相通用。

套件的身分證

Maven 座標與相依範圍

Maven 座標像套件的收件地址，用來唯一辨識你要用的成品。

groupId所屬的組織或命名空間。
artifactId專案或模組名稱。
version成品版本。
<dependency>
  <groupId>com.example</groupId>
  <artifactId>order-client</artifactId>
  <version>1.2.0</version>
  <scope>test</scope>
</dependency>

相依範圍（scope）決定套件在哪些階段可用。沒寫的時候預設是 compile；test 只在測試的編譯與執行時可用；runtime 表示執行時需要、但正式原始碼編譯時不直接依賴它的 API；provided 表示編譯時需要，執行環境會提供——第 1 課講的 Servlet API 就是這一類。

建置流程

生命週期與階段

Maven 主要有 clean、default 與 site 三套生命週期。常用的 compile、test、package、install 是 default 生命週期裡的階段；執行比較後面的階段時，同一套生命週期裡排在前面的階段會依序先跑。

指令主要效果
mvn clean執行 clean 生命週期，清掉先前的建置產出。
mvn compile編譯正式程式碼。
mvn test先完成必要的前置階段，再執行測試。
mvn package測試後產生 JAR 或 WAR 等成品。
mvn install把成品裝進本機的 Maven 儲存庫，供其他本機專案引用。

執行 mvn package 是不是只做打包？

不是。它會照 default 生命週期的順序先完成前置階段，例如編譯與測試，才進到 package。

原筆記在介紹 default 生命週期時把「測試」打成了「攝氏」，那是輸入法的錯字，內容本身沒問題。

架構選擇

單體式系統與微服務

單體式系統把會員、商品、付款與報表都部署在同一個應用程式裡；微服務則依業務能力拆成可以各自部署的服務。重點是切出清楚的業務邊界，不是把每個類別都變成一個服務。

面向單體式架構微服務架構
部署整包一起部署各服務可以獨立部署
擴充通常擴充整個應用程式可以只針對高流量的服務擴充
開發協調程式集中，起步比較直接團隊自主性高，但介面協調變多
失敗影響共用同一個行程，故障容易擴大可以隔離部分故障，但要設計逾時與降級
資料一致性本機交易好處理跨服務的一致性複雜得多
維運成本服務數少，初期較低需要監控、追蹤、部署與服務治理的能力

拆開不等於自動隔離。把功能做成服務之後，「應用程式必須被設計成能夠容忍服務的失敗」——會需要這樣設計，正是因為一個服務掛掉會影響呼叫它的人。要真的隔離，得另外做逾時、重試上限、斷路器與降級出處。

逾時（timeout）等下游回覆等到一個時間就放棄，不要無限等下去，把自己也拖垮。
斷路器（circuit breaker）像家裡的無熔絲開關：發現某個下游一直失敗，就先直接擋掉對它的呼叫、不要再一直試，等一段時間再放行探一次。
降級（fallback）下游叫不到的時候，改給一個堪用的替代結果，例如回傳快取的舊資料或一份預設清單，讓畫面還是出得來。

拆分的思維

微服務不是免費的效能按鈕

原筆記用了全聯收銀台的例子：本來收銀員要結帳又要裝袋，現在只負責結帳，裝袋交給顧客。微服務也用類似方式讓團隊與元件各自負責清楚的業務能力。差別在於軟體服務之間還多了網路延遲、失敗重試與資料一致性的問題。

微服務可能帶來的好處包括獨立部署、個別擴充、技術選擇的彈性，以及把單次變更的範圍縮小。但這些好處要成立，前提是邊界劃得合理、介面穩定，而且有足夠的自動化測試與維運能力。

主要的挑戰包括：

  • 切得太細，網路呼叫與跨團隊溝通的成本反而變高。
  • API 或訊息格式一改，就要處理版本相容與團隊協調。
  • 跨服務的交易、追蹤、日誌彙整與故障排查都更難。
  • 某個服務故障，仍可能透過同步依賴連鎖影響其他服務。
短期的活動網站、小型團隊，或業務還在快速變動的時候，模組化的單體通常比太早拆成微服務更好維護。

一次 Web 請求的完整路徑

Filter 為什麼比 Controller 更早看到請求？

瀏覽器送出的請求先進 Servlet 容器，再通過 Filter 鏈，之後才到 Spring MVC 的 DispatcherServlet。DispatcherServlet 找到對應的 Controller，完成參數解析與方法呼叫，回應再反向穿過 Filter 鏈出去。

  ↓
Filter 鏈（可能包含 Spring Security）
  ↓
DispatcherServlet
  ↓
HandlerMapping／Interceptor
  ↓
Controller
  ↓

  ↓

這三種東西沒辦法排成一條線。官方文件的原話是「Spring Security 的 Servlet 支援包含在 FilterChainProxy 之內。FilterChainProxy 是 Spring Security 提供的一個特殊 Filter」，而且因為它是一個 Bean，「通常會被包在 DelegatingFilterProxy 裡」再用容器自己的標準機制註冊。也就是說，「Spring Security Filter」在容器眼中只是那條鏈上的其中一格，安全 Filter 彼此的順序是那一格內部的事，不能跟容器那條鏈上的 Filter 放在同一條順序上比大小出處。

MVC 範圍內的錯誤

用全域例外處理器統一 Controller 的回應

@RestControllerAdvice 可以集中處理 Spring MVC 方法執行期間傳出的例外，把它們轉成一致的 HTTP 狀態與回應格式。

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ApiError> handleBusiness(
            BusinessException ex) {
        ApiError body = new ApiError(
            ex.getCode(),
            ex.getMessage()
        );
        return ResponseEntity
            .status(HttpStatus.BAD_REQUEST)
            .body(body);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> handleUnexpected(
            Exception ex) {
        ApiError body = new ApiError(
            "INTERNAL_ERROR",
            "系統暫時無法處理請求"
        );
        return ResponseEntity
            .status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(body);
    }
}

對外的回應不要直接吐出堆疊追蹤、資料庫語法、權杖或內部主機資訊。詳細例外記進受控的日誌，回應只給穩定的錯誤碼與使用者看得懂的訊息。

原筆記的範例程式來自一個工作專案，類別名、錯誤碼列舉與例外型別都是內部命名。本課換成通用示例，程式碼裡的名稱不對應任何實際系統。

MVC 範圍外的錯誤

Filter 丟的例外為什麼常常抓不到？

@ControllerAdvice 只參與 DispatcherServlet 內部的例外解析。Filter 跑在 DispatcherServlet 外圍，所以它在呼叫下游之前或期間丟出的例外，不會自然進到 MVC 的全域例外處理器——這正是原筆記整篇的出發點。

常見的處理策略有三種：

  • 在 Filter 裡自己接住例外，直接設定 HTTP 狀態、內容型態與 JSON 回應。
  • 把可共用的錯誤轉換邏輯抽成一個獨立服務，讓 Filter 與全域例外處理器共用。
  • 把例外交給適當的例外解析器或容器的錯誤處理流程，但要避免重複寫入已經送出的回應。
try {
    filterChain.doFilter(request, response);
} catch (BusinessException ex) {
    response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    response.setContentType("application/json;charset=UTF-8");
    response.getWriter().write(
        errorJson(ex.getCode(), ex.getMessage())
    );
}

原筆記列出的四種方式裡，ServletRequestListener 這一條行不通。它只宣告兩個方法，兩個都只吃一個 ServletRequestEvent 參數，沒有任何例外物件；requestDestroyed 的說明是「收到通知：某個 ServletRequest 即將離開這個 Web 應用程式的範圍」——那時候回應多半也已經送出、改不動了出處。

如果是 Spring Security 的認證或授權錯誤，應該用安全框架自己提供的認證進入點與拒絕存取處理器，而不是把所有錯誤都包成一般的 Controller 例外。

錯誤端點

用 /error 之前要理解它的轉送條件

容器或 Spring Boot 可以把未處理的錯誤分派到 /error，再由錯誤控制器建立回應。但這不是「Filter 一丟例外就一定會呼叫你的自訂方法」：會不會進到錯誤分派、能拿到哪些請求屬性、回應是不是已經送出，都會影響結果。

採用自訂錯誤控制器時，至少要檢查狀態碼、例外物件、原始路徑與回應是否已送出，並且不要把未知例外的內部訊息直接丟給用戶端。

Controller 例外 → MVC 例外解析；Filter 例外 → Filter、安全框架或容器的錯誤流程

串起來看

建置、架構與錯誤格式其實互相牽動

Maven 讓每個服務都能用一致的方式編譯、測試與打包；微服務讓服務可以各自部署；全域例外處理讓 API 的錯誤格式保持一致。如果各服務各自回傳不同的錯誤結構，即使部署已經拆開，用戶端整合起來還是很痛苦。

所以可以把錯誤碼規則、追蹤識別碼與共用回應模型講定成一份明確的約定。共用程式庫可以透過 Maven 發布，但要控制相容性，別讓所有服務被迫同時升級。

重點整理

  • Maven 用 POM 管理座標、相依套件與標準化的建置流程。
  • 執行生命週期後段的階段時，同一套生命週期的前置階段會先跑。
  • 微服務能獨立部署與擴充，但網路、資料一致性與維運成本都會增加。
  • 同步依賴會讓故障連鎖，隔離要靠逾時、斷路器與降級自己設計。
  • Filter 的順序由註冊順序與 order 決定，不是照種類排。
  • @RestControllerAdvice 只管得到 Spring MVC 範圍內的例外。
  • 錯誤回應要穩定且不洩漏內部資訊，細節留在受控日誌。
