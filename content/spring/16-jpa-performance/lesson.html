N+1 查詢怎麼發生：先數清楚送了幾次 SQL

看 JPA 效能先數一件事：同一段程式送了幾次 SQL？每一次都是一個來回（round trip，送出一句 SQL、等資料庫回覆），來回越多，回應越慢。延遲載入與 LAZY、EAGER 的設定見〈Hibernate 入門與環境〉〈Hibernate 查詢與關聯〉。

示範專案用 Spring Boot 4.1.1（Spring Framework 7.0.9、Hibernate 7.4.5）、Java 21、H2 記憶體資料庫，資料是三個部門、六名員工（研發部 2 人、業務部 3 人、客服部 1 人）：

@Entity
public class Department {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;
    private String name;

    @OneToMany(mappedBy = "department")            // 一對多預設就是 LAZY
    private List<Employee> employees = new ArrayList<>();
    // 建構子、getter 省略
}

@Entity
public class Employee {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)              // 多對一預設是 EAGER，這裡改成 LAZY
    private Department department;
    // 建構子、getter 省略
}

最簡單的看法是設 spring.jpa.show-sql=true（Whether to enable logging of SQL statements）。出處 這課改用 datasource-proxy 函式庫把 DataSource 包一層，每次真的送到資料庫就編號印出來。使用指南也建議這樣做：DataSource 代理「可以在測試時檢查執行了幾句 SQL」，讓整合測試在偵測到 N+1 時失敗（you can assert the number of executed statements at test time. This way, you can have the integration tests fail when a N+1 query issue is automatically detected.）。出處

在一筆交易裡（tx 是〈Spring AOP 與交易控制〉提過的 TransactionTemplate）查出所有部門，再印每個部門的人數；depts 是繼承 JpaRepository 的 Repository：

tx.executeWithoutResult(s -> {
    List<Department> list = depts.findAll();
    for (Department d : list) {
        System.out.println(d.getName() + " 有 " + d.getEmployees().size() + " 人");
    }
});

findAll() 只送了 SQL 1。員工集合是延遲載入，迴圈每碰一次 getEmployees()，Hibernate 才替那個部門補查一次（SQL 2〜4）。這就是 N+1 查詢：1 次查清單，再為 N 筆各查 1 次；一百個部門就是 101 次。使用指南說「另外送一句 SELECT 去載入」的抓法「就是一般說的 N+1」（This is the strategy generally termed N+1.）。出處

多對一預設 EAGER，也會造成 N+1

JPA 規格規定 @ManyToOne、@OneToOne 預設 EAGER（立即載入）。Hibernate 建議全部標 LAZY，但身為 JPA 實作「會遵守那個預設」（Hibernate, as a Jakarta Persistence provider, honors that default.）。出處 EAGER 不等於一句拿齊。示範專案的筆電實體 owner 沒寫 fetch，四台筆電分給阿明（兩台）、小美、志豪：

@ManyToOne                                      // 沒寫 fetch：照 JPA 預設是 EAGER
private Employee owner;                         // Laptop 實體的欄位

// 在交易裡
List<Laptop> list = laptops.findAll();
System.out.println("拿到 " + list.size() + " 台筆電");
== eager
  SQL 1：select l1_0.id,l1_0.owner_id,l1_0.serial from laptop l1_0
  SQL 2：select e1_0.id,e1_0.department_id,e1_0.name from employee e1_0 where e1_0.id=?
  SQL 3：select e1_0.id,e1_0.department_id,e1_0.name from employee e1_0 where e1_0.id=?
  SQL 4：select e1_0.id,e1_0.department_id,e1_0.name from employee e1_0 where e1_0.id=?
拿到 4 台筆電
共 4 次 SQL

程式沒碰 owner，Hibernate 還是為每個不同的主人補查一次；阿明的兩台共用同一個物件，第二次從一級快取拿（後面會講），所以補 3 次。最佳實務一章說「EAGER 幾乎總是不好的選擇」（EAGER fetching is almost always a bad choice.）：它不能針對單一查詢關掉，JPQL 忘了 JOIN FETCH 時還會另外補查，「進而可能造成 N+1」（which in turn can lead to N+1 query issues）。出處 所以多對一、一對一都明寫 fetch = FetchType.LAZY，需要時再在查詢上指定一起抓。

  • 4 次

筆電 1 次，三個不同的主人各補 1 次；阿明的第二台從一級快取拿，所以不是 5 次。

@ManyToOne 沒寫 fetch 時，照 JPA 規格是哪一種？

  • LAZY
  • EAGER
  • 看資料庫決定
  • 看 Hibernate 版本

規格規定一對一、多對一預設立即載入；一對多、多對多預設才是 LAZY。

Hibernate 使用指南對關聯載入的建議是什麼？

  • 全部標 EAGER，省得之後還要再查一次
  • 只有一對多標 LAZY
  • 不寫關聯，全部改用原生 SQL 查
  • 全標 LAZY，需要時在查詢指定

EAGER 不能針對單一查詢關掉，還可能造成 N+1，所以指南建議全部 LAZY、需要時再指定。

想在整合測試裡自動抓出 N+1，使用指南建議的做法是哪一個？

  • 用 DataSource 代理數句數
  • 把 show-sql 打開，靠眼睛一行一行看
  • 全部改成 EAGER
  • 把測試資料改成只有一筆就好

代理記下每次真的送出的 SQL，測試裡檢查句數，多出來就失敗；只放一筆資料反而看不出 N+1。

一次把要用的都拿回來

JOIN FETCH 與 @EntityGraph：在查詢上指定要一起抓

這個使用情境要用到員工，就在查詢時一起抓。HQL／JPQL 用 join fetch，使用指南：它「蓋過關聯的延遲設定，指定用 SQL 的 join 一起抓」（A fetch join overrides the laziness of a given association, specifying that the association should be fetched with a SQL join.），「沒有它，你很快就會遇上可怕的 n+1 selects 問題」（Without it, you’ll quickly run into the dreaded "n+1 selects" problem.）。出處

interface DepartmentRepository extends JpaRepository<Department, Long> {
    @Query("select d from Department d left join fetch d.employees order by d.id")
    List<Department> findAllWithEmployees();
}

// 在交易裡
List<Department> list = depts.findAllWithEmployees();
System.out.println("list.size() = " + list.size());
for (Department d : list) {
    System.out.println(d.getName() + " 有 " + d.getEmployees().size() + " 人");
}
== joinfetch
  SQL 1：select d1_0.id,e1_0.department_id,e1_0.id,e1_0.name,d1_0.name from department d1_0 left join employee e1_0 on d1_0.id=e1_0.department_id order by d1_0.id
list.size() = 3

共 1 次 SQL
  • left join fetch 與 join fetch 不一樣。join fetch（內部連接）「只回傳有關聯實體的那些」（only returns base entities with an associated entity），一個人都沒有的部門也要列出來就用 left。出處
  • 從 Hibernate 6 起不必再寫 distinct。SQL 回 6 列（一個員工一列），list.size() 卻是 3：join fetch 造成的重複結果「由 Hibernate 在記憶體裡自動去掉」（automatically removed by Hibernate in memory），「不該為了這個目的用 distinct」（distinct should not be used for this purpose）。出處 舊教材的 select distinct d … join fetch 是 Hibernate 5 的寫法。遷移指南

@EntityGraph：衍生查詢也能一起抓

方法名稱衍生查詢（〈Spring 資料存取〉）沒有地方寫 join fetch，改用 @EntityGraph：「給的 attributePaths 會轉成對應的 EntityGraph，不必在實體上另外加 @NamedEntityGraph」（The provided attributePaths are translated into the according EntityGraph without needing to explicitly add @NamedEntityGraph to your domain types）。出處 實體圖（entity graph）就是「這次查詢要一起載入哪些關聯」的清單。

@EntityGraph(attributePaths = "employees")
List<Department> findByNameEndingWith(String suffix);

一樣是一句左外部連接。差別只在寫在哪：JOIN FETCH 在查詢字串裡，@EntityGraph 是方法上的註解。

抓取連接的三個注意事項

分頁要看 Hibernate 版本與資料庫。抓取集合時 SQL 一列是「一個部門配一名員工」，外層直接 limit 切的是列，不是部門。Hibernate 7.4 的實跑：

@Query(value = "select d from Department d left join fetch d.employees",
       countQuery = "select count(d) from Department d")
Page<Department> findPageWithEmployees(Pageable pageable);

// 在交易裡：第一頁、每頁 2 個部門
var page = depts.findPageWithEmployees(PageRequest.of(0, 2));
System.out.println("這一頁 " + page.getContent().size() + " 個部門，共 " + page.getTotalElements() + " 個");
（H2）
== page
  SQL 1：select d1_0.id,e1_0.department_id,e1_0.id,e1_0.name,d1_0.name from (select d1_0.id,d1_0.name from department d1_0 offset ? rows fetch first ? rows only) d1_0(id,name) left join employee e1_0 on d1_0.id=e1_0.department_id
  SQL 2：select count(d1_0.id) from department d1_0

Hibernate 7.4 先在子查詢裡切出這一頁的 2 個部門，再 left join 員工，每個部門的員工都完整；MySQL 8.4 上一樣，只是寫成 limit ?,?。資料庫不支援子查詢裡的 LIMIT 時，hibernate.query.fail_on_pagination_over_collection_fetch 的說明是筆數限制只能「在記憶體裡套用」（the limit must be applied in-memory instead of on the database），預設關閉，打開才會直接丟例外。出處 舊版本要特別小心：同一支程式用 Spring Boot 3.5.16（Hibernate 6.6.53）在 H2 上跑，沒有子查詢，而是印出警告、把整張表撈回來才切：

（Spring Boot 3.5.16、Hibernate 6.6.53、H2，只列警告與 SQL 1）
2026-10-02T19:16:30.881+08:00  WARN 95355 --- [           main] org.hibernate.orm.query                  : HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
  SQL 1：select d1_0.id,e1_0.department_id,e1_0.id,e1_0.name,d1_0.name from department d1_0 left join employee e1_0 on d1_0.id=e1_0.department_id

不要同時抓兩個以上的集合。這會「在資料庫產生笛卡兒積，效能可能非常差」（results in a Cartesian product at the database level, and might exhibit very poor performance）：一個部門 10 名員工、10 個專案，join 起來是 100 列。出處 最佳實務一章建議 JOIN FETCH「最多只抓一個集合」（at most one collection），其他集合用第二句查詢。出處

不要在被抓的那一邊加條件。那樣「抓回來的集合元素會不完整」（the elements of the fetched collection would be incomplete）。出處 例如 join fetch d.employees e where e.name like '阿%'，d.getEmployees() 只剩名字開頭是「阿」的人，看起來卻像完整的集合。

從 Hibernate 6 起，join fetch 造成的重複部門會在記憶體裡去掉。

想列出所有部門和員工，連一個人都沒有的部門也要出現，該用哪一個？

  • join fetch
  • inner join fetch
  • left join fetch
  • 不寫 fetch，用延遲載入

內部連接只回傳有員工的部門；join fetch 就是 inner join fetch；不寫 fetch 會回到 N+1。

衍生查詢 findByNameEndingWith 沒有地方寫 join fetch，想讓它一起抓員工，Spring Data JPA 的做法是？

  • 加 @EntityGraph(attributePaths = "employees")
  • 把 Department.employees 改成 FetchType.EAGER
  • 在方法名稱裡加上 FetchEmployees 關鍵字
  • 把 spring.jpa.open-in-view 打開

attributePaths 會轉成這次查詢的實體圖。改 EAGER 會影響所有查詢；方法名稱沒有 Fetch 這種關鍵字。

Hibernate 7.4 跑 left join fetch 加 PageRequest.of(0, 2)，SQL 1 怎麼切出這一頁？

  • 子查詢先切部門，再 join
  • 全部撈回來，再在記憶體裡切
  • 外層直接 limit 2，只拿兩列
  • 直接丟例外，不送 SQL

實跑是先在子查詢裡切部門、再 join 員工。整批撈回在記憶體裡切，是 Hibernate 6.6 的行為。

假設部門還有專案集合 projects，一句查詢同時 join fetch 員工與專案。使用指南警告什麼？

  • 編譯會失敗
  • 交易會自動還原，資料讀不到
  • 產生笛卡兒積，可能很慢
  • 第二個集合會被 Hibernate 忽略

兩個集合平行 join，列數相乘。JOIN FETCH 最多抓一個集合，其他用第二句查詢。

select d from Department d join fetch d.employees e where e.name like '阿%'，拿到的 d.getEmployees() 有什麼問題？

  • 會再補查一次，變成 N+1
  • 只剩符合條件的員工，集合不完整
  • 會丟出 LazyInitializationException
  • 沒有問題，跟不加條件一樣

集合裡只剩名字開頭是「阿」的人，卻看起來像完整的員工集合。

一次問好幾個，少跑幾趟

批次抓取：@BatchSize 與 hibernate.default_batch_fetch_size

JOIN FETCH 最好只抓一個集合，分頁也不一定能交給資料庫。這時還有一招：延遲載入照舊，但補查時一次補好幾個。使用指南叫它 BATCH：「用一句另外的 SQL，在 WHERE 裡用 IN 條件依批次大小載入」（using an IN-restriction as part of the SQL WHERE-clause based on a batch size）。出處 全站一起開用 spring.jpa.properties.*（原樣交給 JPA 實作的屬性，Additional native properties to set on the JPA provider）：出處

spring.jpa.properties.hibernate.default_batch_fetch_size=10

只開某一個關聯就在集合上加 @BatchSize；預設「只對明確標了 @BatchSize 的實體與集合做批次抓取」（By default, Hibernate only uses batch fetching for entities and collections explicitly annotated @BatchSize.）。出處

@OneToMany(mappedBy = "department")
@BatchSize(size = 2)                               // org.hibernate.annotations.BatchSize
private List<Employee> employees = new ArrayList<>();

第一段那支 N+1 程式一個字都不改，只改設定再跑：

不設全站、只在 employees 加 @BatchSize(size = 2) 再跑一次，輸出跟上面 size=2 那組逐字相同。

讀第一個部門的員工時，Hibernate 順便把還沒載入員工的其他部門一起放進 IN。N 個部門、批次大小 b，補查約 N ÷ b 次（無條件進位）：100 個部門、大小 10 是 1 + 10 次，不是 1 + 100 次。

不過使用指南也說，「多數時候 DTO 投影或 JOIN FETCH 是好得多的選擇，因為一句查詢就拿齊」（most of the time, a DTO projection or a JOIN FETCH is a much better alternative since it allows you to fetch all the required data with a single query）。出處 批次抓取適合 JOIN FETCH 用不上的地方：要抓兩個以上集合，或沒辦法用子查詢分頁的列表。

清單 1 次，員工每 10 個部門補 1 次、共補 10 次。不設批次是 101 次。

批次抓取補查時，SQL 用哪一種條件把好幾個部門一起問？

  • department_id = ?，一次一個
  • department_id in (?, ?, …)
  • left join department
  • department_id between ? and ?

BATCH 用 IN 條件依批次大小載入；只剩一個時才退回 = ?。

@BatchSize 和 hibernate.default_batch_fetch_size 差在哪？

  • @BatchSize 管寫入，另一個管讀取
  • @BatchSize 只管標了它的關聯，另一個是全站預設
  • @BatchSize 是 JPA 標準，另一個是 Hibernate 專屬
  • 兩個一模一樣，只是寫的位置不同

預設只對標了 @BatchSize 的關聯做批次抓取；default_batch_fetch_size 把它變成全站預設。兩者都是 Hibernate 專屬。

使用指南怎麼比較 @BatchSize 與 JOIN FETCH、DTO 投影？

  • @BatchSize 永遠是三者裡最快的
  • 多數時候後兩者更好
  • 三者效果完全相同，只是寫法不同
  • JOIN FETCH 已經不建議再使用

多數時候 DTO 投影或 JOIN FETCH 更好，一句查詢就能拿齊。

open-in-view 的坑

〈Hibernate 入門與環境〉提過 spring.jpa.open-in-view，這裡實際跑一次。Spring Boot 的說明：它「在處理請求的整段期間把 JPA EntityManager 綁在執行緒上」（Binds a JPA EntityManager to the thread for the entire processing of the request.），預設 true；出處 用途是「在原本的交易已經結束之後，仍然可以延遲載入」（to allow for lazy loading in web views despite the original transactions already being completed）。出處 示範端點：服務層在交易裡查出部門就回傳，Controller 才去讀員工集合：

@Service
class DepartmentService {
    @Transactional(readOnly = true)
    public Department find(Long id) {                 // 交易在這個方法結束時就提交了
        return repo.findById(id).orElseThrow();
    }
}

@RestController
class DepartmentController {
    @GetMapping("/departments/{id}")

查過的不再查，改過的晚點一起送

一級快取與 flush 時機

Hibernate 在一個 Session（JPA 叫 EntityManager）裡維護一個持久化環境（persistence context）：這段工作範圍裡它正在管的那批實體物件，也叫一級快取（first level cache）。出處 在這個範圍裡，「Hibernate 保證資料庫的一列與 Java 的一個物件一一對應」（Hibernate guarantees equivalence of persistent identity (database row) and Java identity inside a particular session scope.）。出處 Spring 注入的 EntityManager 是代理，「把所有呼叫轉給目前那筆交易的 EntityManager」（It delegates all calls to the current transactional EntityManager, if any.），出處 所以一級快取通常跟著一筆交易走（開著 open-in-view 時跟著整個請求），不是全站共用。

改過的晚點一起送：flush

持久化環境像一個延後寫入的快取，「變更先套用在記憶體，在 flush 時才同步到資料庫」（changes are first applied in-memory and synchronized with the database during the flush time）。出處 預設的 AUTO 模式在三個時機 flush：出處

  • 交易提交之前（prior to committing a Transaction）
  • 執行一個跟排隊中的變更有重疊的 JPQL／HQL 查詢之前（prior to executing a JPQL/HQL query that overlaps with the queued entity actions）
  • 執行沒有宣告會影響哪些資料表的原生 SQL 查詢之前（before executing any native SQL query that has no registered synchronization）：原生 SQL 是手寫字串，Hibernate 看不出它碰哪些表，沒宣告就先全部 flush

一句一句送，不如一批一批送

批次寫入：hibernate.jdbc.batch_size 與 IDENTITY 主鍵

JDBC 可以把同一句 SQL 的多組參數打包一次送（〈Spring 資料存取〉的 batchUpdate），Hibernate 也能，但預設沒開：「JDBC 批次預設沒有開啟，所以每一句 INSERT 都要一次資料庫來回。要開啟，把 hibernate.jdbc.batch_size 設成 10 到 50 之間的整數」（JDBC batching is not enabled by default, so every insert statement requires a database round trip. To enable JDBC batching, set the hibernate.jdbc.batch_size property to an integer between 10 and 50.）。出處 示範專案有兩個只差主鍵策略的便條實體：SEQUENCE 先從序列（sequence，資料庫裡專門發號碼的物件）拿號碼；IDENTITY 用自動遞增欄位，INSERT 時才由資料庫給號碼。

@Entity
public class SeqNote {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)   // 序列：先拿號碼，INSERT 可以晚點一起送
    private Long id;
    private String text;
}

@Entity
public class IdNote {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)   // 自動遞增：INSERT 完才知道號碼
    private Long id;
    private String text;
}

// 在交易裡（IdNote 那一次把 SeqNote 換成 IdNote）
for (int i = 1; i <= 12; i++) {
    em.persist(new SeqNote("便條 " + i));
}
System.out.println("迴圈結束，準備提交");

大量寫入要定期 flush 與 clear

一次寫幾萬筆時，persist 過的物件都留在一級快取裡。使用指南：「定期呼叫 flush() 與 clear()，控制一級快取的大小」（employ methods flush() and clear() to the session regularly, to control the size of the first-level cache.），出處 筆數跟 batch_size 對齊：

for (int i = 1; i <= 12; i++) {
    em.persist(new SeqNote("便條 " + i));
    if (i % batch == 0) {
        em.flush();
        em.clear();
        System.out.println("第 " + i + " 筆：flush 並 clear，一級快取裡剩 "
                + em.unwrap(org.hibernate.Session.class).getStatistics().getEntityCount() + " 個物件");
    }
}
System.out.println("迴圈結束，準備提交");

IDENTITY 主鍵為什麼讓 INSERT 批次失效？

  • 因為 IDENTITY 欄位不能用預備敘述
  • 自動遞增表不能開交易
  • 要先 INSERT 才拿得到主鍵
  • 因為 Hibernate 7 還沒支援這個

IDENTITY 必須在 persist() 之後馬上 INSERT，號碼不送就拿不到，沒有東西能排隊打包。

IdNote 的實跑輸出裡，12 句 INSERT 出現在「迴圈結束，準備提交」之前還是之後？

  • 之後，提交前才 flush 送出
  • 前 5 句在之前，其他句在之後
  • 完全沒有送出，交易被還原

IDENTITY 一 persist 就 INSERT；SeqNote 才是排著等提交前 flush。

大量匯入時，每 N 筆呼叫一次 flush() 加 clear()，主要是為了什麼？

  • 讓交易每 N 筆就提交一次
  • 讓 IDENTITY 主鍵也能批次寫入
  • 讓資料庫自動幫表建立索引
  • 控制一級快取的大小

flush 把排著的 INSERT 送出，clear 清掉物件；交易仍是一筆，提交在最後。

MySQL 8.4 上 Hibernate 送出 5、5、2 三批，網址沒開 rewriteBatchedStatements。伺服器實際執行幾句 INSERT？

  • 3 句
  • 12 句
  • 1 句
  • 0 句，資料沒寫進去

實測 Com_insert 增加 12；開了 rewriteBatchedStatements 才變成 3。

只要兩個欄位，就只查兩個欄位

投影成 DTO：只查畫面要的欄位

前面的解法都還是查出完整的實體。畫面只要幾個欄位時，可以直接投影（〈Hibernate 查詢與關聯〉講過 HQL 的 select new）。Spring Data JPA 有兩種寫法：

介面投影：回傳型別是只有 getter 的介面。getter 都對應到 Repository 管的那個實體的屬性時叫封閉投影，「Spring Data 可以把查詢最佳化，因為知道撐起投影代理需要哪些屬性」（Spring Data can optimize the query execution, because we know about all the attributes that are needed to back the projection proxy.）。出處

類別投影（DTO）：回傳型別是 record，「Java record 很適合定義 DTO 型別」（Java Records are ideal to define DTO types）；用 @Query 寫 JPQL 時靠建構子表示式 select new，類別名稱要寫完整（Note the usage of a FQDN for the DTO type!）。出處

interface EmployeeName { String getName(); }                       // 介面投影
public record EmployeeRow(String employee, String department) {}    // DTO

interface EmployeeRepository extends JpaRepository<Employee, Long> {
    List<EmployeeName> findByDepartmentName(String departmentName);

    @Query("select new demo.EmployeeRow(e.name, d.name) from Employee e join e.department d order by e.id")
    List<EmployeeRow> findRows();
}

// 在交易裡
for (EmployeeName e : emps.findByDepartmentName("業務部")) System.out.print(e.getName() + " ");
System.out.println();
for (EmployeeRow r : emps.findRows()) System.out.print(r + " ");
System.out.println();

兩句都只選需要的欄位，沒有補查。DTO 不是實體，不進一級快取、不被髒資料檢查追蹤：拿來顯示很合適，要修改還是查實體。

整理：哪個情境用哪一招

情境先考慮
唯讀列表、報表，只要幾個欄位DTO 或介面投影
要修改實體，而且要用到一個集合JOIN FETCH 或 @EntityGraph
要用到兩個以上的集合，或沒辦法用子查詢分頁批次抓取
大量新增batch_size＋序列主鍵＋定期 flush、clear

List<EmployeeName> findByDepartmentName(String)，EmployeeName 只有 getName()。實跑的 SQL 選了哪些欄位？

  • employee 的所有欄位
  • employee 與 department 的所有欄位
  • 只有 employee 的 name
  • 只有 department 的 name

封閉投影讓 Spring Data 只查 name；部門只用在 where 條件裡。

什麼樣的投影介面叫「封閉投影」？

  • 介面宣告成 sealed
  • 只能在交易裡使用的投影
  • 用 @Value 算出新值的投影
  • getter 全對應實體屬性

getter 全部對應到實體的屬性才是封閉投影；用 @Value 算新值的是開放投影。

findRows() 用 select new demo.EmployeeRow(e.name, d.name) 查出 6 名員工與部門名稱，送幾次 SQL？

  • 1 次
  • 7 次
  • 4 次
  • 2 次

一句 join 直接把兩個名稱放進 record，沒有實體，也就沒有補查。

用 findRows() 查出 EmployeeRow 清單，在交易裡把清單裡某一筆換成姓名不同的新 record。交易提交時會怎樣？

  • 送出 UPDATE 更新員工
  • 丟出 LazyInitializationException
  • 送出 INSERT 新增一筆員工
  • 什麼都不會發生

DTO 不是實體，不被追蹤；換掉 record 只是改了記憶體裡的 List。

畫面是「每頁 20 個部門，每個部門列出員工與專案兩個清單」，而且要修改部門資料。最適合先考慮哪一招？

  • 一句同時 join fetch 員工與專案
  • 把兩個集合都改成 EAGER
  • 分頁查部門，兩個集合用批次抓取
  • 打開 open-in-view 讓畫面自己查

兩個集合一起 JOIN FETCH 會產生笛卡兒積；改 EAGER、開 open-in-view 都不對。分頁查部門再用批次抓取。

重點整理

  • N+1：1 次查清單，再為 N 筆的延遲載入關聯各補查 1 次；用 DataSource 代理在測試裡檢查句數。多對一、一對一預設 EAGER 也會造成 N+1，明寫 LAZY。
  • JOIN FETCH 與 @EntityGraph 一句拿齊，Hibernate 6 起不必寫 distinct；Hibernate 7 把分頁放進子查詢（6 是在記憶體裡切）；不要同時抓兩個集合、不要在被抓的一邊加條件。
  • 批次抓取（@BatchSize、default_batch_fetch_size）用 IN 一次補好幾筆，約 N ÷ 批次大小次；適合多個集合。
  • open-in-view 預設 true，延遲載入跑到交易外的 Controller 與 JSON 序列化；直接回傳實體還可能因雙向關聯無限遞迴。
  • 一級快取：同一個 EntityManager 裡一個主鍵只有一個物件；AUTO flush 在提交前、查重疊的表前、原生 SQL 前；flush 不等於 commit。
  • 批次寫入預設沒開；IDENTITY 主鍵讓 INSERT 批次失效；MySQL 還要 rewriteBatchedStatements=true；大量匯入定期 flush、clear。
  • 唯讀畫面優先投影成 DTO 或介面投影：只查需要的欄位、不進一級快取。
