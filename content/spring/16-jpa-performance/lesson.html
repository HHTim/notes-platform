N+1 查詢怎麼發生：先數清楚送了幾次 SQL

〈Hibernate 入門與環境〉講過延遲載入：關聯的資料先不查，等程式真的去讀才查。〈Hibernate 查詢與關聯〉講過 @OneToMany、@ManyToOne 與 LAZY、EAGER 怎麼設定。這一課把它們放到效能上看：同一段程式，到底送了幾次 SQL 給資料庫？每一次都是一個來回（round trip，程式送出一句 SQL、等資料庫回覆），來回越多，回應越慢。

這課的示範專案用 Spring Boot 4.1.1（內含 Spring Framework 7.0.9、Hibernate 7.4.5）、Java 21、H2 記憶體資料庫。資料是三個部門、六名員工：研發部 2 人、業務部 3 人、客服部 1 人。實體跟〈Hibernate 查詢與關聯〉同一套寫法：

@Entity
public class Department {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;
    private String name;

    @OneToMany(mappedBy = "department")            // 一對多預設就是 LAZY
    private List<Employee> employees = new ArrayList<>();
    // 建構子、getter 省略
}

@Entity
public class Employee {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)              // 多對一預設是 EAGER，這裡改成 LAZY
    private Department department;
    // 建構子、getter 省略
}

怎麼數 SQL？最簡單的是設 spring.jpa.show-sql=true（Spring Boot 的說明：「是否記錄 SQL 敘述」，Whether to enable logging of SQL statements）。出處 這課改用 datasource-proxy 這個函式庫把 DataSource 包一層，每次真的送到資料庫就記一筆、編號印出來。Hibernate 使用指南也這樣建議：用 DataSource 代理的另一個好處是「可以在測試時檢查執行了幾句 SQL」，讓整合測試在自動偵測到 N+1 時失敗（Another advantage of using a DataSource proxy is that you can assert the number of executed statements at test time. This way, you can have the integration tests fail when a N+1 query issue is automatically detected.）。出處

findAll() 只送了一句（SQL 1）。員工集合是延遲載入，迴圈每碰一次 getEmployees().size()，Hibernate 才替那個部門補查一次員工（SQL 2〜4）。三個部門就是 1 + 3 次；一百個部門就是 1 + 100 次。這就叫 N+1 查詢：1 次查清單，再為清單裡的 N 筆各查 1 次。Hibernate 使用指南把「另外送一句 SELECT 去載入」這種抓法叫 SELECT，並說它「就是一般說的 N+1」（This is the strategy generally termed N+1.）。出處

多對一預設 EAGER，也會造成 N+1

JPA 規格規定 @ManyToOne 與 @OneToOne 預設是 EAGER（立即載入）。Hibernate 使用指南說：Hibernate 建議全部關聯都標成延遲載入、需要時再在查詢上指定要一起抓，可惜這跟 JPA 規格「一對一與多對一預設立即載入」相衝，而 Hibernate 身為 JPA 實作「會遵守那個預設」（Hibernate, as a Jakarta Persistence provider, honors that default.）。出處 EAGER 不代表「一句 SQL 就拿齊」。示範專案多一個筆電實體，owner 沒寫 fetch，就是 EAGER。四台筆電分給阿明（兩台）、小美、志豪：

@Entity
public class Laptop {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;
    private String serial;

    @ManyToOne                                      // 沒寫 fetch：照 JPA 預設是 EAGER
    private Employee owner;
}

// 在交易裡
List<Laptop> list = laptops.findAll();
System.out.println("拿到 " + list.size() + " 台筆電");

程式根本沒碰 owner，Hibernate 還是在查詢時順手為每個不同的主人補查一次。四台筆電只補了 3 次，是因為阿明的兩台共用同一個 Employee 物件，第二次直接從一級快取拿（後面會講）。使用指南在最佳實務一章講得很重：「EAGER 幾乎總是不好的選擇」（EAGER fetching is almost always a bad choice.），因為它「不能針對單一查詢覆蓋掉」，而且 JPQL 查詢忘了 JOIN FETCH 一個 EAGER 關聯時，Hibernate 會用第二句 SQL 去初始化它，「進而可能造成 N+1 查詢」（which in turn can lead to N+1 query issues）。出處 所以實務上 @ManyToOne、@OneToOne 都明寫 fetch = FetchType.LAZY，再依每個查詢的需要決定要不要一起抓。

「N+1」裡的 1 和 N 各指什麼？

  • 1 是查清單，N 是每筆補查
  • 1 是交易數，N 是連線數量
  • 1 是主鍵，N 是外來鍵
  • 1 是 Repository，N 是實體

先 1 次查出 N 筆資料，再為每一筆的關聯各送 1 次，所以是 N + 1 次。

Hibernate 使用指南對關聯載入的建議是什麼？

  • 全部標 EAGER，省得之後還要再查一次
  • 只有一對多標 LAZY
  • 不寫關聯，全部改用原生 SQL 查
  • 全標 LAZY，需要時在查詢指定

原文是「把所有關聯靜態地標成延遲載入，要立即載入時用動態的抓取策略」。EAGER 不能針對單一查詢關掉，還可能造成 N+1。

  • 全部改成 EAGER
  • 把測試資料改成只有一筆就好

JOIN FETCH 與 @EntityGraph：在查詢上指定要一起抓

解法的方向是：這個使用情境要用到員工，就在查詢時一起抓。HQL／JPQL 用 join fetch。使用指南：抓取連接「蓋過某個關聯的延遲設定，指定用 SQL 的 join 一起抓」（A fetch join overrides the laziness of a given association, specifying that the association should be fetched with a SQL join.），而且這是 Hibernate 最重要的功能之一，「沒有它，你很快就會遇上可怕的 n+1 selects 問題」（Without it, you’ll quickly run into the dreaded "n+1 selects" problem.）。出處

interface DepartmentRepository extends JpaRepository<Department, Long> {
    @Query("select d from Department d left join fetch d.employees order by d.id")
    List<Department> findAllWithEmployees();
}

// 在交易裡
List<Department> list = depts.findAllWithEmployees();
System.out.println("list.size() = " + list.size());
for (Department d : list) {
    System.out.println(d.getName() + " 有 " + d.getEmployees().size() + " 人");
}

  • left join fetch 與 join fetch 不一樣。使用指南：join fetch（內部連接）「只回傳有關聯實體的那些」，left join fetch「回傳所有的基本實體，包括沒有任何關聯實體的」。出處 一個人都沒有的部門也要列出來，就要用 left。
  • 從 Hibernate 6 起不必再寫 distinct。SQL 的 left join 會回 6 列（一個員工一列），但 list.size() 是 3。使用指南：「從 Hibernate 6 起，join fetch 造成的重複結果會由 Hibernate 在記憶體裡自動去掉……不再需要明確去重，尤其不該為了這個目的用 distinct」（As of Hibernate 6, duplicate results arising from the use of join fetch are automatically removed by Hibernate in memory … It’s no longer necessary to remove duplicate results explicitly, and, in particular, distinct should not be used for this purpose.）。出處 舊教材的 select distinct d … join fetch 是 Hibernate 5 的寫法。遷移指南

@EntityGraph：不寫 JPQL 也能指定要一起抓

@EntityGraph(attributePaths = "employees")

資料一多，這等於每翻一頁都把整張表搬回來。維護中的舊專案若還在 Hibernate 6，或資料庫不支援子查詢裡的 LIMIT，分頁列表改用下一段的批次抓取比較保險。

  • 不要同時抓兩個以上的集合。「平行抓取多個集合或對多關聯，會在資料庫產生笛卡兒積，效能可能非常差」（fetching multiple collections or to-many associations in parallel results in a Cartesian product at the database level, and might exhibit very poor performance）。出處 笛卡兒積就是兩邊兩兩配對：一個部門 10 名員工、10 個專案，join 起來是 100 列。最佳實務一章的建議是 JOIN FETCH「最多只抓一個集合」，其他集合用第二句查詢。出處
  • 不要在被抓的那一邊加條件。使用指南：對 join fetch 進來的實體加限制條件「通常是壞主意，因為抓回來的集合元素會不完整」（since the elements of the fetched collection would be incomplete）。出處 例如 join fetch d.employees e where e.name like '阿%'，拿到的 d.getEmployees() 只剩名字開頭是「阿」的人，看起來卻像完整的集合。

在 Hibernate 6 以後的版本寫 join fetch 查一對多，還要不要加 distinct 去掉重複的父實體？

  • 要，不然結果一定會有重複的部門
  • 要，寫在 SQL 裡

使用指南明寫不再需要明確去重，也不該為了這個用 distinct。要加 distinct 是 Hibernate 5 的寫法。

想列出所有部門和員工，連一個人都沒有的部門也要出現，該用哪一個？

  • join fetch
  • inner join fetch
  • left join fetch

內部連接只回傳有關聯實體的部門；left join fetch 才會連沒有員工的部門一起回傳。join fetch 跟 inner join fetch 是同一個意思。不寫 fetch 會回到 N+1。

衍生查詢 findByNameEndingWith 沒有地方寫 join fetch，想讓它一起抓員工，Spring Data JPA 的做法是？

  • 加 @EntityGraph(attributePaths = "employees")
  • 把 Department.employees 改成 FetchType.EAGER
  • 在方法名稱裡加上 FetchEmployees 關鍵字
  • 把 spring.jpa.open-in-view 打開

@EntityGraph 的 attributePaths 會轉成這次查詢的實體圖，不必另外定義 @NamedEntityGraph。改 EAGER 會影響所有查詢；方法名稱沒有 Fetch 這種關鍵字。

用本課的 Hibernate 7.4 在 H2 上跑 left join fetch d.employees 加 PageRequest.of(0, 2)，SQL 1 怎麼切出這一頁？

  • 子查詢先切部門，再 join
  • 全部撈回來，再在記憶體裡切
  • 外層直接 limit 2，只拿兩列
  • 直接丟例外，不送 SQL

實跑的 SQL 1 是 from (select … from department … fetch first ? rows only) left join employee，先在子查詢裡切部門，員工才不會被切掉。全部撈回再在記憶體裡切，是 Hibernate 6.6 的行為，或資料庫不支援子查詢 LIMIT 時的退路。

  • 交易會自動還原，資料讀不到
  • 產生笛卡兒積，可能很慢
  • 第二個集合會被 Hibernate 忽略

兩個集合平行 join，員工與專案兩兩配對，列數相乘。建議 JOIN FETCH 最多抓一個集合，其他集合用第二句查詢。

  • 只剩符合條件的員工，集合不完整
  • 會丟出 LazyInitializationException
  • 沒有問題，跟不加條件一樣

條件套在被抓的那一邊，集合裡只剩名字開頭是「阿」的人，但它看起來像完整的員工集合，之後的程式會被誤導。

一次問好幾個，少跑幾趟

批次抓取：@BatchSize 與 hibernate.default_batch_fetch_size

JOIN FETCH 一次最好只抓一個集合，分頁也不一定能交給資料庫做。這時還有一招：延遲載入照舊，但補查時一次補好幾個。使用指南把這種抓法叫 BATCH：「用一句另外的 SQL，在 WHERE 裡用 IN 條件依批次大小載入好幾筆關聯資料」（Performs a separate SQL select to load a number of related data items using an IN-restriction as part of the SQL WHERE-clause based on a batch size.）。出處

有兩種開法。全站一起開：Spring Boot 的 spring.jpa.properties.* 會原樣交給 Hibernate（說明是「要設定在 JPA 實作上的額外原生屬性」，Additional native properties to set on the JPA provider）。出處

open-in-view 的坑

〈Hibernate 入門與環境〉提過 Open Session in View 與 spring.jpa.open-in-view。這裡把它實際跑一次。Spring Boot 對這個屬性的說明：「註冊 OpenEntityManagerInViewInterceptor，在處理請求的整段期間把 JPA EntityManager 綁在執行緒上」（Register OpenEntityManagerInViewInterceptor. Binds a JPA EntityManager to the thread for the entire processing of the request.），預設值 true。出處 那個攔截器的 API 文件寫它的用途是「讓網頁畫面在原本的交易已經結束之後，仍然可以延遲載入」（to allow for lazy loading in web views despite the original transactions already being completed）。出處

示範專案加了一個 REST 端點。服務層的方法有交易，查出部門就回傳；Controller 拿到部門後，才去讀員工集合組成回應：

@Service
class DepartmentService {
    @Transactional(readOnly = true)
    public Department find(Long id) {                 // 交易在這個方法結束時就提交了
        return repo.findById(id).orElseThrow();
    }
}

@RestController
class DepartmentController {
    @GetMapping("/departments/{id}")
    DepartmentView get(@PathVariable Long id) {
        Department d = service.find(id);
        List<String> names = d.getEmployees().stream().map(Employee::getName).toList();   // 在交易外碰延遲載入的集合
        return new DepartmentView(d.getName(), names);
    }
}

開著看起來比較方便，坑在三個地方：

  • 查詢時機散掉。SQL 不只出現在服務層，Controller、把物件轉成 JSON 的階段都可能觸發延遲載入。直接把實體回傳給 Jackson 轉 JSON 時，它會走遍每個 getter，一個列表就可能在序列化時跑出 N+1，而且服務層的程式看不出來。
  • 那些查詢不在你的交易裡。API 文件的說法就是「原本的交易已經結束之後」仍然可以延遲載入。服務層的 @Transactional 設定（唯讀、隔離層級、逾時）管不到它們。
  • 錯誤被藏起來。關掉之後的 LazyInitializationException 其實是好訊號：它指出「這個使用情境要的資料，服務層沒準備好」。

所以常見的做法是明確設 spring.jpa.open-in-view=false，讓服務層在交易裡把回應要的資料準備齊：用 JOIN FETCH、@EntityGraph，或直接查成下一段之後會講的 DTO。使用指南對 LazyInitializationException 的建議也是一樣：「最好的處理方式是在關閉持久化環境（persistence context，下一段會講）之前，把需要的關聯都抓好」（The best way to deal with LazyInitializationException is to fetch all the required associations prior to closing the Persistence Context.）。出處

查過的不再查，改過的晚點一起送

一級快取與 flush 時機

Hibernate 在一個 Session（JPA 叫 EntityManager）裡維護一個持久化環境（persistence context）：這段工作範圍裡它正在管的那一批實體物件，也叫一級快取（first-level cache）。使用指南說 Session「維護一個通常可重複讀取的持久化環境（一級快取）」（It maintains a generally "repeatable read" persistence context (first level cache) of the application domain model.）。出處 在 Spring 裡，注入的 EntityManager 是個代理，官方文件說它「把所有呼叫轉給目前那筆交易的 EntityManager；沒有交易時，每次操作改用一個新建的 EntityManager」（It delegates all calls to the current transactional EntityManager, if any. Otherwise, it falls back to a newly created EntityManager per operation）。出處 所以一級快取通常跟著一筆交易走（開著 open-in-view 時跟著整個請求），不是全站共用的快取。

改過的晚點一起送：flush

使用指南：flush 是「把持久化環境的狀態同步到資料庫的過程」；持久化環境像一個交易範圍內的延後寫入快取（transactional write-behind cache），「變更先套用在記憶體，在 flush 時才同步到資料庫」（changes are first applied in-memory and synchronized with the database during the flush time）。出處 預設的 AUTO 模式會在這三個時機 flush：出處

  • 交易提交之前（prior to committing a Transaction）
  • 執行一個跟排隊中的變更有重疊的 JPQL／HQL 查詢之前（prior to executing a JPQL/HQL query that overlaps with the queued entity actions）
  • 執行沒有登記同步對象的原生 SQL 查詢之前（before executing any native SQL query that has no registered synchronization）

交易裡先 em.flush()，之後丟出 RuntimeException 讓交易還原。flush 送出去的 UPDATE 呢？

  • 只有一半留下來
  • 跟著交易一起還原
  • flush 會自動提交交易

flush 只是把 SQL 送到資料庫，交易還沒結束；還原時同一筆交易裡的變更都會還原。flush 不等於 commit。

  • 不會，兩張表沒有重疊
  • 會，而且會先提交交易
  • 不會，因為 INSERT 不能 flush

  • 每個 Repository 各一份

一句一句送，不如一批一批送

批次寫入：hibernate.jdbc.batch_size 與 IDENTITY 主鍵

寫入也有來回次數的問題。JDBC 可以把同一句 SQL 的多組參數打包，一次交給資料庫（〈Spring 資料存取〉的 batchUpdate 就是）。Hibernate 也能這樣做，但預設沒開。使用指南：「JDBC 批次預設沒有開啟，所以每一句 INSERT 都要一次資料庫來回。要開啟 JDBC 批次，把 hibernate.jdbc.batch_size 設成 10 到 50 之間的整數」（JDBC batching is not enabled by default, so every insert statement requires a database round trip. To enable JDBC batching, set the hibernate.jdbc.batch_size property to an integer between 10 and 50.）。出處 這個設定「控制 Hibernate 最多把幾句打包在一起，才請驅動程式執行這一批」（Controls the maximum number of statements Hibernate will batch together before asking the driver to execute the batch.）。出處

示範專案有兩個只差主鍵策略的便條實體。SEQUENCE 用資料庫的序列（sequence，資料庫裡專門發號碼的物件）先拿號碼；IDENTITY 用自動遞增欄位，INSERT 時由資料庫給號碼：

@Entity

    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)   // 序列：先拿號碼，INSERT 可以晚點一起送
    private Long id;
    private String text;
}

@Entity
public class IdNote {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)   // 自動遞增：INSERT 完才知道號碼
    private Long id;
    private String text;

前面的解法都還是查出完整的實體。如果畫面只要「員工姓名」或「員工姓名＋部門名稱」，可以直接投影（〈Hibernate 查詢與關聯〉講過 HQL 的 select new）。Spring Data JPA 有兩種寫法。

介面投影：宣告一個只有 getter 的介面當回傳型別。參考文件：getter「對應到聚合根的屬性」時叫封閉投影（closed projection），而「用封閉投影時，Spring Data 可以把查詢最佳化，因為知道撐起投影代理需要哪些屬性」（If you use a closed projection, Spring Data can optimize the query execution, because we know about all the attributes that are needed to back the projection proxy.）。出處 聚合根（aggregate root）在這裡就是 Repository 管的那個實體，例如 Employee。

  • 把兩個集合都改成 EAGER
  • 分頁查部門，兩個集合用批次抓取
  • 打開 open-in-view 讓畫面自己查

有兩個集合，一句 JOIN FETCH 會產生笛卡兒積；改 EAGER 會影響所有查詢；open-in-view 只是把查詢搬到畫面層。分頁查部門再用批次抓取，每個集合大約 N ÷ 批次大小次補查。

重點整理

  • N+1：1 次查清單，再為 N 筆的延遲載入關聯各補查 1 次。用 DataSource 代理數 SQL，測試裡斷言句數。
  • @ManyToOne、@OneToOne 照 JPA 預設是 EAGER，JPQL 查詢沒 JOIN FETCH 時會另外補查，一樣造成 N+1；Hibernate 建議全部標 LAZY，需要時在查詢上指定一起抓。
  • JOIN FETCH 與 @EntityGraph 一句拿齊；從 Hibernate 6 起自動去掉重複的父實體，不必寫 distinct。搭配分頁時，Hibernate 7 會把分頁放進子查詢，資料庫不支援才退回記憶體（Hibernate 6 印 HHH90003004、一律在記憶體裡切）；不要同時抓兩個集合、不要在被抓的一邊加條件。
  • 批次抓取（@BatchSize、hibernate.default_batch_fetch_size）用 IN 一次補好幾筆，N 筆約補 N ÷ 批次大小次；適合分頁與多個集合，但多數時候 JOIN FETCH 或 DTO 更好。
  • spring.jpa.open-in-view 預設 true：EntityManager 活整個請求，延遲載入跑到交易外、Controller 與 JSON 序列化階段。設 false 之後的 LazyInitializationException 代表服務層沒把資料準備齊。
  • 一級快取：同一個 EntityManager 裡依主鍵查過的不再查，JPQL 查回來的也是同一個物件。AUTO flush 在提交前、查重疊的表前、原生 SQL 前；flush 不等於 commit。
  • 批次寫入預設沒開，設 spring.jpa.properties.hibernate.jdbc.batch_size；IDENTITY 主鍵 persist 當下就 INSERT，批次失效；MySQL 還要 rewriteBatchedStatements=true；大量匯入定期 flush、clear。
  • 唯讀畫面優先投影成 DTO 或介面投影：只查需要的欄位、不進一級快取、不被追蹤。
