Spring JDBC 幫你收掉重複的流程

還是寫 SQL，但不用處理樣板程式碼

原生 JDBC 要一直重複取得連線、建立敘述、綁參數、走訪結果、釋放資源。Spring JDBC 把 SQL 的控制權留給你，只替你處理這些固定流程。

DataSource 提供資料庫連線；JdbcTemplate 或 NamedParameterJdbcTemplate 用它執行 SQL。後者以名稱綁定參數，比一排問號好讀很多。

String sql = """
    update student
       set name = :name
     where id = :id
    """;

MapSqlParameterSource params = new MapSqlParameterSource()
    .addValue("name", student.name())
    .addValue("id", student.id());

int affected = jdbcTemplate.update(sql, params);

命名參數不是把字串接進 SQL，而是交給模板做參數綁定，所以不會有自己串接輸入值造成的注入風險與格式問題。

修改與查詢走不同流程

update、batchUpdate 與 query

方法用途常見結果
update執行 INSERT、UPDATE、DELETE受影響的資料筆數
batchUpdate批次執行多組修改參數各批次受影響的筆數
query查詢多筆資料由 RowMapper 轉出來的物件集合
queryForObject預期剛好一筆結果單一值或單一物件

主鍵由資料庫產生時，可以搭配 KeyHolder 取得新增後的鍵值。批次處理適合「同一段 SQL、每次參數不同」而且量很大的情境。

資料列需要一位翻譯

用 RowMapper 建立領域物件

public class StudentRowMapper implements RowMapper<Student> {
    @Override
    public Student mapRow(ResultSet rs, int rowNum) throws SQLException {
        return new Student(
            rs.getLong("id"),
            rs.getString("name"),
            rs.getInt("age")
        );
    }
}

ResultSet 是查詢結果；RowMapper 定義每一列怎麼變成 Java 物件。欄位名稱、SQL 型別與 Java 型別要合理對應，資料庫的 NULL 也要明確處理。

查詢本來就可能沒有結果時，不要把「查無資料」和真正的資料庫故障混為一談。資料存取層應該把底層狀況轉成上層看得懂的結果或例外。

從資料列走向物件關聯

ORM、JPA、Hibernate 與 Spring Data JPA

JPA持久化的規格，定義實體、關聯與 EntityManager 等 API；已改名 Jakarta Persistence。
Hibernate最常見的 JPA 實作，同時也提供自己的 Session API。
Spring Data JPA站在 JPA 之上的 Spring Data 模組，用 Repository 把常見的資料操作抽象化。

所以三者不是同一層的替代品，而是疊起來的：JPA 定規格，Hibernate 負責實作，Spring Data JPA 再幫你把 Repository 的重複程式碼省掉——原筆記那句「JPA 負責定義，Hibernate 負責實作」抓到了前兩層的關係。

用 Repository 表達資料操作

基本操作與方法名稱衍生查詢

public interface StudentRepository
        extends JpaRepository<Student, Long> {

    List<Student> findByNameContainingAndAgeGreaterThan(
        String keyword,
        int age
    );
}

常用操作有 save、findById、findAll 與 deleteById。findById 回傳 Optional<T>，提醒呼叫端資料可能不存在。

原筆記把刪除的方法名寫成 deleteByID(Id id)，正確的是 deleteById(ID id)，大小寫不同會找不到方法。

原筆記寫「save() 集 insert() + update()」，查證後這個方向是對的——save 兩種都做得到。要補的是它不是每次都跑兩段。官方文件說明 save 會先判斷這個實體有沒有被持久化過：還沒有就呼叫 persist，已經有就呼叫 merge。實際發出什麼 SQL 還會受實體狀態影響出處。

方法名稱衍生查詢適合簡單條件。名稱長到看不懂，或需求變複雜時，就該換一種比較清楚的查詢寫法。

複雜查詢要講清楚用哪種語言

@Query 預設不是原生 SQL

@Query("""
    select s
      from Student s
     where s.active = true
       and s.age >= :minAge
    """)
List<Student> findActiveAdults(@Param("minAge") int minAge);

@Query 預設使用 JPQL，查的是實體與它的屬性，不是資料表與欄位名。它的 javadoc 寫得很清楚：value 是「要執行的 JPA 查詢」，而 nativeQuery 用來「設定這個查詢是不是原生查詢，預設為 false」出處。這是很容易踩到的一個坑：把資料表名當成實體名寫進去，執行時就會直接失敗。

原生 SQL 能用到特定資料庫的功能，但換資料庫的成本比較高；JPQL 與衍生查詢則比較貼近實體模型。選哪一種要看查詢複雜度、效能、可讀性，以及你願意跟資料庫綁多緊。

同一個容器管理資料基礎設施

DataSource、EntityManagerFactory 與交易

走 JDBC 這條路時，Spring 管的是 DataSource 與 JDBC 模板；走 JPA 這條路時，管的是 EntityManagerFactory、Repository 與交易管理器。直接整合 Hibernate 時，也可以由 Spring 建立並注入 SessionFactory，這樣就不必再自己寫一個 HibernateUtil。

Web 容器提供的 JNDI DataSource 也可以交給 Spring 查找並註冊成 Bean，服務就不必自己到全域目錄找連線來源，改用注入取得。

原筆記在這裡寫「因為 Controller 是由 Web 容器管理（Tomcat），…這時候 Controller 就只能使用 DL 的方式（Dependency Lookup）取得 Service 物件」。放回它自己的脈絡看是對的：那一章講的是把 Spring 裝進傳統 JavaWeb 專案，控制器是 Tomcat 建立的 Servlet，容器不認得 Spring 的 Bean，只能自己去查找。要補的是它沒講到的另一種情況——改用 Spring MVC 之後，@Controller 是 @Component 的特化，會被掃描並註冊成 Spring 管理的 Bean，直接用建構式注入拿 Service 就好，不必再查找。

資料存取技術與交易管理必須配套。多步驟的寫入流程要由服務層建立清楚的交易邊界，而不是讓每個 Repository 各自送交。

原筆記用 web.xml 加 ContextLoaderListener 載入 Spring 組態，那是 Spring Boot 普及之前的做法。現在的專案多半靠自動組態與註解掃描，不會再寫這份部署描述檔。

工具沒有高下，只有合不合適

Spring JDBC 與 Spring Data JPA 怎麼選？

考量Spring JDBCSpring Data JPA
SQL 控制SQL 明白寫在程式裡，控制最直接透過實體操作、JPQL 或原生 SQL 間接控制
物件關聯要自己組裝可以宣告關聯與載入策略
簡單的增刪改查還是要寫 SQL 與對映Repository 能省掉大量樣板程式碼
複雜報表通常能直接精準寫出 SQL用 JPQL、原生查詢，或另外搭 JDBC
學習重點SQL、參數與 RowMapper實體狀態、關聯、交易與查詢策略

同一個系統也可以兩者並用：一般實體的增刪改查用 Spring Data JPA，複雜報表用 Spring JDBC。關鍵是交易與分層的邊界要清楚。

重點整理

  • Spring JDBC 保留 SQL 的控制力，並省掉連線與資源釋放的樣板程式碼。
  • update 處理資料異動，query 搭配 RowMapper 處理查詢對映。
  • JPA 是規格，Hibernate 是實作，Spring Data JPA 提供 Repository 抽象。
  • save 依實體是不是新的決定走 persist 還是 merge，不是固定的 insert 加 update。
  • @Query 預設是 JPQL；要原生 SQL 得寫 nativeQuery = true。
  • JDBC 與 JPA 可以並用，選擇依據是 SQL 控制、物件關聯、查詢複雜度與維護成本。
