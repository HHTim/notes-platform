置物櫃，鍵直接換成格子編號

雜湊表的想法：用算的找位置

想像車站的投幣置物櫃。如果你手上的收據寫著「17 號」，你會直接走到 17 號櫃子打開，不會從 1 號一路開過去。陣列也是這樣：知道索引，一步就拿到那一格。〈陣列與字串〉的置物櫃要你自己記得號碼；雜湊表多了一台「用名字算號碼」的機器（雜湊函式），你只要報名字。

麻煩在於，我們要找的東西通常不是用「17 號」這種小整數標示，而是帳號、身分證字號、商品編號這種字串。雜湊表（hash table）的想法是：準備一排格子（陣列），再準備一個雜湊函式（hash function，把任何一個鍵算成一個格子編號的公式）。要存就算出編號放進去，要找就用同一個公式算出編號直接去看。普林斯頓《Algorithms》把它拆成兩步：先用雜湊函式「把要找的鍵轉成陣列索引」（compute a hash function that transforms the search key into an array index），第二步是處理「兩個以上不同的鍵算到同一個索引」的情況，叫碰撞處理（collision-resolution process）。出處

在 Java 裡，第一步分成兩半：每個物件都有 hashCode()，回傳一個 32 位元的整數，叫雜湊碼；HashMap 再拿這個整數算出要放進哪一格。HashMap 的每一格叫桶（bucket，因為一格裡可能裝不只一筆）。算法寫在 OpenJDK 原始碼裡：

  • hash() 方法回傳 (h = key.hashCode()) ^ (h >>> 16)，也就是把雜湊碼的高 16 位元用 XOR（逐位元比較，兩邊不同得 1、相同得 0）混進低 16 位元；鍵是 null 時直接當 0。出處
  • 放進第幾個桶用 (n - 1) & hash 算（查找用的 getNode 裡就是 tab[(n - 1) & hash]），n 是桶的數量，而且一定要是 2 的次方。出處getNode

為什麼要 2 的次方、又為什麼要先把高位元混下來：

  • 2 的次方時 n - 1 寫成二進位剛好全是 1：8 個桶時 n - 1 是 7，也就是 111，跟雜湊值做 AND（逐位元比較，兩邊都是 1 才得 1）就是留下最後 3 個位元，等於「除以 8 的餘數」，一個位元運算就算完。
  • 代價是只看得到低位元，只差在高位元的雜湊碼一定會撞在一起，所以先用最便宜的 XOR 把高位元的影響帶下來。出處

下面這段程式用同樣的算法，算出幾個字串在 8 個桶裡會落在哪一格：

public class BucketIndex {
    // 跟 HashMap 內部的 hash() 同一招：把高 16 位元混進低 16 位元
    static int spread(int h) {
        return h ^ (h >>> 16);
    }

    public static void main(String[] args) {
        int n = 8;                                   // 桶的數量，HashMap 一律用 2 的次方
        for (String key : new String[]{"apple", "banana", "cherry", "Aa", "BB"}) {
            int h = key.hashCode();
            int index = (n - 1) & spread(h);         // n 是 2 的次方時，等於取餘數
            System.out.printf("%-6s hashCode=%-11d 桶=%d%n", key, h, index);
        }
    }
}

HashMap 的桶數為什麼永遠是 2 的次方？

  • n − 1 的二進位全是 1，AND 就等於取餘數
  • Java 規定所有陣列的長度都必須是 2 的次方才能配置
  • 桶數是 2 的次方時，不同的鍵就保證不會算到同一個桶
  • 2 的次方個桶比其他數量的桶更省記憶體空間

n 是 2 的次方時，n − 1 的二進位全是 1，AND 只留下低位元，剛好是除以 n 的餘數。碰撞照樣會發生，Java 陣列長度也沒有這種限制。

HashMap 的 hash() 為什麼要把雜湊碼的高 16 位元 XOR 到低 16 位元？

  • 讓雜湊碼一定變成正數，算桶編號時陣列索引才不會變負的
  • 讓同一個物件在每次重新執行程式時，都得到完全一樣的雜湊碼
  • 桶少時只用得到低位元，只差在高位元的雜湊碼會擠在一起
  • 讓之後呼叫 equals 比較兩個鍵時能跑得比較快一些

(n - 1) & hash 只取低位元，高位元不混下來就完全用不到。XOR 不會改變正負號（h >>> 16 的最高位元是 0），也跟 equals 無關。

雜湊表找一個鍵，為什麼比「從頭到尾一筆一筆比」快？

  • 直接算出該去哪個桶，只比那個桶裡的幾筆
  • 它事先把所有鍵排好序，再用二分搜尋去找
  • 它同時派好幾條執行緒去搜每一個桶
  • 它把鍵壓縮成比較短的字串，比較起來比較快

雜湊表的快來自「用算的找位置」：算桶編號是固定步驟，之後只比對同一個桶裡的鍵。它不排序、也不靠多執行緒。

兩把鑰匙指到同一格

碰撞：鏈結法與開放定址

鍵的種類幾乎是無限的，桶卻只有幾個、幾千個，所以一定會有兩個不同的鍵算到同一格，這叫碰撞（collision）。這是鴿籠原理（10 隻鴿子塞進 9 個籠子，至少有一個籠子擠兩隻）：桶數比鍵的可能種類少時，沒有任何雜湊函式能讓每個鍵各得一格，一定存在兩個鍵 a、b 使得 h(a) = h(b)。出處 上一段的 "Aa" 與 "BB" 就是現成的例子，兩個字串的 hashCode() 都是 2112。出處

碰撞了要把第二筆放哪？講義列了兩條路：「放到陣列裡別的位置」（store somewhere else in the array (open addressing)），或「放進另一個資料結構」（store in another data structure ... (chaining)）。出處

鏈結法：每個桶掛一條串列

鏈結法（separate chaining）就像同一個置物櫃格子裡掛一串鑰匙圈：普林斯頓的寫法是替每個索引「建一條鏈結串列，串起雜湊到這個索引的所有鍵值」（build, for each of the M array indices, a linked list of the key-value pairs whose keys hash to that index）；找的時候分兩步，「先雜湊找到可能含有這個鍵的串列，再沿著串列逐一找」（hash to find the list that could contain the key, then sequentially search through that list for the key）。出處 鏈結串列本身怎麼運作，見〈鏈結串列〉。

開放定址：被佔了就往下一格找

開放定址（open addressing）不掛串列，所有鍵都放在陣列本身。最簡單的一種叫線性探測（linear probing）：碰撞時「就檢查表裡的下一格（把索引加一）」（we just check the next entry in the table (by incrementing the index)）。找的時候一路往下看，會遇到三種結果：鍵相同（找到）、空格（確定不在）、別的鍵（繼續看下一格）。出處 因為每格只能放一筆，鍵的數量一定要少於格子數。

開放定址每格只放一筆，鍵一定比格子少；普林斯頓的原句是 it must be less than 1。鏈結法的 α 才可以大於 1（平均每條串列超過一筆）。

兩個不同的鍵雜湊碼完全一樣，HashMap 怎麼知道它們是不同的鍵？

  • 比較兩個物件在記憶體裡的位址大小
  • 比較兩個鍵各自放進來的先後時間
  • 沒辦法分辨，後放進來的鍵會蓋掉先放的那筆
  • 雜湊值相同時，再用 equals 比鍵

查找迴圈先比雜湊值，一樣才用 == 或 equals 比鍵本身；equals 回傳 false 就是不同的鍵，各自留在串列裡。

為什麼再好的雜湊函式也一定會碰撞？

  • 鍵的種類遠多於桶數，總有兩個會同一格
  • Java 的 hashCode 演算法寫得不夠好
  • 因為桶數規定是 2 的次方，剛好容易撞
  • 因為負載因子設成 0.75，表永遠不夠大

這是鴿籠原理：可能的鍵無限多，格子有限，不可能每個鍵各得一格。能做的只是讓鍵分散、讓碰撞少一點。

快滿了就換大一號的櫃子

負載因子與擴容

桶裡擠越多筆，找起來越慢。衡量「擠不擠」的數字叫負載因子（load factor）：鍵的數量 N 除以桶數 M，寫成 α = N/M。在鏈結法裡，α 就是平均每條串列有幾筆，查找與插入要比較的次數跟 N/M 成正比。出處 所以只要讓 α 維持在一個常數以下，每個桶平均就只有一兩筆。

HashMap 有兩個參數：初始容量（桶數）與負載因子。

  • 項目數超過「負載因子 × 目前容量」時，雜湊表會重新雜湊（rehash，也就是重建內部資料結構），桶數大約變成兩倍。
  • 預設負載因子 0.75，在時間與空間成本之間取得不錯的平衡；調高會省空間，但會增加查找成本。出處
  • 預設初始容量是 16（原始碼常數 DEFAULT_INITIAL_CAPACITY = 1 << 4）。出處

預設 HashMap：16 個桶 × 0.75 ＝ 門檻 12；放第 13 筆時「超過」門檻，桶數變 32

這個把桶陣列加大、重新分配的動作叫擴容。下面的程式用反射（reflection，在執行時讀出類別內部私有欄位的機制）讀 HashMap 內部桶陣列的長度，看它在第幾筆變大。因為要讀 java.util 裡的私有欄位，執行時要加 --add-opens 參數：

import java.lang.reflect.Field;
import java.util.HashMap;

// 執行：java --add-opens java.base/java.util=ALL-UNNAMED CapacityPeek
public class CapacityPeek {
    static int buckets(HashMap<?, ?> map) throws Exception {
        Field table = HashMap.class.getDeclaredField("table");   // 內部的桶陣列
        table.setAccessible(true);
        return ((Object[]) table.get(map)).length;
    }

    static void fill(String name, HashMap<Integer, Integer> map) throws Exception {
        int last = -1;
        for (int i = 1; i <= 100; i++) {
            map.put(i, i);
            if (buckets(map) != last) {
                last = buckets(map);
                System.out.println(name + " 放第 " + i + " 筆後：" + last + " 個桶");
            }
        }
    }

    public static void main(String[] args) throws Exception {
        fill("new HashMap<>()", new HashMap<>());
        fill("new HashMap<>(100)", new HashMap<>(100));
        fill("HashMap.newHashMap(100)", HashMap.newHashMap(100));
    }
}

擴容後每個鍵去哪

擴容要把每一筆重新放到新陣列裡，這一次是 O(n)。但因為每次都翻倍，貴的那一次很久才遇到一次；把它的成本平均分攤到前面每一次 put，每次只多付一點點，這叫攤銷（amortized：把偶爾一次很貴的成本平均分攤到每次操作）O(1)，跟 ArrayList 長大的道理一樣：ArrayList 為什麼會長大見〈陣列與字串〉，攤銷怎麼算見〈複雜度：程式跑多快、吃多少記憶體〉。MIT 講義的結論是：雜湊表在桶數跟著筆數調整時，能做到「期望的攤銷 O(1)」（expected amortized O(1) time）。出處

桶數是 2 的次方還有一個好處：擴容時不必重算雜湊碼。原始碼 resize() 的註解說，因為用 2 的次方擴大，「每個桶的元素要嘛留在同一個索引，要嘛移動 2 的次方的距離」（the elements from each bin must either stay at same index, or move with a power of two offset in the new table）。判斷方法是看 hash & oldCap：是 0 就留在原位，不是 0 就搬到「原位＋舊容量」。出處

public class Resize {
    static int spread(int h) {
        return h ^ (h >>> 16);
    }

    public static void main(String[] args) {
        int oldCap = 16, newCap = 32;
        for (String key : new String[]{"apple", "cherry", "kiwi", "lemon", "grape"}) {
            int h = spread(key.hashCode());
            int before = (oldCap - 1) & h;
            int after = (newCap - 1) & h;
            String move = (h & oldCap) == 0 ? "留在原位" : "原位＋16";
            System.out.printf("%-6s 16 桶時在 %2d，32 桶時在 %2d（%s）%n", key, before, after, move);
        }
    }
}

為什麼平均 O(1)、最壞會變差

「HashMap.get 是 O(1)」這句話有前提：

最壞情況與 Java 8 的補救

反過來，如果所有鍵的雜湊碼都一樣，全部擠進同一個桶，那個桶就是一條長串列，找一次要從頭比到尾，O(n)。這可能是意外（hashCode() 寫得太偷懶），也可能是惡意（攻擊者故意送一大堆雜湊碼相同的字串）。普林斯頓的習題就問過 hashCode() 永遠回傳 17 合不合法，答案是：合法，但所有鍵都會落在同一個位置，效能很差。出處

Java 8 起加了補救：桶裡的項目超過門檻時，把串列換成平衡樹，在高碰撞的情況下，最壞效能從 O(n) 改善到 O(log n)。出處 這棵樹是紅黑樹（一種會自己保持平衡的二元搜尋樹，〈樹與二元搜尋樹〉會講平衡為什麼重要）。這個動作叫樹化（把桶裡的串列換成紅黑樹，原始碼叫 treeify）。原始碼裡的三個門檻，跟〈Java 進階快答：JVM 記憶體、垃圾回收與類別載入〉講的一致：

常數值意思
TREEIFY_THRESHOLD8往一個已經至少有這麼多節點的桶再加一筆時，桶就轉成樹

還有一個容易漏掉的前提：樹要能排序。樹化只有在鍵的雜湊碼各不相同、或鍵可以比大小時，才提供最壞 O(log n)。出處 雜湊碼全部一樣、又沒實作 Comparable 的鍵，樹也幫不上忙。下面的程式數兩種鍵各要比較幾次，才確定一個不存在的鍵不在 5,000 筆的表裡：

import java.util.HashMap;
import java.util.Map;

public class WorstCase {
    static int compares = 0;                             // 數一數比了幾次

    // 雜湊碼全部一樣，但可以比大小
    record SameHashSortable(int id) implements Comparable<SameHashSortable> {
        @Override public int hashCode() { return 42; }
        @Override public boolean equals(Object o) {
            compares++;
            return o instanceof SameHashSortable k && k.id == id;
        }
        @Override public int compareTo(SameHashSortable other) {
            compares++;
            return Integer.compare(id, other.id);
        }
    }

    // 雜湊碼全部一樣，也不能比大小
    record SameHash(int id) {
        @Override public int hashCode() { return 42; }
        @Override public boolean equals(Object o) {
            compares++;
            return o instanceof SameHash k && k.id == id;
        }
    }

    public static void main(String[] args) {
        int n = 5_000;
        Map<SameHashSortable, Integer> a = new HashMap<>();
        Map<SameHash, Integer> b = new HashMap<>();
        for (int i = 0; i < n; i++) {
            a.put(new SameHashSortable(i), i);
            b.put(new SameHash(i), i);
        }
        compares = 0;
        a.get(new SameHashSortable(-1));
        System.out.println("同一桶、可比大小：比較 " + compares + " 次");
        compares = 0;
        b.get(new SameHash(-1));
        System.out.println("同一桶、不能比大小：比較 " + compares + " 次");
    }
}

契約，雜湊型集合的地基

equals 與 hashCode：自訂類別當鍵

前面看到，HashMap 先用雜湊碼決定桶、再用 equals 確認是不是同一個鍵。這兩步要配合得上，所以 Object 的文件訂了契約（〈套件與 Object 類別〉有完整說明，這裡從雜湊表的角度再看一次）：

  • 同一個物件在一次執行中多次呼叫 hashCode()，「只要 equals 比較用到的資訊沒被修改」，就要回傳同一個整數（provided no information used in equals comparisons on the object is modified）。
  • 依 equals 相等的兩個物件，hashCode() 一定要相同（If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result）。
  • 反過來不要求：equals 不相等的物件，雜湊碼可以一樣；只是給不同的值「可能提升雜湊表的效能」（may improve the performance of hash tables）。

出處 覆寫 equals 時，通常必須一起覆寫 hashCode。出處

陷阱一：只覆寫 equals

只覆寫 equals 的話，內容一樣的兩個物件用的還是 Object 預設的雜湊碼，通常各不相同，就會落到不同的桶，HashMap 根本不會走到 equals 那一步：

import java.util.HashSet;
import java.util.Objects;
import java.util.Set;

public class EqualsTrap {
    // 只覆寫 equals，忘了 hashCode
    static class Account {
        final String id;
        Account(String id) { this.id = id; }
        @Override public boolean equals(Object o) {
            return o instanceof Account a && a.id.equals(id);
        }
    }

    // 兩個都覆寫，用同樣的欄位
    static class FixedAccount {
        final String id;
        FixedAccount(String id) { this.id = id; }
        @Override public boolean equals(Object o) {
            return o instanceof FixedAccount a && a.id.equals(id);
        }
        @Override public int hashCode() {
            return Objects.hash(id);
        }
    }

    public static void main(String[] args) {
        Set<Account> set = new HashSet<>();
        set.add(new Account("A-001"));
        System.out.println(new Account("A-001").equals(new Account("A-001")));
        System.out.println(set.contains(new Account("A-001")));

        Set<FixedAccount> fixed = new HashSet<>();
        fixed.add(new FixedAccount("A-001"));
        System.out.println(fixed.contains(new FixedAccount("A-001")));
    }
}

用可變物件當鍵要非常小心：物件當鍵期間，如果它的值被改到會影響 equals 比較，Map 的行為就沒有定義。出處 實際跑一次：

import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public class MutableKey {
    static class Point {
        int x, y;
        Point(int x, int y) { this.x = x; this.y = y; }
        @Override public boolean equals(Object o) {
            return o instanceof Point p && p.x == x && p.y == y;
        }
        @Override public int hashCode() { return Objects.hash(x, y); }
    }

    public static void main(String[] args) {
        Map<Point, String> map = new HashMap<>();
        Point p = new Point(1, 2);
        map.put(p, "倉庫");
        p.x = 9;                                      // 當鍵之後才改欄位
        System.out.println(map.get(p));               // 用改過的物件查
        System.out.println(map.get(new Point(1, 2))); // 用原本的值查
        System.out.println(map.size());

  • a.equals(b) 一定是 false
  • a == b
  • 推不出來，要再用 equals 比

HashSet裡面其實是一個 HashMap，元素當鍵不保證平均 O(1)去重、判斷「有沒有」
LinkedHashMap雜湊表＋一條串起所有項目的雙向鏈結串列放入順序（也可以改成最近存取順序）平均 O(1)，略慢於 HashMap要保留順序、做 LRU 快取
TreeMap紅黑樹依鍵排序保證 O(log n)要排序、找「最接近的鍵」、範圍查詢

出處：HashSet、LinkedHashMap、TreeMap

LinkedHashMap 做 LRU 快取

LRU（least recently used，「最久沒用的先丟」）是快取常見的淘汰規則。LinkedHashMap 有一個特別的建構子，把順序改成「最近存取順序」，這種 Map 很適合拿來做 LRU 快取；再覆寫 removeEldestEntry，就能在放入新項目時自動移除最舊的。出處

import java.util.LinkedHashMap;
import java.util.Map;

public class Lru {
    static class LruCache<K, V> extends LinkedHashMap<K, V> {
        private final int capacity;
        LruCache(int capacity) {
            super(16, 0.75f, true);                      // true：照「最近存取」排序
            this.capacity = capacity;
        }
        @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
            return size() > capacity;                    // 超過容量就丟掉最久沒用的
        }
    }

    public static void main(String[] args) {
        LruCache<String, Integer> cache = new LruCache<>(3);
        cache.put("A", 1);
        cache.put("B", 2);
        cache.put("C", 3);
        cache.get("A");                                  // A 變成最近用過
        cache.put("D", 4);                               // 塞不下，丟掉最久沒用的 B
        System.out.println(cache.keySet());
    }
}
[C, A, D]

面試的 LRU 題（動手練清單裡的 146 題）常要求自己用雜湊表加雙向鏈結串列寫，其實就是 LinkedHashMap 內部的做法；雙向串列怎麼接，〈鏈結串列〉會畫。快取淘汰在系統層面的策略見〈系統設計：快取一致性與熱點〉。

TreeMap 找「最接近的鍵」

雜湊表只能回答「這個鍵在不在」，回答不了「比 x 小的最大鍵是誰」，因為它把鍵打散了。這種問題要用 TreeMap，例如依存款金額找利率級距：

import java.util.TreeMap;

public class TreeRange {
    public static void main(String[] args) {

        rate.put(0, "1.0%");

        rate.put(1_000_000, "1.5%");

        System.out.println(rate.ceilingKey(350_000));    // 大於等於 350,000 的最小門檻
        System.out.println(rate.firstKey() + " " + rate.lastKey());
    }
}

四招，把兩層迴圈拆成一層

面試常用手法：計數、查補數、分組、去重

很多題目的暴力解長這樣：對每一個元素，再把其他元素全部掃一遍，兩層迴圈 O(n²)。雜湊表的招式是：走過一次，把看過的東西記在雜湊表裡，之後每次「以前有沒有看過某個值」都是平均 O(1)，整題就變成 O(n)。代價是多用 O(n) 的記憶體，這是典型的「用空間換時間」。以下的「平均 O(1)」都帶著上一段的前提（鍵的雜湊碼夠分散）。

計數：getOrDefault 與 merge

數每個東西出現幾次，用這兩個方法：

  • getOrDefault：有這個鍵就回傳它的值，沒有就回傳給定的預設值。出處
  • merge：鍵還沒有值（或值是 null）就放入給定的值，否則用給定的函式算出新值取代舊值。出處
import java.util.Map;
import java.util.TreeMap;

public class Counting {
    public static void main(String[] args) {
        String text = "banana";

        Map<Character, Integer> a = new TreeMap<>();      // TreeMap 只是為了印出來照字母排
        for (char c : text.toCharArray()) {
            a.put(c, a.getOrDefault(c, 0) + 1);            // 寫法一：沒有就當 0
        }

        Map<Character, Integer> b = new TreeMap<>();
        for (char c : text.toCharArray()) {
            b.merge(c, 1, Integer::sum);                   // 寫法二：沒有就放 1，有就相加
        }

        System.out.println(a);
        System.out.println(b);
    }
}
{a=3, b=1, n=2}
{a=3, b=1, n=2}

這裡用 TreeMap 只為了讓輸出照字母排、每次都一樣；解題時用 HashMap，每次操作才是平均 O(1)。只有小寫英文字母時，也常直接用 int[26] 陣列計數，連雜湊都省了。

查補數：兩數之和

「陣列裡哪兩個數加起來等於目標值」：暴力法是每一對都試。雜湊表解法是邊走邊記「看過的數字 → 它的索引」，每走到一個數 x，就查「目標值 − x」（叫補數）以前有沒有出現過。

import java.util.Arrays;
import java.util.HashMap;
import java.util.Map;

public class TwoSum {
    // 暴力法：每一對都試，O(n²)
    static int[] bruteForce(int[] nums, int target) {
        for (int i = 0; i < nums.length; i++)
            for (int j = i + 1; j < nums.length; j++)
                if (nums[i] + nums[j] == target) return new int[]{i, j};
        return new int[0];
    }

    // 雜湊表：邊走邊記「看過的數字 → 索引」，O(n)
    static int[] withMap(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>();
        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];                   // 要湊成 target 還缺多少（補數）
            if (seen.containsKey(need)) return new int[]{seen.get(need), i};
            seen.put(nums[i], i);                          // 先查再放，才不會跟自己配對
        }
        return new int[0];
    }

    public static void main(String[] args) {
        int[] nums = {3, 8, 11, 5, 7};
        System.out.println(Arrays.toString(bruteForce(nums, 12)));
        System.out.println(Arrays.toString(withMap(nums, 12)));
    }
}

分組：computeIfAbsent

把東西依某個特徵分組，例如「字母相同、順序不同的字」（anagram，重組字）放同一組。Map 文件對 computeIfAbsent 舉的例子就是這種「一個鍵對多個值」的用法：map.computeIfAbsent(key, k -> new HashSet<V>()).add(v);，鍵還沒有值時才建立新的集合。出處

import java.util.ArrayList;
import java.util.Arrays;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class GroupAnagrams {
    public static void main(String[] args) {
        String[] words = {"eat", "tea", "tan", "ate", "nat", "bat"};
        Map<String, List<String>> groups = new LinkedHashMap<>();  // 用 LinkedHashMap 讓印出順序固定
        for (String w : words) {
            char[] cs = w.toCharArray();
            Arrays.sort(cs);
            String key = new String(cs);                           // 字母排序後當組名："eat" → "aet"
            groups.computeIfAbsent(key, k -> new ArrayList<>()).add(w);
        }
        System.out.println(groups);
    }
}

去重：HashSet.add 的回傳值

HashSet.add 在元素已經存在時不改變集合、回傳 false，所以「放放看」本身就是「以前有沒有看過」的判斷。出處

import java.util.HashSet;
import java.util.LinkedHashSet;
import java.util.Set;

public class Dedupe {
    public static void main(String[] args) {
        String[] txIds = {"T9", "T3", "T9", "T5", "T3"};

        Set<String> seen = new HashSet<>();
        for (String id : txIds) {
            if (!seen.add(id)) {                                   // add 回傳 false＝本來就有
                System.out.println("第一個重複的交易：" + id);
                break;
            }
        }

        Set<String> unique = new LinkedHashSet<>();                // 去重又保留第一次出現的順序
        for (String id : txIds) unique.add(id);
        System.out.println(unique);
    }
}

getOrDefault 只是「找不到就回傳 0」，不會把 "b" 放進 Map，所以 containsKey 還是 false。要放進去得自己 put。

用雜湊表解兩數之和，nums = {2, 7, 11, 15}、目標 9。走到 i = 1（值 7）時，seen 是 {2=0}。下一步該做什麼？

  • 先把 7 放進 seen，然後繼續往下看 i = 2 的 11 再說
  • 補數 2 已在 seen 裡，回傳 [0, 1]
  • 回頭把 i 之前的每一個元素都再掃一遍，找出加起來等於 9 的
  • 先把陣列排序，再用二分搜尋去找 2 在不在

每走到一個數就先查補數。2 已經在 seen 裡、索引是 0，答案就是 [0, 1]，不必再往下走。

兩數之和的雜湊表解法為什麼要「先查補數、再把自己放進去」？

  • 避免元素跟自己配對（目標 6、只有一個 3）
  • 這樣 HashMap 在整個過程中就不會觸發擴容
  • 讓回傳的兩個索引一定是由大到小排列好的
  • 避免兩個不同數字的雜湊碼在桶裡發生碰撞

先放再查的話，走到唯一的 3 時會先放入 3，再查補數 3 就查到自己，回傳同一個索引兩次。

雜湊表版的兩數之和，時間與額外空間各是多少（平均）？

  • 時間 O(n)，額外空間 O(1)
  • 時間 O(n log n)，額外空間 O(1)
  • 時間 O(n²)，額外空間 O(n)
  • 時間 O(n)，額外空間 O(n)

下面哪一題最適合用雜湊表把 O(n²) 降成 O(n)？

  • 找出一個沒排序的陣列裡第 k 小的數
  • 判斷陣列裡有沒有兩個數相加等於 k
  • 判斷一串括號是不是每一個都正確配對
  • 找出地圖上兩點之間的最短路徑

「有沒有兩數相加等於 k」就是查補數，邊走邊查一次平均 O(1)。第 k 小要靠排序或堆積，括號配對要靠堆疊，最短路徑要靠圖的搜尋。

要判斷兩個只含小寫字母的字串是不是重組字（字母與次數都一樣、順序不同），下面哪個做法正確？

  • 比較兩個字串的 hashCode 是否相同
  • 只要兩個字串長度相同就算是
  • 數每個字母各出現幾次，再比兩份計數
  • 兩個字串各自排序後，只比第一個字母

重組字的定義就是字母次數一樣，計數比較是 O(n)。hashCode 相同不代表相等（"Aa" 與 "BB"），而且重組字的 hashCode 通常不同；長度與第一個字母都不夠。

「找出最長的連續整數序列長度」（例如 100, 4, 200, 1, 3, 2 → 1、2、3、4 共 4 個）。已經把所有數放進 HashSet，下一步怎麼做才能維持 O(n)？

  • 先把陣列排序，再從頭掃一遍數連續段
  • 對集合裡的每一個數都往上數，看能連到多長
  • 只從「x − 1 不在集合裡」的 x 開始往上數
  • 把集合轉成 TreeSet，再用最大值減最小值

只從序列的起點開始數，每個數最多被數到一次，總共 O(n)。每個數都往上數會重複數同一段，最壞 O(n²)；排序是 O(n log n)；最大減最小不管中間有沒有斷掉。

  • 雜湊表用雜湊函式把鍵算成桶的編號；HashMap 先把 hashCode() 的高 16 位元 XOR 到低位元，再用 (n - 1) & hash 取桶，桶數一律是 2 的次方。
  • 碰撞一定會發生。開放定址（如線性探測）往下一格找；Java 的 HashMap 用鏈結法，同桶串成串列、新節點接尾端，先比雜湊值再用 equals 比鍵。
  • 預設 16 個桶、負載因子 0.75：超過 12 筆（第 13 筆）擴容成 32。擴容是 O(n)，但翻倍讓 put 攤銷 O(1)；每個鍵不是留在原位就是搬到「原位＋舊容量」。要放 N 筆不擴容，Java 19 起用 HashMap.newHashMap(N)。
  • 平均 O(1) 的前提是雜湊碼夠分散；全部撞同一桶最壞 O(n)。Java 8 起桶有 8 個節點再加一筆、且桶陣列至少 64 時樹化，鍵可比大小時最壞 O(log n)。
  • equals 相等，hashCode 一定要相同；只覆寫 equals 會讓 HashSet 找不到。鍵要用不可變的物件（String、Integer、record），鍵放進去後改欄位，資料會卡在舊桶。
  • 只要快查用 HashMap／HashSet；要保留放入順序或做 LRU 用 LinkedHashMap；要排序、找最接近的鍵用 TreeMap（保證 O(log n)）。
  • 面試四招：計數（merge、getOrDefault）、查補數（先查再放）、分組（computeIfAbsent）、去重（add 回傳 false），把內層迴圈換成一次查表，O(n²) 變 O(n)，代價是 O(n) 額外空間。
