  • 說出容器裡的檔案什麼時候還在、什麼時候沒了
  • 依資料的用途在具名 Volume、Bind Mount、tmpfs 之間選對一個
  • 用 Compose 把一長串 docker run 換成一份可以進版控的檔案

先搞清楚資料住在哪

容器可以砍掉重來，資料不行

映像檔的每一層都是唯讀的範本。容器跑起來之後新增、修改、刪除的檔案，全部落在它自己那一層可寫空間（正式名稱：容器層，container layer）。這一層的命運很單純：

容器只是停掉
  • 資料還在。容器本身沒被刪，那一層就還在。
  • start 回來，之前寫的檔案原封不動。
容器被刪掉
  • 那一層跟著消失，資料沒了。
  • 而且這一層綁在單一容器上，別的容器接不過去。

所以資料庫的檔案、使用者上傳的東西、要留著查的紀錄，都不該只放在容器層。把容器想成可以隨時換的旅館房間：日用品放房裡沒差，重要行李要放進另外保管的置物櫃（正式名稱：持久化儲存）。

三種掛法

看資料要活多久，決定用哪一種

方式資料放哪、活多久典型用途
具名 VolumeDocker 自己管；容器刪了它還在資料庫檔案、要跨容器接手的資料
Bind Mount直接對到你主機上的某個路徑開發中的程式碼、要在主機上編輯的設定檔
tmpfs放在記憶體；容器停了就沒不需要留下來的暫存資料
 
# 具名 Volume
docker container run -v app-data:/app/data myapp:1.0

# Bind Mount
docker container run -v /主機上的絕對路徑:/app/config myapp:1.0

# tmpfs
docker container run --tmpfs /app/cache myapp:1.0

原筆記說具名 Volume 是保存資料最好的方式——查證後和官方說法一致：Docker 文件寫的是「Volumes are the preferred mechanism for persisting data」（Volume 是保存資料的首選機制）。出處

具名 Volume

讓新容器接回同一份資料

docker volume create app-data
docker volume ls
docker volume inspect app-data     # 看 Mountpoint 在哪

docker container run --name app-a -v app-data:/app/data myapp:1.0
docker container rm -f app-a
docker container run --name app-b -v app-data:/app/data myapp:1.0   # 資料還在

只要沒把 app-data 刪掉，第二個容器掛上去就接回同一份資料。這就是「容器可以換、資料自己活」的做法。

一個容易中的坑：Dockerfile 裡寫了 VOLUME ["/app"]，但 docker run 的時候沒指定名字，Docker 每開一次容器就幫你生一個隨機名字的 Volume（正式名稱：匿名 Volume；官方文件寫「Anonymous volumes are given a random name」）。出處 原筆記就是這樣累積出一堆看不出用途的 Volume。解法是每次都用 -v 名字:路徑 明確命名。

docker volume inspect 印出來的 Mountpoint（通常長得像 /var/lib/docker/volumes/app-data/_data）是那層 Linux 裡面的路徑。在 Windows 和 macOS 上你用檔案總管或 Finder 找不到它，因為它在 Docker 那層 Linux 裡面（原筆記也是這樣觀察的）。那一層是誰開的、長什麼樣，第 17 課會拆開，那裡有出處。

Volume 有自己的生命週期，但它不是備份。誤刪、磁碟壞掉、資料本身損毀，Volume 一樣救不了你。重要資料另外規畫備份和還原。

Bind Mount

把主機的資料夾直接借給容器

原筆記有個很好的例子：本機沒裝 C 語言的編譯環境，但又想編一支 hello.c。做法是把目前目錄掛進一個裝好 gcc 的容器裡：

docker container run -it -v "$PWD":/root gcc:14 sh
# 在容器裡：gcc -o hello hello.c
# exit 之後，編好的 hello 就出現在你自己的資料夾裡

這一招的重點是雙向：主機改檔案，容器馬上看到；容器在掛載目錄裡產出的檔案，主機也看得到。開發流程很吃這個——程式碼留在主機上，編譯器和執行環境由容器提供。

原筆記踩過一個狀況：用 -d 跑 gcc 容器，容器立刻退出了。原因是第 14 課那條規則——容器的命綁在主程式上，gcc 映像檔的預設指令跑完就結束了。要停在裡面操作就得用 -it。

Bind Mount 的代價是綁死主機：路徑要存在、權限要對，而且 Windows 和 macOS、Linux 的路徑寫法不一樣。只是要保存應用程式資料的話，具名 Volume 比較好搬。另外，掛載會蓋住容器裡那個路徑原本的內容——拿空資料夾掛到本來有檔案的目錄，看起來像檔案不見了，其實只是被蓋住。

Compose

一長串參數，改成一份看得懂的檔案

一個應用程式常常不只一個容器：網站一個、資料庫一個、快取一個，每個都有自己的環境變數、埠號和掛載設定。全部用 docker run 打，遲早漏參數。Compose 讓你把這些寫進一份 YAML：

services:
  web:
    image: myapp:1.0
    ports:
      - "8080:8080"
    environment:
      DB_HOST: db
    depends_on:
      - db

  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
    volumes:
      - db-data:/var/lib/mysql

volumes:
  db-data:

services 底下的 web 和 db 是服務名稱。同一個 Compose 專案裡的服務可以直接用服務名稱找到對方，所以應用程式的資料庫主機就填 db。最下面的 volumes 宣告一個叫 db-data 的具名 Volume，再由資料庫服務掛上去。

密碼那行用 ${MYSQL_ROOT_PASSWORD} 代進來，不要把真的密碼寫死在 Compose 檔裡，含密碼的檔案也不要進版控。

Compose 操作

起、看、收

docker compose config    # 先把設定解析出來看一遍
docker compose up -d     # 背景把整組起起來
docker compose ps        # 看狀態
docker compose logs -f   # 跟著看紀錄
docker compose down      # 收掉這個專案的容器和網路

原筆記打的是 docker-compose up（中間有連字號）。兩種都會看到，但它們是兩代東西：Compose v1 用 Python 寫、指令是 docker-compose；v2 用 Go 重寫、變成 docker 的子指令 docker compose。出處 現在跟著文件學，看到的都是後者。

docker compose down 會收掉容器和網路，但預設不會刪具名 Volume——官方文件把「刪 Volume」放在 --volumes（-v）這個旗標底下。出處 所以重新 up 通常接得回原本的資料；反過來說，手滑加了 -v，資料就可能救不回來。

depends_on 保證不了「資料庫已經可以接查詢了」。官方文件寫得很直白：「啟動時 Compose 不會等到容器『就緒』，只等到它『在跑』。」出處 要真的等，得搭配健康檢查（healthcheck）加上 condition: service_healthy；就算這樣，應用程式自己也該會重試。

跨機器

本機那一套，多台機器就不夠用了

具名 Volume 和 Bind Mount 都在同一台主機上。一旦有第二台機器也要讀同一份資料，就得換成別的 Volume 驅動程式（volume driver，決定 Volume 實際存在哪裡的外掛），例如透過 SSH 掛遠端檔案系統，或用雲端的儲存服務。

換上去之後要重新評估的東西不少：一致性、效能、權限、備份。原筆記走到這裡就停了，因為這個問題再往下就換一個層次——那就是 Kubernetes 的 PVC（一張「我要一塊儲存空間」的申請單）在處理的事，第 19 課會碰到。

需求選哪個為什麼
資料庫檔案要跨容器保存具名 Volume生命週期不綁單一容器
本機改程式碼、容器負責跑Bind Mount主機和容器共用同一個目錄
只在執行期間用的暫存tmpfs停掉就丟，也不用寫進硬碟
多個服務要一起起來Compose把服務關係和參數集中成一份檔案
多台主機共用同一份資料本機 Volume 不夠要換 volume driver 或外部儲存服務

重點整理

  • 容器停掉，那層可寫空間還在；容器刪掉，它才跟著消失。
  • 具名 Volume 放要留的資料、Bind Mount 借主機目錄給容器、tmpfs 放丟得掉的暫存。
  • Dockerfile 寫了 VOLUME 但 run 的時候沒取名字，會一直生出匿名 Volume。
  • Volume 和容器的生命週期分開，但 Volume 不是備份。
  • docker compose down 預設不刪具名 Volume；加 -v 才刪。
  • depends_on 只等到「在跑」，不等到「可以用」——要就緒保證得配健康檢查，應用程式也該會重試。
