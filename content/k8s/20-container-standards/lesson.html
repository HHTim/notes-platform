容器是一種技術，Docker 只是其中一個實作品

原筆記在第一章開頭把這句話連寫了三次，還加一行「容器 != Docker」也寫三次。會這麼激動，是因為這兩個詞被當同義詞用太久了。

前面六課你一直在用 Docker，這一課把周圍的名字補齊——不是為了背術語，是因為不知道這些名字，就看不懂「K8s 拿掉 Docker 之後你的映像檔為什麼照跑」這種事。

Docker 是「容器化技術最成功、使用最廣泛的一個實作品」

補上名字

第 3 課那兩個開關，其實有名字

第 3 課說過：「Linux 本來就內建兩個機制，一個讓每個容器只看得到屬於自己的東西，一個限制它最多能吃多少 CPU 和記憶體。容器就是把這兩個開關打開而已。」這裡給它們正式名字：

Namespace（命名空間）管「看得到什麼」。每個容器有自己的一套視野——看不到別的容器的程序、檔案、網路介面。負責的是隔離。
Cgroup（控制群組）管「能用多少」。一組程序最多吃多少 CPU、多少記憶體，優先權多高。負責的是資源管理與限制。

第 18 課你寫的 requests 和 limits，最後落到節點上就是變成 cgroup 的設定；第 14 課用 docker container top 在主機上看得到容器裡的程序，也是因為它們本來就是同一台機器上的程序，只是被關進不同的 namespace。

原筆記說「Linux Container（LXC）是一種核心層級、作業系統層的虛擬化技術，主要由 Namespace 和 Cgroup 兩大機制實作」——查證後這個拆法是對的（「LXC combines the kernel's cgroups and support for isolated namespaces」），也和第 3 課「容器就是把兩個開關打開」的說法一致。出處

來歷

一條時間軸：容器是慢慢拼出來的

容器不是某天被發明出來的，是好幾樣 Linux 能力一塊一塊補齊之後，才有人把它們包成好用的東西。

限制看得到哪些檔案            chroot
        ↓
隔離程序、網路、掛載點等視野    namespace
        ↓
計量與限制 CPU、記憶體         cgroup
        ↓
包成好用的管理工具與映像檔分發   LXC、Docker……
時間發生什麼
1979chroot 出現在第七版 Unix，可以限制一支程式看得到哪一段檔案系統。1982 年加進 BSD。
2001、2005Linux-VServer、OpenVZ 先後出現，在 Linux 上做出接近容器的隔離。
2006Google 內部做出 Process Containers，後來改名 Control Groups（cgroups）。
2008 年 1 月cgroups 併進 Linux 核心 2.6.24。同年 LXC 出現，把 namespace 和 cgroup 包成一整套容器管理工具。
2013Docker 出現，最初底層就是用 LXC，後來才換成自己的執行元件。
2015OCI 成立，把容器的格式和啟動方式寫成標準。

上面兩條有查證備註。第一，原筆記寫 chroot 是「1979 年 Unix V7 由 Bill Joy 引入」；Linux 基金會的文章只說「chroot 於 1979 年第七版 Unix 開發期間首次出現，1982 年加進 BSD」，沒有把 1979 那次歸給任何人。出處 查不到定論的人名，這裡就不寫。第二，原筆記寫「Process Containers（2006，Google）後來改名 cgroups，2008 年 1 月併入 Linux 2.6.24」——查證後日期與版本都正確。出處

原筆記另外寫 LXC 是「第一個完整的容器管理實作」。這句要加一個範圍才站得住：在 Linux 上它算是第一個把隔離、資源管理和生命週期工具湊齊的一套；但更早的 FreeBSD Jails、Solaris Zones 在別的作業系統上已經做過類似的事。出處

Docker 真正改變局面的地方，其實不在隔離本身——那些能力 2008 年就在核心裡了。它做的是分層映像檔、一個指令就能建、一個倉庫就能分發、一套所有人都看得懂的操作介面。把已經存在的底層能力，整理成做得出來、送得出去、跑得起來的東西。

標準

OCI：讓容器換得掉的那份文件

2015 年，容器圈把格式寫成了公開標準。OCI（Open Container Initiative，開放容器倡議）官方的說法是：2015 年 6 月 22 日由 Docker、CoreOS 等業界成員發起，掛在 Linux 基金會（Linux Foundation）底下。出處

規格規定什麼
Runtime Spec怎麼把一包解開的檔案真的啟動成一個容器——基本操作規範。
Image Spec映像檔長什麼樣：清單、分層、設定。
Distribution Spec怎麼把映像檔推上去、拉下來（registry 的那套 API）。2020 年 5 月到 1.0。

原筆記說「2015 年由 Google、Docker、Red Hat 等廠商聯合組成 OCI」——方向沒錯，這裡補兩點：OCI 自己的介紹把發起寫成「Docker、CoreOS 等」並且強調它是 Linux 基金會底下的專案；另外原筆記只列了 Runtime Spec 和 Image Spec 兩份，現在是三份，第三份 Distribution Spec 管的就是你第 15 課在做的 push 和 pull。出處

名字對照

那幾個名字各站在哪一層

把第 17 課那四棒和標準疊在一起看，整張圖就完整了：

層例子可不可以換掉
你打的指令docker、podman、nerdctl可以
引擎／總管Docker Engine（dockerd）可以，K8s 就換掉了
容器執行環境containerd、CRI-O可以
真的去啟動的那支runc（照 OCI Runtime Spec 做的）可以，只要照同一份規格
映像檔的格式OCI Image Spec這一層就是不能換的共識

為什麼要講這個？因為它直接回答第 6 課提過的那件事：Kubernetes 從 v1.24 起不再用完整的 Docker Engine，改用 containerd，但你用 Docker 建出來的映像檔照樣能跑。原因就在最後一列——上面幾層都可以換，映像檔的格式是共同遵守的規格。你手上那些 Dockerfile 和映像檔，不綁在 Docker 這個產品上。

所以第 13 課那句「同一個映像檔在 docker run／託管服務／K8s 都能跑」，底下撐著它的就是這份標準。

重點整理

  • 容器是技術，Docker 是最成功的實作品之一——兩個詞不是同義詞。
  • 第 3 課那兩個機制的名字：namespace 管「看得到什麼」，cgroup 管「能用多少」。
  • 容器是拼出來的：chroot（1979）→ namespace 與 cgroup（2006、2008 併入核心）→ LXC（2008）→ Docker（2013）。
  • Docker 的貢獻在分層映像檔、建置流程、倉庫分發和好用的介面，不在隔離本身。
  • OCI 從 2015 年起把容器寫成標準，現在有三份：Runtime、Image、Distribution。
  • 指令、引擎、執行環境都能換掉，映像檔格式是不換的那一層——這就是 K8s 拿掉 Docker 也不影響你的原因。
