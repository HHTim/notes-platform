實作篇・收尾

容器是一種技術，Docker 只是其中一個實作品

Docker 是「容器化技術最成功、使用最廣泛的一個實作品」
不是「容器」本身

補上名字

〈容器〉那兩個開關，其實有名字

〈容器〉說過：「Linux 本來就內建兩個機制，一個讓每個容器只看得到屬於自己的東西，一個限制它最多能吃多少 CPU 和記憶體。容器就是把這兩個開關打開而已。」這裡給它們正式名字：

Namespace（命名空間）管「看得到什麼」。每個容器有自己的一套視野——看不到別的容器的程序、檔案、網路介面。負責的是隔離。
Cgroup（控制群組）管「能用多少」。一組程序最多吃多少 CPU、多少記憶體，優先權多高。負責的是資源管理與限制。

〈K8s 上手：Minikube 與上雲〉你寫的 requests 和 limits，最後落到節點上就是變成 cgroup 的設定；〈Docker 上手〉用 docker container top 在主機上看得到容器裡的程序，也是因為它們本來就是同一台機器上的程序，只是被關進不同的 namespace。

Linux Container（LXC）是一種作業系統層的虛擬化技術，直接建在核心本來就有的那些隔離能力上。官方的自我介紹是「LXC is a userspace interface for the Linux kernel containment features.」，而它列出來自己用到的核心能力，清單裡的「Kernel namespaces」和「CGroups (control groups)」——和〈容器〉「容器就是把兩個開關打開」講的是同一件事。出處

來歷

一條時間軸：容器是慢慢拼出來的

容器不是某天被發明出來的，是好幾樣 Linux 能力一塊一塊補齊之後，才有人把它們包成好用的東西。

        ↓

        ↓
計量與限制 CPU、記憶體         cgroup
        ↓
包成好用的管理工具與映像檔分發   LXC、Docker……
時間發生什麼
1979chroot 出現在第七版 Unix，可以限制一支程式看得到哪一段檔案系統。1982 年加進 BSD。
2000 年代初Linux-VServer 出現，在 Linux 上做出接近容器的隔離。
2005SWsoft 把 Virtuozzo 的核心以 GPL 開源，成立 OpenVZ 專案。出處
2006Google 內部做出 Process Containers，後來改名 Control Groups（cgroups）。出處
2008 年 1 月cgroups 併進 Linux 核心 2.6.24。出處 同年 8 月 LXC 首度發佈，把 namespace 和 cgroup 包成一整套容器管理工具。出處
2013Docker 第一個公開版本 v0.1.0 發佈（2013 年 3 月）。出處 最初底層就是用 LXC，後來才換成自己的執行元件。
2015OCI 成立，把容器的格式和啟動方式寫成標準。

chroot 的起點，Linux 基金會的文章寫的是「Chroot was first introduced in 1979, during development of Seventh Edition Unix (also called Version 7), and was added to BSD in 1982.」——1979 年隨第七版 Unix 出現，1982 年加進 BSD。出處

LXC 常被說成「第一個完整的容器管理實作」，這個說法要綁在 Linux 上才成立：在 Linux 上它是第一個把隔離、資源管理和生命週期工具湊齊的一套；別的作業系統更早就有同類的東西——同一篇文章寫「In 2000, FreeBSD extended chroot to FreeBSD Jails. Then, in the early 2000s, Solaris introduced the concept of zones, which virtualized the operating system services.」出處

Docker 真正改變局面的地方，其實不在隔離本身——那些能力 2008 年就在核心裡了。它做的是分層映像檔、一個指令就能建、一個倉庫就能分發、一套所有人都看得懂的操作介面。把已經存在的底層能力，整理成做得出來、送得出去、跑得起來的東西。

標準

OCI：讓容器換得掉的那份文件

2015 年，容器圈把格式寫成了公開標準。OCI（Open Container Initiative，開放容器倡議）官方的說法是：2015 年 6 月 22 日由 Docker、CoreOS 等業界成員發起，掛在 Linux 基金會（Linux Foundation）底下。出處

規格規定什麼
Runtime Spec怎麼把一包解開的檔案真的啟動成一個容器——基本操作規範。
Image Spec映像檔長什麼樣：清單、分層、設定。
Distribution Spec怎麼把映像檔推上去、拉下來（registry 的那套 API）。2021 年 5 月發佈 v1.0.0。出處

規格要注意現在是三份不是兩份——除了 Runtime Spec 和 Image Spec，第三份 Distribution Spec 管的就是你〈映像檔與 Dockerfile〉在做的 push 和 pull。出處

名字對照

那幾個名字各站在哪一層

把〈Docker Desktop 與 Colima〉那四棒和標準疊在一起看，整張圖就完整了：

層例子可不可以換掉
你打的指令docker、podman、nerdctl可以
引擎／總管Docker Engine（dockerd）可以，K8s 預設就不經過它了
容器執行環境containerd、CRI-O可以
真的去啟動的那支runc（照 OCI Runtime Spec 做的）可以，只要照同一份規格
映像檔的格式OCI Image Spec這一層就是不能換的共識

為什麼要講這個？因為它直接回答〈Pod 與 Node〉提過的那件事：Kubernetes 從 v1.24 起，kubelet 不再內建接 Docker Engine 的那段轉接程式（dockershim），改成一律透過 CRI 這個共同介面接容器執行環境——containerd、CRI-O 都可以，不是只有 containerd；要繼續用 Docker Engine 也能裝 cri-dockerd 接上去。而你用 Docker 建出來的映像檔照樣能跑，官方的原話是「the images produced from docker build will work with all CRI implementations」。出處 原因就在最後一列——上面幾層都可以換，映像檔的格式是共同遵守的規格。你手上那些 Dockerfile 和映像檔，不綁在 Docker 這個產品上。

所以〈要不要用 K8s〉那句「同一個映像檔在 docker run／託管服務／K8s 都能跑」，底下撐著它的就是這份標準。

重點整理

  • 容器是技術，Docker 是最成功的實作品之一——兩個詞不是同義詞。
  • 〈容器〉那兩個機制的名字：namespace 管「看得到什麼」，cgroup 管「能用多少」。
  • 容器是拼出來的：chroot（1979）→ namespace 與 cgroup（cgroup 的前身 2006 年在 Google 做出來，2008 年併進核心）→ LXC（2008）→ Docker（2013）。
  • Docker 的貢獻在分層映像檔、建置流程、倉庫分發和好用的介面，不在隔離本身。
  • OCI 從 2015 年起把容器寫成標準，現在有三份：Runtime、Image、Distribution。
  • 指令、引擎、執行環境都能換掉，映像檔格式是不換的那一層——這就是 K8s 拿掉 Docker 也不影響你的原因。
