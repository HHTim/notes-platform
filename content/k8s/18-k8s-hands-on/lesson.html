讀完這課你會

動手之前

一份部署計畫要回答三件事

第 5 課講過 K8s 的核心迴圈：你交一張單子，它一直比對現況。這一課要把那張單子真的寫出來。要準備的東西可以拆成三個問題：

要部署什麼一個容器化的應用程式。也就是先有映像檔（第 15 課）。
要怎麼部署、給多少資源幾份、每份多少 CPU 和記憶體、怎麼換版本、對外怎麼進來。
要部署到哪裡本機的練習叢集，還是雲端的正式叢集。

第 5 課那個迴圈的英文術語，看文件時會一直遇到，這裡對一下：你寫的單子叫期望狀態（desired state），叢集目前的樣子叫現況（current state），「只講結果不講步驟」的寫法叫宣告式（declarative），控制器一直把現況往期望狀態拉的那個動作叫調和（reconciliation）。觀念第 5 課已經講完，這裡只是補名字。

本機練習場

Minikube：在自己電腦上開一個叢集

Minikube 官方對自己的定位就一句話：「minikube is local Kubernetes, focusing on making it easy to learn and develop for Kubernetes.」——本機版的 Kubernetes，目的是讓學習和開發容易一點。出處

minikube start
kubectl cluster-info
kubectl get nodes

minikube start 開出來的是單節點叢集——那一台同時是大腦（master）也是工人（worker）。這跟第 7 課講的正式架構不一樣：正式環境裡大腦那幾台是分開的、而且要奇數台（第 12 課）。Kubernetes 官方教材自己也特別點出這個差別。出處 所以 Minikube 練得起來，不等於正式環境也會這樣。

電腦上同時有好幾個叢集的話，先確認 kubectl 現在指著哪一個，免得把東西套到錯的環境去：

kubectl config current-context
kubectl config get-contexts

第一份單子

Deployment 管幾份，Service 給一個不變的名字

apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: demo-app          # ← 要對上下面 template 的 labels
  template:
    metadata:
      labels:
        app: demo-app        # ← 這裡
    spec:
      containers:
        - name: app
          image: example/demo-app:1.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
---
apiVersion: v1
kind: Service
metadata:
  name: demo-app
spec:
  selector:
    app: demo-app            # ← 也要對上同一組
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP

三個地方要對上同一組標籤（label）：Deployment 的 selector、Pod 範本的 labels、Service 的 selector。這三處像三本要互相核對的地址簿，任何一處拼錯，服務就找不到後端。

port 和 targetPort 也常搞混：port: 80 是這個 Service 對外掛牌的號碼（叢集內其他服務打 80），targetPort: 8080 是容器裡程式真正在聽的號碼。type: ClusterIP 是預設值，意思是只在叢集內部找得到它（第 9 課講的那個「永遠不變的名字」）。

kubectl apply -f app.yaml
kubectl get deployment,pods,service
kubectl rollout status deployment/demo-app
kubectl port-forward service/demo-app 8080:80    # 從你的電腦直接打進去試

單位

500m 和 256Mi 分別是多少

requests（保留量）和 limits（上限）的意思第 8 課講過，這裡只補數字怎麼讀。

寫法是多少怎麼記
1一顆 CPU官方定義：等於一個 vCPU／一個核心／一條超執行緒
500m半顆 CPUm 是千分之一，1000m ＝ 1 顆
100m十分之一顆比 1m 更細的寫法不准
128Mi128 × 1,048,576 位元組（約 134 MB）Mi 是 2 的 20 次方，不是一百萬
128M128,000,000 位元組沒有 i 的才是十進位的一百萬

memory: 16Mi 的 Mi 不要看成「兆」。Mi 是 mebibyte，1 Mi ＝ 1,048,576 位元組，所以 16 Mi 大約是 16.8 MB，不是兆的等級出處。CPU 那邊的單位是 millicore（毫核心）：1000m ＝ 1 個核心，所以 20m 是單一核心的 2%。出處

還有一個第 8 課沒提到的：requests 和 limits 填一樣時，這個 Pod 的服務品質等級（QoS class）是 Guaranteed——意思是節點資源不夠、要趕 Pod 走的時候，Guaranteed 是最後才被趕的那一批（先趕 BestEffort，再趕 Burstable）。注意這不是排班順序：決定「先排誰」的是另一套機制（PriorityClass，Pod 的排班優先權）。出處 填得不一樣（requests 小於 limits）則是可以超用、但要有餘力才超得到。

另外提醒一個第 8 課講過、這裡再確認一次的行為差別：CPU 超過上限是被節流（跑慢一點），記憶體超過上限則可能被直接殺掉。出處

自動長大縮小

HPA：流量大就多開幾份

水平 Pod 自動擴縮器（Horizontal Pod Autoscaler，簡稱 HPA）會依指標調整副本數。它不是魔法，有三個前提：指標拿得到、容器有設合理的 requests、應用程式本身多開幾份也沒問題。

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: demo-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: demo-app
  minReplicas: 3
  maxReplicas: 35
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 80

一個容易踩到的互動：Deployment 寫 replicas: 2、HPA 寫 minReplicas: 3，最後會變成 3 份。HPA 接手之後，Deployment 那個數字就不是最終答案了。

指標可以是幾種：Resource（CPU、記憶體這種現成的）、Pods（每個 Pod 的自訂指標，例如每秒封包數）、Object（某個物件上的指標，例如 Ingress 的每秒請求數）、External（叢集外面來的）。後面三種都要另外有一條指標管線把數字送進來，不是寫下去就會動。

同理，滾動更新（第 8 課）能不能真的不斷線，也有前提：副本要夠、就緒檢查（readiness probe）要設對、而且新舊版本要能同時存在一陣子。策略只是機制，容量和程式設計不對一樣會斷。

設定與密碼

ConfigMap 放一般設定，Secret 放敏感的

把設定從程式碼裡拉出來，換設定就不用重建映像檔。一般設定放 ConfigMap，密碼、金鑰、憑證放 Secret。兩個在 YAML 裡的用法幾乎一樣，第 19 課會實際接上去。

Secret 這個名字很容易讓人以為資料已經被保護好了。Kubernetes 官方文件的警語講得很重：Secret 預設是沒有加密存在 etcd 裡的，任何有 API 存取權、或摸得到 etcd 的人都讀得出來；甚至只要有權在某個命名空間建 Pod，就等於能讀那個命名空間的 Secret出處。base64 是編碼不是加密。要真的安全，官方要求你另外做：開啟靜態加密、用 RBAC（權限控管機制：規定誰可以對哪些東西做什麼）把權限縮到最小、或改用外部的金鑰管理服務。

從本機到雲端

YAML 帶得走，基礎設施帶不走

Kubernetes 把應用程式和特定主機解開了，但不會自動抹平各家雲端的差異。同一份 YAML 搬上去，下面這些還是要重新想過。

面向Minikube雲端叢集
用途學習、本機驗證測試、預備或正式的工作負載
節點通常就一台多台，還可以跨多個可用區
對外入口多半用 port-forward 或本機外掛接雲端的負載平衡器和網域名稱
持久儲存本機的儲存供應器雲端磁碟、檔案或物件儲存服務
誰負責顧你自己的電腦雲端商和你的團隊分攤（第 13 課那張表）

搬之前先把環境差異抽出來：一般設定放 ConfigMap、敏感設定走 Secret 加外部金鑰管理、儲存用 PVC（一張「我要一塊儲存空間」的申請單）申請（第 19 課）、對外入口依平台選 Ingress 或負載平衡服務（第 10 課）。

「為什麼建議上雲」講的也是同一件事的反面：自己在機房做，主機互連、負載平衡、擴縮、權限控管、買硬碟，每一樣都得自己來。

壞掉的時候

先看狀態，再看事件，最後才看紀錄

kubectl get pods
kubectl describe pod POD名稱
kubectl logs POD名稱
kubectl get events --sort-by=.metadata.creationTimestamp
kubectl rollout status deployment/demo-app

Pod 起不來，先分清楚是哪一種：排不進去（沒有節點裝得下）、映像檔拉不到（名字打錯或沒權限）、程式自己崩潰、還是健康檢查沒過。這四種的處理方向完全不一樣，describe 最下面那段事件通常直接告訴你是哪一種。

Service 連不到，先核對標籤有沒有對上、targetPort 對不對、Pod 是不是真的 Ready——不要一上來就砍掉重建整個叢集。

看「這個 Service 到底有沒有後端」時，舊教材常寫 kubectl get endpoints。Kubernetes 從 v1.33 起把 Endpoints 這個 API 標為過時，改用 EndpointSlice，讀寫舊的會收到警告。出處 現在請改打 kubectl get endpointslices——EndpointSlice 就是「這個 Service 目前實際指到哪幾個 Pod」的那份清單。

重點整理

  • 部署計畫回答三件事：部署什麼、怎麼部署給多少資源、部署到哪裡。
  • Minikube 開的是單節點叢集（大腦和工人同一台），適合練，不代表正式架構。
  • Deployment 的 selector、Pod 範本的 labels、Service 的 selector，三處標籤要一致。
  • 1000m ＝ 一顆 CPU；Mi 是 1,048,576 位元組，不是一兆。requests 等於 limits 時 QoS 是 Guaranteed——節點資源不夠要趕人時最後才輪到它，這跟排班順序是兩回事。
  • HPA 的 minReplicas 會蓋過 Deployment 的 replicas；自訂指標要另外有管線送數字。
  • Secret 預設沒有加密，只是 base64；要安全得另外開靜態加密、用 RBAC（權限控管機制）把權限縮到最小，或改用外部金鑰服務。
  • YAML 搬得走，但網路、儲存、權限、成本上雲之後都要重看一遍。
