操作三・讓外面進得來

對外入口：router？Controller？Ingress？

Service 的名字預設只在叢集裡面有效，外面的人叫不到。所以前面要擺一個對外入口。而這裡有三個常被混在一起講的東西，拆開就清楚了：

負載平衡器雲端給你的一個對外 IP，把流量丟進叢集。這是基礎設施，GCP／AWS 提供。
Ingress一張規則表，跟 Service 一樣只是存在檔案室的一筆設定。它本身不轉發任何東西。
Ingress Controller真正在跑、真正在轉發的那個程式，跑在一個 Pod 裡。Ingress 這張表要有一個 Controller 在叢集裡跑，才會生效。

三個最容易混在一起的問題

  • 「Controller 是哪一個程式？」——沒有唯一答案，要自己挑一個裝。Kubernetes 本身不附執行者，官方文件列了一整排可選的 Ingress Controller，各家雲端商、各家廠商都有自己的版本。出處
  • 「是 router 嗎？」——概念上是，但 router 在網路領域專指看 IP 的那種路由器。這裡的東西看得懂網址路徑（/api 跟 /login 可以送去不同地方），業界比較常說反向代理——意思是它代替後面那些服務出面接客，外面的人只看得到它。
  • 「為什麼不直接讓 Service 對外？」——可以，Service 有一種型別會跟雲端要一個對外 IP。但一個 Service 一個 IP，十個服務就十個 IP，又貴又難管。對外入口的價值就是：一個 IP，依網址分給很多 Service。

挑 Controller 之前，先知道 Ingress 這個 API 的現況

「單子＋執行者」這個結構不會變，但單子這一格的規格已經封版了。Kubernetes 官方在 Ingress 說明頁最上面掛了一段話：「The Kubernetes project recommends using Gateway instead of Ingress. The Ingress API has been frozen.」——官方建議改用 Gateway API，Ingress 這個 API 已經凍結。同一頁也把「凍結」講清楚：Ingress 不會被移除、既有的照常能用，但不再新增或修改任何功能。出處

執行者那一格也有一件必須知道的事：歷史上用得最廣的那一個社群 Ingress Controller「Ingress NGINX」已經退役了。Kubernetes 的網路小組（SIG Network）與資安應變委員會在公告裡寫：「Best-effort maintenance will continue until March 2026. Afterward, there will be no further releases, no bugfixes, and no updates to resolve any security vulnerabilities that may be discovered.」——2026 年 3 月之後不再發版、不再修臭蟲、發現資安漏洞也不會補；已經裝好的不會壞掉，但從此沒有人維護。出處

官方後續那篇說明講得更直白：「choosing to remain with Ingress NGINX after its retirement leaves you and your users vulnerable to attack. None of the available alternatives are direct drop-in replacements.」——留著不換等於把自己和使用者暴露在攻擊下，而且沒有任何一個替代品是直接換上去就好的，要排時間做。出處

名字很像、要分清楚的兩個東西：退役的是 Kubernetes 社群維護的 Ingress NGINX。另外還有一個 F5 NGINX Ingress Controller，是 F5（NGINX 這個網頁伺服器的東家）自己的產品、另一個專案，仍在維護——它的產品頁把自己定位成「a stable and enterprise-backed alternative to community-maintained NGINX ingress controllers」。出處

觀念不變：Ingress 是單子，要有一個 Controller 去執行
變的是：官方建議新專案寫 Gateway API，而且社群的 Ingress NGINX 已退役、不再修補漏洞，繼續用等於把自己暴露在攻擊下

換成雲端託管的服務，那個執行者就不見了

「常常看到架構圖上只有一個負載平衡器，中間沒有多一個轉發用的 Pod，那是怎麼回事？」

因為那種架構沒有用 K8s。上面那個 Controller Pod 存在的理由，是「K8s 的 Ingress 只是一張規則表，K8s 自己不提供執行者」——所以你得自己養一個。

雲端託管的負載平衡器本身就是執行者。它的設定裡有一份路徑對照表，雲端商託管的轉發層負責照它執行。單子和執行者被包在同一個產品裡了。

自己架 K8s託管的負載平衡器 + 託管容器服務
規則表（單子）Ingress負載平衡器的路徑對照表
執行者你自己挑、自己養的 Controller Pod雲端商託管，你看不到
找到後端Service負載平衡器的後端設定
送網頁、圖片這類固定檔案Controller，或另外一個 Pod負載平衡器直接從雲端硬碟讀檔送出
要顧幾個容器你的服務 + 1 個 Controller只有你的服務

上面那張圖有一處不精準：圖裡把負載平衡器畫成「只給一個對外 IP」、把「看得懂網址路徑」全歸給那個 Controller Pod。那只對「只認 IP 的那種」負載平衡器成立。

負載平衡器分兩種：只認得機器位址、看不懂網址的（業界說第四層），和看得懂網址的（第七層，也叫應用層）。雲端的第七層負載平衡器自己就會依路徑分流——這種情況下根本不需要再擺一個轉發用的 Pod。

這也是為什麼 GKE 上有兩條路：裝一套自己挑的 Ingress Controller（起一個 Pod），或用 GKE 自己那一套（不起 Pod，直接叫雲端開一個第七層負載平衡器）。

把那個 Controller Pod 拿掉的實際好處

這種架構裡的 Controller Pod 傳統上做兩件事：依路徑分流，和送靜態檔案——「靜態檔案」就是做好之後不會再變的那些檔：網頁、樣式、圖片。這兩件事分別交給負載平衡器的路徑規則、和「負載平衡器直接讀雲端硬碟」之後，它就沒事可做了。

好處很實際：少一個容器要顧、少一份映像檔要建、少一個東西會掛、少一份資安掃描要跑。以 Ingress NGINX 退役這件事為例，少一個自己養的元件，就少一次「上游不維護了，得整套換掉」的遷移。

什麼情況需要自己留一個

  • 要做負載平衡器做不到的事——改寫請求內容、複雜的網址改寫規則、或是在最前面那一關就先把常看的內容存起來、下次直接回。
  • 不想被綁在單一雲——設定寫在自己的 Controller 裡，換雲時搬得動。
  • 前端不只是那些固定檔案——需要在伺服器端先算好畫面再送出，那就得有一個真的在跑的前端程式。

三個都不成立的話，就不需要。

串起來

一個請求實際走哪條路

路徑分兩種，看你的前端是哪一款。判斷方式：「打 API 的那一行程式，是在誰的機器上執行的」。

重點整理

  • Service 的名字只在叢集內有效；對外要靠入口依網址分流。
  • Ingress 是規則表（不會跑）；要有一個 Ingress Controller 在叢集裡跑，那張表才會生效——Kubernetes 不附執行者，要自己挑一個裝。
  • Ingress 這個 API 已凍結（不再新增或修改任何功能），官方建議新專案改用 Gateway API；社群的 Ingress NGINX 已於 2026 年 3 月退役，之後連資安漏洞都不會補。F5 NGINX Ingress Controller 是另一個仍在維護的專案。
  • 負載平衡器分兩種：只認位址的（L4）和看得懂網址的（L7）；雲端 L7 負載平衡器自己就是執行者，所以託管環境常常不必自己養一個 Controller Pod。
  • 判斷請求路徑：看「打 API 的那行程式在誰的機器上執行」。
