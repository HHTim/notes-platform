  • 說出 OpenShift 和 Kubernetes 的關係，以及 Route 補了什麼

先看全景

OpenShift 是 Kubernetes 加上一層平台

Red Hat OpenShift Container Platform（常縮寫成 OCP）核心就是 Kubernetes，上面再補開發、路由、安全和維運的整合。所以第 6〜12 課學的物件幾乎全部通用，指令從 kubectl 換成 oc（oc 也吃大部分 kubectl 的用法）。

最明顯的多出來的東西是 Route：OpenShift 自己的對外 HTTP／HTTPS 入口。第 10 課講的 Ingress 在 OpenShift 上一樣能用，但實務上 OpenShift 的教材和範例多半直接用 Route。

這一課用一個具體的例子把東西串起來：一個部落格網站（WordPress）＋一個資料庫（MySQL）＋一個快取（Redis）。

Deployment、Service、ConfigMap、Secret 的基本觀念見第 8〜10 課與第 18 課；這一課只講怎麼接起來、以及 OpenShift 特有的地方。

先畫相依，再套用

建立順序，跟「能不能用」是兩件事

原筆記整理的順序很實用，照著做少踩坑：

  • 先確認你在哪個專案（OpenShift 的 project 就是 Kubernetes 的命名空間）、配額還剩多少、有哪些儲存類別可用。
  • 建 ConfigMap、Secret、PVC——後面的東西會引用它們。
  • 建工作負載：快取 → 資料庫 → 網站。
  • 等 Pod 通過就緒檢查。
  • 建 Service，再建 Route。
  • 由內往外測：Pod → Service → Route。
oc project            # 現在在哪個專案
oc get resourcequota  # 這個專案還剩多少額度
oc get storageclass   # 有哪些儲存類別可以用

但要講清楚一件事：套用 YAML 的先後順序，不等於應用程式的啟動順序。Kubernetes 是非同步調和的（第 5 課那個迴圈），你先建資料庫不代表網站起來時資料庫已經能接查詢。真正的保證來自就緒檢查（readiness probe）和應用程式自己的重試——這和第 16 課 Compose 的 depends_on 是同一個道理。

設定與密碼

引用的時候，名字和鍵值都要一模一樣

apiVersion: v1
kind: ConfigMap
metadata:
  name: blog-config
data:
  DB_NAME: blog
  DB_USER: blog_user
  CACHE_HOST: cache
---
apiVersion: v1
kind: Secret
metadata:
  name: blog-secret
type: Opaque
stringData:
  DB_PASSWORD: 換成你自己的強密碼
  ADMIN_PASSWORD: 換成你自己的強密碼

工作負載用 configMapKeyRef 或 secretKeyRef 把單一欄位取出來當環境變數。引用時的 name（哪個 ConfigMap／Secret）和 key（裡面哪一個欄位）要和上面完全一致，錯一個字 Pod 就起不來。

Secret 預設沒有加密這件事第 18 課講過，在 OpenShift 上一樣成立。密碼請用佔位字串進版控、實際值另外注入；原筆記直接把 rootpass、wppass 這種明碼寫在檔案裡示範，那是教學方便，不是可以照抄的做法。

還有一個原筆記的寫法會讓人踩空：它用 cat << 'EOF' | oc apply -f - 送 YAML，裡面寫 namespace: $PROJECT_NAME 想代入專案名稱。但 here-document 的結束字（這裡是 EOF）只要加了引號，裡面的內容就不會做變數展開，那一行會原封不動送出去。出處 比較單純的做法是 YAML 裡乾脆不寫 namespace，先用 oc project 切到對的專案再套用。

儲存

PVC 是「我要一塊空間」的申請單

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: database-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi

這又是第 11 課那個模式：PVC 是單子，平台負責去生出真的儲存空間來滿足它。資料庫和網站內容各開一張，快取要不要開則看情況——它只是重建得回來的快取，還是裡面有不能掉的資料？不要因為「這是有狀態的服務」就一律給它一張。

PVC 一直卡在 Pending，優先查四件事：儲存類別（StorageClass）存不存在、存取模式（accessModes）平台支不支援、容量夠不夠、專案配額還有沒有。原筆記踩到的就是第一種——範例寫了某個雲端專屬的儲存類別，但那個環境沒有。

YAML 裡省略 storageClassName 時，會不會自動用預設的儲存類別，取決於叢集有沒有設預設值。省略之前先用 oc get storageclass 看一眼。

工作負載

把資料庫的位置注入網站

apiVersion: apps/v1
kind: Deployment
metadata:
  name: blog
spec:
  replicas: 1
  selector:
    matchLabels:
      app: blog
  template:
    metadata:
      labels:
        app: blog
    spec:
      containers:
        - name: blog
          image: 你的registry/wordpress:釘死的版本
          ports:
            - name: http
              containerPort: 8080
          env:
            - name: WORDPRESS_DATABASE_HOST
              value: database          # ← 就是 Service 的名字
            - name: WORDPRESS_DATABASE_NAME
              valueFrom:
                configMapKeyRef:
                  name: blog-config
                  key: DB_NAME
            - name: WORDPRESS_DATABASE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: blog-secret
                  key: DB_PASSWORD
          readinessProbe:
            httpGet:
              path: /
              port: http
            initialDelaySeconds: 15
            periodSeconds: 5
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi

注意 WORDPRESS_DATABASE_HOST 填的是 database——那是資料庫 Service 的名字，不是任何一個 Pod 的位址。這正是第 9 課講的「永遠不變的名字」實際用起來的樣子。

就緒檢查（readinessProbe）和存活檢查（livenessProbe）的分工不要搞混：就緒檢查決定要不要把流量送進來，存活檢查決定要不要把它砍掉重開。路徑、等待時間、逾時都要照那個映像檔真正的啟動行為調，抄別人的數字常常不合用。

映像檔的兩個坑

原筆記用的 bitnami/wordpress、bitnami/mysql、bitnami/redis 這一組，Bitnami 已經公告從 2025 年 8 月 28 日起把舊映像搬到 docker.io/bitnamilegacy，那邊不再更新也不再支援，只給你暫時遷移用出處。照抄原筆記的映像檔名稱，現在可能拉不下來。要沿用的話請先確認目前還提供哪些映像與標籤。

第二個坑是身分：OpenShift 會用一個隨機指定的、非 root 的使用者編號來跑你的容器。Red Hat 的映像製作指南寫得很清楚——容器裡會被寫入的目錄和檔案，要屬於 root 群組且該群組可讀寫，映像檔的 USER 也該寫數字而不是名字。出處 這也順便解釋了一個常見疑問：為什麼這類映像檔聽的是 8080 而不是 80——1024 以下的埠號一般要 root 才綁得起來。假設自己一定是 root、或假設某個目錄一定寫得進去的映像檔，在 OpenShift 上就會起不來。

還有一點原筆記自己在別篇也強調過、查證後確實是對的：正式環境不要用 latest。標籤是可以被發佈者改掉的，同一個名字下次拉到的可能是不同內容，稽核和重現都會出問題。出處

內部連線

Service 的名字就是叢集內的地址

apiVersion: v1
kind: Service
metadata:
  name: blog
spec:
  selector:
    app: blog
  ports:
    - name: http
      port: 80
      targetPort: http
---
apiVersion: v1
kind: Service
metadata:
  name: database
spec:
  selector:
    app: database
  ports:
    - name: mysql
      port: 3306
      targetPort: 3306

網站連 database:3306，實際上是靠叢集內的名稱解析找到資料庫的 Pod。targetPort 除了寫數字，也可以寫容器那個埠的名字（上面 Deployment 裡的 name: http），改埠號時比較不會漏改。

oc get pods
oc get services
oc get endpointslices     # 這個 Service 到底有沒有後端
oc describe service blog

Service 沒有後端時，一樣先比對 selector 和 Pod 的 labels，再確認 Pod 真的 Ready——沒 Ready 的 Pod 不會被算進去。順帶一提，原筆記用的是 oc get endpoints；Kubernetes 從 v1.33 起把 Endpoints 標為過時，改用 EndpointSlice。出處

對外發布

Route：加密要在哪一段結束

apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: blog
spec:
  to:
    kind: Service
    name: blog
  port:
    targetPort: http
  tls:
    termination: edge

Route 的後端是 Service（不是 Pod）——又是第 11 課那個模式：Route 是單子，真正在轉發的是 OpenShift 的路由器。termination 這個欄位在決定「加密在哪一段結束」，只有三個值：

寫法加密到哪裡什麼時候用
edge在路由器就解密，之後是明文送到 Pod一般情況；憑證放在路由器那一層
reencrypt路由器解密後，再開一條新的加密連線到 Pod叢集內部也要求加密
passthrough完全不解密，直接原封不動送給 Pod要由應用程式自己處理憑證

Red Hat 的文件把這三種和各自的憑證需求寫得很清楚；termination 沒填時預設是 edge。出處 組織要求「一路加密到 Pod」時，edge 就不夠。

oc apply -f manifests/
oc rollout status deployment/database
oc rollout status deployment/blog
oc get route blog

壞掉的時候

由內往外縮小範圍，不要同時改十個檔案

看到的症狀先查通常是
Pod 卡在 Pendingdescribe pod、PVC、配額排不進去，或儲存還沒綁上
ImagePullBackOff映像檔名稱、標籤、拉取憑證名字打錯、標籤不存在、沒權限
CrashLoopBackOff這次和上一次的紀錄設定漏了、權限不足、程式自己崩潰
Service 沒有後端selector、labels、就緒檢查標籤沒對上，或 Pod 還沒 Ready
Route 回錯誤Route、Service、後端、目標埠這條鏈其中一層不通
 
oc describe pod POD名稱
oc logs POD名稱
oc logs POD名稱 --previous       # 上一次崩潰前留下的紀錄
oc get events --sort-by=.metadata.creationTimestamp
oc port-forward service/blog 8080:80

先用 port-forward 確認內部通不通
內部通、外面不通 → 問題就只剩 Route 那一段

這個順序的價值在於每一步都把範圍砍一半。反過來同時調 Route、改 Service、重建 PVC，就算會了也不知道是哪一個修好的。

重點整理

  • OpenShift 核心就是 Kubernetes，物件幾乎通用；多出來最常用的是 Route 這個對外入口。
  • 套用順序幫助操作，但就緒保證來自 readiness probe 和應用程式的重試，不是 YAML 的先後。
  • configMapKeyRef／secretKeyRef 的 name 和 key 要完全一致，錯一個字 Pod 起不來。
  • OpenShift 用隨機的非 root 使用者編號跑容器——假設自己是 root 的映像檔會掛；這也是這類映像檔聽 8080 不聽 80 的原因。
  • 原筆記那組 Bitnami 映像已搬到 legacy 倉庫不再更新，照抄可能拉不下來；正式環境本來就不該用 latest。
  • Route 的 termination 只有 edge、reencrypt、passthrough 三種，決定加密在哪一段結束。
  • 排錯由內往外：Pod → Service（先 port-forward 試）→ Route。
