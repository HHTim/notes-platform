  • 用 DestinationRule 與 VirtualService 做 90/10 的金絲雀，知道權重跟 Pod 數無關、每輪結果為什麼不剛好是 10

先看網格長什麼樣

Service Mesh 解決什麼，以及 sidecar 長什麼樣

〈Service：找路〉解決了「找得到」。找到之後，服務之間的連線還有一堆事：要不要加密、怎麼確認對方是誰、等多久算逾時、失敗要不要重試、新版本先給幾成流量。這些事可以每個服務用函式庫自己做（〈韌性模式：Resilience4j 的斷路器、重試與限流〉就是這條路），也可以交給平台。服務網格（Service Mesh）是後者，Istio 的定義：「一層基礎設施，讓應用程式不必改程式碼就得到 zero-trust 安全、可觀測性與進階的流量管理」（A service mesh is an infrastructure layer that gives applications capabilities like zero-trust security, observability, and advanced traffic management, without code changes.）。出處 zero-trust 的意思是不因為在內網就信任，每條連線都要驗身分。

面試怎麼答見〈微服務與架構面試題：服務發現、韌性、可觀測性與十二要素〉；這課把它裝起來看。兩個名詞先記住：真正轉送流量的代理程式叫資料平面，Istio 用的代理是 Envoy；負責把設定與憑證發給這些代理的叫控制平面，在 Istio 是一個叫 istiod 的程式。

實驗環境：用 kind（在 Docker 裡開 Kubernetes 節點的工具，〈部署策略與探針〉也用它）建一個單節點叢集，再用 istioctl install --set profile=demo 裝 Istio 1.31.1。demo 設定檔官方說是「用不多的資源展示 Istio 功能」，而且開了大量追蹤與存取日誌，「不適合做效能測試」（not suitable for performance tests）。出處 開兩個命名空間：bank 貼上注入標籤，legacy 不貼，當對照組。兩邊各放一個只裝 curl 的 client；bank 另外放 Istio 官方範例 helloworld 的 v1、v2 各一份（呼叫 /hello 會回自己的版本）。出處

同一份 Deployment，bank 那邊是 2/2、legacy 是 1/1：多出來的就是 sidecar（邊車，掛在主程式旁邊、跟它同生共死的輔助容器），也就是 istio-proxy 這個 Envoy。sidecar 不是自己寫進 YAML 的，是 Pod 建立時被 Istio 改寫規格加進去的，這叫注入。所以標籤要在 Pod 建立之前貼好；已經在跑的 Pod 要重啟才會被注入（Istio 的比較表：Label a namespace and restart all pods to have sidecars added）。出處

有個細節：spec.containers 只有 curl，istio-proxy 放在 initContainers，而且 restartPolicy=Always。這是 Kubernetes 的原生 sidecar：在 initContainers 裡設 restartPolicy 的容器會一直跑，不像一般初始化容器跑完就結束；這功能 1.28 加入、1.33 起穩定。出處 Istio 的部落格說這樣設定是「告訴 Kubernetes 把它當 sidecar」（This tells Kubernetes to treat it as a sidecar.），好處是其他容器要等代理就緒才啟動，主程式結束後 Pod 也能結束。出處 另一個 istio-init 是一般的初始化容器，「設定 Pod 的網路流量轉向，進出都先經過 sidecar 代理」。出處 所以程式照常連 helloworld:5000，封包會先被轉到自己旁邊的 Envoy。

代價也寫在官方文件裡：sidecar 模式「經過充分實戰，但有資源成本與維運負擔」（well understood and thoroughly battle-tested, but comes with a resource cost and operational overhead）。出處 每個 Pod 多一個代理要吃 CPU 與記憶體，每一跳多經過兩個代理。

bank 命名空間貼了 istio-injection: enabled，裡面一個單容器的 Pod 跑起來後 READY 顯示什麼？

  • 1/1，sidecar 不算在 READY 裡
  • 2/2，多了 istio-proxy
  • 1/2，sidecar 要等第一個請求才啟動
  • 2/2，多了 istiod

實跑 bank 的 client 是 2/2、legacy 是 1/1。多的是 Envoy 代理 istio-proxy；istiod 是控制平面，跑在 istio-system 裡，不在你的 Pod 裡。

先部署了服務，之後才替命名空間貼上注入標籤。現有的 Pod 會怎樣？

  • 馬上被加上 sidecar，不必重啟
  • 被 Istio 刪掉重建
  • 變成 READY 0/1
  • 不變，要重啟才會被注入

注入發生在 Pod 建立時改寫規格。官方比較表寫 sidecar 模式加入網格要 restart all pods；不必重啟的是 ambient 模式。

實跑的 Pod 裡，istio-proxy 出現在哪個欄位？

  • spec.initContainers，restartPolicy 是 Always
  • spec.containers，跟 curl 並列，一起算在 READY 裡
  • spec.initContainers，跟 istio-init 一樣跑完就結束
  • 不在 Pod 規格裡，由節點上的 kubelet 另外啟動

這是 Kubernetes 的原生 sidecar：放在 initContainers 但設 restartPolicy: Always，會一直跑。restartPolicy 空白的 istio-init 才是跑完就結束的那種。

程式碼裡連的還是 http://helloworld:5000，流量怎麼會經過 Envoy？

  • Istio 改了 DNS，讓 helloworld 指到 Envoy 的位址
  • 程式要改用 Istio 的用戶端函式庫才會經過 Envoy
  • istio-init 設好流量轉向，進出 Pod 都先經過 sidecar
  • Service 的 selector 被改成指向 Envoy

官方：istio-init 設定 Pod 網路流量進出 sidecar 代理的轉向。程式不必知道代理存在，這也是「不必改程式碼」的來源。

官方文件對 sidecar 模式的代價怎麼說？

  • 沒有代價，只是設定比較多
  • 只有控制平面要吃資源
  • 只在跨叢集時才有額外負擔
  • 有資源成本與維運負擔

原文 comes with a resource cost and operational overhead。每個 Pod 都多一個代理，每一跳多經過兩個代理。

服務之間誰是誰

mTLS：自動加密與工作負載身分

一般的 HTTPS 只有伺服器出示憑證（握手過程見〈TCP、UDP 與 TLS 握手〉）。mTLS（雙向 TLS）是兩端都出示憑證，伺服器也能確認呼叫它的是誰。Istio 的流程：「Istio 把用戶端送出的流量轉到用戶端旁邊的 Envoy，用戶端的 Envoy 跟伺服器端的 Envoy 進行 mTLS 握手」（Istio re-routes the outbound traffic from a client to the client’s local sidecar Envoy. The client side Envoy starts a mutual TLS handshake with the server side Envoy.）。程式自己還是送明文 HTTP，加密在兩個代理之間做；而且不用設定，兩個代理之間的流量 Istio 會「自動升級成 mTLS」（Istio automatically upgrades all traffic between two PEPs to mutual TLS，PEP 指的就是代理）。出處

伺服器那一側收不收明文，由 PeerAuthentication 決定，三種模式：出處

模式官方說明
PERMISSIVEmTLS 與明文都收（Workloads accept both mutual TLS and plain text traffic），最適合搬遷期間；沒設定時網格預設就是它
STRICT只收 mTLS（Workloads only accept mutual TLS traffic）
DISABLE關掉 mTLS；除非你有自己的安全方案，否則不該用

官方也說了順序：搬遷時用 PERMISSIVE，「工作負載都注入 sidecar 之後，應該切到 STRICT」（Once workloads are migrated with sidecar injection, you should switch the mode to STRICT.）。出處 實驗：兩個 client 都去打 helloworld，先在預設狀態打一次，再套用下面這份規則打一次。

apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: bank
spec:
  mtls:
    mode: STRICT          # bank 命名空間只接受 mTLS 連線
# 預設（PERMISSIVE）
$ （bank 裡有 sidecar 的 client）curl helloworld.bank:5000/hello
HTTP 200
curl 結束碼 0
$ （legacy 裡沒有 sidecar 的 client）curl helloworld.bank:5000/hello
HTTP 200
curl 結束碼 0

# 套用 PeerAuthentication STRICT 之後
$ （bank 裡有 sidecar 的 client）curl helloworld.bank:5000/hello
HTTP 200
curl 結束碼 0
$ （legacy 裡沒有 sidecar 的 client）curl helloworld.bank:5000/hello
HTTP 000
curl 結束碼 56

PERMISSIVE 時兩邊都通；切到 STRICT 後，有 sidecar 的照樣 200，沒有 sidecar 的拿到 HTTP 000（沒收到任何回應）與 curl 結束碼 56，手冊的意思是「接收網路資料失敗」（Failure in receiving network data）。出處 也就是連線建立了，但 helloworld 旁邊的代理不收明文，直接斷掉。參考文件說 STRICT 的用處就是「確保繞過網格的連線不可能成功」（STRICT mode is useful to ensure that connections that bypass the mesh are not possible.）。出處

加密之外，mTLS 帶來的是身分。把 helloworld 代理手上的憑證拿出來看：

$ istioctl proxy-config secret helloworld-v1-5bb8cc5b68-ptj54 -n bank
RESOURCE NAME     TYPE           STATUS     VALID CERT  NOT AFTER                NOT BEFORE
default           Cert Chain     ACTIVE     true  2026-10-03T20:53:43Z     2026-10-02T20:51:43Z
ROOTCA            CA             ACTIVE     true  2036-09-29T16:13:34Z     2026-10-02T16:13:34Z

$ （把 default 憑證取出來看）openssl x509 -noout -ext subjectAltName -dates
X509v3 Subject Alternative Name: critical
    URI:spiffe://cluster.local/ns/bank/sa/default
notBefore=Oct  2 20:51:43 2026 GMT
notAfter=Oct  3 20:53:43 2026 GMT

憑證裡的身分是 spiffe://cluster.local/ns/bank/sa/default。SPIFFE 是一套工作負載身分的標準，SPIFFE ID 是「唯一且明確識別一個工作負載的字串」，格式是 spiffe:// 信任網域 / 工作負載識別。出處 在 Kubernetes 上，Istio 用的身分是 service account（服務帳號，Pod 跑起來時代表的 K8s 帳號）出處，所以這串讀作「bank 命名空間的 default 服務帳號」。實驗沒有替 Pod 指定服務帳號，大家都是 default；授權規則（AuthorizationPolicy）就是拿這個身分寫「誰可以呼叫我」，例如官方範例的 principals: ["cluster.local/ns/default/sa/sleep"]出處，所以正式環境每個服務要有自己的服務帳號，否則分不出誰是誰。

憑證的有效期間從 10/2 20:51:43 到 10/3 20:53:43，24 小時又 2 分鐘。這對上 Istio 代理的設定 SECRET_TTL，預設 24h0m0s，「Istio 代理要求的憑證壽命」（The cert lifetime requested by istio agent）。出處 這麼短沒關係，因為換證是自動的：Istio 代理與 istiod「一起把金鑰與憑證的輪替自動化」（work together with istiod to automate key and certificate rotation at scale）。出處 根憑證（ROOTCA）實測有效十年。

兩個都有 sidecar 的服務，沒寫任何 PeerAuthentication，它們之間的流量是？

  • 明文，要設 STRICT 才會加密
  • 自動升級成 mTLS
  • 被拒絕，要先設 PERMISSIVE
  • 只有伺服器出示憑證的一般 TLS

官方：Istio automatically upgrades all traffic between two PEPs to mutual TLS。PERMISSIVE 只是伺服器那一側「也收明文」，兩邊都有代理時照樣走 mTLS。

STRICT 之後，沒有 sidecar 的 legacy client 打 helloworld 得到什麼？

  • HTTP 403
  • HTTP 503
  • HTTP 000、curl 結束碼 56
  • HTTP 200，但回應內容是空的，沒有版本號

沒有任何 HTTP 回應（000），curl 56 是 Failure in receiving network data：連上了但被對面代理斷線。這不是 HTTP 層的拒絕，所以沒有 403。

要把一個大家都在呼叫的服務遷進網格，但有幾個呼叫端短期內裝不了 sidecar。PeerAuthentication 先用哪個模式？

  • PERMISSIVE，等呼叫端都進網格再切 STRICT
  • STRICT，逼還沒進網格的呼叫端趕快裝
  • DISABLE，全部改回明文
  • 不必設，沒有 sidecar 的呼叫端會自動被注入

官方原文：PERMISSIVE 最適合搬遷期間，workloads are migrated with sidecar injection 之後再切 STRICT。直接 STRICT 會讓沒 sidecar 的呼叫端立刻斷線。

憑證裡的 spiffe://cluster.local/ns/bank/sa/default，sa/default 指的是？

URI:spiffe://cluster.local/ns/bank/sa/default
  • Pod 用的 Kubernetes 服務帳號
  • Pod 的名字，每次重建都會變
  • Deployment 的名字，default 代表預設那一份
  • 容器映像檔的標籤

Istio 在 Kubernetes 上用 service account 當身分。實驗沒指定，所以都是 default；正式環境每個服務給自己的服務帳號，授權規則才分得出誰呼叫誰。

bank 命名空間裡的服務全部用 default 服務帳號。想寫「只有轉帳服務可以呼叫帳務服務」的授權規則，會遇到什麼問題？

  • 授權規則只能用 IP 寫
  • 大家身分都一樣，分不出誰是轉帳服務
  • STRICT 模式下不能寫授權規則
  • 沒有問題，Istio 會依 Deployment 名稱區分

AuthorizationPolicy 的 principals 寫的是 cluster.local/ns/…/sa/… 這種身分。身分來自服務帳號，全部共用 default 就全部長一樣。

工作負載憑證只有約 24 小時，為什麼不會每天出事？

  • Istio 代理與 istiod 自動輪替
  • 過期後連線改走明文，不影響服務
  • 維運人員每天手動更新一次
  • 過期的憑證 Envoy 仍然照樣接受，不會斷線

pilot-agent 的 SECRET_TTL 預設 24h0m0s；官方說代理與 istiod automate key and certificate rotation。短壽命的好處是外洩了也很快失效。

換版本時只放一點流量

流量切分：用 VirtualService 權重做 90/10 金絲雀

〈部署策略與探針〉的原生金絲雀（canary，先讓一小部分流量試新版）比例只能靠 Pod 數湊：要一成就要九比一的份數。網格把比例寫在規則裡。需要兩份 YAML：DestinationRule 把一個服務的 Pod 依標籤分成幾組（subset），VirtualService 寫流量怎麼分給這些組，參考文件的說法是「權重決定每個版本收到的流量比例」（Weights associated with the service version determine the proportion of traffic it receives.）。出處

apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: helloworld
  namespace: bank
spec:
  host: helloworld
  subsets:                 # 依 Pod 的 version 標籤分成兩組
  - name: v1
    labels: {version: v1}
  - name: v2
    labels: {version: v2}
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: helloworld
  namespace: bank
spec:
  hosts: [helloworld]
  http:
  - route:
    - destination: {host: helloworld, subset: v1}
      weight: 90           # 九成流量給舊版
    - destination: {host: helloworld, subset: v2}
      weight: 10           # 一成給新版（金絲雀）

先在沒有任何規則時，從 bank 的 client 裡打 100 次，只留版本那一段來數：

$ for i in $(seq 1 100); do curl -s helloworld:5000/hello; done | sed 's/, instance.*//' | sort | uniq -c   # 沒有任何流量規則
  54 Hello version: v1
  46 Hello version: v2

v1、v2 各一份 Pod，大約各半。套用 split.yaml 後連打三輪：

$ kubectl apply -f split.yaml
$ for i in $(seq 1 100); do curl -s helloworld:5000/hello; done | sed 's/, instance.*//' | sort | uniq -c   # 第 1 輪
  96 Hello version: v1
   4 Hello version: v2
$ （同一個指令）   # 第 2 輪
  92 Hello version: v1
   8 Hello version: v2
$ （同一個指令）   # 第 3 輪
  89 Hello version: v1
  11 Hello version: v2

v2 三輪分別是 4、8、11 次，合計 300 次裡 23 次，約 7.7%。權重是長期的比例，不是排班表，不保證每 100 次剛好 10 次；要判斷新版好不好，要看夠多請求的錯誤率，不能只看幾十次。重點是兩邊都只有 1 份 Pod，比例照樣是 90/10。官方在流量切分任務裡講的就是這件事：這跟容器平台用份數調流量「非常不同」，兩個版本可以「各自擴縮，不影響兩者之間的流量分配」（you can allow the two versions of the reviews service to scale up and down independently, without affecting the traffic distribution between them）。出處

推進的做法是一步步改權重（10、30、50、100），每步看指標再決定。這些步驟 Istio 本身不會自動推，要人或工具來改；〈部署策略與探針〉提到的 Argo Rollouts 可以接 Istio，它的文件說流量切分是「調整 Istio VirtualService 裡定義的流量權重」（Traffic splitting is accomplished in Istio by adjusting traffic weights defined in an Istio VirtualService.），也就是替你一步步改上面那兩個 weight。出處

要把 Pod 依 version 標籤分成 v1、v2 兩組，寫在哪種資源裡？

  • VirtualService 的 hosts 欄位
  • Service 的 selector 寫兩組標籤
  • PeerAuthentication 的 selector
  • DestinationRule 的 subsets

DestinationRule 定義「有哪幾組」，VirtualService 定義「流量怎麼分給這幾組」。兩份都要有，VirtualService 才找得到 subset: v2。

套了 90/10 之後打三輪 100 次，v2 分別是 4、8、11 次。怎麼解讀？

  • 權重沒生效，應該每輪剛好 10 次
  • v2 的 Pod 有問題，請求被退回 v1
  • 要把 v2 擴成 9 份 Pod 才會準
  • 權重是長期比例，少量請求本來就會上下跳

沒規則時是 54/46，套用後 v2 掉到一成上下，規則有生效。權重不是排班表；判斷新版好壞要看夠多請求的錯誤率。

實驗裡 v1、v2 各 1 份 Pod，結果大約九比一。跟〈部署策略與探針〉的原生金絲雀比，差在哪？

  • 比例寫在規則裡，跟 Pod 數無關
  • 原生做法也能做到，只要改 Service 的權重欄位
  • 網格的比例比較準，每 100 次一定剛好 10 次
  • 沒有差別，都是看 Pod 數

原生 Service 沒有權重欄位，比例只能用份數湊。官方：兩個版本可以 scale up and down independently, without affecting the traffic distribution。

新版的 Pod 被 HPA（〈K8s 上手：Minikube 與上雲〉的自動擴縮）從 1 份擴到 5 份，VirtualService 還是 90/10。新版拿到的流量比例會？

  • 升到大約五成
  • 還是大約一成
  • 升到大約 36%（5 比 9）
  • 變成 0，要重新套用規則

權重決定的是送到 subset 的比例，subset 裡有幾份 Pod 只影響那一成在 Pod 之間怎麼分。這正是官方說的「各自擴縮不影響流量分配」。

從 10% 推到 30%、50%、100%，Istio 本身會自動做嗎？

  • 不會，要人或工具去改權重
  • 會，VirtualService 有自動推進的欄位
  • 會，看到錯誤率下降就自動推
  • 會，每 10 分鐘自動加一成

VirtualService 只寫「現在的比例」。看指標、決定推進或退回，要人來做，或交給接得上網格的漸進式部署工具。

逾時與重試該誰管

重試與逾時：放在網格還是程式裡

先看網格的預設值：「Istio 預設關掉 Envoy 的 HTTP 逾時」（The Envoy timeout for HTTP requests is disabled in Istio by default.）；重試則是「失敗時重試兩次再回傳錯誤」（retry twice before returning the error）。出處 參考文件寫了預設重試的觸發條件：connect-failure,refused-stream,unavailable,cancelled，都是連線層級的失敗。出處

實驗：在 bank 放一個 httpbin（測試用的 HTTP 服務，/delay/3 會等 3 秒才回應），用 VirtualService 替它設 1 秒逾時：

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: httpbin
  namespace: bank
spec:
  hosts: [httpbin]
  http:
  - timeout: 1s              # 網格替呼叫端設的逾時：1 秒沒回應就放棄
    route:
    - destination: {host: httpbin}
$ curl -s -o /dev/null -w "HTTP %{http_code}，花了 %{time_total} 秒\n" httpbin:8000/delay/3   # 沒有逾時規則
HTTP 200，花了 3.017974 秒
$ kubectl apply -f timeout.yaml   # VirtualService 設 timeout: 1s
$ （同一個 curl 指令）
HTTP 504，花了 1.005078 秒

沒規則時等滿 3 秒拿到 200；套用後 1 秒就拿到 504（閘道逾時），是呼叫端旁邊的 Envoy 不等了，程式一行都沒改。

這裡踩過一個坑：一開始想用 Istio 的故障注入（在同一份 VirtualService 加 fault.delay，讓代理故意延遲）來製造慢回應，結果等滿延遲還是 200，逾時沒有作用。參考文件寫了原因：「用戶端啟用故障注入時，逾時與重試不會啟用」（Note that timeouts or retries will not be enabled when faults are enabled on the client side.）。出處 所以實驗改用真的會慢的 httpbin。

網格能設，程式也能設（Resilience4j），兩層各設各的會怎樣？官方在「Working with your applications」一節直說：網格的失敗處理對程式是透明的，程式也設的話「兩者各自運作，可能互相衝突」（both work independently, and therefore might conflict）。它的例子：程式對某個 API 設 2 秒逾時，VirtualService 設 3 秒逾時加重試 1 次，「程式的逾時先到，Envoy 的逾時與重試都沒有作用」（the application’s timeout kicks in first, so your Envoy timeout and retry attempt has no effect）。同一節也說網格不能代替程式處理失敗：所有實體都掛了時 Envoy 回 503，「程式必須自己實作降級邏輯」（The application must implement any fallback logic needed to handle the HTTP 503 error code.）。出處

重試疊在一起還會相乘。網格的 attempts 是「重試」次數（Number of retries to be allowed for a given request）出處，預設 2 等於最多打 3 次；Resilience4j 的 maxAttempts 包含第一次，預設 3。下游連不上時，網格先在自己這層重試，最後回 503 給程式；如果程式把 503 也當成要重試的失敗，程式每試一次網格就打 3 次，最多 3 × 3 = 9 次打到一個已經有問題的下游。下面是整理：

適合放網格適合放程式
逾時全服務統一的上限，各種語言一致依業務決定等多久；要比外層短
重試連線層級的失敗（連不上、被拒）要看業務判斷能不能重試（寫入要冪等）
失敗之後只能回 503、504降級回呼、斷路器、給使用者的訊息

這張表是本課依上面官方說法整理的分工建議，不是 Istio 的規定。原則是同一種重試只放一層，逾時由內往外越來越長；斷路器與降級的寫法見〈韌性模式：Resilience4j 的斷路器、重試與限流〉。

VirtualService 什麼都沒設，Envoy 對 HTTP 請求的逾時預設是？

  • 15 秒
  • 1 秒
  • 關閉，沒有逾時
  • 跟 K8s Service 的設定一樣

官方：The Envoy timeout for HTTP requests is disabled in Istio by default。實跑沒規則時 /delay/3 等滿 3 秒拿到 200。

同一份 VirtualService 同時設了 fault.delay（延遲 3 秒）和 timeout: 1s，結果等滿 3 秒還是 200。為什麼？

  • fault.delay 只對 gRPC 有效
  • timeout 要 2 秒以上才生效
  • 規則還沒傳到代理
  • 啟用故障注入時，逾時與重試不會啟用

參考文件原文：timeouts or retries will not be enabled when faults are enabled on the client side。本課的實驗因此改用真的會慢的 httpbin。

程式對某個 API 設 2 秒逾時，VirtualService 設 3 秒逾時加重試 1 次。下游一直很慢時，實際是？

  • Envoy 先重試一次，總共等 6 秒
  • 程式 2 秒就放棄，Envoy 的逾時與重試都沒作用

這是官方自己舉的例子：the application’s timeout kicks in first, so your Envoy timeout and retry attempt has no effect。外層比內層短，內層的設定就白設了。

程式用 Resilience4j maxAttempts: 3，而且把 503 當成要重試的失敗；網格保留預設重試（2 次）。下游連不上時，最多會試著連幾次？

  • 5 次
  • 9 次
  • 6 次

  • istiod，它會自動換一個健康的叢集
  • 不必處理，網格會一直重試到成功

不想每個 Pod 都帶代理

Ambient 模式一眼

Istio 的另一種資料平面叫 ambient：「用每個節點一個的第四層代理，以及可選的、每個命名空間一個的第七層代理」（a per-node Layer 4 (L4) proxy, and optionally a per-namespace Layer 7 (L7) proxy）。出處 第四層只看 IP 與連接埠，第七層看得懂 HTTP 內容（分層見〈網路與 HTTP 面試題：三向交握、TLS、REST 對 gRPC〉）。每節點那個叫 ztunnel，負責加密與身分；第七層那個叫 waypoint，要用到 HTTP 層的功能才部署。它 2022 年推出，「自 Istio 1.22 起單叢集情境可用於生產」（As of Istio 1.22, it is production-ready for single cluster use cases）。出處 本課的實驗用的是 sidecar 模式，ambient 沒有實跑。

官方的比較表摘幾列：出處

sidecarambient
流量管理（權重、逾時、重試）全部功能全部功能，但要有 waypoint
加入網格貼標籤，重啟所有 Pod貼標籤，不必重啟

連容器都不想管

Lambda 的模型：一個請求一個環境

Serverless 是把「開幾台、什麼時候擴縮」也交給雲端。Lambda 是 AWS 的做法：「一個無伺服器的運算服務，不必準備或管理伺服器就能執行程式」（AWS Lambda is a serverless compute service. With Lambda, you can run code without provisioning or managing servers.）。你寫一個 handler（處理函式），接上觸發來源（API Gateway、S3、SQS 等），Lambda 負責執行。出處 Lambda 跟 ECS、EKS 怎麼選，〈後端與雲端面試題庫〉答過；這一節講它的執行模型，因為適不適合都是從模型推出來的。

最重要的一句：「每一個同時進行的請求，Lambda 都準備一個獨立的執行環境」（For each concurrent request, Lambda provisions a separate instance of your execution environment.）。出處 同時 100 個請求就是 100 個環境；帳戶的同時執行數預設上限 1,000，以區域計算，可以申請提高。出處

一個環境的一生分三段：Init（啟動擴充、啟動語言執行環境、跑 handler 以外的靜態程式碼，限 10 秒）、Invoke（跑 handler）、Shutdown。跑完一次後環境被凍結，下一個請求來了再解凍重用；重用時「宣告在 handler 外面的物件保持已初始化」，官方的例子正是資料庫連線：不必重新建立，沿用原本那條。出處 但同一頁也說，即使一直有請求，Lambda 每隔幾小時就會換掉環境，「不應該假設執行環境會永遠存在」（You should not assume that the execution environment will persist indefinitely.）。出處 單次執行的上限是「900 秒（15 分鐘）」。出處

把兩件事放在一起會推出一個常見的坑（本課的推論，不是文件原文）：每個環境各自留著自己的資料庫連線，流量一衝高，環境數跟著衝高，資料庫連線數也一起衝。用容器跑的服務有固定幾份、每份一個連線池，總數可以算；Lambda 的總數跟同時請求數綁在一起。

某個 Lambda 函式同時有 50 個請求在處理。有幾個執行環境在忙？

  • 1 個，請求排隊
  • 50 個
  • 依記憶體設定決定，通常 4 個
  • 1,000 個，一次開到上限

官方：For each concurrent request, Lambda provisions a separate instance of your execution environment。一個環境同一時間只處理一個請求。

Java 的 Lambda 把資料庫連線建在 static 欄位（handler 外面）。第二個請求剛好用到同一個環境時，連線會？

  • 每次 Invoke 都重建
  • 被 Lambda 自動關閉再開
  • 沿用，handler 外的物件會保持
  • 出錯，Lambda 不允許 static 欄位

官方原文 Objects declared outside of the function's handler method remain initialized，例子就是資料庫連線。建議先檢查連線還在不在再用。

函式一直有請求進來，環境會一直存在嗎？

  • 會，只要有流量就不會被回收
  • 不會，每隔幾小時就會換掉做維護
  • 會，除非重新部署
  • 不會，每次 Invoke 完就銷毀

文件：Lambda 每隔幾小時會終止環境做更新與維護，即使持續被呼叫；所以不能把重要狀態只放在環境裡。

一個對帳批次平均要跑 40 分鐘，想放到 Lambda 一次跑完。問題在哪？

  • 單次執行最長 900 秒（15 分鐘）
  • 沒問題，Lambda 沒有時間上限
  • Init 階段只有 10 秒
  • 要先申請提高帳戶的同時執行數，否則排不進去

配額表：Function timeout 900 seconds (15 minutes)。Init 的 10 秒限的是初始化，不是整次執行。要用 Lambda 就得切成小段。

行銷活動讓同時請求從 10 衝到 800，每個環境開一個 5 條連線的連線池。最可能先出事的是？

  • Lambda 的帳戶上限 1,000 不夠
  • Lambda 不允許超過 100 個環境
  • 資料庫連線數：最多 4,000 條
  • 每個環境的 Init 都會超過 10 秒的上限

環境數跟著同時請求數走，每個環境各有自己的連線。800 還沒到預設上限 1,000，但 800 × 5 條連線對資料庫來說很可能已經太多。

第一個請求為什麼慢

冷啟動與 SnapStart

新環境第一次要跑完 Init 才能 Invoke，這段等待叫冷啟動；文件的數字（通常不到 1% 的呼叫、從不到 100 毫秒到超過 1 秒）〈微服務與架構面試題：服務發現、韌性、可觀測性與十二要素〉整理過。Java 特別吃虧，因為 JVM 啟動與框架初始化都在 Init 裡。官方的兩條路：

預置並行（provisioned concurrency）：事先開好、初始化完的環境，「需要可預期的啟動時間時，建議用這個」（If you need predictable function start times for your workload, provisioned concurrency is the recommended solution）。出處 代價是那些環境沒請求時也在計費。

SnapStart：「發佈函式版本時，Lambda 就先初始化，對初始化完的環境的記憶體與磁碟狀態拍下 Firecracker 微型虛擬機的快照，加密後快取」（Firecracker 是 AWS 用來隔離每個環境的輕量虛擬機）；之後新環境「從快取的快照恢復，而不是從頭初始化」（Lambda resumes new execution environments from the cached snapshot instead of initializing them from scratch）。出處 限制寫在同一頁：支援 Java 11 以上、Python 3.12 以上、.NET 8 以上；只能用在「已發佈的版本」與指向版本的別名；不能跟預置並行一起用。出處

SnapStart 的陷阱是唯一性。快照裡的東西會被複製到每一個恢復出來的環境：「如果你的程式依賴狀態的唯一性，必須確認程式碼經得起快照操作」（If your applications depend on uniqueness of state, you must evaluate your function code and verify that it is resilient to snapshot operations.）。出處 官方的 Java 範例（本課沒有實跑）把 UUID 放在 handler 裡才產生，而不是寫在 static 初始化：

import java.util.UUID;

public class Handler implements RequestHandler<String, String> {

    private static UUID uniqueSandboxId = null;

    @Override
    public String handleRequest(String event, Context context) {
        if (uniqueSandboxId == null)
            uniqueSandboxId = UUID.randomUUID();
        System.out.println("Unique Sandbox Id: " + uniqueSandboxId);
        return "Hello, World!";
    }
}

文件的建議是「避免在初始化時快取應該唯一的資料，例如產生記錄用的唯一 ID 或設定亂數種子」，要在 handler 裡產生，或用快照前後的執行階段掛勾（runtime hook）重新產生。出處 銀行的交易序號、一次性密碼這類東西尤其要注意。

開了 SnapStart 之後，Init 階段什麼時候跑？

  • 每次 Invoke 之前
  • 每個新環境建立時
  • 發佈函式版本時
  • 完全不跑，SnapStart 跳過初始化

官方：Lambda initializes your function when you publish a function version，然後拍快照；之後新環境從快照恢復。初始化有做，只是移到發佈時做一次。

static 初始化時產生一個 UUID 當環境編號，開了 SnapStart。從快照恢復的多個環境會？

  • 各自產生不同的 UUID
  • 恢復時 Lambda 會自動重新產生
  • 恢復失敗，SnapStart 不允許 static 欄位
  • 拿到同一個 UUID

初始化結果被拍進快照，每個環境都從同一份快照恢復。官方範例因此把 UUID.randomUUID() 放在 handler 裡第一次用到時才產生。

想同時開 SnapStart 和預置並行，可以嗎？

  • 不行，SnapStart 不支援預置並行
  • 可以，兩個一起開效果最好，官方也這樣建議
  • 可以，但只限 Python
  • 不行，預置並行只支援 Java

SnapStart 頁明列 does not support provisioned concurrency。兩者是二選一的冷啟動解法。

函式用 $LATEST 直接呼叫，沒有發佈版本，SnapStart 會作用嗎？

  • 會，所有呼叫都會用快照
  • 會，$LATEST 每次部署都會自動拍一份快照
  • 不會，只能用在已發佈的版本與指向版本的別名
  • 不會，要改用容器映像檔部署

流量很稀疏的 Java 轉帳查詢 API，每次冷啟動都讓使用者等很久，而且要求啟動時間可預期。官方建議的是？

  • 把記憶體調到最小，啟動比較快
  • 把逾時調到 15 分鐘

  • 預置並行

換一種計價單位：容器

Cloud Run 的模型：一個執行個體同時處理多個請求

Cloud Run 是 Google Cloud 的做法：「全代管的應用平台，在 Google 的基礎設施上跑你的程式、函式或容器」，只要能做成容器映像檔，什麼語言都可以。出處 你交的是容器，所以要遵守它的容器契約：在 0.0.0.0 的指定連接埠上聽請求，「不應該聽在 127.0.0.1」，預設送到 8080，Cloud Run 會用 PORT 環境變數告訴你是哪個埠。出處

跟 Lambda 最大的差別是同時處理數：一個執行個體可以同時處理多個請求，上限最高可以設到 1,000；用 gcloud 或 Terraform 新建的服務預設是 vCPU 數的 80 倍，用主控台建的預設 80。程式不能平行處理時「把並行數設成 1」。出處

擴縮：請求進來就擴，需求下降就把閒置的容器收掉；沒有請求時連最後一個也收掉（scale to zero），下一個請求來才建新的，「可能拉長這些初始請求的回應時間」。出處 要避免就設最少執行個體數（min instances），官方說可以「避免容器啟動慢、降低延遲」；計費方式選「依請求計費」時，閒置的執行個體用較低的費率計算，最少數設 0 才不必為閒置付費。出處 另一個開關是啟動時暫時加 CPU（startup CPU boost），用來縮短啟動延遲。出處 要保護下游，也可以限制最多執行個體數：官方原文就說「擔心成本或壓垮下游系統時」用它。出處 請求逾時預設 5 分鐘，最長 60 分鐘。出處

重用的規則跟 Lambda 很像：「不能假設請求之間會保留狀態」，但執行個體會被重用，所以昂貴的物件可以放在全域範圍。官方的 Java 範例（本課沒有實跑）註解多了一句 Lambda 沒有的警告：

public class Scopes implements HttpFunction {
  // Global (instance-wide) scope
  // This computation runs at instance cold-start.
  // Warning: Class variables used in functions code must be thread-safe.
  private static final int INSTANCE_VAR = heavyComputation();
  …
}

要執行緒安全，正是因為一個執行個體會同時處理多個請求。出處 這也讓連線數的問題比 Lambda 好控制：80 個同時請求可以共用一個執行個體裡的同一個連線池。

把一個 Spring Boot 容器部署到 Cloud Run，程式設定只聽 127.0.0.1:8080。會怎樣？

  • 正常，Cloud Run 會轉發到本機位址
  • 正常，只要埠是 8080
  • 收不到請求，要聽在 0.0.0.0
  • Cloud Run 會自動改成聽 0.0.0.0

容器契約：must listen for requests on 0.0.0.0，should not listen on 127.0.0.1。埠預設 8080，以 PORT 環境變數為準。

同時 3 個請求，Cloud Run 服務的並行上限是 80。最少需要幾個執行個體？

  • 3 個，一個請求一個
  • 1 個
  • 80 個，先開滿
  • 0 個，Cloud Run 不用執行個體

一個執行個體可以同時處理到並行上限那麼多個請求。這是跟 Lambda「一個請求一個環境」最大的差別。

某支舊程式不是執行緒安全的，同時處理兩個請求會出錯。部署到 Cloud Run 要怎麼設？

  • 最少執行個體數設 1
  • 請求逾時設 60 分鐘
  • 最多執行個體數設 1
  • 並行數設 1

官方：if your code cannot process parallel requests, set concurrency to 1。最多執行個體數設 1 是限制總共幾個執行個體，跟每個執行個體同時處理幾個無關。

深夜沒有流量，早上第一個使用者等特別久。Cloud Run 官方對這個情況的建議設定是？

  • 並行數調到 1,000
  • 設最少執行個體數
  • 請求逾時調長
  • 把映像檔縮小，就不會縮到 0

沒流量時縮到 0，下一個請求要等新執行個體建好。min instances 就是用來 avoid slow container start times and reduce service latency，代價是閒置時也有費用（依請求計費時費率較低）。

Cloud Run 官方範例在全域變數旁註明 must be thread-safe，Lambda 的同類範例沒有。為什麼？

  • 一個執行個體會同時處理多個請求
  • Cloud Run 只支援多執行緒的語言
  • Lambda 的全域變數不會被重用
  • Cloud Run 的全域變數存在資料庫裡

多個請求同時在一個執行個體裡跑，就會同時碰到同一個全域變數。Lambda 一個環境同一時間只處理一個請求，沒有這個問題。

回到「什麼時候值得用」

適合與不適合，以及銀行情境的取捨

把前面的模型整理成判斷依據：

值得用不太值得
服務網格服務多、語言多，要求服務間全面加密並分得出誰呼叫誰；要做比例精細的金絲雀只有少數幾個同語言的服務：函式庫加入口的 TLS 可能就夠，多一個控制平面要維運
Lambda事件驅動、量一陣一陣、每次工作短而獨立超過 15 分鐘的工作；穩定的高流量；大量同時請求又各自連資料庫
Cloud Run已經是容器的 HTTP 服務，流量起伏大，想要自動擴縮又不想管叢集需要節點層級的控制，或已經有一套 K8s 與網格可以用

表格是本課依前面各節官方說法推出來的整理，下面的情境也是自編的。

情境一：行內有幾十個服務、Java 與 Go 混用，資安要求內部連線全部加密，並且能限制哪個服務可以呼叫帳務服務。這是網格最值得的情況：先 PERMISSIVE 讓舊服務照常連，逐一注入後切 STRICT，每個服務給自己的服務帳號，再用授權規則寫「誰可以呼叫我」。只要加密與身分的話，ambient 的成本比較低。

情境二：每天晚上外部單位丟一個對帳檔到 S3，要解析、比對、發通知。一天一次、量不大、事件觸發，適合 Lambda；但如果比對要跑超過 15 分鐘，就要切小段，或改用批次服務。

情境三：核心的轉帳 API，流量穩定且大，對延遲敏感，每個請求都要連資料庫。Lambda 的冷啟動與「一個請求一個環境」帶來的連線數都不利；跑在現有的 K8s 上，或 Cloud Run 搭配最少執行個體數與最多執行個體數，比較好控制。

只有三個 Spring Boot 服務、同一個團隊維護，想要重試與逾時。比較合理的起點是？

  • 裝 Istio，因為重試只能在網格裡做
  • 改寫成 Lambda
  • 先用 Resilience4j 這類函式庫
  • 裝 Istio 的 ambient 模式，因為它有第七層重試

服務少、語言單一，函式庫就做得到重試與逾時，還能寫降級。網格多一個控制平面要維運；ambient 要做重試也得加 waypoint。

每晚一次、外部單位上傳對帳檔到 S3 後要處理，處理約 3 分鐘。哪個最貼近 Lambda 的強項？

  • 用 S3 事件觸發 Lambda，處理完就結束
  • 開一台一直開著的虛擬機每分鐘檢查
  • 裝 Istio，用流量切分把檔案分給兩個版本處理
  • 用 Lambda 跑一個永不結束的迴圈監看

事件觸發、一天一次、幾分鐘內做完，正是 Lambda 的模型。永不結束的迴圈會撞到 15 分鐘上限。

核心轉帳 API 流量穩定且大、對延遲敏感、每個請求都要查資料庫。放 Lambda 最大的顧慮是？

  • Lambda 不能連資料庫
  • Lambda 只能用 Python
  • Lambda 不支援 HTTPS
  • 冷啟動，加上每個環境各自連資料庫

一個請求一個環境，每個環境各有連線；冷啟動又直接加在延遲上。穩定的大流量放在固定份數的容器裡，連線池總數算得出來。

行銷活動要把服務放到 Cloud Run，但後端資料庫最多只撐得住 20 個執行個體的連線。該設什麼？

  • 最少執行個體數 20
  • 並行數 20
  • 最多執行個體數 20
  • 請求逾時 20 分鐘

官方：擔心成本或 overloading downstream systems 時，可以限制最多執行個體數。最少執行個體數是防冷啟動用的，方向相反。

重點整理

  • 服務網格把加密、身分、逾時、重試、流量比例從程式搬到平台。Istio 的資料平面是 Envoy，控制平面是 istiod；sidecar 注入發生在 Pod 建立時，現有 Pod 要重啟。1.31 實測 istio-proxy 是 Kubernetes 原生 sidecar（initContainers 加 restartPolicy: Always）。
  • 兩個代理之間自動走 mTLS；PeerAuthentication 決定伺服器收不收明文：PERMISSIVE 都收（搬遷用、網格預設），STRICT 只收 mTLS。身分是 spiffe://cluster.local/ns/命名空間/sa/服務帳號，憑證預設 24 小時、自動輪替；每個服務要有自己的服務帳號。
  • DestinationRule 定義 subset，VirtualService 寫權重；比例跟 Pod 數無關，但少量請求會上下跳（實測 4、8、11）。推進要人或 Argo Rollouts 這類工具。
  • Istio 預設沒有逾時、連線失敗重試 2 次；啟用故障注入時逾時與重試不啟用。程式與網格各設各的會互相抵銷（外層較短，內層白設）或相乘（3 × 3 = 9）；同一種重試只放一層，降級一定在程式裡。
  • Ambient：每節點 ztunnel 管第四層的加密與身分，waypoint 管第七層；1.22 起單叢集可用於生產，加入網格不必重啟，只要 mTLS 時成本較低。
  • Lambda：一個同時請求一個環境，單次最長 15 分鐘，環境會重用但每幾小時會換；冷啟動用預置並行（可預期、閒置也計費）或 SnapStart（發佈版本時拍快照，注意唯一性，兩者不能併用）。Cloud Run：交容器、聽 0.0.0.0 的 PORT，一個執行個體同時處理多個請求（全域變數要執行緒安全），min instances 防冷啟動、max instances 保護下游。
