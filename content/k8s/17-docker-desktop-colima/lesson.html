先把棒次排好

一行 docker 指令，背後有四棒

第 14 課說過 CLI 自己不做事。完整的傳球是這樣：

誰白話角色正式名稱
docker 指令接單櫃台，把你的要求送出去Docker CLI
dockerd總管，決定要做什麼、管網路和映像檔Docker Engine（容器引擎）
containerd工頭，管映像檔和容器的一生容器執行環境（第 6 課出現過）
runc工人，真的去把那支被隔離的程式啟動起來低階執行工具

第 14 課提過：Linux 容器要的是 Linux 核心。上面這四棒裡，真正需要 Linux 的是後面兩棒。所以 Mac 和 Windows 的問題不是「Docker 裝不起來」，是「要先生出一個 Linux 給後面兩棒站」。這一課就是在講那個 Linux 是誰生的。

Windows 路線

Docker Desktop 借 WSL 2 那層 Linux

Docker Desktop 是一站式的裝法：圖形介面、Docker CLI、容器引擎、Compose、網路轉送、檔案共享，一次包給你。在 Windows 上它用 WSL 2（Windows 內建的 Linux 子系統）當地基。

Windows 終端機
  ↓ docker 指令
Docker Desktop
  ↓
WSL 2 的 Linux 環境
  ↓ dockerd → containerd → runc
Linux 容器

原筆記寫「WSL2 建立輕量級 Linux VM（Ubuntu-based）」。Docker 官方文件的說法是：Docker Desktop 跑在它自己的 docker-desktop 發行版裡，和你裝的其他 WSL 發行版互相隔離出處。所以就算你在 Windows 上裝了 Ubuntu，Docker 也不是跑在那個裡面。

你打 -p 8080:8080 的時候，Docker Desktop 幫你把 Windows 的 8080 轉到 WSL 2、再轉到容器。使用者連 localhost:8080，流量是這樣一路過去的。

macOS 路線

Docker Desktop 或 Colima，差在誰管那台虛擬機

macOS 本身不是 Linux，也沒有 WSL 這種東西，所以要跑 Linux 容器就一定得開一台 Linux 虛擬機。兩條路：

Docker Desktop：一站式
  • 圖形介面、CLI、引擎、Compose 全包。
  • 虛擬機由它自己開、自己管，你不太需要知道。
  • 裝好就能用，適合不想研究底下那層的人。
Colima：模組化
  • Colima 只負責管那台 Linux 虛擬機。
  • Docker CLI、Compose 自己另外裝。
  • 沒有圖形介面，全部在終端機。
  • 裝法：brew install colima docker docker-compose
macOS 終端機
  ↓ docker 指令
Docker context / socket
  ↓
Colima 管的那台 Linux 虛擬機
  ↓ dockerd → containerd → runc
Linux 容器

Colima 自己不開虛擬機，它叫 Lima（一個在 macOS 上開 Linux 虛擬機的工具）去開。啟動時可以指定要給多少資源：

colima start --cpu 4 --memory 8

數字照你電腦的容量調，不要把資源全部塞給虛擬機。

原筆記在這一段有三處要修

  • Docker Desktop for Mac 現在的虛擬機管理器有兩個選項：Docker 自己做的 Docker VMM，和 Apple 的 Virtualization framework；舊的 HyperKit 只剩 Intel Mac 能用，而且已經標為淘汰出處（原筆記寫的是「使用 macOS Hypervisor Framework」）。
  • Colima 從 v0.6.0 起，底下用的是 Ubuntu 映像，不是 Alpine出處（原筆記寫的是「建立 Alpine Linux VM（更輕量）」）。
  • 原筆記寫 Lima 用 QEMU。查證後：Lima 支援多種虛擬化方式，而且預設變過——Lima v1.0 之前預設是 QEMU（一套開源的虛擬機軟體），v1.0 起在 macOS 13.5 以上的新機器預設改用 Apple 的 VZ（Virtualization framework）。出處 所以「Colima 一定用 QEMU」這句現在不成立。

macOS 上 Docker Desktop 那台虛擬機裡面是哪一個 Linux 發行版，Docker 官方的 Mac 虛擬機管理器說明頁沒有明講（這裡查的就是那一頁），原筆記寫的「Ubuntu-based」查不到出處，這裡就不寫。出處

動手

把一個 Spring Boot 的 JAR 變成容器

先用 Maven 或 Gradle 把 JAR 建出來，再寫 Dockerfile（寫法見第 15 課）：

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/my-app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

原筆記的 Dockerfile 用的是 openjdk:17-jre-alpine。Docker Hub 上的 openjdk 官方映像頁面已經掛著停止維護的公告，Java 的基礎映像檔要改用 eclipse-temurin、amazoncorretto 這幾個替代品出處。

docker build -t my-spring-app:1.0 .
docker run -d --name my-spring-app -p 8080:8080 my-spring-app:1.0

docker ps
curl http://localhost:8080

這幾行按下去，實際發生的事是：CLI 把建置內容和指令送給引擎 → 引擎在那台 Linux 虛擬機裡拉基礎映像檔、跑 Dockerfile 的每一步、疊出分層映像檔 → 啟動時由 containerd 和 runc 準備檔案系統、隔離房間、資源上限，最後把 Java 程序起起來。你的 Java 程式從頭到尾都是在那台 Linux 虛擬機裡面跑的，只是連線被一路轉回你的 localhost。

最常見的疑惑

「我的映像檔不見了」

從 Docker Desktop 換成 Colima（或反過來）之後，docker image ls 突然空了。資料通常沒有不見——是你的 CLI 指到另一間工廠了。每個引擎有自己的映像檔和容器，Docker CLI 靠 context（連線設定）決定要跟哪一個講話：

docker context ls      # 有哪些連線設定，哪個是現在用的
docker context show    # 現在指著哪一個
docker info            # 連上去之後看到的是哪一套
面向Docker DesktopColima
平台Windows、macOSmacOS（也支援其他環境）
操作方式圖形介面加命令列命令列為主
那層 Linux產品自己開、自己管透過 Lima 開和管
Docker CLI通常隨產品一起裝要自己另外裝
映像檔放哪在它自己的 Linux 後端裡在 Colima 那台虛擬機裡
Dockerfile 要不要改不用——同一份 Dockerfile 兩邊都能建

兩邊的 Dockerfile 通用，但效能、檔案掛載和網路行為仍然可能不一樣，換工具之後值得重跑一次自己的流程。

重點整理

  • 四棒：docker CLI → dockerd → containerd → runc；需要 Linux 核心的是後面兩棒。
  • Windows 上 Docker Desktop 跑在它自己的 docker-desktop WSL 發行版裡，不是你裝的那個 Ubuntu。
  • macOS 上跑 Linux 容器一定要一台 Linux 虛擬機：Docker Desktop 自己開自己管，Colima 則是叫 Lima 去開。
  • Colima 從 v0.6.0 起用的是 Ubuntu 映像；Lima 的預設虛擬化方式也變過——v1.0 起，在 macOS 13.5 以上新建的機器預設改用 Apple 的 VZ（設定不相容時仍退回 QEMU）。
  • Java 的基礎映像檔別再用 openjdk，它已經停止維護。
  • 換工具之後映像檔「不見了」，先看 docker context——多半只是指到另一個引擎。
