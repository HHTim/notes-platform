先描述現實世界，再決定資料表

實體、屬性與關係

資料庫設計通常先找出實體（Entity，要描述的「東西」）、屬性（Attribute，東西的特徵）與關係（Relationship，東西之間的關聯）。例如書籍與作者是實體；書名是書籍的屬性；「作者參與某本書」則是一種關係。

不要急著問「要開幾張表」，先問：

  • 這筆資料在描述誰或什麼？
  • 兩個實體之間可以各自對應幾筆？
  • 某個欄位屬於實體本身，還是只在兩者關係成立時才有意義？

欄位放哪裡，取決於它描述的是「東西本身」，還是「東西之間的關係」。

先數兩邊各能有幾個

一對一、一對多與多對多

關係例子常見關聯式設計
一對一帳號與獨立的帳號設定其中一表持有帶 UNIQUE 約束的外鍵，或兩表共用主鍵
一對多一個部門有多位員工在「多」的一方 employees 放 department_id
多對多學生修多門課，每門課也有多位學生建立中介表 enrollments

關係還有「是否必須存在」的差異。例如「一位作者可以尚未出版任何書」是零到多；「一本正式出版的合著書至少有一位作者」則是至少一位。

一對一是否需要拆表，要看安全性、欄位使用頻率、生命週期及是否真的存在獨立概念；不是看到一對一就必須分表。

成績不屬於學生，也不屬於課程

用關聯類別承接多對多資訊

學生本身沒有單一的「成績」，課程本身也沒有單一的「成績」。只有當某位學生選了某門課，成績才有意義。因此成績應放在中介的關聯類別（Associative Entity，專門描述兩個實體之間關係的表）中。

students
├── student_id PK
└── student_name

courses
├── course_id PK
└── course_name

enrollments
├── student_id PK, FK
├── course_id PK, FK
├── score
└── enrolled_at

同理，訂單與商品之間的「數量」應放在訂單明細；書籍與作者之間的「主要作者、共同作者、編者」角色，也應放在書籍作者關聯上。

books
├── book_id PK
└── title

authors
├── author_id PK
└── author_name

book_authors
├── book_id PK, FK
├── author_id PK, FK
├── role
└── author_order

容易卡住的一題：role 該填主要作者還是輔助作者的名字？答案是都不填名字——role 描述的是「這位作者在這本書的身分」，例如主要作者、共同作者或編者；名字在 authors 表裡。

關聯式不是唯一形狀

NoSQL 是一組不同的資料模型

NoSQL 常被解釋為「不只 SQL」（Not Only SQL）。它不是單一產品或單一模型，而是一組不以關聯式表格為核心的資料庫類型。

模型資料形狀常見用途
文件式類似 JSON 的文件內容管理、商品目錄
鍵值式一個鍵對應一個值快取、工作階段（session，一次登入期間的狀態）、快速查找
寬欄式依列鍵（識別一列的鍵）與欄族（一組常一起讀的欄位）組織大量分散式寫入、時間序列資料
圖形式節點與邊社交關係、推薦、路徑查詢

選擇資料庫時不應只問哪一種「比較新」，而應評估資料關係、查詢模式、交易需求、一致性要求、資料規模與團隊維運能力。

彈性綱要不等於沒有規則

文件式資料庫的嵌入與參照

以 MongoDB 這類文件式資料庫為例，同一集合中的文件確實可以有不同欄位，但官方的說法是彈性綱要（Flexible Schema）而非「沒有綱要」——需要時可以對文件加上綱要驗證（Schema Validation），應用程式也仍需要清楚的資料契約出處。

{
  "_id": 1001,
  "customer": {
    "customer_id": 7,
    "name": "阿寶"
  },
  "items": [
    {"item_id": 11, "name": "鉛筆", "qty": 2, "unit_price": 20},
    {"item_id": 12, "name": "橡皮擦", "qty": 1, "unit_price": 50}
  ],
  "total": 90
}

把訂單明細嵌入同一份文件，適合資料通常一起讀取、明細數量有合理上限，而且生命週期跟著訂單走的情境。

若資料會被大量文件共同參照、需要獨立更新，或清單可能無限制成長，則改用識別值參照。

策略適合情況代價
嵌入（Embedding）資料總是一起讀、一起建立或刪除可能重複，文件也可能持續膨脹
參照（Referencing）資料被廣泛共用或獨立更新讀取時可能需要額外查詢

關聯式設計常從「避免重複」出發；文件式設計更常從「一次操作需要拿到什麼」出發。

兩種架構都能處理複雜需求

關聯式與 NoSQL 的選擇

考量關聯式資料庫常見優勢NoSQL 常見優勢
資料關係外鍵、JOIN 與約束成熟可直接保存應用程式常用的資料形狀
交易跨資料表交易與一致性工具成熟各產品能力不同，部分產品也支援多文件交易
綱要結構明確、資料品質易集中管控欄位演進通常較有彈性
擴充可垂直或水平擴充，依產品與架構而定部分產品從設計上就著重分散式水平擴充
查詢方式SQL 與臨時分析能力強通常針對既定存取模式設計資料形狀

「SQL 不能水平擴充」或「NoSQL 沒有交易」都是過度簡化。現代產品的能力有所重疊，必須檢查特定資料庫與版本，而不能只看分類標籤。

帳務核心若高度依賴跨資料的一致性與複雜查詢，關聯式資料庫通常是穩健起點；大量快取、文件聚合或圖形路徑問題，則可能由對應的 NoSQL 模型處理得更自然。

切開是為了容量，複製是為了韌性

分片與複寫解決不同問題

技術做法主要目標主要難題
分片（Sharding）把不同資料分散到多個節點擴充容量與吞吐量分片鍵怎麼選、跨片查詢、重新平衡
複寫（Replication）把同一份資料保留多個副本提高可用性、容錯與讀取能力複寫延遲、故障切換、一致性

分片像把不同姓氏的檔案分到多個櫃子；複寫像把同一份重要文件放在不同地點——雞蛋不放在同一個籃子。兩者可以同時使用，但不能互相取代。

複寫能降低單一節點故障的風險，卻不代表備份可以省略。錯誤刪除、應用程式缺陷或勒索軟體可能同步影響所有副本；備份仍需獨立保存並演練復原。

分片回答「資料怎麼分工存」；複寫回答「同一份資料怎麼留副本」。

從查詢反推模型

一套可落地的設計流程

  1. 列出核心業務規則，例如一本書可有多位作者，且角色屬於書籍與作者的關係。
  2. 列出最重要的讀寫操作、交易邊界、資料量與成長速度。
  3. 判斷資料需要強關聯約束、文件聚合、鍵值查找，還是圖形遍歷。
  4. 決定主鍵、關聯方式與必要約束；不要用目前樣本取代業務規則。
  5. 用有代表性的資料量，實際量測查詢、寫入、故障復原與維運成本。
  6. 若要重複資料換取讀取速度，明確記錄哪一份是權威來源，以及如何同步。

同一套系統可以採用多種資料庫，各自負責適合的工作；但每增加一種技術，就會增加部署、監控、備份與一致性管理成本。

重點整理

  • 一對多把外鍵放在多的一方；多對多需要中介表（關聯類別）。
  • 成績、數量與作者角色描述的是兩個實體之間的關係，應放在關聯上。
  • NoSQL 是多種非關聯式資料模型的總稱，不等於沒有綱要或沒有交易。
  • 文件式設計在嵌入與參照之間取捨，關鍵是讀寫模式與資料生命週期。
  • 分片分散資料與負載，複寫建立副本提高可用性；備份仍不可省略。
