兩張表怎麼接、接不上的怎麼辦

四種 JOIN 與 NULL 的坑

JOIN（連接）是把兩張表依條件配對成一列。INNER JOIN 只留兩邊都配得到的；LEFT JOIN 留下左表全部，右表配不到就補 NULL；RIGHT JOIN 反過來；FULL OUTER JOIN 兩邊都留。先看最常用的兩種：

SELECT a.account_id, a.owner, b.name AS branch
FROM accounts a
JOIN branches b ON a.branch_id = b.branch_id
ORDER BY a.account_id;

|        102 | 陳小美    | 台北分行     |
|        103 | 林大同    | 新竹分行     |
|        104 | 張美玲    | 高雄分行     |
|        106 | 黃小華    | 高雄分行     |
+------------+-----------+--------------+
5 rows in set (0.00 sec)
SELECT a.account_id, a.owner, b.name AS branch
FROM accounts a
LEFT JOIN branches b ON a.branch_id = b.branch_id
ORDER BY a.account_id;
+------------+-----------+--------------+
| account_id | owner     | branch       |
+------------+-----------+--------------+
|        101 | 王小明    | 台北分行     |
|        102 | 陳小美    | 台北分行     |
|        103 | 林大同    | 新竹分行     |

INNER JOIN 少了李志明，因為他的 branch_id 是 NULL，跟任何分行都配不上；LEFT JOIN 把他留下來，分行欄補 NULL。MySQL 手冊的說法是：LEFT JOIN 在 ON 或 USING 找不到配對的右表資料列時，「會用一列所有欄位都是 NULL 的資料列當作右表」（a row with all columns set to NULL is used for the right table）。出處 RIGHT JOIN 只是左右對調：

SELECT b.branch_id, b.name AS branch, a.owner
FROM accounts a
RIGHT JOIN branches b ON a.branch_id = b.branch_id
ORDER BY b.branch_id, a.account_id;

手冊說 RIGHT JOIN「跟 LEFT JOIN 的運作方式相同」，並建議「為了讓程式碼能在不同資料庫之間移植，用 LEFT JOIN 取代 RIGHT JOIN」（To keep code portable across databases, it is recommended that you use LEFT JOIN instead of RIGHT JOIN）。出處 實務上把要全部保留的那張表寫在左邊就好。

FULL OUTER JOIN：MySQL 沒有，要自己拼

MySQL 8.4 手冊的 JOIN 語法定義裡，外連接只有 {LEFT|RIGHT} [OUTER] JOIN 兩種（table_reference {LEFT|RIGHT} [OUTER] JOIN table_reference join_specification），沒有 FULL OUTER JOIN。出處 實跑直接是語法錯誤：

SELECT a.owner, b.name AS branch
FROM accounts a
FULL OUTER JOIN branches b ON a.branch_id = b.branch_id;
ERROR 1064 (42000) at line 1: You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'FULL OUTER JOIN branches b ON a.branch_id = b.branch_id' at line 3

SELECT a.owner, b.name AS branch
FROM accounts a LEFT JOIN branches b ON a.branch_id = b.branch_id
UNION ALL
SELECT a.owner, b.name AS branch
FROM accounts a RIGHT JOIN branches b ON a.branch_id = b.branch_id
WHERE a.account_id IS NULL;

LEFT JOIN 的條件：放 ON 還是放 WHERE

題目：列出每個帳戶的提款筆數，沒提款過的也要出現、顯示 0。直覺的寫法是 LEFT JOIN 之後在 WHERE 篩提款：

SELECT a.account_id, COUNT(t.tx_id) AS withdraw_count
FROM accounts a
LEFT JOIN transactions t ON t.account_id = a.account_id
WHERE t.tx_type = 'WITHDRAW'
GROUP BY a.account_id
ORDER BY a.account_id;
+------------+----------------+
| account_id | withdraw_count |
+------------+----------------+
|        101 |              1 |
|        102 |              1 |
+------------+----------------+
2 rows in set (0.00 sec)

只剩兩列，其他四個帳戶不見了。把條件搬進 ON：

SELECT a.account_id, COUNT(t.tx_id) AS withdraw_count
FROM accounts a
LEFT JOIN transactions t ON t.account_id = a.account_id
                        AND t.tx_type = 'WITHDRAW'
GROUP BY a.account_id
ORDER BY a.account_id;
+------------+----------------+
| account_id | withdraw_count |
+------------+----------------+
|        101 |              1 |
|        102 |              1 |
|        103 |              0 |
|        104 |              0 |
|        105 |              0 |
|        106 |              0 |
+------------+----------------+
6 rows in set (0.00 sec)

差在處理的時間點。PostgreSQL 文件講得最直白：「放在 ON 子句的條件在連接之前處理，放在 WHERE 子句的條件在連接之後處理。這對內連接沒差，對外連接影響很大」（a restriction placed in the ON clause is processed before the join, while a restriction placed in the WHERE clause is processed after the join. That does not matter with inner joins, but it matters a lot with outer joins）。出處

放在 WHERE 時，沒提款的帳戶在連接時補了一列 NULL，接著 t.tx_type = 'WITHDRAW' 對 NULL 的結果不是 TRUE，那一列就被濾掉。

這裡的 UNKNOWN（不知道）是 SQL 邏輯運算的第三種結果，手冊寫：「SQL 的所有邏輯運算子結果都是 TRUE、FALSE 或 NULL（UNKNOWN），在 MySQL 實作成 1、0 與 NULL」（In SQL, all logical operators evaluate to TRUE, FALSE, or NULL (UNKNOWN). In MySQL, these are implemented as 1 (TRUE), 0 (FALSE), and NULL.），所以 MySQL 顯示成 NULL。出處 MySQL 手冊把這種條件叫「null-rejected」：條件對「補 NULL 的那些列」算出來是 FALSE 或 UNKNOWN 時，最佳化器乾脆把外連接改成內連接（it converts the outer join to an inner join）。出處

同一個結果裡還有第二個坑：COUNT(*) 數的是列數，COUNT(欄位) 只數非 NULL 的值。手冊：「COUNT()、MIN()、SUM() 這類聚合函式會忽略 NULL 值，例外是 COUNT(*)，它數的是列，不是個別欄位的值」（The exception to this is COUNT(*), which counts rows and not individual column values）。出處

SELECT a.account_id, COUNT(*) AS star, COUNT(t.tx_id) AS tx
FROM accounts a
LEFT JOIN transactions t ON t.account_id = a.account_id
                        AND t.tx_type = 'WITHDRAW'
GROUP BY a.account_id
ORDER BY a.account_id;
+------------+------+----+
| account_id | star | tx |
+------------+------+----+
|        101 |    1 |  1 |
|        102 |    1 |  1 |
|        103 |    1 |  0 |
|        104 |    1 |  0 |
|        105 |    1 |  0 |
|        106 |    1 |  0 |
+------------+------+----+
6 rows in set (0.00 sec)

沒提款的帳戶，LEFT JOIN 補上了一列 NULL，COUNT(*) 數到它是 1；COUNT(t.tx_id) 遇到 NULL 不算，是 0。外連接之後要數「右表有幾筆」，一律數右表的欄位。

一對多再接一對多：加總會變大

題目：算每個帳戶的交易淨額。如果順手把登入紀錄也接進來（例如之後想一起算登入次數），結果會是：

SELECT a.account_id, SUM(t.amount) AS balance
FROM accounts a
JOIN transactions t ON t.account_id = a.account_id
JOIN logins l       ON l.account_id = a.account_id
GROUP BY a.account_id
ORDER BY a.account_id;
+------------+---------+
| account_id | balance |
+------------+---------+
|        101 |   30000 |
|        102 |   20000 |
|        103 |       0 |
+------------+---------+
3 rows in set (0.00 sec)

對照只查交易的正確答案：

SELECT account_id, SUM(amount) AS balance
FROM transactions
GROUP BY account_id
ORDER BY account_id;
+------------+---------+
| account_id | balance |
+------------+---------+
|        101 |    6000 |
|        102 |    4000 |
|        103 |       0 |
|        104 |   11000 |
|        105 |     500 |
+------------+---------+
5 rows in set (0.00 sec)

王小明的淨額 6000 變成 30000，剛好是 5 倍。原因是他有 4 筆交易、5 筆登入，兩個一對多接在一起，每筆交易都跟 5 筆登入各配成一列，共 20 列，每筆金額都被加了 5 次。林大同 0 乘多少都是 0，看起來對，其實一樣是錯的寫法；張美玲和李志明沒有登入紀錄，被內連接直接刪掉。要同時算兩種一對多的東西，先各自 GROUP BY 成「一個帳戶一列」，再接回帳戶表。

自己接自己，以及 NULL 永遠配不上

同一張表可以接兩次，用不同的別名分開。下面把每筆轉出接到「轉出人」與「收款人」，交易表的 counterparty_id 接帳戶表兩次：

SELECT t.tx_id, f.owner AS from_owner, c.owner AS to_owner, -t.amount AS amount
FROM transactions t
JOIN accounts f ON f.account_id = t.account_id
JOIN accounts c ON c.account_id = t.counterparty_id
WHERE t.amount < 0
ORDER BY t.tx_id;
+-------+------------+-----------+--------+
| tx_id | from_owner | to_owner  | amount |
+-------+------------+-----------+--------+
|     2 | 王小明     | 陳小美    |   1200 |
|     8 | 林大同     | 張美玲    |   3000 |
+-------+------------+-----------+--------+
2 rows in set (0.00 sec)

存提款的 counterparty_id 是 NULL，用 = 去配對永遠配不上。手冊寫：「在 SQL 裡，NULL 跟任何值比較都不會是 TRUE，連跟 NULL 比也一樣」（In SQL, the NULL value is never true in comparison to any other value, even NULL）。出處

INNER 只留配得到的、LEFT 留左表全部；外連接的右表條件放 ON；外連接後數右表用 COUNT(右表欄位)；兩個一對多同時接會放大加總；NULL 用 = 永遠配不上

想找出「一筆交易都沒有的帳戶」，哪個寫法對？

  • LEFT JOIN transactions t ON … WHERE t.tx_id = NULL
  • JOIN transactions t ON … WHERE t.tx_id IS NULL
  • LEFT JOIN transactions t ON … AND t.tx_id IS NULL（條件寫在 ON）
  • LEFT JOIN transactions t ON … WHERE t.tx_id IS NULL

LEFT JOIN 讓沒交易的帳戶補一列 NULL，再用 IS NULL 挑出來，實跑回 106。= NULL 永遠不成立（0 列）；內連接根本沒有補 NULL 的列（0 列）；把 IS NULL 放進 ON 只是讓所有帳戶都配不到，6 個帳戶全部回來。手冊用 LEFT JOIN … WHERE 右表.id IS NULL 這個寫法示範怎麼找「沒有對應資料」的列。

  • 直接寫 FULL OUTER JOIN，MySQL 8.4 支援
  • 寫 FULL JOIN，MySQL 只是不認 OUTER 這個字
  • LEFT JOIN 再 UNION ALL 右表多出來的列
  • 改用 CROSS JOIN 再加 WHERE

查詢裡再放查詢

子查詢對 JOIN、EXISTS 對 IN，以及 NOT IN 的 NULL 陷阱

子查詢在〈SQL 三種子語言：DDL、DML、DQL〉看過最簡單的一種：算出一個值給外層比較。這種只回一個值的叫純量子查詢：

SELECT tx_id, account_id, amount
FROM transactions
WHERE tx_type = 'DEPOSIT'
  AND amount > (SELECT AVG(amount) FROM transactions WHERE tx_type = 'DEPOSIT')
ORDER BY tx_id;
+-------+------------+--------+
| tx_id | account_id | amount |
+-------+------------+--------+
|     1 |        101 |   5000 |
|     7 |        104 |   8000 |

NOT IN 遇到 NULL：一列都不回

題目反過來：找出「從來沒當過轉帳對象」的帳戶。轉帳對象是 101、102、103、104，答案應該是 105 和 106：

SELECT account_id, owner
FROM accounts
WHERE account_id NOT IN (SELECT counterparty_id FROM transactions);
Empty set (0.00 sec)

一列都沒有。子查詢回傳的 counterparty_id 裡有 8 個 NULL（存提款），NOT IN 碰到 NULL 就壞了。把同樣的判斷拆開來看：

SELECT 105 NOT IN (102, 101, 104, 103)       AS no_null,
       105 NOT IN (102, 101, 104, 103, NULL) AS with_null,
       102 NOT IN (102, 101, 104, 103, NULL) AS found_102;
+---------+-----------+-----------+
| no_null | with_null | found_102 |
+---------+-----------+-----------+
|       1 |      NULL |         0 |
+---------+-----------+-----------+
1 row in set (0.00 sec)

105 不在 (102, 101, 104, 103) 裡，結果是 1（TRUE）；清單多一個 NULL，結果變成 NULL。

手冊寫：「為了符合 SQL 標準，IN() 不只在左邊是 NULL 時回傳 NULL，在清單裡找不到相符的值、而且清單裡有 NULL 時，也回傳 NULL」（IN() returns NULL not only if the expression on the left hand side is NULL, but also if no match is found in the list and one of the expressions in the list is NULL）出處；NOT IN 就是 NOT (IN)，NOT NULL 還是 NULL。WHERE 只留結果是 TRUE 的列，NULL 不算，所以每一列都被濾掉。

PostgreSQL 文件也是同樣的規則：「沒有相等的值、而且右邊至少有一列是 null 時，NOT IN 的結果是 null，不是 true」（the result of the NOT IN construct will be null, not true），PostgreSQL 18 實跑同一段一樣是 0 列。出處

兩種修法：子查詢自己排除 NULL，或改用 NOT EXISTS。NOT EXISTS 只看「有沒有配得到的列」，NULL 配不到任何帳號，不會干擾：

SELECT account_id, owner
FROM accounts
WHERE account_id NOT IN (SELECT counterparty_id FROM transactions
                         WHERE counterparty_id IS NOT NULL)
ORDER BY account_id;
+------------+-----------+
| account_id | owner     |
+------------+-----------+
|        105 | 李志明    |
|        106 | 黃小華    |
+------------+-----------+
2 rows in set (0.00 sec)
SELECT a.account_id, a.owner
FROM accounts a
WHERE NOT EXISTS (SELECT 1 FROM transactions t WHERE t.counterparty_id = a.account_id)
ORDER BY a.account_id;
+------------+-----------+
| account_id | owner     |
+------------+-----------+
|        105 | 李志明    |
|        106 | 黃小華    |
+------------+-----------+
2 rows in set (0.00 sec)

只問「有沒有」用 IN 或 EXISTS，JOIN 會因為多筆配對而重複；NOT IN 的子查詢裡只要有一個 NULL 就一列都不回，改用 NOT EXISTS 或先排除 NULL

GROUP BY 與 HAVING 的幾個規則

GROUP BY 把同一個值的列併成一組，NULL 也自成一組：

SELECT branch_id, COUNT(*) AS accounts
FROM accounts
GROUP BY branch_id
ORDER BY branch_id;
+-----------+----------+
| branch_id | accounts |
+-----------+----------+
|      NULL |        1 |
|         4 |        2 |
|         5 |        1 |
|         6 |        2 |
+-----------+----------+
4 rows in set (0.00 sec)

規則一：SELECT 裡的欄位，要嘛在 GROUP BY 裡，要嘛包在聚合函式裡。MySQL 8.4 預設開著 ONLY_FULL_GROUP_BY，手冊說它會拒絕「SELECT 清單、HAVING 條件或 ORDER BY 清單參考到沒聚合、又不在 GROUP BY 裡、也不在功能上依賴於它們的欄位」的查詢（MySQL rejects queries for which the select list, HAVING condition, or ORDER BY list refer to nonaggregated columns that are neither named in the GROUP BY clause nor are functionally dependent on them）。出處 一個分行有好幾個戶名，挑哪一個？資料庫不替你猜：

SELECT branch_id, owner, COUNT(*) AS accounts
FROM accounts
GROUP BY branch_id;
ERROR 1055 (42000) at line 1: Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'bank.accounts.owner' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by

「功能上依賴」的意思是：知道 GROUP BY 的欄位，就能唯一決定那個欄位。依帳戶的主鍵分組時，戶名一定只有一個，所以可以直接寫：

SELECT a.account_id, a.owner, COUNT(t.tx_id) AS tx
FROM accounts a
LEFT JOIN transactions t ON t.account_id = a.account_id
GROUP BY a.account_id
ORDER BY a.account_id;

|        101 | 王小明    |  4 |
|        102 | 陳小美    |  3 |
|        103 | 林大同    |  2 |
|        104 | 張美玲    |  2 |
|        105 | 李志明    |  1 |
|        106 | 黃小華    |  0 |
+------------+-----------+----+
6 rows in set (0.00 sec)

規則二：WHERE 篩列、HAVING 篩組，聚合條件只能寫在 HAVING。手冊：「HAVING 子句可以參考聚合函式，WHERE 子句不行」（The HAVING clause can refer to aggregate functions, which the WHERE clause cannot）。出處 把 SUM 寫進 WHERE 是錯誤：

FROM transactions
WHERE SUM(amount) >= 5000
GROUP BY account_id;

FROM transactions
WHERE tx_type = 'DEPOSIT'
GROUP BY account_id

ORDER BY account_id;

+------------+----------+
|        101 |     8000 |
|        104 |     8000 |
+------------+----------+
2 rows in set (0.00 sec)

WHERE 先把非存款的列排除，GROUP BY 再分組，HAVING 最後留下總和至少 5000 的組。規則三，跨資料庫的差異：HAVING 能不能用 SELECT 的別名。MySQL 可以，手冊說這是「MySQL 的延伸」（The MySQL extension permits the use of an alias in the HAVING clause for the aggregated column）出處：

FROM transactions

HAVING deposits >= 5000

+------------+----------+
|        101 |     8000 |
|        104 |     8000 |

不併列，也能算整組的事

視窗函式：ROW_NUMBER、RANK、DENSE_RANK、SUM OVER、LAG

GROUP BY 會把一組併成一列；視窗函式（window function）對「跟目前這列有關的一群列」做計算，但每一列都留著。MySQL 手冊說視窗函式不像聚合函式那樣把列併起來，「而是對每一列各產生一個結果」（Instead, they produce a result for each row）。出處 寫法是函式後面接 OVER (…)：PARTITION BY 決定怎麼分組（不寫就是全部一組），ORDER BY 決定組內順序。

三種排名：同分怎麼辦

SELECT tx_id, account_id, amount,
       ROW_NUMBER() OVER (ORDER BY amount DESC, tx_id) AS rn,
       RANK()       OVER (ORDER BY amount DESC)        AS rnk,
       DENSE_RANK() OVER (ORDER BY amount DESC)        AS dense
FROM transactions
WHERE tx_type = 'DEPOSIT'
ORDER BY amount DESC, tx_id;
+-------+------------+--------+----+-----+-------+
| tx_id | account_id | amount | rn | rnk | dense |
+-------+------------+--------+----+-----+-------+
|     7 |        104 |   8000 |  1 |   1 |     1 |
|     1 |        101 |   5000 |  2 |   2 |     2 |
|     5 |        103 |   3000 |  3 |   3 |     3 |
|     6 |        102 |   3000 |  4 |   3 |     3 |
|    10 |        101 |   3000 |  5 |   3 |     3 |
|    11 |        105 |    500 |  6 |   6 |     4 |
+-------+------------+--------+----+-----+-------+
6 rows in set (0.00 sec)

三筆 3000 同分。

  • ROW_NUMBER 硬是給 3、4、5，同分誰前誰後由 ORDER BY 決定，這裡加了 tx_id 當第二排序鍵；手冊提醒「沒有 ORDER BY，列的編號是不確定的」（Without ORDER BY, row numbering is nondeterministic）出處；有 ORDER BY 但同分時，PostgreSQL 文件寫明同分的列「以不指定的順序編號」（with tied rows numbered in an unspecified order）出處，所以要自己補一個能分出先後的欄位。
  • RANK 給同分的列相同名次（Peers are considered ties and receive the same rank.），名次＝比它大的筆數＋1，所以 500 是第 6 名。
  • DENSE_RANK「同分給相同名次，但下一個名次只加一」（the next higher value has a rank one greater），500 是第 4 名。出處

PostgreSQL 文件的說法一樣：rank 有間隔，dense_rank「等於是在數有幾組同分」（this function effectively counts peer groups）。出處

聚合函式加上 OVER：每列都看得到整組的總和

SELECT tx_id, account_id, amount,
       SUM(amount) OVER (PARTITION BY account_id) AS account_total,
       COUNT(*)    OVER (PARTITION BY account_id) AS account_tx

ORDER BY 進了 OVER：預設框架會把同分的列算在一起

OVER 裡寫了 ORDER BY，SUM 就變成「從頭加到目前這列」的累加。但「目前這列」到哪裡為止有個細節。手冊：沒寫框架（frame，算這一列時要納入哪幾列）時，有 ORDER BY 的預設框架是「從分組的第一列到目前這列，包含目前這列的所有同分列（依 ORDER BY 相等的列）」（including all peers of the current row），等於 RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW。出處 交易 2 和 3 剛好同一時間（14:30）：

SELECT tx_id, tx_time, amount,
       SUM(amount) OVER (ORDER BY tx_time)                 AS by_range,
       SUM(amount) OVER (ORDER BY tx_time
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS by_rows
FROM transactions
WHERE tx_id <= 4
ORDER BY tx_time, tx_id;

| tx_id | tx_time             | amount | by_range | by_rows |
+-------+---------------------+--------+----------+---------+
|     1 | 2026-10-01 09:00:00 |   5000 |     5000 |    5000 |
|     2 | 2026-10-01 14:30:00 |  -1200 |     5000 |    3800 |
|     3 | 2026-10-01 14:30:00 |   1200 |     5000 |    5000 |
|     4 | 2026-10-02 10:00:00 |   -800 |     4200 |    4200 |

4 rows in set (0.00 sec)

by_range 在交易 2 那列就已經是 5000，因為同時間的交易 3 被當成同分列一起加了進去；by_rows 用 ROWS 一列一列算，交易 2 那列才是 3800。做累計餘額時，要嘛 ORDER BY 加上能分出先後的欄位（例如 tx_time, tx_id），要嘛明寫 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW。

視窗函式不能放 WHERE

SELECT tx_id, account_id, amount,
       ROW_NUMBER() OVER (PARTITION BY account_id ORDER BY tx_time DESC) AS rn
FROM transactions

手冊：「視窗函式只能出現在 SELECT 清單與 ORDER BY 子句」（Window functions are permitted only in the select list and ORDER BY clause）。出處 原因跟處理順序有關：視窗函式在 WHERE、GROUP BY、HAVING 之後才算，PostgreSQL 文件說視窗函式看到的是「FROM 子句產生、再經過 WHERE、GROUP BY、HAVING 篩過的虛擬資料表」（the “virtual table” produced by the query's FROM clause as filtered by its WHERE, GROUP BY, and HAVING clauses if any），所以它們「在 GROUP BY、HAVING 和 WHERE 子句裡是禁止的」（They are forbidden elsewhere, such as in GROUP BY, HAVING and WHERE clauses）。出處 要拿排名去篩，就把它包進子查詢或 CTE，在外層篩，下一段的經典題全部都是這個模式。

FROM phone_updates p

    SELECT update_id,

    FROM phone_updates

把長查詢拆成有名字的幾段

CTE 與遞迴 CTE

CTE（common table expression，共用資料表運算式）就是用 WITH 名稱 AS (查詢) 先替一段查詢取名字，後面像資料表一樣用。手冊：CTE 是「只存在於單一陳述式範圍內、有名字的暫時結果集，之後可以在那個陳述式裡被參考好幾次」（a named temporary result set that exists within the scope of a single statement and that can be referred to later within that statement, possibly multiple times）。出處 上一段的連續登入已經用過兩個 CTE 串起來；下面的 deposits 被用了兩次，一次接帳戶、一次算平均：

WITH deposits AS (
    SELECT account_id, SUM(amount) AS total
    FROM transactions
    WHERE tx_type = 'DEPOSIT'
    GROUP BY account_id
)
SELECT a.owner, b.name AS branch, d.total
FROM deposits d
JOIN accounts a ON a.account_id = d.account_id
LEFT JOIN branches b ON b.branch_id = a.branch_id
WHERE d.total > (SELECT AVG(total) FROM deposits)
ORDER BY d.total DESC, a.owner;
+-----------+--------------+-------+
| owner     | branch       | total |
+-----------+--------------+-------+
| 張美玲    | 高雄分行     |  8000 |
| 王小明    | 台北分行     |  8000 |
+-----------+--------------+-------+
2 rows in set (0.00 sec)

存款總和的平均是 4500，高於平均的是張美玲與王小明。不用 CTE 也寫得出來，但同一段子查詢要寫兩次，讀的人也得自己比對兩段是不是一樣。

遞迴 CTE：走一棵樹

CTE 可以參考自己，就是遞迴 CTE，手冊說常見用途是「產生序列，以及走訪階層或樹狀資料」（series generation and traversal of hierarchical or tree-structured data）。結構是兩段用 UNION ALL 接起來：第一段（非遞迴部分）給起點，第二段（遞迴部分）拿上一輪的結果再往下找一層，直到找不到新的列為止。出處 分行表的 parent_id 就是一棵樹，從總行往下走：

WITH RECURSIVE tree AS (
    SELECT branch_id, name, parent_id, 1 AS lvl, name AS path
    FROM branches
    WHERE parent_id IS NULL
    UNION ALL
    SELECT b.branch_id, b.name, b.parent_id, t.lvl + 1, CONCAT(t.path, ' > ', b.name)
    FROM branches b
    JOIN tree t ON b.parent_id = t.branch_id
)
SELECT branch_id, lvl, path FROM tree ORDER BY path;
ERROR 1406 (22001) at line 1: Data too long for column 'path' at row 1

出錯了。手冊寫明：「CTE 結果欄位的型別，只從非遞迴部分的欄位型別推斷」（The types of the CTE result columns are inferred from the column types of the nonrecursive SELECT part only）。起點的 path 來自 name，是 VARCHAR(20)；往下串到「總行 > 北區營運處 > 台北分行 > 信義簡易分行」超過 20 個字，嚴格模式下就是這個錯誤。手冊給的修法是在非遞迴部分用 CAST 把欄位放寬：出處

WITH RECURSIVE tree AS (
    SELECT branch_id, name, parent_id, 1 AS lvl, CAST(name AS CHAR(200)) AS path
    FROM branches
    WHERE parent_id IS NULL
    UNION ALL
    SELECT b.branch_id, b.name, b.parent_id, t.lvl + 1, CONCAT(t.path, ' > ', b.name)
    FROM branches b
    JOIN tree t ON b.parent_id = t.branch_id
)
SELECT branch_id, lvl, path FROM tree ORDER BY path;
+-----------+------+--------------------------------------------------------------+
| branch_id | lvl  | path                                                         |
+-----------+------+--------------------------------------------------------------+
|         1 |    1 | 總行                                                         |
|         2 |    2 | 總行 > 北區營運處                                            |
|         4 |    3 | 總行 > 北區營運處 > 台北分行                                 |
|         7 |    4 | 總行 > 北區營運處 > 台北分行 > 信義簡易分行                  |
|         5 |    3 | 總行 > 北區營運處 > 新竹分行                                 |

|         6 |    3 | 總行 > 南區營運處 > 高雄分行                                 |

遞迴 CTE 產生日期序列，以及停不下來的時候

題目：10 月 1 日到 7 日，每天各有幾次登入，沒人登入的日子也要列出來。資料表裡沒有「沒人登入的日期」，所以先用遞迴 CTE 產生七天，再 LEFT JOIN 登入紀錄：

WITH RECURSIVE dates AS (
    SELECT DATE '2026-10-01' AS d
    UNION ALL
    SELECT d + INTERVAL 1 DAY FROM dates WHERE d < '2026-10-07'
)
SELECT dates.d, COUNT(l.account_id) AS logins
FROM dates
LEFT JOIN logins l ON DATE(l.login_at) = dates.d
GROUP BY dates.d
ORDER BY dates.d;

| d          | logins |

| 2026-10-01 |      2 |
| 2026-10-02 |      2 |
| 2026-10-03 |      3 |

WITH RECURSIVE n AS (
    SELECT 1 AS i
    UNION ALL
    SELECT i + 1 FROM n
)
SELECT COUNT(*) FROM n;

重點整理

  • INNER JOIN 只留配得到的，LEFT JOIN 留左表全部、配不到補 NULL；MySQL 沒有 FULL OUTER JOIN，用 LEFT JOIN 加 UNION ALL 拼；RIGHT JOIN 改寫成 LEFT JOIN 比較好讀。
  • 外連接的右表條件放 ON（連接前處理），放 WHERE（連接後處理）會把補 NULL 的列濾掉；外連接後數右表要用 COUNT(右表欄位)；兩個一對多同時接會放大加總。
  • NULL 跟任何值比較都不是 TRUE；NOT IN 的子查詢裡有一個 NULL 就一列都不回，改用 NOT EXISTS 或先排除 NULL；只問「有沒有」用 IN、EXISTS，JOIN 會重複。
  • SELECT 的欄位要在 GROUP BY 裡、被聚合，或由分組欄位唯一決定；聚合條件寫 HAVING；HAVING 用別名只有 MySQL 認。
  • 視窗函式不併列；ROW_NUMBER 同分硬排（要加第二排序鍵）、RANK 跳號、DENSE_RANK 不跳號；OVER 裡有 ORDER BY 的預設框架會把同分列一起加；LAG 第一列預設 NULL；視窗函式不能放 WHERE，包一層子查詢再篩。
  • 經典題的骨架：每組第 N 名與去重都是「子查詢排名、外層篩」；連續日期是去重後「日期減序號」；累計是 SUM OVER；第二高沒有時要 NULL 就包成純量子查詢。
  • CTE 替子查詢取名、可用多次；遞迴 CTE 要寫 RECURSIVE、要有停止條件（MySQL 預設 1000 層），欄位型別看起點，字串會變長先 CAST。
