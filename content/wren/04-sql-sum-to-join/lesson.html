要回答的問題

這個欄位到底是怎麼算出來的

顧客表有一欄 customer_lifetime_value，名字看起來是「這位顧客總共消費多少」。它是把所有訂單加起來，還是只算已完成的訂單？欄位名稱看不出來，要用資料驗證。下面這段 SQL 就是在做這件事：

select
  count(*) filter (where abs(c.customer_lifetime_value - o.全部) < 0.001)     as 等於全部,
  count(*) filter (where abs(c.customer_lifetime_value - o.只算完成) < 0.001) as 等於只算完成,
  count(*) filter (where c.customer_lifetime_value is null)                  as 是NULL
from customers c
left join (
    select customer_id,
           sum(amount)                                     as 全部,
           sum(amount) filter (where status = 'completed') as 只算完成
    from orders
    group by customer_id
) o on o.customer_id = c.customer_id;

一次看整段會看不懂。讀法是從最裡面的括號開始，一層一層往外。先用一份很小的假資料說明每個動作。

sum、group by、filter

第一層：每位顧客的兩種加總

sum 把一欄的很多列加成一個數字。count（數有幾列）、avg（平均）、max（最大值）是同一類，叫做聚合函式（aggregate function）。

select sum(amount) from orders;            -- 35

group by 先把指定欄位相同的列放成一組，再對每一組各算一次：

select customer_id, sum(amount) as 全部
from orders
group by customer_id;
customer_id全部怎麼來的
115101 的 10 加 102 的 5
220103 的 20

as 全部 是替算出來的欄位取名字（別名）。

filter (where …) 寫在聚合函式後面，讓這一個聚合只算符合條件的列。出處 同一次查詢就能並排算出兩種加總：

select customer_id,
       sum(amount)                                     as 全部,
       sum(amount) filter (where status = 'completed') as 只算完成
from orders
group by customer_id;
customer_id全部只算完成
11510
22020

PostgreSQL 也有 filter 這個寫法。出處 資料庫不支援時，用 sum(case when status = 'completed' then amount end) 可以得到同樣的結果。

left join 與 inner join

第二層：接回顧客表

把上一步的結果用 customer_id 接到顧客表，就能並排比較。括號裡的查詢叫子查詢，後面的 o 是替它取的短名字，c 是顧客表的短名字；on 後面是兩邊怎麼對。

select c.customer_id, c.customer_lifetime_value, o.全部, o.只算完成
from customers c
left join ( …第一層的查詢… ) o on o.customer_id = c.customer_id;

3NULLNULLNULL

Cat 在訂單那邊找不到對應的列。兩種 join 對這種情況的處理不同：出處

inner join
  • 只留兩邊都對得到的列。
  • Cat 整列消失。
  • 結果是 2 列。
left join
  • 左邊的表每一列都保留。
  • 右邊對不到的欄位填 NULL。
  • 結果是 3 列，看得到 Cat。

想知道「沒下過訂單的顧客，這一欄是什麼」，就必須用 left join。到這一層，用眼睛掃過結果就已經能看出 customer_lifetime_value 跟哪一欄一樣。

100 位顧客裡有 38 位從沒下過訂單。把顧客表用 inner join 接上「每位顧客的訂單加總」，會回傳幾列？

  • 100 列
  • 38 列
  • 62 列
  • 138 列

inner join 只留兩邊都對得到的列，沒下過訂單的 38 位在加總結果裡沒有對應的列，所以被丟掉。用 left join 才會是 100 列。

abs 與 count(*) filter

第三層：把「看起來一樣」變成數字

列數一多就不能用眼睛看，要讓資料庫數出「有幾列是一樣的」。

  • count(*) filter (where 條件)：數符合條件的列有幾列。
  • abs(a - b) < 0.001：金額欄位的型別是浮點數（DOUBLE），電腦存小數會有很小的誤差，兩個看起來相同的數字用 = 比可能不相等。所以改成看差距夠不夠小。
  • abs 是絕對值，把負號拿掉。不加的話，差距是 −50 的列也會符合 < 0.001，就數錯了。

用假資料算 等於全部 那一欄：

顧客lifetime value − 全部算不算進去
Amy15 − 15 = 0算
Bob20 − 20 = 0算
CatNULL − NULL = NULL不算。NULL 跟任何東西比較，結果都不會成立

對真正的資料（100 位顧客、99 筆訂單）跑開頭那段 SQL，結果是：

等於全部等於只算完成是NULL
623538

怎麼讀：100 位裡 38 位是 NULL，剩下 62 位全部都等於「全部訂單加總」，沒有例外。所以這一欄是所有訂單的加總，退貨的訂單也算在內。那 35 位同時也等於「只算完成」，是因為他們的訂單剛好全部都是已完成，兩種加總算出來一樣；三個數字加起來超過 100 就是這個原因。

欄位怎麼算的，看名字會猜錯；寫一段 SQL 讓數字回答

from、where、group by、select

SQL 不是照你寫的順序執行

書寫時 select 在最前面，實際執行時它幾乎排最後：出處

順序子句做什麼
1from、join決定資料從哪些表來、怎麼接
2where一列一列篩選
3group by分組，計算聚合函式
4having篩選分組之後的結果
5select算出要輸出的欄位、取別名
6order by排序

這個順序解釋了下面這段為什麼不能跑：

select sum(credit_card_amount + coupon_amount) as 加總
from orders
where 加總 = amount;
-- Binder Error: WHERE clause cannot contain aggregates!

where 在分組和 select 之前執行，那時候還沒有任何聚合的結果，所以 where 裡不能使用 sum 這類聚合函式算出來的值。要篩選聚合後的結果用 having；要「一列一列比，再數有幾列符合」，用 count(*) filter：

select
  count(*) as 訂單數,
  count(*) filter (
    where abs(
      (credit_card_amount + coupon_amount + bank_transfer_amount + gift_card_amount)
      - amount
    ) < 0.001
  ) as 相等的筆數
from orders;              -- 99、99

兩個數字一樣，代表每一筆訂單的 amount 都等於四種付款方式的加總。括號多的時候像這樣一層一行寫，哪個右括號對哪個左括號才看得清楚。

想問的用什麼
全部加起來是多少sum(欄位)
有幾列符合某個條件count(*) filter (where 條件)
只留某些列再算where 條件
只留加總超過某個數的組having sum(欄位) > 數字

NULL、avg、coalesce

NULL 會悄悄改變平均值

NULL 代表「沒有值」，不是 0。sum、avg、max、count(欄位) 這類聚合函式會跳過 NULL；count(*) 數的是列數，不受影響。出處 所以同一個問題，分母可能不一樣：

寫法分母回答的問題結果
avg(customer_lifetime_value)62（跳過 38 個 NULL）有消費的顧客，平均消費多少26.97
avg(coalesce(customer_lifetime_value, 0))100全部顧客，平均消費多少16.72

同一份資料，兩種寫法差了十塊錢。

coalesce(x, 0) 的意思是：x 是 NULL 就當成 0，不是 NULL 就用原本的值。兩種寫法都沒有錯，差別在問的是哪一個問題；寫之前要先確定分母該是誰。

Catalog Error、Binder Error

從錯誤類型判斷錯在哪

DuckDB 的錯誤訊息開頭會寫類型，先看類型就知道往哪個方向找。

SQL Error: Catalog Error: Scalar Function with name awbs does not exist!
Did you mean "abs"?
SQL Error: Binder Error: No function matches the given name and argument types
'abs(BOOLEAN)'. You might need to add explicit type casts.
類型意思先檢查什麼
Catalog Error你寫的表名或函式名，資料庫的清單裡沒有表名、函式名有沒有打錯字。訊息常附一個最接近的建議
Binder Error表和函式都找得到，但這句 SQL 對不起來：欄位名在 from 的表裡找不到、傳進去的型別不對，或放在不能放的位置（例如聚合函式寫進 where）欄位名、括號的位置、子句的位置。訊息會寫出實際收到的型別

第二個錯誤的原因是括號放錯：

  • ✗ abs(a - b < 0.001) → 先算 a - b < 0.001 得到真或假（BOOLEAN），再對真假取絕對值
  • ✓ abs(a - b) < 0.001 → 先取絕對值，再跟 0.001 比

訊息下方用 ^ 標出的位置，就是資料庫認為出錯的那一段。

重點整理

  • 多層的 SQL 從最裡面的括號讀起，每一層可以單獨拿出來跑。
  • group by 分組後各算一次；filter (where …) 讓單一個聚合只算符合條件的列。
  • left join 保留左表每一列，對不到的填 NULL；inner join 會把對不到的列丟掉。
  • 浮點數用 abs(a - b) < 很小的數 比較，不用 =。
  • 執行順序是 from、where、group by、having、select、order by，所以 where 裡不能用聚合函式。
  • sum、avg 這類聚合函式跳過 NULL；要把 NULL 當 0 算，用 coalesce(x, 0)。
  • Catalog Error 先查表名、函式名有沒有打錯；Binder Error 先查欄位名、型別、括號與子句的位置。
