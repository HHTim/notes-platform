validate、build、memory index

寫完檔案之後的三個指令

模型檔、關聯檔、規則檔都是給人編輯的文字檔。要讓 Wren 真的用它們回答問題，還要在專案資料夾裡執行三個指令：

指令做什麼產出
wren context validate檢查專案：YAML 的結構對不對、關聯指到的模型存不存在只印結果，不產生檔案
wren context build編譯：把分散的 YAML 檔合成一個 JSON 檔，給 Wren 的引擎讀target/mdl.json
wren memory index建索引：把模型、欄位、關聯的說明轉成向量，之後可以用意思搜尋.wren/memory/
編譯把人寫的檔案轉成程式讀的格式。這裡是把好幾個 YAML 檔合成一個 JSON 檔。
引擎Wren 裡負責把 SQL 翻譯成資料庫能執行的版本的那一部分。它讀的是 target/mdl.json，不是 YAML。
索引為了找得快而另外整理的一份資料。這裡存的是向量，由 LanceDB 保管。
dry-plan只翻譯 SQL、不連資料庫執行的指令，用來看引擎實際會送出什麼。

模型檔或關聯檔改過之後，這三個指令要照順序重跑。規則檔改過之後，索引也要重建。出處

改 YAML → validate → build → memory index

wren context validate

檢查：格式對了，不代表內容對

$ wren context validate
Valid — 2 models, 0 views, 1 relationships.
  • 2 models：customers 與 orders 兩個模型。
  • 0 views：view 是事先寫好、取了名字的查詢，這個專案沒有用到。
  • 1 relationships：orders_customers 這一條關聯。

數字要跟自己寫的檔案對得起來。寫了兩個模型卻只印 1 models，代表有一個檔案放錯位置或沒有被讀到。

Valid 只代表檔案的結構可以用。說明裡寫的筆數對不對、規則檔跟模型檔有沒有互相矛盾，它都不會檢查。

wren context build

編譯：產生 target/mdl.json

$ wren context build
Built: 2 models, 0 views → /Users/tim/proj/wren-lab/jaffle-wren/target/mdl.json

Next: wren --sql 'SELECT ...' to query your data.

mdl.json 是把兩個模型檔、關聯檔和專案設定合在一起的單一檔案，開頭長這樣：

{"catalog": "wren", "schema": "public",
 "models": [{"name": "customers",
             "properties": {"description": "一列是一位顧客，共 100 位，…"},
             "tableReference": {"catalog": "jaffle_shop", "schema": "main", "table": "customers"},
             "columns": [{"name": "customer_id", "type": "INTEGER", "notNull": true, "isPrimaryKey": true, …
  • 內容跟 YAML 相同，只是換了格式；欄位名稱從 table_reference 這種底線寫法變成 tableReference。
  • 不要手動改它。下次編譯會整份重新產生，要改就改 YAML。
  • 不進 Git。專案的 .gitignore 已經把 target/ 排除，因為它隨時可以從 YAML 重新產生。

之後的 wren dry-plan、wren --sql、wren memory index 預設讀的都是這個檔案。改了 YAML 卻沒有重新編譯，它們用的還是舊的內容。

在 orders 的模型檔新增一個欄位之後，直接執行 wren --sql 查這個欄位。會怎樣？

  • 查得到，Wren 每次查詢都會重新讀 YAML
  • 查得到，但速度比較慢
  • 引擎讀的是舊的 target/mdl.json，裡面還沒有這個欄位
  • YAML 檔會被還原成上次編譯時的內容

引擎只讀編譯後的 mdl.json。改了 YAML 要先 wren context build，新的內容才會生效。

wren memory index 與 wren memory status

建索引：19 和 7 是怎麼來的

$ wren memory index
Indexed 19 schema items, 7 seed queries.
  • 19 schema items：2 個模型、16 個欄位（customers 7 個、orders 9 個）、1 條關聯，加起來 19。每一項連同它的說明各轉成一筆向量。
  • 7 seed queries：Wren 照模型的結構自動產生的 7 組範例問答，例如問句 List all customers 配上 SELECT * FROM customers LIMIT 100。它們是套句型產生的，目的是讓記憶功能一開始不是空的。

用 wren memory status 確認索引的狀態：

$ wren memory status
Backend: lancedb
  embeddings: sentence-transformers (paraphrase-multilingual-MiniLM-L12-v2)
  query_history: 7 rows
  schema_items: 19 rows
這一行意思
Backend: lancedb索引存在 LanceDB。沒裝 memory 那組 extras 時，這裡不會是 lancedb
embeddings用哪個嵌入模型把文字轉成向量
query_history: 7 rows問答有 7 組，目前全是自動產生的範例
schema_items: 19 rows模型、欄位、關聯共 19 項

索引放在專案資料夾裡的 .wren/memory/。它可以從專案的檔案重新產生，所以不進 Git，換一台電腦要重建一次。出處

wren dry-plan

先看翻譯，不連資料庫

在真正的流程裡，SQL 是大型語言模型讀完規則和模型說明之後寫的。自己手寫一次，才看得到中間每一步發生什麼事。照上一課的規則，「營收多少」的 SQL 是：

SELECT sum(amount) FROM orders WHERE status = 'completed'

這段 SQL 裡的 orders 是模型的名字，不是資料庫的表名。這種用模型名字寫的 SQL 叫語意 SQL，要經過引擎翻譯才能送進資料庫。wren dry-plan 只做翻譯、把結果印出來，不連資料庫：出處

$ wren dry-plan --sql "SELECT sum(amount) FROM orders WHERE status = 'completed'"
WITH orders AS (
  SELECT "wren_src_orders".amount AS amount, "wren_src_orders"."status" AS status
  FROM (
    SELECT orders.amount, orders."status"
    FROM (
      SELECT __source.amount AS amount, __source."status" AS "status"
      FROM jaffle_shop."main".orders AS __source
    ) AS orders
  ) AS "wren_src_orders"
)
SELECT SUM(amount) FROM orders WHERE status = 'completed'

實際的輸出是一整行，這裡為了好讀加了換行與縮排，內容沒有更動。

由內往外讀，有三個地方值得看：

  • 最內層的 FROM jaffle_shop."main".orders：模型名字 orders 被換成資料庫真正的位置，三層名稱就是模型檔 table_reference 填的 catalog、schema、table。
  • 只挑了 amount 和 status：模型有 9 個欄位，這一題只用到 2 個，引擎就只跟資料庫要這 2 個。
  • 最後一行跟自己寫的幾乎一樣：引擎用 WITH 先定義出一張叫 orders 的暫時的表，原本的 SQL 接在後面，查的是這張暫時的表。

因為所有查詢都要經過這一層翻譯，SQL 裡只能用模型檔定義過的模型。沒有寫成模型的表，在翻譯這一步就會被擋下來：

$ wren dry-plan --sql "SELECT * FROM raw_orders"
Error: [INVALID_SQL] Error during planning: table 'wren.public.raw_orders' not found phase=SQL_PLANNING

錯誤訊息裡的 wren.public 是 wren_project.yml 裡 Wren 內部用的那組名稱：引擎是在自己的模型清單裡找 raw_orders，找不到就停，不會去問資料庫有沒有這張表。

把模型檔 table_reference 的 table 從 orders 改成 orders_v2，重新編譯之後再執行同一段 wren dry-plan。輸出會有什麼不同？

  • 最內層變成 FROM jaffle_shop."main".orders_v2，其他地方不變
  • 最後一行的 FROM orders 變成 FROM orders_v2
  • 完全一樣，因為沒有連資料庫
  • 報錯，因為資料庫裡沒有 orders_v2 這張表

dry-plan 不連資料庫，所以不會發現那張表不存在；它只照模型檔把名字換掉。模型的名字還是 orders，自己寫的那一段不用改。

執行時報 Could not set lock on file

wren dry-plan 不連資料庫，wren --sql 要連。圖形化工具（例如 DBeaver）用讀寫模式連著同一個 DuckDB 檔時，wren --sql 會報 Could not set lock on file。先在那個工具裡中斷連線，再執行一次。鎖的規則見第 3 課。

instructions、fetch、recall、store

AI 代理人的完整流程，和還沒做的部分

專案骨架裡的 AGENTS.md 是寫給 AI 代理人看的工作說明。它規定回答一個資料問題要走這幾步：

順序指令做什麼
開始前wren context instructions讀業務規則（一段對話裡的第一題才需要）
一wren memory fetch -q "問題"拿到跟問題有關的模型、欄位與說明
二wren memory recall -q "問題" --limit 3找以前問過、意思相近的問題和當時的 SQL
三寫 SQL用模型的名字寫，不用資料庫的表名
四wren --sql "…"經過語意層執行
五wren memory store --nl "問題" --sql "…"把確認正確的問答存起來

這個專案只有兩個模型，wren memory fetch 會把兩個模型的全部欄位與說明都印出來。wren memory recall -q "營收多少" 找回來的三筆都是自動產生的範例（例如 Total credit_card_amount in orders），沒有一筆跟營收有關，因為還沒有存過任何確認過的問答。

下面三件事在這個專案裡沒有實測，只列出它們的用途：

  • wren memory store：把問句和 SQL 寫成 knowledge/sql/ 裡的一個 Markdown 檔，同時更新索引，之後 recall 就找得到。出處
  • 用一組題目量準確率：準備一批問題和各自的正確答案，讓 AI 代理人逐題回答，算出答對的比例。改了規則或說明之後重跑，才知道是變好還是變壞。
  • MCP 串接：用 wren serve mcp 把 Wren 啟動成 MCP 伺服器，讓其他 AI 工具直接呼叫上面那些功能。需要 mcp 那組 extras。出處

重點整理

  • 模型檔或關聯檔改過之後，照順序重跑 wren context validate、wren context build、wren memory index。
  • Valid 只代表結構可以用；說明與規則的內容對不對，要自己查證。
  • 引擎讀的是編譯出來的 target/mdl.json，不是 YAML；它和 .wren/memory/ 的索引都能重新產生，不進 Git。
  • 19 項是 2 個模型、16 個欄位、1 條關聯；7 組問答是自動產生的範例。
  • 第一次建索引要下載嵌入模型，會等上幾分鐘；看最後一行判斷成功與否，警告不等於錯誤。
  • wren dry-plan 不連資料庫，只印出語意 SQL 被翻成什麼：模型名字換成 table_reference 的位置，只取用到的欄位；沒寫成模型的表會被擋下來。
  • 經過 Wren 執行的答案要跟直接查資料庫的答案核對；wren --sql 會被 DuckDB 的讀寫鎖擋住。
