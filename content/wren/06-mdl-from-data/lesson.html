讀完這課你會

  • 寫出一份模型檔 metadata.yml 與關聯檔
  • 分清 Wren 自己用的名稱與資料庫的三層名稱
  • 把欄位說明寫成「怎麼算的」而不是「代表什麼」
  • 用 SQL 驗證說明裡的每個數字

專案資料夾

語意層是一個資料夾

wren context init 會建出專案骨架。跟寫語意層最有關的是這幾個：

jaffle-wren/
├── wren_project.yml          專案設定：用哪個 profile、資料庫種類
├── models/
│   ├── customers/metadata.yml    一個模型一個資料夾
│   └── orders/metadata.yml
├── relationships.yml         模型之間怎麼接
└── knowledge/                業務規則、問題與 SQL 的範例

模型（model）是「希望 AI 使用的一張表」加上它的說明。模型不必把資料庫照抄一份：資料庫裡的原始表、中間過程的表不想讓 AI 用，就不寫模型。

wren_project.yml 裡有 catalog: wren、schema: public 兩行。這兩行是 Wren 內部替這個專案取的名稱，跟資料庫的 catalog、schema 沒有關係，保持預設值不要改。資料庫真正的位置寫在每個模型的 table_reference。出處

寫之前先看資料

三個欄位名稱回答不了的問題

範例資料是一家商店的顧客表（100 列）和訂單表（99 列）。出處 用 describe 看過欄位之後，有三件事從名稱看不出來：

問題怎麼找答案答案
customer_lifetime_value 是全部訂單加總，還是只算已完成的？寫 SQL 比對兩種加總全部訂單，退貨也算。沒下過單的 38 位是 NULL
orders.amount 跟四個付款方式的金額欄位是什麼關係？寫 SQL 數有幾筆相等99 筆全部相等，amount 是四個欄位的加總
算營收要排除哪些訂單狀態？資料查不出來業務定義，要問負責的人，另外寫成規則（見第 7 課）

前兩題的答案是事實，寫進模型檔的說明。第三題是決定，不寫在欄位說明裡。同一個狀態欄位，不同的問題可能要用不同的篩法，所以欄位說明只講每個值是什麼意思。

資料查得出來的寫進模型檔；要人決定的另外寫成規則

models/customers/metadata.yml

模型檔的格式

name: customers
properties:
  description: >-
    一列是一位顧客，共 100 位，包含從來沒下過單的顧客（38 位）。
    沒下過單的顧客，first_order、most_recent_order、number_of_orders、
    customer_lifetime_value 四欄都是 NULL，不是 0。
table_reference:
  catalog: jaffle_shop
  schema: main
  table: customers
columns:
  - name: customer_id
    type: INTEGER
    not_null: true
    is_primary_key: true
    properties:
      description: 顧客 ID，唯一識別每位顧客
  - name: customer_lifetime_value
    type: DOUBLE
    properties:
      description: >-
        這位顧客所有訂單的 orders.amount 加總，包含 returned 和 return_pending，
        沒有扣掉退貨，所以不是淨營收，也不是利潤。
        沒下過單是 NULL，不是 0：avg() 會跳過 NULL，
        問「全部顧客平均」要用 avg(coalesce(customer_lifetime_value, 0))。
primary_key: customer_id
欄位意思
name模型的名字。AI 寫 SQL 時用這個名字，可以跟資料庫的表名不同
properties.description寫給 AI 看的說明。AI 靠它判斷該用哪張表、哪個欄位
table_reference對應到資料庫的哪張表。DuckDB 的 catalog 填資料庫檔名去掉副檔名，schema 是 main
columns 的 type型別，照 describe 查到的填，不要用猜的
not_null、is_primary_key、primary_key主鍵：每一列都不同、而且不會是空的那個欄位

YAML 的三個規矩：

  • 縮排只能用空白，慣例每層兩格，同一層要對齊。
  • - 開頭是清單的一個項目。
  • 冒號後面空一格。

說明太長時用 >- 換行寫，讀進來會把換行接成空白，變回一整段。因為會接成一整段，>- 裡面不要用 - 開頭的清單，要列舉就用頓號。

說明怎麼寫

寫「怎麼算的」，不寫「代表什麼」

檢查的標準：一位只看得到這份檔案、看不到資料庫的新同事，問他「顧客平均消費多少」，他會不會算對？

寫法一
  • customer_lifetime_value：顧客對商店的總貢獻價值
  • 聽起來像扣掉退貨後的淨額，甚至像利潤。
  • 他會寫 avg(customer_lifetime_value)：退貨算進去了，分母也只有 62。
寫法二
  • 所有訂單的 orders.amount 加總，包含退貨；沒下過單是 NULL
  • 只有一種理解方式。
  • 他知道要排除退貨得改從訂單表算，要全部顧客平均得補 coalesce。

三個原則：

  • 寫怎麼算的。「總貢獻價值」每個人理解不同；「orders.amount 加總，包含退貨」不會。
  • 寫出不能用的情況和替代做法。AI 最常犯的錯是拿一個看起來像的欄位直接用。告訴它「這欄不是淨營收，要淨營收改從訂單表依狀態篩選」，它才會換一張表。
  • NULL 要寫出處理方式。只寫「注意 NULL」沒有用，直接寫 coalesce(x, 0)。

不需要每一欄都寫很長。first_name 寫「顧客的名字，例如 John」就夠了；舉一個實際的值，AI 就知道裡面放的是英文名字。力氣花在會被誤解的那幾欄。

寫錯的說明比沒寫更糟

每個數字都要有一段 SQL 支持

寫完顧客表，接著寫訂單表時，很容易沿用同一個句型：

description: >-
  一列是一筆訂單，共 100 筆，包含已退貨的訂單（5 筆）。
  已退貨的訂單，五個金額欄位都是 NULL，不是 0。

句型是對的，三個事實全錯：

寫的實際查到的
共 100 筆99 筆
已退貨 5 筆returned 4 筆、return_pending 2 筆
已退貨的訂單金額是 NULL五個金額欄位沒有任何 NULL，退貨的訂單照樣有金額

有人問「不含退貨的營收是多少」，AI 讀到這段說明就會寫：

select sum(amount) from orders where amount is not null;

六筆退貨訂單全部被算進去，而 AI 以為已經排除了。沒寫說明時，它至少會去看狀態欄位；寫錯了，它會很有把握地算錯。

避免的方法是寫一句、查一句。一段查詢就能把整段說明的數字一次驗完：

select count(*)                                                  as 筆數,
       count(*) filter (where status = 'returned')               as 已退貨,
       count(*) filter (where status = 'return_pending')         as 退貨中,
       count(*) filter (where amount is null)                    as 金額是NULL,
       min(order_date) as 最早, max(order_date) as 最晚
from orders;
-- 99、4、2、0、2018-01-01、2018-04-09

查證過的寫法：

description: >-
  一列是一筆訂單，共 99 筆，下單日期從 2018-01-01 到 2018-04-09。
  包含退貨相關的訂單：returned 4 筆、return_pending 2 筆。
  退貨的訂單金額照樣有值，不是 NULL；要排除退貨必須用 status 篩選。

訂單表的說明寫著「已退貨的訂單金額是 NULL」，實際上退貨訂單都有金額。這個錯誤最直接的後果是什麼？

  • Wren 讀檔時出錯，專案無法建置
  • AI 用 amount is not null 排除退貨，結果退貨全被算進去
  • AI 會拒絕回答跟金額有關的問題
  • 資料庫裡的退貨金額會被改成 NULL

說明只是文字，格式正確就能通過檢查，資料也不會被改動。危險在於 AI 會照著錯的說明寫出看似合理的 SQL。

列舉值、單位、反方向

訂單表還要寫清楚的三件事

  • 列舉值：狀態欄位只有五種值，每一種的意思都寫出來：placed（已下單，貨還沒離開倉庫）、shipped（已出貨，運送中）、completed（顧客已收到）、return_pending（顧客說要退，倉庫還沒收到）、returned（退貨已回到倉庫）。
  • 單位：金額是澳幣（AUD）。資料庫只存數字，不存單位。
  • 容易想錯的地方：折價券在這份資料裡算一種付款方式，所以 amount 包含折價券抵掉的部分，而那部分商店並沒有實際收到錢。

外鍵（這張表裡用來指到另一張表主鍵的欄位，例如訂單表的 customer_id）把兩個方向都寫出來：每筆訂單的 customer_id 都對得到一位顧客；反過來不成立，100 位顧客裡只有 62 位有訂單。

relationships.yml

關聯：告訴 AI 兩個模型怎麼接

relationships:
  - name: orders_customers
    models:
      - orders
      - customers
    join_type: MANY_TO_ONE
    condition: orders.customer_id = customers.customer_id
欄位意思
name這條關聯的名字，自己取
models哪兩個模型，順序要跟 join_type 的方向一致
join_typeMANY_TO_ONE：多筆訂單對到一位顧客。有外鍵的那一邊指向有主鍵的那一邊，就是多對一
condition怎麼對，就是 SQL 裡 on 後面那一段

關聯寫錯不會出錯，只會讓查出來的數字不對，所以條件要先用資料確認：外鍵的值是不是都能在另一張表找到。

generate-mdl 與 enrich-context

這些檔案是人寫，還是 AI 寫

Wren 的設計是 AI 先寫草稿、人確認，分成兩個階段，各有一份給 AI 代理人照著做的指南，用 wren skills get 名稱 可以印出來：

階段指南處理什麼誰擅長
結構generate-mdl表名、欄位、型別、主鍵、關聯AI。都能直接從資料庫查到
意思enrich-context列舉值的意思、單位、NULL 代表什麼、同義詞要靠人。資料庫裡沒有

enrich-context 有兩種進行方式：一次問人一個問題、每題先附上建議的答案；或是由 AI 自己推論後直接寫進去，最後交一份清單，標明每一條的把握程度與依據。

不管哪一種，人要做的事都一樣：AI 從欄位名稱推出「顧客的總消費價值」是合理的猜測，但要發現它其實包含退貨，得有人寫出那段比對的 SQL，並且判斷這樣算對不對。

讓 AI 寫結構和草稿，人把力氣花在驗證意思

重點整理

  • 一個模型一份 models/名稱/metadata.yml；只替希望 AI 使用的表寫模型。
  • wren_project.yml 的 catalog、schema 是 Wren 內部用的名稱，不要改；資料庫的位置寫在 table_reference。
  • 欄位說明寫怎麼算的、不能用的情況與替代做法、NULL 怎麼處理。
  • 說明裡的每個數字與事實都要先用 SQL 查過；寫錯的說明會讓 AI 很有把握地算錯。
  • 列舉值、單位、外鍵的兩個方向，資料庫不會告訴 AI，要寫出來。
  • 資料查得出來的寫進模型檔；要人決定的業務定義另外寫成規則。
  • 關聯用 MANY_TO_ONE 加上 condition 描述；條件要先用資料確認。
