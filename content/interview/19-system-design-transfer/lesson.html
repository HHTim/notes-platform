先別畫圖

從需求問起

面試官：請設計一個銀行轉帳系統。

先問，不要先畫。轉帳系統的設計幾乎全由下面幾個答案決定，建議開場就問：

要問的為什麼會改變設計
只做同行，還是也做跨行？同行兩個帳戶在同一個資料庫，一筆交易就能保證一致；跨行要經過外部清算機構，沒有共同的交易，只能用 Saga 加對帳
即時入帳，還是可以批次？即時要同步回應「成功或失敗」；批次可以先收件、晚點統一處理
每秒幾筆、尖峰在什麼時候？決定要不要拆分資料庫、熱帳戶要不要特別處理（發薪日、月底、大型活動）
有哪些限額與風控規則？決定檢查放在扣款之前的哪一步、要不要跟扣款同一筆交易
稽核與保存要求？決定分錄能不能改、要保存多久、存在哪

需求問完，先講不能妥協的那一條：錢不能多、不能少，帳一定對得上；其他（回應時間、對方多久看到）都可以談。面試集〈系統設計：訊息佇列與最終一致性〉的說法是「『對方何時看到錢』可以最終一致，『錢的總額』不行」。

面試官說「設計一個轉帳系統」，你第一件該做的事是？

  • 先問同行跨行、即時批次、流量
  • 先畫出完整的微服務架構圖
  • 先決定要用 Kafka 還是 RabbitMQ
  • 先把所有資料表的 DDL 寫出來

同行與跨行的一致性做法完全不同，流量決定要不要拆分。不先問清楚，畫出來的架構可能整個方向錯。

為什麼「只做同行」與「也做跨行」會讓設計差很多？

  • 跨行轉帳的金額通常比較大
  • 同行轉帳完全不需要冪等
  • 跨行一定要改用 NoSQL 資料庫
  • 跨行沒有共同的資料庫交易

兩個帳戶都在自己的資料庫裡，ACID 交易就能保證一起成功或一起失敗；對方銀行的帳不在你的資料庫裡，只能分步做、失敗補償、事後對帳。冪等兩邊都要。

轉帳系統裡，下面哪一個要求不能用「最終一致」來妥協？

  • 收款人多久之後在 App 上看到入帳
  • 全部帳戶的錢總額對不對
  • 交易通知簡訊多久送達客戶手機
  • 內部報表多久更新一次

看到的時間可以晚，錢的總額不能錯。其他三項都是「什麼時候看到」的問題。

錢不會憑空出現或消失

帳怎麼記：雙重記帳

面試官：帳戶表只放一個 balance 欄位，轉帳時一邊減、一邊加，不行嗎？

一句話定義：可以跑，但出錯時查不出錢去哪了。複式簿記（double-entry bookkeeping）是「每一筆交易都以相等且相反的分錄（借與貸）記錄」（every financial transaction is recorded with equal and opposite entries (debits and credits)），目的是「維持財務紀錄的正確，並能發現錯誤或舞弊」（allow detection of errors or fraud）。出處 放到資料表上：每筆轉帳寫兩筆分錄，轉出方 −1000、轉入方 +1000，同一筆轉帳的分錄加總一定是 0。

為什麼要分錄，不只要餘額：Fowler 說帳戶也可以看成「某個值的稽核紀錄」：不只想知道現在的值，「還想知道它在過去任何時間點的值，以及每一次個別的變動」（you also want to be able to know it's value at any point in the past, and you want to know each discrete change that happened to that value）。出處 他也建議把產生分錄的事件連到分錄上，這「有助於稽核與後續處理」（helps auditing and later processing）。出處 所以餘額可以留著當快取（查詢快），但真正的帳是分錄：餘額應該永遠等於該帳戶所有分錄的加總，這也是對帳要檢查的第一件事。

CREATE TABLE account (
  id      VARCHAR(16) PRIMARY KEY,
  balance BIGINT NOT NULL CHECK (balance >= 0)            -- 單位：元；不允許透支
);
CREATE TABLE transfer (
  id              BIGINT AUTO_INCREMENT PRIMARY KEY,
  idempotency_key VARCHAR(64) NOT NULL UNIQUE,            -- 同一個鍵只能成功建立一次
  from_id         VARCHAR(16) NOT NULL,
  to_id           VARCHAR(16) NOT NULL,
  amount          BIGINT NOT NULL CHECK (amount > 0),
  status          VARCHAR(16) NOT NULL
);
CREATE TABLE journal_entry (                               -- 分錄：只新增，不修改、不刪除
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  transfer_id BIGINT NOT NULL,
  account_id  VARCHAR(16) NOT NULL,
  amount      BIGINT NOT NULL,                             -- 轉出記負、轉入記正
  created_at  TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
);

三個設計重點：金額用整數（元或分）或 DECIMAL，不用浮點數，MySQL 文件說 DECIMAL 存的是精確值，「在需要保持精確時使用，例如金額」（These types are used when it is important to preserve exact precision, for example with monetary data.）；出處 分錄只新增、不修改，記錯了就再記一筆反向分錄沖回去；轉帳表的冪等鍵是唯一索引（下一段）。CHECK (balance >= 0) 當最後一道防線：MySQL 文件寫，沒寫執行子句或寫 ENFORCED 時，「約束會被建立並執行」（If omitted or specified as ENFORCED, the constraint is created and enforced.）。出處

A 轉 1000 元給 B，照本課的雙重記帳會寫幾筆分錄？加總是多少？

  • 1 筆，1000
  • 2 筆，2000
  • 2 筆，0
  • 1 筆，-1000

A 一筆 −1000、B 一筆 +1000，相等且相反，加總為 0。加總不為 0 就表示錢憑空多了或少了。

分錄記錯了金額，正確的修正方式是？

  • 再記反向分錄沖銷
  • 直接 UPDATE 那筆分錄的金額
  • DELETE 那筆分錄再重寫一筆
  • 只改 balance

分錄只新增不修改，錯誤與更正都留下紀錄，稽核才看得到發生過什麼。直接改或刪，等於把證據抹掉。

有了分錄表，帳戶表的 balance 欄位扮演什麼角色？

  • 唯一的真實資料，分錄只是日誌
  • 沒有用處，應該整個刪掉
  • 只給月底的報表使用
  • 快取，應等於分錄加總

真正的帳是分錄；balance 方便查詢與檢查餘額。兩者不一致就是對帳要抓出來的差異。

金額欄位該用哪一種型別？

  • DOUBLE 浮點數
  • 整數或 DECIMAL
  • FLOAT 浮點數
  • VARCHAR 字串

浮點數有捨入誤差，金額累加之後會對不上。MySQL 文件建議金額這種要精確的值用 DECIMAL；本課示範用 BIGINT 存元。

同一個資料庫，一筆交易搞定

同行轉帳：鎖定、檢查、寫分錄

面試官：同行轉帳怎麼保證不會扣了錢沒入帳？兩筆反方向的轉帳同時進來怎麼辦？

一句話定義：冪等檢查、鎖兩個帳戶、檢查餘額、改餘額、寫兩筆分錄，全部放在一筆資料庫交易裡；鎖帳戶照固定順序。

鎖用 SELECT … FOR UPDATE：MySQL 文件說它會鎖住讀到的列，「就像對那些列下了 UPDATE」，其他交易無法更新這些列（locks the rows and any associated index entries, the same as if you issued an UPDATE statement for those rows）。出處 兩個帳戶要照固定順序鎖：A 轉 B 先鎖 A、B 轉 A 先鎖 B 的話，兩筆交易會各握一把、互等對方，形成死結。MySQL 文件的建議正是「每次都用一致的順序處理」（do those operations in a consistent order each time），這樣「交易會排成明確的佇列，不會死結」（Then transactions form well-defined queues and do not deadlock.）。出處 以下是示範程式的轉帳方法（Java 21＋JDBC，資料庫是 Docker 的 MySQL 8.4.11）：

static String transfer(Connection c, String key, String from, String to, long amount, boolean orderedLocks) throws SQLException {
    c.setAutoCommit(false);
    try {
        long transferId;
        try (PreparedStatement ps = c.prepareStatement(
                "INSERT INTO transfer (idempotency_key, from_id, to_id, amount, status) VALUES (?, ?, ?, ?, 'DONE')",
                Statement.RETURN_GENERATED_KEYS)) {
            ps.setString(1, key); ps.setString(2, from); ps.setString(3, to); ps.setLong(4, amount);
            ps.executeUpdate();
            ResultSet rs = ps.getGeneratedKeys(); rs.next(); transferId = rs.getLong(1);
        } catch (SQLIntegrityConstraintViolationException dup) {   // 同一個冪等鍵已經處理過
            c.rollback();
            return "重送：冪等鍵 " + key + " 已處理過，不再扣款";
        }
        // 兩個帳戶照固定順序上鎖（帳號小的先），避免兩筆反方向的轉帳互相等待
        List<String> order = new ArrayList<>(List.of(from, to));
        if (orderedLocks) Collections.sort(order);
        Map<String, Long> bal = new HashMap<>();
        for (String id : order) {
            try (PreparedStatement ps = c.prepareStatement("SELECT balance FROM account WHERE id = ? FOR UPDATE")) {
                ps.setString(1, id);
                ResultSet rs = ps.executeQuery(); rs.next(); bal.put(id, rs.getLong(1));
            }
        }
        if (bal.get(from) < amount) { c.rollback(); return "餘額不足：整筆還原"; }
        exec(c, "UPDATE account SET balance = balance - ? WHERE id = ?", amount, from);
        exec(c, "UPDATE account SET balance = balance + ? WHERE id = ?", amount, to);
        exec(c, "INSERT INTO journal_entry (transfer_id, account_id, amount) VALUES (?, ?, ?)", transferId, from, -amount);
        exec(c, "INSERT INTO journal_entry (transfer_id, account_id, amount) VALUES (?, ?, ?)", transferId, to, amount);
        c.commit();
        return "成功：轉帳 #" + transferId;
    } catch (SQLException e) {
        c.rollback();
        throw e;
    }
}

主程式先做三件事（正常轉帳、同一個冪等鍵重送、超過餘額），再用 8 條執行緒各做 200 次 A～D 四個帳戶間的隨機轉帳，比較「照帳號排序上鎖」與「照轉出、轉入順序上鎖」；最後用只有 INSERT、SELECT 權限的應用程式帳號試著改分錄：

1. 成功：轉帳 #1
2. 重送：冪等鍵 k-001 已處理過，不再扣款
3. 餘額不足：整筆還原
   分錄 #1 A -1000
   分錄 #1 B 1000
   A=4000，B=6000，分錄加總 0
固定順序上鎖：成功 1206 筆、餘額不足 5 筆、死結 0 次
  總餘額 20000，所有分錄加總 0，分錄筆數 2412，加總不為 0 的轉帳 0 筆
不固定順序上鎖：成功 1036 筆、餘額不足 0 筆、死結 175 次
  總餘額 20000，所有分錄加總 0，分錄筆數 2072，加總不為 0 的轉帳 0 筆
應用程式帳號改分錄：UPDATE command denied to user 'app'@'172.17.0.1' for table 'journal_entry'

兩種上鎖順序最後的帳都對得上（總餘額 20000、分錄加總 0、每筆轉帳的分錄加總都是 0），因為死結時 InnoDB「自動偵測交易死結，還原一筆或多筆交易來解開死結」（InnoDB automatically detects transaction deadlocks and rolls back a transaction or transactions to break the deadlock.），出處 被還原的那筆不留痕跡。差別在死結次數：固定順序 0 次；不固定順序這一次實跑 175 次（每次跑不同，約 160〜185 次；固定順序每次都是 0），每一次都是一筆得重試的失敗轉帳。MySQL 也提醒「隨時準備好在死結時重新執行交易」（Always be prepared to re-issue a transaction if it fails due to deadlock.）、「讓交易小而短」（Keep transactions small and short in duration）。出處 所以交易裡不要呼叫外部服務（簡訊、風控 API），那會讓鎖握得很久。隔離層級與鎖的細節見〈交易隔離層級與鎖〉。

同行轉帳「扣款、入帳、寫兩筆分錄」為什麼要放在同一筆資料庫交易裡？

  • 這樣執行起來比較快
  • 因為 MySQL 規定一定要這樣寫
  • 失敗時全部還原
  • 為了少寫程式

交易的原子性保證一起成功或一起失敗。示範裡餘額不足時 rollback，連轉帳紀錄與分錄都不會留下。

A 轉 B 與 B 轉 A 同時進來，各自先鎖自己的轉出帳戶，會發生什麼？

  • 可能死結，還原其中一筆
  • 兩筆都會成功，互不影響
  • 兩筆都會失敗，一起還原
  • 其中一個帳戶餘額會變成負數

各握一把鎖、等對方那把，就是死結；InnoDB 偵測到後會還原其中一筆。示範的「不固定順序」那組就是這樣產生上百次死結。

示範程式怎麼避免死結？

  • 改用 READ UNCOMMITTED 隔離層級
  • 照帳號排序再依序上鎖
  • 不上鎖，直接 UPDATE
  • 每次轉帳都重新開資料庫連線

固定順序讓所有交易排成同一條隊伍。MySQL 文件建議 do those operations in a consistent order each time；實跑四次都是 0 次死結。

「不固定順序上鎖」那組死結了 175 次，帳卻還是對得上，原因是？

  • MySQL 會把死結的交易改成成功
  • 程式事後會自動補寫分錄
  • 死結那筆整筆還原
  • 剛好運氣好

被選中的交易整筆還原，餘額與分錄都不變，所以總帳對得上；代價是那筆轉帳失敗，要由呼叫端重試。

轉帳交易裡呼叫外部簡訊服務通知客戶，主要的問題是？

  • 簡訊內容會被資料庫記錄下來
  • 簡訊會送失敗
  • MySQL 不允許交易裡有網路呼叫
  • 鎖握太久，別人都要等

MySQL 建議 Keep transactions small and short in duration。通知可以在交易提交後再送，或透過 Outbox 非同步送出。

按兩下也只扣一次

冪等鍵：防重送

面試官：使用者按了兩次送出，或手機網路斷了自動重送，怎麼保證只扣一次？

一句話定義：用戶端每筆轉帳產生一個冪等鍵，伺服器把它存成唯一索引；同一個鍵第二次進來，回傳第一次的結果，不再執行（本課示範只回報「已處理過」；正式做法要存下並回第一次的回應）。

Stripe 的文件是業界常被引用的寫法：冪等鍵讓用戶端在連線錯誤時「可以安全地重送請求，不會建立第二個物件或做兩次更新」（you can safely repeat the request without risk of creating a second object or performing the update twice），伺服器「保存第一次請求的狀態碼與回應內容……之後同一個鍵的請求都回傳同樣的結果」（Subsequent requests with the same key return the same result, including 500 errors.），而且會比對參數，「跟原本的請求不同就回錯誤」（errors if they're not the same to prevent accidental misuse）。出處 IETF 有一份把 Idempotency-Key 這個 HTTP 標頭標準化的草案（draft-ietf-httpapi-idempotency-key-header），目前已過期，不是正式標準。出處 HTTP 介面怎麼寫見〈API 設計進階：版本、分頁、冪等與錯誤格式〉。

示範裡的做法是讓資料庫保證：idempotency_key 是唯一索引，INSERT 撞到就表示做過了。把「記下這個鍵」和「扣款」放在同一筆交易裡很重要：如果鍵先寫進去、扣款失敗卻沒還原，重送會被誤判成已處理。失敗的結果要不要存，有兩種做法：Stripe 與 IETF 草案是連錯誤也存、重送回同一個錯誤（〈API 設計進階：版本、分頁、冪等與錯誤格式〉的範例就是這樣）；本課示範為了簡短沒存失敗結果，餘額不足時鍵會跟著整筆還原，補足餘額後同一個鍵可以重試。正式系統照哪一種，要先跟業務講好。

冪等鍵應該由誰產生？

  • 用戶端，重送時沿用
  • 伺服器，每次收到請求就產生新的
  • AUTO_INCREMENT
  • 不需要產生，用轉帳金額當鍵

重點是「同一筆轉帳的每次重送帶同一個鍵」。伺服器每次新產生，就認不出是重送了；用金額當鍵，兩筆同金額的轉帳會被誤擋。

示範程式第 2 行用同一個冪等鍵 k-001 再送一次，結果是？

  • 再扣一次 1000 元
  • 丟出例外，程式整個中止
  • 扣款成功但沒有寫分錄
  • 回報已處理，不再扣款

INSERT 撞到唯一索引，程式還原並回報已處理過。最後 A=4000、B=6000，只扣了一次。

照 Stripe 的做法，同一個冪等鍵第二次送來、但金額不一樣，伺服器該怎麼做？

  • 用新的金額再轉一次
  • 回錯誤，參數不一致
  • 默默回傳第一次的結果
  • 把兩次的金額加總後轉帳

Stripe 會比對參數，不同就 errors ... to prevent accidental misuse。同一個鍵代表同一個請求，參數變了多半是用戶端的錯。

為什麼「記下冪等鍵」要跟「扣款」放在同一筆交易？

  • 可以省下一次資料庫連線
  • 因為唯一索引只能在交易裡用
  • 避免鍵記了、扣款卻失敗
  • 沒有差別，分開做也一樣

兩件事要一起成功或一起失敗。分開做的話，中間任何一步失敗都會讓鍵與實際狀態不一致。

沒有共同的交易

跨行轉帳：Saga、Outbox 與中間帳戶

面試官：跨行轉帳要經過外部清算機構，怎麼保證一致？

一句話定義：拆成幾個本地交易依序執行（Saga），每一步失敗都有對應的補償；要發給外部的指令先跟本地交易一起寫進 Outbox 表，再由另一個程序送出。

microservices.io 的定義：saga 是「一連串的本地交易」，每個本地交易更新資料庫並發出訊息觸發下一步；某一步違反業務規則失敗時，「saga 會執行一連串補償交易，撤銷前面本地交易做過的變更」（the saga executes a series of compensating transactions that undo the changes that were made by the preceding local transactions）。出處 轉帳適合用編排式（orchestration）：一個協調者記住目前走到哪一步。AWS 的指引提醒「Saga 的參與者必須冪等，才能在暫時性失敗時重複執行」（Saga participants need to be idempotent to allow repeated execution in case of transient failures）。出處

幾個面試常被追問的細節：

  • 中間帳戶：扣款時不是直接把錢「送出去」，而是客戶帳戶 −1000、銀行的轉出中間帳戶 +1000，兩筆分錄加總仍是 0。對方成功後再從中間帳戶結清；對方拒絕就反向記兩筆退回客戶。錢在任何時刻都看得到在哪個帳戶。
  • Outbox：扣款與「要送給清算機構的指令」寫在同一筆本地交易裡（Outbox 表），再由另一個程序讀出來送。microservices.io 說服務必須「原子地更新資料庫並送出訊息」，而資料庫加訊息代理的分散式交易（2PC）常常不可行（it is not viable to use a traditional distributed transaction (2PC) that spans the database and the message broker）。出處 實作見〈訊息佇列：Spring 接 Kafka 與 RabbitMQ〉。
  • 逾時不是失敗：送出之後沒有回覆，可能對方已經入帳、只是回覆丟了。這時建議先用同一個轉帳序號向對方查詢，不要直接補償退款，否則錢會變成兩份。Azure 補償交易模式也提醒「最終一致的某一步什麼時候算失敗，不一定好判斷」，它可能卡住而不是馬上失敗，所以需要逾時機制（It might not be easy to determine when a step in an operation that implements eventual consistency fails. A step might not fail immediately but instead get blocked. You might need to implement a timeout mechanism.）。出處
  • Saga 沒有隔離：microservices.io 也列出它的缺點是「缺乏隔離」（Lack of isolation），並行的 saga 可能讀到中間狀態，要另外設計對策。出處 轉帳的對策就是先把錢移到中間帳戶：客戶在「已扣款」之後就看不到那筆錢，不會被重複花掉。

跨行轉帳為什麼不能像同行一樣用一筆資料庫交易完成？

  • 對方的帳不在你的資料庫
  • 因為跨行轉帳的金額太大
  • 因為 MySQL 不支援跨行
  • 因為法規禁止跨行使用交易

交易只能涵蓋同一個資料庫裡的資料。跨系統只能分步做本地交易，失敗補償，事後對帳。

跨行轉帳扣款時，把錢先轉進「轉出中間帳戶」而不是直接減掉，主要好處是？

  • 可以少記一筆分錄
  • 讓轉帳跑得比較快一點
  • 客戶扣款後還能繼續花那筆錢
  • 加總仍為 0，知道錢在哪

錢從客戶帳戶移到中間帳戶，沒有消失；對方成功才結清、拒絕就退回。客戶在扣款後就不能再花，這也擋住了 saga 缺乏隔離的問題。

送出跨行指令後逾時沒有回覆，最安全的處理是？

  • 立刻補償，把錢退回客戶帳戶
  • 用同一序號查詢，再決定
  • 當作成功
  • 換一個新的序號重新送一次

逾時不代表失敗，對方可能已經入帳。立刻退款可能讓錢變兩份；換新序號重送可能被對方當成兩筆。

Outbox 解決的是哪一個問題？

  • 訊息太大，送不出去
  • 資料庫的查詢太慢
  • 扣款與送指令只成功一半
  • 對方銀行的回覆太慢

指令跟扣款寫在同一筆本地交易的 Outbox 表裡，兩者一起成功；再由另一個程序負責送出，送失敗就重送。

AWS 的 Saga 編排指引特別要求參與者具備什麼性質？

  • 必須同步回應呼叫端
  • 必須共用同一種資料庫
  • 必須部署在同一台機器上
  • 必須冪等

原文：Saga participants need to be idempotent to allow repeated execution in case of transient failures。協調者重試時，同一步做兩次也不能多扣錢。

自動化做不到的，交給人

失敗補償與人工處理

面試官：補償也失敗了怎麼辦？

一句話定義：補償本身也要冪等、可重試；重試到上限還不行，就停在明確的狀態、發出告警、進人工處理清單。

Azure 架構中心的補償交易模式：步驟「可能被重試多次，所以要把每一步設計成冪等的命令」（design each step as an idempotent command），而且「有時候人工介入是從失敗步驟中恢復的唯一方法」，這時「系統應該發出告警，並附上失敗原因的詳細資訊」（the system should raise an alert that includes detailed information about the reason for the failure）。出處 建議的做法：每筆卡住的轉帳都有狀態、最後一次錯誤、重試次數；人工處理只能透過「再記一筆分錄」的方式改帳，不能直接改資料庫，處理過程也要留紀錄。

補償交易重試了 5 次還是失敗，比較好的下一步是？

  • 停住、告警、轉人工
  • 無限重試直到成功為止
  • 直接刪掉紀錄
  • 先改成成功，之後再說

Azure 的說法是有時人工介入是唯一的恢復方法，系統要發出附帶失敗原因的告警。無限重試可能永遠卡住，刪紀錄與假裝成功都會讓帳對不上。

客服人員在人工處理時要把一筆錯誤入帳退回，正確做法是？

  • 用資料庫工具直接改餘額
  • 把原本的兩筆分錄刪掉
  • 記反向分錄並留紀錄
  • 請客戶轉回來

人工處理也要走雙重記帳與稽核紀錄。直接改資料庫會讓餘額與分錄對不上，也查不出是誰改的。

補償交易為什麼也要冪等？

  • 因為補償的金額通常比較大
  • 重試可能退款兩次
  • 補償只執行一次
  • 因為補償不需要寫分錄

Azure：A step might run multiple times when retried, so design each step as an idempotent command。同一個轉帳序號的退款只能生效一次。

檢查放在扣款之前的哪一步

限額與風控放哪

面試官：每日轉帳限額、可疑交易攔截，放在流程的哪裡？

建議的答法（沒有單一標準，要看規則）：

  • 限額跟扣款放在同一筆交易：「今天已轉出多少」要跟扣款一起鎖、一起更新，否則兩筆同時通過檢查，加起來就超過限額。做法跟鎖帳戶一樣，把每日累計放在一列上，FOR UPDATE 之後再判斷。
  • 風控評分放在受理之前，但不放進資料庫交易：呼叫風控服務要時間，放進交易會讓鎖握很久（上一段 MySQL 的建議）。先評分、通過才開始轉帳交易；風控服務掛掉時是「一律拒絕」還是「小額放行」，是要先跟業務講好的規則。
  • 事後監控：通過的交易仍送去非同步分析，發現異常再凍結與人工處理。

限流與斷路器的做法見面試集〈系統設計：秒殺與限流〉與〈韌性模式：Resilience4j 的斷路器、重試與限流〉。

每日限額 5 萬，已轉 4 萬，兩筆 8000 元的轉帳同時進來。限額檢查放在交易外、先查後扣，可能發生什麼？

  • 兩筆都會被拒絕
  • 只有其中一筆會成功
  • 資料庫會自動擋下第二筆
  • 兩筆都過，超過限額

兩筆都讀到「已轉 4 萬」，各自判斷還剩 1 萬額度而通過。累計額度要跟扣款在同一筆交易裡鎖住再判斷。

呼叫外部風控服務評分，為什麼建議放在轉帳交易之前而不是交易之中？

  • 放進交易會讓鎖握很久
  • 因為風控的結果不重要
  • 因為交易裡面不能讀資料
  • 因為風控服務只能非同步呼叫

交易要小而短。先評分、通過再開交易，鎖只在真正改帳的那幾毫秒裡。

風控服務暫時掛掉，轉帳該怎麼辦？

  • 一律放行，事後再說
  • 一律拒絕，不用討論
  • 照事先跟業務約定的規則
  • 讓系統自己隨機決定

這是風險與體驗的取捨，沒有技術上的標準答案。面試時講出「要先跟業務約定」比選一邊更好。

寫了就不能改

稽核紀錄不可改

面試官：怎麼保證分錄與稽核紀錄不會被改？

一句話定義：從權限、資料表設計、儲存三層一起做：應用程式帳號對分錄表只有新增與查詢權限，表的設計只新增不修改，歸檔放在 WORM（寫一次、讀多次）儲存。

  • 權限：示範最後一行，應用程式帳號對分錄表（journal_entry）只有 SELECT, INSERT，想改分錄就被拒絕（轉帳本身要更新 account 的餘額，示範只對分錄表這樣授權）：UPDATE command denied。就算程式有漏洞，也改不了帳。
  • WORM 儲存：Azure Blob 的不可變儲存體讓資料處在 WORM 狀態，「在使用者指定的期間內不能被修改或刪除」（data can't be modified or deleted for a user-specified interval）；出處 Amazon S3 Object Lock 也是「寫一次、讀多次（WORM）模型」（Object Lock uses a write-once-read-many (WORM) model to store objects.）。出處 每日的分錄與稽核紀錄可以定期匯出到這類儲存。
  • 誰做了什麼：稽核紀錄記下操作者、時間、來源、前後狀態；人工處理也要留紀錄（上一段）。

示範裡應用程式帳號只被授予哪些權限，所以改不了分錄？

  • SELECT、INSERT、UPDATE
  • SELECT、INSERT
  • ALL PRIVILEGES
  • 只有 UPDATE

GRANT SELECT, INSERT ON bank.journal_entry；實跑 UPDATE 被拒：UPDATE command denied。

WORM 是什麼意思？

  • 每次寫入都會複製到多台機器
  • 只有管理員帳號可以讀取
  • 資料寫入時會自動加密
  • 寫一次讀多次，期間內不能改

Write Once, Read Many。Azure 不可變儲存體與 S3 Object Lock 都是這個模型。

為什麼「只靠程式不去 UPDATE 分錄」不夠，還要從資料庫權限擋？

  • 權限是最後一道防線
  • 因為權限檢查跑得比較快
  • 因為 MySQL 預設會自動改分錄
  • 沒有差別

多層防護：程式不寫、帳號沒權限、歸檔不可改。任何一層失守，其他層還擋得住。

公司帳戶被大量轉入

高峰流量與熱帳戶

面試官：發薪日、繳費截止日，一個公司帳戶每秒被轉入幾百次，會怎樣？怎麼辦？

一句話定義：每筆轉入都要鎖那一列，所有交易排在同一把鎖後面，吞吐量被一列卡住；做法是把這個帳戶拆成多個子帳戶分散寫入，或入帳時只寫分錄、餘額延後彙總。

這是「熱點」問題：寫入集中在同一筆資料上。示範裡固定順序上鎖讓轉帳排成一條隊伍，對一般帳戶剛好，對熱帳戶就是瓶頸。建議的做法：

  • 拆子帳戶：公司帳戶在內部分成 N 個子帳戶，轉入時隨機或依序挑一個，查詢餘額時加總。Amazon DynamoDB 文件稱類似的手法為寫入碎片（write sharding）：「在分割鍵後面加一個隨機數字」，把寫入「隨機分散到更大的空間」（add a random number to the end of the partition key values. Then you randomize the writes across the larger space.）。出處 同一個道理也適用在關聯式資料庫的列鎖。
  • 入帳只寫分錄：轉入對收款方不會讓餘額變成負數，可以只新增分錄、不鎖餘額那一列，餘額由批次或定時彙總。代價是收款方看到的餘額會晚一點，這要跟業務講清楚。
  • 用佇列緩衝尖峰：先受理、排隊、依處理能力入帳（面試集〈系統設計：秒殺與限流〉的以佇列平衡負載），代價同樣是入帳時間變晚。

轉出不能用「只寫分錄、延後彙總」：轉出要先確定餘額夠，必須讀到最新的餘額並鎖住。

公司帳戶被大量轉入時，瓶頸主要在哪？

  • 網路頻寬不夠
  • 分錄表的資料太多
  • 都在等同一列的鎖
  • 冪等鍵的數量太多

列鎖讓同一個帳戶的更新一次只能進行一筆，加再多機器也一樣排隊。這就是熱點。

把熱帳戶拆成 8 個子帳戶，查詢這個公司帳戶的餘額時要怎麼做？

  • 只看第一個子帳戶
  • 8 個子帳戶加總
  • 取 8 個子帳戶裡最大的
  • 這種帳戶不能查詢餘額

寫入分散到 8 列，讀取時加總回來；寫入變快，讀取多一點工。

為什麼「只寫分錄、餘額延後彙總」可以用在轉入，卻不能用在轉出？

  • 因為轉出不需要寫分錄
  • 因為轉入的金額比較小
  • 因為轉出不需要冪等
  • 轉出要先確認餘額夠

轉入不會讓收款方透支，晚一點彙總無妨；轉出若讀到舊餘額，就可能扣到負數。

每天收工前把帳對一次

對帳批次

面試官：系統都設計好了，為什麼還要對帳？

一句話定義：因為重試、逾時、人工處理、外部系統都可能出錯，對帳是最後確認「帳對得上」的機制，差異進人工處理。

建議至少兩層：

  • 內部對帳：所有分錄加總是否為 0；每筆轉帳的分錄加總是否為 0；每個帳戶的 balance 是否等於它的分錄加總。示範最後的檢查（加總不為 0 的轉帳 0 筆）就是這一層。複式簿記的試算表也是同樣的想法：列出借貸兩欄，「確認借方總額等於貸方總額」（to confirm that total debits equal total credits）。出處
  • 外部對帳：拿清算機構的明細檔逐筆比對我方的跨行轉帳：我方「已送出」對方沒有、對方有我方沒有、金額不同，都列成差異。轉出中間帳戶日終應該結清為 0，不為 0 就是還有沒結案的轉帳。

對帳通常是讀大量資料、逐筆比對、寫差異表的批次工作，Spring Batch 的寫法見〈Spring Batch：銀行批次怎麼寫〉。

內部對帳發現「某帳戶的 balance 不等於它所有分錄的加總」，最可能代表什麼？

  • 有人繞過分錄改了餘額
  • 分錄太多，查詢變慢
  • 這是正常現象，不用處理
  • 冪等鍵在系統裡重複了

餘額應該永遠等於分錄加總。不相等表示有人直接改了 balance、或某個流程沒有在同一筆交易裡完成。

日終「轉出中間帳戶」的餘額不是 0，表示什麼？

  • 銀行今天賺了錢
  • 系統一切正常
  • 還有沒結案的跨行轉帳
  • 某些客戶的帳戶被凍結了

每筆跨行轉帳最後都應該從中間帳戶結清（成功）或退回（失敗）。剩下的金額對應到還卡在途中的轉帳，要逐筆追。

外部對帳最主要比對的是什麼？

  • 我方伺服器的 CPU 使用率
  • 我方紀錄對清算明細
  • 兩個資料庫的版本號碼
  • 系統裡冪等鍵的數量

逐筆比對雙方是否都有、金額是否相同。差異包括我方有對方沒有、對方有我方沒有、金額不同。

出事之前就知道

可觀測性

面試官：上線之後要監控什麼？

一句話定義：技術指標加業務指標。Google SRE 書提出四個黃金訊號：「延遲、流量、錯誤與飽和度」（The four golden signals of monitoring are latency, traffic, errors, and saturation.），並提醒要把成功與失敗請求的延遲分開看。出處 轉帳系統建議再加上：

  • 依失敗原因分類的轉帳失敗數（餘額不足、限額、風控、死結重試、外部逾時）
  • 卡在「已送出」超過 N 分鐘的跨行轉帳數，超過門檻就告警
  • 死結次數與資料庫鎖等待時間（熱帳戶的早期訊號）
  • 對帳差異筆數、中間帳戶日終餘額
  • 每筆轉帳的追蹤（trace）串起受理、扣款、Outbox、跨行回覆，用轉帳序號查得到全程

Micrometer、Prometheus 與 OpenTelemetry 的接法見〈可觀測性：Micrometer、Prometheus 與 OpenTelemetry〉。

Google SRE 書的四個黃金訊號是哪四個？

  • CPU、記憶體、磁碟、網路
  • 成功率、失敗率、重試率、逾時率
  • 日誌、指標、追蹤、告警
  • 延遲、流量、錯誤、飽和度

原文 latency, traffic, errors, and saturation。轉帳系統另外要加上業務指標。

下面哪一個是轉帳系統特有、最值得告警的業務指標？

  • 卡在「已送出」的轉帳數
  • JVM 的垃圾回收次數
  • 首頁的載入時間
  • 伺服器的開機時間

卡在途中的轉帳代表錢在中間帳戶、客戶在等結果，越晚發現越難處理。其他三個是一般技術指標。

把整題串起來

答題順序與整體架構

建議的答題順序（約 30〜40 分鐘的面試）：

順序講什麼一句重點
1問需求同行或跨行、即時或批次、流量、限額、稽核
2資料模型雙重記帳，分錄只新增，每筆加總為 0
3同行轉帳一筆交易，固定順序上鎖
4冪等用戶端產生鍵，唯一索引，跟扣款同一筆交易
5跨行轉帳Saga＋Outbox＋中間帳戶，逾時先查詢
6擴充題限額與風控、稽核不可改、熱帳戶、對帳、監控

時間不夠時，前五項是主幹；面試官追問哪一項就展開哪一項。

只剩 10 分鐘，下面哪一項最不該省略？

  • WORM 歸檔要用哪一家雲
  • 監控儀表板長什麼樣子
  • 雙重記帳與交易邊界
  • 對帳批次用什麼排程工具

資料模型與交易邊界決定錢會不會錯，是整題的主幹；其他是擴充題，被追問再展開。

重點整理

  • 先問需求：同行或跨行、即時或批次、流量、限額、稽核。不能妥協的只有「錢的總額對得上」。
  • 雙重記帳：每筆轉帳兩筆分錄、加總為 0；分錄只新增，錯了用反向分錄沖回；balance 是快取，應等於分錄加總；金額用整數或 DECIMAL。
  • 同行轉帳：冪等檢查、鎖帳戶、檢查餘額與限額、改餘額、寫分錄，全在一筆交易；兩個帳戶照固定順序 FOR UPDATE，避免死結；交易裡不呼叫外部服務。
  • 冪等鍵由用戶端產生，伺服器以唯一索引保證只執行一次，跟扣款同一筆交易；參數不同要回錯誤。
  • 跨行轉帳：Saga 加 Outbox，扣款時先轉入中間帳戶；每一步冪等；逾時不是失敗，先查詢，查不出來進人工處理。補償也失敗就告警、人工處理，人工也只能記分錄。
  • 稽核不可改：帳號只給 SELECT、INSERT，歸檔放 WORM。熱帳戶：拆子帳戶分散寫入、轉入只寫分錄延後彙總。
  • 對帳：內部看加總為 0 與餘額等於分錄，外部逐筆比對清算明細，中間帳戶日終應為 0。監控：黃金訊號加卡住的轉帳、失敗原因、死結、對帳差異。
