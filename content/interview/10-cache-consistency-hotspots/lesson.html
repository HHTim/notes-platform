開場

三種讀寫模式：誰負責把資料放進快取

〈系統設計：短網址的高併發〉與〈系統設計：秒殺與限流〉把快取當擋流量的一層，這課專講快取本身的難處：資料庫改了、快取還是舊的怎麼辦。版本主軸：Redis 8.x（實測 8.10.2）、Spring Framework 7.0（Spring 6 同樣適用）、Caffeine 3.x。

面試官：Cache-Aside、Read-Through、Write-Through、Write-Behind 差在哪？

一句話定義：差在「誰負責把資料放進快取、寫入時快取跟資料庫誰先誰後」。AWS 白皮書把最常見的兩種放在一起講：「Cache-Aside 是在資料被請求之後才更新快取；Write-Through 是主資料庫更新時立刻更新快取」（A cache-aside cache is updated after the data is requested. A write-through cache is updated immediately when the primary database is updated）。出處

模式誰放資料讀不到時寫入時銀行情境
Cache-Aside（旁路快取）應用程式自己應用程式查資料庫、回填快取寫資料庫，再把快取那筆刪掉匯率表、商品頁：讀多寫少、可以晚幾秒
Read-Through（讀穿）快取元件快取自己去資料庫載入同 Cache-AsideSpring Cache 的 @Cacheable
Write-Through（寫穿）快取元件同上同一次寫入更新資料庫與快取，兩邊成功才回應寫完立刻要讀到的資料
Write-Behind（寫回）快取元件同上先寫快取就回應，延後批次寫回資料庫瀏覽次數這類丟一點沒關係的計數

Cache-Aside 的讀取照 AWS 的描述：「先查快取，命中就回傳；未命中就查資料庫，把查到的資料放進快取，再回傳」。出處

// Cache-Aside：讀
Rate get(String pair) {
    Rate r = redis.get("rate:" + pair);            // 1. 先查快取
    if (r != null) return r;
    r = db.findRate(pair);                          // 2. 未命中，查資料庫
    if (r != null) {
        int ttl = 300 + random.nextInt(60);         // 3. 回填，TTL 加隨機秒數（雪崩那題講為什麼）
        redis.set("rate:" + pair, r, EX, ttl);
    }
    return r;
}
// Cache-Aside：寫
void update(String pair, Rate r) {
    db.saveRate(pair, r);                           // 1. 先更新資料庫
    redis.del("rate:" + pair);                      // 2. 再刪快取
}

Write-Through 與 Write-Behind 怎麼答：Coherence 文件講得最直白：Write-Through「在資料成功寫進底層資料來源之前，put 不會回傳」，所以「完全不會改善寫入效能」（This does not improve write performance at all）；Write-Behind 是「修改過的快取項目在設定的延遲之後非同步寫回資料來源」。代價文件自己點名：「Write-Behind 實際上讓快取成為權威紀錄（system-of-record），業務規範必須允許資料只存在叢集記憶體」。出處 帳戶餘額不能用 Write-Behind，這句一定要講。四種模式各由誰放資料的對照圖，見〈快取放哪裡、怎麼失效〉。

一致性

先刪快取還是先更新資料庫

面試官：更新資料時，先刪快取還是先更新資料庫？

一句話定義：先更新資料庫、再刪快取。Azure 架構中心寫明「步驟順序很重要。先更新資料存放區，再移除快取項目。若先移除快取項目，會有一小段時間某個用戶端可能在資料存放區更新前就來讀，未命中之後把過時的資料從資料庫撈回來放進快取，快取裡就留下舊資料」。出處

先刪快取、再更新資料庫（錯的順序）：
  A：刪快取 rate:USD
  B：讀快取未命中 → 查資料庫得到「舊匯率 31.5」
  A：更新資料庫為 31.7
  B：把 31.5 回填進快取          ← 快取是舊的，直到 TTL 到期

先更新資料庫、再刪快取（對的順序）：
  A：更新資料庫為 31.7
  B：讀快取命中「31.5」          ← 只在 A 兩步之間短暫讀到舊值
  A：刪快取
  下一位：未命中 → 查到 31.7 → 回填

這兩條時間線用兩個 Map 模擬、照順序交錯執行的程式與輸出，實跑見〈快取放哪裡、怎麼失效〉。對的順序也只是縮短視窗：Azure 明說「Cache-Aside 模式不保證資料存放區與快取之間的一致性」。出處

面試官：延遲雙刪解決什麼、沒解決什麼？

一句話定義：延遲雙刪（先刪快取、更新資料庫、隔幾百毫秒再刪一次快取）是業界慣用的補救，官方文件沒有這個名字，靠推理答。第二次刪是要清掉「第一次刪與更新資料庫之間被別人回填的舊值」；「幾百毫秒」是估一次讀取回填要多久，還要蓋過主從資料庫的複寫延遲。

  • 解決了：「先刪快取」順序留下的舊值，以及讀寫分離時從庫還沒同步就被讀走回填的舊值。
  • 沒解決：延遲是猜的，讀取比猜的更慢就漏掉；第二次刪也可能失敗，要進訊息佇列重試；兩次刪之間仍讀得到舊值，它是最終一致，不是強一致。
  • 收尾：不管哪種順序，快取都要設 TTL 當最後一道保險：「TTL 到了 key 就從快取刪掉，之後必須回原始資料庫拿更新後的資料」。出處 真的要「寫完立刻讀到」，Azure 的答案是換模式：「若讀多的路徑需要寫後即讀的新鮮度，考慮改用 Write-Through」。出處

先更新資料庫、再刪快取，是「舊值只會短暫存在」跟「舊值可能留到 TTL 到期」的差別；TTL 是最後一道保險，不是主要手段

三種故障

雪崩、穿透、擊穿：都是「快取沒接住、資料庫被打到」

面試官：快取雪崩、穿透、擊穿各是什麼、各怎麼防？

一句話定義：三個名字都是業界慣用語，共同點是「請求繞過快取直接打到資料庫」，差在為什麼繞過：一大批 key 同時失效叫雪崩；查根本不存在的資料叫穿透；一把熱門 key 剛好過期叫擊穿。

故障怎麼發生怎麼防
雪崩整批匯率同一秒過期，或 Redis 整台掛掉TTL 加隨機秒數；Redis 做主從與哨兵（Sentinel）；資料庫端限流、斷路器
穿透拿不存在的帳號狂查，每次未命中、每次打資料庫Bloom Filter 先擋「確定不存在」；查無此人也用短 TTL 快取
擊穿熱門商品頁那把 key 到期的瞬間，幾千個請求同時去重建互斥重建：只讓一個請求查資料庫；或邏輯過期：先回舊值、背景更新

隨機 TTL 有官方依據：AWS 白皮書列為最佳實務：「替 TTL 加一點時間抖動（jitter）……如果所有商品資料同時過期，後端資料庫就得吞下所有商品請求」，做法是「TTL ＝ 原本的秒數 ＋ 隨機產生的值」。出處 Redis 自己也怕同秒到期：「很多 key 在同一刻到期可能成為延遲的來源」（many keys expiring at the same moment can be a source of latency）。出處 Redis 8.10.2 實測：SET rate:usd 31.5 EX 348（300 加隨機 48），TTL 回 348；空結果快取、BF.RESERVE、SET NX 搶鎖的完整輸出，實跑見〈快取放哪裡、怎麼失效〉。

Bloom Filter 怎麼答：原理與名單怎麼建，〈系統設計：短網址的高併發〉講完了；這裡補 Redis 的說法：Bloom Filter「能保證某個元素不在集合裡，但對『在』只能給出估計」（A Bloom filter can guarantee the absence of an item from a set, but it can only give an estimation about its presence），建立時要給預期元素數與誤判率。出處

互斥重建：Spring Cache 文件直接描述這個問題：「預設快取抽象不鎖任何東西，同一個值可能被算好幾次」，解法是 sync 屬性：「鎖住那筆快取項目，只有一條執行緒在算，其他的等到項目更新」。出處 跨機器的版本是用 SET 鍵 值 NX EX 秒數 搶一把短鎖，搶到的查資料庫回填、沒搶到的等一下重讀快取；Redis 8.10.2 實測，第二個搶的回空值。鎖的三個不能省的地方見資料庫模組第 5 課〈分散式鎖與 Redis〉。

@Cacheable(cacheNames = "rates", key = "#pair", sync = true)   // 同一把 key 只讓一條執行緒去查
public Rate findRate(String pair) { return db.findRate(pair); }

@CacheEvict(cacheNames = "rates", key = "#pair")                // 更新後把那筆快取刪掉
public void updateRate(String pair, Rate r) { db.saveRate(pair, r); }

邏輯過期：快取值不設 TTL，另外記一個業務上的到期時間；到期後先把舊值回給使用者，同時只派一個背景任務去更新。Caffeine 的 refreshAfterWrite 就是這個機制：「更新是非同步替 key 載入新值，期間仍回傳舊值；淘汰則強迫讀取者等到新值載入完」。出處 代價是短暫看到舊值，匯率表可以、餘額不行。

熱點

熱 key 與大 key：一個是太多人讀同一把，一個是一把太重

面試官：熱 key 怎麼發現、怎麼拆？

一句話定義：熱 key（hot key，短時間被集中存取的少數 key）的麻煩在 Redis Cluster 裡一把 key 只住一個槽、一個槽只由一個節點服務出處，所以加節點不會分攤它的壓力——理由〈系統設計：秒殺與限流〉講過。

  • 怎麼發現：redis-cli --hotkeys，文件註明「只在 maxmemory-policy 是 *lfu 時有效」出處，因為它靠 LFU 的存取頻率計數；單把 key 用 OBJECT FREQ。工具以外，應用程式端抽樣統計也是常見答法。
  • 拆法一，本地快取擋讀：熱門商品頁先放進應用程式記憶體（Caffeine），大多數讀取連 Redis 都不用去；〈系統設計：秒殺與限流〉用同一招擋售罄後的讀取。代價是各節點短暫不一致。
  • 拆法二，複製多份：把 product:1001 寫成 product:1001:0 到 :9 十份，讀時隨機挑一份；十份多半落在不同的槽、分散到不同節點，壓力就拆開了；代價是更新要刪十份。十把 key 用 CLUSTER KEYSLOT 算出來落在十個不同的槽，以及 --hotkeys 的實際輸出，實跑見〈快取放哪裡、怎麼失效〉。

面試官：大 key 為什麼危險？

一句話定義：大 key（big key，一把 key 的值很大，例如幾十萬個成員的 Set）危險在 Redis 是單執行緒處理指令：「當一個請求很慢，所有其他用戶端都得等它」（when a request is slow to serve all the other clients will wait for this request to be served），SORT、LREM、SUNION 這類多元素指令，文件舉例「取兩個大集合的交集可能花掉可觀的時間」。出處

  • 怎麼發現：redis-cli --bigkeys「抽樣找元素很多的 key」，--memkeys「抽樣找佔記憶體多的 key」，--keystats 兩者合一。出處 它們走 SCAN；KEYS 被文件列為「生產環境很常見的延遲來源」，只准除錯用。出處
  • 怎麼刪：用 UNLINK 不用 DEL：「每把 key O(1) 移除，然後在另一條執行緒做 O(N) 的記憶體回收」。出處 在 Redis 8.10.2 實測：20 萬個成員的 Set，MEMORY USAGE 回 9,234,711 位元組（約 9 MB），UNLINK 立刻回 1；--bigkeys 的輸出見〈快取放哪裡、怎麼失效〉。要讓 DEL 也走背景，設定檔開 lazyfree-lazy-user-del yes（預設 no）。出處
  • 怎麼拆：大 Hash 按欄位名雜湊拆成 100 個小 Hash；大 List 按時間切段；大 String 多半是整份 JSON 塞進一把 key，改存欄位。

Redis 本體

資料結構、為什麼快、持久化、淘汰

面試官：Redis 的資料結構各適合什麼？

一句話定義：看「值的形狀」選：一個值 String，有欄位的紀錄 Hash，有順序 List，去重 Set，要排名 Sorted Set，記「有沒有」Bitmap，只要「大約幾個」HyperLogLog。定義照官方資料型別頁。出處 每種結構的指令與輸出，實跑見〈快取放哪裡、怎麼失效〉。

型別官方定義銀行情境
String「最基本的型別，一串位元組」匯率值、Session、計數器、分散式鎖
Hash「欄位—值配對的紀錄型別」，像 Java 的 HashMap一個帳戶的多個欄位，只改一欄
List「依插入順序排列的字串串列」最近十筆交易、簡單佇列
Set「無序、不重複的字串集合」今天登入過的帳號、黑名單
Sorted Set「不重複字串，依各自的分數維持順序」熱門商品排行、以時間當分數的延遲任務
Bitmap「不是獨立型別，而是定義在 String 上的位元操作」，String 最大 512 MB出處每個帳號一個位元記今天有沒有登入，一億個帳號約 12 MB
HyperLogLog估算不重複元素數，「最多用 12 KB，標準誤差 0.81%」出處活動頁的不重複訪客數

面試官：Redis 為什麼快？它是單執行緒嗎？

一句話定義：快的原因有三：資料在記憶體、指令處理是單執行緒沒有鎖的開銷、用 I/O 多工（multiplexing，一條執行緒同時看管很多條連線，誰有資料就處理誰）不會卡在等網路。官方延遲文件：「Redis 採用大體上單執行緒的設計，單一行程用一種叫多工的技術服務所有用戶端請求」，「被設計成不會卡在系統呼叫上，例如讀寫 socket」。出處 FAQ 補一句：「CPU 很少成為 Redis 的瓶頸，通常瓶頸在記憶體或網路」。出處

版本界線要答對：「單執行緒」指執行指令那條線。Redis 6.0 起「可以選擇用多條執行緒處理 I/O」（Redis can now optionally use threads to handle I/O）出處；設定檔寫「現在也能把用戶端 socket 的讀寫放到不同的 I/O 執行緒」，預設 io-threads 1「就是照舊只用主執行緒」。出處 答法：「指令執行單執行緒，每個指令都是原子的；6.0 起網路讀寫可多執行緒，預設關著」。

面試官：RDB 對 AOF，快取要不要開持久化？

一句話定義：RDB 是「在指定間隔對資料集做某一時刻的快照」，AOF 是「記錄每一個寫入操作，啟動時重播重建資料集」；還有第三個選項「不持久化，做快取時有時會這樣用」（This is sometimes used when caching）。出處

RDBAOF
檔案「非常緊湊的單一檔案，適合備份與災難復原」「一個接一個的操作紀錄，容易看懂、容易匯出」，太大時背景重寫
會丟多少「若要把停機時的資料遺失降到最低，RDB 不好」，快照通常五分鐘以上一次預設 appendfsync everysec「每秒 fsync 一次，最多丟一秒」；always 最安全但很慢
代價「需要常常 fork()，資料集大時可能讓 Redis 停幾毫秒到一秒」「視 fsync 策略可能比 RDB 慢」

怎麼選：官方建議「想要接近 PostgreSQL 的資料安全就兩種都開」、「能接受丟幾分鐘就 RDB 就好」、「不建議只開 AOF」。出處 銀行情境：純快取（匯率、商品頁）可以不開，掛了從資料庫回填、但要防雪崩；當鎖、當預扣庫存這種「丟了會出帳務問題」的用途至少 AOF everysec。不持久化與開 AOF 兩台重開前後的對照，實跑見〈快取放哪裡、怎麼失效〉。

面試官：記憶體滿了怎麼辦？maxmemory-policy 怎麼設？

一句話定義：maxmemory 設上限，maxmemory-policy 決定滿了淘汰誰。官方頁現在列十種：noeviction「不淘汰，寫入回錯誤」；allkeys- 開頭的四種對全部 key 用 LRU（最近最少用）、LFU（最不常用）、LRM（最近最少被改——只看寫入不看讀取，Redis 8.6 起新增）、隨機；volatile- 開頭的五種只淘汰設了 TTL 的 key，多一個 volatile-ttl 挑「剩餘 TTL 最短的」；「volatile 系列在沒有 key 設 TTL 時行為等同 noeviction」。出處

# redis.conf
maxmemory 2mb                    # 上限；0 表示不限制
maxmemory-policy allkeys-lru     # 官方：「沒特別理由時 allkeys-lru 是好的預設選項」
maxmemory-samples 5              # 抽樣近似，預設抽 5 把，10 更準但多吃 CPU

兩個常考細節：第一，Redis 開源版的預設是 noeviction，快取用途一定要改。出處 第二，LRU 是「抽樣少量 key，淘汰其中最久沒用的，而不是精確計算」。出處 Redis 8.10.2 實測：maxmemory 2mb、allkeys-lru，寫進 3,000 把各 1 KB 的 key 後剩 428 把、evicted_keys 2,572，兩個數用同一個 INFO 指令讀，加起來剛好 3,000；另一台用 noeviction 寫同樣 3,000 把，只有 440 把寫進去，其餘回「OOM command not allowed when used memory > 'maxmemory'」。完整輸出見〈快取放哪裡、怎麼失效〉。

兩層與分工

Caffeine 加 Redis 怎麼失效，HTTP 快取又是誰的事

面試官：本地快取加分散式快取兩層，資料改了怎麼讓兩層都失效？

一句話定義：兩層是「每台應用程式自己的記憶體」加「大家共用的 Redis」。Azure 的描述：「先查本地快取、再查共用快取、最後才查原始資料存放區」，代價是「要小心設定，避免本地快取相對共用快取太過時」。出處 難的是散在幾十台機器記憶體裡的 Caffeine。

  • 做法一，短 TTL 認了：本地層只留幾秒到幾十秒。Redis 官方說這是最簡單的解法：「對本地快取的資訊設一個固定的最大存活時間，過了就不再視為有效」。出處
  • 做法二，廣播失效：更新的那台刪 Redis 之後，用 Pub/Sub 發一則「rate:USD 失效」，每台訂閱到就刪自己的 Caffeine。官方點出代價：「訊息會送到每一台，包括根本沒快取那筆的」。出處
  • 做法三，Redis 6 起的用戶端追蹤（client tracking）：伺服器替你記哪台用戶端讀過哪把 key，「key 被修改、因 TTL 到期或因 maxmemory 被淘汰時，所有可能快取著它的用戶端都會收到失效訊息」，用戶端「收到就必須刪掉對應的 key」。出處

Spring Cache 的 @Cacheable、@CacheEvict、sync = true 與「自己呼叫自己不生效」用 Spring Framework 7.0.9 實際執行的程式與輸出，實跑見〈快取放哪裡、怎麼失效〉。

Caffeine 為什麼是本地層的標準答案：官方一句話「高效能的 Java 快取程式庫，提供接近最佳的命中率」出處；淘汰用 Window TinyLfu，比 LRU「在各種工作負載上都有大幅改善」。出處

LoadingCache<String, Rate> local = Caffeine.newBuilder()
    .maximumSize(10_000)                          // 數量上限，「淘汰最近沒用或很少用的」
    .expireAfterWrite(Duration.ofSeconds(30))      // 寫入 30 秒後到期：本地層短 TTL
    .refreshAfterWrite(Duration.ofSeconds(10))     // 10 秒後被查到就背景更新，期間回舊值
    .build(pair -> redis.getOrLoad(pair));         // 未命中往下一層拿

expireAfterWrite「自建立或最近一次替換起算」，expireAfterAccess「自最近一次讀或寫起算」。出處 Spring 裡通常交給快取抽象出處：「@Cacheable 觸發放入、@CacheEvict 觸發移除、@CachePut 不干擾方法執行地更新快取」。出處

面試官：CDN、瀏覽器的 HTTP 快取，跟應用層快取怎麼分工？

一句話定義：HTTP 快取存「整個回應」，由瀏覽器與 CDN 依標頭自動處理，適合靜態檔與公開頁面；應用層快取存「查詢結果」，由程式自己管，適合登入後每個人不同的資料。RFC 9111 分兩種：「共用快取（shared cache）儲存回應給多個使用者重用，通常部署在中介」也就是 CDN；「私有快取（private cache）專屬單一使用者，通常是瀏覽器的一部分」。出處

資料放哪一層標頭或做法
商品圖、JS、CSSCDN 與瀏覽器Cache-Control: public, max-age=31536000，檔名帶版本雜湊
匿名可看的商品頁CDN 幾十秒 ＋ Rediss-maxage「對共用快取覆蓋 max-age」出處
登入後的餘額、明細只在應用層，或不快取Cache-Control: private, no-store；private 是「共用快取不得儲存」出處

新鮮度、no-cache 對 no-store、ETag 與 304，〈網路與 HTTP 面試題：三向交握、TLS、REST 對 gRPC〉講完了。個人資料被 CDN 存起來給別人看，多半是漏了 private。

快取的每一題都在問：舊值能被看到多久、被誰看到；先講這份資料能容忍多舊，再選模式與 TTL

重點整理

  • Cache-Aside 應用程式自己回填、寫完刪快取；Write-Through 兩邊同步寫、寫不會變快；Write-Behind 先寫快取、延後寫回資料庫，餘額不能用。
  • 先更新資料庫、再刪快取；延遲雙刪補舊值但延遲是猜的、仍是最終一致；TTL 是最後一道保險，要強一致改 Write-Through。
  • 雪崩用隨機 TTL；穿透用 Bloom Filter 加快取空結果；擊穿用互斥重建（Spring sync=true、SET NX）或邏輯過期（Caffeine refreshAfterWrite）。
  • 熱 key 一把只住一個槽、加節點沒用：--hotkeys（要 LFU）找，本地快取或複製多份拆。大 key 卡住單執行緒：--bigkeys 找，UNLINK 背景回收，拆小。
  • Redis 快在記憶體、單執行緒執行指令加 I/O 多工；6.0 起 io-threads 可多執行緒讀寫網路，預設關。RDB 快照可能丟幾分鐘；AOF 預設每秒 fsync、最多丟一秒；純快取可不開，當鎖或庫存至少 AOF。淘汰策略預設 noeviction、快取要改 allkeys-lru。
  • 兩層失效三招：本地短 TTL、Pub/Sub 廣播、Redis 6 起的 client tracking。HTTP 快取存整個回應：靜態檔與匿名頁交給 CDN 用 max-age 與 s-maxage，個人資料加 private。
