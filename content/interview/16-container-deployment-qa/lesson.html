做出映像檔

容器、分層、多階段與啟動指令

答題公式：先一句話定義，再講差別與取捨，最後補版本或實務註記。以下版本為準：Kubernetes 1.37出處、Docker 現行文件、Java 25（與 21 不同處會標）、Spring Boot 4.1。

面試官：容器跟虛擬機差在哪？

一句話定義：Docker 文件：虛擬機是「一整套作業系統，有自己的核心」；容器「只是一個被隔離的行程，帶著它執行需要的所有檔案」，多個容器「共用同一個核心」。出處 隔離靠 namespace（管看得到什麼），限量靠 cgroup（管能用多少），見〈容器〉與〈容器不等於 Docker〉。

面試官：映像檔分層怎麼運作？為什麼改一行 Dockerfile，後面全部重建？

一句話定義：「每一層包含一組檔案系統的變更：新增、刪除或修改」，而且建好就不可變；分層讓不同映像檔能共用底層，「建置更快，儲存與傳輸量更少」。出處

快取失效規則：「一旦某一層變了，下游每一層都要重建」，即使結果不會不同。出處 COPY 與 ADD 怎麼判斷變了：看檔案中繼資料算出的檢查碼，但「修改時間不算進去」。出處 所以常改的放後面，例子見〈映像檔與 Dockerfile〉。

面試官：多階段建置解決什麼？Spring Boot 的分層 JAR 是什麼？

多階段：一份 Dockerfile 寫多個 FROM，「可以挑選要從一個階段複製到下一階段的產物，其餘留在後面」，編譯工具不進最終映像檔。出處

分層 JAR（layered jar）：Spring Boot 打出來的可執行 JAR 是「胖 JAR」（uber jar，程式和所有相依套件包成一個檔）。文件說把它整包放進同一層「不是最佳做法」，因為程式碼重新編譯比升級 Spring Boot 頻繁。出處

所以 JAR 裡附一份 layers.idx，預設四層依序是 dependencies、spring-boot-loader、snapshot-dependencies、application，Maven 外掛「預設就會放進」這份索引。出處

下面照官方範例寫，另加一個非 root 使用者（Docker 建議：服務不需要特權就用 USER 換成非 root）出處：

# 第一段：把 jar 拆成四層
FROM bellsoft/liberica-openjre-debian:25-cds AS builder
WORKDIR /builder
ARG JAR_FILE=target/*.jar
COPY ${JAR_FILE} application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

# 第二段：出貨的映像檔，由少變到常變依序 COPY
FROM bellsoft/liberica-openjre-debian:25-cds
RUN groupadd --system app && useradd --system --gid app app
USER app
WORKDIR /application
COPY --from=builder /builder/extracted/dependencies/ ./
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "application.jar"]

拆層指令與兩段結構出自 Spring Boot 的 Dockerfile 頁。出處 用 docker build --progress=plain 可以自己看：只改一個類別再建，只有 application 那層重做，其餘三層標 CACHED。

不寫 Dockerfile 的另一條路是 Buildpacks（替應用自動配好 JRE 並打成映像檔的工具）：mvn spring-boot:build-image，映像檔「以非 root 使用者建置與執行」出處，而且同樣吃 layers.idx。出處

面試官：CMD 跟 ENTRYPOINT 差在哪？COPY 跟 ADD 呢？

分工：「把容器當執行檔用時，應該定義 ENTRYPOINT」；CMD 用來給 ENTRYPOINT 預設參數，或臨時跑別的指令，「容器帶著其他參數啟動時，CMD 會被蓋掉」。出處 會被蓋掉的範例見〈映像檔與 Dockerfile〉。

面試官接著會追問兩種寫法：

  • exec 形式是 JSON 陣列 ["java","-jar","app.jar"]
  • shell 形式是一行字，會自動套一層 shell。

shell 形式的 ENTRYPOINT「以 /bin/sh -c 的子指令啟動，而它不會轉傳訊號，所以你的程式不是容器的 PID 1，收不到 Unix 訊號」，包括 docker stop 送的 SIGTERM（請程式收尾結束的訊號）。出處 為什麼要緊：K8s 刪 Pod 時也是「讓容器執行環境送 TERM 訊號給每個容器裡的 1 號行程」，寬限期預設 30 秒，到期再送 KILL。出處

可以自己驗證：把上面的 ENTRYPOINT 改成 shell 形式，docker exec 容器名稱 cat /proc/1/cmdline | tr '\0' ' '（參數之間用看不見的 \0 字元隔開，換成空白才好讀）會看到 1 號行程是 /bin/sh -c java -jar application.jar；docker stop 後 docker inspect 的結束碼是 137（被 KILL 結束），日誌沒有 Spring 的優雅關閉訊息；exec 形式則有。

COPY 對 ADD：COPY 只做基本複製；ADD 還能抓遠端 HTTPS 與 Git 網址、自動解開 tar 檔。一般用 COPY，要在建置時下載遠端檔案才用 ADD，它支援檢查碼驗證。出處

常改的放後面、編譯工具留在前一段、ENTRYPOINT 用 exec 形式：快、小、收得到 SIGTERM

Java 在容器裡

JVM 讀得到 cgroup 限制嗎，堆該開多大

面試官：容器裡跑 Java 要注意什麼？

一句話定義：讀得到，但預設只拿四分之一當堆。Java 25 手冊：-XX:+UseContainerSupport「僅限 Linux」，讓 JVM「判斷 Docker 容器內 Java 行程可用的記憶體量與處理器數」，「預設為 true」。出處

堆怎麼算：同一份手冊，-XX:MaxRAM 預設是「JVM 行程可用的最大記憶體，或 128 GB，取小的」，可用記憶體取「實體記憶體與環境限制（例如容器）」的小者；-XX:MaxRAMPercentage「預設 25%」。出處 可以自己驗證：拿第二段的基礎映像檔跑 docker run --rm -m 1g bellsoft/liberica-openjre-debian:25-cds java -XX:+PrintFlagsFinal -version，看 MaxHeapSize，記憶體上限 1 GiB 時不加參數是 268435456 位元組（256 MiB），加 -XX:MaxRAMPercentage=75 變 768 MiB。不設到 100%，因為堆外還有 Metaspace、執行緒堆疊等（見〈Java 進階快答：JVM 記憶體、垃圾回收與類別載入〉），加總超過上限就可能被 OOMKilled。

CPU 那半邊：JVM 依可用處理器數決定 GC 與 ForkJoinPool 的執行緒數，要手動壓就用 -XX:ActiveProcessorCount。出處 執行緒池怎麼依核心數開，見〈Java 並行快答：執行緒池、鎖與並行集合〉；預設 G1 的前提是「兩顆以上處理器、且實體記憶體大於等於 1792 MB」，否則預設 Serial出處：容器只給 1 顆 CPU，或記憶體不到 1792 MB（上面 1 GiB 的例子就是）時，回收器會變 Serial，見〈Java 進階快答：JVM 記憶體、垃圾回收與類別載入〉。

版本註記：上面幾個參數的說明與預設值，Java 21 與 25 手冊寫法相同。出處 舊 JDK 要注意 cgroup 版本：Kubernetes 1.35 起棄用 cgroup v1，官方建議 Java 用完整支援 v2 的版本，HotSpot 是「jdk8u372、11.0.16、15 以後」。出處

容器上限決定 JVM 看到的記憶體，MaxRAMPercentage 決定堆拿幾成，剩下的留給堆外

上 K8s、換版本

物件分工、滾動更新與三種部署策略

滾動更新、探針與 OOMKilled 的實跑見〈部署策略與探針〉。

面試官：Pod、Deployment、ReplicaSet、Service、Ingress 各是什麼？

五個物件見〈Pod 與 Node〉、〈Deployment：下單〉、〈Service：找路〉、〈對外入口〉。接著會被追問的是 Deployment 與 ReplicaSet 的關係：ReplicaSet「維持一組穩定數量的副本 Pod」，通常由 Deployment 自動管理。出處 每次換版本，Deployment 開一個新的 ReplicaSet、把舊的縮到 0 但留著，回退就是把舊的放大回來。出處

面試官：滾動更新的 maxSurge、maxUnavailable 是什麼？怎麼回退？

一句話定義：maxUnavailable 是更新中最多幾個 Pod 不可用，百分比換算「無條件捨去」；maxSurge 是最多比期望數多開幾個，「無條件進位」；兩個預設都是 25%，不能同時為 0。出處 10 個副本照預設：最多 2 個不可用、最多多開 3 個。其他算例見〈Deployment：下單〉。

什麼會觸發：「只有 Pod 範本（.spec.template）變了才觸發」，調副本數不會。出處

回退：kubectl rollout undo deployment/core-banking 回上一版，加 --to-revision 指定版本；能退幾版看 revisionHistoryLimit，「預設 10」，設成 0 就「無法回退」。出處 注意 undo 只改叢集上的 Deployment，Git 裡的設定檔還是新版，下次 apply 會把新版帶回來；所以設定檔放在 Git 的團隊，回退要連設定檔一起還原。

核心帳務服務的寫法：maxUnavailable: 0 讓可服務的數量全程不少於期望數，代價是要有多開 Pod 的空間：

spec:
  replicas: 10
  revisionHistoryLimit: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 0

面試官：藍綠、金絲雀、滾動各適合什麼？K8s 原生做得到哪些？

定義：藍綠是準備「兩套盡量相同的正式環境」，新版在閒置那套測好後「切換路由器」，出事切回去。出處 金絲雀是先把新版開給「一小部分使用者」，再推給所有人。出處 三者的取捨表與零停機的前提見〈後端與雲端面試題庫〉。

  • 滾動、重建：Deployment 的 strategy.type 只有 RollingUpdate（預設）與 Recreate（先全部砍掉再開新的）兩種。出處
  • 金絲雀：官方做法是兩個 Deployment，標籤 track: stable 與 track: canary，Service 的 selector 只選共同的標籤，兩組都收流量；「比例靠調兩邊副本數」，例如 3:1，有信心後更新 stable、刪掉 canary。出處 限制是比例只能用 Pod 數湊；要不受 Pod 數限制的比例，可以用 Gateway API（K8s 新一代的對外入口規格，見〈對外入口〉）的 HTTPRoute 替後端設權重。出處
  • 藍綠：沒有內建策略，可以自己組：兩個 Deployment 分別標 version: blue 與 green，Service 的 selector 從 blue 改成 green 就是切換，改回來就是回退。Gateway API 的流量切分頁也示範用權重把流量從舊版整個移到新版。出處
# stable 那個 Deployment 的 Pod 範本（replicas: 3，舊版映像檔）
metadata:
  labels:
    app: core-banking
    track: stable
---
# canary 那個 Deployment 的 Pod 範本（replicas: 1，新版映像檔）
metadata:
  labels:
    app: core-banking
    track: canary
---
# Service 只選共同標籤，流量約 3:1
spec:
  selector:
    app: core-banking

滾動是 Deployment 內建；金絲雀是兩個 Deployment 共用標籤；藍綠可以靠改 Service 的 selector

活著、準備好、吃多少

三種探針與資源、QoS

面試官：存活、就緒、啟動三種探針各決定什麼？設錯會怎樣？

一句話定義：探針是 kubelet 定期對容器做的檢查，依結果「重啟不健康的容器，或停止把流量送給還沒準備好的容器」。出處〈OpenShift 部署實戰〉叫它們「存活檢查」「就緒檢查」。

探針失敗了會怎樣什麼時候跑
存活（liveness）連續失敗次數達到 failureThreshold，kubelet 重啟這個容器整個生命週期定期跑；不等就緒探針
就緒（readiness）不重啟，把 Pod 的 IP 從所有對應 Service 的 EndpointSlice（Service 背後「目前有哪些 Pod 能收流量」的清單）移除整個生命週期定期跑
啟動（startup）kubelet 殺掉容器，依重啟政策處理只在啟動時跑；設了它，成功前另兩種都不跑

表格與預設值出自官方探針頁：periodSeconds 10 秒、timeoutSeconds 1 秒、failureThreshold 3。出處

設錯的後果：

  • 存活探針查了外部系統：官方警告存活探針「實作錯誤可能導致連鎖故障」，高負載下容器反被重啟。出處 Spring Boot 文件講得更具體：存活探針「不應依賴外部系統的健康檢查」，否則資料庫一掛，「Kubernetes 可能重啟所有應用實例，造成連鎖故障」；就緒探針要不要查外部系統，「要由開發者審慎決定」，所以 Spring Boot 預設不替這兩組加其他健康指標。出處
  • 沒設啟動探針：另一個錯是啟動慢卻沒設啟動探針，還在初始化就被存活探針判死重啟。官方做法是啟動探針用同一個端點，讓 failureThreshold × periodSeconds 蓋過最慢的啟動時間，例如 30 × 10 = 300 秒。出處

Spring Boot Actuator 現成的兩個端點是 /actuator/health/liveness 與 /actuator/health/readiness出處；4.1 的屬性附錄寫 management.endpoint.health.probes.enabled 預設 true。出處

startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  periodSeconds: 10
  failureThreshold: 30
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  periodSeconds: 5
  failureThreshold: 3

面試官：requests 跟 limits 差在哪？QoS 等級怎麼判？OOMKilled 是什麼？

一句話定義：排程器確保一台節點上「所有容器的 requests 加總小於節點容量」，所以 requests 決定排在哪；limits 由核心強制執行。CPU 超過上限是被節流（throttling，跑慢一點）；記憶體超過上限「核心可能終止它」，但要等核心偵測到記憶體壓力。出處

被終止時容器狀態的 reason 是 OOMKilled（記憶體不足被殺），結束碼 137。出處 137 只代表被 KILL 訊號結束，shell 形式那個例子也是 137，要看 reason 是不是 OOMKilled 才能確定是記憶體。

基本差別見〈Deployment：下單〉，單位見〈K8s 上手：Minikube 與上雲〉。

QoS 三級怎麼判：出處

  • Guaranteed：每個容器的 CPU 與記憶體都有 request 與 limit、都大於 0，而且 limit 等於 request。
  • Burstable：不符合 Guaranteed，但至少一個容器設了 CPU 或記憶體的 request 或 limit。
  • BestEffort：全都沒設。

驅逐順序見〈K8s 上手：Minikube 與上雲〉。陷阱題：只寫 limit 不寫 request，而叢集也沒有另外替它補預設 request 時，Kubernetes 會「複製 limit 當 request」出處；所以 CPU 和記憶體都只寫 limit 時，兩個 request 各自複製 limit，結果就是 Guaranteed。

resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    memory: 1Gi

這份 CPU 沒設上限，判定是 Burstable；部署後用 kubectl get pod POD名稱 -o jsonpath='{.status.qosClass}' 可以自己看。要 Guaranteed 就補上 cpu 的 limit 並等於 request。

requests 管排在哪，limits 管撞到怎樣：CPU 撞到變慢，記憶體撞到 OOMKilled

設定、擴縮、管線

ConfigMap 與 Secret、HPA、CI/CD 與十二要素

面試官：ConfigMap 跟 Secret 差在哪？Secret 只是 base64，該怎麼看？

一句話定義：ConfigMap 存「非機密資料」，「不提供保密或加密」，上限 1 MiB；當環境變數注入的值「不會自動更新，要重啟 Pod」。出處 Secret 的 data 欄位值「必須是 base64 編碼字串」，不想自己編碼可以寫 stringData。出處

為什麼不等於加密：base64 是編碼，kubectl get secret 取出值再 base64 -d 就是原文。官方警語：Secret 預設「未加密存在 API 伺服器底層的資料存放區（etcd）」，有 API 權限或摸得到 etcd 的人都能讀改。官方列的最低步驟：開啟靜態加密（encryption at rest，存進磁碟前先加密）、用 RBAC 給最小權限、限制只有特定容器能讀、考慮外部金鑰存放服務。出處 RBAC 的白話見〈K8s 上手：Minikube 與上雲〉；Config Server 對 ConfigMap 的選擇見〈微服務與架構面試題：服務發現、韌性、可觀測性與十二要素〉。

面試官：HPA 依什麼擴縮？月底流量高峰怎麼準備？

公式：HPA（水平 Pod 自動擴縮器）的演算法是 desiredReplicas = ceil[currentReplicas × currentMetricValue / desiredMetricValue]。出處 例如 4 個 Pod、CPU 平均 140%、目標 70%：ceil(4 × 140 ÷ 70) = 8 個。

追問細節：出處

  • CPU 使用率是「相對容器 requests 的百分比」；有容器沒設 request，使用率就「沒有定義」，HPA 對這個指標不動作。
  • 比值夠接近 1.0（預設容差 0.1）就不動；控制迴圈預設每 15 秒跑一次。
  • 預設擴容沒有穩定窗口、立刻擴；縮容有 300 秒穩定窗口，避免來回抖動。
  • 資源指標「通常由 Metrics Server 這個附加元件提供，要另外啟動」。

月底高峰：新 Pod 要啟動、通過就緒探針才接得到流量，可以在高峰前先調高 minReplicas；HPA 的 YAML 見〈K8s 上手：Minikube 與上雲〉。

面試官：CI/CD 管線長什麼樣？GitHub Actions 的 workflow 怎麼寫？

骨架：建置、測試、掃描（相依套件與映像檔的弱點）、打映像檔、推上 registry（映像檔倉庫）、部署。對應十二要素第 V 條：建置、發布、執行嚴格分開，每個發布有唯一 ID，「任何變更都要產生新發布」。出處 注意發布是「建置加上設定」：commit 編號適合當建置（映像檔）的標籤，發布 ID 要連設定一起算。Deployment 的修訂版號只在 Pod 範本變了才增加出處，只改 ConfigMap 內容不會多一版。

結構：workflow 檔放 .github/workflows；on 定義觸發事件；jobs 由一或多個工作組成，「預設平行執行」，要排先後用 needs；runs-on 選執行的機器（runner）；steps 裡 uses 呼叫一個現成的 action（可重用的程式單元），run 執行指令列程式。出處

name: core-banking-ci
on:
  push:
    branches: [main]
  pull_request:
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
      - name: 建置與測試
        run: mvn -B verify

設定（III）、行程（VI）、日誌（XI）三條見〈微服務與架構面試題：服務發現、韌性、可觀測性與十二要素〉，建置發布執行（V）在上一題。另外三條：

要素原文主張（節譯）在容器與 K8s 上
VII 連接埠綁定應用「完全自給自足」，不靠執行環境注入網頁伺服器，自己綁連接埠提供 HTTP出處Spring Boot 內嵌 Tomcat，server.port 預設 8080出處，對上 containerPort 與 Service 的 targetPort
IX 可拋棄性行程「可以隨時啟動或停止」；啟動要快，「收到 SIGTERM 時優雅關閉」：停止接新請求、做完手上的再結束出處exec 形式讓 JVM 當 PID 1；Spring Boot 內嵌伺服器「預設就開啟優雅關閉」出處。Spring 預設每個關閉階段最多等 30 秒（spring.lifecycle.timeout-per-shutdown-phase）出處，跟 K8s 的寬限期一樣長；要嘛調大 terminationGracePeriodSeconds，要嘛調小 Spring 的等候時間
X 開發與正式環境一致縮小時間、人員、工具三種落差，開發與正式環境不用不同的後端服務出處同一個映像檔從測試到正式，只換 ConfigMap 與 Secret

一個映像檔走到底：建一次、配上設定成為發布、收到 SIGTERM 好好結束

重點整理

  • 某一層變了，下游每一層都重建；Spring Boot 分層 JAR 依 dependencies、spring-boot-loader、snapshot-dependencies、application 排，改程式只重做最後一層。
  • ENTRYPOINT 用 exec 形式；shell 形式讓 /bin/sh 當 PID 1，收不到 SIGTERM，K8s 寬限期 30 秒後被 KILL。一般用 COPY，下載遠端檔才用 ADD。
  • JVM 預設開容器支援，MaxRAMPercentage 預設 25%（Java 21 與 25 相同）；調高但留空間給堆外。
  • maxUnavailable 捨去、maxSurge 進位，預設都是 25%；回退用 rollout undo，留幾版看 revisionHistoryLimit（預設 10）。金絲雀靠兩個 Deployment 共用標籤，比例看副本數。
  • 存活失敗重啟容器、就緒失敗移出 EndpointSlice、啟動探針成功前另兩種不跑；存活探針不查資料庫。
  • QoS：全部 limit 等於 request 才是 Guaranteed；記憶體超過上限可能被 OOMKilled（結束碼 137 只代表被 KILL，要看 reason），CPU 超過只被節流。
  • Secret 只是 base64，要靠靜態加密與 RBAC；HPA 依 requests 算使用率，公式 ceil(目前副本數 × 目前值 ÷ 目標值)。
