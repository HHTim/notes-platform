從單體到微服務

SOA 的 ESB 跟 API Gateway 差在哪

答題公式：先一句話定義，再講差別與取捨，最後補版本或實務註記。〈後端與雲端面試題庫〉答過服務發現、熔斷、Saga、監控、API Gateway 各一題：那五題是骨架，這課補肉，寫追問層的參數名、原理與代價。版本以撰寫時的現行版為準：Spring Boot 4.1、Spring Cloud 2025.1、Resilience4j 2.4（官方文件站標示 v2.2.0）、Istio 1.31。

面試官：單體、SOA、微服務怎麼演進？ESB 跟現在的 API Gateway 差在哪？

一句話定義：三者差在「拆多細」與「聰明放哪裡」。單體（monolith）是一個部署單位；SOA（服務導向架構）拆成服務，但整合邏輯集中在 ESB（Enterprise Service Bus，企業服務匯流排）；微服務拆得更小，整合邏輯留在服務身上。

ESB 是什麼：Fowler 的微服務文章把 ESB 當「把大量聰明放進通訊機制本身」的代表：「ESB 產品常內建精密的訊息路由、編排、轉換與套用業務規則的功能」（sophisticated facilities for message routing, choreography, transformation, and applying business rules），並點名服務導向的失敗實作之一是「把複雜度藏進 ESB」。出處 以銀行為例：核心帳務、卡務、外匯各一套舊系統，整合規則越堆越多在 ESB 上，改一條就要多個團隊協調。

API Gateway 是什麼：microservices.io 的定義：「提供每個用戶端一個統一介面去存取服務」。出處 它管入口：路由、認證、限流、TLS 終結；業務編排留在服務裡，對應 Fowler 那篇的小標「聰明端點、笨管線」（smart endpoints and dumb pipes）。出處

ESBAPI Gateway
放在哪服務與服務之間的中間層外部流量進來的入口
管什麼路由、協定轉接、欄位轉換、多系統編排、業務規則路由、認證、限流、TLS 終結、觀測
業務邏輯大量在匯流排上不放，留在各服務

收尾一句：Gateway 一旦開始做欄位轉換與跨服務編排，就會長成新的 ESB。

ESB 是聰明的管線，Gateway 是笨的門：門只查證件、數人頭、指路，不替你辦業務

找得到、設定得了

服務發現兩種模式，集中設定兩條路

面試官：服務發現有哪兩種模式？Kubernetes 的 Service 算哪一種？

一句話定義：差別在「誰去查名冊」（名冊就是服務註冊表，Service Registry）。用戶端模式（client-side discovery）：「用戶端查詢服務註冊表，取得服務實例的位置」。出處 伺服器端模式（server-side discovery）：「用戶端透過位置固定的路由器（也就是負載平衡器）發請求，路由器查服務註冊表，再轉給可用的實例」。出處

取捨：用戶端模式「零件與網路跳數較少」，代價是「把用戶端跟服務註冊表綁在一起」、每種語言各寫一次。出處 伺服器端模式「用戶端程式碼較簡單」，代價是路由器是「另一個要安裝、設定」的元件，而且「需要更多網路跳數」。出處

K8s 的 Service 算哪種：伺服器端。microservices.io 伺服器端那頁寫：Kubernetes 這類叢集方案「在每台主機跑一個代理，當作伺服器端發現的路由器」。出處 Kubernetes 文件也說 Service 讓你「不需要改既有的應用去用陌生的服務發現機制」。出處原理見容器與 Kubernetes 模組第 9 課〈Service：找路〉。

版本註記（Eureka 現況）：Spring Cloud Netflix 現行版 5.0.2 只列「服務發現（Eureka）」出處；Hystrix、Ribbon、Zuul、Archaius、Turbine 的模組在 Spring Cloud 2020.0 就移除了。出處 現在的答案：用戶端負載平衡用 Spring Cloud LoadBalancer出處，斷路器用 Spring Cloud Circuit Breaker（「跨不同斷路器實作的抽象層」，支援 Resilience4J 與 Spring Retry）出處；Spring Cloud 2025.1 對應 Spring Boot 4.0 與 4.1。出處

面試官：集中設定怎麼做？Spring Cloud Config 跟 ConfigMap 怎麼選？

一句話定義：Spring Cloud Config「提供分散式系統中外部化設定的伺服器端與用戶端支援」，「儲存後端的預設實作用 git，因此很容易支援有標籤版本的設定」。出處 用戶端設 spring.config.import=optional:configserver: 會「連到預設位置 http://localhost:8888 的 Config Server」，拿掉 optional: 則連不到就失敗。出處

ConfigMap 這條路：「ConfigMap 是用來存放非機密資料的 API 物件，形式是鍵值對」，可當「環境變數、命令列參數，或 volume 裡的設定檔」用；「ConfigMap 不提供保密或加密」，機密的改用 Secret。出處 實作見容器與 Kubernetes 模組第 18 課〈K8s 上手：Minikube 與上雲〉。

怎麼選：已在 K8s 上、設定只是各環境不同的幾個值，ConfigMap 加 Secret 可能就夠；要設定有版本、能從 git 紀錄看出誰改了什麼，Config Server 配 git 比較合適。

韌性四件套

斷路器的參數名、重試的四個配件、隔艙、逾時

斷路器（circuit breaker，面試常叫熔斷）的三態、隨機指數退避、重試預算見〈系統設計：秒殺與限流〉，這節補 Resilience4j 的參數，以及隔艙與逾時。

面試官：斷路器三個狀態怎麼切換？滑動視窗、失敗率門檻、半開試探在 Resilience4j 裡各是哪個參數？

一句話定義：Resilience4j 文件：斷路器是「有限狀態機，三個正常狀態 CLOSED、OPEN、HALF_OPEN」，另有三個特殊狀態；「用滑動視窗儲存並彙總呼叫結果，可選計數型或時間型」。出處

三態的哪一步參數（預設值）文件怎麼說
CLOSED 時記帳slidingWindowType（COUNT_BASED）、slidingWindowSize（100）「計數型彙總最近 N 次呼叫；時間型彙總最近 N 秒」
還不能判斷minimumNumberOfCalls（100）「若設 10，只評估了 9 次，即使 9 次全失敗也不會跳開」
CLOSED 到 OPENfailureRateThreshold（50）、slowCallRateThreshold（100）、slowCallDurationThreshold（60000 毫秒）「失敗率大於等於門檻就轉 OPEN，開始短路呼叫」；慢呼叫比例達門檻同樣跳開
OPEN 時waitDurationInOpenState（60000 毫秒）「OPEN 時以 CallNotPermittedException 拒絕呼叫」，等待時間過後轉 HALF_OPEN
HALF_OPEN 試探permittedNumberOfCallsInHalfOpenState（10）「放行可設定數量的呼叫」，其餘照樣拒絕；試完失敗率或慢呼叫比例仍達門檻就退回 OPEN，都低於門檻就回 CLOSED

同頁：「預設所有例外都算失敗」，列進 ignoreExceptions 的「既不算失敗也不算成功」。出處 餘額不足是正確的業務拒絕，要列進去，否則可能把好端端的下游熔斷掉。

面試官：重試要配什麼才安全？

一句話定義：Azure 架構中心：失敗「不是暫時性的」就取消並回報，暫時性的才等一下再試，「必要時重複，重試間隔遞增，直到達到最大次數」。出處 安全的重試要四個配件：

  • 上限：maxAttempts（預設 3，「含第一次呼叫」）；retryExceptions 列要重試的例外，ignoreExceptions 列不重試的。出處
  • 退避（backoff，間隔越等越久）：waitDuration（預設 500 毫秒，「重試之間的固定等待時間」）出處，Spring Boot 設定再加 enableExponentialBackoff: true 與 exponentialBackoffMultiplier。出處
  • 抖動（jitter，間隔加隨機量，免得大家同時醒來再撞一次）：enableRandomizedWait 與 randomizedWaitFactor；兩個開關都開時，原始碼組出的是 IntervalFunction.ofExponentialRandomBackoff。出處
  • 冪等（idempotent，同一件事做幾次結果都一樣）：Azure：不冪等的操作「重試可能讓它被執行不只一次」，例如服務處理成功卻沒能送出回應。出處 入帳這種寫入要帶請求編號讓下游去重，做法見〈系統設計：訊息佇列與最終一致性〉。

面試官：隔艙解決什麼？

一句話定義：隔艙（bulkhead）「名字來自船體的分艙隔板：船身破了只有受損那一艙進水，船不會沉」；做法是「把應用的元素隔成多個資源池，一個壞了其他照常運作」，例如替每個下游服務各配一個連線池。出處 查餘額、查匯率共用一個池，匯率服務一慢就占滿池子；各下游一池，慢的只拖垮自己那池。

Resilience4j 的參數：兩種實作，「SemaphoreBulkhead 用 Semaphore；FixedThreadPoolBulkhead 用有界佇列加固定執行緒池」。信號量版是 maxConcurrentCalls（預設 25，「允許的最大並行執行數」）與 maxWaitDuration（預設 0，擠不進去時最多卡多久）出處，就是〈Java 並行快答：執行緒池、鎖與並行集合〉的 Semaphore 限量放行。

面試官：逾時怎麼設？為什麼說逾時比重試更重要？

一句話定義：逾時是其他三件的前提。Azure 的斷路器頁：「逾時太長，跑斷路器的執行緒可能被卡很久，斷路器才知道操作失敗」。出處 重試同樣要等上一次結束，隔艙名額也會被卡住的呼叫占著。多長：同頁寫「設短一點，但要夠長，讓操作大多數時候能成功」。

Resilience4j 的做法：TimeLimiter 設逾時時間（timeoutDuration）與要不要取消執行中的 future（cancelRunningFuture），包的是 CompletionStage 或 Future。出處 註解疊加的預設套用順序：「Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( Function ) ) ) ) )」，要改就用各自的 …AspectOrder 屬性。出處 由內往外讀：隔艙拿名額，逾時限住整段，結果記進斷路器，最外層的重試決定要不要再來。

查餘額呼叫核心帳務，四件套在 application.yml 設完。鍵名照文件的 Spring Boot 3 範例頁（模組 resilience4j-spring-boot3，要有 actuator 與 aop 兩個 starter）出處；Spring Boot 4 要換 2.4.0 起的 resilience4j-spring-boot4出處，aop starter 在 Boot 4 改名為 spring-boot-starter-aspectj。出處

resilience4j.circuitbreaker:
  instances:
    coreBanking:
      registerHealthIndicator: true

      slidingWindowSize: 100
      minimumNumberOfCalls: 20

      slowCallRateThreshold: 80

        - com.example.bank.InsufficientBalanceException   # 業務拒絕不算失敗

逾時給每次呼叫一個終點，斷路器數終點、重試等終點、隔艙守名額：沒有逾時，三個都在等一個可能不來的結果

可觀測性

三種訊號、拉取模型、一條 trace 怎麼穿過所有服務

面試官：指標、日誌、追蹤怎麼分工？四個黃金訊號是什麼？

一句話定義：可觀測性（observability）的定義見〈後端與雲端面試題庫〉。OpenTelemetry：「追蹤（Traces）：請求穿過應用的路徑；指標（Metrics）：執行期擷取的量測；日誌（Logs）：一件事的紀錄」，另有在訊號之間傳遞情境資訊的行李（Baggage）。出處

分工怎麼答：指標說「有沒有事」，追蹤說「事在哪一段」，日誌說「那一段發生了什麼」。四個黃金訊號「延遲、流量、錯誤、飽和」見〈系統設計：秒殺與限流〉；追問層補原文：「若只能量四個指標，就專注這四個」，飽和要「強調最受限的資源」出處，例如對帳批次的飽和可能是待處理筆數，不是 CPU。

面試官：Prometheus 為什麼是拉取？Micrometer 跟 Actuator 怎麼把指標吐出來？

一句話定義：Prometheus 總覽列的特性：「多維資料模型，時間序列由指標名稱與鍵值對識別」、「時間序列的收集透過 HTTP 拉取模型進行」（via a pull model over HTTP）、「推送透過中介的 gateway 支援」。出處 Micrometer 是中間那層：「供應商中立的應用可觀測性門面（facade）」，「把它想成可觀測性版的 SLF4J」（Think SLF4J, but for observability）。出處

Actuator 怎麼接：Spring Boot Actuator「替 Micrometer 提供相依管理與自動設定」；「Prometheus 預期抓取或輪詢各個應用實例」，Spring Boot 提供 /actuator/prometheus 端點；來不及被抓的「短命或批次工作」用 Pushgateway。出處容易漏掉的一步：「預設只有 health 端點透過 HTTP 與 JMX 曝露」，要用 management.endpoints.web.exposure.include 打開；文件提醒端點「可能含敏感資訊」。出處

# application.properties（Spring Boot 4.1）
management.endpoints.web.exposure.include=health,info,prometheus   # 預設只有 health
management.tracing.sampling.probability=1.0                        # 預設 0.1；對帳期間全取樣

面試官：分散式追蹤的 trace ID 怎麼從 A 服務傳到 B 服務？OpenTelemetry 在做什麼？

一句話定義：OpenTelemetry 文件：「A 服務呼叫 B 服務時，A 把 trace ID 與 span ID 放進情境（context）；B 用這些值建立屬於同一條 trace 的新 span，把 A 的 span 當父節點」；傳播「通常由 instrumentation 函式庫處理」（替你在程式裡自動收集遙測資料的函式庫），預設用「W3C TraceContext 規格定義的標頭」。出處 OpenTelemetry 是產生、收集遙測資料的框架，「與廠商和工具無關」，「本身不是可觀測性後端」。出處

那個標頭長什麼樣：W3C 規格：「traceparent 標頭識別追蹤系統中的傳入請求，有四個欄位」；trace-id「是整個追蹤森林的 ID」，16 位元組；parent-id「是呼叫端所知的這個請求的 ID（有些追蹤系統叫 span-id）」，8 位元組；全零都是無效值。出處 規格自己的範例：

traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
             │  │                                │                └ trace-flags：01 表示有被取樣
             │  │                                └ parent-id：呼叫端這一段（span）的 ID，8 個位元組
             │  └ trace-id：整條追蹤的 ID，16 個位元組，所有服務帶同一個
             └ version：本規格是 00

Spring Boot 這邊：Actuator「替 Micrometer Tracing 提供相依管理與自動設定」，可接 OpenTelemetry 用 OTLP 送出出處；屬性附錄：management.tracing.propagation.produce 預設 [W3C]、management.tracing.sampling.probability 預設 0.1。出處 追問：日誌怎麼跟 trace 對上——「用了 Micrometer Tracing，預設就把關聯 ID 放進日誌」，形如 [traceId-spanId]；文件點名的斷鏈原因——「RestTemplate、RestClient 或 WebClient 不是用自動設定的 builder 建立，自動的追蹤傳播就不會生效」。出處

指標說有事、追蹤說在哪、日誌說是什麼；三者靠同一個 trace ID 串起來，trace ID 靠 traceparent 標頭傳下去

平台層與原則

服務網格、Serverless 與十二要素

面試官：Service Mesh 是什麼、解決什麼、代價是什麼？

一句話定義：服務網格（Service Mesh）把服務間通訊的事從程式碼搬到平台。Istio 官方：「開源的服務網格，透明地疊在既有的分散式應用之上」，「服務程式碼只需少量或不需修改」；功能包含 mTLS、重試、故障轉移，以及所有流量的指標、日誌、追蹤。出處

兩種模式：Sidecar 模式每個應用旁邊注入一個 Envoy 代理，「經過充分實戰，但有資源成本與維運負擔」。Ambient 模式 2022 年推出，「自 Istio 1.22 起單叢集情境可用於生產」，流量經過每節點一個、只做第四層的代理，要第七層功能再加 Envoy。出處 預設：安裝設定檔 default 裝的是 sidecar 資料平面，ambient 要另選 ambient 設定檔。出處

代價與選型：每個 Pod 多一個代理、每一跳多一次轉發，再加一個要升級、排錯的控制平面。可以這樣答：服務少、語言單一，Resilience4j 加 Micrometer 可能就夠；服務多、多語言、要全面 mTLS，網格比較划算。

面試官：Serverless 適合什麼、不適合什麼？冷啟動是什麼？

一句話定義：Lambda 與 ECS、EKS 的三選一見〈後端與雲端面試題庫〉。追問層是生命週期：「Init 階段做三件事：啟動所有擴充、啟動 runtime、執行函式的靜態程式碼」，「Init 階段限制 10 秒」。出處

冷啟動：同一頁：「下載程式碼與建立環境這前兩步常被稱為冷啟動（cold start）。這段時間會計費，並且加在整次呼叫的延遲上」；「冷啟動通常發生在不到 1% 的呼叫，時間從不到 100 毫秒到超過 1 秒」。出處 JVM 啟動與 Spring 初始化都落在 Init，Java 的冷啟動可能偏長；解法之一是 SnapStart：發布版本時先初始化、存成快照，之後「從快取的快照恢復新環境，而不是從頭初始化」。出處

適合與不適合：適合事件驅動、流量一陣一陣、工作短而獨立，例如對帳完發通知。不適合的從生命週期推：長時間執行、要常駐連線或本機狀態（環境會被凍結與回收）、對延遲敏感又流量稀疏（冷啟動比例高）。

面試官：十二要素裡的設定、日誌、無狀態行程三條怎麼答？

要素原文主張（節譯）
III 設定「要求設定與程式碼嚴格分離。設定隨部署大幅變動，程式碼不會」；試金石是「程式碼能不能隨時開源，而不洩漏任何憑證」；「十二要素應用把設定存在環境變數」出處
XI 日誌「把日誌當事件流」；「十二要素應用從不關心輸出流的路由或儲存，不該嘗試寫入或管理日誌檔；每個行程把事件流不緩衝地寫到 stdout」出處
VI 行程「行程是無狀態且不共享的（share-nothing），要持久的資料必須存進有狀態的後端服務，通常是資料庫」；「黏性工作階段（sticky sessions）違反十二要素，永遠不該使用或依賴」，工作階段資料適合放 Redis 這類有到期機制的存放區出處

追問「登入狀態放哪」：外部存放區或權杖，比較見〈認證與安全面試題：JWT、OAuth 2.0、OIDC 與密碼保存〉。

設定放環境、日誌寫 stdout、行程不留狀態：三條都在讓「換一台跑」變成不用想的事

重點整理

  • ESB 把轉換、編排、業務規則放在中間層；API Gateway 只管入口：「聰明端點、笨管線」。
  • 服務發現差在誰查名冊：用戶端模式跳數少但綁註冊表，伺服器端模式用戶端簡單但多一跳；K8s 的 Service 是伺服器端。
  • 斷路器參數對三態：slidingWindowSize／minimumNumberOfCalls 記帳，failureRateThreshold／slowCallRateThreshold 跳 OPEN，waitDurationInOpenState 等多久，permittedNumberOfCallsInHalfOpenState 試幾個。
  • 重試四配件：maxAttempts、指數退避、隨機抖動、下游冪等；隔艙用 maxConcurrentCalls 分池；逾時是前提，預設順序 Retry 包 CircuitBreaker 包 TimeLimiter 包 Bulkhead。
  • Prometheus 走 HTTP 拉取，短命批次用 Pushgateway；Micrometer 是可觀測性版的 SLF4J；Actuator 預設只曝露 health。
  • trace ID 靠 traceparent 傳：version、trace-id（16 位元組）、parent-id（8 位元組）、trace-flags；Spring Boot 4.1 預設送 W3C 格式、取樣 0.1。
  • Istio 的 default 安裝設定檔用 sidecar，另有 ambient；Lambda 冷啟動是下載程式碼加建環境；十二要素：設定放環境變數、日誌寫 stdout、行程無狀態。
