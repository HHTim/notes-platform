執行時資料區

JVM 把記憶體分成哪幾塊

答題公式：先一句話定義，再講差別與取捨，最後補版本或實務註記。課文以 Java 25（撰寫時的長期支援版）的 HotSpot 為準；Java 21 同樣適用的地方直接寫，兩版有差的地方會標出來。JVM、JRE、JDK 三個縮寫與位元碼怎麼來的，見 Java 模組第 1 課〈Java 是什麼、環境怎麼裝〉。

面試官：JVM 執行時資料區有哪些？哪些是執行緒共用、哪些私有？

一句話定義：Java 虛擬機規格（JVMS，定義 JVM 該怎麼運作的正式文件）第 2.5 節把執行期間用到的記憶體分成幾塊「執行時資料區」（run-time data areas）：有的在 JVM 啟動時建立、關機才銷毀；有的隨執行緒建立與銷毀。出處

區域（JVMS 正式名稱）放什麼誰擁有爆掉時丟什麼
堆（heap）所有物件與陣列的實體全部執行緒共用OutOfMemoryError
方法區（method area）類別結構：欄位與方法的資訊、方法的位元碼、執行時常數池（run-time constant pool，每個類別的常數與符號參考表）全部執行緒共用OutOfMemoryError
JVM 堆疊（Java Virtual Machine stack）每次方法呼叫一個「框」（frame）：區域變數、運算元堆疊每條執行緒一個StackOverflowError；開新執行緒配不出堆疊時是 OutOfMemoryError
pc 暫存器（pc register）這條執行緒目前執行到哪一條指令每條執行緒一個—
本機方法堆疊（native method stack）執行 C 這類原生程式碼時用的堆疊每條執行緒一個StackOverflowError 或 OutOfMemoryError

差別與取捨：面試官真正想聽的是「堆與方法區共用，所以要垃圾回收、要同步；堆疊與 pc 私有，所以區域變數天生執行緒安全」。規格原文：堆「在所有 JVM 執行緒之間共用」，方法區也是；而「每條 JVM 執行緒都有私有的 JVM 堆疊，與執行緒同時建立」。出處 執行緒與共享狀態為什麼要協調，見 Java 模組第 10 課〈執行緒與並行〉。

實務註記：每條執行緒的堆疊大小用 -Xss 設，Linux/x64 與 macOS/x64 預設 1024 KB、Aarch64 預設 2048 KB。出處 遞迴太深丟的是 StackOverflowError，不是 OutOfMemoryError——兩個常被混著答。

面試官：堆裡的年輕代、老年代是什麼？物件什麼時候晉升？

一句話定義：HotSpot 把堆分成年輕代（young generation）與老年代（old generation）；年輕代再分成 Eden 與兩塊 Survivor 空間。分代的依據是「弱分代假說」（weak generational hypothesis）：官方調校指南寫「多數物件只活很短的時間」，所以把新物件集中放一區、頻繁回收那一區，效率最好。出處

差別與取捨：調校指南描述的流程：「多數物件一開始配置在 Eden。任何時候都有一塊 Survivor 是空的，當作垃圾回收時 Eden 與另一塊 Survivor 裡活物件的目的地；回收完，Eden 與來源 Survivor 都清空。」物件「就這樣在兩塊 Survivor 之間來回複製，直到被複製過一定次數、或那邊空間不夠，就複製進老年代」，這個過程叫「老化」（aging），複製進老年代就是「晉升」。出處 年輕代越大，年輕代回收（minor GC）越少發生；但堆總量固定時老年代就變小，老年代回收（major GC）反而變多——這是調年輕代大小的核心取捨。出處

實務註記（一定會被問的參數）：-Xms 設堆的初始（也是最小）大小、-Xmx 設最大；沒設時預設初始值是實體記憶體的 1/64、最大值是 1/4出處。官方手冊寫「伺服器部署通常把 -Xms 與 -Xmx 設成同一個值」——省掉執行中反覆擴縮堆的成本。出處 年輕代對老年代的比例用 -XX:NewRatio（例如 =3 表示 1:3）、Eden 對單塊 Survivor 的比例用 -XX:SurvivorRatio（預設 8）。出處

年輕代靠「大部分物件很快就死」賺效率；活過幾輪 Survivor 來回的才晉升老年代

面試官：Metaspace 取代永久代解決了什麼？

一句話定義：Metaspace是 HotSpot 放類別中繼資料（class metadata，JVM 內部對每個類別的描述：欄位、方法、位元碼）的地方，也就是 JVMS 說的方法區在 HotSpot 的實作。Java 8 起它從堆裡的永久代（permanent generation，PermGen）搬到原生記憶體（native memory，作業系統直接給行程的記憶體，不在 Java 堆內）。出處

差別與取捨：解決的是「要手動調永久代大小」這件事。JEP 122（Java 8）的摘要就一句：「從 HotSpot JVM 移除永久代，因此也不再需要調校永久代的大小」；做法是類別中繼資料改配置在原生記憶體，字串池與類別的靜態變數則搬進 Java 堆。出處 舊時代 -XX:MaxPermSize 設太小就 OutOfMemoryError: PermGen space；現在 Metaspace「預設沒有上限」，要限制才用 -XX:MaxMetaspaceSize。出處

實務註記：「沒有上限」不等於不會爆——類別載入器一直載新類別（例如反覆重新部署、動態產生代理類別）而載入器又沒被回收，就會把 Metaspace 吃到 OutOfMemoryError: Metaspace。調校指南寫得很具體：Metaspace 的空間切成一塊塊（chunk），每塊綁定某個類別載入器；「當某個類別載入器的類別被卸載，它的區塊就回收再用或還給作業系統」。出處 所以 Metaspace 洩漏幾乎都是「類別載入器洩漏」，下一節再講。另一個常被搞混的參數 -XX:MetaspaceSize 不是上限，是觸發垃圾回收的「高水位線」（high-water mark）。出處

垃圾回收

怎麼判斷死活、選哪個回收器、停頓怎麼縮

面試官：什麼是 GC Root？可達性分析怎麼判斷物件死了？

一句話定義：HotSpot 判斷死活的準則是可達性（reachability）：調校指南寫「當一個物件再也無法從執行中程式的任何活物件的任何參考到達，就被視為垃圾，記憶體可以被 VM 重用」。出處 從哪裡開始算「到達」？起點就叫 GC Root（根），HotSpot 詞彙表的定義：「從堆外指進 Java 物件堆的指標，例如來自類別的靜態欄位、執行中方法框裡的區域參考等」。出處 從根出發沿著參考走得到的都算活，走不到的就是垃圾。這種「從根追蹤」的做法叫追蹤式回收（tracing garbage collection）。

差別與取捨：面試官常追問「為什麼不用參考計數？」參考計數（reference counting，每個物件記著有幾個參考指著它，歸零就回收）最單純的版本「無法處理參考循環——一個物件直接或間接指回自己」；兩個互相指著對方、但外面沒人指的物件，計數永遠不會歸零。追蹤式回收從根出發，這兩個物件走不到，自然回收。出處

實務註記：「走得到」有強弱之分——java.lang.ref 套件把可達性分成強、軟、弱、虛四級，後面〈強、軟、弱、虛參考差在哪〉那題會講。

面試官：常見垃圾回收器 Serial、Parallel、G1、ZGC 各適合什麼？現在預設是哪個？

一句話定義：Oracle 的調校指南列了四個回收器，取捨軸只有兩條：吞吐量（throughput，單位時間內能做多少應用程式的工作）對停頓時間（pause time，應用程式被暫停等回收的時間），再加上機器大小。

回收器官方描述適合開啟
Serial「用單一執行緒做所有垃圾回收工作」，沒有執行緒間溝通成本資料量小（約 100 MB 以內）、單處理器、不在意停頓-XX:+UseSerialGC
Parallel「也叫吞吐量回收器」，跟 Serial 一樣分代，差在「用多條執行緒加速回收」要榨出最高峰值吞吐量、能忍受一秒以上停頓（批次工作）-XX:+UseParallelGC
G1「大致並行」（mostly concurrent）的回收器，「能以高機率達成停頓時間目標，同時保有高吞吐量」回應時間重要、要短停頓的一般伺服器應用-XX:+UseG1GC
ZGC「最大停頓在一毫秒以內，但犧牲一些吞吐量」，停頓時間與堆大小無關，適用「幾百 MB 到 16 TB」的堆延遲最優先、堆很大-XX:+UseZGC

以上四列的描述與選擇準則都出自 Java 25 的 HotSpot 調校指南。出處 面試也常提到 Shenandoah：另一個走低停頓路線的回收器，Java 15 起從實驗功能轉正式（JEP 379）。JEP 寫它原本「在 Red Hat 的 8u 與 11u 下游版本中以受支援的垃圾回收器出貨」；而 Oracle 的調校指南只列上面四個、沒有它——用不用得到，要看手上的 JDK 是哪家建置的；有的話用 -XX:+UseShenandoahGC 開。出處

現在預設是哪個：G1 自 Java 9 起是預設回收器（JEP 248），之前是 Parallel。JEP 的理由：「限制停頓時間一般比最大化吞吐量更重要」，改成 G1 這種低停頓回收器「對多數使用者的整體體驗會比吞吐導向的 Parallel GC 更好」。出處 但有一個常被忽略的前提：預設 G1 的條件是「伺服器級機器」——JVM 偵測到「兩顆以上處理器、且實體記憶體大於等於 1792 MB」才算，否則預設 Serial。出處 容器只給 1 顆 CPU 時拿到的是 Serial，這是面試加分點。

版本註記：舊教材裡的 CMS（Concurrent Mark Sweep）在 Java 14 已移除（JEP 363），現在下 -XX:+UseConcMarkSweepGC 只會得到一行「Ignoring option」警告然後用預設回收器。出處 ZGC 在 Java 15 從實驗功能轉正式（JEP 377，不再需要 -XX:+UnlockExperimentalVMOptions）出處；Java 21 加入分代模式，當時要多加 -XX:+ZGenerational（JEP 439）出處；Java 23 起分代是預設（JEP 474）出處；Java 24 起不分代的模式整個移除，ZGenerational 這個選項也拿掉了（JEP 490）出處。所以 Java 21 與 Java 25 答 ZGC 的參數不一樣：21 要加旗標，25 直接 -XX:+UseZGC 就是分代 ZGC。出處

吞吐量要最高選 Parallel，停頓要可預期選 G1，停頓要一毫秒以內選 ZGC，機器小到只有一顆 CPU 就是 Serial

面試官：Stop-The-World 是什麼？G1 怎麼縮短停頓？

一句話定義：Stop-The-World（STW）是回收器把所有應用程式執行緒全部暫停、只剩回收執行緒在跑的那段時間；調校指南把最基本的 Serial 叫作「序列、stop-the-world 回收器」，就是整段回收都在暫停中做完。出處 為什麼一定要停？因為回收器在搬物件、改參考的時候，應用程式若同時在改同一批物件，兩邊會互相踩到。

G1 怎麼做：三招。第一，把堆切成「一組大小相等的區域（region）」，每塊是「配置與回收的單位」；區域大小依最大堆算，「目標是切出大約 2048 塊，上限 32 MB」。這樣每次回收可以只挑幾塊來做，不必整個堆一起。第二，最花時間的「標記活物件」與應用程式同時進行（concurrent marking），用的演算法叫 SATB（Snapshot-At-The-Beginning，「在並行開始那個停頓點對堆拍一張虛擬快照」，之後照快照標），標記結束只剩兩個短的 STW 停頓：Remark 與 Cleanup。第三，有停頓時間目標——-XX:MaxGCPauseMillis 預設 200 毫秒——G1「追蹤過去應用程式行為與回收停頓的資訊，建立成本模型」，用它決定「每次停頓做多少工作」，也就是這一輪挑幾塊區域來搬。出處

要老實講的限制：G1 不是零停頓——官方原文「G1 在 stop-the-world 停頓中執行垃圾回收與空間回收；活物件通常從來源區域複製到一或多塊目的區域，並調整既有參考」，只是它把停頓切小、切得可預期。最壞情況是「疏散失敗」（evacuation failure，要搬的物件找不到地方放），「如果一次回收完全清不出空間，G1 會排一次 Full GC」，對整個堆做原地壓縮，那一次停頓就長了。出處

面試官：強、軟、弱、虛參考差在哪？

一句話定義：一般寫的 Object o = new Object() 是強參考（strong reference）；java.lang.ref 套件另外提供三種「比較弱的參考」，讓程式可以「指著一個物件，但不阻止它被回收」，並在它被回收前後收到通知。四種對應四級可達性，套件文件由強到弱定義：

參考可達性定義（套件文件）官方建議用途
強「不需經過任何 Reference 物件就能到達」——只要強可達就絕不回收一般程式碼
軟（SoftReference）「不是強可達，但經過軟參考可以到達」；類別文件保證「虛擬機丟出 OutOfMemoryError 之前，所有指向軟可達物件的軟參考都已被清除」出處「對記憶體敏感的快取」
弱（WeakReference）「既非強也非軟可達，但經過弱參考可以到達」；回收器一判定物件只剩弱可達，「就會一次清除所有指向它的弱參考」出處「正規化對應表」（canonicalizing mapping，不阻止鍵被回收的對照表，例如 WeakHashMap）
虛（PhantomReference）「非強、軟、弱可達，且已經 finalize 過，但有虛參考指著它」；「虛參考的 get 方法永遠回傳 null」出處「安排物件死後的清理動作」，也可交給 Cleaner 管理

表中引文都出自 java.lang.ref 套件說明。出處 取捨：軟參考當快取看起來省事，代價是回收時機交給 JVM 決定，效能不可預期；弱參考最常見的實務用途是「鍵是別人擁有的物件，不該因為對照表記著它就讓它一直活著」。順帶一提，虛參考定義裡的 finalize 機制官方已不建議用：調校指南寫「不鼓勵使用 finalization，它可能帶來安全、效能與可靠性的問題」，JDK 18 起標為「棄用、預定移除」（JEP 421）。出處

記憶體出問題時

OutOfMemoryError 的種類、洩漏來源與診斷工具

面試官：OutOfMemoryError 有哪幾種？各怎麼排查？

一句話定義：OutOfMemoryError 不是一種錯，是一組錯——訊息文字告訴你是哪一塊記憶體爆了。Oracle 的疑難排解指南逐一列出：

訊息成因（官方說法）先做什麼
Java heap space「物件無法在 Java 堆配置」。官方特別提醒「這不一定代表洩漏」，可能只是 -Xmx 設太小；但長時間執行的應用出現它，「可能表示應用程式無意間持有物件的參考，讓它們無法被回收——這就是 Java 語言版的記憶體洩漏」先確認 -Xmx；還是爆就抓 heap dump 看誰占最多
GC overhead limit exceeded「回收器幾乎一直在跑，Java 程式進展極慢」：一次回收後，若程式「花超過約 98% 的時間在回收、卻回收不到 2% 的堆，連續五次」就丟這個錯；通常是「活資料剛好塞滿堆，幾乎沒空間給新配置」本質同上：堆太小或洩漏。-XX:-UseGCOverheadLimit 能關掉這個檢查，但只是讓它變成另一種 OOM（OutOfMemoryError 的簡稱）
Metaspace「類別中繼資料配置在原生記憶體（Metaspace）」，用量超過 MaxMetaspaceSize 就丟沒設上限卻爆了，找類別載入器洩漏；有設就評估調高
Compressed class space64 位元平台開了壓縮類別指標（把 64 位元的類別指標壓成 32 位元存放以省記憶體）時，類別中繼資料的一部分放在大小固定的區域（CompressedClassSpaceSize，預設 1 GB出處），超過就丟調大 -XX:CompressedClassSpaceSize，或一樣找載入器洩漏
Requested array size exceeds VM limit「要配置的陣列大於 VM 實作上限，跟堆還剩多少無關」程式邏輯錯，改程式
request … bytes for … Out of swap space?「原生堆配置失敗、原生堆可能接近耗盡」——不是 Java 堆，是整個行程的記憶體看 JVM 產生的致命錯誤日誌，用作業系統工具查

表中引文出自 Java 25 疑難排解指南。出處 另外兩種面試常問、但不在那一頁的：

  • unable to create native thread: possibly out of memory or process/resource limits reached——訊息文字定義在 HotSpot 原始碼 os.hpp（搜 OS_NATIVE_THREAD_CREATION_FAILED_MSG），啟動執行緒時作業系統拒絕建立原生執行緒就丟。出處 對應 JVMS 那句「若配不出足夠記憶體給新執行緒建立初始 JVM 堆疊，丟 OutOfMemoryError」出處。排查方向是執行緒數：作業系統的行程執行緒上限、每條執行緒的 -Xss、有沒有執行緒池無上限地開。注意 -XX:+HeapDumpOnOutOfMemoryError 對它無效——官方手冊寫這個選項「只適用於 Java 堆耗盡造成的 OutOfMemoryError……不適用於原生執行緒建立錯誤這類其他資源耗盡」。出處
  • Cannot reserve … bytes of direct buffer memory——ByteBuffer.allocateDirect() 這類直接緩衝區（direct buffer，配置在堆外、讓 I/O 少複製一次的記憶體）超過上限時由 java.nio.Bits 丟出（搜 direct buffer memory）。出處 上限用 -XX:MaxDirectMemorySize 設；沒設時「JVM 自動決定」。出處 它不在 Java 堆裡，所以 -Xmx 調再大也沒用。

怎麼抓 heap dump、看什麼：heap dump（堆轉存，把堆裡所有物件與參考關係一次寫成檔案）有三條路：事前加 -XX:+HeapDumpOnOutOfMemoryError（爆的當下自動寫，配 -XX:HeapDumpPath 指定位置，預設在目前目錄、檔名 java_pid<pid>.hprof）出處；事中用 jcmd <pid> GC.heap_dump filename=heapdump.dmp 或 jmap -dump:format=b,file=snapshot.jmap <pid>。看之前先跑 jcmd <pid> GC.class_histogram（或 jmap -histo）——它列出每個類別有幾個實體、占多少位元組，便宜又常常直接看出兇手。dump 檔用分析工具開（官方頁面舉例 JDK Mission Control、Eclipse Memory Analyzer），看兩件事：哪些物件占最多，以及「從 GC Root 到那個物件的參考鏈」——誰抓著它不放，就是洩漏點。出處

面試官：記憶體洩漏在 Java 怎麼發生？常見來源？

一句話定義：Java 有垃圾回收，所以「忘記釋放」不會洩漏，「忘記放手」才會——官方定義是「應用程式無意間持有物件的參考，讓它們無法被回收」。出處 每一種常見來源都是同一個模式：一個活很久的東西抓著一個本該死掉的東西。

  • static 集合：靜態欄位的壽命跟類別一樣長，而類別「只有在它的類別載入器可被回收時才可能被卸載」，由啟動載入器載的類別「永不卸載」（JLS 12.7）。出處 所以往 static Map 塞東西不拿出來，等於永久持有。
  • 沒關閉的資源：連線、檔案、串流背後是作業系統資源，官方教學要用 try-with-resources——它「宣告一或多個資源」，「資源是程式用完必須關閉的物件」，「這個敘述保證每個資源在敘述結束時被關閉」；任何實作 AutoCloseable 的物件都能放進去。出處
  • ThreadLocal：文件寫「每條執行緒對它那份執行緒區域變數持有隱含參考，只要執行緒活著且 ThreadLocal 實體可存取」；「執行緒消失後」那些副本才可被回收。出處 問題在執行緒池——池裡的執行緒不會消失，值就一直掛在上面，還會被下一個借到這條執行緒的請求讀到。用完呼叫 remove()。
  • 監聽器與回呼：向一個長壽物件（事件來源、全域註冊表）註冊了監聽器卻沒取消註冊，該物件就從長壽物件可達，照可達性定義永遠不是垃圾。出處
  • 類別載入器洩漏（Metaspace 版的洩漏）：只要載入器載出來的任何一個類別還有實體活著、或有人持有那個載入器，整個載入器和它所有類別的中繼資料都留在 Metaspace（由 JLS 12.7 推得）。典型情境是應用伺服器反覆重新部署同一個應用卻不重啟行程。

面試官：常用的 JVM 診斷工具有哪些？

一句話定義：JDK 自帶一整組命令列工具，Oracle 現在的建議是「用最新的 jcmd 取代先前的 jmap、jstack、jinfo，診斷能力更強、效能負擔更低」。出處

類別載入與 JIT

類別怎麼進來、程式碼怎麼變快

面試官：類別載入的三步與父委派模型是什麼？

一句話定義：JVMS 第 5 章把一個類別從 .class 檔到可用分成三步：載入（loading，「找到某個名稱的類別的二進位表示並據此建立類別」）、連結（linking，「把類別結合進 JVM 的執行時狀態，讓它可以執行」）、初始化（initialization，「執行類別初始化方法 <clinit>」，也就是靜態欄位的初始值與 static 區塊）。連結本身又分三小步：驗證（確認二進位結構正確）、準備（建立靜態欄位並設為預設值，例如 0 與 null）、解析（把執行時常數池裡的符號參考換成實際位址）。出處

差別與取捨：面試官愛問「準備」與「初始化」的差別——static int x = 5 在準備階段 x 是 0，初始化才變 5。初始化是懶的（lazy）：JLS 規定類別「在第一次發生下列任一事件之前立刻初始化」——建立它的實體、呼叫它的靜態方法、對它的靜態欄位賦值、讀取它的非常數靜態欄位——載入與連結不會觸發。出處 反過來，Class.forName("X") 文件明寫「會使名為 X 的類別被初始化」，所以舊式 JDBC 程式碼靠它讓驅動程式的 static 區塊執行、把自己註冊進去。出處

三層載入器與父委派：JDK 內建三層——啟動類別載入器（bootstrap，「虛擬機內建的載入器，通常以 null 表示，沒有父載入器」）、平台類別載入器（platform，載「Java SE 平台 API 與其實作類別」）、系統類別載入器（system，「也叫應用程式類別載入器」，載「類別路徑與模組路徑上的類別」）。ClassLoader 文件寫「每個 ClassLoader 實體都有一個關聯的父載入器；被要求找類別時，通常先把搜尋委派給父載入器，再嘗試自己找」；loadClass 的預設演算法就三步：findLoadedClass 看載過沒 → 呼叫父載入器的 loadClass（父是 null 就用啟動載入器）→ 都沒有才呼叫自己的 findClass。出處 這就是父委派模型（parent delegation model；面試常聽到的講法「雙親委派」指的是同一件事——先問父親，父親找不到才自己找）。效果：同一個名稱的類別，由委派鏈上最上層找得到它的載入器定義，自己寫一個 java.lang.String 放進類別路徑也搶不到——而且還有一道硬規定，defineClass 文件寫「名稱以 java. 開頭的類別只能由平台類別載入器或其祖先定義」，否則丟 SecurityException。出處

版本註記：Java 8 以前的第二層叫「擴充類別載入器」，載 jre/lib/ext 下的 jar；Java 9 起這個擴充機制整個移除，「若設定了 java.ext.dirs 系統屬性、或 lib/ext 目錄存在，編譯器與啟動器現在會直接失敗」，rt.jar 也沒了（JEP 220）。出處 面試答「Bootstrap、Extension、Application」三層是 Java 8 的答案，現在中間那層是「Platform」。classpath 與這段歷史的細節見 Java 模組第 6 課〈套件與 Object 類別〉。

載入找檔、連結接線、初始化才跑 static；載入器先問父親、找不到才自己找

面試官：JIT 是什麼？分層編譯做了什麼？為什麼「暖機」後比較快？

一句話定義：JIT（Just-In-Time，即時編譯）是 HotSpot 在程式執行中把位元碼編成機器碼的機制。JVM 指南寫得很直白：「一開始用標準的直譯器啟動應用程式。程式跑起來後，分析程式碼找出效能瓶頸，也就是熱點（hot spots）。HotSpot VM 把效能關鍵的那部分程式碼編譯起來加速，但不編譯很少用到的程式碼（也就是應用程式的大部分）」，並用「自適應編譯器」決定內嵌（inlining，把被呼叫的小方法直接貼進呼叫端）這類最佳化。出處 這也是 HotSpot 名字的由來。

分層編譯做了什麼：HotSpot 有兩個編譯器：C1（client compiler，先求快速編出可用的版本）與 C2（server compiler，負責產生最終、最佳化最深的版本）。分層編譯（tiered compilation）「在 Java SE 7 引入」，官方描述：「沒有分層編譯時，伺服器 VM 用直譯器收集方法的側寫資訊（profiling，記錄哪個分支常走、哪個型別常出現）送給編譯器；有分層編譯時，伺服器 VM 還會用用戶端編譯器先產生一版會自己收集側寫資訊的編譯碼」——編譯碼比直譯器快得多，所以側寫階段本身就跑得快；而且「較快的側寫階段允許側寫更久，可以帶來更好的最佳化」，峰值效能反而更好。分層編譯預設開啟，-XX:-TieredCompilation 可以關。出處 調校指南的預設值表也列著「分層編譯器，同時使用 C1 與 C2」。出處

為什麼要暖機：把上面兩段連起來就是答案——剛啟動時所有程式碼都在直譯器裡跑，慢；要跑一陣子讓熱點浮現、側寫收集夠、C1 再到 C2 逐層編完，速度才到頂。所以壓力測試與效能量測要先跑一段「暖機」（warm-up）再計時，剛部署的服務前幾分鐘延遲偏高也是正常現象。

兩個老面孔

HashMap 的內部與字串池

面試官：HashMap 的內部結構、擴容機制？Java 8 為什麼加紅黑樹？HashMap、ConcurrentHashMap、Hashtable 怎麼選？

一句話定義：HashMap 是一張桶（bucket）陣列：用鍵的 hashCode() 算出落在哪個桶，同一桶裡的多個項目串成鏈結串列。文件定義兩個參數：初始容量（initial capacity，「雜湊表裡桶的數量」，預設 16）與負載因子（load factor，「允許表填到多滿才自動擴容」，預設 0.75）；「當項目數超過負載因子乘以目前容量，雜湊表就重新雜湊（rehash），桶數大約變成兩倍」。出處 所以門檻是 16 × 0.75 = 12，放進第 13 筆（超過 12）時擴到 32。equals() 與 hashCode() 為什麼要一起覆寫，見 Java 模組第 6 課〈套件與 Object 類別〉；集合怎麼選見第 9 課〈集合與泛型〉。

Java 8 為什麼加紅黑樹：紅黑樹是一種自己會保持平衡的搜尋樹。很多鍵撞進同一個桶時，鏈結串列查找退化成 O(n)。JEP 180（Java 8）的解法：「在高碰撞情況下用平衡樹取代鏈結串列存放項目」，最壞情況從 O(n) 改善到 O(log n)。出處 門檻寫在 OpenJDK 原始碼 HashMap.java 的常數裡：同一桶已有 TREEIFY_THRESHOLD（8）個節點、再放進一筆，且表容量已達 MIN_TREEIFY_CAPACITY（64）才樹化（容量還不到 64 時選擇擴容而不樹化），縮回 UNTREEIFY_THRESHOLD（6）個就退回串列；原始碼註解說明樹節點「大約是普通節點的兩倍大」，所以只在值得的時候用。出處

三個怎麼選：

執行緒安全null 鍵值官方定位
HashMap否——「不是同步的」，多執行緒要改結構「必須外部同步」允許單執行緒或外面已經有鎖的預設選擇
Hashtable是——整張表一把鎖都不允許文件自己說：「不需要執行緒安全就用 HashMap；需要執行緒安全又要高並行就用 ConcurrentHashMap」——也就是兩種情況都不該選它
ConcurrentHashMap是——「讀取操作不加鎖，也不支援鎖住整張表」；「讀取（含 get）一般不會阻塞」，可與更新重疊都不允許多執行緒共用的對照表

三段引文分別出自各自的類別文件。HashMapHashtableConcurrentHashMap ConcurrentHashMap 內部怎麼做到讀不加鎖，本課不展開。

面試官：字串池是什麼？intern() 做什麼？為什麼 String 不可變？

一句話定義：String 文件第一段：「字串是常數；建立後值不能改變……因為 String 物件不可變，它們可以被共用。」出處 「可以被共用」就是字串池存在的前提。字串池（string pool）是 String 類別「私下維護的一個字串池」，intern()「若池裡已有 equals 相等的字串就回傳池裡那個，否則把這個字串放進池並回傳它」；而且「所有字面值字串與字串型別的常數表達式都會被 intern」。出處 不可變的鋪陳與 == 對 equals() 的差別見 Java 模組第 3 課〈物件與類別〉。

差別與取捨——那組經典的 == 題：JLS 3.10.5 明講「字串字面值永遠指向同一個 String 實體」，因為字面值與常數表達式「被 intern 以共用唯一實體，如同執行了 String.intern」。規格附的例子："Hello" == "Hel" + "lo" 是 true（兩邊都是編譯期常數），"Hello" == "Hel" + lo（lo 是變數）是 false——執行期串接出來的是新物件，加上 .intern() 後才又是 true。出處 new String("Hi") 也一樣是堆上的新物件，不在池裡。

為什麼要不可變、池在哪裡：理由都是「共用」的推論——池裡的字串被很多變數共用，若能改，改了一個大家都被改；值不變所以 hashCode() 可以算一次存起來（String.java 裡的欄位 hash 註解就寫「快取這個字串的雜湊碼」），HashMap 用字串當鍵才快出處；多執行緒讀同一個字串也不需要鎖。至於池的位置：Java 8 移除永久代時，JEP 122 寫明「類別中繼資料配置在原生記憶體，並把 intern 的字串與類別靜態變數搬進 Java 堆」——所以現在字串池在堆裡，池裡沒人參考的字串一樣會被回收，「intern 太多會爆 PermGen」是永久代時代的老答案。出處

重點整理

  • 五塊執行時資料區：堆與方法區全執行緒共用，JVM 堆疊、pc 暫存器、本機方法堆疊每條執行緒一份；遞迴太深是 StackOverflowError。
  • 堆分年輕代（Eden＋兩塊 Survivor）與老年代，依據是「多數物件很快就死」；活過幾輪複製才晉升。-Xms／-Xmx 伺服器通常設相等。
  • Java 8 起類別中繼資料放原生記憶體的 Metaspace（JEP 122），預設無上限，-XX:MaxMetaspaceSize 才是上限；Metaspace 爆掉幾乎都是類別載入器洩漏。
  • 死活看可達性（從 GC Root 走得到才活），不用參考計數，所以循環參考不是問題；四種參考強度：強不回收、軟快取、弱對照表、虛做死後清理。
  • G1 自 Java 9 預設（JEP 248，前提是兩顆 CPU 以上與 1792 MB 以上，否則 Serial）；吞吐選 Parallel、一毫秒停頓選 ZGC；CMS 在 Java 14 移除；ZGC 在 Java 23 起預設分代、24 起只剩分代。
  • OOM 看訊息：Java heap space／GC overhead limit exceeded 是堆、Metaspace 是類別、unable to create native thread 是執行緒數、direct buffer memory 是堆外。排查順序：jcmd Thread.print → GC.class_histogram → heap dump；長期看 JFR。
  • 類別載入三步是載入、連結、初始化；載入器三層是啟動、平台、應用程式（Java 9 起沒有 Extension），先問父載入器再自己找。JIT 靠直譯器找熱點、C1 先編再側寫、C2 深度最佳化，所以要暖機。
