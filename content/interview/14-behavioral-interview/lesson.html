行為面試，STAR 法，五類題型

把經歷講成故事，不是流水帳

行為面試（behavioral interview）問的是「你過去真的做過什麼」，不是「你覺得該怎麼做」。Amazon 的面試指引寫：「我們的面試以行為題為主，也就是請你分享過去經驗裡的真實例子。」出處 Google 也說行為題「是要引出具體的例子，而不是『我總是會做 X』這種話」出處，而且「每位候選人都用同一套明確的評分標準評估」出處。

STAR 法是把經歷拆成四段講：情境（Situation，當時發生什麼）、任務（Task，你負責什麼）、行動（Action，你一步一步做了什麼）、結果（Result，最後怎麼樣、學到什麼）。Amazon 與 Google 都列它為建議的回答結構。出處出處 工程師套用時有三個容易漏的地方：

  • 行動講「我」，不講「我們」。Amazon 原句：「即使是團隊合作，也請聚焦在你個人的貢獻，用『我』而不是『我們』比較有幫助。」出處
  • 結果要有數字。同一頁寫「有任何數字或具體成果可以佐證，那更好」。出處
  • MIT 職涯中心建議情境、任務、行動、結果的時間大約 20%、10%、60%、10%。情境與任務各一兩句，行動佔大半，結果收尾（most of your response should focus on your Actions）。出處 整段最好兩分鐘內講完（本課的建議）。

常見行為題可以歸成五類。下表每類給一個虛構的工程師範例，一句話濃縮 STAR 四段；建議每類從自己的經歷挑一個真實故事照這個形狀改寫。

題型面試官想看什麼虛構範例（情境 → 任務 → 行動 → 結果）
衝突怎麼跟意見不同的人談定對帳系統要加欄位，上游堅持用字串、你認為該用數值 → 你負責定規格 → 把兩種做法對下游三個系統的影響列成表去談 → 採數值加相容轉換，如期定案
失敗會不會誠實面對，事後改了什麼轉帳 API 呼叫端逾時重送，同一筆被處理兩次 → 你是負責人 → 先手動沖正（把做錯的那筆反向沖銷回去）止血，再加冪等鍵（同一個請求識別碼只處理一次）與測試 → 沒再發生，「對外 API 一律要冪等鍵」進了團隊檢查清單
壓力時間緊時怎麼排優先順序月結批次前一天發現要跑六小時、超過作業窗口 → 隔天前得跑進去 → 用執行計畫找最慢的查詢補索引，不相依的兩段改平行 → 兩個半小時跑完，隔月正式重構
學新東西學習方法，有沒有回饋團隊服務要搬上 Kubernetes，全組沒人用過 → 你自願先搬一個非關鍵服務 → 兩週讀官方文件、在測試環境練，把探針、資源限制、設定檔整理成範本 → 後續五個服務照範本搬，平均各三天
影響別人沒有職權時怎麼讓別人願意改程式碼審查常一天沒人看 → 想讓審查變成習慣 → 自己每天固定審別人的，週會用資料講卡住的天數，提議「兩人核可才能合併」 → 三個月後平均等待從三天降到半天

失敗題不必挑「其實是別人的錯」的故事。Amazon 寫「不是每個故事都得是成功的，重要的是你學到什麼、成長了多少」。出處

開場

「介紹一下你自己」的兩分鐘骨架

這題幾乎每場都有，也是最能事先準備的。它不是念履歷，是替接下來四十分鐘定調：讓面試官知道該往哪裡追問。分三段：

前 30 秒：現在做什麼、做多久、負責哪一塊系統。一句話。
中間 60 秒：兩件代表作挑跟職位最相關的兩件，各用「做了什麼、結果是什麼」兩句講，不展開。這就是你希望被追問的地方。
最後 30 秒：為什麼是這裡把你的下一步跟這個職位接起來，講交集，不講「貴公司很有名」。
範例台詞

「我是後端工程師，做了三年，負責一套 Spring Boot 寫的批次對帳系統。最能代表我的兩件事：一是把月結批次從六小時縮到兩個半小時，靠補索引和把不相依的步驟平行化；二是參與把六個服務搬上 Kubernetes，我自願先搬第一個、把範本整理出來，其他五個照範本搬。接下來想做交易量更大、對正確性要求更高的系統，所以來面試這個職位。」

專題表達

講專題的五步

〈Java 基礎快答〉有一份訂房網站專題的範例答法，本課把它抽成任何專題都能套的骨架。專題題跟行為題的差別是面試官想看技術判斷，所以第三步「決定與取捨」是重心，不是功能清單。Google 寫得很直接：「重點不只是給出『正確』答案，面試官要看的是思考過程，而不是答案本身。」出處

一、問題

替誰解決什麼？一句話。「替客服做一個查客戶交易紀錄的內部系統」就夠。

二、為什麼難

資料量、正確性要求、要整合的舊系統多、時程短，挑最真實的一個。

三、決定與取捨

有哪些選項、選了哪個、放棄了什麼。「我選 A 不選 B，因為在我們的情況下 B 的代價是……」這句是得分點。

四、結果與數字

上線了沒、多少人用、效能或錯誤率前後對照。沒精確數字就講量級。

五、事後會改什麼

回頭看哪個決定會改。這步證明你會反省，也省掉「這設計有什麼缺點」那句追問。

通用範本

「這個專題是替＿＿做＿＿。最難的是＿＿，因為＿＿。我考慮過＿＿和＿＿，最後選＿＿，代價是＿＿。上線後＿＿（一個數字）。重做一次我會把＿＿改成＿＿，因為後來發現＿＿。」

技術經歷

把 K8s、Spring、資料庫的經驗講成有數字的一句話

「你遇過最有挑戰的技術問題」常被答成一串技術名詞。Google 給了一個公式：「達成了 X，以 Y 衡量，靠的是做了 Z。」出處 先用它講出一句話，面試官有興趣再展開成完整的 STAR：

  • K8s：「把部署失敗率從每月三、四次降到幾乎零，靠替每個服務補上就緒探針與資源限制，並把滾動更新的最大不可用數設成零。」
  • Spring：「把一支報表 API 從八秒降到一秒內，靠找出交易範圍設錯造成連線被長期佔住，改成唯讀交易並加兩層快取。」
  • 資料庫：「把月結批次從六小時縮到兩個半小時，靠用執行計畫找到沒走索引的查詢補索引，並把不相依的兩段改成平行跑。」

數字要是真的量過的，被追問「怎麼量」要答得出來。

反問

反問面試官的十個問題

Amazon 寫「我們會試著在每場面試結尾留幾分鐘讓你問問題」。出處 這幾分鐘是你在挑公司，也是面試官在看你關心什麼。挑三到四個問，其餘留給下一輪：

  1. 進來之後，前三個月最希望我完成什麼？
  2. 團隊現在最大的技術債（為了趕時間先湊合的做法，之後得花時間補）是什麼？有還債的計畫嗎？
  3. 一個功能從寫完到上線要經過哪些關卡？多久上線一次？
  4. 有值班嗎？一個月輪幾次、半夜被叫醒的頻率如何？
  5. 技術決策怎麼做？工程師的意見怎麼進到決策裡？
  6. 程式碼審查怎麼進行？測試覆蓋率大約多少？
  7. 目前 Java、Spring Boot、資料庫的主要版本？有升版計畫嗎？
  8. 系統出事後的檢討怎麼做？追究個人還是看流程？
  9. 團隊跟法遵、資安部門怎麼合作？上線前有哪些檢查？
  10. 你自己在這個團隊最喜歡跟最想改變的各是什麼？

薪資福利、幾點下班、多久升遷留到人資那關；官網查得到的事不要問。

銀行業

法遵與資安意識怎麼自然帶到

銀行後端的面試官多半會留意你有沒有「碰錢跟碰個資要小心」的直覺。硬講像背稿，比較好的做法是在 STAR 的行動段順帶提一句。四件常帶到的事：

個資遮罩身分證字號、卡號、手機號碼顯示與寫日誌時只露一部分。台詞：「日誌裡我把卡號遮到只剩後四碼。」
稽核紀錄誰在什麼時間改了哪筆資料，留下不能改的紀錄。台詞：「所有異動都寫稽核紀錄，含操作人與改前改後的值。」
四眼原則重要操作要一個人做、另一個人核可才生效。台詞：「正式環境的資料修正都要另一個人核可。」
最小權限與測試資料服務只拿需要的權限；測試環境不用真實客戶資料；真的要用，先去識別化（把能認出是誰的欄位拿掉或改掉）。台詞：「測試資料是從正式環境抽樣再遮罩的。」

不必引法規條號，面試官看的是習慣，不是背誦。

薪資與時程

薪資與到職時程怎麼回

這兩題多在人資那關出現，原則是保守、給區間、不喊價。

  • 先確認結構再講數字。銀行薪資常是「月薪乘保證月數再加績效獎金」，先問保證幾個月、獎金怎麼算，再談年薪區間；只講月薪，遇到保證月數少的公司，年薪反而變低。
  • 給區間，不給單點。下限是你真的願意接受的數字，一種常見做法是上限抓比目前多兩到三成。台詞：「目前年薪約＿＿，期望＿＿到＿＿，實際數字願意看職級與福利再談。」
  • 不喊價、不比價。「另一家開多少所以你們要開多少」在銀行通常沒好結果，因為同一職級多半有固定的薪資帶（上下限）。
  • 時程講做得到的。現職要交接就照實說「需要一個月」，不為討好答兩週再跳票。可以先問對方期望何時到職，再回「可以配合」或「最快是＿＿」。

面試前一週：把面試集其他二十二課排進七天

面試前一週不學新東西，把懂的講順。每天一個主題，先看「重點整理」，再挑兩三題出聲講；最後一天留給本課。

技術題答「定義、差別與取捨、實務註記」，行為題答「情境、任務、行動、結果」，兩套骨架各背一次就夠

重點整理

  • 行為題問「你真的做過什麼」；用 STAR 法講，行動段用「我」，結果段要有數字。
  • 五類行為題各備一個真實故事；失敗題挑真的錯在自己、事後有改變的那個。
  • 自我介紹兩分鐘三段：現在、兩件代表作、為什麼是這裡；講完就停。
  • 專題五步：問題、為什麼難、決定與取捨、結果與數字、事後會改什麼；取捨是得分點。
  • 技術經歷先講成「達成 X、以 Y 衡量、靠 Z」一句話，被追問再展開。
  • 法遵與資安意識放在行動段順帶提，不背條號。
  • 薪資保守、給區間、不喊價，先確認保證月數與獎金結構；時程講做得到的。
