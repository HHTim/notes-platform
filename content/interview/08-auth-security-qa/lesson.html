認證基礎

誰、能做什麼、憑證怎麼帶

答題公式：先一句話定義，再講差別與取捨，最後補協定編號或版本。版本主軸：Spring Security 依撰寫時的現行版 7.1 官方文件，OWASP Top 10 用 2025 版。Filter 鏈與登入流程見 Spring 模組第 9 課〈Spring Security 認證與授權〉，CORS、CSRF、雜湊與鹽見第 10 課〈網站安全三題：CORS、CSRF、密碼學〉，Gateway 驗 Token 見面試集第 2 課〈後端與雲端面試題庫〉；本課補協定本身與演算法的名字。

面試官：認證與授權差在哪？Session 對 Token 各自的優缺點？

一句話定義：認證（authentication）回答「你是誰」，授權（authorization）回答「你能做什麼」。網銀輸入帳號密碼加簡訊驗證碼是認證；登入後能不能查別人的帳戶是授權。

差別與取捨：Session 是「伺服器記得你」：狀態存伺服器，瀏覽器只拿識別碼放 Cookie；Token 是「你自己帶著證明」：伺服器簽發一段字串，每次請求帶上，驗簽章就知道你是誰。Session 登出、強制下線立刻生效，成本是多台伺服器要共用狀態；Token 無狀態、跨服務好傳遞，代價是簽出去就難以即時作廢——OWASP 的 JWT 速查表點破：一做拒絕清單「工作階段就不再完全無狀態」（user sessions won't be completely stateless anymore）。出處 網銀網頁走 Session 就夠，行動銀行 App 與多個後端服務之間走 Token。

面試官：Basic 認證與 Bearer 認證的格式與風險？

一句話定義：Basic 是把「帳號:密碼」用 Base64 編碼後放進 Authorization 標頭（RFC 7617 第 2 節）出處；Bearer 是把一段權杖（token）放進同一個標頭，格式 Authorization: Bearer mF_9.B5f-4.1JqM（RFC 6750 第 2.1 節）。出處

風險：Basic「除非搭配 TLS 這類外部安全系統，否則不被視為安全的認證方法」，因為帳密「以明文傳送」——Base64 是編碼不是加密。出處 Bearer 依 RFC 6750 第 1.2 節是「任何持有它的一方都能使用」的權杖，所以第 5.3 節的建議全繞著「別外洩」：一律走 TLS、簽發「短效（一小時以內）」的權杖、放進 Cookie 就「必須防範跨站請求偽造」。出處 JWT 是格式、Bearer 是帶法，兩者可各自替換。

JWT

三段、簽章、過期與撤銷

面試官：JWT 三段是什麼？簽章怎麼驗？

一句話定義：JWT（JSON Web Token）依 RFC 7519 第 1 節是「一種精簡、可放進網址的方式，用來表示要在兩方之間傳遞的聲明」（a compact, URL-safe means of representing claims）；聲明（claim）就是一句「關於誰的什麼陳述」。出處

三段與驗法：第 3 節：JWT「以句點分隔的一串網址安全片段表示，每段是 base64url 編碼」——標頭（如 {"typ":"JWT","alg":"HS256"}）、聲明集合、簽章。出處 第 4.1 節登記了 iss、sub、aud、exp、nbf、iat、jti 七個常用聲明。出處 驗證是拿前兩段重算簽章跟第三段比（HS256 用共享祕密金鑰，RS256 用私鑰簽、公鑰驗），再照第 7.2 節檢查 exp、aud 等聲明，「任何一步失敗，JWT 就必須被拒絕」。出處 簽章只保證沒被改、不保證沒被看：OWASP 說有簽章的 JWT「提供完整性與真實性，但不提供機密性」。出處

面試官：alg 改成 none 與演算法混淆攻擊是什麼？怎麼防？

成因：標頭的 alg 是「送來的人」宣告的，驗證方照單全收，就等於讓攻擊者決定怎麼驗。RFC 8725 第 2.1 節列了兩種：「攻擊者可以把演算法改成 none，某些函式庫會相信這個值，不檢查任何簽章就『驗證』通過」；以及「RS256 可以被改成 HS256，某些函式庫會……把 RSA 公鑰當成 HMAC 的共享祕密」——公鑰本來就公開，拿它當金鑰就能簽出通得過的權杖。出處

防法：RFC 8725 第 3.1 節：「函式庫必須讓呼叫者指定一組支援的演算法，且不得使用其他演算法」，「每把金鑰必須只搭配一種演算法」（each key MUST be used with exactly one algorithm）。出處 白話：演算法由驗證端寫死，不從權杖讀。第 3.8、3.9 節還要求驗 iss 與 aud：發給多個服務的權杖「必須包含 aud」，收到方「必須驗證」。出處

面試官：JWT 怎麼過期、怎麼撤銷？Refresh Token 的角色？Token 放 Cookie 還是 localStorage？

過期與撤銷：過期靠 exp；撤銷是弱項，因為簽出去就不會回頭問伺服器。OWASP 給的路是拒絕清單（「通常以 jti 與 iss 為鍵」，代價是又有狀態），並說「權杖重複使用可以靠短過期時間緩解」。出處

Refresh Token：RFC 6749 第 1.5 節：「Refresh token 是用來取得 access token 的憑證」，「只用於授權伺服器，絕不送往資源伺服器」（never sent to resource servers）。出處 所以存取權杖短效、更新權杖長效，撤銷就撤更新權杖；RFC 9700 第 4.14 節再加「更新權杖輪替」：每次換發給新的、舊的作廢，外洩的那把一被重複使用就露餡。出處

放哪裡：localStorage 對頁面上任何 JavaScript 開放，被 XSS（跨網站指令碼，把惡意程式塞進網頁執行）打中就整包被讀走。OWASP 工作階段管理速查表：「不要把認證權杖、JWT、更新權杖或任何憑證存在 localStorage 或 sessionStorage……改用 HttpOnly、Secure、SameSite=Strict 的 Cookie」。出處 Cookie 會被瀏覽器自動帶，所以要另外防 CSRF（第 10 課）。

簽章只保證沒被改；演算法由驗證方寫死；存取權杖短效、更新權杖輪替；憑證放 HttpOnly Cookie 再防 CSRF

OAuth 2.0 與 OIDC

授權框架、身分層與企業單一登入

面試官：OAuth 2.0 的四個角色與授權碼流程？為什麼不建議 Implicit 流程？

一句話定義：OAuth 2.0（RFC 6749）是授權框架，解決「讓第三方應用程式在不拿到你密碼的情況下，代替你存取你的資料」。第 1.1 節的四個角色，用「記帳 App 讀你的銀行交易明細」對照：資源擁有者（resource owner）是你、用戶端（client）是記帳 App、授權伺服器（authorization server，「認證資源擁有者並取得授權後，簽發 access token」）是銀行的登入授權頁、資源伺服器（resource server，「以 access token 回應請求」）是銀行開放 API。出處

授權碼與 Implicit：第 1.3.1 節：用戶端「把資源擁有者導向授權伺服器」，授權伺服器認證並取得同意後「帶著授權碼導回用戶端」，用戶端再拿授權碼換權杖；好處是「資源擁有者的憑證絕不會與用戶端共享」。出處 Implicit（隱含）流程是第 1.3.2 節的簡化版：略過授權碼「直接簽發 access token」給瀏覽器，權杖「可能暴露給其他能存取瀏覽器的應用程式」。出處 2025 年 1 月發佈的 RFC 9700 第 2.1.2 節把話講死：「用戶端不應使用隱含流程」（clients SHOULD NOT use the implicit grant）。出處 現在單頁應用程式也走「授權碼加 PKCE」。

面試官：PKCE 解決什麼？

一句話定義：PKCE（Proof Key for Code Exchange，RFC 7636，念作 pixy）解決「授權碼被攔截後被別人拿去換權杖」。第 1 節：公開用戶端「容易受到授權碼攔截攻擊」，攻擊者「在未受 TLS 保護的路徑上攔截授權碼」，例如同一支手機上的另一個 App。出處 行動銀行 App 就是公開用戶端：裝在使用者手機上，藏不住任何密鑰。

機制：第 4 節：用戶端每次先產生隨機的 code_verifier，把它的 SHA-256 雜湊（code_challenge）隨授權請求送出；換權杖時送出原本的 verifier，授權伺服器「在回傳權杖前驗證 code_verifier」。出處 攔到授權碼的人沒有 verifier，換不到權杖。RFC 9700 第 2.1.1 節：「公開用戶端必須使用 PKCE」，機密用戶端「建議使用」。出處

面試官：OAuth 2.0 與 OIDC 差在哪？ID Token 對 Access Token？

一句話定義：OAuth 2.0 管授權，沒有定義「這個人是誰」；OIDC（OpenID Connect）補上這層。規格第 1 節：「OpenID Connect 1.0 是架在 OAuth 2.0 協定之上的簡單身分層」（a simple identity layer on top of the OAuth 2.0 protocol），讓用戶端能「驗證終端使用者的身分」。出處

面試官：SAML 是什麼、跟 OIDC 差在哪？企業單一登入為什麼還在用 SAML？

一句話定義：SAML（Security Assertion Markup Language）依 OASIS 技術總覽第 2 節是「以 XML 為基礎、在線上商業夥伴之間交換安全資訊的框架」（an XML-based framework for describing and exchanging security information）；第 3.2 節說「跨網域的網頁單一登入可說是 SAML 最重要的使用情境」：身分提供者（負責登入的一方）向服務提供者（你要用的系統）斷言「這個使用者已在它那裡認證」。出處

差別與取捨：做的事一樣，差在格式與年代：SAML 用 XML 斷言、靠瀏覽器表單 POST 傳遞，2.0 版 2005 年定稿；OIDC 用 JSON 與 JWT、走 OAuth 2.0 的導向與 REST 呼叫，2014 年定稿，天生適合行動 App。企業內部還在用 SAML，是因為帳號目錄、人資與內部系統多在 OIDC 普及前就接了 SAML，換掉要動每一個服務提供者；Spring Security 也因此「提供完整的 SAML 2 支援」。出處

密碼保存

慢雜湊、參數，以及 Spring Security 怎麼包

面試官：密碼怎麼存？為什麼 MD5／SHA-256 加鹽也不夠？bcrypt、scrypt、Argon2、PBKDF2 怎麼選？

一句話定義：只存「專為密碼設計的慢雜湊」結果，不存明文、不加密、不用一般雜湊。OWASP 密碼保存速查表：「SHA-256 這類快速雜湊演算法不適合保存密碼，因為它們讓攻擊者能快速進行大量猜測」（Fast hashing algorithms such as SHA-256 are not suitable for password storage）。出處

為什麼加鹽還不夠：鹽（salt，每筆密碼各不相同的隨機值）擋的是「事先算好一張表、一次比對所有人」，但不會讓「猜一次」變慢；MD5、SHA-1「設計上就是要快」，專用演算法「應該慢，而且可以改變工作因子來調整有多慢」。出處 一句話：鹽讓攻擊者不能一次破所有人，慢雜湊讓破一個人也很貴。

演算法OWASP 建議的最低參數什麼時候選
Argon2id「記憶體 19 MiB、迭代 2 次、平行度 1」首選；「2015 年密碼雜湊競賽的優勝者」
scrypt「成本參數 2 的 17 次方、區塊大小 8、平行參數 1」「Argon2id 不可用時」
bcrypt「工作因子 10 以上，密碼長度上限 72 位元組」「舊系統」沿用；超長會被截斷
PBKDF2「600,000 次以上，內部雜湊 HMAC-SHA-256」「需要符合 FIPS-140 合規時」

參數出自同一頁的總結建議。出處 密碼規則也要答對：NIST SP 800-63B-4 第 3.1.1.2 節要求單因子密碼「至少 15 個字元」、「不得強加其他組成規則」（SHALL NOT impose other composition rules）、「不得要求定期更換密碼」、建立時「必須與含常見或已外洩密碼的封鎖清單比對」。出處 「每 90 天改密碼、必須含符號」已不是最佳實務。

面試官：Spring Security 的 DelegatingPasswordEncoder 做了什麼？

一句話定義：帶前綴的分派器：儲存格式是 {id}encodedPassword，編碼時用現行建議的演算法並標上 id，比對時看前綴決定交給哪個 PasswordEncoder，新舊格式可以共存。

為什麼要有它：官方文件說直接把預設換成 bcrypt 會撞到「很多應用程式用的是無法輕易遷移的舊編碼」、「最佳實務還會再變」；它的承諾是「確保密碼以現行建議編碼」、同時「允許以現代與舊格式驗證密碼」。出處

PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
String stored = encoder.encode("password");
// {bcrypt}$2a$10$dXJ3SW6G7P50lGmMkkmwe.20cQQubK3.HZWzG3YB1tlRy.fqvM/BG
encoder.matches("password", stored);   // 照前綴 {bcrypt} 交給 BCryptPasswordEncoder 比對

追問時要補的：把演算法寫在前面「不是問題，因為密碼的保存不依賴演算法保密」。BCryptPasswordEncoder「預設強度 10」，官方建議調到「驗證一組密碼大約花 1 秒」；也因為每次驗證都貴，官方「鼓勵把長期憑證換成短期憑證」——呼應本課第一題。出處

Spring Security 資源伺服器

API 怎麼驗別人簽的 JWT

面試官：Spring Security 當 OAuth 2.0 資源伺服器怎麼驗 JWT？

一句話定義：資源伺服器就是「收 Bearer token 的 API」。Spring Boot 之下兩步：加 spring-security-oauth2-resource-server 與 spring-security-oauth2-jose 兩個相依，再告訴它授權伺服器在哪：

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://idp.example.com/issuer

issuer-uri 是 JWT 裡 iss 聲明的值，資源伺服器「用它自動設定、探索授權伺服器的公鑰，接著驗證進來的 JWT」。出處 對應的預設 SecurityFilterChain：

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests((authorize) -> authorize
            .anyRequest().authenticated()
        )
        .oauth2ResourceServer((oauth2) -> oauth2.jwt(Customizer.withDefaults()));
    return http.build();
}

它實際做了什麼：官方列出收到 JWT 時的三件事：「用從 jwks_url 端點取得、與 JWT 相符的公鑰驗證簽章」、「驗證 exp 與 nbf 時間戳記以及 iss 聲明」、「把每個 scope 對應成前綴 SCOPE_ 的權限」；金鑰換新時「會自動輪替」。出處 aud 預設不驗，多個 API 共用同一個授權伺服器時要自己加驗證器。面試集第 2 課講的「Gateway 驗完、內部服務仍要重新授權」，在 Spring 裡就是每個資源伺服器各自掛這段。

OWASP 與常見漏洞

十大風險、四種攻擊的防法、CSP 與機密

面試官：OWASP 十大風險現行版有哪幾項？各給一個例子與防法

一句話定義：OWASP Top 10 是 OWASP 基金會定期整理的「網頁應用程式最嚴重的十類風險」，現行是 2025 年版。出處 官方導言點出跟 2021 年版的差別：「SSRF 已併入」存取控制失效，「軟體供應鏈失效」與「例外狀況處理不當」是新面孔。出處

官方編號名稱銀行情境的例子 → 防法
A01存取控制失效改網址上的帳號編號就看到別人的對帳單 → 「除公開資源外，預設拒絕」，只在伺服器端檢查出處
A02安全設定錯誤正式環境開著除錯頁 → 各環境同一套強化設定
A03軟體供應鏈失效引進被植入惡意程式的套件 → 追蹤相依、鎖定版本
A04密碼學失效密碼用 MD5 存 → 本課密碼保存那節
A05注入轉帳備註被拼進 SQL → 參數化查詢
A06不安全的設計忘記密碼只問「母親的姓名」 → 設計期做威脅建模
A07認證失效「允許帳密填充這類自動化攻擊」出處 → 多因子認證、限制嘗試次數
A08軟體或資料完整性失效反序列化不受信任的資料 → 只收受信任來源
A09安全記錄與告警失效被撞庫三天沒人知道 → 登入失敗要記錄並告警
A10例外狀況處理不當驗證服務逾時就當作通過 → 失效時關閉

十項名稱依官方 2025 年清單；未另掛出處的例子是依各類別定義整理的。

面試官：SQL 注入、XSS、CSRF、SSRF 各怎麼防？

SQL 注入成因：使用者輸入被拼進 SQL 字串，輸入就能改變查詢結構。防法：OWASP「主要防禦第一項」是「預備語句（參數化查詢）」，Java 對應 PreparedStatement；「跳脫所有使用者輸入」被標為「強烈不建議」。出處
XSS成因：使用者輸入原樣放進 HTML，瀏覽器把它當程式執行。防法：「框架的安全保護、輸出編碼與 HTML 淨化能提供最好的保護」；CSP 只是「額外的一層防禦」。出處
CSRF成因：瀏覽器自動帶 Cookie，惡意網站借你的登入狀態送請求。防法：「先用框架內建的 CSRF 防護」，「有狀態的軟體用同步權杖模式」、「無狀態的用雙重提交 Cookie」；SameSite 屬性可加，但「任何能用 GET 改狀態的操作，SameSite=Lax 都擋不住」。出處 Spring Security 的權杖怎麼帶見第 10 課。
SSRFSSRF（Server-Side Request Forgery，伺服器端請求偽造）成因：應用程式拿使用者給的網址去發請求（下載頭像、呼叫 webhook），攻擊者就能讓伺服器替他連內網或雲端中繼資料服務。防法：目標「只會是已識別、受信任的應用程式」時用允許清單；必須連任意外部位址時，封鎖清單是「最後手段」，加上網路層隔離。出處

面試官：CSP 標頭在擋什麼？跟 XSS 的關係？

一句話定義：CSP（Content Security Policy，內容安全政策）是伺服器用回應標頭告訴瀏覽器「這個頁面允許從哪裡載入什麼」。W3C 的定義：「讓網頁開發者能控制特定頁面可以取得或執行哪些資源的機制」（control the resources which a particular page can fetch or execute）出處；MDN 說它「主要用來防禦跨網站指令碼攻擊」。出處

Content-Security-Policy: default-src 'self'; img-src 'self' example.com

對 XSS 真正有用的是限制指令碼：MDN 說「nonce 是限制 script 與 style 載入的建議做法」——伺服器每次回應產生隨機值放進 script-src，也放進頁面每個 script 標籤的 nonce 屬性，「就算攻擊者能把 JavaScript 插進頁面，他不知道伺服器會用哪個 nonce，瀏覽器就會拒絕執行」；導入先用 report-only 模式，只回報不擋。出處 結論：CSP 是 XSS 發生後讓注入的程式跑不起來的第二道牆，第一道永遠是輸出編碼。

面試官：機密（API 金鑰、資料庫密碼）該放哪？

一句話定義：不進程式碼、不進 git、不進映像檔；正式環境從集中式的機密管理服務取得，並能輪替與稽核。OWASP 機密管理速查表的反面教材：「很多組織把它們以明文寫死在原始碼裡，散落在設定檔與組態管理工具中」。出處

三個層次：環境變數是及格線——比寫死好，但「通常對所有行程可見，可能被寫進日誌」，「除非其他方法不可行，否則不建議」。正解是機密管理服務：OWASP 建議「導入集中式的機密管理方案」，例子有 HashiCorp Vault、CyberArk Conjur，雲端平台也各有自己的；存取權要限縮。出處 銀行情境：資料庫密碼要能定期輪替而不重新部署。

程式碼裡不該出現任何一把鑰匙；環境變數是及格線，機密管理服務加輪替與稽核才是正解

重點整理

  • 認證是「你是誰」、授權是「你能做什麼」；Session 能立刻撤銷但要存狀態，Token 無狀態但難撤銷；Basic 必須配 TLS，Bearer 誰拿著誰能用、要短效。
  • JWT 三段是 base64url 的標頭、聲明、簽章；簽章保證沒被改、不保證沒被看；演算法由驗證方寫死（RFC 8725 第 3.1 節），否則 alg 改 none 與 RS256 換 HS256 都能偽造權杖。
  • 撤銷靠短效存取權杖加更新權杖輪替；憑證不放 localStorage，放 HttpOnly、Secure、SameSite 的 Cookie 再防 CSRF。
  • OAuth 2.0 走授權碼流程，隱含流程「不應使用」，公開用戶端「必須」用 PKCE；OIDC 是 OAuth 2.0 上的身分層，ID Token 給用戶端、Access Token 給 API；SAML 用 XML 做同一件事。
  • 密碼存慢雜湊：Argon2id 首選、scrypt 次之、bcrypt 工作因子 10 以上且限 72 位元組、PBKDF2 留給 FIPS；NIST 現行版要求至少 15 字元、不強制組成規則、不定期換密碼。
  • DelegatingPasswordEncoder 用 {id} 前綴讓新舊格式共存；資源伺服器給 issuer-uri 加 jwt() 就會驗簽章、exp、nbf、iss，aud 要自己加。
  • OWASP Top 10:2025：SSRF 併入存取控制失效、供應鏈失效與例外狀況處理不當是新面孔；注入用參數化查詢、XSS 用輸出編碼加 CSP、CSRF 用框架權杖、SSRF 用允許清單；機密進機密管理服務。
