IoC 容器

容器、Bean 與生命週期

答題公式：先一句話定義，再講差別與取捨，最後補版本或實務註記。課文依撰寫時的現行穩定版官方文件寫（Spring Framework 7.0、Spring Boot 4.1）；Spring 6 與 Spring Boot 3 同樣適用的地方直接寫，兩代有差的地方會標出來。

面試官：IoC 與 DI 差在哪？Spring 容器做了什麼？

一句話定義：控制反轉（Inversion of Control，IoC）是一種原則——物件不再自己建立或尋找它需要的相依物件，改由容器負責；依賴注入（Dependency Injection，DI）是實現這個原則的一種做法——容器在建立物件時把相依物件送進去。

差別與取捨：官方文件把兩者放在同一段講：IoC「也稱為依賴注入」，物件「只透過建構子參數、工廠方法參數，或建立之後設定的屬性」宣告自己需要什麼，「容器在建立 Bean 時注入這些相依」，這個過程「正好是 Bean 自己控制相依物件的建立或查找的反面（所以叫控制反轉）」。出處 追問時要能區分：IoC 是「誰負責」的原則，DI 是「怎麼送進去」的手段。

容器做了什麼：由容器管理的物件叫 Bean，官方定義是「由 Spring IoC 容器實例化、組裝與管理的物件」出處——容器的工作就是這三件。範例程式與「為什麼不該到處 new」見 Spring 模組第 5 課〈Spring 入門與 IoC、DI〉。

面試官：BeanFactory 與 ApplicationContext 差在哪？

一句話定義：BeanFactory 是容器的最底層介面，只管 Bean 的建立與組裝；ApplicationContext 是它的子介面，多了企業應用要的整合功能。

差別與取捨：官方文件寫 ApplicationContext「是 BeanFactory 的子介面」，加上了「與 Spring AOP 功能更容易整合、訊息資源處理（用於國際化）、事件發布、應用層專用的內容（例如 WebApplicationContext）」。出處 對照表裡常被追問的兩列是：BeanPostProcessor 與 BeanFactoryPostProcessor 的自動註冊，BeanFactory 沒有、ApplicationContext 有——用陽春的 BeanFactory 得自己一個個 addBeanPostProcessor，官方也說「這些明確的註冊步驟很不方便，這正是各種 ApplicationContext 變體比陽春的 DefaultListableBeanFactory 更受偏好的原因」。出處

實務註記：官方的結論是「除非有好理由，否則你應該用 ApplicationContext」。出處 另一個常考差別是建立時機：「ApplicationContext 的實作預設會在初始化過程中積極地建立並設定所有 singleton Bean」，好處是「組態或環境的錯誤會立刻被發現」；不想這樣可以標 @Lazy。出處

面試官：Bean 的作用域有哪幾種？singleton 的 Bean 是執行緒安全的嗎？

一句話定義：作用域（scope）決定一個 Bean 定義會產生幾個實例、活多久。官方列了六種：singleton（預設）、prototype，加上只在 Web 環境有效的 request、session、application、websocket。出處

作用域官方描述（節譯）面試要補的一句
singleton「每個 Spring IoC 容器對一個 Bean 定義只有一個物件實例」跟設計模式的 Singleton 不同：後者是「每個 ClassLoader 一個」，Spring 的是「每個容器、每個 Bean 定義一個」
prototype「每次對那個 Bean 提出請求都建立一個新的實例」容器不管它的完整生命週期：初始化回呼會執行，「設定的銷毀回呼不會被呼叫」
request／session／application／websocket分別綁在一次 HTTP 請求、一個 HTTP Session、一個 ServletContext、一條 WebSocket 連線的生命週期「只在 Web 感知的 ApplicationContext 中有效」，一般的 ApplicationContext 用了會失敗

執行緒安全怎麼答：容器不替你保證。singleton 的意思是「只管理一個共用實例，所有對這個 Bean 的請求都回傳同一個實例」出處——多個請求同時進來，就是多條執行緒共用同一個物件。Bean 沒有可變狀態（只持有注入的相依、方法裡只用區域變數）就沒有東西可以壞；一放可變欄位當計數器或暫存，那個欄位就是多執行緒共用的。答案是「取決於 Bean 有沒有可變狀態」，不是「安全」或「不安全」。

面試官：Bean 的完整生命週期是什麼順序？

一句話定義：實例化、屬性填入、各個 Aware 介面回呼、BeanPostProcessor 前置處理、初始化、BeanPostProcessor 後置處理、使用、銷毀。細到每一步的順序，官方寫在 BeanFactory 介面的說明裡。出處

階段發生什麼依據
實例化、屬性填入建立物件，填好建構子參數與屬性（含注入的相依）Aware 回呼「在一般 Bean 屬性填入之後、初始化回呼之前」出處
Aware 介面依序 BeanNameAware、BeanClassLoaderAware、BeanFactoryAware……到 ApplicationContextAwareBeanFactory 說明的初始化順序第 1〜9 項（Web 環境再多第 10 項 ServletContextAware）出處
BeanPostProcessor 前置postProcessBeforeInitialization後置處理器「在容器的初始化方法……被呼叫之前，以及任何 Bean 初始化回呼之後」都會收到回呼出處
初始化依序 @PostConstruct、afterPropertiesSet()、自訂 init 方法「結合多種生命週期機制」那節出處
BeanPostProcessor 後置postProcessAfterInitialization——AOP 代理在這裡包上去「有些 Spring AOP 基礎建設類別是以 Bean 後置處理器實作，用來提供代理包裝邏輯」出處
銷毀容器關閉時依序 @PreDestroy、destroy()、自訂 destroy 方法銷毀「以同樣的順序呼叫」；prototype 不走這步出處

實務註記：被問「該用哪一種初始化回呼」，答 @PostConstruct 與 @PreDestroy：官方說這兩個註解「一般被視為現代 Spring 應用程式接收生命週期回呼的最佳實踐」，因為 Bean「不會綁死在 Spring 專屬介面上」；Aware 介面則相反，官方直言它「把你的程式碼綁在 Spring API 上、不符合控制反轉的風格」，只建議給需要直接操作容器的基礎建設 Bean 用。出處

依賴注入

怎麼注、注哪一個、繞成圈怎麼辦

面試官：建構子注入、setter 注入、欄位注入怎麼選？為什麼官方建議建構子？

一句話定義：必要的相依用建構子注入，可有可無的相依用 setter 注入，欄位注入能動但官方不推。

差別與取捨：官方原句是「Spring 團隊一般提倡建構子注入，因為它讓你能把應用程式元件實作成不可變物件，並確保必要的相依不會是 null」；setter 注入「只該用在可以在類別內給合理預設值的可選相依」，否則「每個用到那個相依的地方都要做非 null 檢查」。出處 欄位注入（@Autowired 直接放在欄位上）官方文件有示範、可以用出處，但欄位不能宣告成 final，單元測試也沒辦法不靠容器就把替身傳進去。

實務註記：「目標 Bean 只定義一個建構子時，那個建構子上的 @Autowired 不是必要的」出處；建構子參數太多不是注入方式的問題，官方說「大量的建構子參數是壞味道，暗示這個類別可能責任太多，應該重構」。出處

面試官：循環相依 Spring 怎麼處理？為什麼建構子注入會直接失敗？

一句話定義：A 需要 B、B 又需要 A 叫循環相依；建構子注入下容器無解，啟動時直接丟例外。

為什麼會失敗：建構子注入要求物件建立那一刻就拿到完整相依，A 建到一半等 B、B 建到一半等 A，誰都建不完。官方原句：「主要使用建構子注入時，有可能造出無法解決的循環相依情境」，容器「在執行期偵測到這個循環參考，並丟出 BeanCurrentlyInCreationException」。出處

setter 注入為什麼能過：官方給的解法是「把某些類別改成用 setter 而非建構子設定」，但同一段提醒這是「雞生蛋、蛋生雞的情境」，其中一個 Bean 會「在還沒完全初始化之前就被注入到另一個裡面」出處——面試常說的「先給一個半成品」就是這個。

版本註記：Spring Boot 2.6 起「Bean 之間的循環參考預設被禁止」，發行說明「強烈建議你更新組態來打破相依循環」，真要放行得把 spring.main.allow-circular-references 設成 true。出處 所以在 Spring Boot 3 與 4 上，標準答案是「循環相依代表責任切錯了，優先重新設計」，不是背容器怎麼繞過去。

面試官：@Autowired、@Resource、@Qualifier、@Primary 差在哪？

@AutowiredSpring 自己的註解，先照型別找候選者；預設 required 為 true，找不到就失敗。型別有多個候選又沒有其他指示時，「Spring 拿注入點的名稱（也就是欄位名或參數名）跟目標 Bean 的名稱比對，選同名的那一個」。出處
@ResourceJakarta 標準註解（jakarta.annotation.Resource），照名稱找：「預設 Spring 把 name 的值解讀成要注入的 Bean 名稱，也就是採用依名稱的語意」；沒寫 name 就「從欄位名或 setter 方法推導」，那個名字找不到才退回照型別找。只能放在欄位與 setter 方法上。出處
@Qualifier加在注入點，「把限定值跟特定參數綁在一起，縮小型別比對的集合，讓每個參數選到特定的 Bean」；「對備援比對而言，Bean 名稱被視為預設的限定值」，所以直接寫 Bean 名稱也行。出處
@Primary加在 Bean 定義上，「表示當多個 Bean 都是某個單值相依的自動綁定候選者時，這個 Bean 應被優先選用」。官方的分工：@Primary 適合「能決定出一個主要候選者」的情況，「需要對選擇過程有更多控制時」才用 @Qualifier。出處

@Autowired 先看型別、@Resource 先看名稱；@Primary 是「沒指定時預設給這個」、@Qualifier 是「這裡就要那一個」

@Qualifier 與 @Primary 的程式碼範例、Bean 名稱怎麼從類別名推出來，見 Spring 模組第 5 課〈Spring 入門與 IoC、DI〉。

AOP 與代理

代理怎麼建，以及它攔不到什麼

面試官：Spring AOP 的代理是 JDK 動態代理還是 CGLIB？Spring Boot 預設哪個？

一句話定義：兩種都會用。官方定義「在 Spring Framework 裡，AOP 代理是 JDK 動態代理或 CGLIB 代理」出處；純 Spring Framework 看目標有沒有實作介面來選，Spring Boot 則預設一律 CGLIB。

差別與取捨：JDK 動態代理是 Java 標準函式庫內建的機制，只能替介面產生代理；CGLIB（一個在執行期直接產生子類別的函式庫，Spring 已把它打包進 spring-core）走的是「替目標型別在執行期產生一個子類別」。選擇規則：目標「至少實作一個介面就用 JDK 動態代理」，「沒有實作任何介面就建立 CGLIB 代理」。CGLIB 的代價來自「子類別」這件事：final 類別不能被代理、final 方法不能被通知，因為子類別覆寫不了它們。出處

版本註記：Spring Boot 的官方文件寫「預設情況下，Spring Boot 的自動組態把 Spring AOP 設成使用 CGLib 代理。要改用 JDK 代理，把 spring.aop.proxy-target-class 設成 false」。出處 這個預設從 Spring Boot 2.0 開始，遷移指南寫「Spring Boot 現在預設用 CGLIB 代理，AOP 支援也包含在內」。出處 面試被問「為什麼 Boot 要改成 CGLIB」，答「這樣不必為了讓代理成立而替每個 Service 多開一個介面，注入具體類別也不會因為拿到 JDK 代理而轉型失敗」。切面、切入點、通知這些名詞與計時切面的範例見 Spring 模組第 6 課〈Spring AOP 與交易控制〉。

面試官：為什麼同一個類別內部呼叫，@Transactional 或 @Cacheable 不會生效？

一句話定義：因為註解的行為長在代理物件上，內部呼叫用的是 this，沒經過代理。

機制怎麼講：容器交給別人的是代理；外部呼叫先到代理、跑完通知才轉給目標。官方接著說：「一旦呼叫終於到達目標物件，它對自己發出的任何方法呼叫……都是對 this 這個參考、而不是對代理發出的……自我呼叫不會讓跟該方法綁在一起的通知有機會執行。」出處 交易與快取都靠這套代理，所以兩份文件各寫了一句一樣的話：「在代理模式（預設）下，只有從外部經由代理進來的方法呼叫會被攔截」，自我呼叫「不會在執行期產生實際的交易，即使被呼叫的方法標了 @Transactional」出處；換成 @Cacheable，「不會在執行期產生實際的快取」。出處

解法怎麼答：官方給三條路，順序也講了：最推薦「重構程式碼，讓自我呼叫不會發生」——把要被攔的方法搬到另一個 Bean；其次把自己注入自己（注入進來的是代理）改對它呼叫；最不建議 AopContext.currentProxy()，因為它「把你的程式碼完全綁死在 Spring AOP」。出處 真要讓自我呼叫也生效，交易文件給的路是 AspectJ 模式（@EnableTransactionManagement(mode = AdviceMode.ASPECTJ)），它直接改位元組碼、不靠代理。出處

交易

傳播行為與失效情境

面試官：@Transactional 的傳播行為有哪些？REQUIRED 與 REQUIRES_NEW 差在哪？

一句話定義：傳播行為（propagation）決定「一個有交易的方法呼叫另一個有交易的方法時，裡面那層要加入外面的交易、另開一筆，還是不要交易」。Spring 定了七種，預設是 REQUIRED。出處

傳播行為外層有交易時外層沒有交易時
REQUIRED（預設）加入現有交易開一筆新的
REQUIRES_NEW暫停外層，另開一筆獨立交易開一筆新的
NESTED在現有交易裡設一個儲存點（savepoint，交易中途的還原點），只還原到那裡行為同 REQUIRED
SUPPORTS加入現有交易不開交易、直接執行
MANDATORY加入現有交易丟例外
NOT_SUPPORTED暫停外層，不在交易中執行不開交易、直接執行
NEVER丟例外不開交易、直接執行

七種的定義依 Propagation 列舉型別的官方說明整理。出處

REQUIRED 與 REQUIRES_NEW 的差別：差在「幾筆實體交易」。REQUIRED 之下，內外兩層「都對應到同一筆實體交易」，各自只是一個邏輯範圍；內層把交易標成只能還原（rollback-only）時，外層並不知情、照常提交，結果會拿到 UnexpectedRollbackException——官方說這是為了「清楚指出實際上做的是還原而不是提交」。REQUIRES_NEW 則「對每個受影響的交易範圍都用一筆獨立的實體交易，絕不參與外層既有的交易」，所以「底層的資源交易不同，可以各自獨立提交或還原」，內層還原不影響外層、內層的鎖也在它完成時就釋放。出處

實務註記：REQUIRES_NEW 多吃一條資料庫連線——外層的還綁著，內層「取得自己的資源，例如一條新的資料庫連線」；官方警告這「可能耗盡連線池，甚至造成死結」，「除非連線池至少比同時執行的執行緒數多 1，否則不要用」。NESTED 靠 JDBC 的儲存點，「只對 JDBC 資源交易有效」，走 JPA 時別拿它當答案。出處 ACID、隔離層級與 rollbackFor 見 Spring 模組第 6 課〈Spring AOP 與交易控制〉，交易邊界為什麼放服務層見第 8 課〈Spring 資料存取〉。

面試官：@Transactional 什麼情況會失效？

一句話定義：宣告式交易是「AOP 代理加上 TransactionInterceptor」出處，所以失效情境分兩類：代理攔不到，或攔到了但還原條件沒成立。

  • 方法不是 public。官方：「在代理模式（預設）下，public 方法上的 @Transactional 永遠受支援。從 6.0 起，類別式代理預設也可以讓 protected 或套件可見的方法有交易」；但介面式代理（JDK 動態代理）「方法永遠必須是 public 而且定義在被代理的介面裡」。private 方法哪一種代理都攔不到。出處 這一條是 Spring 5 到 6 的差異：Spring 5 只認 public。
  • 自我呼叫。同一個類別裡沒交易的方法呼叫有交易的方法，走的是 this，「不會在執行期產生實際的交易」。出處 同理，自己 new 出來的物件不是容器交出的代理，上面的註解不會生效。
  • 丟的是受檢例外。預設「只在執行期的非受檢例外，也就是 RuntimeException 的實例或子類別時，才把交易標成還原（Error 預設也會還原）」，而「交易方法丟出的受檢例外在預設組態下不會導致還原」。要讓受檢例外也還原，用 rollbackFor。出處
  • 例外被吃掉。還原的判斷是在例外「往上冒出呼叫堆疊時」由交易基礎建設「接住任何未處理的例外」做的出處；方法內部 try／catch 把例外吞掉、只寫個日誌，例外到不了攔截器，交易照常提交。
  • 另開執行緒。Spring 的交易資源是綁在執行緒上的——負責管理的 TransactionSynchronizationManager 官方描述就是「以每條執行緒為單位管理資源與交易同步的中央委派」。出處 交易方法裡開新執行緒或丟進執行緒池的工作，跑在另一條執行緒上，拿不到這筆交易綁的連線，等於在交易外執行。

代理攔不到（非 public、自我呼叫、自己 new）→ 根本沒開交易；攔到了但受檢例外、例外被吃、換執行緒 → 開了卻不還原

Spring Boot 與 Spring MVC

自動組態、啟動註解與一次請求的路徑

面試官：Spring Boot 自動組態怎麼運作？

一句話定義：自動組態（auto-configuration）是「根據你加了哪些 jar 相依，自動設定 Spring 應用程式」：官方的例子是「classpath 上有 HSQLDB、而你沒有手動設定任何資料庫連線 Bean，Spring Boot 就自動組態一個記憶體內資料庫」。出處

機制分三層講：

  • 候選者從哪來：每個自動組態類別標 @AutoConfiguration，Spring Boot「檢查你發布的 jar 裡有沒有 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 檔」，一行一個類別名。官方強調它們「只能透過被列在 imports 檔裡載入」，「絕不能成為元件掃描的目標」。出處
  • 要不要生效由條件決定：@Conditional 家族——@ConditionalOnClass／OnMissingClass 看類別在不在、@ConditionalOnBean／OnMissingBean 看容器裡有沒有某個 Bean、@ConditionalOnProperty 看設定值、@ConditionalOnWebApplication 看是不是 Web 應用程式。官方要求自動組態類別「應該標 @ConditionalOnClass，因為那個類別執行期可能不存在」，並說「用 @ConditionalOnMissingBean 是好習慣，讓開發者能覆寫你的預設」。出處
  • 你的設定永遠優先：「自動組態是非侵入式的。任何時候你都可以開始定義自己的組態來取代自動組態的特定部分。例如加了自己的 DataSource Bean，預設的內嵌資料庫支援就會退開。」想知道哪些自動組態生效、為什麼，用 --debug 啟動會印出條件報告；要關掉某一個，用 @SpringBootApplication(exclude = …) 或 spring.autoconfigure.exclude。出處

版本註記：Spring Boot 2 的答案是「META-INF/spring.factories 裡的 EnableAutoConfiguration 鍵」。3.0 遷移指南寫這條路「已被移除」，改用上面的 imports 檔；同一份指南也記了 Boot 3 的三個地基變動：Java 17 起跳、javax 套件全面改 jakarta、底層升到 Spring Framework 6。出處

面試官：@SpringBootApplication 包了哪三個註解？

一句話定義：@EnableAutoConfiguration、@ComponentScan、@SpringBootConfiguration。官方原句：「單一個 @SpringBootApplication 註解可以用來啟用這三項功能」——@EnableAutoConfiguration「啟用 Spring Boot 的自動組態機制」、@ComponentScan「在應用程式所在的套件上啟用 @Component 掃描」、@SpringBootConfiguration「啟用在內容裡註冊額外 Bean 或匯入額外組態類別；是 Spring 標準 @Configuration 的替代品，有助於整合測試中的組態偵測」。出處

追問時要補的：第三個常被答成 @Configuration，要答對是 @SpringBootConfiguration——它本身標了 @Configuration，多出來的價值是測試能自動找到它。@ComponentScan 掃的是啟動類別所在套件及其子套件，這是把啟動類別放最外層套件的理由。官方也說「這些功能沒有一項是必要的」出處，而且「只該加一個 @SpringBootApplication 或 @EnableAutoConfiguration」。出處

面試官：Spring MVC 一次請求走過哪些元件？

一句話定義：Spring MVC「圍繞前端控制器模式設計：一個中央 Servlet——DispatcherServlet——提供共用的請求處理演算法，實際工作則由可設定的委派元件完成」。出處

順序元件官方對它的定義（節譯）
1DispatcherServlet接下請求，把 WebApplicationContext、地區解析器綁上請求，檢查是不是多部分（檔案上傳）請求
2HandlerMapping「把請求對應到一個處理器，連同一串做前後處理的攔截器」；支援 @RequestMapping 的實作是 RequestMappingHandlerMapping
3HandlerAdapter「協助 DispatcherServlet 呼叫對應到請求的處理器，不論處理器實際上怎麼被呼叫」——目的是「讓 DispatcherServlet 不必知道這些細節」
4Controller你的處理器方法，回傳視圖名稱、模型，或直接回傳要序列化的物件
5aViewResolver「把處理器回傳的字串式邏輯視圖名稱解析成實際的 View，用來算繪回應」
5bHttpMessageConverter方法有 @ResponseBody（@RestController 就是 @Controller 加 @ResponseBody）時，「回傳值透過 HttpMessageConverter 序列化到回應本體」，不走視圖
例外HandlerExceptionResolver「解析例外的策略，可能把它們對應到處理器、HTML 錯誤視圖或其他目標」；@ExceptionHandler 走的就是這條

元件定義依「特殊 Bean 型別」與「處理順序」兩頁整理出處處理順序；@ResponseBody 那句出自訊息轉換那頁。出處

追問時要補的：REST API 沒有視圖那一步。官方的處理順序寫「對註解式控制器，回應可以在 HandlerAdapter 內直接算繪，而不是回傳視圖」出處，所以答 @RestController 的路徑時第 5 步講 HttpMessageConverter，不講 ViewResolver。取參數的註解見 Spring 模組第 7 課〈Spring MVC 與 RESTful API〉；DispatcherServlet 之外的例外為什麼 @ControllerAdvice 抓不到，見第 12 課〈Maven、微服務與全域例外〉。

面試官：Filter、Interceptor、AOP 三者的位置與分工？

一句話定義：三個都是「在正事前後插一段共同邏輯」，差在插在哪一層：Filter 在 Servlet 容器、DispatcherServlet 之前；Interceptor 在 DispatcherServlet 之內、Controller 前後；AOP 在任何 Bean 的方法上，跟 Web 無關。

FilterInterceptor（HandlerInterceptor）Spring AOP
誰定義的Jakarta Servlet 規格：「對資源的請求、資源的回應或兩者執行過濾工作的物件」出處Spring MVC；由 HandlerMapping 連同處理器一起交出出處Spring Framework；「在 Spring AOP 裡，連接點永遠代表一次方法執行」出處

追問時要補的：兩個坑。第一，安全不要放 Interceptor：官方明說「攔截器不理想作為安全層，因為可能跟註解式控制器的路徑比對不一致。一般建議用 Spring Security，或整合進 Servlet Filter 鏈、盡早套用的類似做法」。出處 Spring Security 就在 Filter 這一層：整組安全 Filter 裝在 FilterChainProxy——「Spring Security 提供的一個特殊 Filter，允許透過 SecurityFilterChain 委派給許多 Filter 實例」——再由 DelegatingFilterProxy 註冊進容器。出處 第二，postHandle 對 REST API 幾乎沒用：「對 @ResponseBody 與 ResponseEntity 的控制器方法，回應在 HandlerAdapter 內就已寫出並提交，postHandle 才被呼叫」，要改回應本體得用 ResponseBodyAdvice。出處 Spring Security 的 Filter 鏈見 Spring 模組第 9 課〈Spring Security 認證與授權〉，Filter 與 DispatcherServlet 的先後見第 12 課〈Maven、微服務與全域例外〉。

重點整理

  • IoC 是「誰負責建立相依」的原則，DI 是「容器把相依送進去」的手段；ApplicationContext 是 BeanFactory 的子介面，多了自動註冊後置處理器、事件、國際化，官方說沒有好理由就用它。
  • singleton 是「每個容器一份共用實例」，執行緒安不安全取決於 Bean 有沒有可變狀態；生命週期順序照 BeanFactory 官方說明：屬性填入 → Aware → 後置處理器前置 → @PostConstruct → afterPropertiesSet → init → 後置處理器後置。
  • 必要相依用建構子注入（官方提倡：不可變、不為 null）；建構子注入下的循環相依直接丟 BeanCurrentlyInCreationException，Spring Boot 2.6 起循環參考預設禁止，正解是重新設計。
  • Spring AOP 代理有 JDK 動態代理與 CGLIB 兩種，Spring Boot 2.0 起預設 CGLIB；同類別內部呼叫走 this 不經代理，所以 @Transactional 與 @Cacheable 都不生效，官方首選解法是重構、不是 AopContext。
  • REQUIRED 是同一筆實體交易、內層標還原外層會拿到 UnexpectedRollbackException；REQUIRES_NEW 另開一筆、多吃一條連線。
  • @Transactional 失效五情境：非 public（Spring 6 起類別式代理放寬到 protected）、自我呼叫、受檢例外預設不還原、例外被吃掉、另開執行緒。
  • Spring Boot 3 起自動組態靠 AutoConfiguration.imports 檔加 @Conditional 條件，spring.factories 是 Boot 2 的答案；@SpringBootApplication ＝ @EnableAutoConfiguration ＋ @ComponentScan ＋ @SpringBootConfiguration。
