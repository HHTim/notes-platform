索引結構

B+ 樹、叢集索引與二級索引

答題公式：先一句話定義，再講差別與取捨，最後補一句版本或實務註記。ACID 與交易基礎見資料庫模組第 2 課〈SQL 三種子語言：DDL、DML、DQL〉，本課不重講。

面試官：索引是什麼？為什麼用 B+ 樹，不用雜湊或二元樹？

一句話定義：索引是資料表旁邊另外維護的一份排序好的目錄，讓資料庫不用逐列掃描就能找到目標資料列。MySQL 的主鍵、唯一鍵、一般索引都存成 B-tree（多路平衡樹，手冊統稱 B-tree；面試常說的 B+ 樹是它把資料放在葉節點的變形）出處。

為什麼不是二元樹：B-tree 的一個節點可以有很多個子節點，不像二元樹每個節點只能有兩個出處。InnoDB 一個索引頁預設 16KB出處，一頁能放很多個鍵，每往下一層容量就乘上一頁的鍵數，所以樹很矮——從根到葉只要讀少少幾頁。頁（page）正是 InnoDB 在硬碟與記憶體之間一次搬動的資料單位出處，讀幾頁就是幾次 I/O，這是「適合磁碟」的意思。

為什麼不是雜湊：雜湊索引只能做等號比對，不能做範圍查詢、不能幫 ORDER BY 排序、也只能拿整把鍵去查出處；B-tree 隨時保持排序，等號與範圍（大於、小於、BETWEEN）都能用出處。

面試官：InnoDB 的叢集索引與二級索引差在哪？回表是什麼？

一句話定義：每張 InnoDB 資料表都有一個叫叢集索引（clustered index；這裡的「叢集」是資料列聚在索引裡的意思，跟 Redis 叢集那種多台機器無關）的特殊索引，資料列本身就存在它的葉節點裡；有主鍵就拿主鍵當叢集索引，沒有主鍵就拿第一個所有欄位皆 NOT NULL 的唯一索引，兩者都沒有時 InnoDB 自己生一個隱藏的 GEN_CLUST_INDEX出處。

差別：叢集索引之外的索引都叫二級索引（secondary index），它的每一筆記錄除了被索引的欄位，還帶著那一列的主鍵值；InnoDB 拿這個主鍵值再到叢集索引裡找出整列出處——這第二趟就是「回表」。所以走二級索引查一列要找兩棵樹，走主鍵只要一棵。

主鍵越長，每一個二級索引都要跟著變胖——手冊的建議是主鍵要短

面試官：主鍵為什麼建議用自動遞增整數，不用 UUID？

三個理由都能在手冊找到：第一，沒有天然的唯一非空欄位時，手冊直接建議加一個自動遞增欄位當主鍵出處。第二，主鍵值會被複製進每一個二級索引，主鍵長就整體變大出處。第三，依序插入時索引頁大約填到 15/16，隨機插入則只有 1/2 到 15/16出處——UUID 的值是亂跳的，會到處插頁、造成頁分裂（一頁塞滿要拆成兩頁）與空洞。真的要用 UUID，MySQL 提供 UUID_TO_BIN(uuid, 1) 把變動快的時間部分換到後面，手冊說這樣存進索引欄位可以改善索引效率出處。

怎麼用索引

最左前綴、覆蓋索引與五種失效寫法

面試官：複合索引的最左前綴原則是什麼？(a, b, c) 哪些查詢用得到？

一句話定義：複合索引可以想成把多個欄位的值串起來排序的一份清單，查詢條件必須從最左邊那欄開始、連續往右，最佳化器（資料庫裡決定一條查詢要怎麼執行的元件）才能用它定位出處。

WHERE 條件用得到 (a, b, c) 嗎原因
a = 1用得到只用第一欄，是最左前綴
a = 1 AND b = 2、a = 1 AND b = 2 AND c = 3用得到連續的前綴
a = 1 AND c = 3只用到 a 那一欄中間跳過 b，c 不能拿來定位——手冊說這種寫法會被當成只有 a = 1 來最佳化出處；EXPLAIN 的 key_len 只會算到 a
b = 2、b = 2 AND c = 3用不到不是最左前綴，手冊明講不會用索引查找
a = 1 OR b = 2用不到OR 的兩邊沒有共同的索引前綴

手冊的原例是 INDEX name (last_name, first_name)：WHERE first_name = 'John' 與 WHERE last_name = 'Jones' OR first_name = 'John' 都用不到這個索引出處。

面試官：覆蓋索引是什麼？怎麼從 EXPLAIN 看出來？

一句話定義：覆蓋索引（covering index）是「查詢要的欄位全部都在索引裡」的情況：不用拿索引值當指標回表，直接從索引結構回傳結果，省掉磁碟 I/O出處。因為 InnoDB 的二級索引本來就帶著主鍵欄位，SELECT id, status FROM orders WHERE customer_id = 42 AND status = 'PAID' 只要有 (customer_id, status, created_at) 這個索引就能覆蓋。

EXPLAIN 的 Extra 欄出現 Using index，意思就是只靠索引樹取得欄位資料、不必再去讀實際資料列出處。有個邊角要知道：同一筆交易改過的資料表，在交易結束前 InnoDB 不會對它套用覆蓋索引出處。

面試官：哪些寫法會讓索引用不上？

對欄位套函式WHERE YEAR(created_at) = 2026——索引存的是 created_at 原值，不是算過的結果。改寫成範圍條件 created_at >= '2026-01-01' AND created_at < '2027-01-01'，或建函式索引（functional key part，直接對表達式建索引）出處。
隱含型別轉換字串欄位拿來跟數字比，例如 WHERE phone = 900000123，MySQL 沒辦法用該欄位的索引快速查找——因為 '1'、' 1'、'1a' 很多不同字串都會轉成同一個數字出處。寫成 '0900000123' 就好了。
前置萬用字元LIKE '%0123' 用不到索引；LIKE '0900%' 這種常數字串開頭、不以萬用字元起頭的才能用出處。
OR 混到沒索引的欄位WHERE customer_id = 42 OR amount > 29000——手冊的說法是「WHERE 的兩邊沒有都用到索引」就不會用出處。兩邊各自有索引時，最佳化器可能改走 Index Merge（把兩個索引各掃一次再合併結果）出處。
條件挑不掉多少列否定條件（!=、NOT IN）常落在這裡：最佳化器估計走索引仍要碰到資料表的一大部分時，會放棄索引改掃全表，因為順序讀比反覆跳頁快出處。這不算失效，是最佳化器的成本判斷。

看懂執行計畫

EXPLAIN 與慢查詢日誌

面試官：EXPLAIN 要看哪幾欄？

一句話定義：EXPLAIN 印出最佳化器打算怎麼執行這條查詢；四欄最重要——type（存取方式）、key（實際選用的索引）、rows（估計要檢查的列數）、Extra（額外資訊）出處。

type 由好到差意思
const主鍵或唯一索引全部欄位比對常數，最多一列，只讀一次
eq_refJOIN 時對每組前面的列只讀一列，用的是主鍵或 UNIQUE NOT NULL 索引
ref用索引的最左前綴或非唯一索引查找，符合值的列都讀出來
range用索引取一段範圍：>、BETWEEN、IN()、LIKE 'x%' 這些
index掃整棵索引樹；搭配 Using index 時是掃覆蓋索引，比掃表小
ALL全表掃描；手冊說當它不是第一張表時「通常非常糟」，加索引可以避掉

以上各型的定義都在手冊的 EXPLAIN Join Types 一節出處。rows 對 InnoDB 是估計值，不見得準出處。Extra 欄除了 Using index，要認得 Using index condition（先用索引裡的欄位過濾、再決定要不要回表）、Using filesort（要多做一趟排序）、Using temporary（要建暫存資料表）——手冊直接說想讓查詢快就盯後兩個出處。

EXPLAIN SELECT id, status FROM orders WHERE customer_id = 42 AND status = 'PAID';
-- type=ref  key=idx_cust_status_created  key_len=86  rows=14  Extra=Using index
EXPLAIN SELECT * FROM orders WHERE status = 'PAID';
-- type=ALL  key=NULL  rows=19615  Extra=Using where   ← 跳過最左欄，全表掃描
EXPLAIN FORMAT=TREE SELECT id, status FROM orders WHERE customer_id = 42 AND status = 'PAID';
-- -> Covering index lookup on orders using idx_cust_status_created (customer_id=42, status='PAID')

MySQL 8.4 的 EXPLAIN 預設輸出格式由 explain_format 變數決定；TREE 格式描述得更精確，也是 EXPLAIN ANALYZE（真的執行一次、附上實際耗時與列數）固定使用的格式出處。

面試官：慢查詢怎麼找？

開慢查詢日誌（slow query log）：執行時間超過 long_query_time 秒、且檢查的列數達到 min_examined_row_limit 的 SQL 會被記下來；long_query_time 最小 0、預設 10 秒，可以到微秒；日誌預設是關的出處。沒用到索引的查詢預設不記，要另外開 log_queries_not_using_indexes；日誌太長就用 mysqldumpslow 彙整出處。找出來之後就是上一題：拿 EXPLAIN 看它為什麼慢。

交易隔離

四個等級、三種讀異常與 MVCC

面試官：四個隔離等級各允許哪些讀異常？MySQL 預設哪個？PostgreSQL 預設哪個？

一句話定義：隔離等級（isolation level）是「多筆交易同時跑時，彼此看得到對方多少中間狀態」的設定，換的是效能與一致性之間的平衡。SQL 標準的三種讀異常，PostgreSQL 文件的定義最清楚出處：

髒讀（dirty read）讀到另一筆交易還沒提交的資料——對方一旦還原（rollback，取消整筆交易），你讀到的就是從沒存在過的值。
不可重複讀（nonrepeatable read）同一筆交易裡重讀同一列，發現被別的交易改掉並提交了。
幻讀（phantom read）同一筆交易裡重跑同一個條件查詢，符合條件的「列的集合」變了——別人插了或刪了列。
隔離等級髒讀不可重複讀幻讀
READ UNCOMMITTED可能可能可能
READ COMMITTED不會可能可能
REPEATABLE READ不會不會標準允許；PostgreSQL 實作上擋掉；InnoDB 靠快照與 Next-Key 鎖擋住一般情況，但交易內自己 UPDATE 到別人剛提交的列後，那些列會變成看得到出處（見下）
SERIALIZABLE不會不會不會

InnoDB 提供 SQL:1992 標準的全部四級，預設 REPEATABLE READ出處；PostgreSQL 預設 READ COMMITTED，而且內部只實作三級——它的 READ UNCOMMITTED 行為等同 READ COMMITTED；PostgreSQL 的 REPEATABLE READ 實作也不允許幻讀出處。InnoDB 在 REPEATABLE READ 下，一般 SELECT 讀的是交易第一次讀取時建立的快照；READ COMMITTED 則每次讀都拿新快照，而且一般搜尋與索引掃描不加間隙鎖（只剩外鍵檢查與重複鍵檢查會用），所以會出現幻讀出處。SERIALIZABLE 是在 REPEATABLE READ 之上，把所有一般 SELECT 隱含改成 SELECT ... FOR SHARE（autocommit 關閉時）出處。

SELECT @@transaction_isolation;                          -- REPEATABLE-READ
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- 只改這條連線

面試官：MVCC 是什麼？InnoDB 怎麼用 undo log（記錄「修改前長什麼樣」的日誌）讀到舊版本？

一句話定義：MVCC（多版本並行控制）是讓讀取不用等寫入的鎖：InnoDB 保留被改過的資料列的舊版本，查詢看到的是某個時間點的快照——那個時間點之前提交的變更看得到，之後的或未提交的看不到出處。這種讀法叫一致性讀（consistent read），它不對資料表加任何鎖，所以其他連線可以同時改出處。

怎麼做到：舊版本存在 undo 表空間（tablespace，資料庫在硬碟上的一組檔案）裡一個叫還原區段（rollback segment）的結構；InnoDB 替每一列多藏三個欄位，其中 DB_TRX_ID 記最後改它的交易編號，DB_ROLL_PTR 指向 undo log 記錄——那筆記錄裡有把這列還原成修改前內容所需的資訊出處。讀到一列時比對交易編號，若它是在自己的快照之後才改的，就沿著指標回溯出舊版本。

實務代價：只要還有交易的快照可能用到某段 undo log，它就不能被清掉；手冊因此建議連只做讀取的交易也要定期提交，否則還原區段會越長越大、塞滿 undo 表空間出處。長交易在 PostgreSQL 造成的是另一種問題，本課最後一題「MySQL 與 PostgreSQL 差在哪」會提。

鎖

悲觀對樂觀、記錄鎖、間隙鎖與 Next-Key 鎖

面試官：悲觀鎖對樂觀鎖，各適合什麼？

一句話定義：悲觀鎖是「先鎖再改」——假設會有人跟你搶；樂觀鎖是「先改再驗」——假設多半沒人搶，提交時才檢查資料有沒有被動過。手冊對這兩個詞的定義：悲觀策略犧牲效能或並行度換安全，適合失敗比例高或失敗代價大的情況；樂觀策略則假設多數請求會成功，先做再處理少數失敗出處。

悲觀鎖：SELECT ... FOR UPDATE

對搜尋碰到的索引記錄加排他鎖（exclusive lock，同一時間只能一筆交易持有），效果跟對那些列下 UPDATE 一樣；其他交易不能改、不能 FOR SHARE，鎖在提交或還原時才放出處。只擋寫不擋讀的用 FOR SHARE。要注意鎖定讀只在 autocommit（每條語句自動當成一筆交易立刻提交）關閉、或已 START TRANSACTION 時才有意義出處。不想排隊等鎖可以加 NOWAIT（有鎖就立刻報錯）或 SKIP LOCKED（跳過被鎖的列，適合佇列型資料表）出處。

樂觀鎖：版本欄位

資料表多一個 version 欄位，更新時把讀到的版本帶進 WHERE：

UPDATE accounts
   SET balance = balance - 100, version = version + 1
 WHERE id = 1 AND version = 7;
-- 影響列數 = 1 成功；= 0 表示有人先改過，重讀再試

資料庫本身不用長時間持鎖，衝突由應用程式重試處理；適合讀多寫少、衝突機率低的場景。衝突高時重試會一直失敗，這時候悲觀鎖反而省。

面試官：記錄鎖、間隙鎖、Next-Key 鎖是什麼？為什麼可以擋幻讀？

記錄鎖（record lock）鎖一筆索引記錄。SELECT c1 FROM t WHERE c1 = 10 FOR UPDATE 讓其他交易不能插入、更新或刪除 c1 = 10 的列。沒有索引的資料表也是鎖隱藏叢集索引的記錄出處。
間隙鎖（gap lock）鎖兩筆索引記錄之間的「空隙」，或第一筆之前、最後一筆之後的空隙。WHERE c1 BETWEEN 10 AND 20 FOR UPDATE 讓別人插不進 15——不管原本有沒有 15 這個值出處。間隙鎖純粹是「禁止插入」，不同交易可以同時持有同一段間隙的間隙鎖，它們彼此不衝突出處。
Next-Key 鎖記錄鎖加上「該記錄前面那段間隙」的間隙鎖。索引裡有 10、11、13、20 時，可能的 Next-Key 鎖區間是 (負無限, 10]、(10, 11]、(11, 13]、(13, 20]、(20, 正無限)出處。

為什麼擋得住幻讀：幻讀是重跑同一個查詢多出一列；InnoDB 預設的 REPEATABLE READ 對搜尋與索引掃描用 Next-Key 鎖，把「已有的記錄」和「記錄之間可以插入的位置」一起鎖住，別人就插不進你掃過的範圍出處。用唯一索引做等號查找、且條件涵蓋索引全部欄位時，只鎖那一筆記錄、不鎖前面的間隙；非唯一索引或範圍條件才會鎖間隙出處。

-- 連線 A（REPEATABLE READ，customer_id 有非唯一索引）
START TRANSACTION;
SELECT id FROM orders WHERE customer_id = 42 FOR UPDATE;
-- 連線 B：插入 customer_id = 42 的新列 → 被 Next-Key 鎖擋住，等到 A 提交
INSERT INTO orders (customer_id, status, created_at, amount, phone)
VALUES (42, 'NEW', NOW(), 1, '0999999999');
-- 同一組操作改成 READ COMMITTED：B 立刻成功——因為這個等級不加間隙鎖

分散式環境下這些鎖只管得到同一台資料庫；多台機器搶同一把鎖的問題見資料庫模組第 5 課〈分散式鎖與 Redis〉。

死結與結構變更

死結排查、Online DDL 與 PostgreSQL 對照

面試官：死結怎麼發生、InnoDB 怎麼處理、怎麼看 SHOW ENGINE INNODB STATUS？

一句話定義：死結（deadlock）是多筆交易各持有一把對方需要的鎖，全部卡住等待、誰也不放出處。典型情境是兩筆交易以相反順序鎖同一批列：

-- 交易 A                                  -- 交易 B
UPDATE accounts SET ... WHERE id = 1;      UPDATE accounts SET ... WHERE id = 2;
UPDATE accounts SET ... WHERE id = 2;  ←等  UPDATE accounts SET ... WHERE id = 1;  ←等
-- 其中一方收到：ERROR 1213 (40001) Deadlock found when trying to get lock; try restarting transaction

InnoDB 怎麼處理：死結偵測預設開啟，偵測到就還原其中一筆交易（受害者）來解開，挑的是「較小」的那筆——大小以插入、更新、刪除的列數計出處。若用 innodb_deadlock_detect 關掉偵測，就靠 innodb_lock_wait_timeout（預設 50 秒）逾時，錯誤碼 1205。要注意逾時預設只還原當下那一條語句、不是整筆交易（要整筆還原得開 innodb_rollback_on_timeout）；應用程式若以為交易已整筆還原就直接開新交易，前面的語句其實還在原交易裡、鎖也還握著出處。所以就算應用程式邏輯正確，也要處理「交易必須重試」的情況出處。

怎麼排查：SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 區段列出最近一次死結牽涉的交易、各自正在執行的語句、持有與等待的鎖，以及 InnoDB 決定還原哪一筆出處。它只留最近一次；死結頻繁時開 innodb_print_all_deadlocks，把每一次都寫進錯誤日誌出處。

怎麼減少：手冊的清單——交易小而短、做完一組相關變更就提交；不同交易對多張表或大範圍列用同樣的順序操作；替 FOR UPDATE 與 UPDATE ... WHERE 用到的欄位建好索引，掃得少就鎖得少；能接受舊快照的 SELECT 就別加 FOR UPDATE；鎖定讀若能接受，改用 READ COMMITTED 這類較低的隔離等級出處。

「Deadlocks are not dangerous. Just try again.」——手冊原句；面試答到重試機制才算完整

面試官：大表加欄位或加索引會鎖表嗎？

一句話定義：Online DDL 讓 ALTER TABLE 用即時（instant）或就地（in-place）方式改結構，改的同時允許其他連線讀寫（手冊叫並行 DML，DML 就是 INSERT／UPDATE／DELETE）；預設不用特別設定，MySQL 會在允許的範圍內選最少鎖的做法出處。

  • 加欄位：通常可以 INSTANT（COMPRESSED 列格式、帶全文索引的表等例外除外），只改中繼資料（描述資料表結構的那份資料）、不重建表；INSTANT 是 MySQL 8.4 的預設演算法出處。
  • 加二級索引：不能 INSTANT，但可以 in-place、不重建表、允許並行 DML；建索引期間資料表照常可讀可寫，語句會等到所有正在存取這張表的交易結束才完成出處。
  • 改欄位型別：既不能 INSTANT 也不能 in-place，要重建表，且不允許並行 DML出處——這才是正式環境會鎖住的那種。
ALTER TABLE orders ADD COLUMN note VARCHAR(100) NULL, ALGORITHM=INSTANT;
ALTER TABLE orders ADD INDEX idx_created (created_at), ALGORITHM=INPLACE, LOCK=NONE;
-- 明寫 ALGORITHM／LOCK 的好處：做不到就立刻報錯，不會默默退回鎖表的複製法

明寫 LOCK=NONE（允許讀寫）或 LOCK=SHARED（只允許讀），要求的並行度做不到時語句會立刻停止，這是手冊建議用來避免不小心把表鎖住的做法出處。

面試官：MySQL 與 PostgreSQL 主要差在哪？

面向MySQL（InnoDB）PostgreSQL
預設隔離等級REPEATABLE READ出處READ COMMITTED；只實作三級，REPEATABLE READ 不會幻讀出處
MVCC 舊版本放哪undo log（還原區段），另外保存出處留在資料表裡；UPDATE／DELETE 不會馬上移除舊版本，要靠 VACUUM 回收空間出處
索引類型InnoDB 的索引都是 B-tree（空間索引用 R-tree、全文索引用倒排表）出處索引類型多：B-tree、Hash、GiST、SP-GiST、GIN、BRIN 與擴充套件 bloom，預設 B-tree出處
讀寫互擋一致性讀不加鎖出處「讀永不擋寫、寫永不擋讀」，連 SERIALIZABLE 也靠可序列化快照隔離（SSI，靠偵測交易之間的相依關係、必要時中止其中一筆，而不是靠鎖）維持出處

面試時抓兩個對比最有效：預設隔離等級不同（所以同一段程式搬家後幻讀行為會變），以及舊版本的存放位置不同（所以 PostgreSQL 有 VACUUM、MySQL 有 undo 表空間膨脹）。Spring 端 @Transactional 的傳播行為見面試集〈Spring 面試快答：IoC、Bean、AOP 與交易〉；隔離等級怎麼對應見 Spring 模組第 6 課〈Spring AOP 與交易控制〉。

重點整理

  • InnoDB 索引是 B-tree：節點多路、一頁 16KB、樹很矮，等號與範圍都能用；雜湊只能等號。資料列住在叢集索引的葉節點，二級索引帶主鍵值、要回表。
  • 複合索引照最左前綴用；對欄位套函式、字串欄位比數字、LIKE '%x'、OR 混到沒索引的欄位，索引都用不上。查詢欄位全在索引裡就是覆蓋索引，EXPLAIN 顯示 Using index。
  • EXPLAIN 盯 type、key、rows、Extra；ALL、Using filesort、Using temporary 是警訊。慢查詢靠 slow query log 抓，預設關、門檻 10 秒。
  • InnoDB 預設 REPEATABLE READ、PostgreSQL 預設 READ COMMITTED。MVCC 用 undo log 重建舊版本，一致性讀不加鎖；長交易會讓 undo 無法清除。
  • Next-Key 鎖＝記錄鎖＋前一段間隙鎖，InnoDB 靠它在 REPEATABLE READ 擋幻讀；READ COMMITTED 一般搜尋不加間隙鎖。悲觀鎖用 FOR UPDATE，樂觀鎖用版本欄位加重試。
  • 死結由 InnoDB 自動偵測並還原較小的交易，應用程式要重試；SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK。加欄位 INSTANT、加索引 in-place 不鎖表，改型別才重建。
