為什麼要佇列

解耦、緩衝尖峰、非同步，以及要付的代價

答題公式：一句話定義，再講取捨，最後補版本。版本：Apache Kafka 4.3、RabbitMQ 4.3、Spring for Apache Kafka 4.1、Spring AMQP 4.1。名詞：訊息佇列（message queue）是幫程式「留言」的中間站；送的叫生產者（producer）、收的叫消費者（consumer）、中間那台伺服器叫 broker（訊息代理）。

面試官：什麼時候該引進訊息佇列？代價是什麼？

一句話定義：呼叫方不需要馬上拿到結果、兩邊又不該互相拖累時，才值得放 broker；理由是解耦、非同步，以及用佇列緩衝尖峰流量（業界常叫「削峰」；面試集〈系統設計：秒殺與限流〉叫「以佇列平衡負載」）。

理由與代價：Azure 架構中心寫 broker 提供「時間上的解耦：生產者與消費者不必同時執行」（temporal decoupling）。代價同一頁也寫了：「生產者可能不小心把同一則訊息送兩次……消費者的處理邏輯應該是冪等的」，否則「重複下單或重複收費」（duplicate orders or double billing）。出處 引進佇列等於簽三份帳單：一致性從「馬上」變「稍後」、每個消費者都要冪等、多一套要監控。需要同步結果、或本來就在同一筆資料庫交易裡，直接呼叫就好。

面試官：Kafka 與 RabbitMQ 差在哪？

一句話定義：Kafka 是可重讀的分區日誌，RabbitMQ 是讀完即刪的佇列加路由；差在資料模型，不在誰快。

KafkaRabbitMQ
訊息存放日誌（log）：訊息「不會在被消費後刪除」，保留多久由主題（topic）設定出處佇列：消費者確認（ack）後「broker 就可以把那次投遞標記為待刪除」出處
拉還是推拉（pull）：推的話消費者「容易被壓垮」，拉的話「消費者只是落後，之後再追上」（simply falls behind and catches up when it can）出處推（push）：「訂閱之後，RabbitMQ 會把佇列裡的訊息推給它」；靠 prefetch（一次最多欠幾則未確認的訊息）防壓垮出處
怎麼分工消費者群組（consumer group）：主題切成多個分區（partition），「每個分區在任一時刻只被群組裡的一個消費者消費」出處交換器（exchange）依綁定規則把訊息路由到佇列；同一條佇列的多個消費者「以輪流方式收到訊息」出處

取捨：事件流、多個下游各自重讀、量大選 Kafka；工作佇列、複雜路由、讀完即刪選 RabbitMQ。版本要補的兩句：Apache Kafka 4.0 起只支援 KRaft、ZooKeeper 模式已移除出處；RabbitMQ 4.0 起移除鏡像佇列，複製佇列改用仲裁佇列（quorum queue）出處。

送達保證與冪等

三種語意，最後一種靠佇列自己做不到

面試官：至多一次、至少一次、剛好一次——哪個做得到、代價是什麼？

一句話定義：照 Kafka 文件：至多一次「可能丟失，但絕不重送」；至少一次「絕不丟失，但可能重送」；剛好一次「只被處理一次」（At most once – may be lost but never redelivered. At least once – never lost but may be redelivered. Exactly once – processed once and only once）；並提醒「很多系統宣稱剛好一次，但務必細讀但書」。出處

語意生產端消費端代價
至多一次不等確認、失敗不重試先提交位移（offset，記錄讀到哪裡的數字）再處理會丟；只給丟了沒關係的資料
至少一次等 broker 確認，沒收到就重送先處理再提交位移；當機在兩步之間就重做會重複，消費端必須冪等。Kafka「預設保證至少一次送達」（guarantees at-least-once delivery by default）出處；RabbitMQ「使用確認機制可保證至少一次」出處
剛好一次只在「Kafka 讀、Kafka 寫」內成立：交易式生產者把輸出與位移寫進同一筆交易，消費者用 read_committed 只讀已提交的訊息「對其他目的地系統的剛好一次，通常需要那些系統的配合」（generally requires cooperation with such systems）出處，寫進資料庫那步還是靠冪等

生產端細節：acks 決定等幾個複本：acks=0「完全不等伺服器確認」；acks=1 領導者寫進本地日誌就回應，它在追隨者複製完之前掛掉「那筆紀錄就會丟失」；acks=all「只要至少一個同步複本存活，紀錄就不會丟失」。重送造成的重複由 enable.idempotence 處理：「生產者確保每則訊息在串流裡只寫入一份」，「沒有衝突設定時預設開啟」。出處

面試官：消費者怎麼做到冪等？

一句話定義：冪等（idempotent，做一次和做很多次結果一樣）靠三招：去重表、業務唯一鍵、版本號；前提是每則訊息帶全域唯一的編號。

  • 去重表：消費者「必須冪等，例如追蹤已經處理過的訊息編號」出處：一張以「訊息編號＋消費者名稱」為主鍵的表，寫這一列與業務更新放同一筆交易，重複訊息撞主鍵、整筆回復。
  • 業務唯一鍵：直接拿訂單編號、轉帳序號當唯一索引，Kafka 文件：「很多情況下訊息有主鍵，更新因此是冪等的」。出處
  • 版本號：更新加條件 WHERE version = 舊版本，影響列數 0 代表已處理或已過期；順序亂了也不會把舊狀態蓋回去。
CREATE TABLE processed_message (
  message_id   VARCHAR(64) NOT NULL,  -- 生產端給的全域唯一編號
  consumer     VARCHAR(64) NOT NULL,  -- 哪個服務處理的
  processed_at TIMESTAMP   NOT NULL,
  PRIMARY KEY (message_id, consumer)
);

BEGIN;   -- 兩步同一筆交易
INSERT INTO processed_message VALUES (:message_id, 'ledger-service', NOW());  -- 重複會撞主鍵
UPDATE account SET balance = balance - :amount WHERE account_id = :from_id;
COMMIT;

順序、丟失、堆積、死信

四個營運題

面試官：訊息順序怎麼保證？

一句話定義：Kafka 只保證同一分區內有序，所以用帳戶編號當訊息的 key——「同一個 key 的事件會寫進同一個分區」，讀出順序與寫入時相同。出處 全域有序等於只開一個分區，就沒有平行度。RabbitMQ 一條佇列先進先出，但多個消費者輪流取、有人失敗後訊息重新排入佇列（requeue），順序就變。

面試官：訊息丟了怎麼辦？

一句話定義：三個地方會丟——生產者送出但 broker 沒收到、broker 沒寫進足夠複本、消費者收到但處理前當機。

  • 生產者確認：Kafka 用 acks=all 加 min.insync.replicas（最少同步複本數）：分區「只在同步複本數高於最小值時才接受寫入」。出處 RabbitMQ 是發布者確認（publisher confirm）：持久化訊息的「basic.ack 會在寫進磁碟之後才送出」。出處
  • 複本：Kafka「已提交的訊息不會丟失，只要任一時刻至少有一個同步複本存活」出處。RabbitMQ「重要資料務必使用耐久佇列，並以持久化方式發布訊息」出處——耐久（durable）是佇列撐得過重啟，持久（persistent）是訊息寫進磁碟，兩個都要。
  • 手動確認：RabbitMQ 的自動確認「訊息一送出就視為成功送達」，官方說「應視為不安全」（should be considered unsafe）出處；手動模式「在做完該做的事之前不該確認」。出處 Kafka 對應的是關掉 enable.auto.commit（預設 true，每 5 秒「在背景定期提交」），處理完再提交。出處 Amazon SQS 沒有 ack，用可見性逾時（visibility timeout，取走後一段時間別人看不到，沒刪除就重新可見）代替。出處

面試官：訊息堆積怎麼處理？

一句話定義：堆積（backlog，生產快過消費）先加消費者，再批次，最後問它會不會自己消。加消費者的上限是分區數（第一節 Kafka 對 RabbitMQ 那張表：一個分區同時只給一個消費者），多的閒著，所以分區數要先估好。批次是一批只做一次資料庫往返，一次 poll() 最多回 max.poll.records 則（預設 500）。出處 拉模式下尖峰過了會自己消；持續堆積是容量不夠，不是調參數。RabbitMQ 要設 prefetch，否則「消費者可能被壓垮、在記憶體累積訊息、耗盡 heap（程式的記憶體堆）」。出處

面試官：死信佇列是什麼、什麼時候用？

一句話定義：死信佇列（dead letter queue）收容處理不了的訊息。RabbitMQ 四種死信：消費者負面確認且不重新排入、「訊息因 TTL 過期」、「佇列超過長度上限而被丟棄」、「仲裁佇列（quorum queue，RabbitMQ 4.0 起的預設複製佇列）的訊息被退回超過 delivery-limit 次」，收容處叫死信交換器（dead letter exchange）。出處 最後那種叫毒訊息（poison message，每次都失敗、永遠確認不了的訊息），仲裁佇列用 x-delivery-count 標頭記次數。出處 死信不是丟掉，是留證據：數量大於 0 要告警，修好後要能重放。Kafka 沒這概念，靠用戶端框架做（最後一節）。

Outbox 與 Saga

先寫資料庫再發訊息，為什麼會不一致

面試官：為什麼「先寫資料庫再發訊息」會不一致？Outbox 怎麼解？

一句話定義：資料庫交易與發訊息是對兩個系統各寫一次（AWS 叫雙重寫入問題）：「資料庫更新成功但事件通知失敗，下游不會知道這個變更」；反過來「更新失敗但事件送出了，資料可能被弄壞」。出處 不用兩階段提交（2PC，大家都說能做才一起做）是因為「資料庫或 broker 可能不支援，而且把服務同時耦合到兩者通常不是好事」。出處 面試集〈系統設計：短網址的高併發〉「丟進佇列就回成功」的錯誤，正解在這裡。

解法：交易式 Outbox（transactional outbox）「先把訊息當作更新業務實體那筆交易的一部分存進資料庫，再由另一個程序送到 broker」（first store the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages to the message broker）；存訊息的表叫寄件匣（outbox），另一個程序叫訊息轉送器（message relay）。好處是「訊息保證在交易提交時、且只在提交時被送出」。出處

CREATE TABLE outbox (
  id             BIGINT      PRIMARY KEY,  -- 遞增序號，輪詢照它排序；序號小的交易可能較晚提交，所以難保序
  aggregate_type VARCHAR(64) NOT NULL,     -- 'transfer'
  aggregate_id   VARCHAR(64) NOT NULL,     -- 轉帳序號，當 Kafka 的 key 保順序
  event_type     VARCHAR(64) NOT NULL,     -- 'TransferDebited'
  payload        JSON        NOT NULL,
  created_at     TIMESTAMP   NOT NULL,
  published_at   TIMESTAMP   NULL          -- 轉送成功後填上
);

BEGIN;   -- 業務寫入與寄件匣同一筆交易
UPDATE account SET balance = balance - 1000 WHERE account_id = 'A';
INSERT INTO outbox (...) VALUES (...);
COMMIT;

轉送器兩種做法：輪詢發布者（polling publisher）定期查 outbox 表，缺點「難以按順序發布」出處；交易日誌尾隨（transaction log tailing）改讀資料庫的變更日誌，缺點「需要資料庫專屬的方案」出處。AWS 另給不建 outbox 表的做法：用 DynamoDB Streams（把每筆資料變更依序吐出來的串流）這種變更資料擷取（CDC）直接把變更當事件送出。出處

Outbox 把「發訊息」變成至少一次——轉送器「可能在發布之後、記錄之前當機，重啟就再發一次」，消費端還是要冪等出處

面試官：Saga 的兩種協調方式？補償怎麼設計？

一句話定義：Saga「是一連串本地交易，每筆更新資料庫並發布事件觸發下一筆；若某筆因違反業務規則失敗，就執行一連串補償交易（compensating transaction）倒回前面的變更」（A saga is a sequence of local transactions… executes a series of compensating transactions that undo the changes）。出處

兩種協調方式：協同式（choreography；〈後端與雲端面試題庫〉稱事件協作式）「每筆本地交易發布領域事件，觸發其他服務的本地交易」出處，適合參與者少，代價是「參與者變多就難以追蹤彼此的相依」出處。編排式（orchestration；同課稱中央協調式）由「一個編排器（orchestrator）告訴參與者要執行哪些本地交易」出處，AWS 用 Step Functions（AWS 的流程編排服務）實作，代價是「編排器可能成為單點故障」出處。

編排式 Saga 的狀態機（跨行轉帳）

  STARTED ──扣款成功──▶ DEBITED ──對方入帳成功──▶ COMPLETED
     │                    │
   扣款失敗           入帳失敗（帳戶不存在、逾時到上限）
     ▼                    ▼
  FAILED           COMPENSATING ──退回扣款成功──▶ FAILED（錢已回到原帳戶）
                          │
                     退回也失敗 ──▶ 死信 + 人工介入

補償三條規則：第一，補償是反向動作不是刪除——退回同金額、留下兩筆紀錄，因為 Saga「沒有自動回復，開發者必須設計明確倒回變更的補償交易」。出處 第二，每步與每個補償都冪等，才能「在當機或編排器故障後重複執行」。出處 第三，Saga「缺少 ACID 裡的隔離性，多個 Saga 同時執行可能造成資料異常」出處——扣款後入帳前，別人看到的餘額已經少了；AWS 建議「語意鎖」出處，實務上就是把那筆錢標成「轉出中」凍結。

最終一致與銀行帳務

「暫時看不到」可以，「錢不見了」不行

面試官：最終一致對強一致，業務上怎麼解釋「暫時看不到」？

一句話定義：強一致是寫完下一秒任何人都讀到新值；最終一致是複本會在一段時間內趨於一致，期間有人可能讀到舊值。

面試官：銀行轉帳可以用最終一致嗎？

一句話定義：「對方何時看到錢」可以，「錢的總額」不行。同一系統內的轉帳放同一筆 ACID 交易就好；跨系統（跨行、外部支付機構）沒有共同的交易，才用 Saga 加冪等加對帳，每步守住「錢不能少、帳要對得上」。

  • 帳務分錄：複式簿記（double-entry bookkeeping）「每一筆交易都以相等且相反的兩筆分錄（借與貸）記錄」（equal and opposite entries）。出處 套進 Saga：扣款不是「餘額減 1000」而是「客戶帳戶借 1000、轉出中間帳戶貸 1000」（客戶存款是銀行的負債，扣款記借方），錢沒消失，只是換了位置；入帳成功後中間帳戶才結掉，補償則反向再記兩筆。分錄只增不改。
  • 冪等：每筆轉帳一個交易序號，扣款、入帳、補償都拿它當唯一鍵；重送、重跑撞到唯一鍵就是「已經做過」，避開「重複收費」。出處
  • 對帳：日終把兩邊分錄逐筆比對：己方每筆「轉出中」，對方是否都有入帳，差異進人工處理。對帳是承認「至少一次」與「補償也可能失敗」會發生；死信佇列裡的東西最後都要在對帳表上有交代。

跟業務怎麼講：別說「最終一致」四個字，說「送出成功」跟「對方看到」是兩個時間點，畫面顯示「處理中」而不是假裝完成；承諾處理中看得到、多久內一定有結果、失敗一定退回原狀。AWS 的建議也是「跟業務團隊講清楚一致性模型的預期」（setting your business teams' expectations）。出處

Spring 怎麼接

@KafkaListener 與 @RabbitListener 各一眼

面試官：訊息佇列在 Spring 怎麼接？

Spring for Apache Kafka（4.1）：@KafkaListener「把一個 Bean 的方法指定為監聽器容器的監聽器」，需要 @EnableKafka 與名為 kafkaListenerContainerFactory 的工廠 Bean（Spring Boot 自動組態會給）。出處

public class Listener {

    @KafkaListener(id = "foo", topics = "myTopic", clientIdPrefix = "myClientId")
    public void listen(String data) {
        ...
    }
}

位移何時提交由 AckMode 決定：「從 2.3 版起，框架把 enable.auto.commit 設成 false」；預設 BATCH「一次 poll() 的紀錄全部處理完才提交」，MANUAL 則自己呼叫 acknowledge()。出處 丟例外時預設的 DefaultErrorHandler 共試 10 次，用完交給 DeadLetterPublishingRecoverer「預設送到名為 原主題-dlt 的主題」——Kafka 的死信主題由此而來。出處

Spring AMQP（4.1）：「只要 myQueue 有訊息，processOrder 就會被呼叫」；佇列「必須已存在並綁定到某個交換器」，或由 RabbitAdmin 自動宣告。出處

@Component
public class MyService {

    @RabbitListener(queues = "myQueue")
    public void processOrder(String data) {
        ...
    }
}

預設的 acknowledgeMode 是 AUTO：「容器自動確認，除非監聽器丟出例外」。出處 丟例外的預設行為是「訊息被拒絕並由 broker 重新排入佇列」，所以下游暫時故障這類例外會一再重送；解法是 defaultRequeueRejected 設 false「讓訊息被丟棄（或路由到死信交換器）」，或丟 AmqpRejectAndDontRequeueException 針對單一訊息不重新排入。但轉換失敗這類不可能成功的錯誤，預設的錯誤處理器 ConditionalRejectingErrorHandler 會直接拒絕、不重新排入（rejects (and does not requeue) messages that fail with an irrecoverable error）。出處

追問時要補的：@Transactional 包在監聽器方法上，預設情況下只管資料庫那筆交易，管不到位移提交或訊息確認，「資料庫提交了、位移沒提交」的空窗還在——消費端要冪等的另一個理由。@Transactional 本身見 Spring 模組第 6 課〈Spring AOP 與交易控制〉。

重點整理

  • 引進佇列為了解耦、削峰、非同步；代價是一致性變「稍後」、消費者要冪等、多一套要監控。
  • Kafka 是可重讀的分區日誌、消費者拉、群組分工；RabbitMQ 是讀完即刪的佇列、broker 推、交換器路由。
  • 佇列最多給至少一次；剛好一次只在 Kafka 內成立，寫進資料庫靠去重表、業務唯一鍵或版本號。
  • 順序只在同一分區內；不丟靠 acks=all、耐久佇列加持久訊息、處理完再確認（Spring Kafka 預設 BATCH、Spring AMQP 預設 AUTO 且例外會重新排入）；堆積先加消費者再批次；壞訊息進死信佇列。
  • 先寫資料庫再發訊息是雙重寫入；交易式 Outbox 把訊息寫進同一筆交易的寄件匣表再送出，代價是至少一次。
  • Saga 是一連串本地交易加補償；補償是反向動作、每步冪等、缺隔離性用凍結狀態補。
  • 銀行轉帳同一系統用 ACID 交易；跨系統用 Saga，分錄借貸相等、每步冪等、日終對帳——「暫時看不到」可以，「錢不見了」不行。
