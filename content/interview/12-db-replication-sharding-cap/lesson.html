讀完這課你會

  • 講清楚 MySQL 主庫對複本複寫的三條執行緒、非同步與半同步的差別、複寫延遲怎麼量，以及「剛寫完讀不到」的三種解法
  • 分清垂直分割、水平分割與分片，說出範圍、雜湊、一致性雜湊各適合什麼，並回答跨分片 JOIN、交易與全域 ID 怎麼辦
  • 把 CAP 講對：分割是前提不是選項，分割時才在一致與可用之間取捨，平時取捨的是延遲；並用 PACELC 與 BASE 補完
  • 用 HikariCP 的公式估連線池大小並說出前提，列出連線耗盡、鎖等待、磁碟滿、複寫斷掉各怎麼發現

複寫

binlog、三條執行緒與半同步

答題公式：一句話定義、取捨、版本註記。隔離層級、MVCC 與鎖見面試集〈資料庫面試題：索引、交易隔離與鎖〉；分片與複寫解決的是不同問題，對照表見〈NoSQL 與資料庫設計〉，本課不重講。

面試官：MySQL 主從複寫怎麼運作？非同步跟半同步差在哪？

一句話定義：複寫（replication）是把一台 MySQL（手冊叫 source，本課稱主庫）的資料變更，複製到一台或多台其他 MySQL（replica，本課稱複本）出處。主庫把每筆提交的變更記進二進位日誌（binary log，簡稱 binlog），複本拿去重放；8.4 預設用列格式（row-based），記「哪一列改成什麼」而不是 SQL 原句出處。

三條執行緒：複本連上來時，主庫開一條 Binlog Dump 執行緒送 binlog；複本的接收執行緒（I/O receiver thread）把收到的內容寫進本機的中繼日誌（relay log，複本先抄下來、稍後再執行的那份日誌），套用執行緒（SQL applier thread）再讀中繼日誌、執行裡面的交易出處。8.4 的套用端預設多執行緒：replica_parallel_workers 預設 4，由一條協調執行緒派工出處。

模式主庫的提交何時回覆用戶端代價
非同步（預設）寫進自己的 binlog 就回覆；「主庫不知道複本何時、甚至有沒有拿到這筆交易」出處主庫當機時，還沒送出去的交易會丟
半同步等到至少一台複本「收到並寫進日誌」才提交；只要求收到，不要求複本已執行完出處每筆提交多一趟網路來回

半同步是外掛，主庫裝 rpl_semi_sync_source、複本裝 rpl_semi_sync_replica，各自把 _enabled 設成 1出處。兩個細節：rpl_semi_sync_source_timeout（預設 10000 毫秒）內沒有複本回覆，主庫會退回非同步；等待點 rpl_semi_sync_source_wait_point 預設 AFTER_SYNC，即 binlog 寫進磁碟後、提交進儲存引擎前就等複本：主庫意外當機、由複本接手時不會丟交易，因為「主庫上已提交的所有交易都已複製到複本（寫進它的中繼日誌）。主庫意外結束後容錯移轉到複本是無損的」（All transactions committed on the source have been replicated to the replica (saved to its relay log). An unexpected exit of the source server and failover to the replica is lossless）。另一個值 AFTER_COMMIT 是先提交、再等複本回覆，代價有兩個：「提交之後、複本回覆之前，其他用戶端可能比發出提交的那個用戶端更早看到這筆交易」（After the commit and before replica acknowledgment, other clients can see the committed transaction before the committing client）；而且複本若沒處理到這筆交易，主庫又意外當機而容錯移轉，「用戶端可能發現資料比他們在主庫上看到的少了一些」（it is possible for such clients to see a loss of data relative to what they saw on the source）出處。

-- 主庫（8.4.11 實跑）
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SHOW VARIABLES LIKE 'rpl_semi_sync%';
-- rpl_semi_sync_source_enabled                 OFF      ← 還要 SET GLOBAL ... = 1
-- rpl_semi_sync_source_timeout                 10000
-- rpl_semi_sync_source_wait_for_replica_count  1
-- rpl_semi_sync_source_wait_point              AFTER_SYNC

面試官：複寫延遲會造成什麼問題？怎麼量？

兩個問題：讀到舊資料——走複本的查詢看到的是幾秒前的世界；容錯移轉（failover，主庫壞了由複本接手）時，複本還沒收到的交易就丟了——非同步下主庫「不知道複本何時、甚至有沒有拿到並處理這些交易，也不保證任何事件一定會到達任何一台複本」出處；已經寫進中繼日誌、只是還沒套用的交易，複本接手後仍會套用完。

怎麼量：在複本跑 SHOW REPLICA STATUS，看 Seconds_Behind_Source——「複本正在套用的事件，其原始時間戳與複本現在時間的差」；手冊警告它量的其實是接收執行緒與套用執行緒之間的落差，網路慢時接收端本身就落後，這欄卻常顯示 0，「只在快速網路上有用」出處。

傳統複寫要複本記住讀到主庫哪個 binlog 檔的哪個位置；GTID（global transaction identifier，全域交易識別碼）給每筆交易一個 server_uuid:序號 的編號出處，換主庫或新增複本不必再對檔名與位置；同一個 GTID 在同一台伺服器上最多套用一次，重送不會重做出處。

讀寫分離

剛寫完讀不到，三種解法

面試官：讀寫分離之後，使用者剛轉完帳、刷新頁面卻看不到那筆交易，怎麼處理？

一句話定義：讀寫分離是把寫入送主庫、讀取分散到複本；手冊明講這件事要應用程式自己做——「把所有寫入送到主庫，讀取送到主庫或複本」出處。預設非同步，寫完立刻去複本讀可能讀到舊狀態。三種解法由簡到繁：

關鍵讀走主庫「必須看到自己剛寫的結果」的查詢（餘額、交易明細）固定送主庫，能忍受延遲的（月報表、歷史查詢）才走複本。最簡單，但主庫讀壓力減不掉多少。
讀自己的寫寫入成功後幾秒內，同一位使用者的讀取都導回主庫，過了再放回複本。常見做法而非官方規範，門檻值用實測的複寫延遲來定。
GTID 等待寫入後拿到主庫的 GTID 集合，到複本上呼叫 WAIT_FOR_EXECUTED_GTID_SET(gtid_set, timeout)：它等到複本套用完該集合內的所有交易才回傳 0，逾時回傳 1出處。等到了就在這台複本讀；逾時改走主庫。
-- 主庫：寫完後取得已執行的 GTID 集合（實跑）
SELECT @@gtid_executed;      -- b9e303eb-...:1-8
-- 複本：最多等 1 秒
SELECT WAIT_FOR_EXECUTED_GTID_SET('b9e303eb-bbd6-11f1-b1c4-dae0644808c0:1-8', 1);   -- 0

AWS 那邊：Aurora 的複本共用同一個叢集磁碟區，複寫延遲「通常遠低於 100 毫秒」，寫入量大時會拉長出處；RDS 的 Standby 對 Read Replica 見〈RDS 資料庫資源〉。

分片

垂直對水平、分片鍵、跨分片的三個難題

面試官：垂直分割對水平分割？什麼時候該分片？

一句話定義：垂直分割（vertical partitioning）是把一張表的不同欄位拆開存；水平分割（horizontal partitioning）是把不同的列分到不同的實體分區。手冊寫得很直接：MySQL 的分割是水平分割，「不支援垂直分割，目前也沒有引入的計畫」出處。分片（sharding）是把水平分割做到跨伺服器：同一張邏輯表的列散在多台獨立的資料庫上。

什麼時候該分：複寫只複製「同一份」資料，解決的是讀取量與可用性；單一主庫的寫入吞吐或儲存容量到頂時，複本再多也沒用，才輪到分片。代價見〈NoSQL 與資料庫設計〉那張表：分片鍵怎麼選、跨片查詢、重新平衡。順序是先索引、讀寫分離、冷資料歸檔（很少用的舊資料搬去便宜的地方存），最後才分片——這是常見做法而非官方規範。

面試官：分片鍵怎麼選？範圍、雜湊、一致性雜湊各適合什麼？

分法怎麼分好處壞處
按範圍帳號 1〜100 萬第 1 片、100〜200 萬第 2 片；或按月份範圍查詢只掃少數片熱點：新帳號、本月交易全擠在最後一片
按雜湊對鍵算雜湊值，取餘數決定放哪片分布均勻範圍查詢要掃全部片；加減機器時餘數全變，幾乎所有資料要搬
一致性雜湊雜湊值空間當成一個環，節點與鍵都落在環上，鍵順時針找到第一個節點加減節點「只影響它的鄰居，其他節點不受影響」出處節點在環上的位置隨機，資料與負載會不均，也不管機器效能有差

Dynamo 論文第 4.2 節對後兩個缺點的解法是虛擬節點（virtual nodes）：一台實體機器在環上佔多個位置，機器掛掉時它的負載平均散到剩下的機器，容量大的機器多佔幾個位置出處。DynamoDB 也是按雜湊分割：「把分割鍵（partition key）的值丟進內部雜湊函式，輸出決定項目存在哪個分割」；加上排序鍵（sort key）後，同一個分割鍵的項目存在一起、按排序鍵排好出處。

選分片鍵的第一原則：最常一起查的資料要落在同一片——帳務系統通常拿客戶編號，不拿交易編號

面試官：跨分片的 JOIN、交易、全域唯一 ID 怎麼辦？

  • JOIN：資料庫做不了跨機器的 JOIN，只能靠設計避開，三個常見做法（非官方規範）——用同一個分片鍵讓客戶的帳戶與交易落在同一片；小而少變的表（幣別、分行代號）每片各放一份；真的要跨片就分兩次查、在應用程式裡合併。
  • 交易：跨片沒有共同的 ACID 交易。能改設計就讓一筆業務只碰一片；改不了的走 Saga 加交易式 Outbox 加對帳，見面試集〈系統設計：訊息佇列與最終一致性〉。
  • 全域唯一 ID：自動遞增在每片各自數，會撞號。三條路：號段模式（發號服務每次批發一段號碼，見面試集〈系統設計：短網址的高併發〉）；UUID（不撞，但插進叢集索引會亂跳，補救寫法見〈資料庫面試題：索引、交易隔離與鎖〉）；時間戳加機器編號加序號拼成 64 位元整數，大致遞增、不需中心發號（各家實作不同，沒有標準文件）。

CAP

分割是前提不是選項，平時取捨的是延遲

面試官：CAP 定理到底說什麼？為什麼「三選二」是誤解？

先講證明版：Gilbert 與 Lynch 2002 年的論文把三個詞定義死：一致（atomic consistency）是每個操作看起來像在某個瞬間一次完成、所有操作排成一個全序；可用（availability）是「每個沒故障的節點收到的每個請求都必須得到回應」；分割容忍（partition tolerance）是允許網路丟掉任意多的訊息出處。定理 1：「在非同步網路模型中，不可能實作一個讀寫資料物件，在所有公平執行（包含訊息丟失的執行）中同時保證可用性與原子一致性」出處。證明骨架：網路斷成兩半，寫入落在一半、讀取落在另一半，要回應就只能回舊值，要回新值就只能不回應。

再講為什麼三選二是誤解：Brewer 2012 年自己寫道，「三選二的講法一直是誤導的，因為它過度簡化了三個性質之間的張力」出處。三點：

  • P 不是選項。你只能決定分割發生時保 C 還是保 A；「因為分割很少發生，CAP 應該在大多數時間允許完整的 C 與 A」，分割出現時才需要偵測並處理它的策略出處。
  • 不是整個系統選一次。「C 與 A 之間的選擇可以在同一個系統裡發生很多次、粒度很細；不只子系統可以選不一樣，還可以依操作、甚至依特定資料或使用者而不同」出處。帳務餘額保 C、瀏覽紀錄保 A，就是兩個選擇。
  • 分割其實是延遲問題。「務實地說，分割就是通訊的一個時間上限」——等不到回覆時，要嘛取消操作（少了 A），要嘛硬做下去（賭 C）出處。Brewer 的處理三步：偵測分割開始、進入可能限制部分操作的分割模式、通訊恢復後啟動分割復原出處。

PACELC：Abadi 2012 年在 IEEE Computer 寫成論文的補完：「如果發生分割（P），系統怎麼在可用性與一致性之間取捨（A 與 C）；否則（E），系統正常運作時，怎麼在延遲（L）與一致性（C）之間取捨」出處。平時同步複寫多等一趟網路，就是用延遲換一致——CAP 沒講這一半。論文的分類：Dynamo、Cassandra、Riak 預設是 PA/EL（分割時保可用、平時保低延遲）；VoltDB、Megastore 這類完整 ACID 系統是 PC/EC，「拒絕放棄一致性，願意付出可用性與延遲的代價」出處。半同步複寫的 MySQL 較接近 PA/EC：平時每筆提交多等一趟網路，換的是容錯移轉不丟交易，這是耐久性（durability，寫進去的資料不會因當機消失），不是 CAP 定義的一致性；逾時退回非同步、主庫照常提交，則是分割時選可用。論文沒有點名 MySQL，這是常見的歸類說法，套的是論文對 MongoDB 的判準：「MongoDB 可以歸為 PA/EC 系統。平時系統保證讀寫一致；但主節點故障或與系統其餘部分斷開時，其餘節點另選一個新主節點繼續提供讀寫，於是舊主與新主的狀態變得不一致」出處。

答 CAP 的順序：先講 P 是前提、再講分割時的 C 對 A、最後補一句平時是 L 對 C——三句話把三選二的版本蓋掉

面試官：什麼是 BASE？

一句話定義：BASE 是「基本可用（Basically Available）、軟狀態（Soft state）、最終一致（Eventually consistent）」的縮寫：ACID 以一致性為重、是資料庫的傳統路線，BASE 是以高可用為重的設計取向出處。白話：一部分壞掉時其他部分照常服務；各副本某一刻可以不一樣；停止寫入後過一段時間會變成同一個值。Dynamo 是課本例子——為了「永遠可寫」（always writeable），「在某些故障情境下犧牲一致性」出處。業務上怎麼解釋「暫時看不到」、哪些帳務不能最終一致，見面試集〈系統設計：訊息佇列與最終一致性〉。

連線池

為什麼要池、大小怎麼估

面試官：資料庫連線池為什麼重要？大小怎麼估？

一句話定義：連線池（connection pool）是「讓資料庫連線在同一個應用程式內或跨應用程式重複使用，而不是每次操作都新建再拆掉一條連線」的快取區出處。建連線要 TCP 交握、認證、配置執行緒，是毫秒級的固定成本；而且資料庫端連線數有上限——max_connections 預設 151出處，滿了之後新連線收到 Too many connections出處。

大小：HikariCP 的 wiki 給的起點公式是連線數 = 核心數 × 2 + 有效磁碟軸數（磁碟軸 spindle，大致就是幾顆會轉的傳統硬碟），出自 PostgreSQL 專案，4 核心、一顆硬碟的機器大約 10 條出處。核心數與磁碟數是資料庫伺服器的，不是應用程式的。前提：公式假設瓶頸是 CPU 與磁碟尋道，執行緒多過核心數只是增加切換成本；換成 SSD 沒有尋道與轉動延遲、阻塞更少，wiki 的結論是執行緒該更少（接近核心數）而不是更多出處。同一段還給了兩個前提：有效磁碟軸數在活躍資料集全部被快取住時是零，快取命中率越低才越接近實際軸數（Effective spindle count is zero if the active data set is fully cached, and approaches the actual number of spindles as the cache hit rate falls）；這條公式在 SSD 上表現如何，目前還沒有人分析過（There hasn't been any analysis so far regarding how well the formula works with SSDs）出處。同一頁的核心主張：「你要的是一個小池子，塞滿等待連線的執行緒」出處。

Spring Boot：有 HikariCP 就用它（spring-boot-starter-jdbc 或 data-jpa 自帶），沒有才退到 Tomcat 池、Commons DBCP2、Oracle UCP；參數用 spring.datasource.hikari.* 前綴出處。

spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.connection-timeout=3000   # 等不到連線 3 秒就丟例外，不無限排隊

推理題：帳務服務 20 個執行個體（instance，同一個服務跑起來的一份程式）、每個池 10 條＝200 條長連線，超過預設的 151；調大 max_connections 或縮小池，都要算過再選。

壞法與冷資料

四種壞法怎麼發現、冷熱分離、什麼時候用 NoSQL

面試官：資料庫常見的壞法——連線耗盡、鎖等待、磁碟滿、複寫斷掉，各怎麼發現？

壞法症狀去哪裡看
連線耗盡應用程式取不到連線、逾時；資料庫回 Too many connections狀態變數 Max_used_connections（啟動以來同時在用的最高數）與 Connection_errors_max_connections（因達上限被拒的次數）出處。伺服器另留一條給有 CONNECTION_ADMIN 權限的帳號，滿載時仍能連進去下 SHOW PROCESSLIST出處
鎖等待語句卡住，innodb_lock_wait_timeout（預設 50 秒）後報 Lock wait timeout exceeded出處sys.innodb_lock_waits 檢視表：誰在等、等多久（wait_age）、被誰擋（blocking_pid），連 KILL 語句都拼好了出處；底層資料來自 performance_schema.data_lock_waits出處
磁碟滿binlog 寫滿時像卡住而不是報錯：MySQL 每分鐘檢查一次有沒有空間寫下一個事件，有了就繼續；每 10 分鐘往錯誤日誌寫一筆警告（手冊這段只講 MyISAM 表與 binlog）出處。InnoDB 表的資料檔寫滿則是另一種錯誤 The table is full，會直接報錯出處作業系統的磁碟監控；等資料庫報錯已太晚
複寫斷掉複本資料停在某個時間點；Seconds_Behind_Source 變成 NULL（套用執行緒沒在跑）出處SHOW REPLICA STATUS 的 Replica_IO_Running 與 Replica_SQL_Running 正常都該是 Yes出處；停掉的原因在 Last_IO_Error／Last_SQL_Error出處

四種壞法的共同答法：先講症狀，再講哪個指標要提前告警

面試官：冷熱資料分離、歸檔怎麼做？

一句話定義：熱資料常被讀寫（近三個月的交易），冷資料很少碰但依法要留（幾年前的明細）；分離是熱的留在小而快的表、冷的搬去便宜的地方。MySQL 內建的工具是分割表，手冊列的好處有「失去用處的資料通常可以直接丟掉裝它的那個分區」，以及分區修剪（partition pruning）——WHERE 條件只落在某些分區時，其他分區自動不掃出處。

CREATE TABLE tx_log (id BIGINT NOT NULL, booked_on DATE NOT NULL, amount DECIMAL(15,2),
  PRIMARY KEY (id, booked_on))
PARTITION BY RANGE (YEAR(booked_on)) (
  PARTITION p2023 VALUES LESS THAN (2024), PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p2025 VALUES LESS THAN (2026), PARTITION pmax VALUES LESS THAN MAXVALUE);
EXPLAIN SELECT * FROM tx_log WHERE booked_on >= '2025-01-01' AND booked_on < '2026-01-01'\G
-- partitions: p2025            ← 只掃一個分區（實跑）
ALTER TABLE tx_log DROP PARTITION p2023;   -- 整年一次移除，不必逐列 DELETE

記得手冊的警告：「丟掉分區的同時，也刪掉了存在那個分區裡的所有資料」出處——所以先把該分區匯出到歸檔庫或物件儲存、核對筆數、才 DROP；報表與稽核查詢走歸檔庫或複本、不碰帳務主庫（常見安排，非官方規範）。DynamoDB 的對應物是存活時間（TTL）：替每個項目設到期時間戳，到期後「DynamoDB 會在幾天內自動刪除，不消耗寫入吞吐量」出處。

面試官：什麼時候該用 NoSQL？

一句話定義：存取模式固定、以鍵查值為主、資料量與寫入量大到要橫向擴充，且不需要跨表 JOIN 與交易時，鍵值或文件型資料庫比關聯式划算；查詢多變、要複雜關聯與強一致交易的帳務核心，還是關聯式。完整判準見〈NoSQL 與資料庫設計〉。以 DynamoDB 為例，兩個要點：

  • 只有鍵有綱要。「除了主鍵之外，表是無綱要的」；主鍵是分割鍵，或分割鍵加排序鍵出處。所以先想清楚怎麼查再決定鍵，跟關聯式先建模、後想查詢的順序相反。
  • 預設最終一致讀。讀取「可能不反映剛完成的寫入」；要最新資料就把 ConsistentRead 設成 true，但強一致讀只支援表與本地次要索引（local secondary index，跟表用同一個分割鍵、只換排序鍵的索引），全域次要索引（global secondary index，可以用另一組分割鍵與排序鍵）與串流只能最終一致；最終一致讀的價格是強一致讀的一半出處——PACELC 的 L 對 C 變成每次讀都能選。

重點整理

  • MySQL 複寫靠 binlog 加三條執行緒（主庫 Binlog Dump、複本接收與套用），預設非同步、列格式、4 條套用工作執行緒。半同步等至少一台複本「收到並寫進日誌」，逾時退回非同步，等待點預設 AFTER_SYNC。
  • 複寫延遲看 Seconds_Behind_Source，只在快速網路上準。「剛寫完讀不到」三招：關鍵讀走主庫、寫後一段時間讀主庫、複本上 WAIT_FOR_EXECUTED_GTID_SET 等到再讀。
  • 複寫解讀取量與可用性，分片解寫入量與容量；MySQL 只有水平分割。範圍分法有熱點、雜湊分法怕加機器、一致性雜湊加虛擬節點。跨片 JOIN 靠同片設計，交易走 Saga，全域 ID 用號段、UUID 或時間戳拼接。
  • CAP：P 是前提，分割時才在 C 與 A 之間逐操作選；平時是 L 對 C（PACELC）。BASE 是基本可用、軟狀態、最終一致。
  • 連線池起點是資料庫核心數 × 2 加磁碟軸數，前提是瓶頸在 CPU 與磁碟，SSD 要更少。總連線數＝執行個體數 × 池大小，對著 max_connections（預設 151）算。
  • 四種壞法各有指標：Connection_errors_max_connections、sys.innodb_lock_waits、磁碟監控、Replica_IO_Running／Replica_SQL_Running。冷資料用 DROP PARTITION 或 DynamoDB TTL，先歸檔再刪。
