執行緒本身

從作業系統執行緒到虛擬執行緒，以及六種狀態

答題公式：先一句話定義，再講差別與取捨，最後補版本或實務註記。課文以 Java 25（撰寫時的長期支援版）為準，Java 21 答案不同的地方會標出來。基礎都在 Java 模組第 10 課〈執行緒與並行〉，本課只寫面試追問的那一層：參數、原理、選型、排查。

面試官：行程與執行緒差在哪？Java 執行緒跟作業系統執行緒是什麼關係？虛擬執行緒改變了什麼？

一句話定義：基礎見第 10 課。官方教學：行程「每個都有自己的記憶體空間」，執行緒「存在於行程之內……共用行程的資源，包括記憶體與開啟的檔案」（Threads share the process's resources, including memory and open files）。出處

跟作業系統執行緒的關係：Thread 文件分兩種。平台執行緒（platform thread）「通常與作業系統排程的核心執行緒一對一對應」（typically mapped 1:1 to kernel threads），「可能是有限的資源」。虛擬執行緒（virtual thread）「由 Java 執行時、而非作業系統排程」，「一個 JVM 可以支撐數百萬條」，「適合大部分時間在等 I/O 的工作，不適合 CPU 密集運算」。出處

虛擬執行緒改變了什麼：JEP 444（Java 21 正式）叫它 M:N 排程：「大量（M）虛擬執行緒被排到少量（N）作業系統執行緒上」，被排上去的平台執行緒叫載體（carrier）。三句一定要答的原文：「虛擬執行緒不是更快的執行緒……提供的是規模（更高吞吐量），不是速度（更低延遲）」（Virtual threads are not faster threads... They exist to provide scale, not speed）；「不要池化虛擬執行緒」（Do not pool virtual threads）；要限制並行數「改用專門為此設計的結構，例如 semaphore」。出處

版本註記（21 與 25 答案不同）：釘住（pinning）指虛擬執行緒阻塞時卸不下載體。JEP 444 寫 Java 21 在「synchronized 區塊或方法內」阻塞會釘住。出處 JEP 491（Java 24 交付）改了 JVM：「阻塞等待監視器會卸載虛擬執行緒並把載體還給排程器」，之後「可以純粹依哪個最能解決問題來選 synchronized 或 java.util.concurrent.locks」。出處 Java 25 的指南列的是「執行原生方法或外部函式時會被釘住」出處；JEP 491 的「後續工作」（Future Work）段另列類別載入與初始化時阻塞的少數情況。出處

虛擬執行緒換的是吞吐不是速度；不池化、用 Semaphore 限量；Java 24 起 synchronized 不再釘住載體

面試官：執行緒有哪幾種狀態？

一句話定義：Thread.State 列舉六個，「一條執行緒在任一時間點只在一個狀態」，且「這些是虛擬機的狀態，不反映任何作業系統執行緒的狀態」。出處

狀態官方定義（節譯）怎麼進去
NEW「尚未啟動」start() 之前
RUNNABLE「正在 JVM 中執行，但可能在等作業系統的資源，例如處理器」沒有 RUNNING 狀態，排到 CPU 與否不區分
BLOCKED「等監視器鎖，以進入 synchronized 區塊／方法，或在 Object.wait 後重新進入」（就是 synchronized 用的那把內建鎖）只有 synchronized
WAITING「無逾時的 Object.wait、無逾時的 Thread.join、LockSupport.park」等 ReentrantLock、take() 這類工具，底層都是 park
TIMED_WAITING「帶正數等待時間的 Thread.sleep、有逾時的 wait／join、parkNanos、parkUntil」sleep、tryLock(1, SECONDS)
TERMINATED「已完成執行」run() 結束或丟出例外

差別與取捨：追問「等 ReentrantLock 是哪個狀態」答 WAITING，不是 BLOCKED：它靠 LockSupport.park，BLOCKED 只留給監視器鎖。出處

執行緒池

七個參數、一條處理順序、四種拒絕、多大才夠

面試官：ThreadPoolExecutor 的參數有哪些？任務進來怎麼處理？

一句話定義：建構子七個參數：corePoolSize「保留在池中的執行緒數，即使閒置」；maximumPoolSize「允許的最大執行緒數」；keepAliveTime「超過核心數的閒置執行緒最多等這麼久就結束」；unit 是它的單位；workQueue「任務執行前存放的佇列」；threadFactory 建執行緒；handler 是「執行緒與佇列都到頂時」的拒絕處理器。出處

處理順序（文件原句三條）：「少於 corePoolSize 時，永遠偏好新開執行緒而非排隊」，「即使其他執行緒閒置」也照開；「已達 corePoolSize 時，永遠偏好排隊而非新開執行緒」；「排不進佇列才新開執行緒，除非會超過 maximumPoolSize，這時任務被拒絕」。出處 答成「先加到最大再排隊」是反的。

核心沒滿就開執行緒，核心滿了先排隊，佇列滿了才加到最大，最大也滿了才拒絕

批次對帳的池可以這樣建：

int cores = Runtime.getRuntime().availableProcessors();
ThreadFactory factory = Thread.ofPlatform().name("reconcile-", 0).factory();
ExecutorService pool = new ThreadPoolExecutor(
        cores,                                  // corePoolSize：常駐執行緒數
        cores * 2,                              // maximumPoolSize：佇列滿了最多加到這麼多
        60, TimeUnit.SECONDS,                   // keepAliveTime 與 unit：多出來的閒置執行緒活多久
        new ArrayBlockingQueue<>(1_000),        // workQueue：有界佇列，滿了才會加執行緒
        factory,                                // threadFactory：執行緒命名，thread dump（把每條執行緒當下在跑什麼、等什麼全部印出來）才認得出來
        new ThreadPoolExecutor.CallerRunsPolicy()); // handler：塞不進去就由呼叫端自己跑

實務註記（佇列決定一切）：文件列三種佇列策略：直接交遞（SynchronousQueue）「通常需要無上限的 maximumPoolSize」，執行緒可能無上限成長；無界佇列（沒給容量的 LinkedBlockingQueue）「永遠不會建立超過 corePoolSize 的執行緒，maximumPoolSize 因此沒有作用」，佇列可能無上限成長；有界佇列（ArrayBlockingQueue）「有助於避免資源耗盡，但較難調校」。出處

面試官：四種拒絕策略？為什麼常聽到「不要用 Executors 的工廠方法」？

策略官方描述（節譯）什麼時候選
AbortPolicy（預設）「丟出 RejectedExecutionException」寧可失敗也不能默默丟，例如轉帳
CallerRunsPolicy「呼叫 execute 的執行緒自己執行該任務」，「簡單的回饋控制機制，會減慢新任務提交的速度」批次工作：呼叫端被拖慢就是自動減速
DiscardPolicy「直接丟掉」，「只給極少數從不依賴任務完成的情況」可丟的統計、心跳
DiscardOldestPolicy「丟掉佇列最前面的任務再重試」，文件自評「很少能接受」幾乎不選

引文出自同一份文件。出處

工廠方法怎麼答才準：ThreadPoolExecutor 文件自己寫「鼓勵程式設計師使用更方便的 Executors 工廠方法」（programmers are urged to use the more convenient Executors factory methods）出處，所以答「知道預設值再用」。文件寫的預設值：newFixedThreadPool 與 newSingleThreadExecutor「操作一個無界佇列」；newCachedThreadPool「視需要建立新執行緒」，「六十秒沒用到的會被終止」。出處 OpenJDK 原始碼更具體：fixed 是 new LinkedBlockingQueue<>()（容量 Integer.MAX_VALUE）；cached 是 maximumPoolSize = Integer.MAX_VALUE 配 SynchronousQueue。出處 結論：fixed 與 single 在任務湧入時佇列吃光堆（Java heap space）；cached 是執行緒無上限（unable to create native thread），兩種錯見〈Java 進階快答：JVM 記憶體、垃圾回收與類別載入〉。對帳池用有界佇列加 CallerRunsPolicy，兩個洞一起堵。

面試官：執行緒池要開多大？

一句話定義：沒有官方公式，只有通則：CPU 密集約等於核心數，I/O 密集可以多很多。核心數用 Runtime.availableProcessors()「回傳 JVM 可用的處理器數」出處。Linux 容器裡 JVM 預設開著容器支援（-XX:+UseContainerSupport），會「判斷 docker 容器內的 Java 行程可用的記憶體量與處理器數」出處；前提是容器有設 CPU 上限才回傳上限，沒設就是主機核心數。

差別與取捨：文件講白了：「若任務常阻塞（例如 I/O 密集），系統可能有辦法排程比你允許的更多執行緒」。出處 面試常聽到的估算式「執行緒數約等於核心數乘上（1 加 等待時間除以計算時間）」出自並行程式設計教材，不是官方文件，只是起點，要靠壓測與監控修正。

版本註記：Java 21 起 I/O 密集的另一個答案是不估：Executors.newVirtualThreadPerTaskExecutor()「為每個任務啟動一條新的虛擬執行緒，建立的執行緒數無上限」出處，要限的是下游承受量，用 Semaphore。

鎖與記憶體模型

synchronized、ReentrantLock、volatile 與 CAS（比較並交換）

面試官：synchronized 與 ReentrantLock 差在哪？什麼是公平鎖、可中斷、條件變數？

一句話定義：基礎見第 10 課。ReentrantLock 文件第一句：「與 synchronized 所用的隱含監視器鎖有相同的基本行為與語意，但有擴充能力」（same basic behavior and semantics as the implicit monitor lock... but with extended capabilities）。出處 Lock 介面說擴充能力是「更靈活的結構」與「多個關聯的 Condition 物件」。出處

synchronizedReentrantLock
取鎖與解鎖進出區塊自動手動；文件建議「lock 後立刻接 try，unlock 當 finally 第一句」出處
限時、可中斷沒有，拿不到就一直等tryLock(時間)、lockInterruptibly()（等鎖時可被 interrupt() 叫醒）
公平鎖沒有new ReentrantLock(true)「競爭時偏好等最久的執行緒」；代價「吞吐量較低（常常慢很多）」，換到「保證不會飢餓」；「tryLock() 不遵守公平設定」出處
條件變數一個物件一組 wait／notifyCondition「把 wait、notify 拆成獨立物件，達到一個物件多個等待集合的效果」出處，例如「非滿」與「非空」分開等
dump 狀態BLOCKEDWAITING

兩者都可重入（同一條執行緒可以再拿一次自己已經握著的鎖）。轉帳要同時鎖兩個帳戶：tryLock 帶逾時加固定取鎖順序，一次破壞死結兩個條件：

static boolean transfer(Account from, Account to, long amount) throws InterruptedException {
    Account first = from.id < to.id ? from : to;   // 一律照帳號大小拿鎖：破壞循環等待
    Account second = (first == from) ? to : from;
    if (!first.lock.tryLock(1, TimeUnit.SECONDS)) return false;   // 等不到就放棄，不是死等
    try {
        if (!second.lock.tryLock(1, TimeUnit.SECONDS)) return false;
        try {
            if (from.balance < amount) return false;
            from.balance -= amount;
            to.balance += amount;
            return true;
        } finally {
            second.lock.unlock();   // 解鎖一定放 finally
        }
    } finally {
        first.lock.unlock();
    }
}

選型：先用 synchronized：寫法短、忘不了解鎖；要限時、可中斷、公平或多個條件才換 ReentrantLock。

面試官：volatile 保證什麼、不保證什麼？happens-before 是什麼？

一句話定義：JLS 8.3.1.4：「欄位可宣告為 volatile，此時 Java 記憶體模型確保所有執行緒看到該變數一致的值」。出處 「一致」怎麼定義就是 happens-before（先行發生）：JLS 17.4.5「若一個動作 happens-before 另一個，則第一個對第二個可見、且排在它之前」（the first is visible to and ordered before the second）。出處

規則（JLS 17.4.5 列出的推論）：「對 volatile 欄位的寫入 happens-before 之後每一次對該欄位的讀取」；「監視器的解鎖 happens-before 之後每一次對同一監視器的上鎖」；start() 與 join() 也各建立一條。出處 因為可傳遞，寫 volatile 旗標之前寫的普通變數，讀到旗標的執行緒也都看得到，這是 volatile 真正的用處。不保證原子性：count++ 仍是三步，「先檢查再動作」要鎖或原子類別。

加分句：java.util.concurrent 套件文件把 happens-before 延伸到高階工具：「Lock.unlock、Semaphore.release、CountDownLatch.countDown 之前的動作 happens-before 成功 acquire 之後的動作」。出處 透過這些工具交手的資料不必再加 volatile。

面試官：CAS 的 ABA 問題是什麼？AtomicInteger 與 LongAdder 怎麼選？

一句話定義：CAS（compare-and-swap，比較並交換）基礎見第 10 課。ABA 是通則名詞，不是 Java 官方文件用語：值從 A 變 B 又變回 A，CAS 只比「現在是不是 A」，誤判成沒人動過。數字計數器無害，「參考加狀態」有害。解法是 AtomicStampedReference：「同時維護一個物件參考與一個整數『戳記』，可原子地一起更新」出處，戳記當版本號。

差別與取捨：AtomicInteger「可原子更新的 int 值」，用途是「原子遞增的計數器」出處，競爭激烈時大家在同一個位址反覆 CAS 失敗重試。LongAdder 文件直接給準則：「多條執行緒更新一個用於統計、而非精細同步控制的共用總和時，通常比 AtomicLong 更好」；「高競爭時本類別的預期吞吐量顯著較高，代價是較高的空間消耗」（under high contention, expected throughput of this class is significantly higher, at the expense of higher space consumption）。出處 原理是把總和拆成多個格子分散競爭，sum() 時再加總。

要拿「更新後的值」立刻做決定（發序號、判斷扣到沒）用 Atomic；只要累計統計（處理筆數、失敗數）用 LongAdder

並行集合與協調工具

ConcurrentHashMap、三個同步輔助類別、CompletableFuture、BlockingQueue

面試官：ConcurrentHashMap 怎麼做到高並行？Java 8 之後結構變成什麼？

一句話定義：文件原句：「所有操作都是執行緒安全的，但讀取操作不涉及鎖定，也不支援鎖住整張表」（retrieval operations do not entail locking）；「讀取（含 get）一般不阻塞，可與更新重疊」；「讀取反映的是它開始時最近已完成的更新結果」。出處

Java 8 之後的結構（OpenJDK 原始碼註解）：「在空桶插入第一個節點只靠 CAS」（performed by just CASing it to the bin）；「其他更新需要鎖，不想替每個桶配一個鎖物件，所以用桶裡的第一個節點本身當鎖，靠內建的 synchronized 監視器」；桶太長轉紅黑樹（一種會自己保持平衡的搜尋樹；原始碼叫 TreeBin）。Java 7 的 Segment 只剩「沒用到、只在序列化時實例化」的相容用途。出處 所以「16 個 Segment」是 Java 7 的答案，現在是「CAS 加桶級 synchronized」。

實務註記：「不允許 null 當鍵或值」；「先 get 再 put」兩次呼叫之間會被插隊，用 computeIfAbsent、merge、compute 一次做完。文件的範例是拿它「當可擴展的頻率表」：freqs.computeIfAbsent(key, k -> new LongAdder()).increment()。出處 〈系統設計：秒殺與限流〉的單機本地計數就用這一行。

面試官：CountDownLatch、CyclicBarrier、Semaphore 各解決什麼？

類別官方定義（節譯）關鍵性質銀行情境
CountDownLatch「讓一或多條執行緒等待其他執行緒中的一組操作完成」「一次性——計數不能重設；需要重設請用 CyclicBarrier」出處主執行緒 await，等 8 個對帳分片各 countDown 才出總表
CyclicBarrier「讓一組執行緒全部互相等待，直到到達共同的屏障點」「叫 cyclic 是因為釋放後可重用」；可帶一個動作「在最後一條到達後、釋放前執行一次」出處多輪計算，每輪全部算完才進下一輪
Semaphore「維護一組許可（permits）；acquire 在有許可前阻塞然後取走一個，release 加回一個」，「常用來限制能存取某資源的執行緒數」沒有擁有者：「釋放許可的執行緒不必是取得那個許可的執行緒」出處核心帳務一次只接 20 個查詢就開 20 個許可；JEP 444 用它取代「拿池限流」

Latch 是「等別人做完」，Barrier 是「大家互等」，Semaphore 是「限量放行」

面試官：CompletableFuture 跟 Future 差在哪？怎麼組合非同步任務？

一句話定義：Future「代表非同步計算的結果……只能在計算完成後用 get 取得，必要時阻塞直到就緒」出處：只能等，不能「完成時通知我」、不能串接合併。CompletableFuture「是可被明確完成的 Future，並可作為 CompletionStage 使用，支援在完成時觸發的相依函式與動作」。出處

怎麼組合：串接用 thenApply、thenCompose（下一步也是非同步）；兩個合一用 thenCombine；多個用 allOf；錯誤用 exceptionally；逾時用 orTimeout（「逾時未完成就以 TimeoutException 例外完成」）；取結果用 join，不丟受檢例外。出處 授信查核同時問餘額與額度：

CompletableFuture<Balance> balance =
        CompletableFuture.supplyAsync(() -> coreBanking.balance(account), pool); // 指定自己的池，不用 common pool
CompletableFuture<Limit> limit =
        CompletableFuture.supplyAsync(() -> risk.limit(account), pool);
return balance.thenCombine(limit, CreditCheck::decide)       // 兩個結果都到了才合併
        .orTimeout(2, TimeUnit.SECONDS)                         // 超過兩秒以 TimeoutException 結束
        .exceptionally(ex -> {
            // 上游丟出的例外會被包成 CompletionException，先拆一層才看得到真正原因；逾時的 TimeoutException 不會被包
            Throwable cause = (ex instanceof CompletionException && ex.getCause() != null) ? ex.getCause() : ex;
            return Decision.reject("查詢失敗：" + cause.getClass().getSimpleName());
        })
        .join();                                                // 等結果；失敗已在上一段轉成 Decision

實務註記（最常被問倒的坑）：「所有沒有明確 Executor 參數的 async 方法，都在 ForkJoinPool.commonPool() 執行」出處，而 common pool 的平行度（同時在跑的工作執行緒數）預設是可用處理器數減一、最少 1（OpenJDK 原始碼：pc = Math.max(1, Runtime.getRuntime().availableProcessors() - 1)）出處；自己 new ForkJoinPool() 才是「預設等於可用處理器數」出處。它是整個 JVM 共用的，拿它跑阻塞 I/O，幾個慢請求就卡住全 JVM 的非同步工作，所以範例都傳自己的池。

面試官：生產者消費者用 BlockingQueue 怎麼寫？

一句話定義：BlockingQueue「取元素時等待佇列變成非空、放元素時等待有空間」；「主要用於生產者消費者佇列」；「不接受 null」；「本身不支援 close 或 shutdown」，文件建議「生產者放入特殊的結束物件（poison object）」。出處

做不到時放入取出
丟例外add(e)remove()
回傳特殊值（false／null）offer(e)poll()
阻塞put(e)take()
阻塞到逾時offer(e, time, unit)poll(time, unit)

四種形式出自介面文件。出處 生產者消費者要的是「阻塞」那一列，不必自己 wait／notify。對帳檔多執行緒入帳的骨架：

private static final String END = new String("__END__");   // 結束物件：new 出來的獨一物件，比對「是不是同一個物件」而不是內容
BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);   // 有界：生產者太快就會被 put 擋住

Thread producer = Thread.ofPlatform().start(() -> {
    try {
        for (String line : lines) queue.put(line);              // 滿了就等，不丟資料
        for (int i = 0; i < consumers; i++) queue.put(END);     // 每個消費者發一個結束物件
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});

for (int i = 0; i < consumers; i++) {
    Thread.ofPlatform().start(() -> {
        try {
            while (true) {
                String line = queue.take();                     // 空了就等，不會空轉耗 CPU
                if (line == END) break;                         // 比同一性不比內容：資料列剛好是 "__END__" 也照常處理
                process(line);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    });
}

選哪個實作：ArrayBlockingQueue「以陣列實作的有界阻塞佇列，經典的有界緩衝」出處；LinkedBlockingQueue「可選有界，未指定容量就是 Integer.MAX_VALUE」出處；SynchronousQueue「沒有任何內部容量，連一個都沒有」出處，正好對應執行緒池那題的三種佇列策略。放進去之前的動作 happens-before 另一執行緒取出之後的動作。出處

ThreadLocal 洩漏、死結排查、活鎖與飢餓

面試官：ThreadLocal 用在哪？為什麼會洩漏？

一句話定義：「每條存取它的執行緒都有自己獨立初始化的副本」，「通常是 private static 欄位，用來把狀態綁在執行緒上（例如使用者 ID 或交易 ID）」。出處 另一個用途是快取非執行緒安全的物件，指南舉 SimpleDateFormat。出處

洩漏：池裡的執行緒不會死，副本一直掛著，用完一定 remove()；原理與排查見〈Java 進階快答：JVM 記憶體、垃圾回收與類別載入〉。出處

版本註記：虛擬執行緒指南提醒這種快取「只在執行緒被多個任務共用重用時有幫助」，而「虛擬執行緒從不池化、從不被不相關的任務重用」，快取失去意義。出處

面試官：死結的四個條件？線上服務卡住怎麼確認是死結？活鎖、飢餓是什麼？

一句話定義：Oracle 教學：「死結是兩條以上執行緒永遠阻塞、互相等待的情況」（two or more threads are blocked forever, waiting for each other）。出處 四個條件（互斥、持有並等待、不可搶占、循環等待）是作業系統教科書的通則（Coffman 條件），不是 Java 官方文件用語出處，解釋見第 10 課。預防就是破壞其中一條：固定取鎖順序破壞循環等待，tryLock 帶逾時破壞持有並等待，轉帳範例兩招都用了。

怎麼確認：疑難排解指南：「印出 thread dump 之後，HotSpot VM 會執行死結偵測演算法」，偵測到就印 Found one Java-level deadlock:，下面列出誰「waiting to lock」哪個監視器、「which is held by」誰。出處 拿 dump 兩條路：主控台按 Control+\ 或 kill -QUIT pid出處；jcmd <pid> Thread.print -l（「印出所有執行緒與堆疊」，-l 加印「java.util.concurrent 的鎖」）出處。先看 CPU：「吃光 CPU 比較可能是迴圈而不是死結」。出處

活鎖與飢餓：教學定義飢餓（starvation）是「執行緒無法定期取得共用資源而無法推進」，成因是「貪心的執行緒長期佔住資源」；活鎖（livelock）的執行緒「沒有被阻塞，只是忙著回應彼此而無法繼續工作」。出處 搶同一把鎖的飢餓用公平鎖，ReentrantLock 文件「保證不會飢餓」但「鎖的公平不保證執行緒排程的公平」（fairness of locks does not guarantee fairness of thread scheduling）出處；其他飢餓要縮短持鎖時間，教學的例子正是 synchronized 方法「常常要很久才回傳」出處。活鎖的常見解法是重試時加隨機等待（通則）。

重點整理

  • 虛擬執行緒由 JVM 排程、M:N 掛在載體上，換吞吐不換速度，不池化、用 Semaphore 限量；Java 24 起（JEP 491）synchronized 不再釘住載體。
  • Thread.State 六種；BLOCKED 只給 synchronized，等 java.util.concurrent 的鎖與工具是 WAITING（帶逾時的是 TIMED_WAITING）。
  • 執行緒池順序是核心、佇列、最大、拒絕；無界佇列讓 maximumPoolSize 失效。newFixedThreadPool 吃堆、newCachedThreadPool 執行緒無上限；批次選有界佇列加 CallerRunsPolicy。
  • ReentrantLock 多了限時、可中斷、公平、多個 Condition。volatile 靠 happens-before 給可見性與順序，不給原子性。
  • ABA 用 AtomicStampedReference；統計計數選 LongAdder。ConcurrentHashMap 讀不加鎖，寫是 CAS 加桶級 synchronized，複合操作用 compute 家族。
  • Latch 等別人做完、Barrier 大家互等、Semaphore 限量放行；CompletableFuture 跑阻塞 I/O 傳自己的池；BlockingQueue 用 put／take 加結束物件。
  • 卡住先看 CPU，再 jcmd Thread.print 找 Found one Java-level deadlock；ThreadLocal 用完 remove()。
