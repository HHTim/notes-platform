為什麼要佇列

解耦、削峰、非同步，以及要付的代價

答題公式：一句話定義，再講取捨，最後補版本。課文依現行版官方文件寫：Apache Kafka 4.3、RabbitMQ 4.3、Spring for Apache Kafka 4.1、Spring AMQP 4.1。名詞：訊息佇列（message queue）是幫程式「留言」的中間站；送的叫生產者（producer）、收的叫消費者（consumer）、中間存放與轉送的伺服器叫 broker（訊息代理）。

面試官：什麼時候該引進訊息佇列？代價是什麼？

一句話定義：呼叫方不需要馬上拿到結果、而且兩邊不該互相拖累時，才值得放一個 broker；理由是解耦、削峰、非同步。

理由與代價：Azure 架構中心寫 broker「把生產者產生訊息的邏輯與消費者處理訊息的邏輯分開」，並提供「時間上的解耦：生產者與消費者不必同時執行」（temporal decoupling. The producer and consumer don't have to run concurrently）。代價同一頁也寫了：「生產者可能不小心把同一則訊息送兩次……消費者的處理邏輯應該是冪等的」；命令類訊息「重複處理會造成錯誤的交易，例如重複下單或重複收費」（duplicate orders or double billing）。出處 引進佇列等於簽三份帳單：一致性從「馬上」變「稍後」、每個消費者都要冪等、多一套要監控的東西。需要同步結果、或兩邊本來就在同一筆資料庫交易裡，直接呼叫就好。削峰見面試集〈系統設計：秒殺與限流〉。

面試官：Kafka 與 RabbitMQ 差在哪？

一句話定義：Kafka 是可重讀的分區日誌，RabbitMQ 是讀完即刪的佇列加路由；前者消費者拉、後者 broker 推；前者靠消費者群組分工、後者靠交換器分派。

KafkaRabbitMQ
訊息存放日誌（log）：訊息「不會在被消費後刪除」，保留多久由主題（topic）設定出處佇列：消費者確認（ack）後「broker 就可以把那次投遞標記為待刪除」出處
拉還是推拉（pull）：推送式系統下消費者「容易被壓垮」，拉的話「消費者只是落後，之後再追上」（simply falls behind and catches up when it can）出處推（push）：「訂閱之後，RabbitMQ 會把佇列裡的訊息推給它」；用 prefetch（預取上限，一次最多欠幾則未確認的訊息）防壓垮出處
怎麼分工消費者群組（consumer group）：主題切成多個分區（partition），「每個分區在任一時刻只被群組裡的一個消費者消費」出處交換器（exchange）依綁定規則把訊息路由到零到多個佇列；同一條佇列的多個消費者「以輪流方式收到訊息」出處
叢集協調KRaft（Kafka 自帶的共識協定）：「Apache Kafka 4.0 只支援 KRaft 模式，ZooKeeper 模式已被移除」（4.0 only supports KRaft mode - ZooKeeper mode has been removed）出處仲裁佇列（quorum queue）：「基於 Raft 共識演算法的耐久、複製式佇列，需要高可用時應視為預設選擇」；鏡像佇列「從 RabbitMQ 4.0 起移除」出處

取捨：事件流、多個下游各自重讀、量大選 Kafka；工作佇列、複雜路由、確認完就消失選 RabbitMQ。差在資料模型，不在誰快。

送達保證與冪等

三種語意，最後一種靠佇列自己做不到

面試官：至多一次、至少一次、剛好一次——哪個做得到、代價是什麼？

一句話定義：Kafka 文件的定義：至多一次「訊息可能丟失，但絕不重送」；至少一次「絕不丟失，但可能重送」；剛好一次「每則訊息只被處理一次」（At most once – Messages may be lost but are never redelivered. At least once – never lost but may be redelivered. Exactly once – processed once and only once）。同段提醒：「很多系統宣稱剛好一次，但務必細讀但書」。出處

語意生產端消費端代價
至多一次不等確認、失敗不重試先提交位移（offset，記錄讀到哪裡的數字）再處理會丟；只適合丟了沒關係的資料
至少一次等 broker 確認，沒收到就重送先處理再提交位移；當機在兩步之間就重做會重複，消費端必須冪等。Kafka「預設保證至少一次送達」（guarantees at-least-once delivery by default）出處；RabbitMQ「使用確認機制可保證至少一次」出處
剛好一次只在「Kafka 讀、Kafka 寫」範圍內成立：交易式生產者把輸出與位移寫進同一筆交易，消費者用 read_committed 只讀已送交的訊息「對其他目的地系統的剛好一次，通常需要那些系統的配合」（generally requires cooperation with such systems）出處——寫進你的資料庫那步還是靠冪等

生產端細節：acks 決定等幾個複本：acks=0「完全不等伺服器確認」；acks=1 領導者寫進本地日誌就回應，它在追隨者複製完之前掛掉「那筆紀錄就會丟失」；acks=all「只要至少一個同步複本存活，紀錄就不會丟失，這是最強的保證」。重送造成的重複由 enable.idempotence 處理：「為 true 時，生產者確保每則訊息在串流裡只寫入一份」，「沒有衝突設定時預設開啟」。出處 做法是 broker 給每個生產者一個編號，配合訊息序號去重。出處

佇列能給的最好保證是「至少一次」；「剛好一次」是佇列加消費端冪等一起做出來的效果，不是買一台 broker 就有

面試官：消費者怎麼做到冪等？

一句話定義：冪等（idempotent，同一件事做一次和做很多次結果一樣）靠三招：去重表、業務唯一鍵、版本號；前提是每則訊息帶全域唯一的訊息編號。

  • 去重表：消費者「必須冪等，例如追蹤已經處理過的訊息編號」出處。以訊息編號為主鍵的一張表，寫這一列與業務更新放同一筆交易；重複訊息撞主鍵，整筆回復。
  • 業務唯一鍵：直接拿訂單編號、轉帳序號當唯一索引。Kafka 講消費端就是這思路：「很多情況下訊息有主鍵，更新因此是冪等的（收到兩次只是再覆寫一次）」。出處
  • 版本號：更新加條件 WHERE version = 舊版本，影響列數 0 代表已處理或已過期；順序亂了也不會把舊狀態蓋回去。
CREATE TABLE processed_message (
  message_id   VARCHAR(64) PRIMARY KEY,  -- 生產端給的全域唯一編號
  consumer     VARCHAR(64) NOT NULL,
  processed_at TIMESTAMP   NOT NULL
);

BEGIN;   -- 兩步同一筆交易
INSERT INTO processed_message VALUES (:message_id, 'ledger-service', NOW());  -- 重複會撞主鍵
UPDATE account SET balance = balance - :amount WHERE account_id = :from_id;
COMMIT;

RabbitMQ 建議「消費者實作應設計成冪等，而不是明確地去重」；重送的訊息帶 redelivered 旗標，但只保證「旗標沒設就沒被看過」，反過來不成立。出處 客戶端帶進來的冪等鍵見面試集〈系統設計：秒殺與限流〉。

順序、丟失、堆積、死信

四個營運題

面試官：訊息順序怎麼保證？

一句話定義：Kafka 只保證同一分區內有序，所以用帳戶編號當訊息的 key——「同一個 key 的事件會寫進同一個分區，Kafka 保證消費者讀那個分區時順序與寫入時完全相同」。出處 全域有序等於只開一個分區，代價是沒有平行度。RabbitMQ 一條佇列先進先出，但多個消費者輪流取、其中一個失敗重排，順序就變；SQS 的 FIFO 佇列用訊息群組做到「同一佇列裡多個各自有序的群組」。出處

面試官：訊息丟了怎麼辦？

一句話定義：三個地方會丟——生產者送出但 broker 沒收到、broker 沒寫進足夠複本、消費者收到但處理前當機——各有一個開關。

  • 生產者確認：Kafka 用 acks=all 加 min.insync.replicas（最少同步複本數）：分區「只在同步複本數高於最小值時才接受寫入」。出處 RabbitMQ 是發布者確認（publisher confirm）：「持久化訊息路由到耐久佇列時，basic.ack 會在寫進磁碟之後才送出」。出處
  • 複本：Kafka「已送交的訊息不會丟失，只要任一時刻至少有一個同步複本存活」出處，常見「複製因子 3」出處。RabbitMQ「重要資料務必使用耐久佇列，並以持久化方式發布訊息」出處——耐久（durable）是佇列定義撐得過重啟，持久（persistent）是訊息寫進磁碟，兩個都要。
  • 手動確認：RabbitMQ 的自動確認「訊息一送出就視為成功送達」，官方稱它射後不理、「應視為不安全」（should be considered unsafe）；手動模式「在做完該做的事之前不該確認」。出處 Kafka 對應的是關掉 enable.auto.commit（預設 true，位移「在背景定期提交」，間隔 5 秒），改成處理完再提交。出處

「非同步複製會丟已答應的寫入」，資料庫模組第 5 課〈分散式鎖與 Redis〉用 Redis 講過；acks=all 就是改成等同步複本來解。

面試官：訊息堆積怎麼處理？

一句話定義：堆積（backlog，生產快過消費）先加消費者，再批次，最後問它會不會自己消。加消費者有上限：一個分區同時只給群組裡一個消費者出處，超過分區數的閒著，所以分區數要在建主題時估好。批次是把每則一次資料庫往返改成一批一次，一次 poll() 最多回 max.poll.records 則（預設 500）。出處 拉模式下尖峰過了會自己消；持續堆積是容量不夠，不是調參數。RabbitMQ 記得設 prefetch，自動確認下「沒有這個限制，消費者可能被壓垮、在記憶體累積訊息、耗盡 heap」。出處

面試官：死信佇列是什麼、什麼時候用？

一句話定義：死信佇列（dead letter queue）是處理不了的訊息的收容所，讓主流程不被一則壞訊息卡死。RabbitMQ 列了四種死信：消費者負面確認且不重排、「訊息因 TTL 過期」、「佇列超過長度上限而被丟棄」、「仲裁佇列的訊息被退回超過 delivery-limit 次」，收容處叫死信交換器（dead letter exchange），「就是一般的交換器」。出處 最後那種叫毒訊息（poison message，「讓消費者反覆重排、永遠無法被完整處理並正面確認的訊息」），仲裁佇列用 x-delivery-count 標頭記次數。出處 SQS 的對應是 maxReceiveCount，官方提醒「設太低一次失敗就進死信，要設得夠高讓重試有機會」。出處 死信不是丟掉，是留證據：數量大於 0 要告警，修好後要能重放。Kafka 本身沒這概念，是客戶端框架做的，最後一節會講。

Outbox 與 Saga

先寫資料庫再發訊息，為什麼會不一致

面試官：為什麼「先寫資料庫再發訊息」會不一致？Outbox 怎麼解？

一句話定義：資料庫交易與發訊息是兩個系統的兩次寫入（AWS 叫它雙重寫入問題）：「資料庫更新成功但事件通知失敗，下游不會知道這個變更」；反過來「資料庫更新失敗但事件通知送出了，資料可能被弄壞」。出處 不用兩階段提交（2PC，先問大家能不能做、都說能才一起做）是因為「資料庫或 broker 可能不支援，而且把服務同時耦合到兩者通常不是好事」。出處 面試集〈系統設計：短網址的高併發〉那課「丟進佇列就回成功」的錯誤，正解就在這裡。

解法：交易式 Outbox（transactional outbox）「先把訊息當作更新業務實體那筆交易的一部分存進資料庫，再由另一個程序送到 broker」（first store the message in the database as part of the transaction that updates the business entities. A separate process then sends the messages to the message broker）；參與者是寄件者、資料庫、訊息寄件匣（關聯式資料庫就是一張表）、訊息轉送器（message relay）。好處是「訊息保證在交易送交時、且只在送交時被送出」。出處

CREATE TABLE outbox (
  id             BIGINT      PRIMARY KEY,  -- 遞增序號＝訊息編號，轉送順序照它
  aggregate_type VARCHAR(64) NOT NULL,     -- 'transfer'
  aggregate_id   VARCHAR(64) NOT NULL,     -- 轉帳序號，當 Kafka 的 key 保順序
  event_type     VARCHAR(64) NOT NULL,     -- 'TransferDebited'
  payload        JSON        NOT NULL,
  created_at     TIMESTAMP   NOT NULL,
  published_at   TIMESTAMP   NULL          -- 轉送成功後填上
);

BEGIN;   -- 業務寫入與寄件匣同一筆交易
UPDATE account SET balance = balance - 1000 WHERE account_id = 'A';
INSERT INTO outbox (...) VALUES (...);
COMMIT;

轉送器兩種做法：輪詢發布者（polling publisher）「輪詢 outbox 表來發布訊息」，缺點「難以按順序發布」出處；交易日誌尾隨（transaction log tailing，讀資料庫的變更日誌）「不用 2PC、保證準確」，缺點「需要資料庫專屬的方案、難以避免重複發布」出處；AWS 的範例用 DynamoDB Streams 這種變更資料擷取（CDC）做後者。出處

Outbox 把「發訊息」變成至少一次——轉送器「可能在發布之後、記錄之前當機，重啟就再發一次」，消費端還是要冪等出處

面試官：Saga 的兩種協調方式？補償怎麼設計？

一句話定義：Saga「是一連串本地交易，每筆更新資料庫並發布事件觸發下一筆；若某筆因違反業務規則失敗，就執行一連串補償交易（compensating transaction）倒回前面的變更」（A saga is a sequence of local transactions… executes a series of compensating transactions that undo the changes）。出處 它跟 2PC 的取捨面試集〈後端與雲端面試題庫〉講過，這裡展開狀態機。

協同式（choreography）編排式（orchestration）
誰決定下一步「每筆本地交易發布領域事件，觸發其他服務的本地交易」出處「一個編排器（orchestrator）告訴參與者要執行哪些本地交易」出處
適合「參與者只有少數幾個、要簡單實作且沒有單點故障」出處步驟多、要集中看流程狀態；AWS 用 Step Functions 狀態機實作出處
代價「參與者變多就難以追蹤彼此的相依」，逾時、重試「要在每個元件各自實作」出處「編排器可能成為單點故障」出處
 
編排式 Saga 的狀態機（跨行轉帳）

  STARTED ──扣款成功──▶ DEBITED ──對方入帳成功──▶ COMPLETED
     │                    │
   扣款失敗           入帳失敗（帳戶不存在、逾時到上限）
     ▼                    ▼
  FAILED           COMPENSATING ──退回扣款成功──▶ FAILED（錢已回到原帳戶）
                          │
                     退回也失敗 ──▶ 死信 + 人工介入

補償三條規則：第一，補償是反向動作不是刪除——扣款的補償是退回同金額並留下兩筆紀錄，因為 Saga「沒有自動回復，開發者必須設計明確倒回變更的補償交易」。出處 第二，每步與每個補償都冪等：「Saga 參與者需要冪等，才能在當機或編排器故障後重複執行」。出處 第三，Saga「缺少 ACID 裡的隔離性，多個 Saga 同時執行可能造成資料異常」出處——扣款後、入帳前，別人看到的餘額已經少了；AWS 建議「語意鎖」出處，實務上就是把那筆錢標成「轉出中」的凍結狀態。

最終一致與銀行帳務

「暫時看不到」可以，「錢不見了」不行

面試官：最終一致對強一致，業務上怎麼解釋「暫時看不到」？

一句話定義：強一致是寫完的下一秒任何人都讀到新值；最終一致是所有複本會在一段時間內趨於一致，期間有人可能讀到舊值。AWS 對 Saga 寫「依序處理本地交易的結果就是最終一致」，解法是「跟業務團隊講清楚一致性模型的預期，或改用強一致的資料儲存」（setting your business teams' expectations for the consistency model）。出處

跟人怎麼講：別說「最終一致」四個字，說「送出成功」跟「對方看到」是兩個時間點，畫面顯示「處理中」而不是假裝完成。三個承諾：處理中的狀態看得到、多久之內一定有結果、失敗一定退回原狀。答這題要主動說哪些地方不能最終一致——下一題。

面試官：銀行轉帳可以用最終一致嗎？

一句話定義：「對方何時看到錢」可以，「錢的總額」不行。同一系統內的轉帳，扣款與入帳放同一筆 ACID 交易，不必引進佇列；跨系統（跨行、外部支付機構）沒有共同的資料庫交易，才用 Saga 加冪等加對帳，每步守住「錢不能少、帳要對得上」。

  • 帳務分錄：複式簿記（double-entry bookkeeping）「每一筆交易都以相等且相反的兩筆分錄（借與貸）記錄」（recorded with equal and opposite entries (debits and credits)）。出處 套進 Saga：扣款不是「餘額減 1000」而是「客戶帳戶貸 1000、轉出中間帳戶借 1000」，錢從沒消失，只是換了位置；入帳成功後中間帳戶才結掉，補償則反向再記兩筆。分錄只增不改。
  • 冪等：每筆轉帳一個交易序號，扣款、入帳、補償都拿它當唯一鍵；重送、重跑撞到唯一鍵就是「已經做過」，避開 Azure 那句「重複收費」。出處
  • 對帳：定時（例如日終）把兩邊分錄逐筆比對：己方每筆「轉出中」，對方是否都有入帳，差異進人工處理。對帳是承認「至少一次」與「補償也可能失敗」真的會發生；死信佇列裡的東西最後都要在對帳表上有交代。

先問同一系統還是跨系統；同一系統用 ACID 交易；跨系統用 Saga，但分錄借貸相等、每步冪等、日終對帳一個都不能省

Spring 怎麼接

@KafkaListener 與 @RabbitListener 各一眼

面試官：訊息佇列在 Spring 怎麼接？

Spring for Apache Kafka（4.1）：「@KafkaListener 註解用來把一個 Bean 的方法指定為監聽器容器的監聽器」，需要 @EnableKafka 與一個名為 kafkaListenerContainerFactory 的容器工廠 Bean（Spring Boot 自動組態會給）。出處

public class Listener {

    @KafkaListener(id = "foo", topics = "myTopic", clientIdPrefix = "myClientId")
    public void listen(String data) {
        ...
    }
}

位移何時提交由 AckMode 決定：「從 2.3 版起，框架把 enable.auto.commit 設成 false」；預設 BATCH「一次 poll() 的紀錄全部處理完才提交」，RECORD「每筆監聽器回傳後就提交」，MANUAL 由監聽器自己呼叫 Acknowledgment.acknowledge()。出處 這就是「先處理再提交」的實作位置。丟例外時預設的 DefaultErrorHandler 用 FixedBackOff(0L, 9)，共 10 次嘗試；用完交給 DeadLetterPublishingRecoverer，「預設送到名為 原主題-dlt 的主題、與原紀錄相同的分區」——Kafka 的死信主題就是這樣長出來的。出處

Spring AMQP（4.1）：「最簡單的非同步收訊方式是註解式監聽器端點」，「只要 myQueue 有訊息，processOrder 就會被呼叫」；佇列「必須已存在並綁定到某個交換器」，或由 RabbitAdmin 自動宣告。出處

@Component
public class MyService {

    @RabbitListener(queues = "myQueue")
    public void processOrder(String data) {
        ...
    }
}

acknowledgeMode 三種：NONE「不送任何確認，RabbitMQ 叫它 autoack」；MANUAL「監聽器必須自己呼叫 Channel.basicAck()」；AUTO（預設）「容器自動確認，除非監聽器丟出例外」。出處 丟例外的預設行為是「訊息被拒絕並由 broker 重排」，壞訊息「會被一再重送」；解法是 defaultRequeueRejected 設 false「讓訊息被丟棄（或路由到死信交換器）」，或丟 AmqpRejectAndDontRequeueException 針對單一訊息不重排。出處

追問時要補的：@Transactional 包在監聽器方法上只管資料庫那筆交易，管不到位移提交或訊息確認，「資料庫送交了、位移沒提交」的窗口還在——消費端一定要冪等的另一個理由。@Transactional 本身見 Spring 模組第 6 課〈Spring AOP 與交易控制〉。

Amazon SQS：沒有 ack，用可見性逾時（visibility timeout）代替：「收到訊息後它仍在佇列裡，但對其他消費者暫時不可見」（remains in the queue but becomes temporarily invisible to other consumers），逾時前沒刪除就「重新可見、可被另一個消費者取走」，預設 30 秒。出處 標準佇列「至少一次送達，可能送出多份複本、順序偶爾會亂」出處；FIFO 佇列「順序嚴格保留、不引入重複」，但「每秒交易數有限」。出處

重點整理

  • 引進佇列的理由是解耦、削峰、非同步；代價是一致性變「稍後」、每個消費者都要冪等、多一套基礎建設。需要同步結果就不要用。
  • Kafka 是可重讀的分區日誌、消費者拉、消費者群組分工、4.0 起只有 KRaft；RabbitMQ 是讀完即刪的佇列、broker 推、交換器路由、4.0 起用仲裁佇列取代鏡像佇列。
  • 佇列能給的最好保證是至少一次；剛好一次只在 Kafka 讀寫 Kafka 的範圍內成立，寫進自己的資料庫靠去重表、業務唯一鍵或版本號。
  • 順序只在同一分區內成立，用業務鍵當 key；不丟訊息靠 acks=all 加 min.insync.replicas、耐久佇列加持久訊息、處理完再確認；堆積先加消費者（上限是分區數）再批次；處理不了的進死信佇列，要告警、要重放。
  • 先寫資料庫再發訊息是雙重寫入；交易式 Outbox 把訊息寫進同一筆交易的寄件匣表、由轉送器另外送出，代價是至少一次。
  • Saga 是一連串本地交易加補償，協同式靠事件、編排式靠編排器；補償是反向動作、每步冪等、缺隔離性用凍結狀態補。
  • 銀行轉帳：同一系統用 ACID 交易；跨系統用 Saga，但分錄借貸相等、每步用交易序號冪等、日終對帳都不能省——「暫時看不到」可以，「錢不見了」不行。
