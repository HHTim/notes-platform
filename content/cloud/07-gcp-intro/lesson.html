平台全貌

Google Cloud 是一組透過網路使用的雲端服務

Google Cloud Platform（GCP）是 Google 提供的雲端運算平台。不必先自己建好所有實體伺服器，就能用到運算、儲存、網路、資料庫、資料分析、容器與人工智慧等能力。

需求代表服務用途
虛擬機器Compute Engine建立並執行 VM。
物件儲存Cloud Storage存放圖片、影片、備份與其他物件。
虛擬網路Virtual Private Cloud管理 Subnet、路由與防火牆規則等網路設定。
關聯式資料庫Cloud SQL使用代管的關聯式資料庫。
KubernetesGoogle Kubernetes Engine執行與管理容器化的工作負載。

管理階層

Project 是管理資源的基本單位，不是地理位置

Organization（組織，可選）
└── Folder（資料夾，可選）
    └── Project（專案）
        ├── Compute Engine VM
        ├── VPC Network
        ├── Cloud Storage Bucket
        └── 其他服務資源

Organization 通常代表一間公司或機構；Folder 可以依部門、系統或環境整理 Project；Project 則承載 API、IAM、計費關聯、配額與各種服務資源。

可以想成公司的文件櫃：Organization 是整間公司，Folder 是部門抽屜，Project 是實際辦某件事的資料夾。這是管理關係，不是機房地圖，所以 Project 本身不是 Region 也不是 Zone。

政策可以套在不同管理層級，並影響底下的資源。設計權限時要看完整階層，不能只看資源旁邊那一條設定。

更精確地說，權限是往下累加的。Google 的原文是：「一個資源的有效允許政策，是設定在該資源上的允許政策，與從其父項繼承而來的允許政策的聯集。」出處（聯集＝把兩邊的權限全部合起來算，重複的只算一次。）

這句話的實務後果是：你在 Project 上「少給」某個人權限，並不會把他在 Organization 或 Folder 那一層已經拿到的權限收回來。往下看只會越看越多，不會越看越少。

所以查一個人為什麼碰得到某個資源，要從 Organization 一路看到資源本身，不能只看資源旁邊那一格。真的要在低層擋掉上層給出去的東西，得另外用拒絕政策（deny policy），那是一套跟允許政策分開的機制。

地理位置

Region 是地理區域，Zone 是裡面的部署與故障隔離位置

Region 是 Google Cloud 的獨立地理區域；Zone 是 Region 內的部署位置，也是故障隔離單位。一般的 Compute Engine VM 屬於 Zonal Resource，所以建立時要選 Zone。

一個 Region 有幾個 Zone？Google 官方文件寫的是一個 Region 由三個或以上的 Zone 組成出處。同一頁還寫了通則是這些 Zone 分布在三座以上的實體資料中心，但緊接著列了例外：斯德哥爾摩、墨西哥、大阪、蒙特婁這四個 Region，三個 Zone 只落在一或兩座實體資料中心。所以「一個 Zone 對應一棟資料中心」不能當定律，別把 Zone 記成固定的實體資料中心階層。

另外兩個常被引用的延遲數字要小心：Google 的區域與可用區文件只說同一 Region 內的 Zone 之間具有高頻寬、低延遲的網路連線，並沒有把「小於 5 毫秒」或「小於 1 毫秒」寫成承諾出處。

講清楚一點：這不代表實測跑不出那種數字。Google 在選區域指南裡給了一條估算法則——「每 100 公里約 1 毫秒來回延遲」，而且同一段還提醒：網路不會走理想路徑，實際距離通常是地圖直線距離的 1.5 到 2 倍，估的時候要把這個倍數算進去出處。同一 Region 的 Zone 通常只隔幾公里到幾十公里，所以實際延遲很低是合理的。

差別在於：那是估算，不是可以拿來當設計保證的規格。要規劃對延遲敏感的架構，就實測自己那組 Region 與 Zone——Google 的 Network Intelligence Center 也有區域配對的實測延遲可看——別把記憶中的數字當承諾。

選位置時通常要一起考慮使用者延遲、資料落地、災難復原、那裡有沒有你要的服務或硬體，以及資料傳輸成本。把 VM 分散到不同 Zone 能降低單一 Zone 故障的影響，但要自動導流還是得搭配負載平衡、健康檢查或其他故障切換設計。

資源範圍

Global、Regional、Zonal 是資源的適用範圍，不是一條路徑

範圍意義常見例子
Global不隸屬單一 Region 或 ZoneVPC Network
Regional隸屬一個 Region，但不綁定單一 ZoneSubnet
Zonal隸屬一個 Zone一般的 Compute Engine VM
同一台 VM 可以同時這樣描述：
管理上：屬於某個 Project
地理上：建立在某個 Zone
網路上：網路介面連到同一 Region 的 Subnet

不要背成「Project → VPC → Region → Zone → Subnet → VM」。Region 與 Zone 是地理位置，不是建立在 VPC 裡面的子資源。

上面三種講的是「資源屬於哪個範圍」。另外還有一個很容易跟 Regional 搞混的詞叫 Multi-Region（多重區域），它是存資料時可以挑的地理範圍，而且比一個 Region 更大。Cloud Storage 的位置文件把三種選項並列定義：「region 是一個特定的地理位置，例如愛荷華（US-CENTRAL1）」、「dual-region 是一組特定的區域配對，例如東京與大阪（ASIA1）」、「multi-region 是一個大型地理區域，包含兩個或更多的地理區域，例如美國（US）」出處。

Global 和 Multi-Region 是兩件事，別混用。Global（例如 VPC Network）的意思是「這個資源不綁任何地點」；Multi-Region 的意思是「這份資料實際被放在一整片涵蓋多個區域的範圍裡」——你還是選了地點，只是選了一大片。這樣選的用意在官方的地理位置說明裡寫得很清楚：這類跨區域的服務「設計上能在單一區域失效之後繼續運作」出處。會挑 Multi-Region 的多半是存資料的服務，例如 Cloud Storage 的 bucket；前面提過，一般的 Compute Engine VM 是 Zonal，建立時挑的是 Zone。

虛擬網路

VPC 像跨城市的私人道路網，Subnet 像各城市的地址區

Google Cloud 的 VPC Network 是 Global Resource，可以包含位於不同 Region 的 Subnet；每個 Subnet 只屬於一個 Region，而不屬於單一 Zone。

Project：shopping-project
├── VPC：shopping-vpc（Global）
│   ├── taiwan-subnet（Regional）
│   └── tokyo-subnet（Regional）
└── Compute Engine VM（Zonal）
    └── 網路介面 → 與 VM 同一 Region 的 Subnet

所以同一 Region 不同 Zone 的 VM 可以連到同一個 Subnet；但 VM 的網路介面不能直接連到另一個 Region 的 Subnet。

Compute Engine

GCE 像向 Google 租一台可以遠端管理的虛擬電腦

Google Compute Engine（GCE）是基礎設施即服務（Infrastructure as a Service，IaaS）。Google 維護底層實體硬體，使用者選 VM 規格、作業系統、磁碟與網路，並負責作業系統更新、應用程式，以及多數 VM 內部的安全設定。

GCE 適合需要控制作業系統、安裝特定軟體、跑傳統應用程式，或工作負載還不適合容器化的情況。它給你較高的控制度，也代表要承擔較多維運責任。

GCE 常被提到的兩個計費特色是「以秒計費」與「持續使用折扣」（sustained-use discount，同一個月裡跑得夠久就自動打折）。兩項都存在，但各有一個條件：以秒計費是每分鐘起跳，滿一分鐘之後才以一秒為單位計費；持續使用折扣只適用於部分機器系列（例如 N1、N2、N2D、C2、M1、M2），較新的機型不在其中出處。實際計價一律以當下的官方定價與帳務文件為準。

抽象層級

從 VM 到函式，管理責任一層層交給平台

服務主要部署單位適合情境
Compute EngineVM需要作業系統與基礎設施的控制權。
Google Kubernetes Engine容器化工作負載需要 Kubernetes 編排能力，又希望平台代管部分叢集工作。
Cloud Run容器想執行容器，但不想直接管伺服器或叢集。
App Engine應用程式希望由平台處理較多執行環境與擴展工作。
Cloud Functions事件驅動的函式用事件觸發較小的程式單元。

選服務不是單純追求「越自動越好」。需要特殊作業系統設定時，GCE 可能比較合適；已經在用 Kubernetes 且需要編排控制時，可以考慮 GKE；想直接跑容器又不想管基礎設施時，Cloud Run 通常更貼近需求。

角色的三種來源

基本、預先定義、自訂——由粗到細

在 Google Cloud，權限不是一條一條直接給人，而是包成「角色」（role）再授予。角色依來源分三種：

角色種類誰決定內容顆粒度什麼時候用
基本角色（basic）Google 內建，範圍很寬最粗個人實驗、沙盒環境
預先定義角色（predefined）Google 依服務維護中等，對準單一服務日常授權的首選
自訂角色（custom）你自己挑權限組出來最細預先定義的都不剛好時

官方的定義分別是：基本角色「是權限非常寬鬆的角色，給予對 Google Cloud 資源的廣泛存取」；預先定義角色「除了基本角色之外，IAM 還提供額外的預先定義角色，對特定的 Google Cloud 資源給予細緻的存取」；自訂角色則是「IAM 也讓你建立自訂 IAM 角色」出處。

同一頁對基本角色有一則明確的警告：「基本角色包含跨所有 Google Cloud 服務的數千項權限。在正式環境中，除非別無選擇，否則不要授予基本角色。」配合前面講的權限聯集，在高層級隨手給一個基本角色，底下所有專案都會跟著吃到。

名稱這幾年換過，查資料時要對得上：Owner、Editor、Viewer 這三個老面孔，官方現在歸類為舊版基本角色（legacy basic roles），並且寫明「舊版基本角色在 IAM 推出之前就已存在。它們原本被稱為primitive roles（原始角色）」；另外還有一組較新的基本角色是 Admin、Writer、Reader，但這組目前掛著預覽版（Preview）標示、受「Pre-GA 條款」規範，官方註明預覽版功能「以現狀提供，支援可能有限」，而且還不能從主控台授予——官方寫「你無法使用 Google Cloud 主控台授予 Reader、Writer 或 Admin 角色。請改用 API 或 gcloud CLI」出處。所以「Primitive／Predefined／Custom 三種角色」這個講法沒有講錯東西，只是用的是舊名字——Owner、Editor、Viewer 本身還在，照樣能用。

給程式用的帳號

服務帳戶既是「誰」，也是「一個可以被授權的東西」

服務帳戶（Service Account）是給程式用的帳號。官方定義是：「服務帳戶是一種特殊的帳戶，通常由應用程式或運算工作負載使用（例如一個 Compute Engine 執行個體），而不是由人使用。」出處。這跟第 2 課 AWS 用 Role 取代長期金鑰是同一個思路：讓程式帶著一個有身分的帳號去做事，而不是把密碼寫進程式碼。

它有個一開始容易卡住的雙重身分。官方寫的是：「服務帳戶是主體（principal）。這表示你可以授予服務帳戶存取 Google Cloud 資源的權限……然而，服務帳戶同時也是資源。這表示你可以讓其他主體取得存取這個服務帳戶的權限。」出處

「這個服務帳戶能做什麼」和「誰可以使用這個服務帳戶」是兩件要分開設定的事。

講到「程式怎麼拿到這個身分」時要補一個前提：用服務帳戶金鑰（service account key，一個下載下來的憑證檔）確實做得到，也還能用，但這是 Google 現在明講要盡量避開的做法——最佳做法文件寫的是「我們建議你盡可能避免使用服務帳戶金鑰」。理由有三個：金鑰是誰拿去用的查不出來（稽核紀錄只看得到服務帳戶動過資源，看不出是誰用了那把金鑰）、有建立金鑰權限的人可以藉此取得比自己更大的權限，以及「任何持有服務帳戶金鑰的人都能使用它」。建議的替代做法是把服務帳戶直接附加到資源上（VM、GKE 的 Pod）、用身分模擬，或對外部工作負載用 Workload Identity 聯合出處。

這裡要先把兩件事分開，不然容易誤會。第一件：把 A 專案的服務帳戶授權去存取 B 專案的資源（例如讓它讀 B 專案的 Cloud SQL），只要在 B 專案那邊把角色授予這個服務帳戶就成立，預設就能做。第二件：把 A 專案的服務帳戶「附加」到 B 專案的一台 VM 上，讓那台機器直接以這個身分執行，才是下面要過兩關的那件事。前者是給權限，後者是把身分綁到別的專案的機器上。

跨專案的第二件事就卡在後面那一半。把 A 專案建立的服務帳戶，掛到 B 專案的一台 VM 上，並不是預設就能做的事，要先過兩關。第一關是放行一條機構政策的限制條件（機構政策＝organization policy，一套可以套用在組織、資料夾或專案上的規則）：那條限制條件叫 iam.disableCrossProjectServiceAccountUsage，只有開和關兩種值，官方的說法是要確保它「未被強制執行」。這一條要注意設定的位置——官方寫「它預設就是強制執行的，而且只能設定在專案層級，不能設在資料夾或組織層級」，所以去組織那一層找會找不到。第二關是要讓目標服務的服務代理（service agent，Google 代表某個服務去做事的內建帳號），在那個服務帳戶上取得「服務帳戶權杖建立者」角色（roles/iam.serviceAccountTokenCreator）——權杖（token）就是那張有時效的臨時通行證，有了這個角色才能替那個服務帳戶簽發通行證出處。

開通之後會多一個副作用值得先知道：IAM 會自動替放服務帳戶的那個專案加上一道「專案鎖」（project lien），用途是擋住誤刪整個專案。官方原文是「IAM 會新增一道專案鎖，防止該專案被刪除」，來源標記是 iam.googleapis.com/cross-project-service-accounts。所以那個專案之後想刪會刪不掉，要先處理這道鎖出處。

責任不會消失

用了代管服務，還是要管權限、資料與應用程式

Google 負責維護底層基礎設施，但客戶還是要正確設定 IAM、保護資料、限制網路存取，並維護自己控制的作業系統與程式。用的服務抽象程度越高，Google 負責的底層工作越多；客戶對自己資料與存取決策的責任並不會因此消失。

先問「我需要控制到哪一層」，再選服務；不要先挑流行的工具，再勉強把工作負載塞進去。

重點整理

  • Organization、Folder、Project 是管理階層；Region、Zone 是地理位置，兩條線不要混在一起。
  • VPC 是 Global，Subnet 是 Regional，一般的 Compute Engine VM 是 Zonal。
  • VM 建立在 Zone，並透過網路介面連到同一 Region 的 Subnet。
  • GCE 控制度高，相對要管的系統層工作也多。
  • GKE、Cloud Run、App Engine、Cloud Functions 提供不同程度的代管與抽象。
  • 有效權限是「自己身上的」加上「從父項繼承的」的聯集，所以往下只會越加越多，低層擋不掉高層給出去的權限。
  • 角色分基本、預先定義、自訂三種；Owner／Editor／Viewer 是舊版基本角色，舊名叫 primitive roles，正式環境別隨手給。
  • 服務帳戶既是可以被授權的主體，也是別人可以被授權去用的資源；跨專案使用要先放行機構政策，而且會多一道防誤刪的專案鎖。
  • Multi-Region 是比 Region 更大的資料存放範圍，跟「不綁地點」的 Global 不是同一回事。
