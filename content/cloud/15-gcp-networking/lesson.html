先看懂那條斜線

一個位址加一個斜線數字，就圈出一整段範圍

一個 IPv4 位址是 32 個位元（bit，電腦裡最小的資料單位，只有 0 和 1 兩種值），習慣上切成四段、每段用十進位寫出來，例如 10.0.0.7。

但規劃網路時要講的往往不是「某一個位址」，而是「某一段連續的位址」。這時候就用 CIDR 寫法：位址後面加一條斜線和一個數字，例如 10.0.0.0/24。（CIDR＝Classless Inter-Domain Routing，無類別跨網域路由。名字聽起來很大，實際上就是這個斜線寫法。）

斜線後面的數字＝前面幾個位元是固定的「網路」部分；剩下的位元才可以變，用來編號裡面的機器。

所以 10.0.0.0/24 的意思是：32 個位元裡，前 24 個固定，剩下 8 個可以自由變化。8 個位元能排出 2 的 8 次方＝256 種組合，也就是 10.0.0.0 到 10.0.0.255 這 256 個位址。

同一件事還有另一種老寫法叫子網路遮罩（subnet mask）：把「前 24 個位元固定」畫成 255.255.255.0。兩種寫法講的是同一件事，/24 只是比較短。

最容易記反的一點：斜線數字越大，範圍越小。因為固定的位元越多，能自由變化的就越少。/8 是一千六百多萬個位址，/32 只剩一個。想成綁繩子——綁得越緊，能動的空間越少。

兩條路都對得上

最長前綴比對：誰比較精確，就聽誰的

路由表是一張「要去哪裡、下一站走哪條路」的對照表。麻煩的是同一個目的地常常會同時符合好幾條規則。假設表上有這兩條：

目的地 0.0.0.0/0       → 走對外閘道     （任何位址都符合）
目的地 10.0.5.0/24     → 走內部通道     （只有這 256 個位址符合）

現在要送一個封包到 10.0.5.7。兩條都對得上——第一條因為它涵蓋全部位址，第二條因為 10.0.5.7 正好落在那 256 個裡面。該走哪條？

規則叫最長前綴比對（Longest Prefix Match）：挑斜線數字最大、也就是講得最精確的那一條。這裡 /24 比 /0 精確，所以走內部通道。

「前綴」（prefix）就是前面那段固定不變的位元；比得越長，代表這條規則指名得越具體。這是網路設備共通的作法，不是哪一家雲端獨有的。

Google Cloud 的文件描述這件事時用的措辭是「最具體的目的地」而不是「最長前綴比對」——原文是「Google Cloud determines which applicable static or dynamic routes have the most specific destination that contains the destination IP address of the packet」（Google Cloud 會判斷哪些適用的靜態或動態路由，擁有涵蓋該封包目的位址的最具體目的地）出處。兩種講法指的是同一個規則，但你在 Google 的頁面上搜「longest prefix match」多半找不到，搜「most specific」才對得上。

如果兩條路由一樣精確呢？那就再比優先順序值（priority）。Google Cloud 的說明是「優先順序可以從 0（最高優先）到 65535（最低優先）」出處——數字小的贏，跟一般「第一名是 1」的直覺一樣。

不是全部都歸你

Google Cloud 每個子網路先拿走四個位址

切好一個子網路之後，裡面的位址並不是全部都能配給機器。Google Cloud 在每個子網路的主要 IPv4 範圍裡固定保留四個，文件用 10.1.2.0/24 當例子列出來：

位置這個範圍裡是哪一個用途
第一個10.1.2.0網路位址，代表整個網段本身
第二個10.1.2.1預設閘道（default gateway，機器要出這個網段時的出口）
倒數第二個10.1.2.254Google 保留，供日後使用
最後一個10.1.2.255廣播位址（broadcast，一次送給網段內全部機器用的位址）

所以一個 /24 雖然有 256 個位址，實際能配出去的是 252 個出處。

這個數字每家雲端不一樣，換平台時不能沿用。AWS 保留的是五個：「每個子網路 CIDR 區塊中的前四個 IP 位址與最後一個 IP 位址無法供你使用」，多出來的那一個是保留給 VPC 的 DNS 伺服器出處。同樣一個 /24，在 Google Cloud 能配 252 個，在 AWS 只能配 251 個。

切太小會被擋

子網路的上下限：最小 /29

知道要保留四個之後，就看得懂為什麼有最小值。Google Cloud 的規定是：「最小的主要或次要範圍大小是八個 IPv4 位址。換句話說，你能使用的最長子網路遮罩是 /29。」出處

/29 是 8 個位址，扣掉保留的四個，只剩 4 個能配給機器。再往下切一級是 /30、只有 4 個位址，四個保留位址就把它佔滿了，一台機器都配不到——所以下限停在 /29 是有道理的。

另一端的上限則要注意官方的但書：同一頁寫「你能使用的最短子網路遮罩是 /4。然而，對於大多數 /4 的 IP 位址範圍，額外的驗證會阻止你建立這麼大的子網路」，並接著建議「為了把挑到無效子網路範圍的機會降到最低，我們建議你把子網路的最大尺寸限制在 /8」。所以實務上可以把 /8 當成上限來規劃，/4 是理論值出處。

規劃時的順序建議反過來想：先估這個子網路以後最多會放幾台機器，加上保留的四個，再往上找最接近的那個斜線數字。子網路建好之後要改範圍比一開始留寬一點麻煩得多。

沒有對外位址也要連得出去

Cloud NAT 讓私有的 VM 單向連外

為了安全，很多 VM 刻意不給它外部 IP 位址，外面就完全找不到它。但這種機器還是需要主動連出去——抓系統更新、呼叫外部的 API 都要。Cloud NAT 就是補這一段的代管服務。

官方把它的用途寫成一句話：「Cloud NAT 讓沒有外部 IPv4 位址的 Google Cloud 資源，能夠與網際網路上的 IPv4 目的地通訊。」做法則是「為前往網際網路、虛擬私有雲（VPC）網路、地端網路與其他雲端供應商網路的對外流量提供網路位址轉換」出處。（網路位址轉換＝NAT，出去的時候把來源的私有位址換成一個對外位址，回來的時候再換回去，第 3 課講 AWS 時已經出現過。）

兩個特性值得記住，因為都跟直覺不太一樣：

它不是一台你要自己顧的機器。官方寫「Cloud NAT 是一個分散式、軟體定義的代管服務。它並非基於代理虛擬機器或設備」——意思是你不會看到一台「NAT 主機」跑在那裡，也不需要替它擴充規格或做高可用，那些是 Google 在底層處理的。

它只放行回程，不放行主動連入。官方寫「Cloud NAT 只支援已建立連線的入站回應封包的位址轉換。它不允許未經請求的入站連線」——所以裝了 Cloud NAT 不等於把 VM 對外開了一個門，外面仍然連不進來。

拿第 3 課的 AWS 對照著看會比較好記：兩邊解決的是同一個問題，做法的分工不同。AWS 的 NAT Gateway 是你自己在某個公開子網路裡建出來的一個資源（見第 3 課）；Cloud NAT 則沒有對應的實體或虛擬機器可以指著看，官方明講它「並非基於代理虛擬機器或設備」。共同點是兩者都只讓內部主動往外，不讓外面主動連進來。

重點整理

  • CIDR 的斜線數字代表前面幾個位元固定；數字越大、範圍越小，/24 是 256 個位址。
  • 子網路遮罩（255.255.255.0）與 CIDR（/24）是同一件事的兩種寫法。
  • 路由表有多條都符合時，挑最精確的那條（最長前綴比對）；一樣精確才比優先順序值，數字小的贏。
  • Google Cloud 每個子網路保留四個位址：網路位址、預設閘道、倒數第二個、廣播位址；AWS 保留五個。
  • 子網路最小 /29（8 個位址、只剩 4 個可配），上限實務上抓 /8。
  • Cloud NAT 讓沒有外部位址的 VM 主動連外，是分散式的代管服務，而且不允許外面主動連進來。
