先拆解一台虛擬機

EC2 由哪些零件組成

元件角色白話比喻
AMI決定作業系統、開機磁碟配置等啟動內容裝機範本
Instance Type決定 vCPU、記憶體、網路與儲存能力硬體規格單
Instance Metadata提供執行個體 ID、主機名稱等執行環境資訊機器的身分證
ENI提供 IP、所屬 Subnet 與 Security Group 等網路身分虛擬網卡
Instance Profile把 IAM Role 交給這台 EC2 使用權限識別證的套子
EBS Volume透過網路連接的區塊儲存外接硬碟

IAM Role 不是「寫在主機設定裡」就會自動生效。EC2 是透過 Instance Profile（執行個體設定檔）取得角色憑證，應用程式才能在權限範圍內呼叫 AWS 服務，不必把長期金鑰塞進程式。

快，但不一定留得住

Instance Store 與 EBS

Instance Store（執行個體儲存）就在承載這台 EC2 的實體主機旁邊，適合暫存資料、快取，或是弄丟了可以重新產生的高速工作資料。它是短暫性儲存（Ephemeral Storage），不該拿來放唯一一份重要資料。

EBS（Elastic Block Store）是獨立於 EC2 生命週期的區塊儲存。EBS Volume 和掛它的 EC2 必須在同一個 AZ；執行個體停掉或換了底層主機，EBS 裡的資料還在。

最容易失手的動作是「把機器停下來，隔天再開起來」。AWS 官方寫得很直接：「當你啟動一個執行個體時，它通常會被移轉到新的底層主機電腦，並取得新的公有 IPv4 位址。」同一頁還有一則警告：「當你停止一個執行個體時，任何 Instance Store 磁碟上的資料都會被抹除。」出處

這兩句話其實是同一件事的兩面。Instance Store 之所以快，正是因為那些磁碟實體插在「現在承載你這台 EC2 的那台實體主機」上；機器一旦被搬到另一台實體主機，插在舊主機上的磁碟當然跟不過去。

所以重點不是「有沒有關機」，而是「是哪一種關機」。AWS 的資料保存頁把界線畫得很清楚：「Instance Store 磁碟上的資料即使在執行個體重新開機後仍然存在。但是，如果執行個體被停止、休眠或終止，資料就不會保留。」出處（休眠＝hibernate，把記憶體裡的內容先存下來再關機，下次開機接著跑。）

重新開機（reboot）：Instance Store 的資料留著。停止、休眠或終止：資料沒了出處。

這裡要補一個前提，免得把「停止」記成唯一的地雷：同一頁的表格把「變更執行個體類型」「AWS 排定的執行個體停止與退役」「自動復原」也列為資料不保留，而「重新開機」「系統重新開機」「電源中斷後重開」則是資料保留。判斷方式其實一致——只要這台機器有可能被換到另一台實體主機上，Instance Store 就留不住出處。

比較項目Instance StoreEBS
位置與實體主機緊密相連經 AWS 內部網路連接
生命週期執行個體一停止、休眠或終止就消失可以獨立於執行個體保留
適合放什麼快取、暫存、可重建的資料系統磁碟、資料檔與要長期保存的資料
備份方式要由應用程式自己另外複製可以建立 EBS Snapshot

EBS 會不會在 EC2 終止時一起被刪掉，還要看那個裝置的 Delete on termination 設定；不能因為它是 EBS 就假設一定留得下來。

效能不是只看一個數字

IOPS、I/O 大小與 Throughput

IOPS 是每秒能處理幾次輸入輸出操作；I/O 大小是每次操作搬多少資料；Throughput（吞吐量）則是每秒搬運的資料總量。

概念上的吞吐量 ≈ IOPS × 每次 I/O 大小

大量小型、隨機存取的工作通常重視 IOPS；次數少但每次搬很多資料的循序工作，則比較看吞吐量。實際效能還會同時受到 EBS 類型、磁碟設定、工作負載，以及這台 EC2 本身的 EBS 頻寬上限限制。

原筆記在 EC2 建立流程的 Storage 段寫「IOPS = Size(GB) * 500，所以 Size 8GB，IOPS 最高為 4000」——查證後這個算式是對的，講的是 gp3 的上限：AWS 官方寫的是 gp3 可以額外加購 IOPS，比例是每 GiB 最多 500 IOPS、整顆最多 80,000，所以 8 GiB 的上限正好是 500 × 8 = 4,000出處。要補的是兩件原筆記沒講的事：第一，那 4,000 是「最多可以買到」的數字，不是預設就有；gp3 不論容量大小，基準都先給你 3,000 IOPS，多出來的才要另外付錢。第二，這條算式只適用 gp3；老一代的 gp2 是另一套，效能隨容量走，每 GiB 3 IOPS、最低 100、最高 16,000，所以同樣 8 GiB 的 gp2 基準只有 100 IOPS。

磁碟規格像水管的一端，EC2 的 EBS 能力像另一端；水流速度會被比較窄的那一端卡住。

新硬碟不能直接當資料夾

建立檔案系統並掛載 EBS

把新的 EBS Volume 掛到 EC2，只代表作業系統看得到這個區塊裝置。如果它還沒有檔案系統，得先格式化，再掛載到某個目錄。

# 列出區塊裝置與完整路徑
lsblk -p

# 檢查裝置上是否已經有檔案系統
sudo file -s <device-path>

# 只對確認是空白的新磁碟建立 XFS；這個動作會清掉既有資料
sudo mkfs -t xfs <device-path>

# 建立掛載點並掛載
sudo mkdir -p /my_data
sudo mount <device-path> /my_data

# 檢查容量使用狀況
df -h

重新開機後要自動掛載，還得依裝置的 UUID 正確設定作業系統的掛載表。裝置名稱會因環境而異，不要把畫面上看到的名稱當成永遠不變。

備份不必每次整顆複製

EBS Snapshot 與復原

EBS Snapshot 是 EBS Volume 的區塊層級備份。後續的快照是漸進式備份（Incremental Backup）：概念上只加上前次快照之後變動的區塊，但每一個快照仍然都能單獨當成復原點使用。

快照是 Region 層級的資源，可以拿它在目標 AZ 建立新的 EBS Volume，再掛到那個 AZ 的 EC2。這也說明了「Volume 屬於 AZ、Snapshot 屬於 Region」的差別。

EBS Volume
→ 建立 Snapshot
→ 從 Snapshot 建立新的 Volume
→ 把新 Volume 掛到同一 AZ 的 EC2
→ 檢查檔案系統與原有資料

想拿到應用程式層級一致的備份，建立快照前通常還要考慮停止寫入、把檔案系統快取刷回磁碟，或改用資料庫本身的備份機制來協調。

把配置做成可重複使用的範本

AMI 裝了什麼

AMI（Amazon Machine Image）是啟動 EC2 的範本。它描述作業系統、根裝置與區塊裝置對應（Block Device Mapping），也能設定哪些帳號可以使用這個 AMI（Launch Permissions）。

如果你先在一台用 EBS 開機的 EC2 上裝好套件、建好檔案，再由這台執行個體建立 AMI，AWS 會用相關的磁碟快照把映像內容留下來。之後從這個 AMI 開的新機器，就會帶著同一套基礎環境。

基礎 AMI
→ 啟動 EC2
→ 安裝套件與建立檔案
→ 建立新 AMI 與相關 Snapshot
→ 由新 AMI 啟動多台一致的 EC2

建立映像時如果允許重新開機，通常比較容易拿到一致的磁碟狀態；選擇不重新開機的話，就要自己評估當下正在寫入的資料完不完整。

重點整理

  • AMI 管啟動範本，Instance Type 管運算規格，ENI 管網路身分。
  • EC2 透過 Instance Profile 使用 IAM Role，不該把長期憑證寫進主機或程式。
  • Instance Store 適合可重建的暫存資料；EBS 適合要留住的資料。
  • 停止再開機通常會把執行個體搬到另一台實體主機，Instance Store 的資料會被抹除；單純重新開機則留得住。
  • EBS Volume 屬於某個 AZ，EBS Snapshot 是 Region 層級的備份資源。
  • 最終的 EBS 效能同時受磁碟規格與 EC2 本身能力限制。
